1 What is it
- Front-end security is the set of rules that stop attackers from stealing tokens, running scripts in your pages, or tricking a logged-in user's browser into acting for them.
- Authentication here means proving who the user is when a browser app (SPA, single-page application) talks to your API. The standard way is OIDC (OpenID Connect, a login layer on top of OAuth 2.0) with the authorization code flow plus PKCE (Proof Key for Code Exchange, a one-time secret that protects the code exchange).
- Angular is the SPA framework. MSAL (Microsoft Authentication Library) is the Microsoft library that handles login against Entra ID.
- Legacy equivalent: ASP.NET MVC forms authentication with a server-set cookie, where the server owned the session and the browser held nothing sensitive.

2 Why needed
- A SPA runs entirely in the user's browser, so anything it holds can be read by any script that runs in the page.
- Without PKCE, a stolen authorization code can be redeemed by an attacker.
- Without XSS (cross-site scripting) prevention, one injected script can steal tokens and call your API as the user.
- Without CSRF (cross-site request forgery) defence, any site the user visits can make the browser send cookie-authenticated requests to your API.
- Without correct CORS (cross-origin resource sharing) settings, the API is either blocked for your own app or open to every origin.
- Without server-side authorization, a user can bypass the UI and call the API directly.

3 Before you read
- Browser same-origin policy: a page may only read responses from its own origin (scheme, host, port).
- Cookies versus headers: cookies are sent automatically by the browser, an Authorization header is added by your code.
- JWT (JSON Web Token): a signed token with claims such as user id, scopes and expiry.
- OAuth 2.0 roles: user, client app, authorization server (Entra ID), resource server (your API).

4 Features and core concepts

OIDC authorization code with PKCE
- Plain meaning: the app sends the user to Entra ID to sign in, gets back a short-lived code, then swaps the code for tokens using a secret it generated for this one login.
- Why it matters: a SPA cannot keep a client secret, so PKCE replaces it. The old implicit flow (tokens in the URL) is deprecated.
- Steps: generate code_verifier, send hash as code_challenge, receive code, send code plus code_verifier to the token endpoint.

MSAL for Angular
- Plain meaning: a library (msal-browser plus msal-angular) that runs the flow, caches tokens, renews them silently and attaches them to API calls.
- Why it matters: hand-written token code is where most security bugs appear.
- Worth memorizing: MsalInterceptor with a protectedResourceMap that lists which API URLs get which scopes, and MsalGuard for routes.

Token storage (memory vs cookie)
- Plain meaning: where the token lives in the browser. Options are JavaScript memory, sessionStorage, localStorage, or an HttpOnly cookie.
- Why it matters: localStorage and sessionStorage are readable by any script, so XSS steals tokens. Memory is safer but lost on refresh. An HttpOnly cookie cannot be read by JavaScript but brings CSRF risk.
- MSAL defaults to sessionStorage (verify current default). localStorage survives tabs but is the most exposed.

Refresh tokens
- Plain meaning: a long-lived token used to get new access tokens without another login.
- Why it matters: it is the most valuable thing to steal. For SPAs, Entra ID issues refresh tokens with a fixed lifetime (verify exact limit) and they are bound to the SPA origin.
- Rule: never store refresh tokens in a place your own code does not need to reach, and rely on MSAL's silent renewal.

XSS prevention
- Plain meaning: stop attacker-supplied text from running as script in your page.
- Why it matters: XSS defeats nearly every other protection.
- Angular escapes template bindings by default. Danger points are bypassSecurityTrustHtml, innerHTML with untrusted data, direct DOM access via ElementRef, and third-party scripts.

CSRF
- Plain meaning: a malicious site makes the user's browser send a request that carries the user's cookies.
- Why it matters: it only works when authentication is automatic (cookies). Bearer tokens in headers are not sent automatically, so a pure token SPA is largely immune.
- Defences: SameSite cookies, anti-forgery tokens, custom header checks. Angular's HttpClient reads an XSRF-TOKEN cookie and sends X-XSRF-TOKEN, which the server must validate.

CORS configuration in ASP.NET Core
- Plain meaning: the API tells browsers which other origins may call it.
- Why it matters: CORS is a browser rule, not API protection. A wrong setup either breaks your SPA or exposes the API.
- Worth memorizing: builder.Services.AddCors with WithOrigins("https://app.contoso.com"), then app.UseCors before UseAuthentication and UseAuthorization. Never combine AllowAnyOrigin with AllowCredentials.

CSP (Content Security Policy)
- Plain meaning: a response header listing where scripts, styles and connections may load from.
- Why it matters: it limits damage when XSS gets through.
- Start with default-src 'self' and add only what you need. Avoid unsafe-inline for scripts. Angular supports nonces (verify setup for your version).

BFF pattern for SPAs
- Plain meaning: a Backend For Frontend is a small server that does the OAuth flow, keeps the tokens, and gives the browser only an HttpOnly session cookie.
- Why it matters: no tokens ever reach browser JavaScript, which is the strongest answer to token theft. Current security guidance for browser apps favours it for sensitive apps.
- Cost: an extra server to run and secure, and CSRF defences become your job again.

Route guards are not real authorization
- Plain meaning: Angular guards hide screens. The user controls the browser, so they can edit the JavaScript or call the API directly.
- Why it matters: every real permission check must happen in the API (scopes, roles, policies, resource checks).

5 Core focus (exam and interview)
- Most asked: why PKCE, where to store tokens, XSS versus CSRF, why guards are not security, and when to use a BFF.
- Auth code plus PKCE is the recommended SPA flow. Implicit flow is not.
- Access tokens are short-lived (commonly about an hour, verify). Never put secrets in SPA code.
- XSS steals tokens. CSRF abuses cookies. Different attacks, different defences.
- CORS does not protect the API from non-browser clients.
- Access tokens go to the API, ID tokens are for the app only. Never send an ID token to an API.

6 Real-world use case
- Situation: a legacy MVC portal for insurance agents is being rebuilt as an Angular SPA calling an ASP.NET Core API, with Entra ID sign-in.
- Choice: MSAL Angular with auth code plus PKCE, API protected with JWT bearer validation and scope-based policies, strict CORS with one origin, CSP header, tokens in MSAL's default cache, no refresh token handling in custom code.
- Trade-off: simple and no extra server, but tokens live in the browser, so XSS discipline is mandatory.
- When not to use it: for apps handling highly sensitive data (payments, health), use a BFF so tokens stay on the server. Also avoid a pure SPA design if you cannot enforce a strict CSP and dependency control.

7 Interview lens
- Q: Why PKCE for a SPA? A: A SPA cannot hold a client secret, so PKCE binds the code to the client that started the login. A stolen code is useless without the verifier.
- Q: localStorage or cookie for tokens? A: localStorage is readable by XSS. An HttpOnly cookie is not, but needs CSRF protection. For high-risk apps, keep tokens server-side in a BFF.
- Q: Do bearer tokens need CSRF protection? A: Not in the usual sense, since the browser does not attach them automatically. Cookie-based sessions do.
- Q: Is an Angular route guard enough to secure an admin page? A: No. It only controls the UI. The API must check scopes and roles on every call.

8 Common mistakes
- Using AllowAnyOrigin with credentials. Shows up as a security finding or a blocked request. Fix: list exact origins.
- Calling bypassSecurityTrustHtml on user content. Shows up as stored XSS. Fix: sanitize or render as text.
- Storing tokens in localStorage by hand. Shows up as account takeover after any XSS. Fix: use MSAL's cache or a BFF.
- Relying only on guards. Shows up as users reaching data by calling the API. Fix: authorize in the API.
- Sending the ID token to the API. Shows up as validation failures or wrong audience. Fix: request an access token for the API scope.
- Putting UseCors after authorization. Shows up as preflight requests failing with 401. Fix: correct middleware order.

9 Mental model
- Browser (untrusted) <-> Entra ID (login, issues tokens) and Browser <-> API (trusted, checks everything).
- Treat the browser as a hostile room: anything you hand it can be read, so the API must verify every request itself.
- BFF variant: Browser (cookie only) -> BFF (holds tokens) -> API.

10 Mini lab (30 to 40 minutes, Entra free tier)
- Steps:
- 1. In the Entra admin centre, register an app, platform Single-page application, redirect URI http://localhost:4200.
- 2. Register a second app for the API and expose a scope such as access_as_user.
- 3. Create an Angular app and add @azure/msal-browser and @azure/msal-angular. Configure clientId, authority and redirectUri.
- 4. Add MsalInterceptor with a protectedResourceMap pointing to your API URL and scope.
- 5. Create an ASP.NET Core minimal API with AddMicrosoftIdentityWebApi, a CORS policy for http://localhost:4200, and RequireAuthorization.
- 6. Sign in and call the API. In browser DevTools Application tab, look at where MSAL stored tokens. Then try calling the API without a token.
- Expected result: signed-in call returns 200, the no-token call returns 401, and you can see tokens in browser storage, which shows why XSS matters.
- Clean-up: delete both app registrations and remove the local projects.

11 Revision summary
- Use auth code plus PKCE for SPAs. Implicit flow is out.
- MSAL handles login, renewal and token attachment. Do not hand-roll it.
- XSS steals tokens, CSRF abuses cookies.
- localStorage is script-readable. HttpOnly cookies are not.
- CORS is browser-only protection, so keep the origin list exact.
- CSP limits the damage from XSS.
- A BFF keeps tokens off the browser entirely.
- Guards hide UI, only the API enforces authorization.
