1 What is it
- A front-end architecture note for a tech lead, not a coding tutorial. It covers how a front-end codebase is organized, shared, built, monitored and kept healthy as the team and app grow.
- Plain terms: it is the set of agreed rules for folders, shared code, API contracts, builds, errors, releases and upgrades, so ten developers do not build ten different apps.
- Legacy equivalent: the MVC solution layout with Scripts and Views folders, bundling in BundleConfig, jQuery plugins copied across projects, and Web.config transforms for environment settings.

2 Why needed
- Without structure, a front end becomes one large folder where every change touches everything.
- Shared code gets copied between apps, and fixes are applied in some copies and missed in others.
- Hand-written API calls drift from the real backend and break at runtime.
- Errors in the browser are invisible, because nobody sees what the user saw.
- Outdated packages pile up until an upgrade becomes a rewrite.

4 Features and core concepts
- Feature folder structure. Group code by business feature (orders, billing), not by type (all components, all services). Why it matters: a change to one feature stays inside one folder, and teams can own folders.
- Shared libraries. Common UI parts, helpers and types live in one internal package used by all apps. Why it matters: one fix reaches every app. Risk: a shared library becomes a dumping ground, so keep it small and versioned.
- Monorepo (Nx) awareness. One repository holds several apps and libraries, and Nx builds and tests only what a change affects. Why it matters: shared code and apps change together in one commit. Cost: tooling and repository size need care.
- API client generation from OpenAPI. A tool reads the backend's OpenAPI file and generates typed TypeScript clients. Why it matters: a backend change that breaks the front end fails at build time, not in production. Command worth memorizing: npx openapi-generator-cli generate -i openapi.json -g typescript-angular -o src/api (verify the generator name and options).
- Error handling and telemetry (Application Insights JS). A global error handler and an SDK send browser errors, page timings and API failures to Azure. Why it matters: you learn about user-side failures before users complain. Attach a correlation ID so a browser error links to the backend trace (verify SDK package name and setup).
- Feature flags. A switch in config turns a feature on or off without redeploying. Why it matters: you can merge unfinished work safely and roll back by flipping a flag. Cost: old flags must be removed.
- Environment config. API URLs and keys differ per environment. In Angular, avoid baking values into the build. Prefer loading a config file at startup so one build artifact runs in every environment. Why it matters: build once, deploy many. Never put secrets in front-end config, because the browser can read everything.
- CI for front end (lint, test, build, audit). Each pull request runs lint, unit tests, a production build and a dependency audit (npm audit). Why it matters: bad code is blocked before review.
- Dependency upgrade policy. A written rule, for example: patch updates weekly through an automated bot, minor updates monthly, major framework versions within a set time after release (verify Angular's current support window). Why it matters: small steady upgrades cost far less than one big jump.
- Design systems. A shared set of components, colors, spacing and rules (Angular Material or a custom library, documented in Storybook). Why it matters: consistent screens and faster delivery.
- Accessibility (WCAG basics). Keyboard use, labels, contrast, focus order, screen reader support. Why it matters: it is a legal and client requirement in many contracts. Aim for WCAG 2.1 or 2.2 level AA (verify the version a client requires).
- i18n. Text and formats are kept out of code so the app supports more languages and regions. Why it matters: adding a language later is cheap only if you planned for it. Angular has built-in i18n, and runtime libraries like Transloco exist.

5 Core focus (exam and interview)
- Asked most: how to structure a large Angular app, how to share code across apps, and why generate API clients.
- Asked most: how one build runs in many environments, and where secrets must never live.
- Know the trade-off of a monorepo versus separate repositories.
- Know that front-end telemetry needs sampling and care about personal data.
- Know that route guards and hidden buttons are not security. The backend must enforce access.
- Remember: aim for WCAG AA, run npm audit in CI, and use a lockfile for repeatable builds.

6 Real-world use case
- Situation: a client has three Angular apps (customer portal, admin portal, partner portal) built by different teams. Login, tables and API calls are copied in each. A backend field rename broke two apps in production.
- Choice made: move to an Nx monorepo with feature folders, a shared UI library, a shared auth library and clients generated from the backend's OpenAPI file in CI. Add Application Insights JS with a correlation ID, a runtime config file, and a pipeline running lint, test, build and audit.
- Trade-off: the setup takes weeks, and teams must follow one upgrade rhythm and review shared library changes carefully.
- When NOT to use it: a single small app with one team. A simple feature-folder layout and a CI pipeline are enough, and a monorepo would be overhead.

7 Interview lens
- Q: Why feature folders over type folders?
  A: A feature change stays in one place and a team can own it. Type folders scatter one change across many folders.
- Q: Why generate API clients instead of writing them?
  A: Types come from the contract, so a breaking backend change fails at build time. It also removes repetitive hand-written code.
- Q: How do you run one build in dev, test and production?
  A: Load environment values from a config file at startup, not at build time. The same artifact is promoted through environments, and secrets stay on the server.
- Q: How do you keep a large front end from rotting?
  A: Automated small dependency updates, CI gates for lint, tests and audit, and a written upgrade policy. Remove old feature flags on a schedule.

8 Common mistakes
- Shared library grows into a dumping ground. Shows up as every app breaking on each release. Fix: strict ownership, small scope, semantic versioning.
- Secrets placed in environment files. Shows up as keys visible in browser dev tools. Fix: keep secrets on the backend and use a BFF if needed.
- Generated client edited by hand. Shows up as changes lost on the next generation. Fix: never edit generated files, and regenerate in CI.
- Telemetry sends everything. Shows up as high Azure cost and personal data in logs. Fix: sampling, filters, and no personal data in events.
- Feature flags never cleaned up. Shows up as dead code paths nobody understands. Fix: an owner and removal date per flag.
- Upgrades postponed for years. Shows up as a forced, risky major migration. Fix: scheduled small upgrades.

9 Mental model
- Think of a city plan, not a building.

  apps (thin) -> features (business) -> shared libs (UI, auth, api clients) -> generated contract (OpenAPI)

  CI is the gate at every road in. Telemetry is the camera feed back out. Flags and config are the switches.

10 Mini lab
- Time: about 35 minutes. Tools: Node.js (LTS, verify), npm, a terminal.
- Step 1: run npx create-nx-workspace@latest lab-ws, choose an Angular preset and a standalone app named portal (verify the prompts).
- Step 2: generate a library with the Nx Angular library generator (npx nx g @nx/angular:library shared-ui) (verify the generator name).
- Step 3: import a component from shared-ui into portal and run npx nx serve portal. Expected result: the page shows the shared component.
- Step 4: run npx nx affected -t lint test build after changing only shared-ui. Expected result: Nx runs tasks for shared-ui and portal.
- Step 5: add a public/config.json with an apiUrl, load it with fetch in main.ts before bootstrap, and show the value on screen. Expected result: changing the file changes the value without rebuilding.
- Step 6: run npm audit and note the output.
- Clean-up: delete the lab-ws folder.

11 Revision summary
- Organize by feature, not by file type.
- Shared libraries must be small, owned and versioned.
- Generate API clients from OpenAPI so contract breaks fail at build time.
- Build once, deploy many: load environment config at runtime, and never place secrets in front-end config.
- Send browser errors to Application Insights with a correlation ID, with sampling and no personal data.
- CI on every pull request: lint, test, build, audit.
- Upgrade dependencies in small, scheduled steps.
- Target WCAG AA and plan i18n early.
