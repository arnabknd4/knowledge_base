1 What is it

TypeScript is JavaScript with a type system added on top. You write .ts files, the compiler checks the types, then it removes them and outputs plain JavaScript. The types exist only at compile time and are gone at runtime.

Legacy equivalent: the TypeScript you already used with MVC and jQuery, now treated as an architecture tool with strict mode, generics and typed API contracts.

2 Why needed

- JavaScript finds type errors at runtime, in front of users. TypeScript finds them while you type.
- Large Angular code bases need safe refactoring. Rename a field and the compiler lists every broken usage.
- API shapes become shared contracts. Without types, a backend DTO change breaks the UI silently.

4 Features and core concepts

K topic, so basics are skipped and the focus is on gaps and depth.

- Types vs interfaces: both describe object shapes. Interfaces can be extended and merged by redeclaration. Types can also name unions, tuples and mapped types. Rule: interface for public object contracts, type for unions and compositions.
- Generics: reusable code that keeps the type, for example function first<T>(a: T[]): T. Constraints narrow them: <T extends { id: number }>. They matter because they replace any in reusable code.
- Unions and intersections: A | B means one of them. A & B means both combined. Unions model states such as loading, success and error.
- Narrowing and type guards: the compiler narrows a union after typeof, instanceof, in, or an equality check. A user-defined guard is function isErr(x: Result): x is Err. A discriminated union (a shared literal field such as kind) gives exhaustive checking with a never default case.
- Utility types: Partial, Required, Readonly, Pick, Omit, Record, ReturnType, NonNullable, Awaited. They derive new types from existing ones, so you do not duplicate DTOs.
- Strict mode: "strict": true turns on strictNullChecks, noImplicitAny, strictFunctionTypes, strictPropertyInitialization and more. Add noUncheckedIndexedAccess and exactOptionalPropertyTypes for extra safety. Angular new projects enable strict by default (verify).
- tsconfig: target, module, moduleResolution, lib, paths, skipLibCheck, isolatedModules. Use extends to share a base config across a monorepo.
- Declaration files: .d.ts files describe types for JavaScript code. They come from @types/* packages or declare module blocks.
- Mapped and conditional types basics: { [K in keyof T]: ... } transforms every key. T extends U ? X : Y picks a type by condition. They are the base of the utility types.

Worth memorizing:

- type ApiResult<T> = { kind: "ok"; data: T } | { kind: "err"; message: string };
- type Dto = Pick<User, "id" | "name">;
- type ReadonlyAll<T> = { readonly [K in keyof T]: T[K] };

5 Core focus (exam and interview)

- unknown vs any: unknown forces a check before use, any switches checking off.
- Types are erased at runtime, so they cannot validate incoming JSON. Use a runtime validator such as zod at API boundaries.
- Structural typing: compatibility depends on shape, not on names.
- enum vs union of string literals: literal unions are lighter and tree-shake better.
- as casts are assertions, not conversions. Prefer guards and satisfies.
- interface merging and declaration merging.
- Excess property checks apply only to object literals.

6 Real-world use case

Situation: an Angular front end calls a .NET API and the DTOs drift. Production bugs appear after backend releases.

Choice: generate TypeScript types or an API client from the OpenAPI spec (see 3.07 and 2.06). Enable strict mode. Model screen state as a discriminated union. Validate only untrusted payloads at runtime.

Trade-off: strict mode on an old code base produces hundreds of errors. Migrate folder by folder, or use a separate stricter tsconfig for new code.

When not to use heavy typing: throwaway scripts, and complex conditional types that nobody on the team can read. Readability beats cleverness.

7 Interview lens

- Q: interface or type? A: Interfaces for extendable object contracts, types for unions, tuples and mapped types. In most cases either works, so pick one team convention.
- Q: any vs unknown? A: any disables checks. unknown is the safe top type and requires narrowing before use.
- Q: Do TypeScript types protect against bad API data? A: No. Types are erased at compile time. Validate at the boundary with a runtime schema.
- Q: How do you make a switch exhaustive? A: Use a discriminated union and assign the value to never in the default branch. Adding a new case then fails compilation.

8 Common mistakes

- Using any to silence errors. Bugs return at runtime. Fix: unknown plus guards.
- Trusting casts on JSON. Shows up as undefined errors in production. Fix: runtime validation.
- Strict mode left off. Null reference errors appear. Fix: enable it and migrate gradually.
- Duplicating DTO types by hand. They drift from the backend. Fix: generate them or derive with utility types.
- Deep conditional types. Slow builds and unreadable errors. Fix: keep types simple.

9 Mental model

Source (.ts) -> compiler checks types -> emits plain JavaScript -> types are gone at runtime.

Types are a compile-time safety net over JavaScript. They do not exist at runtime.

11 Revision summary

- TypeScript types are erased at runtime.
- Interface for contracts, type for unions and compositions.
- unknown is safe, any is not.
- Narrow unions with typeof, in, instanceof and discriminant fields.
- Utility types derive types: Pick, Omit, Partial, Record.
- strict true plus noUncheckedIndexedAccess is the baseline.
- Validate API data at runtime, not only with types.
- .d.ts files describe JavaScript libraries.
