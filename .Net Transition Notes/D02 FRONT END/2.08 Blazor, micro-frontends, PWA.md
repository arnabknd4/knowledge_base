2.08 Blazor, micro-frontends, PWA is an optional (O) topic, so this is a SHORT note: sections 1, 4, 6 and 11.

1 What is it

- Blazor lets you build browser UI in C# and Razor instead of JavaScript. Micro-frontends split one large web UI into independently built and deployed pieces. A PWA (progressive web app) is a website that can be installed, works offline and receives push messages.
- Legacy equivalent: Razor views in MVC for server-rendered pages, jQuery and TypeScript bundles for client logic, and one big deployment of the whole web project.

4 Features and core concepts

- Blazor Server: components run on the server and UI changes travel to the browser over a SignalR (persistent real-time connection) link. Why it matters: small download and fast start, but every user holds a live connection, so scale and network latency are the cost.
- Blazor WebAssembly: the .NET runtime and your code run inside the browser using WebAssembly (a binary format browsers can run). Why it matters: works offline and needs no server connection per click, but the first download is larger.
- Blazor Web App render modes (verify): modern .NET lets one app mix static server rendering, interactive server and interactive WebAssembly per component. Why it matters: you pick the cheapest mode for each page instead of one mode for everything.
- Module Federation: a webpack feature where one app loads code from another app's URL at run time. Why it matters: it is the usual way to compose Angular or React micro-frontends without rebuilding a shell. Angular teams use it through Native Federation (verify).
- Micro-frontends: each team owns a vertical slice (UI plus API) and deploys on its own. Why it matters: it gives independent releases for large teams, but adds shared-dependency, styling and routing problems. Do not use it for a small team.
- SSR (server-side rendering): the server sends ready HTML so the page shows fast and search engines read it. SSG (static site generation): pages are built into HTML at build time and served from a CDN. Why it matters: SSR helps first load and SEO, SSG is cheapest for content that rarely changes.
- PWA basics: a web manifest (name, icons, start URL), a service worker (a background script that caches files and handles offline requests) and HTTPS. Why it matters: gives install-to-home-screen and offline use without an app store.
- Setting worth memorizing: Blazor WebAssembly project template with PWA support is created using the --pwa option on dotnet new blazorwasm (verify exact template name for your SDK).

6 Real-world use case

- Situation: an internal claims portal for a client has an old MVC site and a new Angular front end. A new admin module is needed by a separate team.
- Choice: build the admin module as a Blazor Server app, because the team knows C# and the users are on the office network. Host it beside the Angular app behind YARP (reverse proxy) so both appear under one domain.
- Trade-off: you reuse C# skills and share DTO classes, but you now maintain two UI stacks and a SignalR connection per user.
- When NOT to use it: public sites with heavy traffic (Blazor Server connections do not scale cheaply), or when the main front end is already Angular and the team is strong in it. Skip micro-frontends if fewer than about three teams share the UI.

11 Revision summary

- Blazor Server runs on the server over SignalR; Blazor WebAssembly runs in the browser.
- WebAssembly needs a bigger first download but supports offline use.
- Modern Blazor lets you choose a render mode per component (verify).
- Module Federation loads another app's code at run time.
- Micro-frontends solve team independence, not performance.
- SSR helps first paint and SEO; SSG serves prebuilt HTML from a CDN.
- A PWA needs a manifest, a service worker and HTTPS.
