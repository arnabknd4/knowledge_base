1 What is it

- The browser is the program that runs your front end. It turns HTML, CSS and JavaScript into pixels, and it also enforces many security and caching rules.
- The DOM (Document Object Model) is the in-memory tree of the page that JavaScript reads and changes.
- This topic covers how pages render, how the browser caches, and the browser security rules (CORS, CSP, cookie flags) that decide whether your API calls work.
- Legacy equivalent: jQuery DOM manipulation, ASP.NET MVC Razor pages, Cache-Control headers set in IIS web.config, and the CORS errors you fought when calling MVC or Web API from another site.

---

2 Why needed

- Most "the API works in Postman but fails in the browser" bugs are browser rules: CORS, cookies, CSP.
- Slow pages are usually caused by blocking resources, layout thrashing or missing caching, not by the server.
- Without cookie flags and CSP, a single XSS bug can leak sessions.
- An architect must decide cache headers, security headers and CORS policy. That needs this knowledge.

4 Features and core concepts

- DOM: a tree of nodes the browser builds from HTML. JavaScript edits it. Why it matters: every UI framework (Angular, React) is a smarter way to update this tree.
- Critical rendering path: the steps from bytes to pixels: parse HTML into DOM, parse CSS into CSSOM, combine into the render tree, layout (sizes and positions), paint, composite. Why it matters: CSS and synchronous JavaScript block rendering, so they decide first-paint speed. Tip: use defer on scripts and keep critical CSS small.
- Reflow (layout) and repaint: reflow recalculates positions and sizes. Repaint redraws pixels. Reflow is more expensive. Why it matters: reading layout values (offsetHeight) then writing styles in a loop forces repeated reflows (layout thrashing). Batch reads, then writes. Animate transform and opacity, which avoid reflow.
- Browser HTTP caching: the browser stores responses and reuses them based on Cache-Control (max-age, no-cache, no-store), ETag and Last-Modified. Why it matters: it removes network calls entirely. Fingerprinted file names (app.3f9a.js) allow very long max-age. Memorize: Cache-Control: public, max-age=31536000, immutable for hashed assets; no-cache for index.html.
- Service workers (awareness): a script that sits between page and network. It enables offline use, custom caching and push. Why it matters: it is the base of PWAs, and a buggy one can serve stale apps for weeks. Needs HTTPS.
- CORS (Cross-Origin Resource Sharing): the server tells the browser which other origins may read its responses, using Access-Control-Allow-Origin and related headers. Why it matters: the browser enforces it, not the server. Non-simple requests (custom headers, JSON content type, PUT, DELETE) trigger a preflight OPTIONS request first. Credentials need an exact origin, never *. Memorize ASP.NET Core: builder.Services.AddCors(...) then app.UseCors() placed after routing and before auth.
- CSP (Content Security Policy): a response header listing where scripts, styles, images and frames may load from. Why it matters: it limits damage from XSS. Example: Content-Security-Policy: default-src 'self'; script-src 'self'. Avoid 'unsafe-inline'. Report-Only mode lets you test first.
- Cookie flags: HttpOnly hides the cookie from JavaScript (blocks theft via XSS). Secure sends it only over HTTPS. SameSite (Strict, Lax, None) controls sending on cross-site requests (CSRF defence). SameSite=None requires Secure. Why it matters: these three settings decide most session security.
- DevTools network and performance panels: Network shows each request, timing, size, cache status and headers. Performance records main-thread work, layout and paint. Why it matters: it is the first tool for slow-page and CORS debugging. Useful: Disable cache, throttling, Lighthouse tab.

5 Core focus (exam and interview)

- Most asked: what is CORS and why does preflight happen; why Allow-Origin * cannot be used with credentials.
- Same-origin policy blocks reading cross-origin responses. CORS relaxes it. CORS does not stop the request reaching the server and is not authentication.
- Cookie flag trio: HttpOnly, Secure, SameSite. Know what each stops (XSS theft, sniffing, CSRF).
- no-cache means revalidate before use, not "do not store". no-store means do not store at all.
- Reflow vs repaint, and layout thrashing.
- CSP stops inline script execution unless allowed by nonce or hash.
- Defaults: browsers treat cookies without SameSite as Lax (verify for your browser targets).

6 Real-world use case

- Situation: Angular app on https://app.client.com calls an ASP.NET Core API on https://api.client.com, hosted on Azure App Service. Calls fail with a CORS error, and the team wants cookie-based login.
- Choice: configure a named CORS policy with the exact app origin, AllowCredentials, and only the needed headers and methods. Set auth cookies HttpOnly, Secure, SameSite=None (cross-site) or put both under one domain and use Lax. Add CSP and HSTS. Serve hashed assets with one-year caching and index.html with no-cache through Azure Front Door.
- Trade-off: SameSite=None widens CSRF exposure, so add anti-forgery tokens. Long caching needs a reliable build fingerprint process.
- When NOT to use: do not enable permissive CORS (AllowAnyOrigin) for an API that uses cookies. Do not cache authenticated responses on a shared CDN without Vary or private.

7 Interview lens

- Q: Why do I see a CORS error in the browser but not in Postman? A: Postman does not enforce the same-origin policy. The browser blocks reading the response unless the server sends the right CORS headers.
- Q: What is a preflight request? A: An automatic OPTIONS request the browser sends before a non-simple cross-origin request. The server must answer with allowed origin, methods and headers.
- Q: How do you protect a session cookie? A: HttpOnly stops script access, Secure forces HTTPS, SameSite limits cross-site sending. Add CSP to reduce XSS risk.
- Q: How do you make a page load faster? A: Cut render-blocking CSS and JS, defer scripts, cache hashed assets for a long time, compress, and avoid layout thrashing. Verify with Lighthouse and the Performance panel.

8 Common mistakes

- Using AllowAnyOrigin together with AllowCredentials. It is rejected by the framework or the browser. Fix: list exact origins.
- UseCors placed after UseAuthorization. Preflight gets 401 and shows as CORS error. Fix: put UseCors before auth.
- Caching index.html for a year. Users run old code after release. Fix: no-cache on index.html, long cache only on hashed files.
- Storing tokens in localStorage. Any XSS steals them. Fix: HttpOnly cookies or in-memory tokens (see 2.05).
- Writing 'unsafe-inline' into CSP to make it work. It cancels the protection. Fix: nonces or hashes.
- Forgetting Vary: Origin, so a CDN serves one origin's CORS headers to another.

---

9 Mental model

- The browser is a strict security guard plus a renderer:

  bytes -> DOM + CSSOM -> render tree -> layout -> paint -> composite
  Every request passes the guard: same-origin policy -> CORS headers -> CSP -> cookie flags -> cache rules.

10 Mini lab (30 minutes, local only)

- Step 1: create two tiny apps. Run a minimal API with dotnet new web on http://localhost:5000 with one endpoint /hello. Serve a static index.html on http://localhost:8080 (python -m http.server 8080).
- Step 2: in index.html call fetch('http://localhost:5000/hello') and log the result. Open it in the browser with DevTools Network open.
- Step 3: you should see a CORS error in Console and the request marked blocked.
- Step 4: add AddCors with a policy allowing http://localhost:8080, call app.UseCors() before the endpoint. Reload. The call now succeeds. Note the Access-Control-Allow-Origin header.
- Step 5: add a custom header (headers: {'X-Test':'1'}) in fetch. See the OPTIONS preflight appear in Network. Allow the header in the policy.
- Step 6: set a cookie from the API with HttpOnly, Secure and SameSite flags using Response.Cookies.Append. Check Application tab, then try reading document.cookie and confirm it is hidden.
- Step 7: add the header Content-Security-Policy: default-src 'self' to index.html responses and see an inline script blocked.
- Clean-up: stop both servers and delete the two folders.

11 Revision summary

- Browser builds DOM + CSSOM, then render tree, layout, paint, composite.
- CSS and synchronous JS block rendering. Use defer.
- Reflow costs more than repaint. Batch DOM reads then writes.
- Hashed assets: long max-age and immutable. index.html: no-cache.
- CORS is enforced by the browser. Preflight is an OPTIONS request. Credentials need an exact origin.
- UseCors goes before auth in ASP.NET Core.
- Cookies: HttpOnly (XSS), Secure (HTTPS only), SameSite (CSRF). SameSite=None needs Secure.
- CSP limits script sources. Avoid 'unsafe-inline'.
