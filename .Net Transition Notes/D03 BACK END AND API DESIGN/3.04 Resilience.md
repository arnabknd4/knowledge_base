3.04 Resilience

1 What is it
- Resilience means your service keeps working, or fails in a controlled way, when something it depends on is slow or broken.
- The tools are timeouts, retries, circuit breakers, bulkheads, fallbacks, rate limits, idempotency keys, health checks and graceful shutdown.
- Legacy equivalent: try/catch with a hand-written retry loop around WCF or ADO.NET calls, plus IIS app pool recycling and Windows Server failover.

2 Why needed
- In the cloud, network calls fail often for short moments. Azure services throttle you. Dependencies slow down.
- Without resilience, one slow dependency holds threads, threads run out, and the whole API goes down. This is a cascading failure.
- Blind retries make it worse. Many clients retrying at once can crush a recovering service.

4 Features and core concepts
- Timeout: a limit on how long you wait. Why: a call with no limit can hang forever and hold a thread.
- Retry with exponential backoff and jitter: try again after waits that grow (1s, 2s, 4s) with a random offset. Why: it handles brief faults without all clients retrying together.
- Circuit breaker: after many failures, stop calling the dependency for a while, like a fuse. States: closed (normal), open (blocked), half-open (test with a few calls). Why: it gives the dependency time to recover and makes your callers fail fast.
- Bulkhead: limit how many concurrent calls go to one dependency, like ship compartments. Why: one slow dependency cannot use up all your threads.
- Fallback: a backup answer when the call fails, such as cached data or a default value. Why: the user sees reduced service instead of an error.
- Rate limiting and load shedding: reject extra requests early (429 or 503) to protect yourself. Why: it is better to serve most users than to fail everyone.
- Idempotency key: a unique ID sent with a request so a repeated request does not repeat the effect. Why: retries are safe for payments and orders.
- Deduplication: the receiver ignores a message it already processed. Why: queues deliver at least once, so duplicates happen.
- Graceful degradation: turn off non-essential features under stress. Why: the core flow survives.
- Health checks: liveness means the process is alive. Readiness means it can take traffic. Startup means it has finished booting. Why: the platform restarts or stops routing based on these.
- Graceful shutdown: on SIGTERM, stop taking new work, finish current work, then exit. Why: deployments and scale-in do not drop requests.
- Code worth memorizing (verify package names for your .NET version):
  builder.Services.AddHttpClient<OrdersClient>().AddStandardResilienceHandler();
  builder.Services.AddHealthChecks();
  app.MapHealthChecks("/health/ready");

5 Core focus (exam and interview)
- Most asked: retry vs circuit breaker, why jitter, why idempotency is needed before retries, liveness vs readiness.
- Retry only transient faults (timeouts, 5xx, 429). Never retry 400 or 401.
- Honor the Retry-After header on 429.
- Retry only idempotent operations, or add an idempotency key.
- Order of policies matters. Common order outside to inside: total timeout, retry, circuit breaker, per-attempt timeout.
- Library: Microsoft.Extensions.Http.Resilience, built on Polly v8 (verify).
- Kubernetes: a failing liveness probe restarts the pod. A failing readiness probe removes it from the service. Keep the liveness probe light and do not check dependencies in it.
- Kubernetes default termination grace period is 30 seconds (verify).

6 Real-world use case
- Situation: an order API calls a payment provider and an inventory service on Azure App Service. Inventory is slow during sales.
- Choice: typed HttpClient with the standard resilience handler: 3 retries with jitter, a circuit breaker, a 5-second per-attempt timeout. Payments use an idempotency key. Inventory has a fallback to a cached stock level. A bulkhead limits inventory calls to 20 at once.
- Trade-off: more moving parts and more settings to tune. A fallback can show stale data. Retries add latency.
- When NOT to use: do not retry non-idempotent calls without a key. Do not add a circuit breaker to a single local in-process call. For long outages, use a queue and background processing instead of retrying inline.

7 Interview lens
- Q: Why add jitter to retries?
  A: Without it, all clients retry at the same moments and create traffic spikes. Random offsets spread the load.
- Q: Circuit breaker vs retry?
  A: Retry handles short faults by trying again. A circuit breaker stops calls during longer faults. Use both together.
- Q: Liveness vs readiness?
  A: Liveness asks whether to restart the process. Readiness asks whether to send it traffic.
- Q: How do you make a payment call safe to retry?
  A: Send an idempotency key. The server stores the result for that key and returns it on repeats.

8 Common mistakes
- Retrying with no limit: a retry storm hits an already weak service. Fix: cap attempts, add backoff, jitter and a breaker.
- No timeout on HttpClient: threads hang and the app stalls. Fix: set per-attempt and total timeouts.
- Retrying inside every layer: 3 retries at each of 3 layers means 27 calls. Fix: retry at one layer only.
- Dependency checks in the liveness probe: a database blip restarts every pod. Fix: put dependency checks in readiness only.
- Retrying non-idempotent POST: duplicate orders. Fix: idempotency keys.
- Ignoring SIGTERM: in-flight requests are cut off on deploy. Fix: use the host shutdown timeout and honor CancellationToken.

9 Mental model
- Think of electrical safety in a building.
  request -> [timeout] -> [retry] -> [breaker] -> [bulkhead] -> dependency
  Timeout is the stopwatch. Retry is pressing the button again. Breaker is the fuse. Bulkhead is the separate circuit per room. Fallback is the emergency light.

10 Mini lab (30 to 40 minutes, local only)
- Steps:
  - Create two projects: dotnet new webapi -n FlakyApi and dotnet new webapi -n Caller.
  - In FlakyApi, add a minimal endpoint /data that returns 500 for the first 2 calls out of every 3, and otherwise 200 (use a static counter).
  - In Caller, add package Microsoft.Extensions.Http.Resilience and register a typed client with AddStandardResilienceHandler. Set the base address to FlakyApi.
  - Add an endpoint in Caller that calls /data and returns the result.
  - Run both apps. Call the Caller endpoint several times. Add a log line in FlakyApi for each hit.
  - Then stop FlakyApi and call Caller about 15 times fast.
- Expected result: with FlakyApi running, one call to Caller causes 2 or 3 hits in the FlakyApi log and then succeeds. With FlakyApi stopped, early calls are slow, then the circuit opens and calls fail immediately with a BrokenCircuitException (verify exact exception name).
- Clean-up: stop both apps and delete both folders.

11 Revision summary
- Timeout first: no call without a limit.
- Retry only transient faults, with exponential backoff and jitter.
- Retry only idempotent calls, or use an idempotency key.
- Circuit breaker states: closed, open, half-open.
- Bulkhead limits concurrency per dependency.
- Liveness restarts, readiness removes from traffic, startup protects slow boot.
- Retry at one layer only, to avoid multiplying calls.
- Graceful shutdown: stop new work, finish current work, exit on SIGTERM.
