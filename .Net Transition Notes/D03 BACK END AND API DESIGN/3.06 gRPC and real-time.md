1 What is it
- gRPC is a way for services to call each other's functions over the network using a compact binary format, defined by a contract file.
- Real-time means the server can push data to clients as it happens, instead of the client asking again and again.
- This topic covers gRPC, SignalR, WebSockets and server-sent events, plus a brief look at GraphQL.
- Legacy equivalent: WCF for gRPC (contract-first, binary, typed proxies); SignalR classic on ASP.NET for real-time; AJAX polling for what real-time replaces.

4 Features and core concepts
- Protobuf (Protocol Buffers): a contract file (.proto) that defines messages and services. Code is generated from it for C# and other languages. Why it matters: small binary payloads and a strict, versioned contract.
- Unary call: one request, one response, like a normal REST call. Why it matters: it is the default and covers most service-to-service calls.
- Streaming: server streaming (one request, many responses), client streaming (many requests, one response) and bidirectional streaming (both sides send freely). Why it matters: it suits feeds, uploads and long-running updates without repeated calls.
- Deadlines: an absolute time limit on a call that travels with the request across services. Why it matters: it stops slow calls from piling up and ties into resilience. Prefer deadlines over open-ended timeouts.
- gRPC vs REST: gRPC is faster, strongly typed and streaming-capable, but needs HTTP/2, has weaker browser support and is harder to inspect by hand. REST is simpler, cacheable and universal. Why it matters: gRPC suits internal service-to-service traffic, REST suits public APIs.
- gRPC-Web: a variant that lets browsers call gRPC services through a proxy or middleware. Why it matters: browsers cannot use full gRPC directly. It does not support client or bidirectional streaming (verify).
- SignalR: the ASP.NET Core library for real-time server-to-client messaging. It picks a transport automatically: WebSockets, then server-sent events, then long polling. It uses hubs, groups and users to target messages. Why it matters: it is the standard .NET answer for live dashboards, notifications and chat. Scaling across several servers needs a backplane (Redis) or Azure SignalR Service.
- WebSockets: one long-lived two-way connection between browser and server. Why it matters: it is the underlying transport for low-latency two-way messaging.
- Server-sent events (SSE): a one-way stream from server to browser over plain HTTP. Why it matters: it is simpler than WebSockets when only the server pushes, such as progress or news feeds.
- GraphQL (awareness): a query language where the client asks for exactly the fields it needs from a single endpoint. Why it matters: it reduces over-fetching for varied clients, but adds caching, security and query-cost complexity.
- Code worth memorizing (server, Program.cs):
  - builder.Services.AddGrpc();
  - app.MapGrpcService<GreeterService>();

6 Real-world use case
- Situation: an order platform on Azure has an internal pricing service called by several backend services at high volume, plus an operations dashboard that must show order status live.
- Choice: gRPC with a shared .proto contract for the pricing calls, with deadlines set on every call. SignalR (with Azure SignalR Service for scale-out) for pushing live status to the Angular dashboard. REST stays for the public API.
- Trade-off: gRPC gives lower latency and a strict contract, but makes debugging harder and needs HTTP/2 end to end, including load balancers and ingress. SignalR adds persistent connections that consume server resources and need sticky sessions or a backplane.
- When NOT to use: do not use gRPC for public or third-party APIs, or when browsers call directly without gRPC-Web. Do not use SignalR when simple polling every 30 seconds is enough. Do not adopt GraphQL for a single known client.

11 Revision summary
- gRPC uses protobuf contracts and HTTP/2, and is best for internal service-to-service calls.
- Four call types: unary, server streaming, client streaming, bidirectional.
- Set a deadline on every gRPC call so slow calls do not stack up.
- gRPC-Web is needed for browsers and has streaming limits (verify).
- SignalR picks WebSockets, then SSE, then long polling; scaling out needs Redis backplane or Azure SignalR Service.
- WebSockets are two-way; SSE is one-way server to browser over plain HTTP.
- REST for public APIs, gRPC for internal, SignalR for push to UI.
- GraphQL is awareness only: flexible queries, but harder caching and cost control.
