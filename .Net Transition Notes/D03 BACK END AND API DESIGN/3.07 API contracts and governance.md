1 What is it

An API contract is the written, machine-readable agreement between a service and its consumers about what requests are valid and what responses come back. Governance is the set of rules that keeps all your APIs consistent and stops one team from breaking another.

OpenAPI is the standard file format (YAML or JSON) for describing a REST API: paths, parameters, schemas, status codes, auth.

Legacy equivalent: the WSDL file from ASMX and WCF services, plus the informal Word or wiki API documents that MVC and Web API projects used to share.

---

2 Why needed

- Frontend, mobile and partner teams cannot wait for the backend to finish before they start.
- Without a contract, a renamed field or removed property breaks consumers silently in production.
- Without standards, every team invents its own error format, naming and versioning.
- Without a gateway layer, auth, throttling and caching get copied into every service.

4 Features and core concepts

OpenAPI-first design
- Plain meaning: write the OpenAPI file first, review it, then build server and clients from it.
- Why it matters: the contract is agreed before code, so consumers work in parallel with mocks.
- Memorize: openapi: 3.0.x or 3.1 at the top (verify current version); paths, components/schemas, responses.

Naming and error standards
- Plain meaning: one rule set for URL style, casing, date format, pagination fields and error body.
- Why it matters: consumers learn one pattern, not ten.
- Use RFC 9457 Problem Details (application/problem+json) for errors, the successor to RFC 7807 (verify).

Versioning policy
- Plain meaning: a written rule on how and when versions change (URL segment, header or query).
- Why it matters: consumers know how long old versions live and how they will be told.
- Include a deprecation window and Sunset and Deprecation headers.

Breaking vs non-breaking changes
- Plain meaning: breaking changes make an existing valid client fail. Non-breaking changes do not.
- Why it matters: this decides when a new version is needed.
- Breaking: remove or rename a field, change a type, add a required request field, tighten validation, change a status code meaning.
- Non-breaking: add an optional field, add a new endpoint, add an optional query parameter.
- Rule for consumers: be tolerant, ignore unknown fields.

Consumer-driven contracts (Pact)
- Plain meaning: each consumer records what it actually uses. The provider runs those expectations in its build.
- Why it matters: the provider learns exactly who breaks before release.
- Flow: consumer test generates a pact file, publish it to a broker, provider verifies it, then can-i-deploy checks.
- OpenAPI describes the whole API. Pact describes only what real consumers use.

API Management basics (Azure API Management)
- Plain meaning: a managed gateway in front of your APIs that applies shared rules.
- Why it matters: cross-cutting rules live in one place, not in every service.
- Policies: XML rules applied on inbound, backend, outbound and on-error stages.
- Products: bundles of APIs with a subscription key, quota and terms.
- JWT validation: validate-jwt policy checks issuer, audience and signature before the call reaches the backend.
- Caching: cache-lookup and cache-store policies.
- Throttling: rate-limit (per time window) and quota-by-key (long-term cap).

5 Core focus (exam and interview)

- OpenAPI-first vs code-first: first gives a reviewed contract; code-first is faster but the contract drifts.
- Which changes are breaking. This is asked in almost every API design round.
- Pact vs OpenAPI: consumer-driven vs provider-described.
- APIM tiers differ in features such as VNet support, multi-region and SLA (verify on Microsoft Learn).
- Policy scopes: global, product, API, operation. The more specific scope runs closer to the operation.
- Subscription key identifies a consumer. It is not strong authentication. Use JWT for that.
- rate-limit returns 429 with Retry-After.

6 Real-world use case

Situation: a Kolkata-based team moves an MVC and Web API monolith toward services. An Angular app, a mobile app and a partner all consume the Orders API.

Choice made:
- Orders API is defined in OpenAPI first, reviewed in a pull request, with a linter (Spectral) in the pipeline.
- A diff tool (such as oasdiff) runs in CI and fails the build on breaking changes.
- The Angular team generates its client from the OpenAPI file.
- The partner is exposed through Azure API Management with a product, a subscription key, validate-jwt and rate-limit.
- Pact is used between Angular and Orders API to protect fields the UI really reads.

Trade-off: more upfront review and tooling, slower first endpoint. In return, far fewer production breaks and parallel team work.

When NOT to use it: a small internal API with one consumer owned by the same team. A shared OpenAPI file and normal integration tests are enough. Skip APIM and Pact there.

7 Interview lens

Q1: What is a breaking change in an API?
A: Any change that makes a previously valid client fail, such as removing a field, changing a type or adding a required input. Adding optional fields or endpoints is non-breaking.

Q2: OpenAPI-first or code-first, and why?
A: First when several teams consume the API, because the contract is agreed early and clients can be generated. Code-first is acceptable for a single-team internal API if the spec is still published and checked in CI.

Q3: How is Pact different from an OpenAPI spec?
A: OpenAPI describes everything the provider offers. Pact captures only what each consumer really uses and lets the provider verify it, so you see exactly who breaks.

Q4: What would you put in an API gateway and not in the service?
A: Cross-cutting concerns: JWT validation, throttling, caching, header changes, version routing. Business rules and fine-grained authorization stay in the service.

8 Common mistakes

- Spec generated from code and never reviewed: contract changes slip in unnoticed. Fix: publish the spec as a build artifact and diff it in the pull request.
- Treating a renamed field as minor: consumers crash on release. Fix: add the new field, keep the old, deprecate, then remove after the window.
- Different error shapes per service: clients need custom parsing. Fix: one Problem Details standard.
- Relying only on subscription keys: anyone with the key is trusted. Fix: validate-jwt plus authorization in the service.
- Putting heavy business logic in APIM policies: hard to test and version. Fix: keep policies thin.
- No deprecation policy: old versions live forever. Fix: published dates and Sunset headers.

9 Mental model

  Consumer teams --> OpenAPI contract <-- Provider team
                          |
                CI: lint + breaking-change diff + Pact verify
                          |
        Azure API Management (JWT, throttle, cache, products)
                          |
                      Backend services

The contract sits in the middle. Nobody changes it alone.

11 Revision summary

- OpenAPI-first: write and review the contract before code.
- Errors follow one standard: Problem Details, RFC 9457 (verify).
- Breaking: remove, rename, change type, new required input. Non-breaking: new optional field or endpoint.
- Deprecate with a notice period and Sunset header before removing.
- Pact is consumer-driven: consumer pact file, provider verification, can-i-deploy.
- APIM policy stages: inbound, backend, outbound, on-error.
- validate-jwt checks the token at the gateway. Subscription key only identifies the caller.
- rate-limit is short-term throttling, quota is long-term, both return 429.
