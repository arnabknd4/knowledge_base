1 What is it

Background processing means running work outside the request-response cycle of a web API. The API accepts the request, hands the work to something else, and returns quickly. A worker later does the slow or scheduled job.

- BackgroundService: a base class for a long-running loop that the host starts and stops.
- IHostedService: the lower-level interface with StartAsync and StopAsync. BackgroundService implements it.
- Worker service: a .NET project template that hosts only background services, with no web endpoints.
- Queue plus worker: the API puts a message on a queue, a separate worker reads and processes it.
- Hangfire and Quartz: libraries that add persistent jobs, scheduling and a dashboard (Hangfire) or advanced cron-style triggers (Quartz).

Legacy equivalent: Windows Services, scheduled tasks calling console exes, SQL Agent jobs, and Task.Run or Thread fire-and-forget code inside IIS apps.

----

2 Why needed

- Long work inside an HTTP request causes timeouts, blocked threads and angry users.
- Work that must run at 2 AM or every 5 minutes needs a scheduler.
- Spikes of work need a buffer (a queue) so the system is not overwhelmed.
- Without it, fire-and-forget code inside a web app dies silently when the app pool recycles or the container stops. The work is lost and nobody knows.

4 Features and core concepts

BackgroundService and IHostedService
- Plain meaning: code the host starts when the app starts and stops when the app stops.
- Why it matters: the host gives you the shutdown signal through a CancellationToken, so you can finish cleanly. Override ExecuteAsync and loop while the token is not cancelled.
- Trap: a hosted service is a singleton. To use a scoped service (like DbContext), create a scope inside the loop with IServiceScopeFactory.
- Memorize:
  - protected override async Task ExecuteAsync(CancellationToken ct)
  - while (!ct.IsCancellationRequested) { await DoWorkAsync(ct); await Task.Delay(TimeSpan.FromSeconds(30), ct); }

Worker services
- Plain meaning: a project with no web server, only hosted services (dotnet new worker).
- Why it matters: you can scale and deploy the worker separately from the API, in a container, App Service WebJob or Container Apps.

Queue plus worker pattern
- Plain meaning: producer writes a message, consumer reads and processes it later.
- Why it matters: it decouples speed. The API stays fast, and workers scale by queue length. Failed messages can retry or go to a dead-letter queue.
- In Azure: Service Bus or Storage Queues as the queue, a worker as the consumer.

Hangfire and Quartz
- Plain meaning: libraries that store jobs in a database (SQL Server, Redis) and run them with retries.
- Hangfire: fire-and-forget, delayed, recurring and continuation jobs, plus a built-in dashboard. Easiest to start with.
- Quartz.NET: powerful cron triggers, calendars, clustering. No built-in dashboard.
- Why it matters: jobs survive restarts because they are persisted. Plain BackgroundService loops do not persist anything.

Scheduled jobs
- Plain meaning: work that runs on a time rule (cron expression).
- Why it matters: in multi-instance deployments, every instance would run the same job. You need a lock, a single scheduler, or a library with clustering.

Outbox processors
- Plain meaning: a worker that reads an outbox table (events saved in the same database transaction as business data) and publishes them to the message broker.
- Why it matters: it avoids the lost-message problem where the database commit succeeds but the publish fails. See 6.03.

Idempotent jobs
- Plain meaning: running the same job twice gives the same result as running it once.
- Why it matters: queues and retries are at-least-once, so duplicates will happen. Use a processed-ID table, unique constraints or upserts.

Concurrency control
- Plain meaning: stopping two workers from handling the same work at once, or limiting parallelism.
- Why it matters: prevents double processing and overload. Tools: SemaphoreSlim, database row locks, distributed locks (Redis), Service Bus peek-lock, Hangfire DisableConcurrentExecution attribute.

Azure Functions timer and queue triggers
- Plain meaning: serverless code that runs on a schedule (timer) or when a message arrives (queue trigger).
- Why it matters: no server to manage and scaling is automatic. The Consumption plan scales to zero, with cold-start and execution time limits (verify current limits per plan).

Durable Functions awareness
- Plain meaning: an extension of Azure Functions for long, multi-step workflows with saved state (chaining, fan-out/fan-in, human approval).
- Why it matters: it is the answer when a job has many steps and needs to survive restarts. Awareness only for now. See 6.06.

5 Core focus (exam and interview)

Asked most:

- Why a hosted service cannot inject a scoped service directly.
- How to run a job safely on several instances.
- Why jobs must be idempotent.
- What happens to in-flight work at shutdown.

Defaults and limits to remember:
- Host shutdown timeout defaults to 30 seconds in recent .NET (verify).
- An unhandled exception in a BackgroundService stops the host by default in .NET 6 and later (BackgroundServiceExceptionBehavior).
- Service Bus peek-lock default lock duration is 1 minute (verify).
- Functions timeout limits depend on hosting plan (verify).

6 Real-world use case

Situation: an ASP.NET Core API accepts invoice PDF requests. Generation takes 40 seconds. Users see timeouts.

Choice made: the API validates the request, saves a job record, puts a message on an Azure Service Bus queue and returns 202 Accepted with a status URL. A worker service (in Azure Container Apps, scaled by queue length with KEDA) generates the PDF, stores it in Blob Storage and updates the job status. Failed messages retry three times, then go to the dead-letter queue. The worker checks a job-ID record first, so duplicates are harmless.

Trade-off: more moving parts (queue, worker, status endpoint, monitoring) and eventual consistency. The user must poll or be notified.

When NOT to use it: work that takes under a second and must return its result in the response; tiny internal apps where one nightly job is enough (a simple timer-based BackgroundService or Functions timer trigger is simpler); work that cannot tolerate any delay or loss without a proper persistent queue.

7 Interview lens

Q1: Why not use Task.Run in a controller for slow work?
A: The work is not tracked or persisted, so a recycle or deploy kills it silently. Use a queue plus worker or a persisted job library.

Q2: How do you use DbContext inside a BackgroundService?
A: Inject IServiceScopeFactory and create a scope for each unit of work. The hosted service is a singleton, DbContext is scoped.

Q3: Your scheduled job runs on 3 instances. What do you do?
A: Use a distributed lock, a library with clustering (Quartz or Hangfire with a shared store), or run the scheduler as a single instance such as a separate worker or a Functions timer trigger.

Q4: Hangfire or Azure Functions?
A: Hangfire when you already host the app and want a dashboard and simple persistence. Functions when you want serverless scaling, event triggers and less infrastructure.

8 Common mistakes

- Injecting a scoped service into a hosted service. It shows up as a startup error or, with scope validation off, as stale data and connection leaks. Fix: use IServiceScopeFactory.
- No try/catch in the loop. One exception kills the host or the loop quietly stops. Fix: catch, log, continue, and use retry with backoff.
- Ignoring the CancellationToken. Shutdown hangs, then the process is killed mid-job. Fix: pass the token everywhere.
- Non-idempotent handlers. Retries create duplicate emails or double charges. Fix: processed-ID table or unique constraint.
- Timer jobs on every instance. The job runs 3 times after scaling out. Fix: locking or single scheduler.
- Tight loop with no delay. CPU stays at 100 percent. Fix: Task.Delay or PeriodicTimer.
- No monitoring on the dead-letter queue. Failed jobs pile up unseen. Fix: alert on queue depth and dead-letter count.

9 Mental model

  API --(message)--> Queue --(pull)--> Worker(s) --> Database / Blob
   |                                      |
   +-- returns 202 + job id               +-- retry, then dead-letter

  Scheduler (cron) --(triggers)--> same Worker or a Function

The API only takes orders. The kitchen (workers) cooks at its own speed. The queue is the order rail.

10 Mini lab

Time: about 30 minutes. Tools: .NET SDK, local only.

Steps:
- Run: dotnet new worker -n JobLab, then cd JobLab.
- Open Worker.cs. In ExecuteAsync, loop with a PeriodicTimer of 5 seconds and log "tick" with the time.
- Add a System.Threading.Channels Channel<string> as a singleton in Program.cs. Make a second BackgroundService that reads from the channel and logs each item after a 2-second Task.Delay.
- In the first service, write "job-1", "job-2" and so on to the channel on each tick.
- Run dotnet run. Watch ticks and processing logs.
- Press Ctrl+C. Watch the host stop the services. Add ct to every await so shutdown is quick.
- Stretch: make the consumer throw on "job-3" and see the host stop. Then wrap the work in try/catch and confirm it continues.

Expected result: ticks every 5 seconds, jobs processed in order, clean stop on Ctrl+C, and a clear difference between a crashed and a caught exception.

Clean-up: delete the JobLab folder.

11 Revision summary

- BackgroundService is a singleton, so use IServiceScopeFactory for scoped services.
- Always honor the CancellationToken and catch exceptions inside the loop.
- Queue plus worker decouples the API from slow work and scales by queue length.
- Hangfire and Quartz persist jobs. A plain hosted-service loop does not.
- Every job must be idempotent because delivery is at-least-once.
- Scheduled jobs on multiple instances need a lock or a single scheduler.
- The outbox processor publishes events saved in the same transaction as the data.
- Functions timer and queue triggers are the serverless option. Durable Functions handles multi-step workflows (awareness only).
