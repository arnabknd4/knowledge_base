1 What is it

- Authentication means proving who you are. Authorization means deciding what you are allowed to do.
- OAuth 2.0 is a standard way for an app to get permission to call an API without handling the user's password. OIDC (OpenID Connect) adds a login layer on top of OAuth 2.0 so the app also learns who the user is.
- A JWT (JSON Web Token) is a signed text token that carries claims (facts) about the user or app. Entra ID (formerly Azure AD) is Microsoft's identity service that issues these tokens.
- Legacy equivalent: Forms authentication, Windows authentication with AD groups, and the old Membership provider with [Authorize(Roles = "...")] in MVC.

2 Why needed

- APIs must know the caller and limit what each caller can do.
- Without a standard, every app invents its own login, stores passwords, and shares credentials between services.
- Without scopes and policies, any valid token can do everything.
- Without managed identity, services keep secrets in config files and those secrets leak.

3 Before you read

- HTTP headers: the Authorization: Bearer header carries the token.
- Public and private keys: a signature made with a private key is checked with a public key.
- Base64 encoding: JWT parts are Base64URL text, not encrypted.
- Tenant: one organization's own Entra ID directory.

4 Features and core concepts

- OAuth 2.0 grants: a grant is a recipe for getting a token. Why it matters: choosing the wrong grant is a common security error.
  - Authorization code with PKCE: for users on web and SPA apps. Use this by default.
  - Client credentials: app talks to app with no user. Used for background services.
  - On-behalf-of (OBO): API A exchanges the user's token for a new token to call API B as that same user.
  - Implicit and password grants: old and unsafe. Avoid them.
  - Device code: for devices with no browser, such as CLI tools.
- OIDC: adds an ID token (who the user is) and a standard login flow. Why it matters: OAuth alone says nothing about identity.
- JWT structure: three parts, header.payload.signature. Header names the algorithm and key id (kid). Payload holds claims. Signature proves nothing was changed. Why it matters: you must validate it, not just decode it.
- JWT validation: check the signature using the issuer's published keys, then issuer (iss), audience (aud), expiry (exp) and not-before. Why it matters: skipping the audience check lets a token for another API work on yours.
- Scopes vs roles vs claims:
  - Claim: any fact in the token.
  - Scope: a delegated permission, such as "Orders.Read", that the user granted to the app. Appears in the scp claim.
  - Role: an app role assigned to a user or app. Appears in the roles claim.
  - Why it matters: scopes limit what an app can do for a user. Roles describe what a user or app is.
- Policy-based authorization: named rules in code, such as "must have role Admin and claim department=Finance". Why it matters: rules live in one place instead of being scattered as [Authorize(Roles=...)] strings.
- Resource-based authorization: the decision depends on the specific object, such as "only the owner can edit this order". Done with IAuthorizationService inside the handler. Why it matters: it prevents broken object-level access.
- Entra ID app registrations: the identity record of your app in Entra ID.
  - App roles: roles you define for your API.
  - Exposed scopes: permissions you define for your API.
  - Consent: a user or admin approves the permissions an app asks for. Admin consent is needed for high-privilege permissions.
  - Why it matters: most real failures are misconfigured registrations, not code.
- Managed identity: Azure gives a service its own identity with no secret to store. Why it matters: it removes secrets from config.
- Client credentials flow: the app proves itself with a secret, a certificate, or a federated credential and receives an app-only token. Why it matters: it is the standard for service-to-service calls.
- Token lifetime, refresh and revocation: access tokens are short-lived (default around one hour, verify). Refresh tokens get new access tokens without a new login. A JWT cannot be recalled before it expires, so keep lifetimes short and use Continuous Access Evaluation where available (verify). Why it matters: a stolen token works until it expires.
- ASP.NET Core Identity basics: a library with its own user store, password hashing and cookies. Why it matters: it suits apps that own their users, but it is not a replacement for Entra ID in enterprise APIs.
- Entra External ID (verify): Microsoft's service for customer-facing sign-up and sign-in. It replaces Azure AD B2C for new work (verify current status).
- Code worth memorizing:
  - builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));
  - builder.Services.AddAuthorization(o => o.AddPolicy("OrdersRead", p => p.RequireClaim("scp", "Orders.Read")));
  - app.UseAuthentication(); app.UseAuthorization();

5 Core focus (exam and interview)

- Most asked: which grant for which scenario, and the difference between authentication and authorization.
- Scopes are for delegated access (user present). App roles are for app-only access and for user roles.
- A token has an audience. Your API must reject tokens meant for someone else.
- A JWT is signed, not encrypted. Do not put secrets in it.
- UseAuthentication must come before UseAuthorization in the pipeline.
- Managed identity: system-assigned is tied to one resource and deleted with it. User-assigned is a separate resource that can be shared.
- Exam (AZ-104, AZ-305, AZ-204 style): managed identity vs service principal, app registration vs enterprise application, and RBAC vs Entra roles. Check Microsoft Learn for the current wording (verify).
- Default access token lifetime and exact limits can change (verify).

6 Real-world use case

- Situation: a legacy MVC portal with Forms authentication is being split into an Angular front end and an ASP.NET Core API on Azure App Service. An internal reporting service also calls the API every night.
- Choice made:
  - Users: Entra ID sign-in with authorization code plus PKCE from Angular (MSAL). The API validates JWTs and checks the scope Orders.Read.
  - Nightly service: client credentials flow with a managed identity, holding the app role Orders.ReadAll.
  - Order edits: resource-based authorization so only the owner or a manager can change an order.
  - API B calls: on-behalf-of when the API must call a downstream API as the user.
- Trade-off: more setup (app registrations, consent, role assignment) in return for no stored passwords, central control and audit logs.
- When NOT to use it: a small internal tool with a single trusted caller may be fine with network restrictions and managed identity only. A consumer app with its own user database may be better served by ASP.NET Core Identity or Entra External ID.

7 Interview lens

- Q: What is the difference between OAuth 2.0 and OIDC?
  - A: OAuth 2.0 gives access to an API and says nothing about who the user is. OIDC adds an ID token and standard login so the app learns the user's identity.
- Q: A service needs to call your API with no user. Which flow, and how do you avoid secrets?
  - A: Client credentials flow, giving an app-only token with app roles. Use a managed identity or a federated credential so no secret is stored.
- Q: What must your API check when it receives a JWT?
  - A: Signature (from the issuer's keys), issuer, audience, expiry, then scope or role. A token for a different audience must be rejected.
- Q: How do you handle logout or revocation with JWTs?
  - A: You cannot recall a JWT before expiry, so use short access tokens, refresh tokens that can be revoked, and Continuous Access Evaluation where supported (verify).

8 Common mistakes

- Decoding a JWT but not validating it. Shows up as forged tokens being accepted. Fix: use the JwtBearer middleware with signature, issuer and audience checks on.
- Skipping the audience check. Shows up as tokens from another API working on yours. Fix: set the Audience and test with a wrong-audience token.
- Using roles for everything. Shows up as rigid code and role explosion. Fix: use policies and scopes, and keep roles for coarse grouping.
- Only checking [Authorize] and forgetting object ownership. Shows up as users reading each other's data. Fix: resource-based authorization on every object fetch.
- Storing client secrets in appsettings or the repo. Shows up as leaked credentials. Fix: managed identity, certificates or Key Vault.
- Putting UseAuthorization before UseAuthentication. Shows up as every request returning 401 or 403. Fix: correct the order.
- Using the implicit flow for a new SPA. Shows up as tokens in the URL. Fix: authorization code with PKCE.

9 Mental model

- Think of a hotel.
  - The front desk (Entra ID) checks your ID and gives you a key card (the JWT).
  - The card lists which floors you can enter (scopes and roles).
  - Each door (your API) reads the card, checks it is real (signature), meant for this hotel (audience) and not expired.
  - A room safe (resource-based check) opens only for the guest who booked the room.

User --login--> Entra ID --token--> App --Bearer token--> API --validate + policy--> data

10 Mini lab (about 35 minutes)

- Goal: protect a minimal API with Entra ID and call it with a token.
- Steps:
  1. In the Azure portal (free tenant), go to Entra ID, App registrations, New registration. Name it "orders-api". Single tenant. Create.
  2. Open "Expose an API", set the Application ID URI, and add a scope named Orders.Read.
  3. Create a second registration "orders-client". Under API permissions, add Orders.Read from orders-api and grant admin consent. Under Certificates and secrets, create a client secret (lab use only).
  4. Run: dotnet new web -n OrdersApi, then dotnet add package Microsoft.Identity.Web.
  5. In Program.cs, add AddMicrosoftIdentityWebApi with your TenantId and ClientId in appsettings under "AzureAd", add the policy "OrdersRead" requiring scp = Orders.Read, add UseAuthentication and UseAuthorization, and map GET /orders with .RequireAuthorization("OrdersRead").
  6. Call the endpoint with no token. Expected: 401.
  7. Get a token for the client using the client credentials flow (az account get-access-token works for user tokens; for the app token, use a short script or Postman). Decode it at jwt.ms and look at aud, iss, exp and roles or scp.
  8. Call with the token. Note: a client credentials token has roles, not scp, so the policy for scp will fail with 403. This is expected and teaches the difference. Change the policy to require an app role (add the role under App roles) and retry. Expected: 200.
- Clean-up: delete both app registrations and the secret, and delete the local project folder.

11 Revision summary

- Authentication is who you are. Authorization is what you can do.
- OIDC adds identity on top of OAuth 2.0.
- Default flow for users: authorization code with PKCE. For services: client credentials.
- A JWT is signed, not encrypted. Always validate signature, issuer, audience and expiry.
- Scopes are delegated permissions (scp). App roles come in the roles claim.
- Prefer policies and resource-based checks over hard-coded roles.
- Managed identity removes stored secrets. System-assigned dies with the resource.
- A JWT cannot be revoked early, so keep access tokens short-lived.
