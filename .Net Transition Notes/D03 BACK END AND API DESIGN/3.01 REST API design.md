1 What is it

- REST API design is the set of rules for shaping an HTTP API around resources (things like orders or customers), using standard HTTP verbs and status codes so any client can predict how it behaves.
- A resource is a noun you can address with a URL. A verb is the HTTP method (GET, POST, PUT, PATCH, DELETE) that says what to do with it.
- Legacy equivalent: MVC action methods like /Order/GetOrderDetails or /Order/Save, or WCF/ASMX operations, where the URL named an action and almost everything returned 200.

2 Why needed

- Many clients (Angular app, mobile, partner systems, other microservices) call the same API. A predictable design means less documentation and fewer integration bugs.
- Without it: inconsistent URLs, wrong status codes that break retries, duplicate orders from repeated POSTs, clients that break when you add a field, and slow endpoints that return a million rows.

3 Before you read

- HTTP basics: request, response, headers, body.
- JSON as a data format.
- What a stateless server means: each request carries everything needed, no server session.
- Difference between safe (does not change data) and idempotent (same result if repeated).

4 Features and core concepts

- Resources and URIs: nouns, plural, hierarchical. Example: /orders/42/items. Why: URLs stay stable while actions are expressed by verbs. Avoid verbs in paths like /getOrder.
- Verb semantics: GET reads (safe, idempotent). POST creates or triggers (not idempotent). PUT replaces (idempotent). PATCH changes part (not guaranteed idempotent). DELETE removes (idempotent). Why: caches, proxies and retry logic rely on these meanings.
- Status codes: 200 OK, 201 Created (with Location header), 204 No Content, 400 bad input, 401 not authenticated, 403 not allowed, 404 not found, 409 conflict, 412 precondition failed, 422 validation failed, 429 too many requests, 500 server fault, 503 unavailable. Why: clients branch on the code, not the message.
- Idempotency: repeating a request has the same effect as sending it once. For POST, use an Idempotency-Key header that the server stores. Why: networks time out and clients retry, and without a key you get double charges.
- PUT vs PATCH: PUT sends the full resource and replaces it. PATCH sends only changed fields (JSON Merge Patch or JSON Patch). Why: PUT with a partial body silently wipes missing fields.
- Pagination: offset (page and size, simple, slow on deep pages, shifts when rows change) vs cursor (opaque token pointing after the last item, stable and fast). Why: unbounded lists crash servers and clients. Always cap page size.
- Filtering and sorting: query string, such as ?status=open&sort=-createdAt. Whitelist allowed fields. Why: stops arbitrary column access and slow unindexed sorts.
- Versioning (URL, header): URL version /v1/orders is visible and easy to route. Header or media type versioning keeps URLs clean but is harder to test in a browser. Why: lets you ship breaking changes without breaking existing clients.
- ETags and concurrency: server returns ETag on GET. Client sends If-Match on update. If it no longer matches, server returns 412. Why: prevents lost updates when two users edit the same record. Also If-None-Match gives 304 Not Modified for caching.
- Content negotiation: client sends Accept (and Content-Type for the body). Server returns 406 or 415 if it cannot comply. Why: supports JSON now and other formats later.
- Long-running operations: return 202 Accepted with a Location header pointing to a status resource. Client polls, and the status resource eventually points to the result. Why: avoids HTTP timeouts on slow work such as report generation.
- Rate limits: return 429 with a Retry-After header. Why: protects the service from one noisy client.
- Maturity model (Richardson): level 0 single endpoint, level 1 resources, level 2 proper verbs and status codes, level 3 hypermedia links. Why: most real APIs target level 2. Level 3 is rare.
- Worth memorizing (ASP.NET Core, creation response):
  return CreatedAtAction(nameof(Get), new { id = o.Id }, o);

5 Core focus (exam and interview)

- Most asked: PUT vs PATCH, which verbs are idempotent, 401 vs 403, 400 vs 422, 200 vs 201 vs 204, offset vs cursor pagination, how to version an API.
- Safe and idempotent: GET, HEAD, OPTIONS are safe. GET, PUT, DELETE are idempotent. POST is neither. PATCH is not guaranteed idempotent.
- 401 means not authenticated (no or bad token). 403 means authenticated but not allowed.
- Creation returns 201 plus Location. Update with no body returns 204.
- Retry only idempotent calls automatically. POST needs an idempotency key first.
- Defaults are conventions, not specs. Where teams differ (for example 400 vs 422), pick one and document it.

6 Real-world use case

- Situation: an order service is exposed to an Angular front end and a partner system. The partner retries on timeout and created duplicate orders in the old MVC endpoint.
- Choice: POST /v1/orders with a required Idempotency-Key header, stored in a table with the response for 24 hours. GET /v1/orders uses cursor pagination with a max page size of 100. Updates use ETag and If-Match. Report export returns 202 with a status URL. Errors use one consistent format (see 3.02, ProblemDetails).
- Trade-off: idempotency storage adds a table, cleanup job and extra latency. Cursor pagination cannot jump to page 50.
- When NOT to use full REST: chatty internal service-to-service calls with streaming (consider gRPC), or a front end needing flexible shapes across many entities (consider GraphQL). Do not force a verb-style action like "approve" into awkward PATCH; POST /orders/42/approval is fine.

7 Interview lens

- Q: PUT or PATCH for updating one field? A: PATCH. PUT replaces the whole resource, so a partial body would erase missing fields.
- Q: How do you make POST safe to retry? A: Client sends an Idempotency-Key. Server stores key and result, and returns the stored result on repeats.
- Q: Offset or cursor pagination? A: Offset is simple but slow on deep pages and unstable under inserts. Cursor is fast and stable but has no random page jump. Use cursor for large or changing data.
- Q: How do you version an API and avoid breaking clients? A: URL version for breaking changes, and only add optional fields within a version. Announce deprecation with a sunset date and monitor old version usage.

8 Common mistakes

- Verbs in URLs (/getUsers): inconsistent API, hard to cache. Fix: nouns plus HTTP verbs.
- Always returning 200 with an error in the body: clients and monitoring miss failures. Fix: correct status codes.
- No page size cap: one request pulls the whole table. Fix: default 20, hard max 100.
- Using PUT for partial updates: fields wiped to null. Fix: PATCH, or require full body.
- Returning EF entities directly: leaks internal columns and couples the schema to clients. Fix: DTOs.
- Changing a field name or type within a version: mobile apps crash. Fix: add new field, deprecate old, bump version only for breaking changes.
- Exposing internal IDs and sort fields freely: enumeration and slow queries. Fix: authorization checks and whitelists.

9 Mental model

Resource = noun, URL = address, verb = what you do, status code = the answer.

  client --PUT /orders/42 (If-Match: "v3")--> 204 or 412

11 Revision summary

- URLs are plural nouns; verbs express the action.
- GET, PUT, DELETE are idempotent; POST is not; retry POST only with an idempotency key.
- 401 means who are you, 403 means you may not.
- Create returns 201 plus Location; update returns 204 or 200.
- PUT replaces, PATCH changes part.
- Cursor pagination beats offset for large changing data; always cap page size.
- ETag plus If-Match gives 412 on lost updates; If-None-Match gives 304.
- Slow work returns 202 plus a status URL; throttling returns 429 plus Retry-After.
