Topic 3.08 is API security, tagged P2 R L, so it is a full note with a mini lab.

---

1 What is it

- API security is the set of habits and controls that stop attackers from misusing your HTTP APIs.
- OWASP is a non-profit that publishes lists of the most common security failures. The OWASP API Top 10 is its list for APIs (verify the current edition).
- Most API attacks are not clever hacks. They are normal requests that the server should have refused.
- Legacy equivalent: MVC form validation, [Authorize] attributes and web.config request filtering, but now applied to JSON endpoints that anyone can call from a script.

2 Why needed

- APIs expose data and actions directly, with no UI to hide behind.
- Without these controls, one user can read or change another user's data by editing an ID in the URL.
- Without limits, a single client can flood the service or guess passwords at will.
- Without careful logging rules, your logs become a data leak.

3 Before you read

- Authentication proves who the caller is. Authorization decides what that caller may do (topic 3.03).
- A JWT is a signed token carrying claims about the caller.
- HTTP status codes and headers (topic 3.01).
- Basic SQL and what a DTO is (a plain object used only to carry data in and out of the API).

4 Features and core concepts

- OWASP API Top 10: a ranked list of the most common API flaws. It gives you a checklist for reviews and a shared vocabulary in interviews. Check the current edition (verify).
- Input validation: reject any request that does not match the shape, type, length and range you expect. Bad input is the root of injection, crashes and logic bugs. Validate on the server always, because client checks can be bypassed.
- Mass assignment: the framework binds every JSON field to your model, so a caller adds "isAdmin": true and it sticks. Fix it by binding to a DTO that has only the allowed fields, never to the entity directly.
- Broken object-level authorization (BOLA): the API checks that you are logged in but not that the record is yours, so GET /orders/124 shows someone else's order. It is the top API risk. Fix it by checking ownership on every object access, for example filtering by the caller's user ID in the query.
- Rate limiting: cap how many requests a caller can make in a time window. It slows brute force, scraping and denial of service. In .NET use the built-in rate limiter middleware, or API Management throttling in front of it.
- Security headers: response headers that tell browsers to behave safely (Strict-Transport-Security, X-Content-Type-Options, Content-Security-Policy). They matter mostly when the API serves browsers. Add them in middleware.
- Secrets handling: keep connection strings, keys and client secrets out of code and repos. Use Key Vault and managed identity (topics 1.04 and 12.08).
- SQL injection: attacker text gets treated as SQL because the query was built by joining strings. Use parameterized queries or EF Core LINQ, which parameterize for you.
- SSRF (server-side request forgery): the server fetches a URL the caller supplied, and the attacker points it at internal addresses such as the cloud metadata endpoint. Fix it with an allow-list of hosts and no raw URL fetching from user input.
- File upload risks: uploads can carry malware, oversized files or disguised types. Limit size, check the real content type, rename the file, store it outside the web root (for example Blob storage), and scan it.
- Logging without personal data: logs outlive requests and are widely readable. Never log tokens, passwords or personal data. Mask or omit them, and log IDs instead.
- One thing worth memorizing, the BOLA fix:

```
var order = await db.Orders
    .FirstOrDefaultAsync(o => o.Id == id && o.OwnerId == userId);
if (order is null) return Results.NotFound();
```

5 Core focus (exam and interview)

- BOLA is the most asked item. Authentication alone never prevents it.
- Know the difference between BOLA (wrong record) and function-level authorization (wrong operation, such as a normal user calling an admin endpoint).
- Mass assignment fix: DTOs and explicit field lists.
- Return 404 rather than 403 for other people's records when you do not want to confirm they exist.
- Rate limit status code is 429 with a Retry-After header.
- Validation location: server side, at the edge of the API.
- Do not quote exact ranks from the Top 10 list without checking the current edition (verify).

6 Real-world use case

- Situation: a client portal API in ASP.NET Core exposes /api/invoices/{id}. A tester changes the ID and downloads another client's invoice.
- Choice made: add an ownership filter on every query through a shared helper, bind requests to DTOs, add per-user rate limits, and put API Management in front with JWT validation and throttling.
- Trade-off: ownership checks add a condition to every query and need tests per endpoint. Rate limits can block legitimate batch clients, so they need tuning and exceptions.
- When NOT to use heavy controls: a purely internal, low-risk API behind a private network still needs authorization, but a full gateway and per-client throttling may be more cost than it is worth. Basic validation and authorization are never optional.

7 Interview lens

- Q: What is BOLA and how do you prevent it?
  A: The API lets a user access another user's object by changing an ID. Check ownership or permission for every object access, in the query or a policy handler.
- Q: How do you stop mass assignment in ASP.NET Core?
  A: Bind to request DTOs with only the allowed properties and map them manually. Never bind JSON straight to entities.
- Q: Where do rate limits belong?
  A: At the edge (API Management or Front Door) for coarse protection, plus the in-app rate limiter for per-user rules.
- Q: How do you prevent SSRF?
  A: Do not fetch user-supplied URLs, or allow only a list of approved hosts. Block private and metadata IP ranges.

8 Common mistakes

- Checking only [Authorize] and assuming that is enough. It shows up as users reading each other's data. Fix: add resource-level checks.
- Returning EF entities directly from endpoints. It leaks internal fields and enables mass assignment. Fix: DTOs.
- Building SQL with string concatenation in dynamic search. It shows up as injection findings in a pen test. Fix: parameters.
- Logging full request bodies and tokens. It shows up as secrets in Log Analytics. Fix: log IDs and mask sensitive fields.
- Rate limiting only by IP. Users behind one corporate NAT get blocked together, and attackers rotate IPs. Fix: limit by user or client ID too.
- Trusting the file name and extension on uploads. It shows up as stored malware or path tricks. Fix: generate your own names and check content.

9 Mental model

```
Request -> [rate limit] -> [authN] -> [validate shape] -> [authZ: is THIS record yours?]
        -> [DTO map] -> [parameterized query] -> response (no extra fields)
Every arrow is a place to say no.
```

10 Mini lab (30 minutes, local only)

- Steps:
  - Create a minimal API: dotnet new web -n SecLab, then cd SecLab.
  - Add a list of orders in memory, each with Id, OwnerId and Total. Add GET /orders/{id} that returns the order without checking OwnerId.
  - Add a fake user ID read from a request header X-User, and test with curl as user 1 requesting an order owned by user 2. You will see the other user's order. That is BOLA.
  - Fix it by adding the OwnerId match from section 4. Retest. You should now get 404.
  - Add a POST /orders endpoint that binds directly to the Order class. Send "ownerId": 99 in the body and see it accepted. Switch to a CreateOrderDto with only Total, and set OwnerId from the header. Retest.
  - Add the built-in rate limiter (AddRateLimiter, fixed window, 5 requests per 10 seconds). Call the endpoint 6 times quickly and expect 429 on the sixth.
- Expected result: the cross-user read is blocked, the injected ownerId is ignored, and the sixth fast call returns 429.
- Clean-up: delete the SecLab folder.

11 Revision summary

- BOLA means a valid login does not equal permission for that record, so check ownership on every access.
- Mass assignment is stopped by DTOs, never by binding to entities.
- Validate on the server at the API edge.
- Parameterize queries. Never join strings into SQL.
- SSRF is stopped by host allow-lists and no raw user URLs.
- Rate limit returns 429 with Retry-After, and should limit by user as well as IP.
- Do not log tokens, passwords or personal data.
- Uploads need size limits, content checks, renamed files and scanning.
- Check the current OWASP API Top 10 edition before an exam or interview (verify).
