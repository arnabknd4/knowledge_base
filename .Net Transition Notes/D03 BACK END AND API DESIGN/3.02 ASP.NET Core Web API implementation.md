1 What is it

- Web API implementation in ASP.NET Core means building HTTP endpoints that other systems call, using either controllers (classes with action methods) or minimal APIs (small route handlers declared in Program.cs).
- Around the endpoints sit supporting pieces: binding the request into objects (model binding), checking input (validation), shaping errors (ProblemDetails), publishing a contract (OpenAPI), and keeping internal data models out of the public contract (DTOs).
- Model binding means ASP.NET Core reads route values, query string and body and turns them into method parameters.
- ProblemDetails is a standard JSON error format (RFC 9457, earlier RFC 7807) with fields like type, title, status and detail.
- OpenAPI is a machine-readable description of your API, used to generate docs and client code.
- Legacy equivalent: ASP.NET Web API 2 controllers (ApiController, DataAnnotations, Swashbuckle, AutoMapper) plus Global.asax filters and ExceptionFilterAttribute.

------

2 Why needed

- Without a consistent implementation style, every endpoint validates, fails and returns errors differently, and clients cannot rely on the contract.
- Exposing EF entities directly leaks columns, breaks on schema change, and opens mass assignment (a caller sets fields they should not).
- Unhandled exceptions return stack traces or empty 500s. A global handler gives one safe error shape.
- Without OpenAPI, front-end and partner teams guess the contract, and breaking changes go unnoticed.

4 Features and core concepts

Controllers vs minimal APIs
- Plain meaning: controllers are classes with attributes and filters. Minimal APIs are lambdas or static methods mapped to routes.
- Why it matters: controllers give structure for large APIs. Minimal APIs have less ceremony and start faster. Both run on the same endpoint routing, so mixing is allowed.
- Memorize: app.MapGet("/orders/{id}", (int id, IOrderService s) => s.Get(id));

Model binding
- Plain meaning: sources are route, query, header, body and form. Attributes like [FromBody], [FromQuery] and [FromServices] pick the source.
- Why it matters: wrong source causes silent nulls or 400 errors. [ApiController] gives automatic 400 on binding failure.

Validation (DataAnnotations, FluentValidation)
- Plain meaning: DataAnnotations are attributes like [Required] and [Range] on the model. FluentValidation is a library where rules are written in separate validator classes.
- Why it matters: DataAnnotations are quick for simple rules. FluentValidation handles conditional and cross-field rules and is easier to unit test. Minimal APIs do not validate automatically in older versions, so check the current .NET version (verify).

Filters
- Plain meaning: code that runs before or after an action (authorization, resource, action, exception, result filters). Minimal APIs have endpoint filters.
- Why it matters: cross-cutting logic like validation or audit sits here instead of inside every action. Filters see MVC context such as the bound arguments, middleware does not.

ProblemDetails
- Plain meaning: one standard error body. AddProblemDetails() registers it.
- Why it matters: clients parse one shape for 400, 404 and 500.

Global exception handling (IExceptionHandler)
- Plain meaning: an interface (from .NET 8) you implement to turn exceptions into ProblemDetails responses. Register with AddExceptionHandler and enable with UseExceptionHandler.
- Why it matters: one place maps domain exceptions to status codes and hides internals. Never return stack traces outside Development.

API versioning library
- Plain meaning: the Asp.Versioning packages let you declare versions per endpoint and read them from URL, header or query.
- Why it matters: lets v1 and v2 run side by side. Package names changed from older Microsoft.AspNetCore.Mvc.Versioning (verify).

OpenAPI generation (built-in, Swashbuckle, NSwag)
- Plain meaning: built-in support from .NET 9 generates the document (Microsoft.AspNetCore.OpenApi). Swashbuckle and NSwag also generate it and add UI or client generators.
- Why it matters: Swashbuckle is no longer in the default template from .NET 9, so know all three (verify). NSwag also generates typed C# and TypeScript clients, useful for your Angular front end.

DTO vs entity
- Plain meaning: an entity maps to a table. A DTO is the shape you send or receive over HTTP.
- Why it matters: prevents over-posting, hides internal columns, lets the contract and database change independently. Records work well for DTOs.

Mapping libraries pros and cons
- Plain meaning: AutoMapper, Mapster, Mapperly copy fields between types.
- Why it matters: they save typing, but hide logic and fail at runtime (AutoMapper). Mapperly generates code at compile time. Note AutoMapper licensing changed to commercial for new versions (verify). Hand-written mapping is acceptable for small APIs.

Output caching
- Plain meaning: server-side caching of whole responses, using AddOutputCache and a policy per endpoint.
- Why it matters: cheap speed-up for read endpoints. Differs from response caching, which only sets client or proxy cache headers. Vary by query or header to avoid serving wrong data to users.

5 Core focus (exam and interview)

- Asked most: controllers vs minimal APIs, where validation runs, how errors become ProblemDetails, DTO vs entity, and why not to expose entities.
- [ApiController] gives automatic 400 with ProblemDetails, binding source inference and attribute routing requirement.
- Order to remember: middleware, then routing, then filters, then action.
- Exceptions thrown inside actions reach the exception handler middleware, so register it early in the pipeline.
- Default JSON is System.Text.Json with camelCase.
- Interviewers like: "How do you version an API without breaking clients?"

------

6 Real-world use case

- Situation: an order service migrated from a Web API 2 app to ASP.NET Core 8 on Azure App Service. The Angular front end and two partner systems call it.
- Choice: controllers for the main resource-heavy API, FluentValidation for rules, DTO records, Mapperly for mapping, IExceptionHandler returning ProblemDetails, Asp.Versioning with URL segments, and NSwag to generate the TypeScript client in the pipeline.
- Trade-off: more files and layers than a single minimal API, but safer contracts and fewer partner support calls.
- When NOT to use it: for a tiny internal webhook or health endpoint, minimal APIs with no mapping library and no versioning are enough. Skip output caching on user-specific data.

7 Interview lens

- Q: Controllers or minimal APIs?
  A: Controllers for large, convention-heavy APIs with many filters. Minimal APIs for small services and speed. Both share the same routing and middleware.
- Q: Why DTOs when entities already have the fields?
  A: Entities expose internals and invite mass assignment. DTOs keep the public contract stable while the schema changes.
- Q: How do you handle errors consistently?
  A: Register an IExceptionHandler plus AddProblemDetails. Map known exceptions to status codes and return a generic message for unknown ones.
- Q: Output caching vs response caching?
  A: Output caching stores responses on the server and can be invalidated by tag. Response caching only sets HTTP headers for clients and proxies.

8 Common mistakes

- Returning EF entities: breaks when a navigation property creates a JSON cycle or leaks private columns. Fix: return DTOs.
- Validation only on the client: bad data reaches the database. Fix: validate on the server always.
- Catching exceptions in every action: inconsistent errors. Fix: one global handler.
- Output caching authenticated responses without varying: one user sees another's data. Fix: vary by user or do not cache.
- Putting the exception handler late in the pipeline: errors from earlier middleware escape. Fix: register it first.
- Using AutoMapper on hot paths with nested projections: slow and surprising SQL. Fix: map in the query with projection.

------

9 Mental model

Request -> middleware (exception handler, auth) -> routing -> filters -> model binding and validation -> action -> map entity to DTO -> response (ProblemDetails if anything fails)
OpenAPI describes the whole thing from outside.

10 Mini lab (30 minutes, local)

- Run: dotnet new webapi -n OrdersApi --use-controllers, then cd OrdersApi.
- Add a record CreateOrderDto(string Customer, decimal Amount) with [Required] and [Range(0.01, 100000)] attributes.
- Add an OrdersController POST that accepts the DTO and returns 201.
- Add AddProblemDetails and an IExceptionHandler class that maps InvalidOperationException to 409. Register with AddExceptionHandler and UseExceptionHandler.
- Throw InvalidOperationException from a GET action.
- Run with dotnet run. Post an invalid body and see a 400 ProblemDetails. Call the GET and see a 409 ProblemDetails.
- Open the OpenAPI document at /openapi/v1.json (verify path for your version).
- Clean up: delete the OrdersApi folder.

11 Revision summary

- Controllers and minimal APIs share routing and middleware.
- [ApiController] gives automatic 400 and binding inference.
- DataAnnotations for simple rules, FluentValidation for complex ones.
- ProblemDetails is the standard error body.
- IExceptionHandler is the global handler; register it first.
- Never expose entities. Use DTOs.
- Built-in OpenAPI in .NET 9 (verify); Swashbuckle and NSwag still common.
- Output caching is server-side. Response caching is header-only.
