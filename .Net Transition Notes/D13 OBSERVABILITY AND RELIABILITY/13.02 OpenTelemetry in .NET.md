1 What is it
- OpenTelemetry (OTel) is a vendor-neutral standard and set of libraries for producing telemetry from your app. Telemetry means traces, metrics and logs.
- In .NET it is built on types that already ship in the runtime: ActivitySource and Activity for traces, Meter for metrics, ILogger for logs.
- You instrument once, then choose where the data goes (Azure Monitor, Jaeger, Prometheus, any OTLP backend) by changing exporters, not code.
Legacy equivalent: Application Insights SDK with TelemetryClient, plus Serilog sinks, plus Windows performance counters in .NET Framework apps.

2 Why needed
- Each vendor SDK used its own API, so switching monitoring tools meant rewriting instrumentation.
- In microservices a request crosses many services. Without a shared trace ID passed along, you cannot see the full path.
- Without it: separate logs per service, no end-to-end view, lock-in to one vendor.

3 Before you read
- A trace is the story of one request across services. A span is one step inside it.
- A metric is a number sampled over time (requests per second, queue length).
- HTTP headers can carry extra data between services.
- Basic ILogger usage (note 1.06) and Application Insights awareness (note 13.01).

4 Features and core concepts
- Traces API (ActivitySource): ActivitySource creates Activity objects, and one Activity is one span. Why: this is how you add your own spans for business steps. Memorize: var src = new ActivitySource("Orders"); using var a = src.StartActivity("PlaceOrder");
- Metrics API (Meter): a Meter creates instruments such as Counter, Histogram and ObservableGauge. Why: cheap numeric data for dashboards and alerts. Memorize: var m = new Meter("Orders"); var c = m.CreateCounter<int>("orders.placed"); c.Add(1);
- Logs API: ILogger entries are exported as OTel log records with the current trace ID attached. Why: you can jump from a log line to its trace.
- Auto-instrumentation: ready-made libraries that create spans for ASP.NET Core, HttpClient, SqlClient and similar without your code. Why: you get most coverage with no edits. Packages are named OpenTelemetry.Instrumentation.* (verify names).
- Exporters (OTLP, Azure Monitor): an exporter sends data out of the process. OTLP is the standard wire protocol. Why: this is the only part that changes when you switch backend. Azure Monitor option is the Azure Monitor OpenTelemetry distro (verify package name).
- Collector: a separate service that receives OTLP, processes it (filter, batch, add attributes) and forwards it. Why: keeps backend credentials and routing out of apps; one place to change.
- Propagation across HTTP and messaging: the trace context travels in a header (W3C traceparent) on HTTP calls. For queues you must put it into message properties yourself and read it in the consumer. Why: without this the trace breaks at the queue.
- Baggage: small key-value pairs that travel along with the trace to downstream services. Why: share context such as tenant ID. Risk: it is sent in headers, so never put secrets or personal data in it.
- Resource attributes: fixed facts about the producing service (service.name, service.version, deployment.environment). Why: every backend groups and filters by service.name; if it is missing you get "unknown_service".
- Semantic conventions: agreed attribute names (http.request.method, db.system, url.full). Why: dashboards and queries work across services and tools. Check the current spec for exact names (verify).
- Memorize the minimum setup shape: builder.Services.AddOpenTelemetry().ConfigureResource(r => r.AddService("orders-api")).WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation().AddOtlpExporter()).WithMetrics(m => m.AddAspNetCoreInstrumentation().AddMeter("Orders").AddOtlpExporter());

5 Core focus (exam and interview)
- Most asked: difference between the OTel API (in runtime) and the SDK (packages that process and export).
- Know the three signals and how they link: trace ID on logs, exemplars are out of scope here.
- Default propagation format is W3C Trace Context.
- Custom ActivitySource and Meter names must be registered (AddSource, AddMeter) or nothing is collected.
- Sampling decides how many traces are kept. Head sampling decides at the start; tail sampling decides after the trace finishes and is usually done in the collector.
- OTel vs Application Insights SDK: OTel is the direction for new work, with Azure Monitor as one exporter (verify current Microsoft guidance).

6 Real-world use case
- Situation: an order system with an API, a worker and Service Bus between them. Users report slow checkout, and nobody can tell which service is slow.
- Choice: add OTel to both services, auto-instrumentation plus one custom ActivitySource for the checkout steps. Copy traceparent into Service Bus message properties and restore it in the worker. Export OTLP to a collector, which forwards to Azure Monitor.
- Result: one trace shows API, database, queue wait and worker time together.
- Trade-off: extra packages and a collector to run, and high-volume tracing costs money unless sampled.
- When not to use: a single small internal app already well served by built-in Application Insights, where you gain little and add moving parts.

7 Interview lens
- Q: What is the difference between ActivitySource and Tracer in .NET? A: .NET uses ActivitySource and Activity as its native tracing API, and OTel maps spans to Activity. No separate Tracer type is needed.
- Q: Why does a trace break at a message queue? A: HTTP instrumentation injects the header automatically, but queues have no standard hook in all SDKs. You must inject and extract the trace context in message properties.
- Q: Why use a collector instead of exporting straight from apps? A: One place for routing, batching, filtering and credentials. Backend changes need no app redeploy.
- Q: How do you control telemetry cost? A: Sampling, dropping noisy spans and metrics in the collector, and avoiding high-cardinality attributes.

8 Common mistakes
- Custom source or meter not registered: your spans and metrics never appear. Fix: AddSource("Name") and AddMeter("Name").
- No service.name: all services show as one unknown service. Fix: set it in ConfigureResource.
- High-cardinality metric labels (user ID, order ID): memory and bill explode. Fix: use low-cardinality labels; put IDs on spans or logs instead.
- Sensitive data in baggage or span attributes: leaks to headers and backends. Fix: allow-list what you attach.
- Sampling at 100 percent in production: large cost. Fix: sample, and keep errors.
- Broken trace at queues or background jobs: carry context manually.

9 Mental model
- Your code makes spans, numbers and logs, plus a context tag (trace ID).
- App code -> OTel SDK (processing) -> exporter -> collector (optional) -> backend.
- The tag rides along on every call and message so the backend can stitch one story.

10 Mini lab (30 to 40 minutes, local)
- Install .NET SDK and Docker. Run: dotnet new webapi -n OtelLab
- Add packages: OpenTelemetry.Extensions.Hosting, OpenTelemetry.Instrumentation.AspNetCore, OpenTelemetry.Instrumentation.Http, OpenTelemetry.Exporter.OpenTelemetryProtocol (verify current versions).
- In Program.cs add the setup shown in section 4 with ConfigureResource service name "otel-lab". Add a custom ActivitySource "Lab" and one StartActivity inside an endpoint.
- Start Jaeger (all-in-one image, verify current image name) with ports 16686 and 4317 mapped. Run the app with OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317.
- Call the endpoint a few times with curl. Open http://localhost:16686, choose service otel-lab.
- Expected: traces with the ASP.NET Core span and your custom "Lab" span nested inside. Remove the AddSource line, call again, and notice your span disappears.
- Clean-up: stop and remove the Jaeger container; delete the OtelLab folder.

11 Revision summary
- OTel gives one standard for traces, metrics and logs; only the exporter changes per backend.
- .NET API types: ActivitySource/Activity for traces, Meter for metrics, ILogger for logs.
- Custom sources and meters must be registered with AddSource and AddMeter.
- OTLP is the standard protocol; the collector routes, batches and filters.
- W3C traceparent carries context over HTTP; messaging needs manual propagation.
- Set service.name or services appear as unknown.
- Baggage travels in headers: no secrets or personal data.
- Avoid high-cardinality metric labels; use sampling to control cost.
