1 What is it
- Observability is the ability to understand what is happening inside a running system by looking at the data it emits: logs, metrics and traces.
- Logs are timestamped records of events. Metrics are numbers measured over time. Traces follow one request across all the services it touches.
- Think of a doctor with a thermometer (metric), a patient diary (log) and an X-ray of the journey of one meal through the body (trace).
- Legacy equivalent: Event Viewer, log4net text files, IIS logs and Performance Monitor counters, each read separately by hand.

2 Why needed
- In a monolith you open one log file. In many services, one user request touches five processes and three machines.
- Without shared IDs and good data, you cannot say which service is slow or failing.
- Without it, incidents take hours to diagnose, and you find out about problems from customers.

4 Features and core concepts
- Logs: discrete event records. They give the detail of what happened. Keep them structured.
- Metrics: numeric measurements (request count, CPU, latency). Cheap to store and good for alerts and trends.
- Traces: the path of one request through services, made of timed steps called spans. They show where time is spent.
- Correlation and trace IDs: one ID attached to a request and passed to every service it calls. It lets you join logs and traces for one request.
- W3C trace context: the standard HTTP header (traceparent) that carries the trace ID and parent span ID between services, so tools from different vendors interoperate.
- Structured logs: logs as named fields (key and value), not free text. They can be filtered and counted. Example: logger.LogInformation("Order {OrderId} paid", id);
- Log levels and cost: Debug and Trace in production produce huge volume. Ingestion is billed per GB in most platforms (verify your platform). Pick levels on purpose.
- Sampling: keep only a fraction of traces or telemetry to control cost. Head sampling decides at the start of a request. Tail sampling decides after seeing the whole trace, so errors and slow requests can be kept.
- Cardinality: the number of distinct values of a metric label. A label like userId or requestId creates millions of series and breaks or bills heavily. Use low-cardinality labels (status code, route template).
- RED method: for services, watch Rate, Errors, Duration. It answers "are users happy".
- USE method: for resources (CPU, disk, memory), watch Utilization, Saturation, Errors. It answers "is the machine the problem".
- Golden signals: latency, traffic, errors, saturation. Same spirit as RED plus USE.
- Business metrics: orders per minute, payments failed, signups. They show real impact that CPU graphs miss.

5 Core focus (exam and interview)
- Know the three pillars and what question each one answers: logs say what, metrics say how much, traces say where.
- Know why correlation IDs and W3C traceparent matter in microservices.
- Know the cardinality trap and the cost levers (levels, sampling, retention).
- Know RED for services and USE for resources, and name the golden signals.
- Header format to remember: traceparent has version, trace-id, parent-id and flags (verify exact field widths on w3.org).
- Percentiles (p95, p99) tell more than averages.

6 Real-world use case
- Situation: an order API on App Service calls a pricing service, a Service Bus consumer and Azure SQL. Customers report slow checkout, but the API dashboard looks fine.
- Choice: add trace context propagation across HTTP and messaging, structured logs with the trace ID, RED metrics per endpoint, and a business metric for checkout success.
- Result: the trace shows the delay is in the pricing service call to a slow SQL query, not in the API.
- Trade-off: more telemetry means more cost and more setup. Sampling and log level discipline are needed.
- When not to: do not trace every internal function call or log every request body. For a small single-process internal tool, plain structured logs and a few metrics are enough.

7 Interview lens
- Q: What is the difference between monitoring and observability?
  A: Monitoring checks known failure conditions with set alerts. Observability lets you ask new questions about unknown problems using rich telemetry.
- Q: How do you follow one request across ten services?
  A: Generate or accept a trace ID at the edge, pass it by the W3C traceparent header, and propagate it through message properties too. Log it in every service.
- Q: What is cardinality and why does it matter?
  A: It is the count of unique label values on a metric. High cardinality explodes storage and cost, so never use IDs as labels.
- Q: How do you control telemetry cost?
  A: Set sensible log levels, sample traces, drop noisy health-check data, and set retention by value of the data.

8 Common mistakes
- Free-text logs: you cannot query them at scale. Fix: use structured logging with named properties.
- No correlation ID through queues: traces break at messaging. Fix: put trace context in message properties.
- Alerting on averages: hides slow tail. Fix: alert on p95 or p99 and error rate.
- Putting userId in metric labels: bill and memory spike. Fix: use traces or logs for per-user detail.
- Logging secrets or personal data: compliance breach. Fix: mask and exclude sensitive fields.
- Debug level left on in production: cost and noise. Fix: set level per environment.

9 Mental model
- Metrics tell you something is wrong. Traces tell you where. Logs tell you why.
- Metric alert -> open trace for a slow request -> read logs for that trace ID.

10 Mini lab
Time: about 30 minutes. Tools: .NET SDK, a terminal, Serilog packages from NuGet.
- Step 1: run dotnet new webapi -n ObsLab and cd ObsLab.
- Step 2: add packages: dotnet add package Serilog.AspNetCore and dotnet add package Serilog.Sinks.Console.
- Step 3: in Program.cs, configure Serilog with a console sink and an output template that includes the TraceId property, and call builder.Host.UseSerilog().
- Step 4: in an endpoint, write logger.LogInformation("Fetching forecast for {City}", city);
- Step 5: run the app and call the endpoint with curl -H "traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01" http://localhost:5000/weatherforecast (use your actual port).
- Expected result: the log line shows City as a named field and the TraceId 0af7651916cd43dd8448eb211c80319c.
- Step 6: send the same request without the header and notice a new TraceId is generated.
- Clean-up: stop the app and delete the ObsLab folder.

11 Revision summary
- Three pillars: logs (what), metrics (how much), traces (where).
- A trace is made of spans; the trace ID joins everything for one request.
- W3C traceparent carries trace context across services.
- Structured logs use named fields and can be queried.
- Sampling and log levels control cost; ingestion is usually billed by volume (verify).
- High-cardinality labels break metrics.
- RED for services, USE for resources, plus the four golden signals.
- Alert on percentiles and business impact, not averages alone.
