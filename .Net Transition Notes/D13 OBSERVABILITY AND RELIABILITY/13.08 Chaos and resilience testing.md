13.08 Chaos and resilience testing [P4 O]. SHORT note: sections 1, 4, 6 and 11.

1 What is it
- Chaos and resilience testing means deliberately breaking parts of a system, in a controlled way, to see whether it survives and recovers as designed.
- Azure Chaos Studio is the Azure service that injects faults into resources such as VMs, AKS and Cosmos DB (verify the current list of supported targets).
- Legacy equivalent: manually pulling a network cable or stopping IIS on a test server before go-live and watching what happens, but planned, repeatable and automated.

4 Features and core concepts
- Azure Chaos Studio: a managed service that runs fault experiments against Azure resources. Why it matters: you test failures on purpose before production does it for you.
- Experiment: a saved definition of which faults run, on which targets, in which order and for how long. Why it matters: it makes the test repeatable and reviewable.
- Fault types: service-direct faults act on the resource itself (for example stopping a VM). Agent-based faults run inside the machine (for example CPU or memory pressure). Why it matters: it tells you which setup each test needs (verify the current fault library).
- Managed identity and permissions: the experiment needs its own identity with rights on the targets. Why it matters: without the right role assignment the experiment fails to start.
- Game day: a planned session where the team runs failure scenarios live and practices incident response. Why it matters: it tests people, runbooks and alerts, not only code.
- Hypothesis and blast radius: state what you expect to happen, and limit how much can be affected. Why it matters: it keeps the test safe and the result meaningful.
- Steady-state check: define normal behaviour first (error rate, latency, queue depth). Why it matters: without a baseline you cannot tell if the system survived.
- Capacity modeling: estimating how much load and how many resources the system needs, including under failure (for example one zone lost). Why it matters: surviving a failure is useless if the remaining capacity cannot carry the load.
- Observability cost control: deciding what to log, trace and keep, using sampling and retention limits. Why it matters: telemetry bills grow fast, and chaos tests produce extra data.
- Memorize: start in a non-production environment, run one fault with a short duration, and keep a stop or abort path ready.

6 Real-world use case
- Situation: an order API runs on AKS across three zones, using Service Bus and Azure SQL with failover groups. The team claims it survives a zone loss.
- Choice made: a Chaos Studio experiment stops one node pool's workload in a staging cluster, then adds network latency to the SQL connection. The hypothesis is that p95 latency stays under target and no messages are lost. Alerts and the runbook are checked during a game day.
- Result: the test shows retries piling up because timeouts were too long. The team fixes timeouts and the circuit breaker settings, then re-runs.
- Trade-off: it costs engineering time, needs a realistic test environment and carries some risk if the blast radius is too wide.
- When NOT to use it: when you have no monitoring, no baseline, no rollback path or no resilience patterns yet. Fix those first. Also avoid it on production without approval, a small blast radius and an on-call team ready.

11 Revision summary
- Chaos testing injects failures deliberately to prove resilience instead of assuming it.
- Azure Chaos Studio runs experiments made of faults against targeted Azure resources.
- Service-direct faults hit the resource itself. Agent-based faults run inside the VM or node.
- The experiment needs a managed identity with the right role on its targets.
- Always write a hypothesis, a steady-state baseline and a limited blast radius first.
- A game day tests people, alerts and runbooks, not only the system.
- Capacity modeling must include failure cases such as one zone lost.
- Control observability cost with sampling, retention and log-level discipline.
- Verify the current Chaos Studio fault list and supported targets on Microsoft Learn.
