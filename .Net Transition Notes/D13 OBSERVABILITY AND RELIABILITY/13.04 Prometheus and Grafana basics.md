13.04 Prometheus and Grafana basics
Tags: P3 R L (no K tag, so full note with mini lab)

---

1 What is it

- Prometheus is a monitoring system that collects numbers about your running applications and servers at regular intervals and stores them with timestamps. A number measured over time is called a metric.
- Grafana is a separate tool that reads data from Prometheus (and other sources) and draws it as graphs and dashboards.
- Prometheus works by pulling. It visits each application's metrics page on a schedule and copies the numbers. This visit is called a scrape.
- Legacy equivalent: Windows Performance Monitor counters plus a custom dashboard, or SCOM with perfmon data, now done in a cloud-native way.

2 Why needed

- Kubernetes pods start and stop all the time, so you cannot log in to a server and look at counters by hand.
- Prometheus finds targets automatically and keeps history, so you can answer "was the API slow at 2 AM?"
- Without it, you learn about problems from users. With it, alerts fire before users notice.
- Azure Monitor works well for Azure resources, but Prometheus is the common standard on Kubernetes and in job interviews.

3 Before you read

- Metric: a named number with a timestamp, such as requests served so far.
- Kubernetes pod and service basics (note 8.04 and 8.05).
- HTTP endpoint: a URL that returns text when you call it.
- Percentile latency idea: p95 means 95 percent of requests were faster than this value.

4 Features and core concepts

- Scraping model: Prometheus calls /metrics on each target every N seconds (default interval is 1 minute, verify). Why it matters: a dead target is visible at once because the scrape fails.
- Target and job: a target is one thing being scraped. A job is a group of similar targets. Why it matters: you query and alert by job.
- Labels: key-value tags on a metric, such as method="GET" or status="500". Why it matters: one metric name can be sliced many ways. Too many label values (high cardinality) makes Prometheus slow and costly.
- Counter: a number that only goes up (total requests, total errors). Why it matters: you never read it raw, you take its rate.
- Gauge: a number that goes up and down (memory in use, queue length, active connections). Why it matters: it shows current state.
- Histogram: counts observations in buckets (how many requests took under 0.1s, 0.5s, 1s). Why it matters: it lets you compute p95 and p99 latency.
- PromQL basics: the query language. Memorize these:
  - rate(http_requests_total[5m])
  - sum by (status) (rate(http_requests_total[5m]))
  - histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))
  Why it matters: rate turns a counter into per-second speed, sum by groups the result, histogram_quantile gives percentiles.
- Alertmanager: a separate component that receives alerts from Prometheus rules, groups them, removes duplicates, silences them and sends them to email, Teams or paging tools. Why it matters: Prometheus decides when to alert, Alertmanager decides who hears about it.
- Grafana dashboards: panels built on PromQL queries, with variables and folders. Why it matters: one shared view for the team, can be saved as JSON in Git.
- Exporters: small programs that expose metrics for things that do not do so themselves. Examples: node_exporter for Linux hosts, kube-state-metrics for Kubernetes objects. Why it matters: lets you monitor databases and servers without changing their code.
- ELK and Loki awareness: ELK (Elasticsearch, Logstash, Kibana) and Loki store logs, not metrics. Loki is Grafana's lightweight log store. Why it matters: Prometheus answers "how much and how fast", logs answer "what exactly happened".

5 Core focus (exam and interview)

- Prometheus pulls. Push is only for short jobs through Pushgateway.
- Metric types: counter, gauge, histogram (and summary, which cannot be combined across instances).
- Always use rate() on counters, never plot the raw value.
- Default scrape interval is 1 minute and default local retention is 15 days (verify).
- Prometheus is not built for long-term storage or logs. Use remote storage or managed services for that.
- High cardinality labels (user ID, request ID) are the top mistake.
- Azure link: Azure Managed Prometheus and Azure Managed Grafana exist for AKS (verify names and current features).

6 Real-world use case

- Situation: an order API on AKS shows random slowness. Users complain but there are no errors.
- Choice: add the prometheus-net library to the .NET API, expose /metrics, and run Prometheus (or Azure Managed Prometheus) to scrape it. Build a Grafana dashboard with request rate, error rate and p95 latency per endpoint. Add an Alertmanager rule: p95 above 1 second for 10 minutes.
- Result: the dashboard shows one endpoint with slow database calls. The team fixes the query.
- Trade-off: you run and tune more components yourself. Cardinality and storage need care.
- When NOT to use it: a small app on App Service with no Kubernetes. Application Insights alone is simpler and cheaper to operate.

7 Interview lens

- Q: Why does Prometheus pull instead of push?
  A: Pull makes a dead target obvious and keeps control with the monitor. Push suits only short-lived jobs through Pushgateway.
- Q: How do you get p95 latency?
  A: Record request duration in a histogram, then use histogram_quantile(0.95, ...) over the rate of the bucket series.
- Q: Counter vs gauge?
  A: A counter only increases and you read its rate. A gauge moves both ways and you read it directly.
- Q: What is high cardinality and why is it bad?
  A: Too many unique label values create too many time series. Memory and query time grow fast and Prometheus can fall over.

8 Common mistakes

- Plotting a raw counter. The graph only climbs. Fix: use rate().
- Using user ID or URL with IDs as a label. Prometheus memory explodes. Fix: label by route template and status only.
- Alerting on every spike. The team ignores alerts. Fix: alert on symptoms for a set duration, such as 10 minutes.
- Treating Prometheus as long-term storage. Data disappears after retention. Fix: use remote write or a managed service.
- Using summary metrics across many pods. Percentiles cannot be added up. Fix: use histograms.

9 Mental model

- Think of a school registrar walking classrooms every minute with a clipboard.

  App /metrics page <-- scraped by --> Prometheus (stores + queries)
  Prometheus --> Alertmanager --> email / Teams / pager
  Prometheus --> Grafana --> dashboards

- Prometheus collects and calculates. Grafana only displays. Alertmanager only notifies.

10 Mini lab (about 35 minutes, local Docker, free)

- Step 1: create a folder with a file prometheus.yml containing one scrape job that targets localhost:9090 (Prometheus scraping itself) every 15s.
- Step 2: run Prometheus with Docker, mount the file, and publish port 9090.
- Step 3: run Grafana with Docker and publish port 3000. Log in (default admin/admin, change it).
- Step 4: in Grafana add a data source of type Prometheus. Use the Prometheus container address (put both containers on one Docker network, or use host.docker.internal).
- Step 5: in the Prometheus UI at localhost:9090, run: rate(prometheus_http_requests_total[5m]). You should see lines per handler.
- Step 6: in Grafana create a dashboard, add a panel with the same query. You should see the same graph.
- Step 7 (optional): add a .NET sample using prometheus-net, expose /metrics, and add it as a second scrape target.
- Expected result: a Grafana panel showing live request rate from Prometheus.
- Clean-up: stop and remove both containers, the Docker network and the folder.

11 Revision summary

- Prometheus pulls metrics from /metrics on a schedule (scrape).
- Metric types: counter (only up), gauge (up and down), histogram (buckets).
- Labels slice data. High cardinality labels break Prometheus.
- rate() on counters, histogram_quantile() for percentiles.
- Alertmanager groups, silences and routes alerts. Prometheus only evaluates rules.
- Grafana displays data. It does not store metrics itself.
- Exporters expose metrics for systems that cannot do it themselves.
- Metrics say how much and how fast. Logs (ELK, Loki) say what happened.
