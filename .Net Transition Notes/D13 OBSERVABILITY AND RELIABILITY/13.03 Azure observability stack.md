1 What is it
- Azure observability stack means the set of Azure tools that collect, store, query and alert on telemetry from your apps and infrastructure.
- Telemetry is the data an app emits about itself: logs (events), metrics (numbers over time) and traces (the path of one request).
- Application Insights collects app telemetry. Log Analytics stores it. KQL (Kusto Query Language) queries it. Azure Monitor alerts on it. Grafana draws dashboards from it.
- Legacy equivalent: Event Viewer, IIS logs, Windows performance counters and log4net files, now collected centrally instead of read machine by machine.

2 Why needed
- In the cloud, one request may cross an App Service, a queue, a function and a database. No single machine holds the full story.
- Without central telemetry, you learn about outages from users, and you debug by guessing.
- Without retention and cost control, the telemetry bill grows silently.

3 Before you read
- Logs, metrics and traces are the three telemetry types.
- A resource in Azure can send diagnostic data to a destination you choose.
- A distributed trace follows one request across services using a shared ID.
- Kubernetes pods are containers managed by AKS (needed only for the Container Insights and Prometheus part).

4 Features and core concepts
- Application Insights SDK vs OpenTelemetry distro
  - Application Insights is Azure's application performance monitoring (APM) service, meaning it measures how an app behaves. The classic SDK is Microsoft's own library. The OpenTelemetry distro (Azure Monitor OpenTelemetry Distro) sends the same data using the open OpenTelemetry standard.
  - Why it matters: Microsoft now steers new work to OpenTelemetry (verify), and it avoids vendor lock-in. Existing classic SDK apps still work.
  - Memorize: builder.Services.AddOpenTelemetry().UseAzureMonitor(); (package name and method may change, verify)
- KQL queries
  - KQL is a read-only query language. You write a table name, then pipe (|) through steps like where, summarize and project.
  - Why it matters: every Azure Monitor screen is a KQL query underneath, and interviews ask for simple ones.
  - Memorize: requests | where success == false | summarize count() by bin(timestamp, 5m)
- Workbooks
  - A workbook is an interactive report built from KQL queries and text in the portal.
  - Why it matters: you share an investigation view without exporting data.
- Alerts (metric, log, smart)
  - Metric alert: fires when a number crosses a threshold, such as CPU above 80 percent. Fast and cheap.
  - Log alert: runs a KQL query on a schedule and fires on the result. More flexible, a bit slower.
  - Smart detection: Application Insights learns normal behavior and flags anomalies such as a sudden failure rate rise (verify current naming).
  - Why it matters: choosing the wrong type gives late or noisy alerts.
- Action groups
  - An action group is a reusable list of who or what gets notified: email, SMS, push, webhook, Azure Function, Logic App, ITSM.
  - Why it matters: one group serves many alerts, so you change the on-call target in one place.
- Availability tests
  - A synthetic probe that calls your URL from several Azure locations on a schedule and records pass or fail.
  - Why it matters: it detects an outage even when no real user is online. Check current test types and which are retiring (verify).
- Container Insights
  - An Azure Monitor feature that collects node and pod metrics and container logs from AKS.
  - Why it matters: it shows OOMKilled pods, restarts and node pressure without installing your own stack.
- Managed Prometheus and Grafana
  - Prometheus is an open metrics system. Azure Monitor managed service for Prometheus runs it for you. Azure Managed Grafana hosts the dashboards.
  - Why it matters: Kubernetes teams already know PromQL and Grafana, and you avoid operating the servers.
- Dashboards
  - Portal dashboards pin tiles. Grafana dashboards give richer charts.
  - Why it matters: one overview screen for on-call beats ten open tabs.
- Retention and cost
  - Log Analytics bills mainly by data ingested (GB), plus retention beyond the free period. Pricing tiers and free retention days change (verify).
  - Why it matters: this is the most common surprise bill. Levers: sampling, daily cap, table plans such as Basic Logs (verify), shorter retention, and dropping noisy logs.
- Application map
  - An auto-drawn diagram of your services and the calls between them, showing failure rate and latency on each link.
  - Why it matters: it finds the slow or failing dependency fast. It needs correlated telemetry to be accurate.

5 Core focus (exam and interview)
- Most asked: which alert type to use, how to cut telemetry cost, and how to trace one request across services.
- Application Insights is now workspace-based: its data lives in a Log Analytics workspace. Classic standalone resources are retired (verify).
- Metric alerts are near real time. Log alerts depend on the query frequency you set.
- Sampling reduces volume but loses some individual records. Metrics stay accurate when sampling is done correctly.
- Action groups are separate resources, shared by many alert rules.
- Diagnostic settings decide where a resource sends its logs: Log Analytics, storage account or Event Hubs.
- Defaults and limits such as retention days, daily cap and alert rule counts: (verify) on Microsoft Learn.

6 Real-world use case
- Situation: a legacy order system moved to App Service plus Service Bus plus Azure SQL. Support had no way to follow an order across the three.
- Choice: Application Insights through the OpenTelemetry distro, one Log Analytics workspace, a workbook for order flow, a log alert on failed orders, an action group paging on-call, and an availability test on the health endpoint.
- Trade-off: one shared workspace is simple to query but mixes teams and costs. Per-team workspaces give cost clarity but make cross-service queries harder.
- When NOT to use it: if the company already standardizes on Datadog or Splunk, forcing Azure Monitor creates two systems. Also avoid logging every debug line at full volume, since the cost grows fast.

7 Interview lens
- Q: Metric alert or log alert for a rising failure rate?
  - A: Metric alert if the platform emits a failure metric, because it is faster and cheaper. Log alert when you need a custom KQL condition, such as failures for one customer tier.
- Q: How do you trace one request across App Service and Service Bus?
  - A: Use OpenTelemetry or Application Insights with W3C trace context so the operation ID propagates in message properties. Then view it in transaction search or the application map.
- Q: Your Application Insights bill doubled. What do you do?
  - A: Find the top tables by GB in Log Analytics. Then add sampling, remove noisy logs, set a daily cap and cut retention where allowed.
- Q: Why use managed Prometheus and Grafana on AKS?
  - A: You keep standard PromQL and dashboards without running or patching the servers. Container Insights covers basic health, Prometheus covers custom app metrics.

8 Common mistakes
- Telemetry sent only to a local file: after a pod restart the evidence is gone. Fix: ship to Log Analytics.
- Alerts with no action group: they fire and nobody is told. Fix: attach an action group and test it.
- Alerting on every error: alert fatigue and ignored pages. Fix: alert on symptoms such as failure rate and latency.
- No sampling on a high-traffic API: cost spike. Fix: enable sampling and review ingestion weekly.
- Missing correlation across queues: the trace breaks at Service Bus. Fix: propagate trace context in message properties.
- Availability test hits a page behind login: constant false failures. Fix: test a dedicated anonymous health endpoint.

9 Mental model
App -> (OpenTelemetry/App Insights) -> Log Analytics workspace
                                           |
            KQL -> Workbooks / Grafana (see)
            KQL -> Alert rule -> Action group (act)
AKS -> Container Insights + Prometheus -> same workspace / Grafana
Probes (availability tests) -> same workspace

Think: collect, store, query, then see or act. Cost lives in the "store" step.

10 Mini lab
Time: about 30 minutes. Azure free tier, plus a local ASP.NET Core app.
- Create a resource group, a Log Analytics workspace and a workspace-based Application Insights resource in the portal. Copy its connection string.
- Create a small ASP.NET Core minimal API locally. Add the Azure Monitor OpenTelemetry package and call UseAzureMonitor (check the current package name on Microsoft Learn, verify). Set the connection string as an environment variable.
- Run the app. Call one endpoint about 20 times, and one endpoint that throws an exception about 5 times.
- Wait a few minutes. In Application Insights, open Logs and run: requests | summarize count() by resultCode
- Open Application map and Failures to see the exception.
- Create a log alert on exceptions above 3 in 5 minutes. Attach a new action group that sends an email to you.
- Add an availability test only if you have a public URL (optional).
Expected result: request counts by status code, the failing endpoint visible in Failures, and an alert email after the next batch of errors.
Clean-up: delete the resource group, which removes the workspace, Application Insights, alert rule and action group.

11 Revision summary
- Telemetry types: logs, metrics, traces.
- Application Insights is workspace-based and stores data in Log Analytics.
- OpenTelemetry distro is the forward path, the classic SDK still works (verify).
- KQL pattern: table | where | summarize | project.
- Metric alerts are fast, log alerts are flexible.
- Action groups are reusable notification targets.
- Cost is driven by ingestion volume: sample, filter, cap, shorten retention.
- Container Insights is basic AKS health, managed Prometheus plus Grafana is custom metrics and dashboards.
