1 What is it
- Performance testing means running your system under controlled, measured traffic to see how fast it responds and where it breaks.
- Start with a baseline: the normal numbers (latency, throughput, CPU, memory, error rate) at today's typical load, recorded before you change anything.
- Four test shapes: load (expected peak), stress (beyond peak until failure), soak (normal load for many hours), spike (sudden jump and drop).
- Tools: k6 (JavaScript scripts, runs from the command line), JMeter (GUI and XML plans), Azure Load Testing (managed service that runs JMeter or k6 scripts at scale).
- Legacy equivalent: Visual Studio web performance and load tests, or JMeter runs against an IIS-hosted MVC app with PerfMon counters.

2 Why needed
- Functional tests prove the code is correct. They do not prove it stays fast with 2,000 users.
- Without a baseline you cannot tell if a release made things slower.
- Without load tests, the first real load test is a production incident.
- Without percentile latency, an average of 200 ms can hide users waiting 5 seconds.

3 Before you read
- Latency is the time one request takes. Throughput is requests completed per second.
- Percentile: p95 means 95 percent of requests were faster than this value.
- Thread pool: the fixed set of worker threads .NET uses to run requests and async continuations.
- Application Insights: Azure's telemetry service that collects request, dependency and exception data.

4 Features and core concepts
- Baseline: recorded normal-load numbers. Why it matters: it is the reference for every later comparison and for deciding what "slow" means.
- Load test: run at expected peak traffic for a set time. Why it matters: confirms you meet your target at the busiest normal hour.
- Stress test: keep raising load until errors or latency collapse. Why it matters: finds the breaking point and shows how the system fails (graceful or crash).
- Soak test: moderate load for 4 to 24 hours. Why it matters: exposes memory leaks, connection leaks and slow degradation that short tests miss.
- Spike test: sudden jump, then drop. Why it matters: checks autoscale delay, cold starts and queue buildup.
- k6: write the test in JavaScript, set virtual users (VUs) and duration, define thresholds that fail the run. Why it matters: easy to put in a pipeline as a pass or fail gate.
- JMeter: thread groups, samplers, listeners, usually run headless with a .jmx plan. Why it matters: very common in Indian enterprise projects, so interviewers ask about it.
- Azure Load Testing: managed service that runs your JMeter or k6 script from many Azure-hosted engines and shows server-side metrics next to client results. Why it matters: no need to build your own load generator machines. (verify current script format support)
- Bottleneck analysis: find which resource is saturated first.
  - CPU: high CPU with rising latency means compute-bound code.
  - Memory: growing working set, frequent gen 2 GC, means leaks or large allocations.
  - IO: slow disk or network calls, high wait times.
  - Database: slow queries, missing indexes, connection pool exhaustion.
  - Locks: blocking and deadlocks in SQL, or lock contention in code.
  - Thread pool: starvation from sync-over-async; latency rises while CPU stays low.
- Production profiling: dotnet-trace and dotnet-counters for live .NET processes; Application Insights profiler for traces of slow requests in Azure. Why it matters: some problems only appear with real traffic and data.
- Percentile latency (p95, p99): the slow tail. Why it matters: SLOs are written on p95 or p99, not averages.
- Little's law basics: L = lambda x W. Concurrent requests in the system equals arrival rate times average time in system. Why it matters: at 100 requests per second and 0.5 s average time, about 50 requests are in flight; use it to size pools and instances.
- Command worth memorizing:
  - k6 run --vus 50 --duration 5m script.js

5 Core focus (exam and interview)
- Most asked: name the four test types and say when you use each.
- Most asked: why p99 matters more than average.
- Most asked: how you find a bottleneck step by step (watch CPU, memory, IO, DB, locks, thread pool in that order of cheapness to check).
- Always test in an environment shaped like production (same data volume, same SKU or close to it). A tiny database gives meaningless numbers.
- Warm up first. Ignore the first minute (JIT, cold caches).
- Separate the load generator from the system under test, or the generator becomes the bottleneck.
- Defaults and limits: set explicit thresholds (example: p95 under 500 ms, error rate under 1 percent). Check Azure Load Testing quotas on Microsoft Learn (verify).

6 Real-world use case
- Situation: a legacy MVC app was moved to ASP.NET Core on App Service. Marketing plans a campaign that triples traffic.
- Choice: record a baseline on the current system, then run a k6 load test at 3x peak in a staging copy with production-size data. Run it from Azure Load Testing so you can see App Service CPU and Azure SQL DTU or vCore usage beside client latency.
- Finding: p95 doubles at 2x load while CPU is only 35 percent. The profiler and dotnet-counters show thread pool starvation from a sync-over-async call in one filter. Fix it, retest, then add a 30-minute k6 smoke test with thresholds to the pipeline.
- Trade-off: realistic tests cost time, money and a production-like environment, and test data must be prepared.
- When NOT to use it: do not run stress tests against production or shared dependencies (payment gateways, third-party APIs) without permission. Do not load test before functional bugs are fixed, since errors will hide the real picture.

7 Interview lens
- Q: What is the difference between load, stress, soak and spike testing?
  - A: Load checks expected peak. Stress pushes past it to find the breaking point. Soak runs for hours to find leaks. Spike jumps suddenly to test autoscale and recovery.
- Q: Why use p95 and p99 instead of average?
  - A: Averages hide the slow tail. A few very slow requests still hurt real users and break SLOs.
- Q: CPU is low but latency is high under load. What do you check?
  - A: Thread pool starvation, blocking calls, database waits, lock contention, or a slow downstream dependency. Use dotnet-counters and traces to confirm.
- Q: How would you use Little's law?
  - A: Concurrency equals arrival rate times time in system. It tells me how many concurrent requests to expect, so I can size connection pools, instances and test VUs.

8 Common mistakes
- Testing without a baseline: you cannot prove improvement or regression. Fix: record numbers first and store them.
- Using averages: production complaints appear while the dashboard looks fine. Fix: report p95 and p99.
- Tiny test database: queries are fast in test and slow in production. Fix: use production-scale data (masked).
- Load generator on the same machine: results are distorted by the generator's own CPU. Fix: run it elsewhere.
- Ignoring warm-up: first requests skew results. Fix: add a ramp-up and discard it.
- Only testing the happy path: real traffic includes logins, searches and writes. Fix: model a realistic mix.
- Testing once: performance drifts with each release. Fix: automate a smaller test in CI.

9 Mental model
- A highway with a toll booth: more cars (load) is fine until the slowest booth (bottleneck) saturates, then queues grow.

```
users -> load balancer -> app (CPU, threads) -> cache -> database
          measure at every hop; the first saturated hop is the bottleneck
```

10 Mini lab
Time: about 30 minutes. Tools: local machine, k6, a small ASP.NET Core API.
- Step 1: create a minimal API with dotnet new web. Add a GET /fast that returns text, and a GET /slow that does Thread.Sleep(200) and returns text.
- Step 2: run it with dotnet run and note the URL.
- Step 3: install k6 and create script.js. Import http from k6/http, loop calling /fast and /slow, and set options with 20 vus, duration 1m and a threshold of http_req_duration p(95)<300.
- Step 4: in a second terminal run dotnet-counters monitor on the API process to watch CPU and thread pool queue length.
- Step 5: run k6 run script.js.
- Expected result: /fast is quick, /slow is around 200 ms or more, the threshold check shows as failed or passed depending on mix, and k6 prints p95 and p99 values. Increase vus to 200 and watch the thread pool queue grow and latency rise while CPU stays modest.
- Clean-up: stop the API and k6, delete the project folder, uninstall tools if not needed.

11 Revision summary
- Baseline first, then change, then compare.
- Load is expected peak, stress is past peak, soak is long, spike is sudden.
- Use p95 and p99, not averages.
- Check CPU, memory, IO, database, locks and thread pool to find the bottleneck.
- Low CPU with high latency often means thread pool starvation.
- Little's law: concurrency equals arrival rate times time in system.
- Test with production-like data, away from the load generator, after a warm-up.
- Put a small thresholded test into the pipeline as a gate.
