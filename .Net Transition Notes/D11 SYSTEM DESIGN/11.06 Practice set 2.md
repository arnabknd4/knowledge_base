11.06 Practice set 2 [P3 R L]. FULL note, new-to-you depth (no K tag), with mini lab.

1 What is it

- A second set of system design exercises. Each one is a classic interview problem: chat, news feed, e-commerce checkout and orders, payment processing, job scheduler, logging and metrics pipeline, search autocomplete, booking with inventory, multi-tenant SaaS, audit log, report generation.
- Method for every problem: requirements, API, data model, high-level design, deep dive, bottlenecks, trade-offs.
- Legacy equivalent: the monolith you built on MVC, EF6 and SQL Server, where one database transaction and one IIS farm solved most of these. Here you design the same needs across many nodes.

2 Why needed

- Architect and senior lead interviews test whether you can reason about scale, failure and trade-offs, not recall facts.
- Without practice you jump to tools (Kafka, Redis) before requirements, and miss correctness traps such as double booking or double charging.
- Set 1 covered simpler building blocks. Set 2 adds money, inventory, real-time and multi-tenancy, where wrong answers lose data or money.

3 Before you read

- Notes 11.01 to 11.05: estimation, load balancing, replication, sharding, caching, queues.
- Idempotency: doing the same request twice has the same effect as once.
- Outbox: write the event to the database in the same transaction, publish it later.
- Optimistic concurrency: detect conflicting updates with a version number instead of locking.

4 Features and core concepts

Chat
- Plain meaning: users send messages in real time, one-to-one and groups. Why: tests persistent connections and ordering.
- Core: WebSocket or SignalR connections, a connection gateway tier, a message store partitioned by conversation ID, per-conversation sequence numbers, presence, offline delivery via push.
- Azure shape: SignalR Service, Service Bus or Redis pub/sub for fan-out, Cosmos DB for messages (verify).

News feed
- Plain meaning: a personalised list of posts from people you follow. Why: tests read-heavy design.
- Core: fan-out on write (precompute feeds) vs fan-out on read (build at request time), hybrid for celebrity accounts, feed cached in Redis, cursor pagination.

E-commerce checkout and orders
- Plain meaning: cart to paid order. Why: tests consistency across services.
- Core: reserve stock, create order, take payment, confirm. Use a saga with compensating actions (release stock on payment failure), outbox for events, order state machine.

Payment processing (idempotency, reconciliation)
- Plain meaning: charge a customer exactly once. Why: duplicate charges are the worst failure.
- Core: client sends an idempotency key, server stores key and result and returns the stored result on retry. Never retry a charge blindly after a timeout; query the provider status. Reconciliation: a daily job compares your ledger with the provider's settlement report and flags mismatches. Use an append-only ledger.

Job scheduler
- Plain meaning: run tasks at a time or on a schedule. Why: tests distributed coordination.
- Core: jobs table with next-run time, workers claim jobs with a lease (lock with expiry), heartbeats, retries with backoff, idempotent jobs, at-least-once execution.
- .NET: Hangfire, Quartz, Azure Functions timer (verify).

Logging and metrics pipeline
- Plain meaning: collect telemetry from many services. Why: tests high write throughput.
- Core: agents or OpenTelemetry collector, buffer in Event Hubs or Kafka, stream processor, hot store for recent data, cold store (blob) for archive, sampling, retention tiers.

Search autocomplete
- Plain meaning: suggest completions as the user types. Why: tests low latency reads.
- Core: trie or prefix index, top-K suggestions per prefix, precomputed offline from query logs, cached at edge, debounce on the client.

Booking with inventory (double booking)
- Plain meaning: sell limited seats or rooms without selling one twice. Why: classic correctness trap.
- Core: conditional update (UPDATE ... WHERE available > 0), unique constraint on seat and show, optimistic concurrency with a row version, temporary hold with expiry (reservation then confirm), avoid distributed locks as the only guard.

Multi-tenant SaaS
- Plain meaning: one system serving many customers with isolation. Why: tests data isolation and cost.
- Core: shared schema with TenantId column, schema per tenant, database per tenant. EF Core global query filter on TenantId. Noisy neighbour control with rate limits per tenant. Tenant resolved from token claim or host name.

Audit log
- Plain meaning: tamper-evident record of who did what and when. Why: compliance.
- Core: append-only, written in the same transaction or via outbox, who, what, when, before and after values, immutable storage, retention policy, separate access.

Report generation
- Plain meaning: heavy reports built without blocking users. Why: long-running work.
- Core: request returns 202 with a status URL, queue plus worker builds the file, stored in blob, link via SAS (verify), read replica or reporting store for queries, schedule off-peak.

Worth memorizing (idempotent insert pattern):
- INSERT payment (idempotency_key, ...) with a UNIQUE index on idempotency_key. On duplicate key, return the stored result.

5 Core focus (exam and interview)

- Always start with requirements, scale numbers and the read-write ratio.
- Say the consistency choice out loud: strong for money and inventory, eventual for feeds and counters.
- At-least-once delivery plus idempotent consumers is the default answer.
- Exactly-once does not exist end to end; you simulate it with idempotency.
- Every design needs: failure handling, bottleneck, one thing you would monitor.
- 45 minutes: 5 requirements, 5 estimation, 15 high-level, 15 deep dive, 5 wrap-up.

6 Real-world use case

- Situation: a Kolkata retail client moves a legacy checkout (MVC, EF6, one SQL Server transaction) to Azure services.
- Choice: order service with its own Azure SQL database, payment service calling the gateway with idempotency keys, inventory service with conditional updates, Service Bus for events, outbox on the order service, saga orchestrated by the order service.
- Trade-off: you give up the single ACID transaction and accept eventual consistency, compensations and more operational work.
- When NOT to use it: low traffic, one team, one database. A modular monolith with a single transaction is simpler and safer.

7 Interview lens

- Q: How do you prevent double booking?
  A: Make the database enforce it: conditional update or unique constraint. Add a short hold with expiry for the checkout window.
- Q: A payment call times out. What now?
  A: Do not retry the charge blindly. Query the provider by idempotency key, then retry or mark failed. Reconcile daily.
- Q: Fan-out on write or on read for a feed?
  A: Write for normal users (fast reads). Read for celebrities (avoid millions of writes). Hybrid in practice.
- Q: Which multi-tenant model?
  A: Shared schema for many small tenants (cheap), database per tenant for large or regulated ones (isolation). Choose by isolation need, cost and tenant count.

8 Common mistakes

- Starting with technology, not requirements. Shows as a design that solves the wrong problem. Fix: write requirements first.
- Using a distributed lock as the only inventory guard. Shows as oversold items after a lock expires. Fix: database constraint as final guard.
- Retrying payments without idempotency keys. Shows as duplicate charges. Fix: key per attempt, stored result.
- Forgetting the TenantId filter on one query. Shows as cross-tenant data leak. Fix: global query filter plus tests.
- Synchronous report generation. Shows as timeouts and thread pool starvation. Fix: 202 plus worker.
- Ignoring celebrity or hot-key cases. Shows as one partition overloaded. Fix: hybrid fan-out, key salting.

9 Mental model

- Money and stock: one source of truth, enforced by the database, every request safe to repeat.
- Everything else: events flow through queues, consumers are idempotent, views are rebuilt from events.

User -> API -> database (truth) -> outbox -> queue -> workers -> caches, search, reports

10 Mini lab (about 40 minutes)

Goal: prove idempotent payments and no double booking locally.
- Install SQL Server in Docker: docker run -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD=Your_pass123 -p 1433:1433 -d mcr.microsoft.com/mssql/server:2022-latest (verify image tag).
- Create tables: Payments (Id, IdempotencyKey UNIQUE, Amount, Status) and Seats (Id, ShowId, Status, RowVersion).
- Write a small .NET console app that inserts a payment with a fixed key twice, catches the unique violation, and returns the stored row.
- Write a second test that starts 20 parallel tasks all running UPDATE Seats SET Status='Held' WHERE Id=1 AND Status='Free' and counts rows affected.
- Expected result: second payment insert returns the first result; exactly one of the 20 seat updates reports 1 row affected.
- Clean-up: docker stop and docker rm the container, delete the console project.

11 Revision summary

- Method: requirements, API, data model, high-level design, deep dive, bottlenecks, trade-offs.
- Payments: idempotency key, stored result, never blind retry, daily reconciliation, append-only ledger.
- Double booking: conditional update or unique constraint, hold with expiry.
- Checkout: saga with compensations, outbox for events.
- Feed: fan-out on write, on read, or hybrid.
- Multi-tenant: shared schema, schema per tenant, database per tenant, always filter by TenantId.
- Long reports: 202 plus status URL, queue and worker, blob result.
- Delivery is at-least-once, so consumers must be idempotent.
