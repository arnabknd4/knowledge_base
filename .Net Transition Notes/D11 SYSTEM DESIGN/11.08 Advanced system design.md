1 What is it
- Advanced system design is the set of deeper distributed-systems ideas behind databases, queues and coordination services. You rarely build them yourself. You need to recognize them and know why they exist.
- Consensus means several machines agreeing on one value even when some fail. Raft and Paxos are the best-known algorithms.
- Leader election means choosing one node to coordinate work. Distributed locks let one worker at a time use a shared resource.
- CRDTs (conflict-free replicated data types) are data structures that merge concurrent edits without conflict.
- LSM trees and B-trees are two ways a database stores data on disk. Bloom filters answer "is this item possibly in the set?" using little memory.
- Geo-distribution means running across regions. Stream processing handles events continuously. Lambda and kappa are two designs for mixing batch and streaming.
- Legacy equivalent: SQL Server clustering and failover, MSMQ, and Windows Server failover cluster quorum.

4 Features and core concepts
- Consensus (Raft, Paxos awareness): nodes vote so that a majority agrees on one ordered log of changes. It matters because it gives a single source of truth without a single point of failure. Raft is the easier one to explain. Paxos is older and harder. Key rule: a majority (quorum) must be alive, so a 3-node cluster survives 1 failure and a 5-node cluster survives 2.
- Leader election: one node is chosen to make decisions, and a new one is chosen if it dies. It matters because two active leaders (split brain) corrupt data. Examples: Raft inside etcd, and a blob lease in Azure (verify). Fencing tokens stop an old leader from writing after it lost leadership.
- Distributed locks: a lock held across machines, usually with an expiry (lease). It matters for jobs that must run on one instance only. Risk: a paused process wakes up after its lease expires and still thinks it holds the lock. Fix: fencing tokens and idempotent work. Redis locks are best-effort, not a guarantee.
- CRDTs: data types designed so replicas can be edited independently and always converge. Examples: counters, sets, collaborative text. It matters for offline-first and multi-region writes. Trade-off: limited data shapes and metadata growth.
- LSM trees vs B-trees: LSM writes to memory and appends sorted files to disk, then merges them (compaction). B-trees update pages in place. LSM gives fast writes and more read cost (used by Cassandra, RocksDB). B-trees give steady reads (SQL Server, most relational databases).
- Bloom filters: a small bit array that says "definitely not present" or "maybe present". False positives are possible, false negatives are not. It matters because it avoids costly disk or network lookups, for example in LSM reads and caches.
- Geo-distribution: placing data and compute in several regions. It matters for latency and regional failure. Costs: replication lag, conflict handling, and higher cost. Choices: single-write region with read replicas, or multi-write with conflict resolution (Cosmos DB multi-region writes, verify).
- Stream processing: handling events as they arrive, with windows (fixed, sliding, session) and state. It matters for real-time alerts and metrics. Concepts to know: event time vs processing time, late data, exactly-once effects through idempotence. Azure options: Event Hubs, Stream Analytics, Kafka-based tools (verify).
- Lambda architecture: a batch layer for accuracy plus a speed layer for freshness, merged at query time. It matters historically. Cost: two code paths to maintain.
- Kappa architecture: everything is a stream, and reprocessing means replaying the log. It matters because it has one code path. Cost: needs a long-retention log and replay capacity.

6 Real-world use case
- Situation: an order system in Azure runs a nightly reconciliation job on 3 App Service instances. It sometimes runs twice and double-posts entries.
- Choice: use a lease (blob lease or a database row with expiry) for leader election, and make the job idempotent with a run ID and a unique constraint. Add a fencing token to every write.
- Why not build consensus: Azure services, SQL Server and etcd already do it. Use them.
- Trade-off: a lease can expire during a long pause, so idempotence is the real safety, not the lock.
- When NOT to use: if the job is already idempotent and cheap to run twice, skip the lock. If you need strong correctness across regions, do not use a Redis lock, use a database transaction or a consensus-backed store.

11 Revision summary
- Consensus needs a majority: 3 nodes tolerate 1 failure, 5 nodes tolerate 2.
- Two leaders at once is split brain. Fencing tokens prevent stale writes.
- A distributed lock with expiry is not a guarantee. Make work idempotent.
- CRDTs converge without coordination but support limited data shapes.
- LSM trees favor writes, B-trees favor steady reads.
- Bloom filter: no false negatives, some false positives.
- Lambda keeps batch plus speed layers, kappa keeps one streaming path with replay.
- Do not build these yourself. Pick managed services and know the trade-offs.
