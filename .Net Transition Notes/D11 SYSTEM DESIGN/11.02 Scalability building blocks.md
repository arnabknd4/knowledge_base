1 What is it

Scalability building blocks are the standard parts you combine so a system can handle more users and more data without falling over. Vertical scaling means a bigger machine. Horizontal scaling means more machines behind a load balancer. The other blocks (caches, CDNs, queues, rate limiters) reduce or smooth the load that reaches your servers.

Legacy equivalent: a web farm of IIS servers behind a hardware load balancer, with sticky sessions and a shared SQL Server.

2 Why needed

- One server has a ceiling. CPU, memory, connections and network all run out.
- A single server is a single point of failure.
- Traffic is spiky. Without these blocks, a spike causes timeouts, then retries, then a full outage.
- Without stateless services, you cannot add machines freely.

3 Before you read

- Latency is time per request. Throughput is requests per second.
- A load balancer spreads requests across servers.
- HTTP is stateless by design. State lives in cookies, sessions or databases.
- A cache stores answers so you do not recompute them.

4 Features and core concepts

- Vertical vs horizontal scaling: bigger machine vs more machines. Vertical is simple but capped and a single point of failure. Horizontal is the long-term path but needs stateless design.
- Stateless services: no user data kept in server memory between requests. Any instance can serve any request, so you can add or kill instances freely. Session goes to Redis or a token. Legacy InProc session breaks this.
- Load balancing L4 and L7: L4 routes by IP and port (fast, blind to content). L7 routes by URL, header or cookie (smarter, more CPU). Azure examples: Load Balancer is L4, Application Gateway is L7 (verify).
- LB algorithms: round robin (equal turns), least connections (pick the least busy), weighted (bigger servers get more), IP hash (same client, same server). Why it matters: uneven request cost makes plain round robin overload some nodes.
- Reverse proxy: a server in front of your apps that handles TLS, compression, routing and caching. Nginx, YARP, IIS ARR. It hides internal servers and gives one place for cross-cutting rules.
- CDN: copies of static content at edge locations near users. Cuts latency and takes load off origin. Azure Front Door or Azure CDN (verify).
- DNS routing: DNS answers differ by region, health or weight. Gives geo routing and failover. Limited by DNS TTL caching, so failover is not instant.
- Autoscaling: add or remove instances by rule (CPU, queue length, schedule). Saves cost and absorbs spikes. Needs a warm-up time and a minimum and maximum limit.
- Connection pooling: reuse open database connections instead of opening new ones. Databases have a connection limit, so many instances times pool size can exhaust it. Pool size per instance times instance count must stay under the server limit.
- Queue-based load leveling: put a queue between producer and consumer. The consumer works at its own pace and spikes become backlog, not failure. Azure Service Bus or Storage Queues.
- Rate limiting: cap requests per client or key. Protects the system from abuse and noisy neighbors. Returns HTTP 429.
- Token bucket: bucket refills at a steady rate; each request takes a token. Allows bursts up to bucket size.
- Leaky bucket: requests drain at a fixed rate. Smooths traffic, no bursts.
- Sliding window: counts requests in a moving time window. More accurate than a fixed window, which allows a double burst at the window edge.
- Backpressure: a slow consumer signals the producer to slow down or stops accepting work. Without it, memory fills with unbounded queues. Bounded channels and 429 or 503 responses are examples.

Worth remembering (ASP.NET Core rate limiting, verify exact API):
- builder.Services.AddRateLimiter(o => o.AddTokenBucketLimiter("api", x => { x.TokenLimit = 100; x.TokensPerPeriod = 10; x.ReplenishmentPeriod = TimeSpan.FromSeconds(1); }));
- app.UseRateLimiter();

5 Core focus (exam and interview)

- Most asked: how to make an app horizontally scalable. Answer: stateless, externalize session and cache, shared nothing between instances.
- L4 vs L7 and when to use each.
- Which algorithm fits which case (token bucket for bursts, leaky for smooth output).
- What the database does when you scale the app tier (connection limits, becomes the bottleneck).
- Queue vs direct call for spiky load.
- Autoscale needs a metric, a min, a max and a cooldown. Scaling out lags the spike.
- DNS TTL limits failover speed.
- The data tier scales harder than the web tier.

6 Real-world use case

Situation: a booking portal moved from two IIS servers to Azure App Service. Month-end traffic is five times normal and emails and PDF generation slow the API.

Choice: make the API stateless (session in Azure Cache for Redis), autoscale App Service on CPU with a minimum of 2 and a maximum of 10, Front Door as CDN and L7 entry point, Service Bus queue for PDF and email jobs processed by a worker, and token bucket rate limits per API key.

Trade-off: more moving parts, Redis and queue cost, and eventual completion of jobs instead of instant. The database remains the single scaling limit.

When not to use it: a small internal app with a few hundred users. A single instance with a backup is cheaper and simpler. Do not add queues or a CDN without a measured need.

7 Interview lens

- Q: How do you scale a web app horizontally?
  A: Make instances stateless and identical. Put session and cache in Redis, use a load balancer, and autoscale on a metric.
- Q: L4 or L7 load balancer?
  A: L4 for raw speed and non-HTTP traffic. L7 when you need path routing, TLS termination, WAF or cookie affinity.
- Q: Token bucket or leaky bucket?
  A: Token bucket allows controlled bursts. Leaky bucket gives a constant output rate.
- Q: What is backpressure and why does it matter?
  A: It stops a slow consumer from being overwhelmed. Without it you get unbounded memory growth and cascading failure.

8 Common mistakes

- Sticky sessions or InProc session kept after scaling out. Users lose session when an instance is replaced. Fix: Redis or token-based auth.
- Scaling the app tier and ignoring the database. Connection exhaustion and slow queries appear. Fix: pool limits, read replicas, caching.
- Autoscale with no maximum. A bug or attack creates a huge bill. Fix: set a cap and a budget alert.
- Unbounded queues or channels. Memory grows until the process dies. Fix: bounded capacity and a dead-letter queue.
- Rate limit counted per instance, not globally. Real limit becomes limit times instances. Fix: shared store such as Redis, or limit at the gateway.
- Retries with no backoff on 429. Creates a retry storm. Fix: exponential backoff with jitter.

9 Mental model

Users -> DNS -> CDN (static) -> L7 load balancer + rate limit -> stateless app instances (autoscaled) -> cache -> database
                                                      |
                                                      +-> queue -> workers (async work)

Think of it as a funnel: each layer removes load before it reaches the expensive, hard-to-scale database.

10 Mini lab

Goal: see round robin, statelessness and rate limiting locally (about 30 minutes). Needs Docker Desktop and the .NET SDK.

- Create a minimal API that returns the machine name: dotnet new web -n Lab; edit Program.cs so GET / returns Environment.MachineName.
- Add AddRateLimiter with a fixed or token bucket policy of 5 requests per 10 seconds and apply UseRateLimiter with RequireRateLimiting on the endpoint.
- Add a Dockerfile (or use dotnet publish /t:PublishContainer) and run 3 containers on ports 8081, 8082, 8083.
- Run an nginx container with an upstream block listing the 3 containers and proxy_pass to it on port 8080.
- Call curl http://localhost:8080 ten times.
- Expected result: responses cycle through three different machine names (round robin). After the limit, you get HTTP 429 from the instance that hit it.
- Note that each instance counts its own limit, which shows the per-instance limit mistake.
- Clean-up: docker rm -f the four containers, delete the Lab folder and any images created.

11 Revision summary

- Vertical is simple and capped. Horizontal needs stateless services.
- L4 routes by IP and port. L7 routes by HTTP content.
- CDN and cache remove load before it hits the origin.
- Autoscale needs metric, min, max and cooldown, and it lags spikes.
- Pool size times instance count must stay under the database connection limit.
- A queue turns a spike into backlog. Backpressure stops overload.
- Token bucket allows bursts. Leaky bucket smooths. Sliding window is the most accurate.
- Rate limits must be global, not per instance, and clients must retry with backoff and jitter.
