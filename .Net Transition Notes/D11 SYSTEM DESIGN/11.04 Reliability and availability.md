1 What is it
- Reliability is the ability of a system to keep serving users when parts of it fail. Availability is the share of time it is actually usable.
- Redundancy means keeping more than one copy of a component so one failure does not stop the service.
- Failover means moving traffic from a failed component to a healthy one, either automatically or by hand.
- Legacy equivalent: two IIS web servers behind a hardware or Windows NLB load balancer, with SQL Server failover clustering or log shipping to a standby server.

2 Why needed
- Every component fails eventually: disks, VMs, zones, networks, deployments, people.
- Without a plan, one failure becomes a full outage and the recovery time is unknown.
- Business owners ask for numbers (how much downtime, how much data loss). An architect must turn those into design choices and costs.

3 Before you read
- Load balancer: spreads requests across several servers.
- Stateless service: any instance can serve any request because no session data lives on the instance.
- Replication: copying data from one store to another.
- SLA: a promised availability percentage, usually with a refund if missed.

4 Features and core concepts
- Redundancy: run two or more copies of each component. Matters because a single copy is a single point of failure. N+1 means one spare beyond the load you need.
- Failover, active-active: all copies serve traffic at once. Matters because failover is nearly instant, but it costs more and needs data that can be written from several places.
- Failover, active-passive: one copy serves, the other waits. Matters because it is cheaper and simpler, but the switch takes time and the standby may be cold.
- Health checks: a probe (HTTP endpoint, TCP check) that tells the load balancer if an instance is fit to serve. Matters because failover only works if failure is detected. Separate liveness (process is alive) from readiness (can take traffic).
- Multi-zone: spread copies across availability zones (separate datacenters in one region). Matters because it survives a datacenter failure with low latency and usually no data loss.
- Multi-region: copies in two or more regions. Matters because it survives a whole region outage, but adds latency, cost and data consistency problems.
- RPO (recovery point objective): the maximum data loss you accept, measured in time. Matters because it decides how often to back up or how replication works.
- RTO (recovery time objective): the maximum time to be back up. Matters because it decides whether you need a warm standby or can restore from backup.
- Backup and restore tests: a backup is only real if a restore has been tested. Matters because untested backups often fail when needed.
- Graceful degradation: when a dependency fails, serve a reduced experience instead of an error (cached prices, hide recommendations). Matters because partial service beats none.
- Bulkheads: isolate resources (separate thread pools, queues, connection pools) per dependency or tenant. Matters because one slow dependency cannot exhaust everything.
- Retry budgets: cap retries to a small share of traffic (for example 10 percent extra). Matters because unlimited retries multiply load on a struggling service.
- Cascading failure prevention: timeouts, circuit breakers, load shedding, backpressure. Matters because one overloaded service can drag down all its callers.
- Composite SLA math: serial dependencies multiply (99.9 percent x 99.9 percent = about 99.8 percent). Parallel redundant copies combine as 1 minus the product of failure rates. Matters because a chain of services is less available than any one of them.
- DR tiers, backup-restore: back up data and rebuild after a disaster. Cheapest, slowest. RTO in hours or days.
- DR tiers, pilot light: data replicated and a minimal core running, rest scaled up on demand. RTO in tens of minutes to hours.
- DR tiers, warm standby: a scaled-down full copy running all the time. RTO in minutes.
- DR tiers, active-active: full capacity in several regions serving traffic. RTO near zero, highest cost and complexity.
- Worth memorizing: composite SLA = SLA1 x SLA2 x ... for services in series.

5 Core focus (exam and interview)
- Most asked: map a stated RPO and RTO to a DR tier and justify the cost.
- Know the difference between high availability (survive local failure, same region) and disaster recovery (survive a region loss).
- Be able to do SLA math on a diagram: serial multiplies, redundant paths improve.
- Nines table to recall: 99.9 percent is about 8.8 hours of downtime a year, 99.99 percent about 53 minutes, 99.999 percent about 5 minutes.
- Azure service SLAs and zone or region features change (verify) on Microsoft Learn before an exam.
- Asynchronous replication means possible data loss (RPO above zero). Synchronous replication gives zero loss but adds write latency.

6 Real-world use case
- Situation: an order-processing system on Azure with App Service, Azure SQL and Service Bus. Business asks for RPO 5 minutes and RTO 1 hour.
- Choice: zone-redundant App Service and Azure SQL in the primary region for HA. A warm standby in the paired region with a SQL failover group. Front Door or Traffic Manager for routing. A written failover runbook.
- Trade-off: warm standby costs roughly the price of running a second smaller copy all the time, but meets the 1 hour RTO. Asynchronous geo-replication may lose a few seconds of orders, which fits the RPO.
- When NOT to use it: an internal reporting tool with RTO of one day does not justify a second region. Backup-restore is enough. Also avoid active-active when the data model cannot handle conflicting writes.

7 Interview lens
- Q: What is the difference between RPO and RTO?
  A: RPO is how much data you can lose, in time. RTO is how long you can be down.
- Q: Why is a chain of 99.9 percent services not 99.9 percent available?
  A: Failures multiply across serial dependencies, so two give about 99.8 percent. Add redundancy or remove synchronous calls to improve it.
- Q: When would you pick warm standby over active-active?
  A: When RTO of minutes is acceptable and cost or write-conflict complexity matters. Active-active is for near-zero RTO and a data model that supports it.
- Q: How do you stop one failing service from taking down everything?
  A: Timeouts, circuit breakers, bulkheads, load shedding and retry budgets. Degrade gracefully instead of returning errors.

8 Common mistakes
- Backups never restored: restore fails during the incident. Fix: scheduled restore drills with timing recorded.
- Redundant copies in the same zone or sharing one dependency: one fault takes both. Fix: spread across zones and check shared dependencies.
- Health check that only returns 200 without testing the database: traffic goes to a broken instance. Fix: readiness checks that test critical dependencies, kept light.
- Unlimited retries: a small blip becomes a retry storm. Fix: backoff, jitter, retry budget.
- DR plan exists only on paper: failover takes days. Fix: run game days and keep runbooks current.
- Region failover without a data plan: app is up but data is stale or missing. Fix: define RPO first and test data failover.

9 Mental model
- Think of a hospital with backup power.
- Generator in the building (zones): covers local failure.
- Second hospital in another city (region): covers a disaster.
- The tier is how ready the second hospital is: empty building (backup-restore), core team on call (pilot light), small staffed ward (warm standby), fully running (active-active).

10 Mini lab
Goal: see health-check based failover and measure a restore. Time: about 30 minutes. Uses local Docker, no Azure cost.
- Create two copies of a small ASP.NET Core app, each with a /health endpoint, running as two containers on ports 5001 and 5002.
- Run an Nginx container as a load balancer with an upstream block listing both, and max_fails=1 fail_timeout=10s.
- Run curl in a loop against Nginx and note that responses alternate between both instances.
- Stop one container with docker stop. Expected result: a few errors at most, then all responses come from the surviving instance.
- Start it again. Expected result: traffic returns to both after the fail timeout.
- Extra step: run a SQL Server container with a volume, take a backup, delete the data, restore, and record the time taken. That time is your measured RTO for this setup.
- Clean-up: docker rm -f for all containers and remove the volume and Nginx config.

11 Revision summary
- HA survives local failure, DR survives a region or site loss.
- RPO is data loss in time, RTO is downtime in time.
- Serial SLAs multiply, redundant copies improve availability.
- 99.9 percent is about 8.8 hours of downtime a year, 99.99 percent about 53 minutes.
- DR tiers in order of cost and speed: backup-restore, pilot light, warm standby, active-active.
- Readiness checks should test real dependencies, not just return 200.
- Retry budgets, circuit breakers and bulkheads stop cascading failure.
- An untested backup or untested failover is not a plan.
