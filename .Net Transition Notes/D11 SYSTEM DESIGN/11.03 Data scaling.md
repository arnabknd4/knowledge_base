---

1 What is it

- Data scaling means keeping a data store fast and available as data volume and traffic grow beyond one machine.
- Two basic moves: copy data to more machines (replication) or split data across machines (sharding).
- The rest of this topic is the trade-offs those two moves create: lag, hot spots, and consistency.
- Legacy equivalent: SQL Server log shipping or a read-only secondary for reports, and the manual habit of splitting a big database into per-region databases.

2 Why needed

- One server has a ceiling on CPU, memory, disk and connections. Vertical scaling gets expensive and then stops.
- Without replication, one node failure means downtime or data loss.
- Without sharding, one table or one database becomes the bottleneck for writes and storage.

4 Features and core concepts

- Replication: keep copies of the same data on several nodes. Why: read scale-out and failover.
- Leader-follower replication: one node takes writes, followers copy them and serve reads. Why: simplest model, used by Azure SQL and most SQL setups.
- Multi-leader replication: several nodes accept writes and sync with each other. Why: multi-region writes, but conflicts must be resolved (last write wins, merge, custom rules).
- Leaderless replication: any node accepts reads and writes, quorum decides success. Why: high availability, used by Cassandra and Dynamo-style stores.
- Replica lag: followers are behind the leader by some delay. Why: a user can save data, then read the old version from a replica.
- Sharding: split data into partitions, each on a different node, by a shard key. Why: scales writes and storage, not only reads.
- Hash sharding: shard = hash(key) mod N. Even spread, but range queries touch all shards.
- Range sharding: key ranges per shard (A-F, G-M). Good for range queries, but sequential keys such as timestamps create a hot shard.
- Directory sharding: a lookup table maps key to shard. Flexible, but the directory is a new bottleneck and single point of failure.
- Consistent hashing: nodes and keys sit on a hash ring, so adding a node moves only a small share of keys. Why: avoids reshuffling everything when you resize.
- Hot partitions: one shard gets far more traffic than others (a celebrity user, a tenant, today's date). Why: the cluster is only as fast as its hottest shard. Fix with better key choice, key salting or splitting.
- Secondary indexes: lookups by a non-shard-key column. Local index: each shard indexes its own data, so a query scatters to all shards. Global index: a separate partitioned index, faster reads, slower and possibly stale writes.
- CAP: during a network partition you choose consistency or availability. PACELC: else (no partition), you still trade latency against consistency.
- Consistency models: strong (everyone sees the latest write), eventual (replicas converge later), causal (cause is seen before effect), read-your-writes (you see your own writes).
- Quorum: with N replicas, write to W and read from R. If W + R > N, reads overlap the latest write. Common: N=3, W=2, R=2.
- Cross-shard transactions: a transaction spanning shards needs two-phase commit or a saga. Why: expensive and fragile, so design the shard key to avoid them.

5 Core focus (exam and interview)

- Most asked: how to pick a shard key, replication types, CAP vs PACELC, quorum formula, hot partition fixes.
- Good shard key: high cardinality, even distribution, matches the main query pattern.
- Quorum rule: W + R > N gives strong-ish reads. W=1, R=1 is fast but may be stale.
- CAP is about partitions only. PACELC adds the everyday latency vs consistency trade-off.
- Cosmos DB consistency levels (verify): strong, bounded staleness, session, consistent prefix, eventual. Session is the default.
- Azure SQL read scale-out and geo-replication are leader-follower (verify current options).
- Resharding is painful. Plan the shard count early (verify with service limits).

6 Real-world use case

- Situation: an order system on one Azure SQL database. Reporting queries slow down order writes. Order table passes 2 TB.
- Choice: first add a read replica for reports (leader-follower). Later, shard orders by tenant ID with a directory table, one database per group of tenants.
- Trade-off: reports may lag by seconds. Cross-tenant queries and joins now need a separate reporting store.
- When NOT to use: below a few hundred GB with modest traffic. Indexing, caching (Redis) and a bigger tier are cheaper and simpler. Do not shard before you have to.

7 Interview lens

- Q: Leader-follower vs leaderless?
  A: Leader-follower has one write point, simple and consistent, but the leader is a bottleneck and failover is needed. Leaderless survives node loss easily but needs quorums and conflict handling.
- Q: How do you pick a shard key?
  A: High cardinality, even load, aligned with the most common query so it hits one shard. Avoid monotonically increasing keys on range sharding.
- Q: What is a hot partition and how do you fix it?
  A: One shard takes disproportionate load. Fix by changing the key, adding a salt or suffix, splitting the partition, or caching the hot items.
- Q: Why does consistent hashing help?
  A: Adding or removing a node moves only about 1/N of the keys. Plain mod-N hashing remaps almost everything.

8 Common mistakes

- Sharding too early: complexity and cost arrive before the need. Fix: scale up, index, cache and add read replicas first.
- Reading from a replica right after a write: user sees old data. Fix: read-your-writes by routing to the leader for a short window.
- Timestamp as range shard key: all new writes hit one shard. Fix: hash or composite key.
- Ignoring cross-shard queries and joins: slow scatter-gather. Fix: model data around access patterns, keep a reporting copy.
- Assuming multi-leader just works: silent data overwrite. Fix: define conflict resolution up front.

9 Mental model

- Replication is photocopying a book so many people can read it. Sharding is tearing the book into chapters stored in different rooms.

    client -> router (hash of key) -> shard 1 (leader + followers)
                                   -> shard 2 (leader + followers)
                                   -> shard 3 (leader + followers)

10 Mini lab

Time: about 30 minutes. Tools: Python 3 locally, no cloud needed.
- Step 1: write a script with 3 shard names and 10,000 keys like user1 to user10000.
- Step 2: place each key with hash mod 3 (use hashlib.md5, not Python's built-in hash). Print the count per shard.
- Step 3: change to 4 shards. Count how many keys moved to a different shard. Expect about 75 percent.
- Step 4: build a consistent hash ring (sorted list of node hashes, use bisect to find the next node, 100 virtual nodes each). Repeat the 3 to 4 node change.
- Expected result: mod-N moves roughly 75 percent of keys, the ring moves roughly 25 percent.
- Clean-up: delete the script file.

11 Revision summary

- Replication copies data for reads and failover. Sharding splits data for write and storage scale.
- Leader-follower is simplest. Multi-leader needs conflict resolution. Leaderless needs quorums.
- Replica lag causes stale reads. Use read-your-writes where it matters.
- Shard key: high cardinality, even load, matches the main query.
- Hot partitions limit the whole cluster. Fix by key design.
- Consistent hashing moves only about 1/N keys on resize.
- Quorum: W + R > N overlaps the latest write.
- CAP is partition-time. PACELC adds latency vs consistency otherwise.
- Cross-shard transactions are costly. Design to avoid them.
