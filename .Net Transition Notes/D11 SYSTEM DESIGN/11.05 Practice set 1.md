1 What is it

A system design practice set. You solve eight classic problems using one repeatable method: requirements, API, data model, high-level design, deep dive, bottlenecks, trade-offs. The set covers URL shortener, rate limiter, notification service, file upload and storage, unique ID generator, key-value store, pastebin and web crawler.

Legacy equivalent: In .NET Framework projects you designed a single IIS plus SQL Server application. Here you design for many servers, many users and partial failure.

Note on depth: this topic line is a list of eight problems, not eight concepts. One 700-word page cannot fully solve eight designs. This note gives the method once, then the key decision for each problem. Solve each on paper in 45 minutes.

2 Why needed

- Architect interviews in the Kolkata and remote India market almost always include one system design round.
- It tests whether you can turn vague requirements into numbers, then into components.
- Without a method you jump to boxes and miss requirements, scale and trade-offs.
- Without the numbers you cannot justify cache, queue or sharding choices.

4 Features and core concepts

The method (use it for every problem):

- Requirements: functional (what it does) and non-functional (scale, latency, availability). Ask before drawing.
- API: two to four endpoints with inputs and outputs. Fixes the scope.
- Data model: tables or documents, keys, access patterns. Why: storage choice follows reads and writes.
- High-level design: client, load balancer, services, storage, cache, queue. Why: shows the main flow.
- Deep dive: pick the hardest one or two parts and go deep.
- Bottlenecks: where it breaks at 10x load. Why: shows operations thinking.
- Trade-offs: what you gave up (consistency, cost, simplicity) and why.

The eight problems and the key decision in each:

- URL shortener: generate a unique short code. Options: counter with base62, hash with collision check, pre-generated key pool. Read-heavy, so cache hot codes. Use 301 (permanent, cacheable) or 302 (redirect each time, allows analytics).
- Rate limiter: limit requests per user per window. Algorithms: token bucket, leaky bucket, sliding window. Shared counters in Redis. Trade-off: accuracy versus memory and race conditions. Fail open or fail closed if Redis is down.
- Notification service: send email, SMS, push. Accept request, put on queue, workers send through providers. Needs retry with backoff, idempotency key, per-channel queues, user preferences, rate limits per provider, dead-letter queue.
- File upload and storage: do not stream big files through your API. Give the client a pre-signed URL (Azure: SAS token, the valet key pattern) to upload directly to Blob Storage. Chunked and resumable upload for large files. Metadata in a database, content in object storage.
- Unique ID generator: need ids that are unique across servers and roughly time-ordered. Options: GUID (no coordination, poor index locality), database sequence (single point), Snowflake style (timestamp plus machine id plus sequence). Trade-off: clock skew and machine id assignment.
- Key-value store: partition by consistent hashing, replicate to N nodes, quorum reads and writes (R plus W greater than N), handle node failure. Trade-off: consistency versus availability. Compare with Cosmos DB and Redis.
- Pastebin: like the shortener but stores content. Content in blob storage, metadata in database, expiry with TTL, cleanup job, read cache.
- Web crawler: URL frontier queue, fetchers, parser, deduplication (URL set, content hash), politeness (per-host rate limit, robots.txt), priority, retry. Trade-off: freshness versus load on sites.

Worth memorizing: token bucket state is two values per user, tokens and last refill time.

5 Core focus (exam and interview)

- Always state numbers: requests per second, storage per year, read-to-write ratio.
- Rule of thumb: about 100,000 seconds in a day, so 1 million per day is about 12 per second average (verify your own math each time).
- Most asked: URL shortener, rate limiter, notification service.
- Interviewers look for: clarifying questions, stated assumptions, one deep dive, named trade-offs.
- Spend about 5 minutes on requirements, 10 on design, 20 on deep dive and bottlenecks, 5 on wrap-up.
- AZ-305 link: map each design to Azure services (Front Door, API Management, Service Bus, Blob, Cosmos DB, Redis).

6 Real-world use case

Situation: your client's .NET app sends order emails from inside the web request. During sale days the SMTP calls slow the site.

Choice: build a notification service. API accepts the event and returns 202. A Service Bus queue holds it. Worker services (BackgroundService or Azure Functions) send via the provider. Idempotency key prevents duplicate emails. Failed messages go to the dead-letter queue.

Trade-off: delivery is no longer instant and you must monitor queue depth. More moving parts than a direct call.

When not to use it: low volume internal app where a direct call with retry is enough.

7 Interview lens

- Q: How do you generate short URL codes without collisions? A: Use a counter or key range per server encoded in base62, so no collision check is needed. Hashing needs a collision check and retry.
- Q: Token bucket or sliding window? A: Token bucket allows bursts and uses little memory. Sliding window is more accurate but costs more memory per user.
- Q: How do you avoid duplicate notifications? A: Idempotency key per notification, stored with a TTL, and idempotent consumers. Delivery is at-least-once, so duplicates must be handled.
- Q: Why not upload files through the API? A: It ties up your servers and bandwidth. A pre-signed URL sends the bytes straight to storage and the API only handles metadata.

8 Common mistakes

- Drawing the design before asking requirements. Shows up as designing for the wrong scale. Fix: always list functional and non-functional requirements first.
- No numbers. Shows up as vague "it will scale". Fix: do a quick QPS and storage estimate.
- Adding every component (Kafka, Redis, microservices) by default. Fix: add a component only when a stated requirement needs it.
- Ignoring failure. Fix: for each component say what happens when it dies.
- Silent on trade-offs. Fix: end each decision with "I chose X over Y because Z".

9 Mental model

Every design is the same pipeline:

requirements -> numbers -> API -> data -> boxes -> hardest part -> failure and 10x -> trade-offs

Read-heavy problems add cache. Write-heavy or slow work adds queue. Large data adds sharding or object storage.

10 Mini lab

Time: 40 minutes per problem. Do the URL shortener first. Paper only, then optional local code.

- Step 1: write requirements. Assume 100 million new URLs per month and a 100 to 1 read to write ratio.
- Step 2: calculate. Writes about 40 per second, reads about 4,000 per second. Storage: 100 million times 500 bytes is about 50 GB per month (verify the arithmetic yourself).
- Step 3: write two APIs: POST create and GET redirect by code.
- Step 4: choose the data model (code as key, long URL, created date, expiry) and database.
- Step 5: draw the flow with load balancer, app, cache and database.
- Step 6: deep dive on code generation, pick one option and defend it.
- Step 7: list three bottlenecks and fixes, then three trade-offs.
- Step 8: answer aloud in 45 minutes without notes.
- Expected result: one A4 page with numbers, diagram and trade-offs.
- Clean-up: nothing to delete. File the page in your D11 binder section.

11 Revision summary

- Method: requirements, API, data model, high-level design, deep dive, bottlenecks, trade-offs.
- Always estimate QPS, storage and read-to-write ratio before designing.
- URL shortener: counter with base62 or key pool avoids collisions; cache hot codes.
- Rate limiter: token bucket for bursts; counters in Redis; decide fail open or closed.
- Notification service: queue, workers, retry with backoff, idempotency key, dead-letter queue.
- File upload: pre-signed URL (SAS) direct to Blob; metadata in database.
- ID generator: Snowflake style is timestamp plus machine id plus sequence.
- Key-value store: consistent hashing, replication, quorum R plus W greater than N.
- Web crawler: URL frontier, dedupe, politeness, robots.txt.
