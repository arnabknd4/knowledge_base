1 What is it

Networking fundamentals explain how computers, servers, applications, and cloud services communicate. A network moves data between devices using agreed rules called protocols.

A protocol defines how communication works, including addressing, message formats, delivery, and error handling. For example, the Internet Protocol (IP) addresses and routes packets, Transmission Control Protocol (TCP) provides reliable data delivery, and Hypertext Transfer Protocol (HTTP) supports communication between web clients and servers.

Understanding networking is essential for diagnosing application failures, configuring Azure infrastructure, securing services, and designing reliable systems.

Legacy equivalent: Physical network administration using routers, switches, IP addresses, and traditional firewalls; these concepts remain relevant in modern cloud networks.

2 Why needed

* Troubleshooting: Determine whether a failure comes from DNS, routing, a firewall, TLS, or the application itself.
* Cloud architecture: Design virtual networks, subnets, routes, private connectivity, and load balancing.
* Security: Understand which traffic should be allowed and how encrypted connections work.
* Performance: Distinguish latency, bandwidth limits, packet loss, and transport-protocol behavior.
* Application delivery: Understand how browsers, APIs, proxies, and web servers communicate.
* Interview readiness: Explain the journey of an HTTP request from a client to a server.

4 Features and core concepts

* OSI and TCP/IP models: The Open Systems Interconnection (OSI) model divides networking into seven conceptual layers. The TCP/IP model groups networking functions into fewer layers. Both help isolate problems by function, from physical connectivity to application protocols.
* IP addressing: An Internet Protocol address identifies a network interface for communication. IPv4 uses 32-bit addresses; IPv6 uses 128-bit addresses. Correct addressing is necessary for devices to communicate.
* CIDR and subnetting: Classless Inter-Domain Routing (CIDR) expresses an IP network using a prefix length, such as `192.168.1.0/24`. Subnetting divides an address range into smaller networks. This helps organize workloads and control traffic.
* Routing: Routing determines the next hop for packets travelling between networks. A missing or incorrect route can prevent connectivity even when the source and destination addresses are valid.
* NAT: Network Address Translation modifies IP address information as traffic passes through a network device. It is commonly used for address translation between private and public networks. NAT is not, by itself, a complete security boundary.
* DNS: The Domain Name System translates names such as `example.com` into records containing information such as IP addresses. Resolution is the process of finding the requested record. Time to live (TTL) tells resolvers how long a record may be cached.
* DHCP: Dynamic Host Configuration Protocol automatically supplies network configuration such as IP addresses, gateways, and DNS servers. Incorrect DHCP configuration can leave clients unable to communicate correctly.
* TCP handshake: TCP normally establishes a connection through a SYN, SYN-ACK, and ACK exchange. TCP also provides ordered delivery, retransmission, flow control, and congestion control.
* UDP: User Datagram Protocol sends datagrams without establishing a TCP-style connection. It does not provide TCP's built-in reliable, ordered delivery. Applications may implement their own reliability mechanisms.
* HTTP/1.1, HTTP/2, and HTTP/3: These are versions of the Hypertext Transfer Protocol used by web applications and APIs. HTTP/2 supports features such as multiplexing over a connection. HTTP/3 uses QUIC, which runs over UDP. Actual support depends on clients, servers, and infrastructure.
* TLS handshake: Transport Layer Security establishes cryptographic parameters and authenticates the server using certificates in typical HTTPS connections. Configuration errors, expired certificates, or trust problems can prevent secure connections.
* L4 and L7 load balancers: Layer 4 load balancing distributes traffic using transport-level information, such as IP addresses and ports. Layer 7 load balancing can make decisions using application-level information, such as HTTP hostnames and paths.
* Proxies: A proxy intermediates communication between a client and another service. Forward proxies commonly serve clients; reverse proxies sit in front of servers and can provide routing, TLS termination, and other application-delivery features.
* Firewalls: Firewalls enforce traffic rules based on characteristics such as addresses, ports, protocols, or application information. A connection may fail because a firewall blocks it even when DNS and routing are correct.
* VPN: A Virtual Private Network creates a protected logical connection over another network. VPNs can connect remote users or separate networks, depending on their design.
* Latency, bandwidth, and MTU: Latency is the time taken for data to travel; bandwidth is the available data-transfer capacity; Maximum Transmission Unit (MTU) is the largest packet payload a network link can carry at a given layer without fragmentation or equivalent handling.
* Diagnostic tools: `ping` tests reachability using ICMP where permitted; `traceroute` helps identify network hops; `dig` queries DNS; `curl -v` displays HTTP and connection details; `ss` inspects sockets; `tcpdump` captures packets; Wireshark analyzes packet captures; `openssl s_client` helps inspect TLS connections.

6 Real-world use case

An application hosted on a cloud virtual machine is unreachable through its public hostname.

Troubleshoot in a logical order:

* Use `dig` to confirm that DNS returns the expected address.
* Use `curl -v` to inspect connection establishment, HTTP behavior, and TLS errors.
* Check whether the destination service is listening on the expected port using `ss`.
* Inspect firewall and network security rules.
* Verify routes and whether the destination is reachable from the client network.
* If TLS fails, inspect certificate validity, trust, and hostname matching.
* If the TCP connection succeeds but the application returns an HTTP error, investigate the web server and application logs.

Trade-off: Layer-by-layer troubleshooting is systematic and helps avoid random configuration changes, but it can take time in complex networks. Use centralized telemetry and packet captures where appropriate. Avoid changing production firewall rules or routing blindly; confirm the intended traffic path and test changes safely.

7 Interview lens

* What happens when a user opens an HTTPS website?

  The client resolves the hostname through DNS, establishes network connectivity, negotiates TLS, and sends an HTTP request. Routing, firewalls, certificates, and the server application can each affect the outcome.

* What is the difference between TCP and UDP?

  TCP provides reliable, ordered byte-stream delivery with connection management and congestion control. UDP sends datagrams without built-in guarantees of delivery or ordering.

* Why can a hostname fail while an IP address works?

  DNS resolution may be wrong, unavailable, or cached with an old value. Direct IP access may also behave differently when the service depends on hostname-based routing or TLS certificate validation.

* What is the difference between an L4 and an L7 load balancer?

  L4 makes forwarding decisions using transport-level information such as IP addresses and ports. L7 can use application-level information such as HTTP hostnames and paths.

8 Common mistakes

* Assuming a successful DNS lookup proves the application is reachable.
* Treating NAT as a replacement for firewall rules.
* Assuming `ping` failure always means a server is down; ICMP may be blocked.
* Confusing bandwidth with latency.
* Forgetting that DNS results may be cached until their TTL expires.
* Assuming that opening a TCP port guarantees that the application works.
* Ignoring TLS certificate expiry, trust chains, or hostname mismatches.
* Confusing a subnet's address range with the addresses actually assigned to resources.
* Making broad firewall changes without identifying the required source, destination, protocol, and port.
* Capturing packets without checking the correct interface or traffic direction.

9 Mental model

Think of networking as a delivery system.

* IP addressing identifies where traffic should go.
* DNS helps translate human-readable names into network information.
* Routing selects the path between networks.
* Firewalls decide which traffic is permitted.
* TCP or UDP carries application data.
* TLS protects communication and authenticates the server.
* HTTP defines how web clients and servers exchange requests and responses.
* Load balancers and proxies help direct traffic to the appropriate service.

When communication fails, identify the layer where the expected behavior stops before changing configuration.

10 Mini lab

Goal: Diagnose DNS, HTTPS connectivity, and TLS behavior using common command-line tools.

Requirements: A terminal with `dig`, `curl`, and `openssl` available. Install missing tools using your operating system's package manager if appropriate.

Steps:

* Query DNS with `dig example.com`.
* Review the returned answer section and note the record type and address.
* Inspect HTTPS connectivity using `curl -v https://example.com`.
* Look for DNS resolution, connection establishment, TLS negotiation, and the HTTP response status.
* Inspect the TLS connection using `openssl s_client -connect example.com:443 -servername example.com`.
* Review the certificate information and whether the handshake completes. Exact output depends on the local OpenSSL version and the remote server.
* Check local listening sockets with `ss -lnt` to see TCP ports in the listening state.
* Run `ping example.com` and compare the result with the HTTPS request. Remember that ICMP may be blocked even when HTTPS works.
* Write down which layer each tool helps investigate and one limitation of each tool.

Expected result: You should be able to distinguish DNS resolution from TCP connectivity, TLS negotiation, and application-level HTTP behavior. Local listening sockets show services on your own machine, not the remote server's sockets.

Clean-up: No configuration changes are required. Stop any optional test services you started and close the terminal when finished.

11 Revision summary

* OSI and TCP/IP models provide a framework for understanding networking functions.
* CIDR and subnetting organize IP address ranges into networks.
* DNS resolves names; TTL influences how long records may be cached.
* TCP provides reliable, ordered delivery; UDP does not provide those guarantees by default.
* TLS protects connections and typically authenticates servers using certificates.
* L4 load balancing uses transport-level information; L7 can use application-level information.
* Routing, firewalls, DNS, and listening services must work together for connectivity.
* Use `dig`, `curl -v`, `ss`, `tcpdump`, Wireshark, and `openssl s_client` to investigate different parts of a network problem.
