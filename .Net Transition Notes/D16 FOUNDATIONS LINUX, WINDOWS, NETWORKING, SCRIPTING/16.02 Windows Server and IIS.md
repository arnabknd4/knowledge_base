16.02 Windows Server and IIS

1 What is it

Windows Server is Microsoft's server operating system. It provides services for hosting applications, managing users, storing data, running scheduled tasks, and supporting enterprise infrastructure.

IIS stands for Internet Information Services. It is Microsoft's web server platform for hosting websites, web applications, and APIs on Windows.

When a user opens a website, IIS receives the HTTP or HTTPS request, determines which website should handle it, and passes the request through the appropriate application-processing configuration.

Key terms:

* Website: An IIS configuration that identifies how a site is hosted and accessed.
* Application pool: An isolated IIS worker-process environment used to run web applications.
* Binding: The combination of network information, such as IP address, port, hostname, and protocol, used to match incoming requests to a website.
* Application pool identity: The Windows identity under which an application pool runs.
* web.config: An XML configuration file used to configure an ASP.NET application and supported IIS settings.
* Event Viewer: A Windows tool for inspecting operating system and application events.
* PowerShell: A command-line shell and scripting language for managing Windows and other systems.
* Active Directory: Microsoft's directory service for centrally managing identities and domain resources.
* Group Policy: A mechanism for centrally applying supported configuration settings to Windows users and computers.

Legacy equivalent: Windows-based application hosting using IIS, Windows Services, Event Viewer, scheduled tasks, certificate management, and Active Directory domain administration.

2 Why needed

Windows Server and IIS knowledge helps you host and troubleshoot applications running on Windows infrastructure.

It is useful for:

* Hosting websites and APIs.
* Understanding how IIS selects a website for an incoming request.
* Diagnosing application pool failures.
* Investigating HTTP errors and application startup problems.
* Reading application logs and Windows events.
* Managing application configuration through web.config.
* Understanding Windows services and scheduled tasks.
* Configuring and troubleshooting certificates used for HTTPS.
* Recognizing how Active Directory and Group Policy affect server operations.

The important skill is to distinguish an IIS configuration problem from an application problem, a Windows problem, or a network and certificate problem.

4 Features and core concepts

* IIS architecture: Sites

  * Plain meaning: An IIS website defines how a website is hosted and how requests are mapped to it.
  * Why it matters: A server can host multiple websites with different hostnames, ports, configurations, and application content.
  * Troubleshooting consideration: Confirm that the requested hostname and port map to the intended site.

* Application pools

  * Plain meaning: An application pool provides an execution boundary for one or more IIS applications and uses a worker process to handle application requests.
  * Why it matters: Separating applications into different pools can reduce the impact of an application failure and allow different runtime or identity settings.
  * Trade-off: More pools can improve separation but may consume additional resources. Isolation is not a substitute for correct security permissions.

* Bindings

  * Plain meaning: Bindings define how IIS websites are associated with incoming connections. Common elements include protocol, IP address, port, and hostname.
  * Why it matters: Incorrect bindings can send requests to the wrong site or prevent the intended site from responding.
  * HTTPS bindings also involve certificate configuration.
  * When troubleshooting, inspect hostname resolution, port access, protocol, and the site's binding configuration.

* Application pool identity

  * Plain meaning: The application pool identity determines the Windows security context used by the IIS worker process.
  * Why it matters: The application needs appropriate access to files, databases, network resources, and other dependencies.
  * Security principle: Grant only the permissions the application needs. Giving an application broad administrator privileges increases the impact of a compromise.

* web.config

  * Plain meaning: An XML file that stores application settings and supported ASP.NET and IIS configuration.
  * Why it matters: Incorrect configuration can prevent an application from starting or change its behavior.
  * Troubleshooting consideration: Check recent changes, XML structure, configuration inheritance, runtime settings, and permissions.
  * Protect sensitive configuration values. Avoid exposing credentials in logs or source control.

* Logging and failed request tracing

  * Plain meaning: IIS logs record information about HTTP requests. Failed Request Tracing can capture details about requests that match configured tracing rules.
  * Why it matters: Logs help identify response codes, request patterns, and possible failure points.
  * Use IIS logs to investigate what happened to requests. Use tracing when more detail is needed about a particular failure.
  * The available log fields, paths, and tracing configuration depend on the server setup.

* Performance counters

  * Plain meaning: Windows performance counters provide measurements about operating system and application activity.
  * Why it matters: They help investigate high CPU use, memory pressure, request queues, and other performance problems.
  * Consider performance data alongside application logs and user-visible symptoms. A single high counter does not automatically identify the root cause.

* Event Viewer

  * Plain meaning: Event Viewer displays logs produced by Windows and applications.
  * Why it matters: Application startup failures, service errors, security events, and other operational problems may leave useful evidence here.
  * Inspect the time of the failure and correlate relevant events with IIS logs and application logs.

* PowerShell basics

  * Plain meaning: PowerShell provides commands and scripting capabilities for Windows administration.
  * Why it matters: Administrators can inspect services, processes, configuration, and logs and automate repeatable tasks.
  * Use scripts carefully. Verify the target computer and understand whether a command only reads information or changes system state.

* Services and scheduled tasks

  * Plain meaning: Windows services run background functions. Task Scheduler launches programs or scripts according to configured triggers.
  * Why it matters: Applications may depend on background services or scheduled jobs for data processing and maintenance.
  * Troubleshooting should include service state, startup configuration, task history, permissions, and execution context.

* Certificates

  * Plain meaning: Digital certificates support server identity verification and are commonly used to establish HTTPS connections.
  * Why it matters: Incorrect, expired, or mismatched certificate configuration can cause browser warnings or connection failures.
  * Check the certificate's validity, hostname coverage, binding, and trust chain. Correct certificate selection alone does not guarantee that every client will trust it.

* Active Directory and Group Policy awareness

  * Plain meaning: Active Directory can centrally manage domain identities and resources. Group Policy applies supported settings to domain users and computers.
  * Why it matters: Authentication, permissions, security settings, and server behavior may depend on domain configuration.
  * When troubleshooting, distinguish a local server issue from an identity or policy issue controlled elsewhere.

* Distinguish IIS request logs, Failed Request Tracing, and Windows Event Viewer.
* Explain how performance counters support troubleshooting.
* Describe the difference between Windows services and scheduled tasks.
* Explain how certificates support HTTPS.
* Understand how Active Directory and Group Policy can affect server behavior.
* Use PowerShell for basic inspection and administration.

6 Real-world use case

A company hosts an ASP.NET application on IIS. Users report that the application returns HTTP 500 errors after a deployment.

A reasonable investigation is:

* Confirm the affected website and the time the errors began.
* Inspect IIS logs to identify the affected requests and response codes.
* Check the application pool's state and relevant worker-process events.
* Review the Windows Application log in Event Viewer.
* Examine recent web.config and application changes.
* Verify the application pool identity and access to required files or dependencies.
* Use Failed Request Tracing when the existing evidence is insufficient and tracing is appropriate.
* Check performance counters if the symptoms suggest resource pressure.
* Apply a targeted fix and verify the result with a test request.

Trade-off: Restarting an application pool can sometimes restore service, but it may interrupt active requests and remove useful transient evidence. Investigate the failure first when possible.

When not to use this approach: If the issue is clearly a network routing, DNS, or client-side certificate-trust problem, IIS application troubleshooting alone may not solve it. Investigate the layer supported by the evidence.

7 Interview lens

* Q: What is the difference between an IIS website and an application pool?

  * A: A website defines how incoming requests map to hosted content and configuration.
  * An application pool provides an execution boundary and worker-process environment for applications.

* Q: What would you check if an IIS application returns HTTP 500?

  * A: Inspect IIS logs, application logs, Event Viewer, application pool state, and recent configuration changes.
  * Use the evidence to identify the cause before changing permissions or restarting services.

* Q: What is the purpose of an IIS binding?

  * A: A binding associates a website with connection details such as protocol, IP address, port, and hostname.
  * Incorrect bindings can prevent the intended site from receiving requests or cause requests to reach another site.

* Q: How would you investigate an HTTPS certificate problem?

  * A: Check certificate validity, hostname coverage, trust chain, and the certificate assigned to the relevant HTTPS binding.
  * Also verify DNS, client trust, and the connection path because certificate errors may have causes outside IIS.

8 Common mistakes

* Confusing a website with its application pool.
* Assuming every HTTP 500 error is caused by IIS rather than application code or configuration.
* Giving an application pool identity excessive permissions.
* Editing web.config without backing up the original configuration.
* Looking only at IIS logs while ignoring Event Viewer and application logs.
* Restarting application pools before collecting useful diagnostic evidence.
* Assuming a certificate is correct because it has not expired.
* Ignoring hostname and port details when investigating bindings.
* Confusing a Windows service with a scheduled task.
* Assuming a server's local configuration is independent of Active Directory or Group Policy.
* Making production changes without a rollback plan or validation.

9 Mental model

Think of IIS as a reception and operations system for a building.

* The website is the destination being hosted.
* The binding is the information that directs visitors to the correct destination.
* The application pool is the controlled workspace where application code runs.
* The application pool identity is the security identity used by that workspace.
* web.config contains application configuration instructions.
* IIS logs record incoming requests and their outcomes.
* Failed Request Tracing provides deeper evidence for selected requests.
* Event Viewer records relevant Windows and application events.
* Performance counters show how the server and application are behaving.
* Certificates help clients verify server identity for HTTPS.
* Active Directory and Group Policy provide centralized identity and configuration controls.

When a request fails, trace it from the connection and site selection through the application pool and application, using logs and configuration to locate the failing layer.

10 Mini lab

Goal: Understand IIS websites, bindings, application pools, and logs without changing a production server.

Time: 20–40 minutes.

Tools: A Windows machine with IIS installed, or a Windows Server virtual machine. Administrator permissions may be required to inspect or change some IIS settings. If IIS is unavailable, use the lab as a guided inspection exercise and do not install server components on a production machine.

Steps:

* Open IIS Manager by searching for “Internet Information Services (IIS) Manager” in Windows.
* Expand the local server and select Sites. Inspect the available website entries.
* Select a test website, if one exists, and open Bindings. Record its protocol, IP address, port, and hostname. Do not change existing bindings.
* Select Application Pools. Identify the pool used by the test website and inspect its state and basic settings.
* Select the website and open its Basic Settings to inspect the configured physical path and application pool.
* Locate the IIS log directory configured for the site, if accessible. Inspect a recent log file and identify fields such as timestamp, requested path, and HTTP status.
* Open Event Viewer and inspect Windows Logs, especially Application, for relevant application or IIS-related events around the same time.
* If no test website exists, use the IIS Manager interface for read-only inspection rather than creating or modifying a site on a production server.

Expected result:

* You can identify a website and its bindings.
* You can find the application pool associated with a website.
* You can locate request logs and relevant Windows events.
* You understand how IIS configuration, application execution, and troubleshooting evidence relate to one another.

Clean-up:

* Close IIS Manager and Event Viewer.
* Since this is a read-only exercise, no configuration cleanup is needed.
* If you performed the exercise in a test environment and created any temporary objects, remove only those objects after confirming they are not needed.

11 Revision summary

* IIS hosts websites and applications on Windows.
* Websites define hosted endpoints and content; application pools provide execution boundaries.
* Bindings map connection details to the intended website.
* Application pool identities control the Windows security context of application execution.
* web.config contains application configuration that can affect startup and behavior.
* IIS logs, Failed Request Tracing, and Event Viewer provide different types of troubleshooting evidence.
* Certificates support HTTPS, while Active Directory and Group Policy can affect identity and server configuration.
* Diagnose the failing layer before restarting services or making production changes.
