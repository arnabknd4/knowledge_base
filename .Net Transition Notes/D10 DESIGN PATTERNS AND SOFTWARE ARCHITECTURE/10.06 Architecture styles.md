1 What is it
- Architecture style: the way you organize a codebase and its dependencies so that business rules stay separate from frameworks, databases and UI.
- Layered and N-tier: code split into presentation, business and data layers. Each layer calls the one below it.
- Clean, onion and hexagonal: the domain sits in the centre. Everything else (database, web, queues) depends on it, never the reverse. Hexagonal calls the boundaries ports (interfaces the core defines) and adapters (implementations outside the core).
- Vertical slice: code is organized by feature (one folder per use case) instead of by technical layer.
- Modular monolith: one deployable unit, split inside into modules with strict boundaries.
- Event-driven: components communicate by publishing and reacting to events instead of calling each other directly.
- Microkernel and plugin: a small core plus extensions loaded on demand.
- Pipe and filter: data flows through a chain of independent processing steps.
- Legacy equivalent: the classic MVC plus business layer plus data access layer solution with a shared Entities project that every other project references.

2 Why needed
- Without a deliberate style, dependencies grow in every direction. A change in the database schema breaks the UI. Business rules end up in controllers and stored procedures.
- The cost shows up late: slow builds, fear of change, tests that need a database, and a codebase no one dares upgrade.
- A chosen style makes trade-offs explicit. You pick it based on the quality attributes that matter (changeability, testability, scalability, team autonomy), not on fashion.

3 Before you read
- Interface and abstraction: code depends on a contract, not an implementation.
- Dependency injection (topic 1.03): how the implementation is supplied at runtime.
- Coupling and cohesion: coupling is how much modules know about each other, cohesion is how well a module's contents belong together.
- Quality attributes: the non-functional goals such as performance, availability, maintainability.

4 Features and core concepts
- Layered and N-tier. Plain meaning: horizontal slices, each depending only on the layer below. Why it matters: simple, familiar, fine for CRUD apps. Tier (physical machine boundary) is not the same as layer (logical boundary in code). Weakness: the data layer ends up as the centre, so business logic leaks toward the database.
- Clean architecture. Plain meaning: concentric rings: Domain, Application (use cases), Infrastructure and Presentation outside. Why it matters: the core has no reference to EF Core, ASP.NET or Azure SDKs, so it is testable and survives framework upgrades.
- Onion architecture. Plain meaning: the same idea with the domain model at the centre and domain services, application services and infrastructure as outer rings. Why it matters: interviewers use clean, onion and hexagonal almost interchangeably. Know the shared rule, not the differences in drawing.
- Hexagonal architecture (ports and adapters). Plain meaning: the core exposes ports, and adapters plug in on each side (HTTP controller, queue consumer, SQL repository). Why it matters: the same core can be driven by a test, an API or a message handler.
- The dependency rule. Plain meaning: source code dependencies point inward only. Why it matters: it is the one rule behind clean, onion and hexagonal. In .NET it is enforced by project references.
- .NET solution structure. Plain meaning: typical projects are Domain (no references), Application (references Domain), Infrastructure (references Application and Domain), Api (references Application and Infrastructure for DI wiring). Why it matters: the compiler stops a wrong reference.
- Vertical slice. Plain meaning: each feature owns its request, handler, validation and data access in one folder (for example CreateOrder). Why it matters: changes touch one place, and you can use a different data approach per slice (EF for writes, Dapper for reads). Weakness: duplication, and weaker guidance on shared domain rules.
- Modular monolith structure. Plain meaning: one deployable, but each module (Orders, Billing) has its own public contract and its own schema or tables, and modules do not reference each other's internals. Why it matters: it is the usual first step before microservices and often the right final step.
- Event-driven. Plain meaning: producers publish events, consumers react, and neither knows the other. Why it matters: loose coupling and scalability, at the price of eventual consistency and harder debugging.
- Microkernel and plugin. Plain meaning: a core that loads extensions through a defined interface. Why it matters: fits products with customer-specific behaviour (rules, exporters, connectors).
- Pipe and filter. Plain meaning: each step takes input, transforms it and passes it on. Why it matters: ASP.NET Core middleware and data processing pipelines work this way.
- Choosing by quality attributes. Plain meaning: map the top two or three goals to a style. Why it matters: this is the architect's actual job and the most common interview angle.
- Architecture tests (NetArchTest). Plain meaning: unit tests that fail the build when a dependency rule is broken. Why it matters: rules written in a document decay, rules in a test hold.
- Worth memorizing: Types.InAssembly(domainAssembly).ShouldNot().HaveDependencyOn("Infrastructure").GetResult().IsSuccessful (NetArchTest, verify exact API for the current version)

5 Core focus (exam and interview)
- Most asked: explain the dependency rule, and justify why you chose a style for a given system.
- Layered is the default for simple CRUD. Clean or hexagonal fits rich domain logic and long-lived systems. Vertical slice fits feature-heavy APIs with many independent use cases. Modular monolith fits teams that want boundaries without distributed-system cost. Event-driven fits integration and decoupled workflows.
- Clean architecture does not mean four projects every time. Over-layering a small CRUD service is a recognised failure.
- Styles combine: a modular monolith where each module uses vertical slices, or clean architecture inside each microservice.
- Decision input is quality attributes first, team size and skills second, fashion last.
- Azure exam angle: the Azure Architecture Center names N-tier, web-queue-worker, microservices and event-driven as styles (see topic 12.10). Verify the current list there.

6 Real-world use case
- Situation: a 12-year-old MVC monolith for order management. The business logic is spread across controllers, stored procedures and a shared DAL project. A team of 10 needs faster delivery, but a microservices move is too costly now.
- Choice: modernise into a modular monolith on modern .NET. Modules: Orders, Inventory, Billing. Each has a public contract project, internal Domain and Application code, its own tables, and cross-module calls only through contracts or in-process events. Inside the complex module (Orders) use clean architecture. Inside simple modules use vertical slices with plain EF Core. Add NetArchTest rules in CI to block cross-module internal references.
- Trade-off: you get clear boundaries and one deployment, but one scaling unit, one release train, and the discipline depends on the tests holding.
- When NOT to use it: a small CRUD app or a short-lived internal tool (use plain layers), or when teams truly need independent deployment and scaling (consider services, but only after the module boundaries are proven).

7 Interview lens
- Q: What is the dependency rule? A: Source dependencies point only toward the domain at the centre. Outer details such as the database and the web framework depend on inner abstractions, never the reverse.
- Q: Clean architecture vs vertical slice? A: Clean organizes by technical concern and protects the domain. Vertical slice organizes by feature and minimizes cross-feature coupling. Many teams combine them: slices inside a clean boundary.
- Q: Why a modular monolith before microservices? A: It gives enforced boundaries and clear data ownership without network calls, distributed transactions or per-service ops. If a module needs to leave later, the boundary is already there.
- Q: How do you stop architecture from eroding? A: Architecture tests in CI, project references that match the rule, code review checks, and ADRs recording the intended rules.

8 Common mistakes
- Fake layers: four projects but the Domain references EF Core attributes, or entities are just data bags. Shows up as tests that still need a database. Fix: keep the domain free of infrastructure references and test it alone.
- Repository per table over EF Core, wrapping what DbContext already is. Shows up as pointless boilerplate. Fix: abstract at the use-case or aggregate level, or use EF directly in slices.
- Shared database between modules. Shows up as hidden coupling and breaking schema changes. Fix: each module owns its tables and exposes data through contracts.
- Choosing microservices for style rather than team or scale needs. Shows up as a distributed monolith. Fix: start modular, split on evidence.
- Boundaries documented but not enforced. Shows up as drift within months. Fix: NetArchTest in the pipeline.

9 Mental model
- Concentric circles, arrows pointing inward:
  Api and Infrastructure  ->  Application  ->  Domain
- Modular monolith: one box containing several smaller boxes, each with a front door (contract) and a locked back room (internals).
- Vertical slice: a cake cut into feature wedges instead of horizontal layers.

10 Mini lab (about 35 minutes, local tools, .NET SDK only)
- Step 1: create the solution and four projects: dotnet new sln -n Shop; then dotnet new classlib for Shop.Domain, Shop.Application, Shop.Infrastructure and dotnet new webapi for Shop.Api (use -n and -o for each, then dotnet sln add each).
- Step 2: add references that follow the rule: Application references Domain. Infrastructure references Application. Api references Application and Infrastructure. Do not add Domain referencing anything.
- Step 3: in Domain add an Order class with a method Place() that throws if there are no items. In Application add IOrderRepository and a PlaceOrder handler. In Infrastructure add an in-memory repository. Register it in Api with DI.
- Step 4: add a test project Shop.ArchTests, reference all four projects and the NetArchTest.Rules package. Write one test: Domain must not depend on Infrastructure.
- Step 5: break the rule on purpose by adding a Domain reference to Infrastructure and a using statement that uses it. Run dotnet test.
- Expected result: the build or the architecture test fails. Remove the bad reference and the test passes.
- Clean-up: delete the solution folder.

11 Revision summary
- The dependency rule: dependencies point inward to the domain.
- Clean, onion and hexagonal share one idea: the domain does not know about infrastructure.
- Layer is a logical split, tier is a physical one.
- Vertical slice organizes by feature, layered organizes by technical concern.
- Modular monolith: one deployable, enforced module boundaries, each module owns its data.
- Pick the style from quality attributes and team context, not fashion.
- NetArchTest turns architecture rules into failing tests.
- Over-layering a small CRUD app is a mistake, not a virtue.
