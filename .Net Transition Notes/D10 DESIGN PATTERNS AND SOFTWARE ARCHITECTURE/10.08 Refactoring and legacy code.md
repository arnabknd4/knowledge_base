1 What is it
- Refactoring means changing the internal structure of code without changing what it does from the outside.
- Legacy code is code that is in production, valuable, and hard to change safely, usually because it has no tests.
- This topic covers how to spot problems (code smells), how to change code safely (characterization tests, seams, small steps), and how to decide what to fix (technical debt, metrics).
- Legacy equivalent: the 12-year MVC and Entity Framework codebase you maintain, with fat controllers, God classes and stored-procedure-heavy logic that nobody dares touch.

2 Why needed
- Every system you modernize starts as legacy code. Migration (1.12) and strangler fig (9.03) both depend on being able to change code safely.
- Without safe refactoring, each change adds risk and cost. Delivery slows down and the team starts to fear the code.
- Without a way to measure and record debt, you cannot argue for time to fix it.
- Architect interviews ask how you handle an untested monolith. This is the answer.

4 Features and core concepts
- Code smells: surface signs that a design problem may exist, such as long method, large class, long parameter list, duplicated code, feature envy, shotgun surgery, primitive obsession, switch statements on type. Why it matters: smells tell you where to look. They are hints, not proof.
- Refactoring catalog: named, small, behavior-preserving moves such as Extract Method, Extract Class, Move Method, Rename, Inline, Replace Conditional with Polymorphism, Introduce Parameter Object. Why it matters: a shared vocabulary makes reviews and plans clear, and each move is small enough to be safe.
- Characterization tests: tests that record what the code does today, right or wrong, before you touch it. Why it matters: they are your safety net when no tests exist. You write the test, run it, see the real output, and assert that output.
- Seams: a place where you can change behavior without editing the code at that spot. Examples: an interface, a virtual method, a constructor parameter, a DI registration. Why it matters: seams let you break hard dependencies (static calls, new HttpClient, DateTime.Now, direct DB access) so the code becomes testable.
- Boy Scout rule: leave the code a little cleaner than you found it. Why it matters: steady small cleanup beats a rare big cleanup that never gets approved.
- Technical debt quadrant: Martin Fowler's grid of deliberate vs inadvertent and prudent vs reckless debt. Why it matters: it helps you tell a conscious trade-off from plain sloppy work, and talk about each differently with the client.
- Measuring complexity, coupling and churn: cyclomatic complexity, cognitive complexity, afferent and efferent coupling, and how often a file changes. Why it matters: files that are both complex and frequently changed (hotspots) are where refactoring pays off most.
- Static analysis: Roslyn analyzers, SonarQube, code metrics in Visual Studio (verify current tooling). Why it matters: it finds smells and bugs automatically and enforces quality gates in the pipeline.
- Safe refactoring with tests and IDE tools: use automated refactorings in Visual Studio or Rider, commit after each small step, keep tests green. Why it matters: tool-driven refactors are far less error-prone than hand edits.
- Code review practices: small pull requests, review for design and readability, separate refactor commits from feature commits. Why it matters: mixing both makes review hard and hides bugs.
- Recording refactor decisions: write a short ADR or a tech debt ticket with context, options and decision (15.01). Why it matters: the team remembers why, and managers can see the debt budget.
- Memorize this cycle: red (failing characterization test), green (passes on current behavior), refactor (small step), run tests, commit.

5 Core focus (exam and interview)
- Most asked: how do you refactor code that has no tests? Answer: characterization tests first, find seams, small steps, commit often.
- Know the difference between refactoring (no behavior change) and rewriting or adding features.
- Know three or four smells with their usual fix.
- Know the debt quadrant and give one example per box.
- Know that hotspot analysis combines churn and complexity to pick targets.
- Know that refactoring and feature work should be in separate commits.
- No fixed numeric limits to remember. Any complexity threshold (for example 10 for cyclomatic complexity) is a team convention, not a standard (verify).

6 Real-world use case
- Situation: a 9-year-old MVC order module. One 1,800-line OrderController action calculates price, discounts, tax and writes to the database. No tests. A client wants new discount rules.
- Choice made:
  - Find churn and complexity hotspots first. The action turns out to be the top file.
  - Write characterization tests through a thin seam: extract the pricing code into a method, then a class behind an interface.
  - Replace the static call to the tax service and DateTime.Now with injected dependencies.
  - Refactor in small steps (Extract Method, then Extract Class) with tests green after each step.
  - Add the new discount rules to the new class, test first.
  - Record the decision in an ADR and book the remaining work as a tech debt item.
- Trade-off: you spend 2 to 3 sprints of slower visible output to gain safe, fast change later.
- When NOT to use it: code about to be deleted (a module planned for retirement in the strangler migration), code that never changes, or when the tests would cost more than a rewrite of a tiny module. Also do not refactor right before a release deadline without tests.

7 Interview lens
- Q: How do you start on a legacy codebase with no tests?
  A: I pick hotspots using churn and complexity. I add characterization tests around the area I must change, then create seams and refactor in small tested steps.
- Q: What is a seam?
  A: A place where I can alter behavior without editing the code in that place, such as an interface or constructor parameter. I use seams to replace hard dependencies in tests.
- Q: How do you convince a client to pay for refactoring?
  A: I tie it to business cost: slower delivery, defect rate and incident history in the hotspot files. I propose a fixed debt budget per sprint and show metrics before and after.
- Q: Refactor or rewrite?
  A: Refactor by default, because rewrites lose hidden behavior and take long. I rewrite only small, well-understood modules, or use strangler fig for larger parts.

8 Common mistakes
- Refactoring without tests: shows up as a regression in production after a harmless-looking cleanup. Fix: characterization tests first.
- Big-bang refactor branch that lives for weeks: shows up as painful merges and a stalled feature work. Fix: small steps merged to main often.
- Mixing refactor and feature in one commit: shows up as unreadable reviews and hard rollbacks. Fix: separate commits or pull requests.
- Chasing metrics: shows up as meaningless splits to lower complexity numbers. Fix: use metrics to find hotspots, judge by readability and change cost.
- Refactoring stable code nobody touches: shows up as wasted effort and risk. Fix: only refactor where change is coming.
- Unrecorded decisions: shows up as the next developer undoing your work. Fix: ADR or ticket.

9 Mental model
Think of renovating an occupied house.

  find hotspot -> pin behavior with tests -> create seam -> small step -> tests green -> commit -> repeat

You never knock down a load-bearing wall in one go. You prop it (tests), cut a small opening (seam), and replace it piece by piece while people keep living inside (production keeps running).

10 Mini lab (30 to 40 minutes, local tools only)
- Steps:
  - Create a console project: dotnet new console -n RefactorLab, then add xUnit with dotnet new xunit -n RefactorLab.Tests and reference the first project.
  - In the console project, write a class OrderCalculator with one method that takes quantity and price, applies a 10 percent discount if quantity is above 10, adds 18 percent tax, and reads DateTime.Now to apply an extra 5 percent discount on weekends.
  - Write three characterization tests by running the method first, noting the real outputs, and asserting those values. The weekend case will be hard to test, which exposes the missing seam.
  - Introduce a seam: add an IClock interface with a Now property, inject it through the constructor, and use a fake clock in the weekend test.
  - Use your IDE to Extract Method for the discount logic and the tax logic. Run the tests after each extraction.
  - Run the metrics: in Visual Studio use Analyze, Calculate Code Metrics, and compare cyclomatic complexity before and after.
- Expected result: all tests stay green through every step, the weekend case is now testable, and the main method is shorter with lower complexity.
- Clean-up: delete the RefactorLab folder, or keep it as a portfolio sample with a short README.

11 Revision summary
- Refactoring changes structure, not behavior.
- No tests: characterization tests first, then seams, then small steps.
- A seam lets you change behavior without editing at that spot.
- Hotspot equals high churn plus high complexity.
- Keep refactor commits separate from feature commits.
- Fowler's debt quadrant: deliberate or inadvertent, prudent or reckless.
- Boy Scout rule: leave code a little cleaner each time.
- Record decisions in an ADR or a tech debt ticket.
