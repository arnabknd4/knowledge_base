1 What is it
- Event sourcing: instead of storing only the current state of a record, you store every change as an immutable event (OrderPlaced, ItemAdded, OrderShipped). Current state is rebuilt by replaying the events.
- CQRS (advanced): writes and reads use separate models. The write side validates commands and appends events. The read side holds query-shaped views built from those events.
- Event store: an append-only log of events, grouped into one stream per aggregate (for example, one stream per order).
- Projection: code that reads events and builds a read model (a table or document) for queries.
- Snapshot: a saved copy of state at event N, so replay starts there instead of from event 1.
- Functional style in C#: pure functions, immutable data (records), and state change as "old state + event = new state". This fits event sourcing naturally.
- Reactive programming: code that reacts to streams of events or data (IObservable, System.Reactive, Rx).
- Legacy equivalent: an audit or history table beside the main table, or SQL triggers writing to a log table. Here the log is the source of truth and the current table is derived.

4 Features and core concepts
- Event store basics: append-only, one stream per aggregate, each event has a version number. Why it matters: full history and a built-in audit trail. Appends use optimistic concurrency (expected version), so two writers cannot silently overwrite each other.
- Events are facts in the past tense: OrderPlaced, not PlaceOrder. Why it matters: they never change, so old events must stay readable forever (event versioning, upcasting).
- Rehydration: load the stream, apply each event to an empty aggregate, get current state. Why it matters: this is how every write begins.
- Projections: handlers that update read models as events arrive. Why it matters: reads become fast and shaped for each screen or report. You can drop and rebuild any projection by replaying events.
- Eventual consistency of projections: the read model lags the write by milliseconds to seconds. Why it matters: the UI must cope (show a pending state, or read your own write from the stream).
- Snapshots: store state every N events (for example every 100). Why it matters: replay time stays flat for long-lived streams. Do not add them until streams are long.
- Advanced CQRS: separate command handlers and query handlers, possibly separate databases. Why it matters: you can scale and tune each side independently. It is not required to have event sourcing, and event sourcing almost always pairs with CQRS.
- Functional style in C#: aggregate as a pure function, State Apply(State s, Event e). Use records and switch expressions. Why it matters: easy to test, no hidden mutation, replay is just a fold over events.
- Reactive programming: Rx operators (Select, Where, Throttle, Buffer) over event streams. Why it matters: a natural way to compose live feeds and UI updates, but a different mental model with a learning cost.
- Worth memorizing: State Apply(State s, object e) => e switch { OrderPlaced p => s with { Status = "Placed" }, OrderShipped => s with { Status = "Shipped" }, _ => s };
- Tools to know by name: EventStoreDB, Marten (PostgreSQL), Azure Cosmos DB change feed, Event Hubs (verify current tooling).

6 Real-world use case
- Situation: a payments or order system where auditors ask "why did this balance change, and who did it?" Your current SQL Server tables show only the latest value.
- Choice: model Order as an aggregate with an event stream. Commands produce events. A projection builds an OrderSummary table for screens. Another projection feeds a reporting database. Events are also published through the outbox to Service Bus for other services.
- Why it works: complete audit with no extra work, any new report can be built later by replaying history, and you can debug production by replaying a stream locally.
- Trade-off: more moving parts, eventual consistency in the UI, event schema versioning for years, harder ad hoc queries on the write side, and a team learning curve.
- When NOT to use it: plain CRUD apps, admin screens, reference data, small teams without a clear audit or history need, and anywhere "current state only" is enough. Use it for one or two core domains, not the whole system.

11 Revision summary
- Event sourcing stores events as the source of truth. Current state is derived by replay.
- Events are immutable, past tense, and appended to one stream per aggregate.
- Appends use expected-version optimistic concurrency.
- Projections build read models. They are rebuildable and eventually consistent.
- Snapshots speed up replay. Add them only when streams get long.
- CQRS can be used without event sourcing. Event sourcing nearly always needs CQRS.
- Functional style: state = fold of Apply over events, using records and pure functions.
- Use it for audit-heavy core domains only. It is costly for ordinary CRUD.
