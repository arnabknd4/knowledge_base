1 What is it

Structural patterns are ways to compose classes and objects into larger structures while keeping them flexible. They answer the question: how do I wire these pieces together without tying them in knots?

- Adapter: wraps one interface so it looks like another.
- Decorator: wraps an object to add behavior without changing it.
- Facade: one simple entry point over a complicated subsystem.
- Proxy: a stand-in that controls access to a real object.
- Composite: treats a single item and a tree of items the same way.
- Bridge: splits an abstraction from its implementation so both can vary.
- Flyweight (awareness): shares common state across many small objects to save memory.

Legacy equivalent: wrapper classes around old COM or ASMX services, HttpModules and HttpHandlers in the System.Web pipeline, and "Manager" or "Helper" classes hiding messy subsystems.

----------

2 Why needed

- Without Adapter, your code is welded to a vendor or legacy API shape. Replacing it means edits everywhere.
- Without Decorator, cross-cutting needs (logging, caching, retry) get copied into every class or pushed into inheritance chains.
- Without Facade, callers learn five subsystem APIs and call them in the right order, and every caller repeats that knowledge.
- Without Proxy, lazy loading, access control and remote calls leak into business code.
- Without Composite, tree structures (menus, permissions, folders) need if-else for leaf vs branch.

----------

4 Features and core concepts

Adapter
- Plain meaning: converts one interface into the one the caller expects.
- Why it matters: it is the main tool for isolating legacy or third-party code. It is also the anti-corruption layer idea at class level.
- Memorize: class LegacyPayAdapter : IPaymentGateway { ctor(LegacyPayClient c); Pay(...) => c.MakePayment(...) }

Decorator
- Plain meaning: same interface as the wrapped object, adds behavior before or after delegating.
- Why it matters: lets you stack logging, caching and retry without touching the core class.
- DI decoration: register the inner service, then wrap it. Scrutor does this with services.Decorate<IOrderService, CachedOrderService>(); (verify package version). Without Scrutor, use a factory registration that builds the wrapper manually.
- .NET example: DelegatingHandler on HttpClient, GZipStream wrapping a Stream.

Facade
- Plain meaning: one simple class that calls many subsystem classes in the right order.
- Why it matters: reduces coupling and gives callers one place to learn.
- Watch out: a facade that grows business logic becomes a god class.

Proxy
- Plain meaning: an object with the same interface that controls access to the real one.
- Why it matters: covers lazy loading, caching, access checks and remote calls.
- Types: virtual proxy (lazy), protection proxy (access), remote proxy (network), caching proxy.
- .NET example: EF Core lazy-loading proxies, gRPC and WCF client proxies, Castle DynamicProxy.

Decorator vs Proxy
- Decorator adds behavior. Proxy controls access. The code shape is the same, the intent differs. This is a favorite interview question.

Composite
- Plain meaning: leaf and group share one interface, so callers treat both the same.
- Why it matters: simplifies tree logic such as folders, menus, org charts, nested permission rules.
- .NET example: ASP.NET control tree in WebForms, WPF visual tree, expression trees.

Bridge
- Plain meaning: keep the abstraction and the implementation as two separate hierarchies, joined by a reference.
- Why it matters: avoids a class explosion (for example Notification x Channel: Email, SMS, Push become 2 hierarchies, not 6+ classes).
- .NET example: ILogger (abstraction) over many logging providers.

Flyweight (awareness)
- Plain meaning: share the unchanging part of many objects.
- Why it matters: saves memory when you have huge object counts.
- .NET example: string interning, cached boxed small integers.

.NET pipeline examples
- Middleware is a chain of wrappers around the next delegate. It behaves like decorators and chain of responsibility.
- Streams: new StreamReader(new GZipStream(new FileStream(...))) is decorator stacking.

5 Core focus (exam and interview)

- Know the one-line intent of each pattern, and the Adapter vs Decorator vs Proxy vs Facade differences:
  - Adapter changes the interface.
  - Decorator keeps the interface and adds behavior.
  - Proxy keeps the interface and controls access.
  - Facade creates a new, simpler interface over many classes.
- Know that built-in DI in .NET has no decorator support. Use Scrutor or manual factory registration (verify).
- Know that DelegatingHandler is a decorator and middleware is a pipeline of wrappers.
- Decorator order matters: cache outside retry, or retry outside cache, gives different behavior.
- Keep a short answer ready for "where do you use these in real projects?"

6 Real-world use case

Situation: a .NET Framework 4.8 app calls a SOAP payment service from 40 places. You are moving to .NET 8+ (verify current LTS) and a REST gateway.

Choice:
- Define IPaymentGateway in your domain.
- Write a SoapPaymentAdapter now and a RestPaymentAdapter later. Callers never change.
- Add a LoggingPaymentGateway decorator and a RetryPaymentGateway decorator, registered via DI.
- Put an OrderFacade in front of inventory, payment and shipping for the checkout controller.

Trade-off:
- More small classes and indirection. Debugging means stepping through wrappers.
- Decorator stacks hide order dependencies.

When NOT to use:
- Do not adapt an API you control and can simply change.
- Do not use a facade to hide a poor subsystem design you could fix.
- Do not decorate when a middleware or MediatR-style behavior already covers the concern.
- Do not use Bridge or Flyweight for small, stable code. It is overengineering.

7 Interview lens

Q1. Adapter vs Facade?
- Adapter makes one existing interface fit another expected one. Facade creates a new simpler interface over a group of classes.

Q2. Decorator vs Proxy?
- Same shape, different intent. Decorator adds behavior; proxy controls access or lifetime of the real object.

Q3. How do you apply decorators with .NET built-in DI?
- Built-in DI has no native decoration. Use Scrutor's Decorate, or register the wrapper with a factory that resolves the inner service (verify).

Q4. Where do you see structural patterns inside .NET itself?
- Streams (decorator), middleware and DelegatingHandler (decorator and chain), ILogger over providers (bridge), EF lazy-loading proxies (proxy), expression trees (composite).

8 Common mistakes

- Facade becomes a god class: it starts as orchestration, then collects business rules. Fix: keep it thin, push logic into domain services.
- Decorator order bug: retry wrapped inside cache, so failures get cached. Fix: decide order deliberately and cover it with a test.
- Wrapping everything in adapters "just in case": more code, no benefit. Fix: adapt only at real boundaries (legacy, vendors).
- Lazy-loading proxies in EF causing N+1 in production. Fix: explicit Include or projections, avoid lazy loading by default.
- Decorating a singleton with a scoped dependency (captive dependency). Fix: match lifetimes.
- Confusing proxy and decorator in design docs. Fix: name the intent in the class name (CachingX, AuthorizingX, RetryingX).

----------

9 Mental model

Think of wrappers around a core:

  Caller -> [Logging] -> [Retry] -> [Cache] -> Real service

- Adapter: a travel plug converter. Different socket, same electricity.
- Decorator: layers of clothing on one person.
- Proxy: a receptionist who decides whether you reach the person.
- Facade: a hotel concierge who talks to many departments for you.
- Composite: folders inside folders, all treated as "items".
- Bridge: remote control (abstraction) and TV brand (implementation), varying independently.

11 Revision summary

- Adapter changes an interface. Decorator adds behavior. Proxy controls access. Facade simplifies a subsystem.
- Decorator and proxy look alike. Intent separates them.
- Composite makes leaf and group look the same to callers.
- Bridge separates abstraction from implementation to avoid class explosion.
- Flyweight shares common state to save memory (awareness only).
- Built-in .NET DI has no decorators. Use Scrutor or a factory (verify).
- Middleware, DelegatingHandler and Stream wrapping are decorator-style chains.
- Keep facades thin and adapt only at real boundaries.
