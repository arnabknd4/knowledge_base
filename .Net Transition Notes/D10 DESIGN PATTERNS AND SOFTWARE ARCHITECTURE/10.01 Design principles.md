1 What is it
- Design principles are the rules of thumb that keep code easy to change: SOLID, DRY, KISS, YAGNI, separation of concerns, composition over inheritance, Law of Demeter, coupling and cohesion, cyclomatic complexity, fail fast, immutability.
- They are not laws. They are trade-offs that you apply when a design starts to hurt.
- Legacy equivalent: the "layered MVC with a fat service class" habits of .NET Framework projects, where Unity or Ninject was often used as a service locator.

2 Why needed
- Without them, a change in one place breaks three other places.
- Teams get slow because every class knows too much about every other class.
- As lead and architect, you review designs. You need names for what you see, so your review comments are precise and defensible.
- Interviews use these terms as the base vocabulary for every design question.

4 Features and core concepts

SOLID
- S, Single Responsibility: a class has one reason to change. Why: smaller blast radius. .NET example: split OrderService into OrderPricing, OrderRepository, and OrderNotifier. Split by reason to change, not by method count.
- O, Open/Closed: add behavior by adding code, not by editing tested code. Why: fewer regressions. .NET example: a new IDiscountRule implementation registered in DI instead of another if branch.
- L, Liskov Substitution: a subtype must work wherever the base type is used. Why: callers stop checking types. Gap: a ReadOnlyRepository that inherits Repository and throws on Save breaks this.
- I, Interface Segregation: many small interfaces beat one large one. Why: implementers are not forced to stub methods. .NET example: IReader and IWriter instead of one IFileService.
- D, Dependency Inversion: high-level code depends on abstractions, and the abstractions are owned by the high level. Why: you can swap and test infrastructure. Gap: DI containers are the tool, inversion is the principle. Injecting a concrete class through a container is not inversion.

Other principles
- DRY: one piece of knowledge lives in one place. Why: one fix, not five. Gap: duplicate code that changes for different reasons is not a DRY violation. Wrong sharing creates coupling, which is worse than duplication.
- KISS: pick the simplest design that works. Why: simple code is cheaper to read and operate.
- YAGNI: do not build for needs you do not have yet. Why: speculative code is carried cost. Gap: YAGNI applies to features, not to quality practices like tests and logging.
- Separation of concerns: each part handles one kind of work (UI, rules, data). Why: you can change one without touching the rest.
- Composition over inheritance: combine small objects instead of deep class trees. Why: inheritance is a tight, compile-time bond. .NET example: ASP.NET Core middleware and DI decorators are composition. Legacy MVC base controllers are inheritance.
- Law of Demeter: talk to your direct collaborators only. Smell: order.Customer.Address.City.ToUpper(). Why: callers do not depend on the shape of distant objects.
- Coupling and cohesion: aim for low coupling between modules and high cohesion inside them. Why: this pair predicts how painful change will be.
- Cyclomatic complexity: the count of independent paths through a method. Why: it estimates minimum tests needed. Rule of thumb: above about 10 deserves review (verify team standard).
- Fail fast: reject bad input at the edge with clear errors. Why: bugs surface near the cause. .NET example: ArgumentNullException.ThrowIfNull(x) and validation on start for options.
- Immutability: objects that do not change after creation. Why: safe across threads, easy to reason about. Modern C#: records, init, required, readonly struct, IReadOnlyList.

Code worth memorizing
- public record Money(decimal Amount, string Currency);
- ArgumentNullException.ThrowIfNull(order);

5 Core focus (exam and interview)
- Most asked: SOLID with a real .NET example for each letter, and a bad-code-to-good-code walk-through.
- Most asked: DIP vs DI vs IoC. Principle, technique, and container.
- Most asked: DRY vs wrong abstraction, and YAGNI vs planning ahead.
- Most asked: composition vs inheritance with middleware or decorators.
- Number to recall: cyclomatic complexity of about 10 as a review trigger (verify team policy).
- Azure exams touch this only lightly, through loose coupling and queue-based designs.

6 Real-world use case
- Situation: a legacy MVC invoice module had a 1,200-line InvoiceService with tax, discounts, PDF, and email in one class. Every GST rule change risked the whole flow.
- Choice: extract an ITaxRule interface with one class per rule, register them in DI, and have the service loop over IEnumerable<ITaxRule>. PDF and email moved behind IInvoiceRenderer and INotifier.
- Trade-off: more files and more indirection. New joiners need a short map of the structure.
- When NOT to use it: a small CRUD screen with one rule. A plain method is better than five interfaces. Abstract at the second or third variation, not the first.

7 Interview lens
- Q: What is the difference between DIP, DI, and IoC?
  A: DIP is a design principle: depend on abstractions. DI is the technique of passing dependencies in. IoC is the broader idea that a framework or container controls the flow, and the container is the usual tool.
- Q: When is DRY harmful?
  A: When two pieces of code look alike but change for different reasons. Merging them couples unrelated features. Wait for the third occurrence and confirm they change together.
- Q: How do you spot an LSP violation in review?
  A: A subclass throws NotSupportedException, ignores a base contract, or callers use type checks or "is" before calling it. Fix by splitting the interface or using composition.
- Q: Give a .NET example of composition over inheritance.
  A: ASP.NET Core middleware and decorating a service in DI with logging or caching. Behavior is stacked at runtime without a class hierarchy.

8 Common mistakes
- Interface for every class: shows up as IFooService with one implementation and no second caller. Fix: add the interface when you need a seam for tests or a second variant.
- Premature abstraction: shows up as a generic base repository nobody can change. Fix: duplicate once, abstract on the third case.
- Static helpers and new inside classes: shows up as code that cannot be unit tested. Fix: inject the dependency.
- God class named Manager or Helper: shows up as constant merge conflicts. Fix: split by reason to change.
- Service locator (calling IServiceProvider.GetService inside classes): shows up as hidden dependencies and runtime failures. Fix: constructor injection.
- Deep inheritance for code reuse: shows up as changes in the base class breaking unrelated children. Fix: extract a collaborator and compose.
- Mutable shared state in singletons: shows up as rare, hard-to-reproduce bugs under load. Fix: immutable objects or scoped state.

9 Mental model
- Think of a building with standard sockets. Appliances (classes) plug into sockets (interfaces). You can replace an appliance without rewiring the wall.

  High-level policy
        |
   [interface it owns]
        ^
  Low-level detail (EF, SMTP, Blob)

- Arrows of dependency point toward the policy, not toward the detail.

11 Revision summary
- SOLID: one reason to change, extend not edit, substitutable subtypes, small interfaces, depend on abstractions.
- DIP is a principle, DI is a technique, the container is a tool.
- DRY applies to knowledge, not to similar-looking text.
- YAGNI limits features, not tests or quality.
- Prefer composition: middleware and DI decorators are the .NET examples.
- Aim for low coupling and high cohesion.
- Cyclomatic complexity above about 10 is a review signal (verify team policy).
- Fail fast at the edge. Use records and init for immutability.
