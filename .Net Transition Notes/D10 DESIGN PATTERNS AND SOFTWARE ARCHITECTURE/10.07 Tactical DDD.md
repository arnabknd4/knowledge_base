1 What is it
- Tactical DDD is the set of building blocks you use inside one bounded context to model business rules in code. The blocks are entities, value objects, aggregates, repositories, domain events, domain services and factories.
- An entity is an object with an identity that stays the same over time (an Order with an OrderId). A value object has no identity and is defined only by its values (Money, Address).
- An aggregate is a cluster of objects treated as one unit for changes. One member is the aggregate root, and outside code may talk only to the root.
- Legacy equivalent: EF6 entity classes with public setters and a service or manager class that holds all the rules (anemic model), with one DbContext save covering many tables.

2 Why needed
- Business rules (invariants) end up scattered across controllers, services and stored procedures. Nobody knows where the rule "an order cannot exceed the credit limit" lives.
- Without clear boundaries, any code can change any object. Data becomes inconsistent and bugs are hard to trace.
- Large transactions lock many rows and cause blocking. Aggregates keep each transaction small and well defined.
- Code that does not use the business language makes talking to domain experts slow and error-prone.

3 Before you read
- Bounded context: a boundary inside which one model and one vocabulary apply (topic 9.02).
- Invariant: a rule that must always be true, for example "order total equals the sum of its lines".
- Transaction: a group of changes saved all together or not at all (topic 4.03).
- EF Core mapping basics: owned types and value converters (topic 4.05).

4 Features and core concepts
- Entities: objects with identity. Why it matters: two Customers with the same name are still different people, so equality is by ID, not by values.
- Value objects: immutable objects compared by value. Why it matters: Money(100, INR) replaces a loose decimal and cannot hold an invalid state. In C#, a record is a natural fit.
- Aggregates and invariants: a group of objects that must stay consistent together. Why it matters: the aggregate guarantees its rules after every operation.
- Aggregate roots: the single entry point of an aggregate. Why it matters: outside code cannot reach inner objects directly, so rules cannot be bypassed.
- Repositories per aggregate: one repository to load and save each whole aggregate. Why it matters: no repository for inner objects, so nobody changes parts of an aggregate behind the root.
- Domain events: a record that something meaningful happened (OrderPlaced). Why it matters: other parts react without the aggregate knowing them, which reduces coupling.
- Domain services: business logic that does not belong to one entity (transfer between two accounts). Why it matters: avoids forcing logic into the wrong object.
- Factories: code that creates a valid aggregate. Why it matters: complex creation rules live in one place and an invalid object cannot be built.
- Ubiquitous language in code: class and method names match the words domain experts use (order.Confirm(), not order.Status = 2). Why it matters: code can be read and checked by the business.
- Anemic vs rich models: anemic means data-only classes with logic in services. Rich means the object owns its behaviour. Why it matters: rich models protect invariants, anemic models cannot.
- Transaction boundaries: one aggregate changes per transaction. Why it matters: small, fast transactions with less locking.
- Eventual consistency between aggregates: changes in other aggregates happen later through events. Why it matters: it replaces large cross-aggregate transactions and works across services.
- Code worth memorizing:
- public record Money(decimal Amount, string Currency);
- public void AddLine(Product p, int qty) { if (qty <= 0) throw new DomainException("Qty"); _lines.Add(new OrderLine(p.Id, qty)); }

5 Core focus (exam and interview)
- Most asked: what is an aggregate, why one root, why one aggregate per transaction, entity vs value object.
- Rule to remember: reference other aggregates by ID, not by object reference.
- Rule to remember: design small aggregates. Large ones cause concurrency conflicts.
- Rule to remember: domain events inside one process are in-memory. Cross-service events need an outbox (topic 6.03).
- Rule to remember: repositories belong to aggregates, not to tables.
- Not every domain needs this. It pays off only where business rules are complex.
- Aggregate boundaries come from invariants, not from database foreign keys.

6 Real-world use case
- Situation: a Kolkata insurance client has a policy system with a 3,000-line PolicyService and public setters on every entity. Premium rules break when two screens edit the same policy.
- Choice: model Policy as an aggregate root with PolicyCoverage children and a Premium value object. All changes go through root methods. A PolicyIssued domain event triggers billing through a Service Bus message via an outbox.
- Trade-off: more classes, a learning curve for the team, and EF Core mapping effort (private setters, owned types, backing fields).
- When NOT to use it: simple CRUD screens, reporting, admin master data. A transaction script or plain EF model is cheaper and clearer there.

7 Interview lens
- Q: What is an aggregate?
- A: A cluster of objects changed as one consistency unit through a single root. The root enforces the invariants.
- Q: Why keep aggregates small?
- A: Big aggregates load more data and conflict more under concurrent edits. Small ones keep transactions short.
- Q: How do two aggregates stay consistent?
- A: Through domain events and eventual consistency, not one big transaction. Use an outbox for reliability.
- Q: Entity vs value object?
- A: An entity has identity and a lifecycle. A value object is immutable and compared by its values.

8 Common mistakes
- Anemic model with an "aggregate" label: public setters let any code break rules. Fix: private setters and behaviour methods on the root.
- Giant aggregate (Customer holding all orders): slow loads and concurrency conflicts. Fix: split and reference by ID.
- Repository for every table: inner objects get changed directly. Fix: one repository per aggregate root.
- Aggregate holds references to other aggregates: lazy loading surprises and hidden coupling. Fix: store IDs only.
- Publishing events before the transaction commits: events sent for changes that were rolled back. Fix: outbox pattern.
- Applying DDD everywhere: slow delivery on simple screens. Fix: use it only in the core domain.

9 Mental model
- An aggregate is a locked room with one door. The root is the doorkeeper.
- Everything inside obeys the rules and changes together.
- Rooms talk to each other by sending notes (domain events) and address them by room number (ID).

10 Mini lab
- Time: about 35 minutes. Tools: .NET SDK and xUnit locally, no Azure needed.
- Step 1: run dotnet new classlib -n Shop.Domain and dotnet new xunit -n Shop.Tests, then add a project reference from tests to domain.
- Step 2: create a record Money(decimal Amount, string Currency) that throws if Amount is negative.
- Step 3: create Order as an aggregate root with a private List<OrderLine>, a public read-only view, and methods AddLine and Confirm. AddLine rejects quantity 0 or a confirmed order. Confirm rejects an empty order and adds an OrderConfirmed event to a list.
- Step 4: write four tests: invalid quantity fails, adding a line after confirm fails, empty confirm fails, confirm raises one event.
- Expected result: all four tests pass, and the code will not let you build an invalid Order from outside.
- Clean-up: delete the Shop folder when done.

11 Revision summary
- Entity has identity. Value object is immutable and compared by value.
- Aggregate is the consistency boundary. The root is the only entry point.
- One aggregate per transaction. Other aggregates update through events.
- Reference other aggregates by ID, not by object.
- One repository per aggregate root.
- Rich model puts behaviour and invariants inside the object. Anemic does not.
- Domain events need an outbox for reliable delivery across services.
- Use tactical DDD only where business rules are complex.
