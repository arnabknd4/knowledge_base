1 What is it
- A set of named, reusable designs for organizing business logic and data access in an application.
- Repository: a collection-like object that hides how data is stored. Your code asks it for objects and does not see SQL.
- Unit of Work: one object that tracks all changes in a business operation and saves them together in one transaction.
- Specification: a small object that holds one query rule (for example "active orders over 1000") so rules can be reused and combined.
- Active Record: a class that holds data and also saves itself. Data Mapper: a separate mapper class moves data between plain classes and the database.
- DTO (Data Transfer Object): a plain class used only to carry data across a boundary such as an API.
- Service layer: a layer of classes that coordinate use cases and hold no UI or storage details.
- Domain model: business rules live inside rich objects. Transaction script: business rules live in one procedure per use case.
- CQRS (Command Query Responsibility Segregation): separate models for writing and for reading.
- Anti-corruption layer: a translation layer that stops a messy external model from leaking into your model.
- Result pattern: a method returns success or failure as a value instead of throwing an exception.
- Null Object: a do-nothing object used instead of null.
- Options pattern: strongly typed configuration classes bound from settings.
- Legacy equivalent: DAL classes with ADO.NET or EF6 DbContext, BLL classes, and ViewModels in your MVC projects.

2 Why needed
- Business rules, data access and API shapes change at different speeds. Mixing them makes every change risky.
- Without these patterns: controllers contain SQL and rules, tests need a real database, and one schema change breaks the API contract.
- Interviewers use these patterns to test whether you can judge when a pattern helps and when it is ceremony.

4 Features and core concepts
- Repository: hides storage behind an interface. Matters because business code becomes testable and storage can change. In EF Core, DbSet is already a repository, so a wrapper often adds nothing (see section 5).
- Unit of Work: groups changes into one commit. Matters because partial saves leave bad data. EF Core DbContext is already a Unit of Work (SaveChanges commits everything tracked).
- Specification: a reusable, combinable query rule. Matters because it stops repository interfaces growing a method per query. It works well with EF Core by building an expression.
- Active Record: object saves itself. Matters because it is fast to build for simple CRUD, but business code is tied to the database.
- Data Mapper: separate mapper (EF Core is a Data Mapper). Matters because domain classes stay free of database code.
- DTO: shape built for the caller. Matters because you never expose entities, so you avoid over-posting, accidental data leaks and breaking changes. In C#, a record is a good DTO: public record OrderDto(int Id, decimal Total);
- Service layer: use-case classes such as PlaceOrderService. Matters because controllers stay thin and the same use case can serve API, jobs and messages.
- Domain model vs transaction script: transaction script is one procedure per request and is simple. Domain model puts rules in entities and pays off when rules are complex. Choose by rule complexity, not fashion.
- CQRS: commands change state, queries only read. Matters because read shapes (joins, projections) differ from write rules. Start simple: same database, different classes. Use Dapper or EF projections on the read side.
- Anti-corruption layer: adapter and translator in front of a legacy or third-party system. Matters during migration, because the old model does not pollute the new one. Pairs with strangler fig (topic 9.03).
- Result pattern: Result<T> with IsSuccess and Error. Matters because expected failures (validation, not found) are not exceptional, and exceptions are slow and hide control flow.
- Null Object: for example NullLogger or a NoDiscount policy. Matters because it removes null checks.
- Options pattern: services.Configure<SmtpOptions>(config.GetSection("Smtp")); inject IOptions<SmtpOptions>. Matters because settings are typed, validated and testable (topic 1.04).

5 Core focus (exam and interview)
- Most asked: "Is the Repository pattern still needed with EF Core?" Strong answer: DbContext already implements Repository and Unit of Work. A wrapper is useful only for testing isolation you cannot get otherwise, or for a domain aggregate boundary. A generic Repository<T> over EF is usually an anti-pattern.
- Also asked: Active Record vs Data Mapper, DTO vs entity, service layer vs domain model, and when CQRS is overkill.
- Defaults to remember: one repository per aggregate root, never per table. Unit of Work scope equals one request (scoped lifetime). DTOs never contain behavior.
- Smell to name: anemic domain model, where entities are only getters and setters and all rules sit in services.
- Exam angle (AZ-305): CQRS and anti-corruption layer appear in the Azure Architecture Center cloud design patterns list.

6 Real-world use case
- Situation: a legacy .NET Framework order system (EF6, business logic in controllers) is being modernized to .NET on Azure. It must call an old SOAP billing system.
- Choice: service layer for use cases, EF Core directly in handlers for simple queries, a repository only for the Order aggregate, DTO records at the API, and an anti-corruption layer wrapping the SOAP billing client. Read endpoints use Dapper projections (light CQRS).
- Trade-off: more classes and mapping code, in return for testable rules and a clean boundary to billing.
- When NOT to use: a small CRUD admin app. Use EF Core directly in minimal API handlers. Full repository, specification and CQRS there is ceremony with no payoff.

7 Interview lens
- Q: Why not expose EF entities from the API? A: It leaks internal columns, allows over-posting and ties the contract to the schema. Use DTOs and map.
- Q: Is Repository plus Unit of Work needed with EF Core? A: Usually not, because DbContext is both. Add a repository per aggregate only when you need domain isolation or easier tests.
- Q: When do you choose a domain model over transaction script? A: When rules are complex and change often. For simple CRUD workflows, transaction script is faster and clearer.
- Q: When is CQRS justified? A: When read and write shapes or loads differ a lot. Separate classes first, separate databases only with a proven need, because that adds eventual consistency.

8 Common mistakes
- Generic IRepository<T> with GetAll returning IQueryable. Shows up as queries leaking into controllers and N+1 problems. Fix: aggregate-specific repositories or direct DbContext use.
- Repository per table. Shows up as business rules scattered across services. Fix: repository per aggregate root.
- Returning entities from controllers. Shows up as breaking client changes after a column rename. Fix: DTOs.
- Throwing exceptions for validation failures. Shows up as slow requests and noisy logs. Fix: Result pattern.
- Singleton Unit of Work or DbContext. Shows up as concurrency errors and stale data. Fix: scoped lifetime.
- Applying CQRS everywhere. Shows up as double the code with no benefit. Fix: use it only on hot or complex areas.

9 Mental model
- Request flow:
  Controller -> DTO in -> Service layer (use case) -> Domain model / Repository -> DbContext (Unit of Work) -> Database
  Back out: entity -> mapper -> DTO out.
  Side door: Service layer -> Anti-corruption layer -> legacy or third-party system.
- Picture: the service layer is the conductor, the domain model holds the rules, the repository is the filing clerk, and the DTO is the envelope that leaves the building.

10 Mini lab (30 minutes, local tools only)
- Steps:
  - Run dotnet new webapi -minimal -n PatternsLab and add Microsoft.EntityFrameworkCore.Sqlite.
  - Create an Order entity and an OrderDto record (Id, Total). Create an AppDbContext with a DbSet<Order>.
  - Add a minimal API endpoint that reads orders through DbContext, projects with Select to OrderDto, and returns it.
  - Add an IOrderRepository only for a method AddOrder with a rule (Total must be above 0). Return Result<Order> instead of throwing.
  - Register the repository as scoped. Call SaveChangesAsync once per request.
  - Add a second endpoint that returns a failed Result as ProblemDetails with status 400.
- Expected result: the GET returns DTOs with no entity-only fields, and a POST with Total of 0 returns 400 without any exception in the log.
- Clean-up: delete the PatternsLab folder and the SQLite file.

11 Revision summary
- DbContext is already Repository plus Unit of Work, so wrap it only for a reason.
- One repository per aggregate root, never per table.
- Never expose entities at the API, use DTOs (records).
- Result pattern for expected failures, exceptions for unexpected ones.
- Domain model for complex rules, transaction script for simple ones.
- CQRS starts as separate classes, not separate databases.
- Anti-corruption layer protects your model from legacy and third-party models.
- Options pattern gives typed, validated configuration (IOptions<T>).
