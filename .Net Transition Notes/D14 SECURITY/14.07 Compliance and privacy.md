14.07 Compliance and privacy
Tags: P3 R L (no K tag, so new-topic depth, FULL note, with mini lab)

---

1 What is it

- Compliance means proving your system follows rules set by laws, customers or industry bodies. Privacy means handling personal data only in ways the person agreed to and the law allows.
- GDPR is the EU data protection law. India's DPDP Act (Digital Personal Data Protection Act, 2023) is India's equivalent (verify current rules and timelines).
- Data residency means keeping data in a named country or region. Audit logging means a tamper-resistant record of who did what, when.
- Legacy equivalent: the "data retention policy" and "audit table" requests that arrived late in .NET Framework projects, usually as a column like IsDeleted plus a CreatedBy/ModifiedBy trigger.

2 Why needed

- Clients (especially EU, US and BFSI clients of Indian IT firms) will not sign contracts without proof of compliance.
- Without it: fines, failed audits, lost deals, and expensive late rework because deleting a user's data from five systems is very hard after the fact.
- An architect is expected to design for it up front, not bolt it on.

3 Before you read

- Personal data: any information that identifies a person, directly (name, phone) or indirectly (device ID, IP address).
- Data store map: you know which databases, caches, queues and logs hold which data.
- Encryption at rest and in transit, and Key Vault (notes 14.02, 12.08).
- Role-based access (note 12.02).

4 Features and core concepts

- GDPR basics: EU law with principles of lawful basis, purpose limitation, data minimisation, accuracy, storage limitation and security. Matters because it is the model most other laws copy. Key roles: data subject (the person), controller (decides why and how), processor (handles data for the controller). Penalties go up to 4 percent of global turnover (verify).
- India DPDP Act awareness (verify): Indian law built on consent, with "data principal" (person) and "data fiduciary" (organisation). Matters because Kolkata and remote India jobs will ask about it. Rules, deadlines and any cross-border limits change, so check the official source.
- Data residency: data stays in a chosen region. Matters because laws or contracts may ban moving it abroad. In Azure you choose the region per resource and use Azure Policy to deny other regions.
- Audit logging: append-only record of access and changes. Matters because auditors ask "who viewed this record?". Write who, what, when, from where, result. Never log the personal data itself.
- Retention: keep data only as long as needed, then delete or anonymise. Matters because old data is liability. Tools: blob lifecycle rules, Log Analytics retention, scheduled purge jobs.
- Right to erasure impact on design: a person can ask you to delete their data. Matters because data lives in the DB, backups, caches, logs, search indexes and analytics. Design a single "delete user" flow that reaches all of them. Crypto-shredding (delete the per-user encryption key) helps when backups cannot be edited.
- PCI-DSS (card data), HIPAA (US health data), SOC 2 (service organisation controls report), ISO 27001 (information security management standard): awareness only. Know what each protects and that SOC 2 and ISO 27001 are audited reports or certificates a vendor shows to clients. PCI scope shrinks if you never store card numbers (use a payment provider).
- Privacy by design: privacy is a default in the design, not an add-on. Matters because retrofitting costs far more. Examples: collect less, mask by default, separate identity data from activity data.
- Data classification: label data as public, internal, confidential or restricted. Matters because labels decide encryption, access and retention. In Azure use Microsoft Purview labels (verify service name).

Worth memorizing, an Azure Policy built-in idea: "Allowed locations" policy with effect Deny, so resources cannot be created outside approved regions.

5 Core focus (exam and interview)

- Most asked: how do you design for right to erasure; how do you keep data in one country; what do you log for audit and what you must not log.
- Data residency is about where data is stored and processed. Region pairs and geo-redundant storage can copy data to a paired region, so check the pair (verify).
- Backups, logs and caches are the usual hidden copies of personal data.
- Consent can be withdrawn, so design must record consent state and purpose.
- Pseudonymisation (replace identifiers with tokens) still counts as personal data under GDPR. Full anonymisation does not.
- Breach notification has fixed time limits under GDPR (72 hours to regulator, verify).

6 Real-world use case

- Situation: an Indian firm builds a customer portal for an EU retailer on Azure, with Azure SQL, Redis, blob storage and Application Insights.
- Choices: deploy to an EU region with the Allowed locations policy; classify tables and tag PII columns; keep a UserId-keyed erasure job that deletes or anonymises across SQL, blob and search, and expires Redis keys; mask PII in logs; Log Analytics retention set to a defined period; audit trail table append-only.
- Trade-off: more engineering effort, slower debugging because logs hold no PII, and backup copies expire on a schedule, not instantly.
- When not to over-engineer: an internal tool with no personal data or an early prototype. Still keep logging clean from day one.

7 Interview lens

- Q: How do you handle a delete request when backups exist? A: Delete from live systems at once and document that backups expire on a fixed cycle. Use per-user keys (crypto-shredding) where backup immutability blocks edits.
- Q: Difference between controller and processor? A: The controller decides the purpose and means of using the data. The processor acts on the controller's instructions, which is usually the IT service company.
- Q: How do you enforce data residency in Azure? A: Allowed locations policy, region-specific resources, and a check on geo-redundant replication targets and cross-region services.
- Q: What do you put in an audit log? A: Who, what action, which record, when, source, outcome. Not the personal data values.

8 Common mistakes

- Logging full request bodies with emails and phone numbers into Application Insights. Shows up when an audit finds PII in logs. Fix: scrub or mask at logging time.
- Soft delete (IsDeleted flag) treated as erasure. The data is still there. Fix: hard delete or anonymise after the retention window.
- Forgetting copies in caches, search indexes, analytics exports and test databases. Fix: data map plus one erasure workflow covering all.
- Geo-redundant storage replicating to a region outside the allowed zone. Fix: check the paired region before choosing the redundancy level.
- Production data copied to dev. Fix: masked or synthetic test data.

9 Mental model

Data lifecycle with a compliance gate at each step:

collect (consent, minimum) -> store (region, encryption, classification) -> use (access control, audit log) -> share (processor contracts) -> retain (time limit) -> erase (all copies)

10 Mini lab (30 minutes, local)

Goal: see PII in logs and fix it with masking, plus a simple erasure endpoint.
- Create a minimal API: dotnet new web -n PrivacyLab, then cd PrivacyLab.
- Add an in-memory list of users (Id, Name, Email) and a POST /users endpoint that logs the new user with the Email using ILogger.
- Run it, POST one user, and note the email visible in the console log. That is the problem.
- Change the log line to log only the user Id and a masked email (first character plus domain). Run again and confirm the console no longer shows the full email.
- Add DELETE /users/{id} that removes the user and writes one audit log line with action, Id and UTC time, but no name or email.
- Call DELETE and confirm the user is gone from GET /users and the audit line appears.
- Expected result: logs contain no full personal data, and erasure plus audit both work.
- Clean-up: stop the app and delete the PrivacyLab folder.

11 Revision summary

- Personal data includes indirect identifiers like IP and device ID.
- GDPR roles: data subject, controller, processor. DPDP roles: data principal, data fiduciary (verify).
- Data residency is enforced with region choice plus Azure Policy Allowed locations.
- Audit logs record who, what, when, outcome, and never the personal data itself.
- Erasure must reach DB, backups, caches, logs, search and analytics.
- Soft delete is not erasure.
- Pseudonymised data is still personal data.
- SOC 2 and ISO 27001 are audit proof for vendors. PCI-DSS covers card data, HIPAA covers US health data.
