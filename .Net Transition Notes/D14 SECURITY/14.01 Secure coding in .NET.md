1 What is it
- 14.01 Secure coding in .NET is the habit of writing ASP.NET Core code so that common attacks (injection, broken access control, weak crypto and others) do not work against it.
- It is organised around the OWASP Top 10, which is a public ranked list of the most common web application security risks (OWASP = Open Worldwide Application Security Project).
- You already do parts of this (parameterized queries, anti-forgery tokens). The goal here is to name each risk, map it to a .NET control and answer interview questions about it.
- Legacy equivalent: validateRequest, AntiForgeryToken in MVC 5, Machine Key based forms auth, and hand-written sanitizers in Web Forms and MVC projects.

2 Why needed
- Most breaches come from a small set of known mistakes, not clever zero-days.
- Without secure coding, one unchecked ID in a URL can expose another customer's data, and one string-built SQL query can expose the whole database.
- Architects are expected to review designs and code for these risks, and to set team standards.

4 Features and core concepts
OWASP Top 10 mapped to .NET (names follow the 2021 list; verify whether a newer edition is current).
- Injection: untrusted input is run as a command (SQL, OS, LDAP). Why it matters: full data theft or server takeover. Fix: parameters, never string concatenation.
- Broken access control: a user does something they should not (read another user's order). Why it matters: the number one risk. Fix: [Authorize] policies plus a server-side ownership check on every resource.
- Cryptographic failures: sensitive data is unprotected or protected with weak algorithms. Fix: TLS everywhere, strong password hashing, no custom crypto.
- Insecure design: the flaw is in the design, not the code. Fix: threat modeling and abuse cases before coding.
- Security misconfiguration: defaults left on, detailed errors shown, open storage. Fix: hardened config per environment, no developer exception page in production.
- Vulnerable components: outdated NuGet or npm packages with known CVEs (CVE = published vulnerability ID). Fix: dotnet list package --vulnerable, Dependabot.
- Authentication failures: weak login, session or token handling. Fix: use Entra ID or ASP.NET Core Identity, lockout, MFA, never roll your own.
- Integrity failures: trusting unsigned updates, packages or serialized data. Fix: signed packages, pinned versions, avoid unsafe deserializers.
- Logging failures: attacks go unnoticed, or logs leak secrets. Fix: log security events, never log passwords, tokens or personal data.
- SSRF (server-side request forgery): your server is tricked into calling an internal URL. Fix: allow-list outbound hosts, block internal IP ranges.

Controls to know in detail
- Parameterized queries: values travel separately from SQL text, so input can never become code. EF Core does this automatically for LINQ. Raw SQL is safe only with FromSql interpolation or explicit parameters.
  - var rows = db.Users.FromSql($"SELECT * FROM Users WHERE Email = {email}");
- Output encoding: convert special characters to safe text when writing into HTML. Razor encodes by default. Danger is Html.Raw and innerHTML. Why: this stops XSS (cross-site scripting, attacker script running in a victim's browser).
- Anti-forgery tokens: a secret per user session that proves a form post came from your own page. This blocks CSRF (cross-site request forgery). Use [ValidateAntiForgeryToken] or AutoValidateAntiforgeryToken for cookie-based apps. Pure bearer-token APIs are not exposed to CSRF in the same way.
- Data Protection API: built-in .NET service that encrypts cookies, anti-forgery tokens and your own small secrets. Key ring must be shared and persisted (blob storage plus Key Vault) when you run several instances, or cookies break after restarts.
- Input validation: check type, length, range and format on the server, using allow-lists. Why: it reduces attack surface, but it is not a replacement for encoding or parameters.
- Deserialization risks: turning untrusted bytes into objects can run attacker code. BinaryFormatter is dangerous and removed in modern .NET. Use System.Text.Json with explicit types. With Newtonsoft, never set TypeNameHandling to anything but None for untrusted data.
- File upload safety: check extension and content type against an allow-list, check size, generate your own file name, store outside the web root or in blob storage, scan for malware. Why: uploads can carry scripts or overwrite files.

5 Core focus (exam and interview)
- Most asked: SQL injection, XSS, CSRF, broken access control (IDOR, insecure direct object reference), and password storage.
- Know the difference: authentication = who you are; authorization = what you may do.
- Know the trap: hiding a button or using a route guard is not security. The server must check every request.
- Password storage: slow salted hash such as PBKDF2, bcrypt or Argon2, never plain SHA or MD5. ASP.NET Core Identity uses PBKDF2 by default.
- Security headers: HSTS, Content-Security-Policy, X-Content-Type-Options. Cookie flags: HttpOnly, Secure, SameSite.
- Defaults: Razor encodes output; EF Core LINQ is parameterized; developer exception page is only on in Development.

6 Real-world use case
- Situation: a customer portal on ASP.NET Core and Azure SQL shows orders at /orders/1042. A tester changes it to 1043 and sees another customer's order.
- Choice: add a resource-based authorization check (does this order belong to the signed-in user?) and use non-guessable GUIDs as public IDs. Add a security test for it in the pipeline.
- Trade-off: extra database lookup per request and more code in handlers, in exchange for closing the top OWASP risk.
- When not to rely on it alone: GUIDs are not security by themselves. Never use obscurity instead of the ownership check.

7 Interview lens
- Q: How do you prevent SQL injection in EF Core?
  A: Use LINQ or FromSql with interpolation so values become parameters. Never concatenate user input into SQL, including in stored procedures that build dynamic SQL.
- Q: What is IDOR and how do you stop it?
  A: A user changes an ID and reaches someone else's data. Check ownership on the server for every resource, using policy or resource-based authorization.
- Q: Does an API using JWT bearer tokens need CSRF protection?
  A: Usually no, because the browser does not attach the token automatically. If the token is stored in a cookie, you do need it.
- Q: Why is BinaryFormatter dangerous?
  A: Deserializing attacker-controlled data can instantiate arbitrary types and run code. Use typed System.Text.Json instead.

8 Common mistakes
- String-built SQL in a "quick" report query: shows up as a data leak. Fix: parameters, and a code review rule.
- Html.Raw on user content: stored XSS in comments or profile fields. Fix: encode, or sanitize with an allow-list library.
- Authorization only on the controller, not on the resource: users read others' data. Fix: ownership checks and tests.
- Verbose errors and stack traces in production: attackers learn your stack. Fix: ProblemDetails with a correlation ID, details only in logs.
- Secrets in appsettings.json in Git: credential leak. Fix: Key Vault and managed identity.
- Logging full request bodies: passwords and personal data land in logs. Fix: redact and log IDs only.
- Never updating packages: known CVEs stay live. Fix: automated dependency scanning in CI.

9 Mental model
- Think of airport security with layers:
  Internet -> TLS and headers -> authentication (who) -> authorization (what, which record) -> validation (is input sane) -> safe sinks (parameters, encoding) -> logging (who did what)
- Every layer assumes the one before it can fail.

10 Mini lab
Time: about 30 minutes. Tools: .NET SDK and SQLite, no Azure needed.
- Create a project: dotnet new web -o SecLab, then add EF Core SQLite package.
- Add a Users table with two rows and an endpoint that builds SQL by string concatenation using a query string value.
- Call it with a normal name, then with ' OR '1'='1 and see all rows returned.
- Replace it with FromSql interpolation and repeat the attack. Expected result: no rows returned for the attack input.
- Add a second endpoint returning HTML with Results.Content and Html.Raw-style concatenation of ?name=<script>alert(1)</script>. Open it in a browser and see the script run. Then HTML-encode with System.Net.WebUtility.HtmlEncode and see it shown as text.
- Run dotnet list package --vulnerable and read the output.
- Clean-up: delete the SecLab folder.

11 Revision summary
- OWASP Top 10 is the checklist: access control, crypto, injection, insecure design, misconfiguration, components, authentication, integrity, logging, SSRF (verify current edition).
- Parameters stop injection; encoding stops XSS; anti-forgery tokens stop CSRF.
- Broken access control is the top risk: check ownership on the server every time.
- Hash passwords with PBKDF2, bcrypt or Argon2, with salt, never fast hashes.
- Data Protection API needs a shared, persisted key ring in multi-instance hosting.
- Never use BinaryFormatter; avoid TypeNameHandling with untrusted JSON.
- Uploads: allow-list type, limit size, rename, store outside web root, scan.
- Never log secrets or personal data; never ship stack traces to users.
