1 What is it
- A software supply chain is everything that goes into your running app: your code, NuGet packages, base images, build tools, pipeline agents and the artifacts you ship.
- DevSecOps means building security checks into every step of the pipeline instead of testing only at the end.
- Supply chain attacks target the parts you did not write: a poisoned package, a tampered image, or a hijacked build agent.
Legacy equivalent: a manual security review before go-live, plus packages.config and DLLs copied from shared drives with nobody tracking versions.

2 Why needed
- Most of your code is other people's code. A typical .NET service pulls in hundreds of transitive packages.
- Without scanning, a known vulnerability in one package reaches production unnoticed.
- Without signing and pinned versions, an attacker can swap a package or image and you cannot detect it.
- Without pipeline hardening, anyone who can edit the pipeline file can steal secrets or ship malicious code.
- Late security testing finds problems when they are most expensive to fix.

4 Features and core concepts
- Dependency scanning
  - Plain meaning: a tool compares your package list against databases of known vulnerabilities.
  - Why: catches known-bad versions before release.
  - Tools: Dependabot, NuGet audit, OWASP Dependency-Check (verify).
  - dotnet list package --vulnerable --include-transitive
- SBOM (software bill of materials)
  - Plain meaning: a machine-readable list of every component inside a build.
  - Why: when a new CVE appears, you can search your SBOMs and know which apps are affected within minutes.
  - Common formats: CycloneDX, SPDX.
- Signed artifacts and images
  - Plain meaning: a cryptographic signature proves who built the artifact and that it was not changed afterwards.
  - Why: stops tampering between build and deploy.
  - Tools: Sigstore Cosign, Notation (verify). Verify the signature at deploy time, not just at build time.
- Pinned versions
  - Plain meaning: use exact versions, not floating ranges like 1.*, and lock files with hashes.
  - Why: the same build gives the same result, and a surprise new version cannot slip in.
  - Setting: RestorePackagesWithLockFile and --locked-mode in restore. Pin images by digest, not tag.
- Private feeds
  - Plain meaning: your own package source (Azure Artifacts) that proxies public NuGet.
  - Why: you control what enters the build and can block bad packages.
  - Risk to know: dependency confusion, where a public package with your private package's name wins. Fix with package source mapping and a single trusted feed.
- Pipeline hardening
  - Plain meaning: lock down who can change and run pipelines.
  - Why: the pipeline holds your deployment credentials, so it is a prime target.
  - Practices: protected branches, required reviews on pipeline YAML, least-privilege service connections, OIDC instead of stored secrets, pin third-party actions and tasks to a commit SHA.
- SAST, DAST, IAST
  - SAST: scans source code without running it. Fast, runs on every pull request. Examples: SonarQube, CodeQL.
  - DAST: attacks the running app from outside. Finds runtime and configuration problems. Example: OWASP ZAP.
  - IAST: an agent inside the running app watches tests and reports issues. Less common.
  - Why three: each finds different bugs.
- Container and IaC scanning
  - Plain meaning: scan images for vulnerable OS packages and Terraform or Bicep for insecure settings.
  - Tools: Trivy, Defender for Cloud, Checkov.
  - Why: a public storage account in Terraform is caught before it exists.
- Policy as code
  - Plain meaning: rules written as code that automatically allow or block changes.
  - Why: consistent, auditable enforcement. Examples: Azure Policy, OPA (verify).
- Vulnerability management SLAs
  - Plain meaning: agreed deadlines to fix findings by severity.
  - Why: without deadlines, findings pile up. Example target: critical in days, high in weeks (set by your org, not a standard).
- Secure build agents
  - Plain meaning: build machines that are isolated, patched and short-lived.
  - Why: a shared self-hosted agent can leak secrets or cache poisoned files between builds. Prefer Microsoft-hosted or ephemeral agents.

5 Core focus (exam and interview)
- Asked most: what to scan at which stage, and what each tool type finds.
- Scan early (pull request), gate at merge, verify again at deploy.
- Know the difference: SBOM tells you what is inside, signing tells you who made it, scanning tells you what is wrong with it.
- Transitive dependencies are the usual blind spot.
- Floating tags like latest are a supply chain risk.
- AZ-400 links: Defender for Cloud and GitHub Advanced Security features, Azure Artifacts upstream sources (verify current names).
- Gates should fail on severity thresholds, not on every finding, or teams will bypass them.

6 Real-world use case
- Situation: you lead a .NET 8 API on AKS, built in Azure DevOps. A new critical CVE is announced in a JSON library.
- Choice made: the pipeline already generates a CycloneDX SBOM per build and stores it with the artifact. You search the SBOMs and find three affected services in minutes. Dependabot raises pull requests. Images are signed, and an admission policy only allows signed images.
- Trade-off: scans add build time and false positives. Signing and policy add setup and key management work. Developers get blocked by gates and need a clear exception process.
- When NOT to use full controls: a throwaway prototype or internal lab needs only basic dependency scanning. Do not add signing, admission policy and SLAs to a weekend experiment.

7 Interview lens
- Q: What is an SBOM and why do you want one?
  A: A list of all components in a build. When a new CVE lands, you can find affected apps quickly.
- Q: How do you stop dependency confusion?
  A: Use one private feed with upstream proxying and package source mapping. Reserve your internal package names.
- Q: SAST versus DAST?
  A: SAST reads code early and cheaply. DAST attacks the running app and finds runtime and config issues. Use both.
- Q: How do you harden a pipeline?
  A: Protected branches, reviewed YAML, OIDC not stored secrets, least-privilege connections, pinned actions, ephemeral agents.

8 Common mistakes
- Scanning only direct packages. Production shows a vulnerable transitive dependency. Fix: include transitive scanning.
- Using latest or floating versions. A build breaks or changes unexpectedly. Fix: pin versions and image digests.
- Signing at build but never verifying at deploy. Signing gives no protection. Fix: enforce verification at the cluster or release gate.
- Failing the build on every low finding. Teams disable the gate. Fix: threshold by severity and track the rest.
- Secrets in pipeline variables with wide access. A leak exposes production. Fix: Key Vault, OIDC, scoped connections.
- Unpinned third-party pipeline tasks. A compromised task runs with your secrets. Fix: pin to a commit SHA.

9 Mental model
- Think of a food factory:
  - Ingredients arrive (packages, base images) -> inspect and log them (scan, SBOM)
  - Kitchen (build agent) -> clean, locked, only authorized staff (hardening)
  - Sealed package (signing) -> tamper-evident label
  - Shop door (deploy gate) -> checks the seal before it goes on the shelf

10 Mini lab
Time: about 30 minutes. Local tools plus a free GitHub account. Needs the .NET SDK and Docker.
- Step 1: create a console app with dotnet new console -n SupplyLab and cd into it.
- Step 2: add an old package: dotnet add package Newtonsoft.Json --version 12.0.3 (an old version with a known issue).
- Step 3: run dotnet list package --vulnerable --include-transitive. Expected result: a vulnerability warning for that package.
- Step 4: install Trivy and run trivy fs . . Expected result: a findings table listing the same package.
- Step 5: install the CycloneDX tool (dotnet tool install --global CycloneDX) and run dotnet CycloneDX SupplyLab.csproj. Expected result: a bom file listing all components.
- Step 6: update the package to the latest version and rerun steps 3 and 4. Expected result: the warning disappears.
- Step 7 (optional): build a small image and scan it with trivy image. Expected result: a list of OS package findings.
- Clean-up: delete the SupplyLab folder and remove any local images with docker rmi.

11 Revision summary
- Supply chain means everything you did not write that ends up in production.
- Scan direct and transitive dependencies; scan early and again at deploy.
- SBOM = what is inside; signature = who built it; scan = what is wrong.
- Pin versions, lock files and image digests; never rely on latest.
- Use a private feed and package source mapping against dependency confusion.
- SAST reads code, DAST attacks the running app, IAST watches from inside.
- Harden pipelines: OIDC, least privilege, protected branches, pinned tasks, ephemeral agents.
- Set fix deadlines by severity and gate on thresholds, not every finding.
