1 What is it
- Cloud security is protecting your Azure workloads, data and identities using layered controls: shared responsibility, Defender for Cloud, network controls, identity controls, data protection and logging.
- Think of a bank: the building (Microsoft) is secured by the landlord, but locks on your own vault, who holds keys, and the camera footage are your job.
- Legacy equivalent: on-premises hardening of IIS and SQL Server boxes, domain firewall rules, Active Directory groups and Windows Event Logs.

2 Why needed
- Cloud resources are reachable over the internet by default. One public storage account or an over-permissioned identity can expose everything.
- Without these controls: public databases, stolen credentials with no second factor, unencrypted data with no key control, and no trail to investigate a breach.
- Audits (PCI-DSS, ISO 27001, DPDP) ask for proof of these controls, not just intent.

4 Features and core concepts
- Shared responsibility: Microsoft secures physical, host and the platform. You secure identity, data, configuration and (for IaaS) the OS. It matters because most breaches come from the customer side. The split shifts by service type: IaaS gives you most duties, PaaS fewer, SaaS fewest.
- Defender for Cloud: a service that scores your security posture (CSPM) and detects threats (CWPP, through Defender plans per resource type). It matters because it gives a prioritized fix list and alerts. The free tier gives posture recommendations. Paid plans add threat protection (verify).
- Microsoft cloud security benchmark: Microsoft's set of security controls and best practices, the default policy initiative in Defender for Cloud. It matters because it is the checklist behind your secure score.
- Network security, private endpoints: gives a PaaS service (SQL, Storage, Key Vault) a private IP inside your VNet, so traffic stays off the public internet. Pair with disabling public network access.
- Network security, NSG: stateful allow/deny rules at subnet or NIC level. Default is deny inbound from the internet except what you allow.
- Network security, WAF: Layer 7 firewall on Application Gateway or Front Door that blocks OWASP-type attacks (SQL injection, XSS).
- Network security, DDoS: DDoS protection tier adds adaptive tuning and cost protection beyond the basic always-on infrastructure protection (verify tiers).
- Identity security, Conditional Access: policies of the form "if user, app, location, device and risk match, then require MFA, compliant device or block". It matters because passwords alone get phished.
- Identity security, PIM: Privileged Identity Management gives just-in-time, time-boxed, approved admin roles instead of permanent ones. It reduces standing privilege.
- Data security, customer-managed keys (CMK): you hold the encryption key in Key Vault instead of Microsoft-managed keys. It matters for compliance and revocation control.
- Data security, TDE: Transparent Data Encryption encrypts SQL database files at rest. It is on by default in Azure SQL.
- Data security, purge protection: stops a deleted Key Vault or key from being permanently purged during the retention period. It is required for CMK scenarios.
- Security logging, Activity log: control-plane record of who did what to which resource (create, delete, role change). Retained about 90 days by default, so export it to Log Analytics for longer (verify).
- Security logging, Sentinel awareness: Microsoft's cloud SIEM that collects logs from many sources and runs analytics rules to raise incidents. Know what it is, not how to operate it.
- Incident response basics: detect, contain, eradicate, recover, learn. Containment in Azure usually means isolating a VM with an NSG, revoking sessions or tokens, and rotating keys.
- Command worth memorizing:
  az keyvault update --name kv1 --enable-purge-protection true

5 Core focus (exam and interview)
- Most asked: who is responsible for what in IaaS vs PaaS vs SaaS.
- Private endpoint vs service endpoint: private endpoint gives a private IP for one resource. Service endpoint extends VNet identity to a public endpoint of the service.
- Defender for Cloud: secure score, recommendations, regulatory compliance dashboard, and the difference between free CSPM and paid plans (verify).
- Conditional Access needs Entra ID P1 or higher. PIM needs P2 or Governance licensing (verify).
- Azure SQL TDE is on by default. CMK requires Key Vault with soft delete and purge protection.
- Activity log is control plane. Resource or diagnostic logs are data plane. You must enable diagnostic settings to send them out.
- Security principle: defense in depth, least privilege, assume breach.

6 Real-world use case
- Situation: a .NET API on App Service stores customer data in Azure SQL, secrets in Key Vault, and is migrating from an on-prem IIS setup.
- Choice made:
  - Managed identity for App Service to reach SQL and Key Vault, so no connection-string passwords.
  - Private endpoints for SQL and Key Vault, public access disabled, App Service uses VNet integration.
  - Front Door with WAF in front of the app.
  - Conditional Access with MFA for all admins and PIM for Owner and Contributor roles.
  - Defender for Cloud plans on App Service, SQL and Key Vault. Activity log and diagnostics sent to Log Analytics.
- Trade-off: more cost (private endpoints, WAF, Defender plans) and more complexity (private DNS zones, harder local debugging).
- When NOT to use: a throwaway dev or demo environment does not need CMK, premium WAF or all Defender plans. Use baseline controls and low cost.

7 Interview lens
- Q: What is shared responsibility in Azure?
  A: Microsoft owns the physical, host and platform layers. You own identity, data, access and configuration, plus the OS in IaaS.
- Q: Private endpoint vs service endpoint?
  A: A private endpoint puts a private IP for the resource in your VNet and allows disabling public access. A service endpoint keeps the public IP but restricts access to your subnet.
- Q: How do you reduce admin account risk?
  A: Use MFA through Conditional Access, PIM for just-in-time roles, and separate break-glass accounts. Review access regularly.
- Q: How would you investigate a suspicious change in a subscription?
  A: Query the Activity log in Log Analytics for who and when, check Defender for Cloud alerts, and review role assignments. Then contain by revoking access or isolating the resource.

8 Common mistakes
- Storage or SQL left with public network access on: shows up as data exposure. Fix: private endpoints plus disabled public access, enforced with Azure Policy.
- Permanent Owner roles for many users: shows up as large blast radius after one phish. Fix: PIM and least privilege.
- Secrets in app settings or code: shows up as leaked credentials in repos. Fix: managed identity and Key Vault.
- CMK without purge protection: shows up as irrecoverable data after key deletion. Fix: enable soft delete and purge protection.
- Logs not exported: shows up as no evidence after 90 days. Fix: diagnostic settings to Log Analytics or storage.
- Ignoring secure score recommendations: shows up as audit failures. Fix: triage by severity monthly.

9 Mental model
- Castle with layers:

  Identity (who) -> Network (where from) -> App/WAF (what request) -> Data (encrypted, keys yours) -> Logs (what happened)
  Defender for Cloud watches all layers. Microsoft owns the ground under the castle.

10 Mini lab
- Time: about 30 minutes, Azure free tier. Local tool: Azure CLI or portal.
- Steps:
  - 1. Create a resource group rg-sec-lab and a storage account with a unique name.
  - 2. In the storage account Networking blade, set public network access to Disabled. Try to browse blobs from the portal.
  - 3. Open Defender for Cloud, then Recommendations. Note the secure score and one storage-related recommendation.
  - 4. Create a Key Vault with purge protection enabled. Confirm in Properties.
  - 5. Open Monitor, then Activity log, and filter by your resource group. Find the create events.
- Expected result: the storage access is blocked from the public internet, Defender shows recommendations, and the Activity log shows your own create operations.
- Clean-up: az group delete --name rg-sec-lab --yes (and purge the vault if soft-deleted).
