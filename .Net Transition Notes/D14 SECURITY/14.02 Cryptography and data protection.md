1 What is it

- Cryptography is the set of techniques that keep data secret, unchanged and provably from the right sender. Data protection is the practice of applying those techniques to stored data, data on the move and personal data.
- Three families do the work. Encryption hides data (only someone with the key can read it). Hashing makes a fixed-size fingerprint of data (cannot be reversed). Signing proves who produced data and that it was not altered.
- Legacy equivalent: Membership provider password hashing, machineKey in Web.config, encrypted connection strings with aspnet_regiis, and IIS server certificates.

2 Why needed

- Databases and backups get stolen. Without encryption and proper password hashing, one leak exposes every user.
- Traffic crosses networks you do not control. Without TLS, anyone on the path can read or change it.
- Tokens and cookies must not be forgeable. Without signing, a user can edit their own role claim.
- Privacy laws expect personal data to be protected and minimised.

3 Before you read

- A key is a secret value (or a key pair) that controls encryption or signing.
- A byte array is how crypto sees data. Text is converted to bytes first.
- A certificate is a public key with an identity attached, signed by an authority.
- JWT and OAuth basics from topic 3.03.

4 Features and core concepts

- Symmetric encryption: one shared key encrypts and decrypts. It is fast, so it is used for bulk data. The risk is sharing the key safely. Example: AES-GCM (verify current guidance).
- Asymmetric encryption: a public key encrypts or verifies, a private key decrypts or signs. It is slow, so it protects small things like keys. It solves the key-sharing problem. Examples: RSA, ECDSA.
- Hashing: a one-way function giving a fixed fingerprint. Used to check integrity and to store passwords. Why it matters: you can compare without ever holding the original. Example: SHA-256.
- Encryption vs hashing vs signing: encryption is reversible with a key. Hashing is not reversible. Signing is a hash of the data encrypted with a private key, so anyone can verify it with the public key. Choose by question: hide it, check it, or prove it.
- Password hashing (PBKDF2, Argon2, bcrypt): deliberately slow, salted hashes. Slowness makes guessing expensive. Plain SHA-256 is too fast for passwords. ASP.NET Core Identity uses PBKDF2 by default (verify iteration count).
- Salts: random value added per password before hashing. Why it matters: identical passwords give different hashes, and precomputed rainbow tables fail. A pepper is a separate secret kept outside the database.
- TLS versions, certificates and chains: TLS 1.2 and 1.3 are the acceptable versions, older ones are disabled (verify). A server certificate is trusted through a chain: leaf, intermediate, root. A missing intermediate causes "works in browser, fails in code" errors.
- mTLS: both sides present certificates. The server also verifies the client. Used for service-to-service trust and strict B2B APIs.
- Key management and rotation: keys have a life cycle: generate, store, use, rotate, retire. Rotation limits damage from a leaked key. Store keys in Azure Key Vault, never in code or config files.
- Envelope encryption: a data key encrypts the data, and a master key in Key Vault encrypts the data key. Why it matters: rotating the master key only re-wraps small data keys, not terabytes. This is how Azure Storage, TDE and customer-managed keys work.
- Encryption at rest, in transit, in use: at rest is on disk (TDE, Storage encryption). In transit is TLS. In use is data while processed (confidential computing, Always Encrypted awareness).
- Certificate lifecycle: issue, deploy, monitor expiry, renew, revoke. Why it matters: expired certificates are a top cause of outages. Automate renewal (Key Vault, App Service managed certificates, Let's Encrypt).
- Personal data handling: collect the minimum, protect it, limit who sees it, delete on schedule.
- Tokenization: replace a sensitive value (card number) with a random token. The real value lives in a separate vault. It reduces how many systems hold sensitive data.
- Masking: show only part of a value (XXXX-1234), in logs, UI and non-production copies. It limits exposure to people and tools that do not need the full value.
- Worth memorizing in .NET (verify API names): Rfc2898DeriveBytes.Pbkdf2 for hashing, AesGcm class for encryption, CryptographicOperations.FixedTimeEquals for safe comparison, RandomNumberGenerator for random bytes.

5 Core focus (exam and interview)

- Asked most: hashing vs encryption vs signing, and why passwords are hashed with a salt and a slow algorithm.
- Asked most: symmetric vs asymmetric, and how TLS uses both (asymmetric to agree a key, symmetric for the data).
- Asked most: envelope encryption and why Key Vault holds the master key.
- Remember: never invent your own cryptography. Use platform libraries.
- Remember: use a cryptographic random generator for keys and salts, not Random.
- Remember: compare hashes and MACs in constant time.
- Remember: Azure Key Vault soft delete and purge protection protect against key loss (verify defaults).
- Remember: Azure Storage and Azure SQL encrypt at rest by default with Microsoft-managed keys (verify). Customer-managed keys are optional.

6 Real-world use case

- Situation: a customer portal stores user passwords as MD5 from an old Membership setup and keeps card numbers in a SQL column. The client wants a security review pass.
- Choice: move password hashes to PBKDF2 or Argon2 with per-user salt, upgrading each hash at next login. Move card handling to a payment provider and store only tokens. Enable TDE and TLS 1.2 or higher. Keep keys in Key Vault with managed identity access and a rotation schedule.
- Trade-off: slow hashing adds CPU cost per login. Key Vault adds a network dependency and latency, so cache keys in memory briefly.
- When NOT to use: do not use field-level encryption or Always Encrypted on columns you must search, sort or join on without checking its query limits. Do not use mTLS everywhere if a simpler managed identity and private endpoint meet the need.

7 Interview lens

- Q: Why not store passwords with SHA-256? A: It is fast, so attackers test billions of guesses per second. Use a slow, salted, purpose-built algorithm such as PBKDF2, Argon2 or bcrypt.
- Q: What is the difference between encryption and signing? A: Encryption hides content and needs a key to read it. Signing proves origin and integrity and anyone with the public key can verify.
- Q: What is envelope encryption? A: A data key encrypts the data and a master key in Key Vault encrypts the data key. You rotate the master key without re-encrypting all data.
- Q: How does a TLS handshake use both key types? A: Asymmetric crypto and certificates authenticate the server and agree a shared secret. Then fast symmetric encryption protects the traffic.

8 Common mistakes

- Hardcoded keys or connection strings in source control. They leak through repositories and build logs. Fix: Key Vault, managed identity, secret scanning.
- Fast hash (MD5, SHA-1, plain SHA-256) for passwords. A database leak is cracked quickly. Fix: PBKDF2, Argon2 or bcrypt with per-user salt.
- Reusing an AES nonce or IV with the same key. This can break confidentiality. Fix: generate a fresh random nonce per message and use AES-GCM.
- Ignoring certificate expiry. The site or API call fails suddenly at midnight. Fix: expiry alerts and automated renewal.
- Turning off certificate validation to "make it work". This removes protection against interception. Fix: install the correct chain instead.
- Logging full personal data or tokens. Logs spread to many people and tools. Fix: mask or omit sensitive fields.

9 Mental model

- Think of a safe deposit system.
- Hashing is a fingerprint: you can match it, never rebuild the person.
- Encryption is a locked box: the key opens it.
- Signing is a wax seal: anyone can check it, only the owner can make it.
- Envelope encryption: a small key in a bank vault opens the box that holds the keys to the big boxes.

  Data --(data key)--> ciphertext
  Data key --(master key in Key Vault)--> wrapped data key

10 Mini lab

Time: about 30 minutes. Tools: .NET SDK, a console project, no Azure needed.

- Step 1: create a console app with dotnet new console -n CryptoLab.
- Step 2: hash the string "Password1" with SHA-256 twice. Print both. Confirm the output is identical.
- Step 3: hash the same password with Rfc2898DeriveBytes.Pbkdf2 using two different random 16-byte salts from RandomNumberGenerator. Print both. Confirm the outputs differ.
- Step 4: time one SHA-256 hash and one PBKDF2 hash with 100000 or more iterations using Stopwatch. Note how much slower PBKDF2 is.
- Step 5: encrypt a short text with AesGcm using a random 32-byte key and a random 12-byte nonce. Decrypt it and confirm the original text.
- Step 6: change one byte of the ciphertext and decrypt again. Confirm it throws an error (integrity check works).
- Expected result: identical SHA-256 outputs, different salted PBKDF2 outputs, PBKDF2 clearly slower, tampered ciphertext rejected.
- Clean-up: delete the CryptoLab folder. No cloud resources were created.

11 Revision summary

- Hash is one-way, encryption is two-way with a key, signing proves origin and integrity.
- Passwords need slow salted hashing: PBKDF2, Argon2 or bcrypt.
- Salt is unique per password and stored with the hash. Pepper is secret and stored elsewhere.
- Symmetric is fast for data, asymmetric is for key exchange and signatures. TLS uses both.
- Envelope encryption: data key wrapped by a Key Vault master key.
- TLS 1.2 or higher only (verify). Certificates are trusted through a chain.
- Rotate keys and renew certificates automatically. Keys live in Key Vault, never in code.
- Tokenize or mask sensitive personal data. Never invent your own crypto.
