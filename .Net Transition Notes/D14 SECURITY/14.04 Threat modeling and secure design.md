14.04 Threat modeling and secure design [P3 R L] — FULL note, new topic (no K tag), mini lab included.

---

1 What is it

- Threat modeling is a structured way to ask, before you build: what are we building, what can go wrong, what will we do about it.
- You draw the system, mark where data moves and where trust changes, then list the ways an attacker could abuse each part.
- Secure design means the fixes are built into the architecture, not patched on later.
- Legacy equivalent: the security checklist or pen test done just before go-live on a .NET Framework MVC app, except this happens at design time.

2 Why needed

- Many serious flaws are design flaws (missing authorization step, trusting a client, one shared secret). Code scanners cannot find a missing control.
- Fixing a flaw at design time costs a whiteboard edit. Fixing it after release costs a hotfix, an incident and sometimes a breach report.
- Without it, security becomes a last-week checklist and the real risks are found by attackers.
- For an architect, it is also the evidence that you considered risk before choosing a design.

3 Before you read

- Data flow: where data enters, moves, is stored and leaves.
- Authentication (who are you) vs authorization (what may you do).
- Basic web attack types: injection, tampering, replay.
- Attack surface: every place an outsider can send input or reach the system.

4 Features and core concepts

- STRIDE: six threat categories. Spoofing (pretending to be someone), Tampering (changing data), Repudiation (denying an action), Information disclosure (leaks), Denial of service (making it unavailable), Elevation of privilege (gaining rights you should not have). It matters because it is a checklist that stops you missing whole categories. Each maps to a control: authentication, integrity checks, audit logs, encryption, rate limits, authorization.
- Data flow diagrams (DFD): a simple picture with four shapes: external entity, process, data store, data flow. It matters because you can only find threats in something you have drawn. Draw it at the level of services and stores, not classes.
- Trust boundaries: lines on the diagram where the level of trust changes (internet to API, API to database, your service to a third party). It matters because most threats happen when data crosses one. Rule: validate and authorize at every crossing.
- Attack surface: the sum of entry points (endpoints, queues, file uploads, admin pages, build pipeline). It matters because every entry point you remove is a risk you never have to defend. Reduce it before hardening it.
- Abuse cases: a use case written from the attacker's view. Example: "as a malicious user I change the order ID in the URL to see another customer's order". It matters because normal requirements never list what must not happen.
- Security requirements: testable statements derived from threats. Example: "every order read must check the caller owns the order". It matters because a threat with no requirement never gets built or tested.
- Defense in depth: several independent layers so one failure is not fatal (WAF, authentication, authorization, input validation, least-privilege database account, encryption, monitoring). It matters because every single control will fail someday.
- Zero trust principles: verify explicitly (check identity, device and context every time), use least privilege (minimum rights, minimum time), assume breach (design so one compromised part cannot reach everything). It matters because the old idea "inside the network is safe" fails once you are in the cloud.
- Secure SDLC: security activities in each phase: requirements (security requirements), design (threat model), build (secure coding, scanning), test (security tests), release (gates), operate (monitoring, incident response). It matters because one late test cannot cover it.
- Design review checklist: a short list used in design reviews. Typical items: authentication method, authorization model, data classification, secrets handling, encryption, logging without personal data, failure behaviour, third-party trust, rate limiting, audit trail. It matters because it makes reviews repeatable across teams.

Worth memorizing: the four questions (Shostack): What are we working on? What can go wrong? What are we going to do about it? Did we do a good job?

5 Core focus (exam and interview)

- Most asked: name the six STRIDE letters and give a control for each.
- Most asked: what is a trust boundary and why do you place checks there.
- Most asked: difference between a threat, a vulnerability and a risk. Threat: possible bad event. Vulnerability: weakness that allows it. Risk: likelihood times impact.
- Most asked: three zero trust principles (above).
- Responses to a threat: mitigate, eliminate, transfer, accept. Accepting needs a named owner and a record.
- When to do it: at design time, and again when the design changes (new integration, new data type, new boundary).
- Exam link: Microsoft documents STRIDE and the Security Development Lifecycle; check the current page on Microsoft Learn (verify). Microsoft Threat Modeling Tool is a free diagramming tool for DFDs (verify current status).

6 Real-world use case

- Situation: a Kolkata client wants an order-tracking API (ASP.NET Core) with an Angular front end, Azure SQL, Service Bus and a payment gateway.
- Draw the DFD: browser, API, database, queue, payment provider. Boundaries: internet to API, API to payment provider, API to database.
- Findings: Spoofing, so use Entra ID sign-in with token validation. Tampering with order IDs, so check ownership on every read (broken object-level authorization). Information disclosure, so private endpoint for the database and no personal data in logs. Denial of service, so rate limiting at API Management or Front Door. Elevation of privilege, so the API's managed identity gets only the rights it needs.
- Trade-off: each control adds build time and some latency. You rank threats by risk and fix the high ones first, and record accepted ones in an ADR.
- When NOT to do a full model: a throwaway prototype, or a tiny change inside an already-modeled boundary. Use a 15-minute checklist review instead.

7 Interview lens

- Q: How do you run a threat model? A: Draw a DFD with trust boundaries, walk each element with STRIDE, rank threats by risk, write requirements and owners, then review on every design change.
- Q: What is the difference between a threat and a vulnerability? A: A threat is a possible harmful event, such as someone reading another user's order. A vulnerability is the weakness that makes it possible, such as a missing ownership check.
- Q: What does assume breach mean in design? A: Design as if an attacker is already inside one component. Use least-privilege identities, network segmentation, short-lived credentials and good logging so the damage stays small and visible.
- Q: When do you threat model in an agile team? A: At the design of each significant feature or change, in a short session of 60 to 90 minutes. Keep the model in the repository and update it, not as a one-time document.

8 Common mistakes

- Doing it once at the end. It shows up as a late finding that forces a redesign. Fix: do it at design time and on every boundary change.
- Diagram too detailed or too vague. It shows up as a session that never finishes or finds nothing. Fix: service and data store level, with trust boundaries marked.
- Listing threats with no owner or requirement. It shows up as the same issue found again in the next pen test. Fix: every threat gets an action, an owner and a status.
- Trusting the internal network. It shows up as lateral movement after one compromised service. Fix: authenticate and authorize service-to-service calls.
- Treating the model as a security team task only. It shows up as threats that miss real business logic. Fix: developers, architect and a tester are in the room.

9 Mental model

Think of a building plan reviewed by a burglar.

  [Internet] ==boundary==> [API] ==boundary==> [Database]
                             |
                         ==boundary==> [Payment provider]

At every double line ask STRIDE: who is this, was it changed, can they deny it, does it leak, can it be flooded, can it gain more rights.

10 Mini lab (30 to 40 minutes, no cost)

- Step 1: open the free tool draw.io in a browser, or use pen and paper. (If you prefer the Microsoft Threat Modeling Tool, it runs on Windows only (verify).)
- Step 2: draw a DFD of a small system you know: Angular app, ASP.NET Core API, SQL Server, a queue, an external payment API. Use four shapes only.
- Step 3: draw dashed trust boundaries: internet to API, API to payment provider, API to database.
- Step 4: for each flow that crosses a boundary, write one threat per STRIDE letter where it applies. Aim for 12 to 15 threats.
- Step 5: mark each threat High, Medium or Low (likelihood times impact).
- Step 6: for the top five, write one security requirement each, in testable form.
- Expected result: one diagram, a table of about 12 threats, and 5 requirements you can paste into a design document.
- Clean-up: save the diagram into your capstone repository folder (docs/threat-model) and delete any temporary files.

11 Revision summary

- Four questions: what are we building, what can go wrong, what will we do, did we do well.
- STRIDE: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
- Trust boundary: where trust level changes; check input and identity there.
- Risk: likelihood times impact; responses are mitigate, eliminate, transfer, accept.
- Defense in depth: several independent layers, never one control.
- Zero trust: verify explicitly, least privilege, assume breach.
- Do it at design time and redo it when the design changes.
- Abuse case: a use case from the attacker's view that becomes a security requirement.
