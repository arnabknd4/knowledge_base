1 What is it

- Secrets are credentials your app needs: connection strings, API keys, certificates, client secrets, tokens. Least privilege means every person, app and pipeline gets only the access it needs, only for as long as it needs it.
- Secret sprawl is when secrets end up scattered across appsettings files, web.config, pipeline variables, wikis, chat messages and laptops, with no owner and no rotation.
- Managed identity is an Azure-issued identity for a resource (an App Service, a VM, an AKS pod) so the app can log in to other Azure services without any stored password.
- Legacy equivalent: connection strings with passwords in web.config, transformed per environment, with an admin SQL login shared by every app and everyone knowing the password.

2 Why needed

- A leaked secret is a direct way into your data. Secrets in Git history stay there even after you delete the file.
- Shared admin credentials mean one compromised app exposes everything.
- Without rotation, a secret stolen two years ago still works today.
- Without least privilege, a bug or a stolen token does far more damage than it should.

3 Before you read

- Azure RBAC: a role (what actions are allowed) is assigned to an identity at a scope (subscription, resource group, resource).
- Microsoft Entra ID: the Azure identity service that holds users, groups, service principals and managed identities.
- Service principal: an app's identity in Entra ID, usually with a client secret or certificate.
- Key Vault: the Azure service that stores secrets, keys and certificates.

4 Features and core concepts

- Secret sprawl: the same secret copied to many places. Matters because you cannot rotate or revoke what you cannot find.
- Key Vault patterns: store secrets once in Key Vault, give each app its own vault or its own access, and read secrets at runtime. Matters because there is one place to audit, rotate and revoke. Common patterns: one vault per app per environment, App Service Key Vault references, and the Key Vault configuration provider in ASP.NET Core.
- Managed identities: system-assigned lives and dies with one resource; user-assigned is a separate resource you can attach to many. Matters because the app has no password to leak. Use DefaultAzureCredential in .NET code.
- Workload identity: lets a Kubernetes pod or a pipeline (GitHub Actions, Azure DevOps) get an Azure token by federation with its own trusted token (OIDC), with no client secret stored. Matters because there is nothing to rotate or leak.
- Least-privilege RBAC: assign the narrowest built-in role at the narrowest scope. Example: Key Vault Secrets User on one vault, not Contributor on the subscription. Matters because blast radius stays small.
- Just-in-time access: privileged roles are not permanent. You activate them for a limited time, with approval and a reason (Entra PIM). Matters because standing admin rights are a standing target.
- Rotation: replace secrets on a schedule and after any suspected leak. Prefer short-lived secrets or two overlapping secrets so rotation causes no downtime. Matters because it limits how long a stolen secret is useful.
- Secret scanning: tools that scan commits and repos for leaked credentials (GitHub secret scanning and push protection, gitleaks). Matters because developers will commit secrets by mistake.
- Break-glass accounts: emergency admin accounts excluded from normal Conditional Access, with very long passwords kept offline and with alerts on every sign-in. Matters because a mistake in access policy can lock everyone out.
- Service principal hygiene: one principal per app and environment, owners assigned, prefer certificates over secrets, short expiry, delete unused ones, review regularly. Matters because forgotten principals with old secrets are a classic breach path.
- Worth memorizing: new DefaultAzureCredential() in code, and az role assignment create --assignee <id> --role "Key Vault Secrets User" --scope <vault-id>

5 Core focus (exam and interview)

- Most asked: how to remove passwords from an app. Answer: managed identity plus RBAC, secrets in Key Vault only when a password truly cannot be avoided.
- System-assigned vs user-assigned: system-assigned is tied to one resource lifecycle; user-assigned is reusable and survives resource deletion.
- Key Vault permission models: Azure RBAC is the current recommended model; access policies are the older model (verify).
- Soft delete and purge protection protect against accidental or malicious deletion of vault items.
- Managed identity does the authentication; RBAC does the authorization. Both are needed.
- Entra PIM gives time-limited, approval-based role activation (needs a suitable licence, verify).
- Limits and defaults change, so check Microsoft Learn for current Key Vault limits and soft-delete retention (verify).

6 Real-world use case

- Situation: an Infosys-style client has a .NET Web API on App Service, and the SQL password sits in pipeline variables and appsettings.
- Choice: turn on a system-assigned managed identity for the App Service. Use Entra authentication to Azure SQL for that identity. Store the remaining third-party API key in Key Vault, referenced from App Service settings. The pipeline logs in to Azure with workload identity federation. Developers get Reader on production and use PIM for anything higher.
- Trade-off: more setup, more RBAC assignments to manage, and local development needs a different way to sign in (developer credentials through Azure CLI or Visual Studio).
- When NOT to use it: a small internal prototype with no sensitive data, or a third-party service that only accepts API keys (then use Key Vault, not managed identity). Also if the app runs outside Azure and cannot get a federated token, a certificate-based service principal may be the practical choice.

7 Interview lens

- Q: Why prefer managed identity over a client secret?
  A: There is no credential to store, leak or rotate. Azure issues and renews the token for the resource.
- Q: Key Vault holds the secret, but how does the app prove who it is to Key Vault?
  A: With its managed identity, which has a Key Vault role assignment. This avoids the "secret zero" problem of needing a secret to fetch secrets.
- Q: How do you let a CI pipeline deploy to Azure without a stored secret?
  A: Create a federated credential on an Entra app or user-assigned identity that trusts the pipeline's OIDC token. The pipeline exchanges it for an Azure token.
- Q: What is a break-glass account and how do you protect it?
  A: An emergency admin account for lockouts. Keep it cloud-only, exclude it from normal Conditional Access, store credentials offline and alert on any use.

8 Common mistakes

- Secrets committed to Git: they appear in history and forks. Fix: revoke and rotate first, then clean up, and turn on push protection.
- Contributor or Owner at subscription scope for an app identity: one bug becomes a full compromise. Fix: narrow role and scope.
- One shared Key Vault and one shared identity for every app: no isolation. Fix: separate identities, and vault per app or per environment.
- Secrets that never expire and are never rotated: Fix: short expiry, rotation automation, expiry alerts.
- Secrets printed in logs or build output: Fix: masking, no logging of configuration values.
- Break-glass account locked by the same policy it is meant to bypass, or never tested: Fix: exclude it deliberately, test it, and alert on use.
- Orphaned service principals nobody owns: Fix: assign owners and run access reviews.

9 Mental model

- Think of a hotel key card system, not a master key.

  App (identity) -> proves who it is -> Entra ID -> short-lived token
  Token + RBAC role on one resource -> access to that one thing only
  Secrets, if unavoidable -> Key Vault -> audited, rotated, revocable

10 Mini lab

Time: about 30 minutes. Needs an Azure free account, Azure CLI and the .NET SDK.

- Create a resource group and a Key Vault with RBAC authorization enabled: az group create, then az keyvault create --enable-rbac-authorization.
- Give yourself the Key Vault Secrets Officer role on the vault, then add a secret named DemoSecret.
- Create a small console app that reads DemoSecret using SecretClient with DefaultAzureCredential (packages Azure.Identity and Azure.Security.KeyVault.Secrets). Run it locally. Expected result: it prints the secret, using your Azure CLI sign-in.
- Remove your Secrets Officer role and run again. Expected result: a 403 Forbidden error, proving that RBAC controls access.
- Optional: deploy the app to App Service, enable a system-assigned identity, assign it Key Vault Secrets User, and check it works.
- Clean-up: az group delete --name <your-group> --yes. Remember that the vault is soft-deleted; purge it if you want the name back (verify purge protection settings).

11 Revision summary

- Secret sprawl means unknown copies; fix by storing once and reading at runtime.
- Managed identity removes stored passwords; RBAC decides what the identity may do.
- System-assigned is tied to one resource; user-assigned is reusable.
- Workload identity federation (OIDC) replaces pipeline and pod secrets.
- Least privilege means narrowest role at narrowest scope.
- Just-in-time access (PIM) removes standing admin rights.
- Rotate on a schedule and after any leak; scan repos for secrets.
- Break-glass accounts are for lockouts only, offline credentials, alert on use.
- Service principals need an owner, a short expiry and regular review.
