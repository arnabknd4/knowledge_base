1 What is it

- Dependency injection (DI) means a class does not create the objects it needs. It receives them from outside, usually through its constructor.
- A container (the DI container) is a built-in .NET component that knows how to create objects and hands them out. You register types once at startup, and the container supplies them wherever they are requested.
- A dependency is any object a class needs to do its work, such as a logger, a repository or an HTTP client.
- Legacy equivalent: Unity, Autofac or Ninject in MVC 5 projects, or manual "new" calls and static helpers. In .NET Framework DI was an add-on. In modern .NET it is built into the framework.

2 Why needed

- Without DI, classes call "new" on their own dependencies. They become tightly coupled and cannot be tested without the real database or the real service.
- Object lifetimes become scattered. Nobody decides who disposes a connection or who shares an instance.
- With DI, you swap implementations in one place, such as a fake in tests or a different provider per environment.
- ASP.NET Core itself depends on DI. Controllers, middleware, options and logging all arrive through the container.

3 Before you read

- Interface: a contract listing methods without code. A class implements it.
- Constructor: the method that runs when an object is created.
- Object lifetime: how long an object lives before it is thrown away.
- Program.cs and the WebApplicationBuilder (note 1.02).

4 Features and core concepts

- Lifetimes: how long the container keeps an instance.
  - Singleton: one instance for the whole application. Use for stateless or thread-safe shared services.
  - Scoped: one instance per scope. In a web app, one scope is one HTTP request. DbContext is the classic example.
  - Transient: a new instance every time it is requested. Use for lightweight, stateless services.
  - Why it matters: the wrong lifetime causes shared-state bugs or wasted memory.
- Registration patterns: telling the container what to build. Register an interface with its implementation, or a concrete type alone. Why it matters: this is the single place where wiring decisions live.
  - builder.Services.AddScoped<IOrderService, OrderService>();
- Constructor injection: dependencies are declared as constructor parameters and the container fills them in. Why it matters: dependencies are visible and the class cannot exist half-built.
- Captive dependency: a longer-lived service holds a shorter-lived one. Example: a singleton holding a scoped DbContext. The scoped object is "captured" and lives far too long. Why it matters: stale data and thread-safety bugs that only show under load.
- Scope validation: a development-time check that throws an error when a scoped service is resolved from the root container. It is on by default in the Development environment. Why it matters: it catches captive dependencies early.
- Keyed services (.NET 8 and later): register several implementations of one interface under different keys, then pick by key. Why it matters: replaces custom factory code when you have, for example, two payment providers.
  - builder.Services.AddKeyedScoped<IPay, UpiPay>("upi");
  - public Checkout([FromKeyedServices("upi")] IPay pay) { }
- Factory registration: you give the container a lambda that builds the object. Why it matters: needed when construction depends on runtime values or configuration.
  - builder.Services.AddSingleton<IClock>(sp => new Clock(tz));
- Service locator anti-pattern: a class asks the container directly (IServiceProvider.GetService) instead of declaring dependencies in its constructor. Why it matters: dependencies become hidden, so tests and readers cannot see what the class needs. Allowed only in rare spots such as factories or middleware Invoke.
- Decorating services: wrap an existing implementation with another one that adds behaviour such as caching or logging. The built-in container has no decorator feature. Use the Scrutor library (verify) or a factory registration. Why it matters: adds cross-cutting behaviour without touching the original class.
- Testing with DI: pass fakes or mocks into the constructor in unit tests. In integration tests, replace registrations through WebApplicationFactory. Why it matters: DI is what makes classes testable in isolation.

5 Core focus (exam and interview)

- Most asked: the three lifetimes and which to choose for DbContext (scoped), HttpClient factories, caches and loggers.
- Captive dependency: a singleton must never depend on a scoped service.
- Default container is Microsoft.Extensions.DependencyInjection. It supports constructor injection only, not property injection.
- If a type has several constructors, the container uses the one with the most resolvable parameters. If it is ambiguous, an exception is thrown.
- Registering the same interface twice: the last registration wins when you ask for a single instance. IEnumerable<T> returns all of them.
- The container disposes IDisposable services it created. It does not dispose instances you registered yourself.
- Scope validation is on in Development by default (verify for your target version).

6 Real-world use case

- Situation: an order API sends confirmation emails. In the legacy MVC app, controllers did "new SmtpEmailSender()" directly, so tests sent real emails.
- Choice: define IEmailSender, register SmtpEmailSender as scoped in production, and register a fake in integration tests. Add a decorator that logs failures.
- Trade-off: more interfaces and registration lines, and a small startup cost. Wiring errors surface at runtime instead of compile time.
- When not to use it: tiny console utilities or scripts where a container adds ceremony. Also avoid an interface for every class when there will only ever be one implementation and no test need.
- Move to Autofac or another container only if you need features the built-in one lacks, such as property injection or advanced modules.

7 Interview lens

- Q: Explain singleton, scoped and transient with an example each.
  - A: Singleton is one instance for the app, for example a cache. Scoped is one per request, for example DbContext. Transient is new every time, for example a lightweight validator.
- Q: What is a captive dependency and how do you detect it?
  - A: A longer-lived service holding a shorter-lived one, such as a singleton holding a DbContext. Scope validation in Development throws on it, and code review catches the rest.
- Q: Why is the service locator an anti-pattern?
  - A: It hides what a class needs, which makes tests and refactoring harder. Constructor injection makes dependencies explicit.
- Q: How do you handle two implementations of one interface?
  - A: Use keyed services in .NET 8 and later, or register a factory. Resolve IEnumerable<T> if you need all of them.

8 Common mistakes

- Singleton holding DbContext: shows up as "A second operation was started" errors or stale data under load. Fix: make the consumer scoped, or create a scope with IServiceScopeFactory inside the singleton.
- Registering everything as singleton: shared mutable state causes cross-request data leaks. Fix: default to scoped or transient and use singleton only for stateless or thread-safe types.
- Resolving services in the constructor through IServiceProvider: hidden dependencies and untestable code. Fix: declare each dependency as a constructor parameter.
- Too many constructor parameters (more than five or so): a sign the class does too much. Fix: split the class.
- Forgetting a registration: shows up as an InvalidOperationException at first request. Fix: add a startup test that resolves key services, and keep scope validation on.

9 Mental model

- The container is a restaurant kitchen. You register the recipes at startup. Each request is a table, and the kitchen hands each table what it ordered.
- Lifetime is how long a dish stays on the counter.

  Program.cs registers --> Container builds --> Request scope --> Controller gets its dependencies

  Singleton = lives in the kitchen all day. Scoped = one per table. Transient = made fresh for every order.

10 Mini lab (about 30 minutes, local, free)

- Step 1: run dotnet new web -o DiLab, then cd DiLab.
- Step 2: add a class Counter with a public Guid Id set to Guid.NewGuid() in its constructor.
- Step 3: in Program.cs register three services built on that class: AddSingleton, AddScoped and AddTransient. Use small wrapper types (SingletonCounter, ScopedCounter, TransientCounter) that inherit from Counter. Each gets its own registration.
- Step 4: map GET /ids. Inject all three plus a second TransientCounter parameter. Return their Ids as JSON.
- Step 5: run dotnet run and call /ids three times.
- Expected result: the singleton Id never changes. The scoped Id changes on each request but is the same within one request. The two transient Ids always differ, even within one request.
- Step 6 (captive dependency): register a singleton class that takes ScopedCounter in its constructor and resolve it from an endpoint.
- Expected result: in Development, the app throws "Cannot consume scoped service from singleton". That confirms scope validation works.
- Clean-up: delete the DiLab folder.

11 Revision summary

- Three lifetimes: singleton (app), scoped (request), transient (every request for it).
- DbContext is scoped. A singleton must not depend on a scoped service.
- The built-in container supports constructor injection only. Property injection is not supported.
- Keyed services (.NET 8 and later) pick between implementations of one interface by key.
- The service locator hides dependencies. Prefer constructor injection.
- Decoration needs Scrutor or a manual factory (verify).
- The container disposes what it creates. It does not dispose instances you pass in yourself.
- Tests replace registrations through WebApplicationFactory or pass fakes directly.
