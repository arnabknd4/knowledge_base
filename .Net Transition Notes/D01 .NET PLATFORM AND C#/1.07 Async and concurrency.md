# 1.07 Async and concurrency
1 What is it

- Async and concurrency is how a .NET program does many things at once without freezing threads.
- Async means a thread is released while it waits for I/O (database, HTTP, disk). Concurrency means several operations are in progress at the same time. Parallelism means several operations are executing at the same instant on different cores.
- A Task is an object that represents work that will finish later. The async and await keywords let you write code that looks sequential but does not block a thread while waiting.
- Legacy equivalent: Thread, ThreadPool.QueueUserWorkItem, BackgroundWorker, Begin/End async pairs and blocking calls like .Result in ASP.NET MVC and Web API 2.

2 Why needed

- A web server has a limited pool of threads. Each blocked thread is a thread that cannot serve another request.
- Without async, slow database or HTTP calls hold threads idle. Under load the pool runs dry and requests queue up. This is thread pool starvation.
- Without safe concurrency tools (lock, Interlocked, concurrent collections), shared data gets corrupted by race conditions (two threads change the same value at once and one update is lost).
- Without CancellationToken, work continues after the client has disconnected and wastes resources.

3 Before you read

- Thread: an OS-level worker that runs code one instruction at a time.
- Thread pool: a shared set of ready-made threads that .NET reuses for short work.
- I/O-bound work waits on something outside the CPU. CPU-bound work uses the processor heavily.
- Synchronization context: a mechanism that sends continuations back to a specific thread. ASP.NET Framework had one. ASP.NET Core does not.

4 Features and core concepts

- Task and async/await state machine
  - Plain meaning: the compiler rewrites an async method into a state machine class that remembers where it paused. When the awaited work finishes, it resumes from that point.
  - Why it matters: no thread is blocked during the wait, so the same threads serve many requests.
  - Memorize: public async Task<string> GetAsync() { var s = await client.GetStringAsync(url); return s; }

- Sync-over-async deadlocks
  - Plain meaning: calling .Result or .Wait() on a Task from synchronous code blocks the current thread while the Task waits to resume on that same thread.
  - Why it matters: in classic ASP.NET and UI apps this freezes the request forever. In ASP.NET Core there is no synchronization context, so it usually does not deadlock but still wastes a thread and can starve the pool.
  - Fix: be async all the way up the call chain.

- ConfigureAwait
  - Plain meaning: ConfigureAwait(false) tells await not to return to the original context after finishing.
  - Why it matters: it avoids the deadlock above in library code. In ASP.NET Core application code it is not needed. Library authors still use it.

- CancellationToken
  - Plain meaning: a signal object that says "stop, the caller no longer needs this".
  - Why it matters: it frees resources when a user cancels, times out or disconnects. ASP.NET Core passes HttpContext.RequestAborted into actions that accept a token.
  - Memorize: pass the token to every async call you make (EF Core, HttpClient, Task.Delay).

- ValueTask
  - Plain meaning: a struct alternative to Task that avoids allocating an object when the result is already available.
  - Why it matters: it helps in hot paths such as cache hits. Rules: await it only once, do not await it twice and do not use .Result on an incomplete one. Default to Task unless profiling shows allocation pressure.

- Task.WhenAll
  - Plain meaning: waits for many tasks to finish together.
  - Why it matters: independent calls run concurrently, so total time is the slowest call, not the sum. If one task throws, WhenAll surfaces the first exception when awaited. The others are still in the Task objects.
  - Memorize: await Task.WhenAll(t1, t2, t3);

- Concurrency vs parallelism
  - Plain meaning: concurrency is overlapping waits (async). Parallelism is real simultaneous CPU work (Parallel.For, Task.Run).
  - Why it matters: async helps I/O-bound work. Parallelism helps CPU-bound work. Using Task.Run in a web request for CPU work only moves load to another pool thread and adds no benefit.

- Channels
  - Plain meaning: System.Threading.Channels is an in-memory async queue with producers writing and consumers reading.
  - Why it matters: it gives bounded buffering and backpressure inside one process. Think of it as a modern replacement for BlockingCollection. Used for background work inside BackgroundService.

- SemaphoreSlim
  - Plain meaning: a gate that lets only N callers in at once and supports await (WaitAsync).
  - Why it matters: it limits concurrent calls to a downstream service. It is the async-friendly substitute for lock.

- lock
  - Plain meaning: only one thread may run the protected block at a time.
  - Why it matters: it prevents race conditions. You cannot await inside a lock block. Lock on a private readonly object, never on this or a string. (Newer .NET versions add a dedicated Lock type, verify.)

- Interlocked
  - Plain meaning: atomic operations (Increment, Add, CompareExchange) on a single variable without a lock.
  - Why it matters: lock-free counters are fast and safe. Use it for simple counters and flags only.

- ConcurrentDictionary
  - Plain meaning: a dictionary safe for many threads.
  - Why it matters: individual operations are safe. GetOrAdd with a factory can run the factory more than once, so keep the factory side-effect free or store Lazy values.

- Thread pool starvation
  - Plain meaning: all pool threads are busy or blocked, so new work waits. The pool adds threads slowly (about one or two per second after its minimum).
  - Why it matters: it shows up as latency spikes with low CPU. Causes: sync-over-async, long blocking calls, too many Task.Run. Diagnose with dotnet-counters (ThreadPool Queue Length, ThreadPool Thread Count).

- IAsyncEnumerable
  - Plain meaning: an async stream. You consume it with await foreach and items arrive one by one.
  - Why it matters: it streams large results (database rows, API pages) without loading everything into memory. Pass a token with [EnumeratorCancellation] on the parameter.

5 Core focus (exam and interview)

- Most asked: why async scales a web server, what a deadlock from .Result is, difference between concurrency and parallelism, lock vs SemaphoreSlim, Task vs ValueTask.
- Remember: async void only for event handlers. It cannot be awaited and its exceptions can crash the process.
- Remember: Task.Run is for CPU-bound offloading. Never wrap I/O in Task.Run in a web app.
- Remember: do not await in a lock. Use SemaphoreSlim.WaitAsync instead.
- Remember: Task.WhenAll for independent calls, but cap the degree of parallelism when calling a slow dependency (SemaphoreSlim or Parallel.ForEachAsync with MaxDegreeOfParallelism).
- Remember: fire-and-forget Task without handling exceptions loses errors. Use a queue plus worker or BackgroundService.

6 Real-world use case

- Situation: an order API calls inventory, pricing and customer services one after another, taking about 900 ms. Under load the app slows down at low CPU.
- Choice: make the whole chain async, start the three independent calls together with Task.WhenAll, pass CancellationToken to each call and limit outbound calls to inventory with SemaphoreSlim (say 20 at a time).
- Result: latency drops toward the slowest call and thread pool queue length falls.
- Trade-off: more concurrency means more load on downstream services. Errors from several tasks need careful handling. Debugging async stacks is harder.
- When NOT to use: pure CPU loops (use Parallel or a worker service), code that runs once at startup, or tiny methods where an async wrapper adds overhead without any I/O.

7 Interview lens

- Q: Why is async good for a web API?
  A: It releases the thread during I/O waits, so fewer threads serve more requests. Throughput rises and memory per request falls.

- Q: Why can .Result cause a deadlock?
  A: It blocks the thread that the continuation needs to resume on (classic ASP.NET or UI context). In ASP.NET Core it mostly causes starvation instead.

- Q: lock or SemaphoreSlim?
  A: lock is for short synchronous sections and cannot contain await. SemaphoreSlim supports WaitAsync and can allow N callers.

- Q: How do you find thread pool starvation?
  A: Look for high latency with low CPU, then run dotnet-counters and watch thread pool queue length and thread count. Take a dump or trace to find the blocking calls.

8 Common mistakes

- Calling .Result or .Wait() in a controller. Shows up as random timeouts under load. Fix: await all the way.
- async void methods. Unhandled exceptions crash the process. Fix: return Task.
- Ignoring CancellationToken. Work continues after client disconnect. Fix: accept and pass the token everywhere.
- Task.Run around I/O in ASP.NET. Burns pool threads for no gain. Fix: call the async API directly.
- Awaiting inside a loop when calls are independent. Total time is the sum. Fix: collect tasks and use WhenAll (with a limit).
- Using lock with await inside. Compile error or hidden blocking. Fix: SemaphoreSlim.
- Fire-and-forget without error handling. Silent failures. Fix: BackgroundService or queue plus worker.
- Reading shared fields without synchronization. Intermittent wrong values. Fix: lock, Interlocked or concurrent collections.

9 Mental model

- Think of a restaurant. A thread is a waiter. Blocking is a waiter standing at the kitchen window until the dish is ready. Async is the waiter taking the next table and returning when the bell rings.

  request -> thread starts -> await I/O -> thread freed
  I/O done -> any free thread resumes -> response

10 Mini lab (30 minutes)

- Tools: .NET SDK, dotnet-counters (dotnet tool install -g dotnet-counters), curl or a browser. No Azure needed.
- Steps:
  - Create a project: dotnet new web -n AsyncLab, then cd AsyncLab.
  - In Program.cs add two endpoints. /sync calls Thread.Sleep(2000) then returns "ok". /async does await Task.Delay(2000) then returns "ok".
  - Run: dotnet run. Note the port from the console.
  - In another terminal run: dotnet-counters monitor -n AsyncLab (or by process id) and keep it open.
  - Send 100 parallel requests to /sync. In bash: seq 100 | xargs -P100 -I{} curl -s localhost:PORT/sync > /dev/null. Watch ThreadPool Queue Length and Thread Count.
  - Repeat for /async.
- Expected result: /sync shows a growing queue and threads, with total time well above 2 seconds. /async finishes close to 2 to 3 seconds with a near-empty queue.
- Extra step (5 minutes): add a /all endpoint that runs three Task.Delay(1000) calls with Task.WhenAll. Confirm it returns in about 1 second, not 3.
- Clean-up: stop the app and dotnet-counters with Ctrl+C. Delete the AsyncLab folder.

11 Revision summary

- Async releases the thread during I/O. It does not make one operation faster.
- Never block on a Task (.Result, .Wait). Be async all the way.
- ConfigureAwait(false) is for library code. ASP.NET Core app code does not need it.
- Pass CancellationToken through every async call.
- Task.WhenAll runs independent work together. Limit it for slow dependencies.
- No await inside lock. Use SemaphoreSlim.WaitAsync.
- Interlocked for simple counters. ConcurrentDictionary.GetOrAdd factory may run twice.
- Thread pool starvation: high latency, low CPU. Check dotnet-counters queue length.
