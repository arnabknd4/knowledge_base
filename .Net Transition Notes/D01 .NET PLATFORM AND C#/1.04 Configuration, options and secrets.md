# 1.04 Configuration, options and secrets
1 What is it

- Configuration is how an app gets its settings (connection strings, URLs, keys, toggles) from outside the code.
- ASP.NET Core reads many sources into one key-value set. The options pattern then maps sections of it to typed C# classes.
- Secrets are sensitive settings (passwords, API keys). They must never sit in source control.
- Legacy equivalent: Web.config appSettings, connectionStrings and config transforms (Web.Release.config).

----------------------------------------

2 Why needed

- One build must run in Dev, Test and Prod with only the settings changed.
- Without this, people hard-code values or commit passwords to Git. Changing a setting then means a rebuild and a redeploy.
- Typed options catch a missing or wrong value at startup instead of at 2 AM in production.

4 Features and core concepts

- Sources and precedence: settings come from layers, and a later layer overrides an earlier one. Default order in WebApplication.CreateBuilder (verify): appsettings.json, appsettings.{Environment}.json, user secrets (Development only), environment variables, command line. This is why Prod can override a file value without a rebuild.
- appsettings: JSON files shipped with the app. They hold non-secret defaults.
- Environment variables: set by the host (App Service, container, pipeline). Use a double underscore for nesting, for example ConnectionStrings__Default. This is the standard way to configure containers.
- Command line: highest default priority. Good for quick one-off overrides.
- User secrets: a per-developer file outside the repo, for local development only. It is not encrypted. Command: dotnet user-secrets set "Api:Key" "value"
- Key Vault: the central secret store in Azure. You add it as a configuration source and access it with a managed identity. Secrets then never touch your repo or pipeline variables.
- IOptions<T>: singleton. Read once, no reload. Use it for values that never change at runtime.
- IOptionsSnapshot<T>: scoped. Re-read on each request, so file or source changes show up. Cannot be injected into singletons.
- IOptionsMonitor<T>: singleton with change notifications. Use it inside singletons or background services that need live values.
- Validation on start: check the settings when the app starts and fail fast. Code: services.AddOptions<MyOpts>().BindConfiguration("My").ValidateDataAnnotations().ValidateOnStart();
- Per-environment config: ASPNETCORE_ENVIRONMENT selects the appsettings.{Environment}.json layer.
- Twelve-factor config: store config in the environment, strictly separated from code. Same artifact everywhere.
- Azure App Configuration: a managed service for central, non-secret settings and feature flags, with refresh. Keep secrets in Key Vault and reference them.
- Feature flags (FeatureManagement): switch features on or off without redeploying. Use IFeatureManager or the [FeatureGate] attribute. Flags can live in appsettings or App Configuration.

5 Core focus (exam and interview)

- Most asked: the precedence order and the three options interfaces (lifetime and reload behaviour).
- Snapshot is scoped, Monitor is singleton. Injecting Snapshot into a singleton fails.
- Colon separates keys in JSON paths. Use a double underscore in environment variables.
- User secrets are for Development only and are not encrypted.
- Key Vault access uses managed identity with Azure RBAC or access policies.
- ValidateOnStart is needed for early failure. Plain validation runs lazily, at first use.
- (verify) exact default source order and App Configuration refresh behaviour on Microsoft Learn.

6 Real-world use case

- Situation: a migrated API runs on App Service across Dev, Test and Prod with a SQL connection string and a payment API key.
- Choice: non-secret defaults in appsettings. Environment-specific values in App Service settings. The payment key in Key Vault, read through managed identity. A flag toggles the new checkout. Options classes use ValidateOnStart.
- Trade-off: more moving parts than one Web.config, and Key Vault adds a startup dependency and a small latency.
- When not to use it: do not put secrets in App Configuration or appsettings. Do not use IOptionsSnapshot in a high-throughput singleton path. A tiny internal tool may not need App Configuration.

7 Interview lens

- Q: Order of configuration sources? A: appsettings, then environment appsettings, user secrets (Dev), environment variables, command line. Later wins.
- Q: IOptions vs IOptionsSnapshot vs IOptionsMonitor? A: IOptions is singleton with no reload. Snapshot is scoped and reloads per request. Monitor is singleton and notifies on change.
- Q: How do you keep secrets out of Git? A: User secrets locally, Key Vault in Azure, managed identity for access. Pipeline variables only for bootstrap values.
- Q: How do you fail fast on bad config? A: Bind to an options class, add validation, and call ValidateOnStart. The app refuses to start with bad config.

----------------------------------------

8 Common mistakes

- Committing appsettings with real secrets. Shows up as a leaked key in Git history. Fix: rotate the key and move it to Key Vault.
- Snapshot injected into a singleton. Shows up as a startup exception. Fix: use IOptionsMonitor.
- Wrong key separator in environment variables. The value is silently ignored. Fix: use double underscore.
- No validation. The app starts, then fails on the first request. Fix: ValidateOnStart.
- Assuming a change reloads. IOptions never reloads. Fix: choose the right interface.
- Using a Key Vault client secret instead of managed identity. A secret is now needed to get secrets. Fix: managed identity.

----------------------------------------

9 Mental model

Layers of transparent sheets, stacked from file to environment to command line. You look from the top, so the top-most value you see wins. Options classes are a typed window onto one region of the stack.

  appsettings.json (bottom)
  + appsettings.Prod.json
  + user secrets (Dev only)
  + environment variables
  + command line (top)
  -> IConfiguration -> typed Options<T>

10 Mini lab (30 minutes)

- Run dotnet new web -n CfgLab and cd into it. Run dotnet user-secrets init.
- Add "Api": { "Url": "http://local", "Key": "none" } to appsettings.json. Create class ApiOptions with Url and Key, both with [Required].
- In Program.cs, bind it: builder.Services.AddOptions<ApiOptions>().BindConfiguration("Api").ValidateDataAnnotations().ValidateOnStart(); Add an endpoint that returns IOptionsMonitor<ApiOptions>.CurrentValue.
- Run it. Expected: it returns the appsettings values.
- Run dotnet user-secrets set "Api:Key" "secret1". Restart. Expected: Key is secret1.
- Set the environment variable Api__Key=env2 and restart. Expected: env2 wins over user secrets.
- Run dotnet run --Api:Key=cli3. Expected: cli3 wins.
- Delete Api:Url from appsettings and restart. Expected: startup fails with a validation error.
- Clean-up: dotnet user-secrets clear, remove the environment variable, delete the CfgLab folder.

11 Revision summary

- Later source wins: appsettings, env appsettings, user secrets, env vars, command line.
- Environment variable nesting uses a double underscore.
- IOptions: singleton, no reload. Snapshot: scoped, reloads per request. Monitor: singleton, change notifications.
- ValidateOnStart gives fail-fast startup.
- User secrets: local development only, not encrypted.
- Secrets go in Key Vault, read via managed identity.
- App Configuration holds non-secret settings and feature flags.
- Feature flags toggle behaviour without a redeploy.
