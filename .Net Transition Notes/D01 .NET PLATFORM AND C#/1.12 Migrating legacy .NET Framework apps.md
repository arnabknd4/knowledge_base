1 What is it
- A migration is the work of moving an existing .NET Framework app (MVC, Web API, WCF, EF6, Web.config, IIS) to modern .NET (currently .NET 8 or later, verify the current LTS).
- It is not a recompile. System.Web, Web.config, Global.asax, WCF and EF6 have no direct equivalent, so each piece is replaced or bridged.
- Three routes: in-place upgrade, strangler (move piece by piece behind a proxy), or full rewrite.
- Legacy equivalent: moving a Classic ASP application to ASP.NET, or an old VB6 app to .NET. A different runtime, with the same business rules to preserve.

2 Why needed
- .NET Framework 4.8 gets security fixes only. No new features, no Linux, no containers-first support, weak cloud fit.
- Modern .NET is faster, runs on Linux, starts fast in containers and is cheaper to host.
- Without a plan, teams either stay stuck on Windows and IIS forever or start a big-bang rewrite that runs over time and budget.

3 Before you read
- You know what System.Web, Web.config, Global.asax and IIS do.
- You know the difference between .NET Framework, .NET and .NET Standard (note 1.01).
- You know the ASP.NET Core pipeline and dependency injection (notes 1.03 and 1.05).
- Strangler fig means replacing a system slowly, one slice at a time, while the old one keeps running.

4 Features and core concepts

Assessment (APIs, dependencies, analyzers)
- Plain meaning: scan the codebase first to list what will break.
- Why: the scan gives you a size estimate and shows blockers early, such as a NuGet package with no .NET version.
- Tools: .NET Portability Analyzer replacements and the Upgrade Assistant analysis (verify current tooling), plus NuGet package compatibility checks.

.NET Upgrade Assistant
- Plain meaning: a Microsoft tool that converts the project file, updates packages and fixes common API changes.
- Why: it saves the mechanical work, but it does not finish the job. Expect manual work on auth, config and hosting.
- Verify: whether it is still the recommended tool or has been replaced by newer guidance.

In-place vs strangler (YARP) vs rewrite
- In-place: upgrade the whole app in one go. Best for small or medium apps with few blockers.
- Strangler: put a reverse proxy (YARP, which is a .NET reverse proxy library) in front. New or migrated routes go to modern .NET. Everything else still goes to the old app.
- Rewrite: build new from scratch. Last choice, because you lose years of embedded bug fixes and business rules.
- Why: the choice sets risk, cost and how long two systems run side by side.
- Setting to remember: YARP routes and clusters in appsettings, mapped by path.

System.Web replacements
- Plain meaning: System.Web does not exist in modern .NET. HttpContext, HttpModules, HttpHandlers and Session are replaced by ASP.NET Core equivalents.
- Why: this is the largest source of rewrite work in MVC apps.
- Bridge: System.Web adapters (verify current package) let shared libraries use HttpContext during a gradual move.

Web.config to appsettings
- Plain meaning: configuration moves from XML to appsettings.json, environment variables and the options pattern (note 1.04).
- Why: web.config still matters for IIS-only settings such as request limits, but app settings move out.

Global.asax to middleware
- Plain meaning: Application_Start becomes Program.cs setup. Application_BeginRequest, error handling and similar events become middleware.
- Why: order matters in the pipeline, so a migrated event can behave differently if placed wrongly.

EF6 to EF Core
- Plain meaning: EF Core is a rewrite, not an upgrade. Some features differ or are missing, and some queries behave differently.
- Why: query translation changes can cause silent performance or result changes. Test with real data.
- Options: move to EF Core, or run EF6 on .NET temporarily (EF6 supports modern .NET, verify) to reduce risk in step one.

WCF to CoreWCF, gRPC or REST
- Plain meaning: server-side WCF is not in modern .NET. Choose CoreWCF (community-supported port, keeps contracts), gRPC (new internal services) or REST (public APIs).
- Why: external clients that depend on SOAP contracts may force CoreWCF.

Windows-only APIs
- Plain meaning: registry, GDI+, COM, Windows auth specifics and event log may not work on Linux.
- Why: this decides whether you can leave Windows hosting.

Session and auth state
- Plain meaning: in-process session and forms authentication do not carry over. Move to distributed cache for session and to cookie or token auth (OIDC) for identity.
- Why: during side-by-side hosting, users must stay logged in across both apps. Share the auth cookie or use a single identity provider.

Side-by-side hosting
- Plain meaning: old and new run together behind one URL.
- Why: it enables gradual cutover and fast rollback.

Rollback plan
- Plain meaning: a written way to return traffic to the old app within minutes.
- Why: without one, a failed cutover becomes an outage. Keep the old app deployable until the new one is stable.

5 Core focus (exam and interview)
- Most asked: why not rewrite, how do you choose in-place vs strangler, what breaks first.
- Standard answer: assess first, strangler for large or business-critical apps, in-place for small apps.
- Remember: System.Web is gone, WCF server is gone, EF Core is not EF6, and sessions need a shared store.
- Remember: the Upgrade Assistant helps but does not complete the migration.
- Exam link: AZ-305 and migration topics reference rehost, refactor and rearchitect (note 12.09).

6 Real-world use case
- Situation: a 10-year-old MVC 5 app with EF6, WCF endpoints for partners, session login, hosted on IIS in a data centre.
- Choice: strangler with YARP. First move stateless read APIs to .NET. Later move auth to OIDC. Keep WCF behind the proxy until partners can switch.
- Trade-off: you run two apps and two deployments for months, and need shared auth and shared database access. Cost is higher at first.
- When NOT to use strangler: tiny apps, or apps with no active development. An in-place upgrade is simpler. When NOT to do in-place: large apps with heavy System.Web coupling and no automated tests.

7 Interview lens
- Q: How do you decide between rewrite and strangler?
  A: Rewrite only if the code is unusable or the domain is changing completely. Otherwise strangler, because it delivers value early and limits risk.
- Q: What are the biggest blockers moving MVC 5 to .NET?
  A: System.Web usage, WCF, EF6 differences and session or auth state. Third-party packages with no .NET support also block.
- Q: How do you keep users logged in during a side-by-side migration?
  A: Use one identity provider (OIDC) or share the auth cookie with data protection keys stored centrally.
- Q: How do you roll back?
  A: Keep the old app live, route by proxy, and switch routes back. Avoid database changes that the old app cannot read.

8 Common mistakes
- Starting with the Upgrade Assistant and no assessment. Shows up as late surprises. Fix: assess first.
- Skipping tests. Shows up as silent behavior changes. Fix: add characterization tests before moving code.
- Not sharing session or auth. Shows up as users logged out at route boundaries. Fix: central identity and distributed cache.
- Breaking the database for the old app. Shows up as failed rollback. Fix: backward-compatible schema changes (note 4.08).
- Migrating everything at once. Shows up as a long freeze. Fix: slice by route or feature.

9 Mental model
- Old app and new app sit behind one front door (YARP).
  Client -> YARP -> new .NET app (migrated routes)
                 -> old .NET Framework app (everything else)
- Over time, routes move left. When the old box is empty, switch it off.

10 Mini lab
Time: about 40 minutes. Tools: .NET SDK and a free local setup. No Azure needed.
- Step 1: create a small ASP.NET Core app: dotnet new web -n NewApp
- Step 2: create a second app to stand in for the legacy one: dotnet new web -n OldApp
- Step 3: in OldApp, map a route: app.MapGet("/legacy", () => "old");
- Step 4: in NewApp, map: app.MapGet("/new", () => "new");
- Step 5: create a third project, Gateway, and add YARP: dotnet add package Yarp.ReverseProxy
- Step 6: in Gateway appsettings, add two routes: /new/{**catch-all} to NewApp and everything else to OldApp (verify YARP config syntax in its docs).
- Step 7: run all three on different ports. Call the gateway at /new and at /legacy.
- Expected result: /new returns "new" from the new app, /legacy returns "old" from the old app, both through one URL.
- Clean-up: stop the three processes and delete the three folders.

11 Revision summary
- Assess first, then choose in-place, strangler or rewrite.
- Strangler with YARP is the default for large apps.
- System.Web does not exist in modern .NET.
- WCF server needs CoreWCF, gRPC or REST.
- EF Core is a rewrite of EF6, so test queries.
- Sessions and auth must be shared during side-by-side hosting.
- Always keep a rollback path to the old app.
- Upgrade Assistant helps but does not finish the job (verify current tooling).
