1 What is it

- HttpClient is the .NET class for calling other services over HTTP. IHttpClientFactory is a helper that creates and manages HttpClient instances for you. Serialization is converting objects to JSON text and back. System.Text.Json is the built-in JSON library.
- Typed client: a class that wraps one HttpClient for one external service, so callers use methods instead of raw URLs.
- Delegating handler: a piece of code that sits in the HttpClient pipeline and can inspect or change every request and response (like middleware, but for outgoing calls).
- Resilience handler: a handler that adds retries, timeouts and circuit breaking (Polly is the library behind it).
- Legacy equivalent: new HttpClient() inside a using block or a static field in MVC controllers, WebClient or HttpWebRequest, and Newtonsoft.Json (Json.NET) for JSON.

2 Why needed

- Creating a new HttpClient per request and disposing it leaves sockets in TIME_WAIT state. Under load this causes socket exhaustion (SocketException, "address already in use").
- A static HttpClient fixes exhaustion but never refreshes DNS, so it keeps calling an old IP after a failover or blue-green swap.
- Without central handlers, every team writes its own retry, logging and auth-header code. Behaviour becomes inconsistent.
- Without timeouts, one slow dependency holds threads and takes the whole API down.
- Reflection-based JSON is slow at startup and breaks under trimming and native AOT.

4 Features and core concepts

- HttpClient lifetime and socket exhaustion
  - Meaning: HttpClient owns a connection pool (via its handler). The pool is what matters, not the client object.
  - Why it matters: short-lived clients with their own handlers create a new pool each time and leak sockets.
  - Memorize: either use IHttpClientFactory, or a long-lived client with PooledConnectionLifetime set.

- IHttpClientFactory
  - Meaning: a factory that pools and recycles the message handlers (default handler lifetime is 2 minutes, verify) while handing out cheap HttpClient objects.
  - Why it matters: fixes both socket exhaustion and stale DNS.
  - Memorize: builder.Services.AddHttpClient();

- Named vs typed clients
  - Meaning: named is looked up by a string; typed is a class receiving HttpClient in its constructor.
  - Why it matters: typed clients give compile-time safety and one place per external API. Prefer typed.
  - Memorize: builder.Services.AddHttpClient<GitHubClient>(c => c.BaseAddress = new Uri("https://api.example.com/"));

- Delegating handlers
  - Meaning: classes inheriting DelegatingHandler, chained in order, each calling base.SendAsync.
  - Why it matters: one place for correlation IDs, bearer tokens, logging, metrics. Order matters: the first registered is outermost.
  - Memorize: .AddHttpMessageHandler<AuthHandler>()
  - Handlers must be registered as transient in DI. Do not inject scoped services directly (the handler lives longer than a request scope).

- Resilience handlers (Polly)
  - Meaning: policies for retry with backoff and jitter, circuit breaker, timeout, bulkhead.
  - Why it matters: handles transient faults without writing loops by hand.
  - Memorize: .AddStandardResilienceHandler() from Microsoft.Extensions.Http.Resilience (verify package and defaults). Older code uses Microsoft.Extensions.Http.Polly with AddPolicyHandler.
  - Retry only idempotent calls (GET, PUT, DELETE). Be careful retrying POST.

- Timeouts
  - Meaning: HttpClient.Timeout is a total cap for the call (default 100 seconds). Per-attempt timeouts come from the resilience handler. CancellationToken lets the caller cancel.
  - Why it matters: unbounded waits exhaust the thread pool and connections.
  - Memorize: always pass a CancellationToken to SendAsync and GetAsync.

- System.Text.Json options
  - Meaning: JsonSerializerOptions control naming, case sensitivity, null handling, enums, comments.
  - Why it matters: web defaults (JsonSerializerDefaults.Web) use camelCase and case-insensitive reading. Reuse one options instance, since creating new ones is costly.
  - Memorize: ReadFromJsonAsync<T>() and PostAsJsonAsync() extension methods.

- Source-generated serialization
  - Meaning: a compile-time generator writes the serialization code instead of using reflection.
  - Why it matters: faster startup, lower memory, trimming and native AOT safe.
  - Memorize: [JsonSerializable(typeof(Order))] on a class deriving JsonSerializerContext.

- Newtonsoft migration
  - Meaning: moving from Json.NET to System.Text.Json.
  - Why it matters: behaviours differ. Examples: STJ is stricter by default, no support for some Json.NET features such as JObject-style dynamic access (JsonNode is the replacement), different handling of private setters, enum strings, and circular references (verify specifics for your version).
  - Keep Newtonsoft only where a library needs it, and test serialized payloads on both sides.

5 Core focus (exam and interview)

- Most asked: why new HttpClient() in a loop is bad, and why a static one has the DNS problem. Answer: IHttpClientFactory.
- Typed clients over named clients.
- Handler order and the transient-handler rule.
- Defaults to remember: HttpClient.Timeout 100 seconds; factory handler lifetime 2 minutes (verify).
- Retry only transient errors (5xx, 408, network failures), with exponential backoff plus jitter. Never retry blindly on 4xx.
- Circuit breaker states: closed, open, half-open.
- STJ vs Newtonsoft differences and when source generation is needed (AOT, trimming).

6 Real-world use case

- Situation: an order API calls a payment gateway and an inventory service. After a Black Friday peak, the legacy code (new HttpClient per call) throws socket errors and a slow gateway stalls requests.
- Choice: two typed clients (PaymentClient, InventoryClient) registered with AddHttpClient. A handler adds the correlation ID and the OAuth token. AddStandardResilienceHandler gives retry with jitter, a circuit breaker and per-attempt timeouts. JSON uses a source-generated context.
- Trade-off: retries add load on a struggling service and add latency. Tune attempts and breaker thresholds. Retrying payments is only safe with an idempotency key.
- When NOT to use it: a one-off console tool making a few calls (a single static HttpClient is fine). Do not wrap every call in retries where the caller already retries, because stacked retries multiply traffic (retry storm).

7 Interview lens

- Q: Why not create HttpClient in a using block per request?
  A: Each instance has its own connection pool, and closed sockets linger in TIME_WAIT. Under load you run out of ports. Use IHttpClientFactory or a shared client.
- Q: What problem does IHttpClientFactory solve beyond socket reuse?
  A: It recycles handlers so DNS changes are picked up. It also gives one place to configure clients, handlers and resilience.
- Q: Typed client or named client?
  A: Typed. It encapsulates one API, gives compile-time safety and is easy to mock. Named is for simple cases.
- Q: Why use source-generated System.Text.Json?
  A: No runtime reflection, so faster startup, less memory and safe for trimming and native AOT.

8 Common mistakes

- new HttpClient() per call. Shows up as socket errors under load. Fix: factory or shared client.
- Singleton HttpClient with no PooledConnectionLifetime. Shows up as calls hitting old servers after failover. Fix: set the lifetime or use the factory.
- No timeout or cancellation token. Shows up as thread pool starvation when a dependency slows. Fix: set timeouts and pass tokens.
- Retrying non-idempotent POSTs. Shows up as duplicate orders or charges. Fix: idempotency keys or no retry.
- Injecting a scoped service into a delegating handler. Shows up as stale or disposed objects. Fix: use IHttpContextAccessor or pass data via request options.
- Creating new JsonSerializerOptions per call. Shows up as high CPU and allocations. Fix: one static instance.
- Reading large responses with ReadAsStringAsync. Shows up as memory spikes. Fix: stream with ReadFromJsonAsync or HttpCompletionOption.ResponseHeadersRead.

9 Mental model

Your code
  -> typed client (one API)
  -> handler chain: logging -> auth -> resilience (retry, breaker, timeout)
  -> pooled connection (recycled by factory)
  -> remote service
JSON in and out goes through one shared options or generated context.

10 Mini lab

Time: about 30 minutes. Tools: .NET SDK (current LTS, verify), no cloud needed.

- Step 1: dotnet new web -n HttpLab; cd HttpLab
- Step 2: add package Microsoft.Extensions.Http.Resilience (dotnet add package).
- Step 3: create a record Todo(int Id, string Title, bool Completed) and a class TodoClient taking HttpClient, with a method GetAsync(int id, CancellationToken ct) using GetFromJsonAsync<Todo>.
- Step 4: in Program.cs register AddHttpClient<TodoClient>(c => c.BaseAddress = new Uri("https://jsonplaceholder.typicode.com/")).AddStandardResilienceHandler();
- Step 5: add MapGet("/todo/{id}", (int id, TodoClient c, CancellationToken ct) => c.GetAsync(id, ct));
- Step 6: dotnet run, open /todo/1. Expected: JSON of the todo.
- Step 7: change BaseAddress to a dead port such as http://localhost:9999/ and call again. Expected: several retry attempts visible in the console logs (set Logging level for System.Net.Http to Information), then an error after the retries and timeouts.
- Step 8: add a DelegatingHandler that adds an X-Correlation-Id header, register with AddHttpMessageHandler, and confirm the header with a local echo endpoint or logging.
- Clean-up: stop the app and delete the HttpLab folder.

11 Revision summary

- Never new HttpClient per request. The connection pool is the real resource.
- IHttpClientFactory recycles handlers (about 2 minutes, verify), fixing socket exhaustion and stale DNS.
- Prefer typed clients. Register delegating handlers as transient. First registered handler is outermost.
- AddStandardResilienceHandler gives retry, breaker, timeouts (verify defaults).
- Retry only transient, idempotent calls, with backoff and jitter.
- HttpClient.Timeout default is 100 seconds. Always pass CancellationToken.
- Reuse JsonSerializerOptions. Use source generation for AOT and trimming.
- Newtonsoft to STJ: test behaviour differences, JsonNode replaces JObject-style access.
