1 What is it

- The .NET runtime is the engine that runs your compiled code. The SDK is the toolkit (compiler, CLI, build tools) that builds it.
- CLR (Common Language Runtime) is the runtime that manages memory, threads and type safety. JIT (Just-In-Time compiler) turns intermediate code into machine code while the app runs. BCL (Base Class Library) is the built-in set of types such as List, File, HttpClient.
- Legacy equivalent: .NET Framework 4.x installed once per machine, with a GAC (Global Assembly Cache) and an old-style csproj with packages.config.

---

2 Why needed

- .NET Framework is Windows-only and tied to the OS version. Upgrades are machine-wide and risky.
- Modern .NET runs on Windows, Linux and containers. It supports side-by-side versions, so each app picks its own.
- Without a clear target framework and version strategy, builds break across machines, containers fail, and apps run out of support unnoticed.

---

3 Before you read

- Assembly: a compiled .dll or .exe.
- IL (Intermediate Language): the compiled output before JIT converts it to machine code.
- NuGet: the package manager for .NET libraries.
- Container: an isolated, portable way to run an app (covered later in 8.01).

---

4 Features and core concepts

- CLR, JIT, BCL: CLR runs the code, JIT compiles IL to native code at run time, BCL gives base types. Matters because startup time, memory and performance all trace back to these.
- .NET Framework vs .NET vs .NET Standard: Framework is old, Windows-only, in maintenance. .NET (5 and above, previously .NET Core) is the modern cross-platform line. .NET Standard was an API contract for sharing libraries across both. Matters because migration decisions depend on this split. Today, new libraries target modern .NET directly or multi-target.
- LTS vs STS: LTS (Long Term Support) gets longer support, STS (Standard Term Support) gets shorter. Matters because production should use LTS. Check the current LTS version and support dates (verify).
- Target frameworks: a Target Framework Moniker (TFM) says what the project builds for, for example net8.0 (verify current LTS TFM) or net48. Matters because it decides which APIs you can call.
- SDK-style csproj: a short project file with no file lists and no packages.config. Matters because it is easy to read, merge and review in Git.
- NuGet and versioning: packages are referenced with PackageReference in the csproj. Versions follow semantic versioning (major.minor.patch). Matters because version conflicts and vulnerable packages are common production issues.
- global.json: pins the SDK version used by a repo. Matters because every developer and the pipeline build with the same SDK.
- Multi-targeting: one project builds for several frameworks, using the TargetFrameworks element. Matters because shared libraries often serve both old and new apps during migration.
- Side-by-side installs: several runtimes and SDKs coexist on one machine. Matters because there is no more machine-wide upgrade risk.
- Framework-dependent vs self-contained: framework-dependent needs the runtime installed on the host and gives a small output. Self-contained bundles the runtime with the app and gives a bigger output but no host dependency. Matters for container and server deployment choices.
- ReadyToRun, trimming, native AOT awareness: ReadyToRun precompiles code to cut startup time. Trimming removes unused code to shrink size. Native AOT (Ahead-Of-Time) compiles fully to native code with no JIT, giving fast startup but with feature limits (reflection-heavy code can break). Matters for serverless and container cold starts.

Commands worth memorizing:

- dotnet --list-sdks
- dotnet --list-runtimes
- dotnet new globaljson --sdk-version <version>
- dotnet publish -c Release -r linux-x64 --self-contained false

5 Core focus (exam and interview)

- Most asked: .NET Framework vs modern .NET, LTS vs STS, framework-dependent vs self-contained.
- Know the default: dotnet publish is framework-dependent unless you set self-contained.
- Know that .NET Standard is legacy; new work targets modern .NET.
- Know that global.json pins the SDK, not the runtime.
- Know that native AOT trades flexibility (reflection, dynamic loading) for startup speed and size.
- Current LTS version and end-of-support dates change. Always check the official .NET support policy page (verify).

6 Real-world use case

- Situation: a Kolkata client runs an MVC app on .NET Framework 4.8 on IIS, plus a shared class library used by three other apps.
- Choice: convert the shared library to multi-target net48 and the current LTS TFM. The apps migrate one at a time while all keep using the same library.
- Trade-off: multi-targeting adds build time and conditional code for APIs missing on one side.
- When not to use it: if every consumer has already moved, drop net48 and target only modern .NET. Also avoid self-contained deployment when the container base image already has the runtime, since it only bloats the image.

7 Interview lens

- Q: Difference between .NET Framework and .NET?
  A: Framework is Windows-only and installed machine-wide. Modern .NET is cross-platform, open source, side-by-side and faster, and it is where new features land.
- Q: Framework-dependent or self-contained?
  A: Framework-dependent for smaller output and shared runtime patching. Self-contained when the host cannot install the runtime or you need exact version control.
- Q: Why use global.json?
  A: It pins the SDK version so local, CI and build agents behave the same. It prevents "works on my machine" build drift.
- Q: When would you choose native AOT?
  A: For fast startup and low memory, such as serverless or small microservices. Avoid it when the app relies heavily on reflection or dynamic code.

8 Common mistakes

- Using STS in production: support ends early and forces a surprise upgrade. Fix: standardize on LTS.
- No global.json: a new SDK on the build agent changes behavior and breaks the pipeline. Fix: pin it.
- Targeting .NET Standard for new libraries: adds needless limits. Fix: target modern .NET, multi-target only if old consumers exist.
- Self-contained inside a container with a runtime image: image size doubles. Fix: use framework-dependent with the matching runtime image.
- Floating NuGet versions: a patch release changes behavior overnight. Fix: pin versions or use lock files.

---

9 Mental model

Your code (IL) -> CLR + JIT -> machine code, using BCL types.

SDK builds it, NuGet supplies libraries, and the TFM decides which runtime and APIs it targets.

Framework-dependent: app + (runtime on host). Self-contained: app + runtime together.

10 Mini lab (25 minutes)

- Steps:
  - Run dotnet --list-sdks and dotnet --list-runtimes. Note the versions.
  - Run dotnet new console -n VersionLab, then cd VersionLab.
  - Run dotnet new globaljson --sdk-version <an installed SDK version>.
  - Open VersionLab.csproj. Note the TargetFramework and the short SDK-style layout.
  - Run dotnet publish -c Release -o out-fd. Note the folder size.
  - Run dotnet publish -c Release -r win-x64 --self-contained true -o out-sc (use linux-x64 on Linux). Note the folder size.
  - Edit the csproj and change TargetFramework to TargetFrameworks with two values, one older and one current, if you have both SDKs. Run dotnet build.
- Expected result: out-sc is far larger than out-fd, because it includes the runtime. The multi-target build produces one output folder per framework.
- Clean-up: delete the VersionLab folder.
