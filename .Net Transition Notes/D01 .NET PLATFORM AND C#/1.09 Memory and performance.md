# 1.09 Memory and performance
1 What is it

Memory and performance is about how .NET stores your data in memory, how the garbage collector (GC, the runtime's automatic memory cleaner) reclaims it, and how to write code that allocates less and runs faster. It also covers how to measure before you optimize.
- Stack: fast, small memory area for method calls and local value types. Cleared automatically when a method returns.
- Heap: larger memory area for objects. Cleaned by the GC, not by you.
Legacy equivalent: the same CLR and GC as .NET Framework, but modern .NET adds Span, ArrayPool and much better tooling (dotnet-trace, BenchmarkDotNet).

2 Why needed

- Slow APIs and high latency often come from too many allocations and GC pauses.
- Memory leaks in long-running services (APIs, workers) end in OutOfMemory or container restarts.
- Without measurement, tuning is guesswork and often makes code worse.
- In cloud and containers, memory is billed and limited, so waste costs money and causes OOMKilled pods.

4 Features and core concepts

- Value vs reference types: value types (int, struct, enum) hold data directly. Reference types (class, string, array) hold a pointer to a heap object. Why it matters: copying a struct copies data, copying a class copies only the pointer.
- Stack and heap: stack is per thread and auto-cleaned, heap is shared and GC-managed. Why it matters: heap allocations cost GC time, stack ones are almost free.
- Boxing: wrapping a value type into an object on the heap (object o = 5). Why it matters: hidden allocation in loops, and in non-generic collections like ArrayList.
- GC generations: Gen0 holds new short-lived objects, Gen1 is a buffer, Gen2 holds long-lived objects. Gen0 collections are cheap, Gen2 are expensive. Why it matters: most objects should die young, so avoid keeping things alive longer than needed.
- LOH (Large Object Heap): objects of 85,000 bytes or more (verify) go here and are collected only with Gen2. Why it matters: big arrays and strings cause fragmentation and expensive collections.
- IDisposable and IAsyncDisposable: interface for releasing unmanaged resources (files, connections, sockets) deterministically. Why it matters: the GC does not close your database connection or file handle on time. Use using or await using.
  using var conn = new SqlConnection(cs);
  await using var stream = File.OpenRead(path);
- Span and Memory: a view over a slice of existing memory (array, stack, string) with no copy. Span lives only on the stack (cannot be a field in a class or cross await). Memory is the heap-friendly version. Why it matters: parse and slice without allocating new strings or arrays.
- ArrayPool: a shared pool of reusable arrays (ArrayPool<byte>.Shared.Rent and Return). Why it matters: avoids allocating big buffers repeatedly and hitting the LOH. Always return in a finally block.
- String allocations: strings are immutable, so every concat or Substring makes a new object. Why it matters: use StringBuilder in loops, string interpolation handlers, or Span-based parsing for hot paths.
- BenchmarkDotNet: library that runs micro-benchmarks properly (warm-up, many iterations, memory diagnoser). Why it matters: gives real numbers for time and allocations. Run in Release mode only.
- Profiling (dotnet-trace, PerfView): tools that record where CPU time and allocations go in a running app. Why it matters: find the real hotspot instead of guessing. dotnet-trace works on Linux and containers too.
- Common leaks: event handlers never unsubscribed, static collections that grow forever, HttpClient created per request (socket exhaustion), captured closures holding large objects. Why it matters: these are the usual causes of slow memory growth in production.

5 Core focus (exam and interview)

- Most asked: Gen0, Gen1, Gen2, LOH, boxing, IDisposable pattern, Span use case, HttpClient misuse.
- Default LOH threshold is about 85,000 bytes (verify).
- Server GC vs Workstation GC: server uses a heap and thread per core, better throughput for APIs. Concurrent (background) GC reduces pause time. (verify defaults for your .NET version)
- GC does not call Dispose for you. A finalizer is only a safety net and delays cleanup.
- Measure first, optimize second. Never tune without a benchmark or profile.
- In containers, GC respects the container memory limit (verify settings for your .NET version).

6 Real-world use case

Situation: an order API on Azure App Service slows down under load, and memory climbs until the app restarts every few hours.
Investigation: capture a dump or trace with dotnet-dump and dotnet-trace. Findings: a static Dictionary caches customer data with no expiry, and a new HttpClient is created per call.
Choice: replace the static dictionary with IMemoryCache with size limit and expiry, use IHttpClientFactory, and use ArrayPool for the large report buffers.
Result: stable memory, fewer Gen2 collections, lower latency.
Trade-off: pooling and Span code is harder to read and easier to get wrong (using a buffer after returning it).
When NOT to use: do not apply Span, pooling or struct tricks to normal business code. Use them only in proven hot paths.

7 Interview lens

Q1: What is the difference between stack and heap?
A: Stack holds method frames and local value types, cleaned automatically on return. Heap holds objects and is cleaned by the GC.

Q2: Why is HttpClient per request a problem?
A: Each instance opens new sockets that stay in TIME_WAIT, causing socket exhaustion. Use IHttpClientFactory or a long-lived client.

Q3: When would you use Span over string or array?
A: In hot paths for parsing or slicing where copies would allocate. Span gives a no-copy view of the data.

Q4: How do you find a memory leak in production?
A: Watch memory and GC counters with dotnet-counters, take a dump with dotnet-dump, and check which types hold the most memory and what roots keep them alive.

8 Common mistakes

- Not disposing connections or streams: shows as connection pool exhaustion. Fix with using.
- Subscribing to events and never unsubscribing: memory grows slowly. Fix by unsubscribing or using weak events.
- Static caches without limit or expiry: memory grows until restart. Fix with a size-limited cache.
- Benchmarking in Debug mode or with a stopwatch: misleading numbers. Fix with BenchmarkDotNet in Release.
- Calling GC.Collect manually: usually hurts performance. Fix by finding the cause of allocation pressure.
- Forgetting to return rented arrays: pool empties and falls back to allocation. Fix with try/finally.
- Optimizing without profiling: effort wasted on non-bottlenecks. Fix by profiling first.

9 Mental model

Think of a restaurant kitchen.
- Stack = the chef's cutting board: small, quick, cleared after each dish.
- Heap = the pantry: large and shared, cleaned by a staff member (GC) who pauses the kitchen briefly.
- Gen0 = today's fresh orders, thrown out quickly. Gen2 = stock kept for weeks.
- LOH = the big freezer: slow to clean, so avoid filling it with one-time items.
- Allocation = taking from the pantry. Fewer trips means less cleaning time.

10 Mini lab (30 minutes, local)

Goal: see boxing and string allocations in numbers.
Steps:
- dotnet new console -n MemLab and cd MemLab
- dotnet add package BenchmarkDotNet
- In Program.cs add two benchmark methods with [MemoryDiagnoser]: one that builds a string with += in a loop of 1000, one that uses StringBuilder.
- Add a third pair: sum a List<object> filled with ints (boxing) vs a List<int>.
- Run: dotnet run -c Release
Expected result: the table shows the Allocated column. The += and boxing versions allocate far more memory and have extra Gen0 collections.
Then run: dotnet-counters monitor --process-id <pid> System.Runtime (install with dotnet tool install -g dotnet-counters) on a loop app and watch GC counts.
Clean-up: delete the MemLab folder. Optionally uninstall the tool with dotnet tool uninstall -g dotnet-counters.

11 Revision summary

- Value types hold data, reference types hold pointers to heap objects.
- Boxing allocates on the heap, so avoid it in loops.
- Gen0 is cheap and frequent, Gen2 and LOH collections are expensive.
- LOH starts around 85,000 bytes (verify).
- GC frees memory but never closes unmanaged resources, so use using or await using.
- Span is a no-copy slice and lives on the stack only. ArrayPool reuses arrays, always return them.
- Typical leaks: events, statics, HttpClient per request.
- Measure with BenchmarkDotNet and dotnet-trace before changing code.
