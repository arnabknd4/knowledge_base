1 What is it

- Logging records what your application did, in order, so you can find out why something failed after the fact.
- Diagnostics means the live tools you attach to a running process to see CPU, memory, threads and slow calls.
- ILogger is the built-in logging interface in .NET. You write to it, and a provider (console, file, Azure Monitor) decides where the text goes.
- Structured logging keeps values as named fields (UserId=42) instead of one flat sentence, so you can search and filter by field.
- Legacy equivalent: log4net or NLog with Web.config appenders, plus Event Viewer and PerfMon on the IIS server.

2 Why needed

- Production has no debugger. Logs and counters are your only evidence.
- Without structured logs, finding one failed order among millions of lines means text search and guesswork.
- Without correlation IDs, you cannot follow one request across several services.
- Without health checks, a load balancer keeps sending traffic to a broken instance.
- Too much logging at Debug level slows the app and inflates cloud bills.

3 Before you read

- Dependency injection: logger instances are injected into your classes.
- Middleware pipeline: a request passes through ordered steps, and logging hooks into them.
- HTTP request and response basics: status codes, headers.
- Process, thread and heap: what a running program uses on a machine.

4 Features and core concepts

- ILogger and levels
  - Plain meaning: ILogger<T> is the logging interface. Levels rank importance: Trace, Debug, Information, Warning, Error, Critical.
  - Why it matters: the minimum level per category is set in config, so you can turn Debug on in one namespace without redeploying.
  - Memorize: logger.LogInformation("Order {OrderId} placed by {UserId}", id, user);
  - Rule: never use string interpolation inside the message. Use named placeholders so the fields stay structured.

- Structured logging (Serilog)
  - Plain meaning: Serilog is a third-party library that stores each placeholder as a property, not just text.
  - Why it matters: you can query OrderId=1234 in Seq, Elasticsearch or Log Analytics.
  - Memorize: builder.Host.UseSerilog((ctx, cfg) => cfg.ReadFrom.Configuration(ctx.Configuration));
  - Use @ to capture an object (destructuring) and keep secrets and personal data out of it.

- Scopes
  - Plain meaning: logger.BeginScope adds fields to every log line written inside a using block.
  - Why it matters: you set TenantId or OrderId once and every nested log carries it.

- Correlation IDs
  - Plain meaning: one ID attached to a request and passed to every downstream call and log line.
  - Why it matters: it lets you stitch together logs from many services for one user action.
  - Detail: modern .NET already creates a trace ID through Activity (W3C traceparent header). Prefer it over a hand-made header, and echo it in error responses.

- Sinks
  - Plain meaning: a sink is where logs go: console, file, Seq, Application Insights, Elasticsearch.
  - Why it matters: in containers, write to console and let the platform collect. Avoid local files on ephemeral instances.

- Sampling
  - Plain meaning: keep only a fraction of telemetry (for example 10 percent of successful requests).
  - Why it matters: it controls cost. Keep all errors and slow requests, sample the rest.
  - Application Insights offers adaptive sampling (verify current defaults).

- dotnet-counters
  - Plain meaning: a CLI that shows live metrics (CPU, GC counts, request rate, thread pool queue) from a running process.
  - Why it matters: first check when an app is slow. No restart needed.
  - Memorize: dotnet-counters monitor --process-id 1234

- dotnet-trace
  - Plain meaning: records a trace of what the process is doing over time (method timings, events).
  - Why it matters: shows where CPU time goes. Open the file in PerfView, Visual Studio or speedscope.
  - Memorize: dotnet-trace collect --process-id 1234

- dotnet-dump
  - Plain meaning: captures and analyzes a memory dump, a snapshot of the heap and threads.
  - Why it matters: used for memory leaks, hangs and deadlocks. Analysis commands include dumpheap -stat and clrstack.
  - Memorize: dotnet-dump collect --process-id 1234

- Health check endpoints
  - Plain meaning: a URL such as /health that answers whether the app can serve traffic.
  - Why it matters: load balancers, App Service and Kubernetes use it to route traffic or restart.
  - Memorize: builder.Services.AddHealthChecks().AddSqlServer(cs); then app.MapHealthChecks("/health");
  - Split liveness (process is alive) from readiness (dependencies are ok). Do not put slow external checks in liveness.

5 Core focus (exam and interview)

- Most asked: log levels and when to use each, structured vs plain text, correlation across services, and the three dotnet CLI tools and when each applies.
- Default: ASP.NET Core logs to console and debug providers, with a default minimum level of Information.
- Level config lives in the Logging section of appsettings.json, with per-category overrides.
- Message templates are cached and are faster than interpolated strings. Analyzer rule CA2254 warns on non-constant templates.
- Counters first (what is happening), trace second (where time goes), dump third (what is in memory).
- On Azure, App Service and Container Apps stream console output to Azure Monitor. Use Application Insights for traces and requests (verify current SDK vs OpenTelemetry distro guidance).
- High-cardinality fields (such as a user ID as a metric dimension) are fine in logs but costly in metrics.

6 Real-world use case

- Situation: an order API on Azure App Service has intermittent 500 errors. Logs are plain text files on the instance, with no way to link one request across the API and a Service Bus worker.
- Choice made: add Serilog with a console sink and Application Insights sink, log with message templates, use the W3C trace ID as correlation ID, return it in ProblemDetails, add liveness and readiness health checks, and use dotnet-counters on a staging replica.
- Trade-off: more telemetry means more cost and more risk of leaking personal data. Mitigate with sampling, level filtering and redaction.
- When NOT to use heavy logging: hot loops and per-item logging at Information level in high-throughput paths. Use metrics there. Also do not log request bodies containing secrets or personal data.

7 Interview lens

- Q: Why use message templates instead of string interpolation?
  - A: Templates keep named fields for querying and avoid building strings when the level is disabled.
  - A: Interpolation produces flat text and allocates every time.
- Q: How do you trace one request across microservices?
  - A: Propagate the W3C traceparent header, which Activity and HttpClient do automatically, and log the trace ID.
  - A: Export to a backend such as Application Insights to see the end-to-end view.
- Q: The app is slow in production and CPU is high. What do you do?
  - A: Check dotnet-counters for CPU, GC and thread pool queue length, then collect a dotnet-trace to find hot methods.
  - A: If memory grows, take dotnet-dump and inspect the heap.
- Q: Liveness vs readiness?
  - A: Liveness says the process should keep running, and failure means restart. Readiness says it can accept traffic, and failure means remove from rotation.
  - A: Putting database checks in liveness can cause restart storms during a database outage.

8 Common mistakes

- Logging with string interpolation: you lose fields and pay allocation cost. Fix: use templates.
- Logging secrets, tokens or personal data: shows up in audits and breaches. Fix: redact, avoid destructuring whole objects.
- Everything at Information or Error: noise hides real problems. Fix: agree on level guidelines and review them.
- Swallowing exceptions or logging and rethrowing at every layer: duplicate entries. Fix: log once at the boundary, with the exception object as first argument.
- Writing logs to local files in containers: lost on restart. Fix: write to stdout.
- Health check that tests every dependency in liveness: cascade restarts. Fix: separate liveness and readiness.
- Running dotnet-dump on production without planning: it can pause the process and create very large files. Fix: use a replica or off-peak window, and check disk space.

9 Mental model

- Request comes in -> gets a trace ID -> every log line carries that ID and scope fields -> sinks ship lines to a store -> you query by field.
- Separate tray for live checks: counters (what now), trace (where time goes), dump (what is in memory).
- Health endpoint = a doorbell the platform presses to ask whether to send traffic.

10 Mini lab

Time: about 30 minutes. Tools: .NET SDK (current LTS, verify), a terminal, no cloud needed.

- Step 1: dotnet new webapi -n LogLab and cd LogLab.
- Step 2: dotnet add package Serilog.AspNetCore.
- Step 3: in Program.cs, add builder.Host.UseSerilog((ctx, cfg) => cfg.WriteTo.Console().Enrich.FromLogContext()); and builder.Services.AddHealthChecks(); then app.MapHealthChecks("/health");
- Step 4: in an endpoint, call logger.LogInformation("Order {OrderId} requested", id); using an injected ILogger.
- Step 5: dotnet run, call the endpoint and /health with curl. Expected result: console shows the line with OrderId as a property and /health returns Healthy.
- Step 6: dotnet tool install --global dotnet-counters, find the process ID with dotnet-counters ps, then run dotnet-counters monitor --process-id <id>. Expected result: live CPU, GC and request counters update while you send requests.
- Step 7: change Logging level for Microsoft.AspNetCore to Warning in appsettings.json and observe less noise.
- Clean-up: press Ctrl+C to stop the app and the monitor, then delete the LogLab folder. Optionally dotnet tool uninstall --global dotnet-counters.

11 Revision summary

- ILogger levels in order: Trace, Debug, Information, Warning, Error, Critical.
- Use message templates with named placeholders, never interpolation.
- Serilog keeps fields as properties and sends them to sinks.
- Correlation ID: use W3C trace ID, propagate on every call, return it in errors.
- In containers, log to console, not local files.
- Counters to see, trace to find hot code, dump to inspect memory.
- Health checks: liveness (alive) vs readiness (dependencies ok).
- Sample high-volume telemetry, and never log secrets or personal data.
