# 1.11 Testing in .NET
1 What is it

Testing in .NET means writing automated checks that prove your code works and keeps working after changes. A test is a small program that runs your code with known input and compares the result to what you expect. A test runner (xUnit here) finds and runs them, usually on every build.
Legacy equivalent: MSTest or NUnit tests in a .NET Framework solution, often with a hand-made fake database and Rhino Mocks or early Moq.

2 Why needed

- Lets you change code, upgrade .NET versions and refactor without fear.
- Catches regressions before the client or QA sees them.
- Makes migration from .NET Framework (topic 1.12) safe, because tests prove behaviour did not change.
- Without tests, every release needs manual regression, and bugs reach production.

4 Features and core concepts

- xUnit: the standard .NET test framework. A [Fact] is one test, a [Theory] with [InlineData] runs one test with many inputs. A new class instance is created per test, so tests do not share state. Matters because shared state causes flaky tests.
- Mocking (Moq, NSubstitute): a library that creates a fake object from an interface at runtime. Matters because it isolates the class under test from slow or external things. NSubstitute is a safe default (verify current library licensing and status before choosing).
- Arrange-act-assert: set up the data, call the code once, check the result. Matters because it keeps each test short and readable.
- Test doubles: the family of fakes. Dummy (unused filler), stub (returns canned answers), fake (a working light version, like an in-memory list), mock (records calls so you can check them), spy (a real object that records calls). Matters because interviewers ask you to name the difference.
- WebApplicationFactory: starts your whole ASP.NET Core app in memory and gives you an HttpClient to call it. Matters because it tests routing, middleware, auth and serialization together, with no real server. You can replace services with fakes in ConfigureWebHost.
- Testcontainers: starts a real SQL Server, Redis or Service Bus emulator in Docker for the test and removes it afterwards. Matters because the in-memory EF provider does not behave like SQL Server (no real constraints, transactions or SQL translation).
- Database test strategies: options are in-memory provider (fast, inaccurate), SQLite in-memory (closer, still different from SQL Server), real database in a container (accurate, slower), shared database with reset (fast, fragile). Matters because wrong choice gives false confidence. Reset data per test or per class.
- Test data builders: a small class with sensible defaults and fluent overrides, like new OrderBuilder().WithStatus(Paid).Build(). Matters because tests then show only the data that matters.
- Coverage as a signal: percentage of lines executed by tests. Matters only as a hint to find untested areas. High coverage with weak assertions proves nothing.
- Snapshot tests: compare output to a saved approved file (Verify library). Contract tests: check that a consumer and provider agree on an API shape (Pact, see 9.07). Matters for large JSON outputs and service boundaries.
- Test pyramid: many fast unit tests, fewer integration tests, very few end-to-end UI tests. Matters because the top is slow and brittle.
- Flaky tests: pass and fail with no code change. Causes are time, random values, shared state, async timing and order dependence. Matters because a team stops trusting a flaky suite.

Worth memorising:
- dotnet test --filter "Category=Integration"
- var client = factory.CreateClient(); var res = await client.GetAsync("/orders/1");

5 Core focus (exam and interview)

- Unit vs integration vs end-to-end: scope, speed, cost.
- Names of test doubles and when to use mock vs stub.
- Why the EF in-memory provider is discouraged for testing relational behaviour.
- WebApplicationFactory<Program> needs Program to be visible to the test project (partial class Program or InternalsVisibleTo).
- xUnit creates a new class instance per test; IClassFixture shares one object per class, ICollectionFixture across classes.
- Coverage is not quality.
- Tests should run in the pipeline on every commit (7.03, 7.05).

6 Real-world use case

Situation: an Orders API is being moved from .NET Framework to modern .NET and EF Core. Choice: write integration tests first with WebApplicationFactory plus a SQL Server Testcontainer, covering the main order flows. Run the same tests before and after the migration steps. Unit tests cover pricing and discount rules. Trade-off: container startup adds a minute to the pipeline, and the build agent needs Docker. Share one container across the test class to save time.
When NOT to use it: do not write integration tests for simple pure logic; a unit test is faster. Do not chase 100 percent coverage on generated code or plain DTOs. Do not test private methods directly.

7 Interview lens

- Q: Mock vs stub?
A: A stub returns canned data so the code under test can run. A mock also lets you verify that a call happened. Prefer stubs and check results; verify calls only when the call is the behaviour.
- Q: Why not use the EF Core in-memory provider?
A: It does not enforce relational rules, transactions or SQL translation, so tests pass but production fails. Use SQLite in-memory for light checks or Testcontainers with SQL Server for accuracy.
- Q: How do you handle flaky tests?
A: Find the cause: time, shared state, async waits, order. Inject a clock, isolate data, await properly. Quarantine the test with a ticket, never ignore it silently.
- Q: What does 90 percent coverage tell you?
A: Only that 90 percent of lines ran. It says nothing about assertion quality. I use it to find untested areas and add mutation testing or review for quality (verify tool choice).

8 Common mistakes

- Testing the mock instead of the code: test passes, nothing real is checked. Fix: assert on outputs and state.
- Over-mocking everything: tests break on every refactor. Fix: mock only external boundaries.
- Shared database state between tests: random failures in parallel runs. Fix: reset data per test or unique data per test.
- Using DateTime.Now or Random in code: untestable and flaky. Fix: inject TimeProvider (verify availability for your target framework) or a clock interface.
- Sleeping in tests (Thread.Sleep): slow and still flaky. Fix: await the actual condition.
- Async test methods returning void: failures are lost. Fix: return Task.
- Asserting too many things in one test: unclear failures. Fix: one behaviour per test.

9 Mental model

Pyramid:
- Top: few end-to-end tests (slow, real browser or full environment).
- Middle: integration tests (WebApplicationFactory plus Testcontainers).
- Base: many unit tests (xUnit plus test doubles, milliseconds each).
The wider the layer, the cheaper and faster. Push every check as low as it can go and still prove the behaviour.

10 Mini lab (about 35 minutes)

Tools: .NET SDK (current LTS, verify), Docker Desktop or Docker Engine.
- Step 1: dotnet new web -n Shop.Api, then dotnet new xunit -n Shop.Tests, then dotnet new sln and add both projects.
- Step 2: In Shop.Api, add one endpoint, app.MapGet("/ping", () => "pong"). At the end of Program.cs add: public partial class Program { }
- Step 3: In Shop.Tests, add a reference to Shop.Api and package Microsoft.AspNetCore.Mvc.Testing (match the version to your SDK).
- Step 4: Write a test with IClassFixture<WebApplicationFactory<Program>>. Create a client, call /ping, assert status 200 and body "pong".
- Step 5: Add a [Theory] that tests a small pure method (for example a discount calculator) with three InlineData rows.
- Step 6: Add package Testcontainers.MsSql, start a container in an IAsyncLifetime fixture, open a connection and run SELECT 1. Needs Docker running.
- Expected result: dotnet test shows all tests passed. The container test takes longer than the others (seconds to start).
- Clean-up: confirm no leftover container with docker ps -a, remove any with docker rm -f <id>. Delete the lab folder if not needed.

11 Revision summary

- Pyramid: many unit, fewer integration, very few end-to-end.
- xUnit: [Fact] one case, [Theory] many cases, new class instance per test.
- Stub gives answers, mock verifies calls, fake is a light working version.
- WebApplicationFactory<Program> runs the full app in memory; Program must be visible.
- Testcontainers gives a real SQL Server per run; the EF in-memory provider is not accurate.
- Test data builders keep arrange steps short and clear.
- Coverage finds gaps; it does not prove quality.
- Flaky causes: time, shared state, async waits, order. Inject clocks and isolate data.
