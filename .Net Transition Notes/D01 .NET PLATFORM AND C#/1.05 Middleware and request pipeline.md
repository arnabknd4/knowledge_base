# 1.05 Middleware and request pipeline

1 What is it

Middleware is a chain of small components that every HTTP request passes through, in order, before it reaches your endpoint. The response travels back through the same chain in reverse. Each component can inspect the request, change it, short-circuit it, or pass it to the next one. The whole chain is called the request pipeline. It is configured in Program.cs.
- Legacy equivalent: HTTP modules and HTTP handlers (IHttpModule, Global.asax events) in ASP.NET, plus MVC action filters.

2 Why needed

- Cross-cutting work (error handling, HTTPS, CORS, compression, rate limiting) must run for every request without repeating code in each controller.
- Without a pipeline, each endpoint duplicates this logic and security rules get missed on some routes.
- Without correct ordering, features fail silently, for example auth running before routing, or CORS headers missing on error responses.

4 Features and core concepts

- Ordering: middleware runs in the order you register it. It matters because each component only sees what earlier ones have done. Rule to memorize: exception handler first, then HTTPS and HSTS, static files, routing, CORS, rate limiting, authentication, authorization, endpoints.
- Use, Run, Map: Use adds a component that can call next. Run adds a terminal component that ends the chain. Map branches the pipeline by path. It matters because Run placed early swallows every request after it.
- Custom middleware: a class with a constructor taking RequestDelegate and an InvokeAsync(HttpContext) method, registered with app.UseMiddleware<T>(). It matters for correlation IDs, tenant resolution and audit logging. Scoped services must be injected into InvokeAsync, not the constructor, because middleware is created once as a singleton.
- Exception handling: UseExceptionHandler (or IExceptionHandler) catches unhandled errors and returns a safe response. It must be first so it wraps everything. Never use the developer exception page outside Development.
- Endpoint routing: UseRouting selects the endpoint, then later middleware (CORS, auth) can read which endpoint was chosen, then UseEndpoints or MapControllers runs it. In the minimal hosting model routing is added implicitly, but explicit placement still matters when auth and CORS must sit between routing and endpoints.
- Filters vs middleware: middleware sees every request and knows nothing about MVC. Filters run inside MVC, know the action, model binding and action result. Use middleware for global concerns, filters for per-action concerns such as validation or result shaping.
- CORS: browser rule relaxation for cross-origin calls. app.UseCors("policy") must come after routing and before authorization. Wrong order gives missing headers and browser errors that look like network failures.
- Compression: UseResponseCompression shrinks responses (Brotli, Gzip). It matters for bandwidth. Be careful with compressing responses that mix secrets and user input over HTTPS (BREACH attack awareness).
- Rate limiting: built-in UseRateLimiter with fixed window, sliding window, token bucket and concurrency limiters. It protects APIs from abuse. Rejected requests return 429. In multi-instance deployments the built-in limiter is per instance, not global.
- HTTPS redirection and HSTS: UseHttpsRedirection sends http to https. UseHsts tells browsers to use https only. HSTS is for non-Development environments only. Behind a reverse proxy, forwarded headers must be configured first or you get redirect loops.
- Request buffering: by default the body is a forward-only stream. EnableBuffering lets you read it more than once, for example for audit logging. It matters for memory use on large uploads, so set size limits.

Memorize:
- app.UseExceptionHandler("/error");
- app.UseHttpsRedirection();
- app.UseRouting();
- app.UseCors("web");
- app.UseAuthentication();
- app.UseAuthorization();

5 Core focus (exam and interview)

- Most asked: correct middleware order and why. Authentication before authorization. CORS before auth. Exception handler first.
- Use vs Run vs Map. Run is terminal.
- Middleware vs filters, and when to choose each.
- Short-circuiting: a component that does not call next ends the pipeline. Responses still flow back through earlier components.
- Middleware is a singleton-lifetime object. Inject scoped services through InvokeAsync parameters.
- Once the response has started, you cannot change status code or headers. Writing headers after next() can throw.
- Default rate limit rejection status is 503 unless you set RejectionStatusCode to 429 (verify).
- Built-in rate limiter requires .NET 7 or later (verify current LTS).

6 Real-world use case

- Situation: an Angular SPA calls an ASP.NET Core API hosted on Azure App Service behind Front Door. Users on mobile report random CORS errors on 500 responses.
- Choice: put UseExceptionHandler first, and place UseCors before UseAuthentication. Add a correlation ID middleware right after the exception handler so every log and error carries the ID. Add the rate limiter after authentication so limits can be per user.
- Trade-off: more middleware means more latency per request and harder debugging of order issues. Each component adds a small cost on every call.
- When NOT to use middleware: logic needed only for specific actions (use filters), or logic needing access to model-bound arguments or action results (use filters). Do not put heavy business logic in middleware.

7 Interview lens

- Q: Why does middleware order matter? A: Each component only sees what earlier ones did, so wrong order breaks features. For example authorization before authentication always rejects, and CORS after auth drops headers on 401s.
- Q: Middleware vs filters? A: Middleware is global and framework-level, working on raw HttpContext. Filters run inside MVC and can see actions, arguments and results.
- Q: How do you use a scoped service in custom middleware? A: Inject it as a parameter of InvokeAsync. The constructor is resolved once at startup, so a scoped service there becomes a captive dependency.
- Q: How do you handle exceptions globally? A: Register UseExceptionHandler or an IExceptionHandler first in the pipeline and return ProblemDetails. This catches errors from everything after it.

8 Common mistakes

- Registering UseAuthorization before UseAuthentication: every request returns 401 or 403. Fix: authentication first.
- CORS after authorization: browser shows CORS error on 401 responses. Fix: place UseCors before auth.
- Run placed too early: later endpoints never execute. Fix: use Use with next, reserve Run for the end of a branch.
- Reading the request body without EnableBuffering: endpoint receives an empty body. Fix: enable buffering and reset the stream position.
- HSTS and https redirection behind a proxy without forwarded headers: redirect loop. Fix: UseForwardedHeaders first and trust the proxy.
- Scoped service in middleware constructor: stale data across requests. Fix: inject in InvokeAsync.
- Leaking stack traces: developer exception page in production. Fix: environment check.

9 Mental model

A security checkpoint corridor with several desks. Every visitor (request) walks through desk 1, 2, 3 to reach the room (endpoint). Any desk can turn the visitor away. On the way out the visitor passes the same desks in reverse.

request -> [ErrorHandler] -> [HTTPS] -> [Routing] -> [CORS] -> [Auth] -> [Endpoint]
response <- [ErrorHandler] <- [HTTPS] <- [Routing] <- [CORS] <- [Auth] <- [Endpoint]

10 Mini lab (30 minutes, local, no Azure needed)

- Step 1: run dotnet new web -n PipelineLab and cd PipelineLab.
- Step 2: in Program.cs, add three Use components before app.MapGet. Each one logs "A in", calls await next(), then logs "A out". Name them A, B, C.
- Step 3: add app.MapGet("/", () => "hello").
- Step 4: run dotnet run and call the URL. Expected: A in, B in, C in, then C out, B out, A out. This shows the in-and-back flow.
- Step 5: make B not call next and return "blocked". Expected: A in, B in, B out, A out. C and the endpoint never run.
- Step 6: add a custom middleware class that reads a scoped service via InvokeAsync and adds an X-Correlation-Id header. Confirm the header with curl -i.
- Step 7: add app.UseRateLimiter with a fixed window of 2 requests per 10 seconds. Call 3 times quickly. Expected: third call is rejected.
- Clean-up: stop the app and delete the PipelineLab folder.

11 Revision summary

- Middleware is an ordered chain; request goes in, response comes back out in reverse.
- Use calls next, Run ends the chain, Map branches by path.
- Order: exception handler, HTTPS and HSTS, routing, CORS, authentication, authorization, endpoints.
- Middleware is a singleton; inject scoped services into InvokeAsync.
- Filters live inside MVC; middleware is global.
- Built-in rate limiter is per instance, not distributed.
- Behind a proxy, configure forwarded headers before HTTPS redirection.
- After the response starts, headers and status cannot change.
