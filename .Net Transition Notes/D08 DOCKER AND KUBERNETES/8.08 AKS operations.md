1 What is it
- AKS operations means the day-to-day work of building, securing, upgrading, watching and paying for an Azure Kubernetes Service cluster.
- AKS is Kubernetes where Azure runs the control plane (API server, etcd, scheduler) for you. You own the node pools, the workloads and the settings around them.
- A cluster is the whole Kubernetes environment. A node pool is a group of identical VMs that run your pods. A pod is the smallest unit Kubernetes runs, one or more containers.
- Legacy equivalent: running an IIS web farm on Windows Server, with patching, load balancer, monitoring and access control, except the machines are managed through one API.

2 Why needed
- Creating a cluster is easy. Keeping it patched, secure, observable and affordable for years is the real job.
- Without upgrade discipline, versions fall out of support (verify the support window) and you face forced, risky jumps.
- Without identity and RBAC design, pods carry stored secrets and users get broad admin rights.
- Without monitoring and cost control, outages are found by users and node bills grow silently.

4 Features and core concepts
- Cluster and node pool creation. A cluster has one system pool (runs core components like CoreDNS) and optional user pools (run your apps). Why: separating them keeps your app load from starving cluster services. Spot pools use cheap evictable VMs, good for batch only.
  - az aks create -g rg -n aks1 --node-count 3 --enable-managed-identity --network-plugin azure
- Upgrades. Two kinds: the Kubernetes version upgrade and the node image upgrade (OS patches). Channels are auto-upgrade settings (none, patch, stable, rapid, node-image) (verify names). Surge means extra temporary nodes added during an upgrade so pods can move before old nodes are removed. Why: surge keeps capacity during rollouts; too small a surge makes upgrades slow, too big costs money.
- Managed identity and workload identity. A managed identity is an Azure-held credential for the cluster itself (to pull images, create load balancers). Workload identity lets one pod act as one Entra identity through a federated token, with no secret stored. Why: it replaces secrets in config and the old pod identity approach (verify status).
- Entra integration and RBAC. Entra integration lets people sign in to the cluster with their company account. Kubernetes RBAC (or Azure RBAC for Kubernetes) decides what they can do. Why: no shared admin kubeconfig, and access is auditable.
- ACR integration. Attach the registry so the kubelet identity can pull images without passwords.
  - az aks update -g rg -n aks1 --attach-acr myacr
- Monitoring. Container Insights sends logs and metrics to Log Analytics. Managed Prometheus collects metrics and managed Grafana draws dashboards. Why: Container Insights is quick for logs; Prometheus is better for metric alerting. Both cost money by data volume.
- Ingress options. Ingress is the rule set for HTTP traffic entering the cluster. Options: managed NGINX add-on (verify), Application Gateway for Containers or AGIC (verify), Istio gateway. Why: choose by WAF need, TLS handling and who runs it.
- Defender. Defender for Containers scans images and watches runtime threats. Why: gives vulnerability and threat alerts without building your own.
- Policy. Azure Policy for Kubernetes (Gatekeeper-based) blocks bad deployments, such as privileged pods or untrusted registries.
- Cost control. Right-size node VMs, set pod requests and limits, use cluster autoscaler, stop dev clusters at night, use spot for batch, use reservations for steady load.
- Private clusters. The API server gets a private IP only, reachable from your VNet or peered networks. Why: no public API endpoint. Cost: you need a jump host, VPN or self-hosted pipeline agent to run kubectl.
- SLA tiers. Free tier has no financially backed uptime SLA. Standard tier gives an SLA, and more with availability zones. Premium adds long-term support (verify all). Why: production should not sit on Free.

5 Core focus (exam and interview)
- Most asked: system vs user pools, upgrade order (control plane first, then node pools), surge, and why N+1 minor version steps only (verify skip rules).
- Most asked: managed identity vs workload identity vs service principal.
- Networking choice made at creation is hard to change: kubenet vs Azure CNI vs CNI overlay (verify).
- Defaults to remember: you cannot downgrade Kubernetes versions; the system pool needs at least one node; the Free tier has no SLA.
- Private cluster trade-off: security gain, access complexity.
- Know the order of fixes for a stuck upgrade: check PodDisruptionBudgets, quota, and surge capacity.

6 Real-world use case
- Situation: a legacy .NET Framework order system is split with YARP and the new .NET APIs run on AKS for a Kolkata client with a 99.9 percent target.
- Choice: Standard tier, system pool of 3 nodes across zones, a user pool with autoscaler, Entra sign-in with group-based RBAC, workload identity to reach Key Vault and Service Bus, ACR attached, Container Insights plus managed Prometheus, Azure Policy blocking latest tags, and a stable auto-upgrade channel with a weekend maintenance window.
- Trade-off: much more control and portability than App Service, but your team now owns upgrades, node sizing, and troubleshooting.
- When NOT to use it: a small team with a few simple web APIs and no need for Kubernetes features. Use App Service or Container Apps (see 8.11).

7 Interview lens
- Q: How do you upgrade an AKS cluster safely?
  A: Check version support and deprecated APIs, upgrade in staging first, then the control plane, then node pools with surge. Make sure PodDisruptionBudgets and replicas allow pods to move.
- Q: How does a pod reach Key Vault without a secret?
  A: Workload identity. The pod's service account is federated to an Entra identity, and Azure RBAC on the vault grants access to that identity.
- Q: Why use separate system and user node pools?
  A: Core components stay protected from noisy apps, and you can scale, size and upgrade each pool independently.
- Q: What do you give up with a private cluster?
  A: Easy kubectl access. You need a VNet-connected jump host, VPN, or agent, and DNS must resolve the private endpoint.

8 Common mistakes
- Staying on one version for a year. Shows up as forced upgrades past deprecated APIs. Fix: auto-upgrade channel and regular windows.
- Giving everyone cluster-admin. Shows up as accidental deletes in production. Fix: Entra groups mapped to namespace roles.
- Stored service principal secrets in pods. Shows up as expired secrets causing outages. Fix: workload identity.
- No pod requests and limits. Shows up as noisy neighbours and OOMKilled pods. Fix: set them and use Policy to require them.
- Choosing the network plugin casually. Shows up as IP exhaustion later. Fix: plan pod and node IP ranges first.
- Logging everything to Log Analytics. Shows up as surprise bills. Fix: filter tables, set retention.

9 Mental model
- Azure owns the building (control plane). You own the floors (node pools), tenants (pods), keys (identity), alarms (monitoring) and the rent (cost).
- Diagram: Entra ID -> kubectl -> API server (Azure managed) -> system pool + user pools -> pods -> workload identity -> Key Vault, Service Bus; ACR feeds images; Monitor watches all.

10 Mini lab
- Time: 30 to 40 minutes. Use the Azure free tier or a Visual Studio credit (verify cost; AKS nodes bill as VMs). Use a small VM size and 1 node.
- Steps:
  - Open Cloud Shell. Run az group create -n rg-aks-lab -l centralindia
  - Create the registry: az acr create -g rg-aks-lab -n <uniquename> --sku Basic
  - Create the cluster: az aks create -g rg-aks-lab -n aks-lab --node-count 1 --generate-ssh-keys --attach-acr <uniquename>
  - Get credentials: az aks get-credentials -g rg-aks-lab -n aks-lab
  - Check with kubectl get nodes. Expect one node in Ready state.
  - Add a user pool: az aks nodepool add -g rg-aks-lab --cluster-name aks-lab -n userpool --node-count 1
  - Run az aks nodepool list and see two pools. Run az aks get-upgrades to see available versions.
  - In the portal open Insights for the cluster and view node CPU (enable monitoring if prompted).
- Expected result: a cluster with a system pool and a user pool, ACR attached, and visible upgrade options.
- Clean-up: az group delete -n rg-aks-lab --yes --no-wait

11 Revision summary
- AKS: Azure runs the control plane, you run nodes and workloads.
- System pool for core components, user pools for apps, spot only for batch.
- Upgrade control plane first, then node pools; surge adds temporary nodes; no downgrades.
- Workload identity means no secrets in pods; kubelet identity pulls from ACR.
- Entra sign-in plus RBAC replaces shared admin kubeconfig.
- Private cluster hides the API server; you need VNet access to use it.
- Standard tier for production SLA; Free tier has none (verify).
- Cost levers: right-size, autoscaler, requests and limits, spot, reservations.
