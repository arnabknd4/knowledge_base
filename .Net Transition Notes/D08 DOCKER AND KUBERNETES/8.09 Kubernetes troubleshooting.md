1 What is it
- Kubernetes troubleshooting is the habit of finding why a workload is not running or not healthy, using a fixed set of commands and a fixed list of failure states.
- A Pod is the smallest unit Kubernetes runs: one or more containers sharing network and storage. Most problems show up as a Pod stuck in a bad status.
- kubectl is the command-line client that talks to the cluster API server.
- Legacy equivalent: Event Viewer, IIS failed request tracing and attaching a debugger to a w3wp process on a Windows server.

2 Why needed
- Kubernetes hides the machine. You cannot RDP in and look around.
- Without a method, you restart things randomly and lose the evidence.
- Most production incidents on AKS are one of about ten known failure states.
- A runbook habit makes on-call faster and makes you credible in architect interviews.

3 Before you read
- A container is a packaged process; an image is the package it starts from.
- A Pod is managed by a Deployment, which creates ReplicaSets, which create Pods.
- Requests are the CPU and memory a Pod asks for. Limits are the maximum it may use.
- A probe is a health check Kubernetes runs against a container.

4 Features and core concepts
- describe: shows one object's full state plus its recent events. Why: the Events section at the bottom usually names the cause.
- logs: shows container output. Use --previous for the crashed instance. Why: the failure is often in the last lines before the restart.
- events: cluster messages sorted by time. Why: shows scheduling, pulling and probe failures even when the Pod is gone.
- exec: runs a command inside a running container. Why: check files, env vars and DNS from the Pod's point of view.
- port-forward: tunnels a local port to a Pod or Service. Why: test an app without exposing it.
- top: shows live CPU and memory use (needs metrics-server). Why: spots resource pressure.
- CrashLoopBackOff: the container starts, exits, and Kubernetes keeps retrying with growing delays. Cause: app crash, bad config, missing secret, failing startup. Fix: logs --previous, then fix the cause.
- ImagePullBackOff: the node cannot download the image. Cause: wrong name or tag, no registry permission, registry unreachable. Fix: check the image string, ACR attach or pull secret, network.
- OOMKilled: the container exceeded its memory limit and was killed (exit code 137). Fix: raise the limit or fix the leak; compare with the .NET GC behaviour in containers.
- Pending pods: the scheduler found no node that fits. Cause: requests too large, taints, affinity, unbound volume, node pool full. Fix: describe pod and read the scheduling message.
- Failing probes: liveness failure restarts the container; readiness failure removes it from Service endpoints; startup probe protects slow starters. Fix: correct the path, port and timings.
- DNS and Service issues: Service has no endpoints (selector does not match labels), or cluster DNS (CoreDNS) fails. Fix: check endpoints, labels, and nslookup from a Pod.
- Config errors: wrong ConfigMap or Secret name, missing key, bad env var. Shows as CreateContainerConfigError. Fix: describe pod and compare names.
- Node NotReady: the node stopped reporting to the control plane. Cause: kubelet down, disk or memory pressure, network loss. Fix: describe node, check conditions, cordon and drain, replace the node.
- Stuck rollouts: a new Deployment version never becomes ready, so the old one stays. Fix: rollout status, then rollout undo.
- Ephemeral debug containers: a temporary container attached to a running Pod, for images with no shell. Why: debug distroless .NET images safely.
- Runbook habit: write each incident as symptom, command, cause, fix.
- Commands to memorize:
- kubectl get pods -n NS -o wide
- kubectl describe pod POD -n NS
- kubectl logs POD -n NS --previous
- kubectl get events -n NS --sort-by=.lastTimestamp
- kubectl rollout undo deployment/NAME -n NS
- kubectl debug -it POD --image=busybox --target=CONTAINER

5 Core focus (exam and interview)
- Standard order: get, describe, events, logs, then exec or debug.
- Read the status first: it tells you which family of problem it is.
- Exit code 137 means killed, usually OOM. Exit code 1 usually means the app threw an error.
- Liveness restarts; readiness only removes from traffic.
- Pending is a scheduling problem, not an app problem.
- A Service with empty endpoints means a label or readiness problem.
- Default pull behaviour and the latest tag cause surprise image changes (verify defaults for your version).
- Base64 in a Secret is encoding, not protection.

6 Real-world use case
- Situation: after a release on AKS, an order API shows CrashLoopBackOff in one namespace.
- Steps: describe shows exit code 1; logs --previous shows a missing connection string key from a Secret; the key was renamed in the pipeline.
- Choice: fix the Secret reference and redeploy; rollout undo was used first to restore service in minutes.
- Trade-off: rollback is fast but hides the cause; always capture logs and events before rolling back.
- When not to use exec or debug: do not change files inside a running Pod to fix it. The change is lost on restart and hides drift. Fix the image or manifest.

7 Interview lens
- Q: A Pod is Pending. What do you check? A: describe pod and read the scheduler event. Then check requests, taints, node capacity and PVC binding.
- Q: Difference between liveness and readiness failures? A: Liveness failure restarts the container. Readiness failure keeps it running but removes it from Service endpoints.
- Q: Pod shows OOMKilled but the app looks fine. Why? A: The container limit was lower than real peak memory. Check limits, GC settings and leaks, then size from measured use.
- Q: Users get errors but all Pods are Running. Where next? A: Check Service endpoints, readiness, ingress rules, DNS and recent rollout. Running does not mean ready.

8 Common mistakes
- Deleting the Pod before reading logs: the evidence is gone. Fix: logs and describe first, use --previous.
- Setting liveness probe too aggressive: healthy slow apps get restarted in a loop. Fix: add a startup probe and realistic timings.
- Memory limit equal to request with no headroom: random OOMKilled. Fix: measure and leave margin.
- Using latest tag: a restart pulls a different image. Fix: version plus git SHA tags.
- Debugging by editing live objects: drift from Git. Fix: change manifests and redeploy.
- Not checking the namespace: you look at the wrong Pods. Fix: always pass -n or set the context namespace.

9 Mental model
- Walk the Pod's life like a pipeline and find the stage where it stopped:
- scheduled (Pending) -> image pulled (ImagePullBackOff) -> config loaded (CreateContainerConfigError) -> process started (CrashLoopBackOff, OOMKilled) -> probes pass (Ready) -> Service endpoints -> traffic.

10 Mini lab
Time: about 30 minutes. Tools: Docker Desktop with Kubernetes, or minikube or kind (local, free).
- Step 1: kubectl create namespace lab
- Step 2: kubectl create deployment bad-image --image=nginx:doesnotexist -n lab
- Step 3: kubectl get pods -n lab, wait for ImagePullBackOff, then run describe pod and read the Events. Fix with kubectl set image deployment/bad-image nginx=nginx:1.27 -n lab (verify tag).
- Step 4: kubectl create deployment crasher --image=busybox -n lab -- sh -c "exit 1". Watch CrashLoopBackOff, read logs --previous.
- Step 5: create a Pod with a memory limit of 10Mi running a memory-hungry command, for example stress. Confirm OOMKilled in describe.
- Step 6: create a Service with a selector that does not match any Pod label. Run kubectl get endpoints -n lab and see it is empty. Fix the selector.
- Expected result: you see each status once and can name the command that explains it.
- Clean-up: kubectl delete namespace lab

11 Revision summary
- Order: get, describe, events, logs (--previous), exec or debug.
- Pending means scheduling; ImagePullBackOff means image or registry access; CrashLoopBackOff means the app keeps exiting.
- OOMKilled equals exit code 137 and a memory limit problem.
- Liveness restarts, readiness removes from endpoints, startup protects slow starters.
- Empty Service endpoints mean selector or readiness mismatch.
- NotReady node: describe node, cordon, drain, replace.
- Roll back first to restore service, but save logs and events before.
- Write every incident into a runbook: symptom, command, cause, fix.
