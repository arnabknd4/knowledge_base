8.06 Networking and exposure [P2 R E L] is a new topic for you (no K tag), so this is a FULL note with a mini lab.

---

1 What is it

- Pods in Kubernetes get their own IP addresses, but those IPs change every time a Pod is recreated. Networking and exposure is how other Pods and outside users reach your app reliably.
- A Service gives a set of Pods one stable name and IP. An Ingress routes outside HTTP traffic to Services by host and path.
- Legacy equivalent: a load balancer VIP plus IIS bindings and host headers in front of a web farm, with DNS entries for each site.

2 Why needed

- Pods are temporary. Without a stable address, every caller breaks when a Pod restarts or scales.
- Without exposure rules, nothing outside the cluster can reach your app, or everything inside can reach everything.
- Without TLS handling, each app must manage its own certificates.

3 Before you read

- Pod: the smallest unit that runs your container, with its own IP.
- Label and selector: a tag on a Pod, and a rule that finds Pods by that tag.
- Reverse proxy: a server that receives requests and forwards them to backends (like IIS ARR or Nginx).
- DNS name: a text name that resolves to an IP address.

4 Features and core concepts

- Service ClusterIP: a stable virtual IP reachable only inside the cluster. This is the default type. It matters because internal service-to-service calls use it.
- Service NodePort: opens the same port on every node (default range 30000-32767) (verify). It matters for quick tests; rarely used in production.
- Service LoadBalancer: asks the cloud for a public or internal load balancer. In AKS this creates an Azure Load Balancer. It matters because it is the simplest way to expose one service, but each Service gets its own IP and cost.
- Cluster DNS: every Service gets a name like orders.shop.svc.cluster.local. It matters because code calls names, never IPs.
- Ingress: rules (host and path) for HTTP and HTTPS routing to Services. It matters because one entry point can serve many apps.
- Ingress controller: the actual proxy (for example Nginx, or the AKS application routing add-on) that reads Ingress rules and does the work. An Ingress object does nothing without a controller.
- Gateway API awareness: the newer, more expressive replacement for Ingress, with separate roles for platform and app teams.
- NetworkPolicy: firewall rules between Pods (who may talk to whom). By default all Pods can talk to all Pods. Needs a network plugin that enforces it.
- TLS and cert-manager: cert-manager requests and renews certificates (for example from Let's Encrypt) and stores them as Secrets that Ingress uses. It matters because manual renewals cause outages.
- AKS networking: kubenet gives Pods IPs from a separate range with NAT. Azure CNI gives Pods real VNet IPs, so plan address space. Azure CNI Overlay gives Pods overlay IPs and saves VNet space. Check current defaults and retirement status of kubenet (verify).
- Internal vs external load balancers: external gets a public IP. Internal gets a private VNet IP, set with an annotation (service.beta.kubernetes.io/azure-load-balancer-internal: "true"). It matters for private APIs.
- Worth memorizing: kubectl expose deployment web --port=80 --type=ClusterIP

5 Core focus (exam and interview)

- Most asked: ClusterIP vs NodePort vs LoadBalancer, and Service vs Ingress.
- Service finds Pods by label selector. Wrong labels mean no endpoints.
- Ingress needs a controller. LoadBalancer is layer 4, Ingress is layer 7.
- Default is allow-all between Pods. A NetworkPolicy selecting a Pod makes it deny anything not allowed.
- Azure CNI: plan IPs per node and Pod. Overlay avoids this.
- Internal load balancer for private apps. Public one for internet apps.
- Exam likely: choose the networking model for IP exhaustion, or expose a service privately.

6 Real-world use case

- Situation: you migrate an IIS-hosted order system to AKS as three services (web, orders, payments) on .NET.
- Choice: ClusterIP for orders and payments, one Ingress with the application routing add-on for web at shop.company.com, cert-manager for TLS, NetworkPolicy so only orders can call payments. Azure CNI Overlay because the VNet is shared with other teams and IPs are scarce.
- Trade-off: more moving parts than App Service (controller, cert-manager, policies) in exchange for control and one entry point.
- When NOT to use it: a single small web app. App Service or Container Apps is simpler.

7 Interview lens

- Q: Why not use Pod IPs directly? A: Pod IPs change on restart and scale. A Service gives a stable IP and DNS name and load balances across ready Pods.
- Q: Ingress vs LoadBalancer Service? A: LoadBalancer is layer 4, one IP per service. Ingress is layer 7 routing by host and path through one entry point, but needs a controller.
- Q: Azure CNI vs kubenet vs Overlay? A: CNI gives Pods VNet IPs (direct reach, more IP planning). Kubenet uses NAT and a separate Pod range. Overlay keeps Pod IPs out of the VNet, saving address space.
- Q: How do you restrict Pod traffic? A: NetworkPolicy with a default deny, then allow specific sources by label. Needs a policy-capable network plugin.

8 Common mistakes

- Service selector does not match Pod labels. Shows as a Service with no endpoints and connection refused. Fix: compare labels, run kubectl get endpoints.
- Creating an Ingress with no controller installed. Shows as no address assigned. Fix: install a controller first.
- One LoadBalancer Service per app. Shows as many public IPs and rising cost. Fix: put apps behind one Ingress.
- Undersized subnet with Azure CNI. Shows as Pods stuck Pending or scale-out failing. Fix: plan IP ranges, or use Overlay.
- Assuming NetworkPolicy works everywhere. Policies are ignored if the plugin does not enforce them. Fix: enable a policy engine on the cluster.
- Expired TLS certificates. Shows as browser warnings. Fix: use cert-manager with auto renewal.

9 Mental model

Internet -> Load Balancer (public IP) -> Ingress controller (Pod, reads rules) -> Service (stable name) -> Pods (labels match)
Inside the cluster: Pod -> DNS name -> Service ClusterIP -> Pod
NetworkPolicy is the firewall between the Pod boxes.

10 Mini lab (30 minutes, local)

Tools: Docker Desktop, kind or minikube, kubectl.

- Create a cluster: kind create cluster --name net-lab
- Deploy two Pods: kubectl create deployment web --image=nginx --replicas=2
- Expose it: kubectl expose deployment web --port=80 (ClusterIP by default)
- Test from inside: kubectl run tester --rm -it --image=busybox -- wget -qO- http://web
- Expected: the nginx welcome page HTML prints.
- Break it: kubectl label pod -l app=web app=broken --overwrite, then repeat the wget and check kubectl get endpoints web. Expected: endpoints empty and the call fails or hangs. Restore the label to see it work again.
- Optional: apply a default-deny NetworkPolicy and repeat the test. On a default kind cluster the policy may not be enforced, which shows the "plugin must enforce it" point.
- Clean-up: kubectl delete deployment web; kubectl delete service web; kind delete cluster --name net-lab

11 Revision summary

- Pod IPs are temporary. A Service is the stable address, found by label selector.
- Service types: ClusterIP (internal, default), NodePort (node port), LoadBalancer (cloud LB, layer 4).
- Ingress is layer 7 routing and needs an Ingress controller to work.
- Cluster DNS name format: service.namespace.svc.cluster.local.
- Default Pod networking is allow-all. NetworkPolicy restricts it and needs enforcement support.
- cert-manager automates TLS certificate issue and renewal.
- AKS: kubenet (NAT), Azure CNI (VNet IPs), Overlay (saves IPs) (verify current status).
- Internal load balancer uses a private IP via annotation. External uses a public IP.
