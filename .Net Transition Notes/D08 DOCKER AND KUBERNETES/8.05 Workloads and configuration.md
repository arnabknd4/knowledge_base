1 What is it
- A Pod is the smallest deployable unit in Kubernetes. It holds one or more containers that share network and storage.
- A Deployment keeps a set of identical Pods running and handles updates. It manages ReplicaSets, which hold the Pod count steady.
- StatefulSet, DaemonSet, Job and CronJob cover Pods that need stable identity, one per node, or run-to-completion work.
- ConfigMap and Secret hold settings outside the image. Probes, requests and limits tell Kubernetes how to check and size Pods.
- Legacy equivalent: IIS app pool with web.config, plus a Windows service or scheduled task for background work, and a load balancer rotating servers during deployment.

2 Why needed
- Containers alone do not restart, scale or roll out safely. Kubernetes workload objects add this.
- Without Deployments, a crashed Pod stays dead and an update means downtime.
- Without requests and limits, one noisy Pod starves its neighbours on the same node.
- Without probes, traffic reaches Pods that are still starting or are stuck.
- Without config separated from the image, you rebuild the image for every environment.

3 Before you read
- Container image: a packaged app with its dependencies, from note 8.01.
- Node: a VM that runs Pods. A cluster is a group of nodes.
- Declarative model: you describe the desired state and Kubernetes works to match it (note 8.04).
- Label: a key-value tag on an object, used to select groups of objects.

4 Features and core concepts
- Pod lifecycle: phases are Pending, Running, Succeeded, Failed, Unknown. Pending means not yet scheduled or image still pulling. Why it matters: the phase is the first thing you read when debugging.
- Deployment: declares the desired Pod count and template, and manages updates. Why it matters: it is the default for stateless .NET APIs.
- ReplicaSet: keeps the exact number of Pods alive. Why it matters: Deployments create one per version, which is how rollback works.
- Rolling update and rollback: new Pods replace old ones gradually, controlled by maxSurge and maxUnavailable. Why it matters: zero-downtime releases. Rollback command: kubectl rollout undo deployment/api
- StatefulSet: Pods with stable names, stable storage and ordered start. Why it matters: databases and brokers that need identity.
- DaemonSet: one Pod on every node (or selected nodes). Why it matters: log shippers and monitoring agents.
- Job: runs a Pod until it completes successfully. Why it matters: one-off tasks like data migrations.
- CronJob: creates Jobs on a schedule. Why it matters: replaces scheduled tasks and Windows Task Scheduler.
- ConfigMap: non-secret settings as env vars or mounted files. Why it matters: same image across environments.
- Secret and the limits of base64: Secrets are base64 encoded, which is encoding, not encryption. Anyone with API access can decode them. Why it matters: use encryption at rest and Key Vault with CSI Secrets Store for real protection.
- Init containers: run to completion before the app containers start. Why it matters: wait for a dependency or run setup.
- Sidecars: helper containers in the same Pod sharing network and volumes. Why it matters: logging, proxies, certificate refresh. Newer Kubernetes supports native sidecars (verify version).
- Probes: liveness restarts a stuck container. Readiness removes the Pod from traffic until ready. Startup protects slow starters. Why it matters: a wrong liveness probe causes restart loops. Match these to the .NET health check endpoints from note 3.04.
- Requests and limits: request is the amount the scheduler reserves. Limit is the cap enforced at runtime. Why it matters: CPU over the limit is throttled, memory over the limit is OOMKilled.
- QoS classes: Guaranteed (requests equal limits), Burstable, BestEffort. Why it matters: BestEffort Pods are evicted first under pressure.
- PodDisruptionBudget: limits how many Pods can be down during voluntary disruptions like node upgrades. Why it matters: AKS upgrades do not take all replicas at once.
- Graceful termination: SIGTERM is sent, then the Pod gets terminationGracePeriodSeconds (default 30 seconds) before SIGKILL. Why it matters: .NET must finish in-flight requests, which ties to hosted lifetime shutdown from note 1.02.

5 Core focus (exam and interview)
- Most asked: Deployment vs StatefulSet, the three probes, requests vs limits, and how rolling updates work.
- Defaults to remember: rolling update strategy is the Deployment default. maxSurge and maxUnavailable default to 25% each (verify). Termination grace period is 30 seconds.
- CPU limit means throttling. Memory limit means OOMKilled.
- Readiness failure stops traffic. Liveness failure restarts the container.
- Secrets are base64, not encrypted by default.
- Rollback uses the previous ReplicaSet. History depth is controlled by revisionHistoryLimit (default 10, verify).

6 Real-world use case
- Situation: a .NET order API on AKS, moved from IIS VMs.
- Choice: Deployment with three replicas, readiness probe on /health/ready, liveness on /health/live, requests set at observed average, memory limit set with headroom, PodDisruptionBudget with minAvailable 2. Settings in ConfigMap, connection string pulled from Key Vault via CSI driver. A CronJob runs nightly cleanup.
- Trade-off: more YAML and more concepts than App Service. You gain fine control over scaling and rollout.
- When not to use: small teams with a few simple web apps. App Service or Container Apps is cheaper to operate (see note 8.11).

7 Interview lens
- Q: Deployment or StatefulSet for a SQL-like database?
  A: StatefulSet for stable identity and storage. In Azure, prefer managed Azure SQL over running it in Pods.
- Q: Liveness vs readiness probe?
  A: Liveness restarts a stuck container. Readiness only removes it from Service traffic.
- Q: What happens when a container exceeds its memory limit?
  A: It is OOMKilled and restarted. Exceeding the CPU limit only throttles it.
- Q: Are Kubernetes Secrets secure?
  A: Base64 is not encryption. Enable encryption at rest, restrict RBAC, and use Key Vault with CSI Secrets Store.

8 Common mistakes
- Liveness probe calls a dependency like the database. A database blip restarts every Pod. Fix: liveness checks only the process, readiness checks dependencies.
- No requests or limits. A node runs out of memory and random Pods die. Fix: set both from measured load.
- Memory limit too close to .NET usage. Pods OOMKill during GC spikes. Fix: add headroom and test under load.
- Using the latest tag. Rollouts do not pull or roll back predictably. Fix: use versioned tags or digests.
- Ignoring SIGTERM. Requests drop during deployments. Fix: handle graceful shutdown and set a suitable grace period.
- Single replica with no PodDisruptionBudget. Node upgrade causes an outage. Fix: run at least two replicas with a budget.

9 Mental model
- Deployment (the manager)
  -> ReplicaSet (the headcount)
  -> Pods (the workers) with containers inside
- ConfigMap and Secret are the instruction sheets handed to the workers.
- Probes are the supervisor's checks. Requests and limits are the desk space each worker gets.

10 Mini lab
Time: 30 minutes. Tools: Docker Desktop with Kubernetes enabled, or kind or minikube (all free).
- Step 1: kubectl create deployment web --image=nginx:1.25 --replicas=3
- Step 2: kubectl get pods and confirm three Pods Running.
- Step 3: kubectl set image deployment/web nginx=nginx:1.26 then watch with kubectl rollout status deployment/web
- Step 4: kubectl rollout undo deployment/web and confirm the old image with kubectl describe deployment web.
- Step 5: kubectl create configmap app-cfg --from-literal=MODE=dev, then kubectl get configmap app-cfg -o yaml.
- Step 6: kubectl create secret generic db --from-literal=pwd=abc123, then kubectl get secret db -o jsonpath='{.data.pwd}' | base64 -d. You should see abc123, which proves base64 is not encryption.
- Step 7: delete one Pod with kubectl delete pod <name> and watch the Deployment replace it.
- Expected result: three Pods always running, update and rollback both succeed, the secret decodes in plain text.
- Clean-up: kubectl delete deployment web, kubectl delete configmap app-cfg, kubectl delete secret db.

11 Revision summary
- Deployment manages ReplicaSets, which manage Pods. Rollback switches back to the old ReplicaSet.
- StatefulSet gives stable identity and storage. DaemonSet runs one Pod per node.
- Job runs to completion. CronJob creates Jobs on a schedule.
- Readiness controls traffic. Liveness controls restarts. Startup protects slow starts.
- CPU limit throttles. Memory limit kills (OOMKilled).
- QoS order of eviction: BestEffort first, Guaranteed last.
- Secrets are base64, not encrypted. Use Key Vault with CSI Secrets Store.
- PodDisruptionBudget protects availability during voluntary disruptions. Default grace period is 30 seconds.
