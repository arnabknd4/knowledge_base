1 What is it
- Kubernetes storage and scaling cover how pods keep data (PV, PVC, StorageClass, CSI) and how workloads and nodes grow or shrink on demand (HPA, VPA, KEDA, cluster autoscaler, node pools, scheduling rules).
- A pod is disposable and its local disk dies with it. Persistent storage is a separate object that outlives the pod.
- Scaling means changing the number of pods, the size of pods, or the number of nodes.
- PV (PersistentVolume): a piece of real storage in the cluster.
- PVC (PersistentVolumeClaim): a pod's request for storage.
- StorageClass: a recipe that creates storage on demand.
- CSI (Container Storage Interface): the plugin standard that lets Kubernetes talk to storage systems.
- HPA: Horizontal Pod Autoscaler. VPA: Vertical Pod Autoscaler. KEDA: Kubernetes Event-Driven Autoscaler.
- Legacy equivalent: SAN or file-share mounts on IIS servers, plus adding web servers to a farm behind a load balancer or resizing the VM by hand.

2 Why needed
- Containers are ephemeral. Without persistent volumes, a database pod restart loses all data.
- Without autoscaling, you size for peak and pay all month, or you size for average and fall over at peak.
- Without scheduling rules, all replicas can land on one node or one zone, and a single failure takes the service down.
- Without capacity planning, pods sit in Pending because no node has room.

4 Features and core concepts
- PV: a cluster-level storage object, either created by an admin or created automatically. Why: it decouples the storage lifecycle from the pod lifecycle.
- PVC: a namespaced request stating size, access mode and class. Why: developers ask for storage without knowing the backend.
- StorageClass: names a provisioner, disk type and reclaim policy. Why: enables dynamic provisioning, so no one creates disks by hand. Reclaim policy Delete removes the disk with the PVC; Retain keeps it.
- CSI: a driver model that moved storage code out of Kubernetes core. Why: AKS uses CSI drivers for Azure Disk and Azure Files, and snapshots and expansion depend on it.
- Access modes: ReadWriteOnce (one node), ReadOnlyMany, ReadWriteMany (many nodes), ReadWriteOncePod. Why: wrong mode means pods cannot attach.
- Azure Disk: block storage, attached to one node at a time (RWO), zone-bound, low latency. Why: right for databases and single-writer workloads.
- Azure Files: SMB or NFS share, supports RWX, higher latency. Why: right for shared content across many pods.
- HPA: adds or removes pod replicas based on metrics (CPU, memory, custom). Why: handles variable traffic for stateless services. It needs resource requests set to compute percentages.
- VPA: adjusts the requests and limits of pods. Why: right-sizing for workloads that cannot scale out. Do not combine it with HPA on the same CPU or memory metric.
- KEDA: scales on event sources such as Service Bus queue length, and can scale to zero. Why: queue workers should scale on backlog, not CPU. It feeds HPA under the hood.
- Cluster autoscaler: adds nodes when pods are Pending for lack of room, removes underused nodes. Why: pod scaling is useless without node capacity.
- Node pools: groups of identical nodes. System pool runs core components. User pools run your apps. Spot pools use cheap evictable VMs. Why: separate cost, size and failure domains.
- Affinity: attract pods to nodes or to other pods. Anti-affinity: keep pods apart.
- Taints and tolerations: a taint repels pods from a node unless the pod tolerates it. Why: reserve nodes for special workloads.
- Topology spread constraints: spread replicas across zones or nodes evenly. Why: survive a zone failure.
- Capacity planning: estimating pods per node, node counts and headroom from requests, not from actual usage. Why: avoids Pending pods and overspend.
- Worth memorizing: kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10

5 Core focus (exam and interview)
- Most asked: HPA vs VPA vs KEDA vs cluster autoscaler, and which one scales what.
- Most asked: Azure Disk (RWO, zonal) vs Azure Files (RWX).
- Most asked: why a pod is stuck Pending after HPA scales (no node capacity, or PVC zone mismatch).
- Remember: HPA needs metrics-server and CPU requests set. Default HPA target is commonly 80 percent CPU (verify).
- Remember: StorageClass default reclaim policy is Delete for dynamic volumes.
- Remember: cluster autoscaler reacts to Pending pods, not to CPU usage.
- Remember: AKS needs at least one system node pool. Spot pools are user pools only (verify).
- Remember: StatefulSet uses volumeClaimTemplates to give each replica its own PVC.

6 Real-world use case
- Situation: an order-processing system on AKS has a .NET API and a worker that reads Azure Service Bus. Traffic spikes at sales events.
- Choice: HPA on the API (CPU 70 percent, min 3, max 20). KEDA on the worker, scaling on queue length, down to zero overnight. Cluster autoscaler on a user node pool. Topology spread across three zones. Report files written to Azure Files so any pod can read them.
- Trade-off: KEDA and autoscaler add moving parts and scale-up delay of a few minutes while nodes boot, so keep warm minimum replicas for the API.
- When not to use: do not autoscale a single-writer database pod. Do not use Azure Files for latency-sensitive database files. Do not scale on CPU when the real bottleneck is a downstream database.

7 Interview lens
- Q: HPA or VPA? A: HPA changes replica count and suits stateless services. VPA changes pod size and suits workloads that cannot scale out. Avoid both on the same metric.
- Q: Why scale a queue worker with KEDA? A: Queue depth shows real backlog, CPU does not. KEDA can also scale to zero.
- Q: A pod needs a disk but stays Pending in a multi-zone cluster. Why? A: Azure Disk is zonal. The pod may be scheduled to a different zone than the disk. Use zone-aware binding (WaitForFirstConsumer) or ZRS disks (verify).
- Q: How do you keep replicas alive through a zone outage? A: Topology spread constraints plus a node pool across zones and a PodDisruptionBudget.

8 Common mistakes
- No resource requests: HPA shows unknown and never scales. Fix: set requests on every container.
- HPA scaled pods but nodes full: pods Pending. Fix: enable cluster autoscaler and set max node count high enough.
- Azure Disk on a Deployment with several replicas: second pod fails to attach. Fix: use StatefulSet or Azure Files.
- Reclaim policy Delete on important data: deleting the PVC deletes the disk. Fix: Retain for critical volumes, and take snapshots.
- Spot nodes for stateful or critical pods: sudden eviction. Fix: spot only for interruptible jobs, with tolerations.
- Requests set far above real usage: low density, high bill. Fix: use VPA recommendations or measured usage.

9 Mental model
- Pod = tenant, node = flat, PVC = rental request, PV = the actual storage room, StorageClass = the agency that builds rooms on demand.
- Scaling ladder: more pods (HPA, KEDA) -> bigger pods (VPA) -> more nodes (cluster autoscaler).
- Rule: pods scale first, nodes follow when pods cannot be placed.

10 Mini lab
- Time: about 30 minutes. Tools: local Docker Desktop with kind, or minikube. No Azure cost.
- Step 1: create a cluster: kind create cluster
- Step 2: install metrics-server (kind needs the --kubelet-insecure-tls argument) (verify).
- Step 3: apply a Deployment named web using nginx with requests cpu 100m and limits cpu 200m.
- Step 4: create a PVC of 1Gi with the default StorageClass, mount it in a pod, write a file, delete the pod, recreate it, and confirm the file remains.
- Step 5: run kubectl autoscale deployment web --cpu-percent=50 --min=1 --max=5
- Step 6: generate load with a busybox pod running a wget loop against the web service.
- Expected result: kubectl get hpa shows CPU rising above target and replicas increasing toward 5. After load stops, replicas fall back after the cooldown (several minutes). The file in the PVC survives pod deletion.
- Clean-up: kubectl delete deployment web, delete the PVC and pods, then kind delete cluster.

11 Revision summary
- PVC requests storage, PV is the storage, StorageClass creates it dynamically, CSI is the driver layer.
- Azure Disk: RWO, zonal, fast. Azure Files: RWX, shared, slower.
- HPA scales replicas, VPA scales pod size, KEDA scales on events and can reach zero.
- Cluster autoscaler adds nodes only when pods are Pending.
- HPA requires resource requests and metrics-server.
- Node pools: system, user, spot. Spot is for interruptible work only.
- Taints repel, tolerations allow, affinity attracts, topology spread distributes across zones.
- Capacity plan from requests, with headroom for zone loss and upgrades (surge).
