1 What is it
- A container is a normal Linux process that the kernel isolates from other processes. It sees its own filesystem, network and process list, and it has CPU and memory limits.
- An image is the read-only package a container starts from. It holds your app, the runtime and its libraries.
- A VM (virtual machine) is a full guest operating system on virtual hardware. A container shares the host kernel, so it is smaller and starts in seconds.
- Legacy equivalent: an MSDeploy or Web Deploy package plus a hand-built IIS server, except the server setup travels inside the package.

2 Why needed
- "Works on my machine" failures come from different runtime versions, missing libraries and config drift between dev, test and production.
- An image is built once and runs the same everywhere, so environments stop drifting.
- Without containers, each server is hand-configured, deployments are slow, and rollback means rebuilding a server.
- Containers pack many apps on one host with limits, which cuts cost compared with one VM per app.
- Kubernetes, AKS, Container Apps and App Service containers all assume you have an image.

3 Before you read
- Process: a running program with its own memory.
- Kernel: the core of the OS that manages processes, memory, network and disk.
- Basic Linux filesystem and command line (see 16.01).
- .NET publish output: the folder dotnet publish produces.

4 Features and core concepts
- Containers vs VMs: containers share the host kernel; VMs each run their own OS. Why it matters: containers are lighter, but isolation is weaker than a VM, and a Linux container needs a Linux kernel.
- Namespaces: a kernel feature that gives a process its own private view of things like process IDs, network and mounts. Why it matters: this is what makes a container feel like its own machine.
- cgroups (control groups): a kernel feature that limits CPU, memory and IO for a group of processes. Why it matters: it stops one container from starving others, and an exceeded memory limit gets the container killed (OOMKilled).
- Images and layers: an image is a stack of read-only layers, one per Dockerfile instruction that changes files. Why it matters: layers are cached and shared, so unchanged layers rebuild and pull fast.
- Registries: a server that stores images, such as Docker Hub or Azure Container Registry. Why it matters: it is the hand-off point between build and deploy.
- Tags vs digests: a tag (app:1.4) is a movable label. A digest (sha256:...) is a fixed content hash. Why it matters: tags can be overwritten, so production should pin a digest or a unique tag.
- FROM: picks the base image. Why it matters: it sets the OS, runtime and size.
- COPY: copies files from your build context into the image. Why it matters: copy dependency files before source code to use layer caching.
- RUN: runs a command at build time and saves the result as a layer. Why it matters: chain related commands to avoid extra layers and leftover files.
- ENTRYPOINT vs CMD: ENTRYPOINT is the fixed executable. CMD is the default arguments, which are easy to override. Why it matters: use the exec form (JSON array) so the app receives stop signals.
- ENV vs ARG: ENV is set at runtime and in the image. ARG exists only at build time. Why it matters: never put secrets in either, because they stay visible in image history.
- EXPOSE: documents the port the app listens on. Why it matters: it does not publish the port. Publishing happens with -p at run time.
- USER: sets which user runs the process. Why it matters: running as root inside the container raises the damage from an escape or bug.
- HEALTHCHECK: a command Docker runs to test whether the app is healthy. Why it matters: it marks a container unhealthy, though Kubernetes uses its own probes instead.
- Multi-stage builds for .NET: build in the SDK image, then copy only the published output into the smaller ASP.NET runtime image. Why it matters: the final image drops compilers and source, so it is smaller and safer.
- Layer caching: Docker reuses a layer if the instruction and its inputs are unchanged. Why it matters: put rarely changing steps first, such as dotnet restore before copying source.
- .dockerignore: lists files left out of the build context. Why it matters: it keeps bin, obj, .git and secrets out of the image and speeds up builds.
- Non-root user: a user that is not root runs the app. Why it matters: it is a basic hardening step. Recent .NET images ship a non-root user (verify).
- Image size: the total size of all layers. Why it matters: small images pull faster and have fewer packages to patch.
- BuildKit: the modern build engine with parallel stages, better caching and build secrets. Why it matters: it is the default in current Docker (verify), and it can pass secrets without leaving them in a layer.
- Worth memorizing (multi-stage .NET):
  FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build (verify tag)
  COPY *.csproj . / RUN dotnet restore / COPY . . / RUN dotnet publish -c Release -o /out
  FROM mcr.microsoft.com/dotnet/aspnet:10.0 / COPY --from=build /out . / USER app
  ENTRYPOINT ["dotnet", "MyApp.dll"]

5 Core focus (exam and interview)
- Most asked: container vs VM, how an image is built from layers, why multi-stage builds, ENTRYPOINT vs CMD, and tag vs digest.
- Namespaces isolate what a process can see. cgroups limit what it can use. Know both.
- Containers share the host kernel, so a Linux container cannot run on a Windows kernel without a Linux VM layer.
- A container is ephemeral. Data written inside is lost when it is removed, so use volumes (8.02).
- Latest is only a tag name. It is not a guarantee of newest, and it is a bad production tag.
- Default Dockerfile user is root unless you set USER.
- Exam link: AZ-104 and AZ-305 expect you to pick Container Instances, Container Apps, App Service or AKS (see 8.11).

6 Real-world use case
- Situation: a legacy MVC app is being moved to ASP.NET Core and must run the same in dev, test and Azure.
- Choice: a multi-stage Dockerfile, non-root user, .dockerignore, image pushed to Azure Container Registry with a version plus git SHA tag, then run on Container Apps or App Service.
- Trade-off: you take on image patching, registry management and a new build step in the pipeline in return for repeatable deployments and fast rollback.
- When NOT to use it: a tiny internal app that never moves from one stable server, or a workload tied to Windows-only components that needs Windows containers and a heavier setup.

7 Interview lens
- Q: Container vs VM?
  A: A VM virtualizes hardware and runs its own OS. A container isolates a process on the host kernel using namespaces and cgroups, so it is lighter but shares the kernel.
- Q: Why multi-stage builds?
  A: They keep the SDK, source and build tools out of the final image. The result is smaller, faster to pull and has less attack surface.
- Q: ENTRYPOINT vs CMD?
  A: ENTRYPOINT is the program that always runs. CMD gives default arguments that can be overridden at docker run.
- Q: Why not deploy by tag latest?
  A: A tag can point to a different image tomorrow. Deploy a unique tag or digest so every release is traceable and rollback is exact.

8 Common mistakes
- Secrets in ENV, ARG or COPY: they stay in image layers and history. Fix: inject at runtime or use BuildKit secrets.
- Running as root: a bug becomes a bigger breach. Fix: add USER.
- Copying source before restore: every code change reruns restore. Fix: copy csproj first, restore, then copy the rest.
- Shell-form ENTRYPOINT: the app misses SIGTERM and shutdown is not graceful. Fix: use the exec form.
- Using latest in production: a rebuild silently changes what runs. Fix: pin version plus git SHA or digest.
- No .dockerignore: huge slow builds with bin, obj and .git inside. Fix: add one.
- Storing data in the container filesystem: data vanishes on restart. Fix: use volumes or external storage.

9 Mental model
- Image = recipe-plus-ingredients frozen in layers (read-only).
- Container = one running instance of that image, with a thin writable layer on top.
- Host kernel (shared)
    -> namespaces: what it can see
    -> cgroups: how much it can use
    -> image layers: what files it starts with

10 Mini lab
- Time: about 30 minutes. Needs Docker Desktop or Docker Engine and the .NET SDK. No Azure needed.
- Steps:
  - dotnet new webapi -n LabApp, then cd LabApp
  - Create a .dockerignore containing: bin, obj, .git
  - Create a Dockerfile using the multi-stage pattern in section 4. Match the SDK tag to your installed version (verify).
  - docker build -t labapp:1 .
  - docker run --rm -p 8080:8080 labapp:1 (the port depends on the .NET version, so check the startup log)
  - Open the app in a browser or curl it on localhost:8080.
  - docker images labapp, and note the size. Then run docker history labapp:1 and read the layers.
  - Edit one source file, rebuild, and watch the restore layer show CACHED.
- Expected result: the app responds, the image is a few hundred MB at most, and the rebuild reuses the restore layer.
- Clean-up: docker rmi labapp:1, then docker image prune.

11 Revision summary
- A container is an isolated process on the shared host kernel, not a VM.
- Namespaces isolate the view. cgroups limit resources.
- An image is read-only layers. A container adds a thin writable layer.
- A tag moves. A digest does not. Never rely on latest.
- Multi-stage builds: SDK image to build, aspnet image to run.
- Copy csproj and restore first to use layer caching.
- Use exec-form ENTRYPOINT, USER non-root and a .dockerignore.
- Never put secrets in ENV, ARG or image layers.
