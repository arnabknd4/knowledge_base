1 What is it
- Helm is the package manager for Kubernetes. A chart is a folder of templated Kubernetes YAML plus a values file. Helm renders the templates with your values and installs the result as one release.
- Template: a YAML file with placeholders. Values: the settings that fill the placeholders. Release: one named, versioned install of a chart in a cluster.
- Legacy equivalent: Web.config transforms plus MSDeploy or Octopus packages, one package deployed to many environments with different settings.

2 Why needed
- A real app has many Kubernetes files (Deployment, Service, Ingress, ConfigMap). Copying them per environment causes drift.
- Without Helm there is no single unit to install, upgrade or roll back. You apply files by hand and lose track of what is running.

3 Before you read
- Kubernetes objects: Deployment, Service, ConfigMap, Secret.
- kubectl apply and how manifests are declarative.
- YAML syntax and indentation.
- Container registry basics (ACR).

4 Features and core concepts
- Chart: a package of templates, defaults and metadata. Why it matters: one reusable unit per service.
- Templates: Go-template YAML files in templates/. Why it matters: one file serves every environment.
- values.yaml: default settings, overridden per environment with -f or --set. Why it matters: dev, test and prod differ only by values.
- Helpers (_helpers.tpl): named snippets for repeated labels and names. Why it matters: consistent labels, less copy-paste.
- Release: a named install with a revision number, stored as a Secret in the cluster namespace. Why it matters: Helm knows what it deployed and can compare.
- Upgrade: helm upgrade creates a new revision. Why it matters: changes are tracked, not blind applies.
- Rollback: helm rollback goes back to an earlier revision. Why it matters: fast recovery from a bad deploy.
- OCI chart repositories: charts stored in a registry such as ACR, same as images. Why it matters: one registry, one auth model, versioned charts.
- Kustomize overlays: patch base manifests per environment without templates. Why it matters: simpler than Helm when you only need small per-environment differences.
- Helm in pipelines: pipeline logs in to the cluster and runs the upgrade. Why it matters: repeatable, audited deployments.
- Secrets handling: CSI Secrets Store driver mounts Key Vault secrets into pods. External Secrets syncs them into Kubernetes Secrets. Why it matters: secrets stay out of values files and Git.
- Worth memorizing:
- helm upgrade --install myapp ./chart -f values-prod.yaml -n prod --atomic
- helm template ./chart -f values-prod.yaml (render without installing)
- helm history myapp -n prod
- helm rollback myapp 2 -n prod

5 Core focus (exam and interview)
- Most asked: install versus upgrade, rollback, values precedence, and Helm versus Kustomize.
- Values precedence, lowest to highest: chart values.yaml, then -f files in order, then --set.
- Helm 3 has no Tiller. Release state lives in the cluster as Secrets by default.
- --atomic rolls back automatically if the upgrade fails. --wait waits for readiness.
- helm template and helm lint catch errors before deploy.
- OCI push and pull of charts is supported in Helm 3 (verify the exact commands for your Helm version).
- Rollback does not undo database changes or external state.

6 Real-world use case
- Situation: you split a legacy .NET monolith into six services on AKS. Each has a Deployment, Service, Ingress and ConfigMap, for dev, test and prod.
- Choice: one shared base chart, with one values file per service per environment. The pipeline pushes the chart to ACR as an OCI artifact and runs helm upgrade --install --atomic. Secrets come from Key Vault through the CSI driver.
- Trade-off: Go templates get hard to read and debug as logic grows. Teams must version and maintain the chart.
- When NOT to use it: one or two simple services, or only small per-environment patches. Plain manifests or Kustomize is simpler. Also avoid it when the team cannot yet read Kubernetes YAML.

7 Interview lens
- Q: Helm versus Kustomize?
- A: Helm templates and packages with versioned releases and rollback. Kustomize patches plain YAML with overlays and has no templating or release history.
- Q: How do you roll back a bad release?
- A: helm history to find the last good revision, then helm rollback. Better still, use --atomic in the pipeline so failures revert automatically.
- Q: How do you keep secrets out of Helm values?
- A: Store them in Key Vault and mount them with the CSI Secrets Store driver, or sync them with External Secrets. Values files hold only references.
- Q: Where is release state stored in Helm 3?
- A: As Secrets in the release namespace, one per revision. There is no Tiller.

8 Common mistakes
- Secrets in values.yaml committed to Git. Shows up as leaked credentials. Fix: Key Vault with CSI or External Secrets.
- Deploying with no --atomic or --wait. Pipeline shows success while pods crash. Fix: add both.
- Using the latest image tag in values. Upgrades do nothing or deploy unknown code. Fix: semver plus git SHA tags.
- Over-templating with deep conditionals. Charts nobody can read. Fix: keep templates simple, split charts.
- Skipping helm template and helm lint in CI. Broken YAML found in production. Fix: run both in the build stage.
- Editing live resources with kubectl after a Helm install. Next upgrade overwrites or conflicts. Fix: change only through Helm.

9 Mental model
- Chart plus values equals rendered YAML, which equals a release with revision numbers.
- chart (template) + values.yaml --helm--> Kubernetes YAML --> release v1, v2, v3
- Rollback means pointing back to an earlier numbered revision.

10 Mini lab
- Time: about 30 minutes. Needs Docker Desktop with Kubernetes, or kind or minikube, plus Helm.
- Step 1: helm create demo
- Step 2: helm lint demo and helm template demo to see rendered YAML.
- Step 3: kubectl create namespace lab, then helm install demo ./demo -n lab.
- Step 4: create prod.yaml with replicaCount: 3. Run helm upgrade demo ./demo -f prod.yaml -n lab.
- Step 5: helm history demo -n lab shows revision 2. Run kubectl get pods -n lab and see 3 pods.
- Step 6: helm rollback demo 1 -n lab. Pods return to 1 replica.
- Expected result: history shows revisions 1, 2 and 3 (the rollback creates revision 3).
- Clean-up: helm uninstall demo -n lab, then kubectl delete namespace lab.

11 Revision summary
- Helm equals chart plus values rendered into Kubernetes YAML as a named release.
- Each upgrade creates a new revision. Rollback restores an earlier one as a new revision.
- Values precedence: chart defaults, then -f files, then --set.
- Helm 3 has no Tiller. Release state is stored as Secrets in the cluster.
- Use --atomic and --wait in pipelines. Run helm lint and helm template in CI.
- Charts can be stored in ACR as OCI artifacts.
- Kustomize patches plain YAML. Helm templates and packages. Pick the simpler one.
- Never put secrets in values files. Use CSI Secrets Store or External Secrets with Key Vault.
