1 What is it
- Kubernetes (K8s) is a system that runs and manages containers across many machines. The control plane is its brain: it decides what should run and where.
- You describe the state you want in files (manifests). Kubernetes keeps comparing the real state with that wish and fixes any difference. This is called reconciliation.
- A cluster has two kinds of machines: control plane (decides) and nodes (run the containers).
Legacy equivalent: IIS web farm plus a load balancer and deployment scripts, but with a self-healing controller that keeps the farm in the shape you declared.

2 Why needed
- Running many containers by hand does not scale. Someone must place them, restart crashed ones, and replace dead machines.
- Without it: a crashed container stays down until a human notices, deployments are scripts that differ per environment, and capacity is guessed.
- Kubernetes gives one API for scheduling, healing, scaling and rollout across all machines.

3 Before you read
- Container: a packaged app with its dependencies, started from an image (see 8.01).
- Image registry: where images are stored and pulled from (see 8.03).
- YAML: the text format used for manifests.
- Basic Linux process and network idea: a node is just a Linux machine.

4 Features and core concepts
Control plane
- API server: the single front door. Every tool (kubectl, controllers, kubelet) talks only to it. It validates and stores requests. Why it matters: one place for auth, audit and rules.
- etcd: a key-value database holding all cluster state. Why it matters: lose it without a backup and you lose the cluster definition.
- Scheduler: picks a node for each new Pod, based on free CPU and memory, affinity and taints. Why it matters: it decides placement, not the node.
- Controller manager: runs many loops, each watching one kind of object and fixing drift (for example, keep 3 replicas). Why it matters: this is where self-healing lives.

Node components
- kubelet: the agent on each node. It gets Pod specs from the API server, tells the runtime to start containers, and reports health. Why it matters: it is the only part that touches containers.
- kube-proxy: sets up network rules so a Service address reaches the right Pods. Why it matters: stable addressing while Pods change.
- Container runtime: the engine that pulls images and runs containers, for example containerd. Docker is no longer the default runtime (verify).

Model and objects
- Declarative model and reconciliation: you say "3 copies of this app", not "start a container". Controllers loop: observe, compare, act. Why it matters: repeatable, and recovery is automatic.
- Namespaces: named partitions inside a cluster for teams or environments. Why it matters: separation of names, quotas and permissions. They are not a hard security wall.
- Labels and selectors: key-value tags on objects, and queries that pick objects by tag. Why it matters: Services, Deployments and policies find Pods through labels, not names.
- kubectl and contexts: kubectl is the command-line client. A context is a saved cluster plus user plus namespace. Why it matters: it prevents running a command against the wrong cluster.
- Manifests: YAML files describing objects (apiVersion, kind, metadata, spec). Why it matters: they live in Git and are the source of truth.
- Kustomize: patches a base manifest per environment without templates, built into kubectl. Why it matters: dev, test and prod differ only by overlays.

Worth memorizing:
- kubectl config get-contexts
- kubectl config use-context <name>
- kubectl apply -f app.yaml
- kubectl get pods -n <ns> -l app=web
- kubectl apply -k overlays/prod

5 Core focus (exam and interview)
- Name the four control plane components and what each does. Most asked.
- Request flow: kubectl to API server, stored in etcd, scheduler picks a node, kubelet on that node starts the Pod.
- Only the API server talks to etcd. Components never talk to each other directly.
- Scheduler only chooses a node. The kubelet starts the container.
- In AKS, the control plane is managed by Azure and you do not see or patch it (verify current SLA tiers for the control plane).
- Namespaces scope names, quotas and RBAC, but do not isolate the network by default.
- Know the default namespaces: default, kube-system, kube-public, kube-node-lease.
- Secrets are base64 encoded, not encrypted, unless encryption at rest is configured (see 8.05).

6 Real-world use case
- Situation: a legacy .NET Framework app is split out into three ASP.NET Core services on AKS. Dev, test and prod are separate namespaces or clusters.
- Choice: one base manifest per service in Git. Kustomize overlays set replicas, image tag and config per environment. An Azure DevOps pipeline runs kubectl apply -k.
- Result: a node dies, the controllers reschedule its Pods on other nodes with no human action.
- Trade-off: you take on learning cost, YAML volume, and cluster operations (upgrades, networking, cost).
- When NOT to use it: one or two small apps, a small team, or no one to own the platform. App Service or Container Apps is simpler (see 8.11).

7 Interview lens
- Q: What happens when you run kubectl apply on a Deployment?
  A: kubectl sends it to the API server, which validates and stores it in etcd. The controller creates Pods, the scheduler assigns nodes, and each kubelet starts the containers.
- Q: What is the difference between the control plane and a node?
  A: The control plane stores state and makes decisions. Nodes run the actual workload containers through kubelet and the runtime.
- Q: What is reconciliation and why does it matter?
  A: Controllers keep comparing desired and actual state and correct drift. That is how crashed Pods and lost nodes get fixed without human action.
- Q: What does etcd hold and how do you protect it?
  A: All cluster state. Back it up and restrict access. On AKS, Azure manages it for you.

8 Common mistakes
- Running kubectl against the wrong cluster: a delete hits production. Fix: check the context first, name contexts clearly, use separate credentials per environment.
- Treating namespaces as security isolation: a Pod reaches another team's service. Fix: add NetworkPolicy and RBAC (see 8.06).
- Editing live objects by hand: the live state drifts from Git and the next apply surprises you. Fix: change manifests in Git only.
- Bad or missing labels: the Service finds no Pods. Fix: check selectors against Pod labels with kubectl get pods --show-labels.
- No etcd backup on self-managed clusters: one failure loses the cluster. Fix: scheduled snapshots, restore tested.

9 Mental model
Think of an airport.
- API server = the control tower desk where all requests arrive.
- etcd = the master flight record.
- Scheduler = the gate assigner.
- Controllers = supervisors checking the board and fixing mismatches.
- Nodes = gates, with kubelet as the gate agent.

  kubectl -> API server <-> etcd
                |
       scheduler, controllers
                |
          kubelet (node) -> runtime -> container

10 Mini lab (30 minutes, local, free)
- Install Docker Desktop and kind (or minikube). Run: kind create cluster --name lab
- Run: kubectl config get-contexts. Expected: a context named kind-lab is current.
- Run: kubectl get nodes -o wide and kubectl get pods -n kube-system. Expected: one node Ready, and pods for etcd, kube-apiserver, kube-scheduler, kube-controller-manager, kube-proxy.
- Create namespace and app: kubectl create namespace demo, then kubectl create deployment web --image=nginx --replicas=2 -n demo.
- Add a label: kubectl label deployment web tier=front -n demo. Run kubectl get pods -n demo -l app=web. Expected: 2 Pods.
- Test self-healing: kubectl delete pod <one-pod-name> -n demo, then kubectl get pods -n demo. Expected: a new Pod appears within seconds.
- Try Kustomize: make a folder with a kustomization.yaml listing a deployment.yaml, then kubectl apply -k . Expected: objects created.
- Clean-up: kubectl delete namespace demo, then kind delete cluster --name lab.

11 Revision summary
- Control plane: API server, etcd, scheduler, controller manager.
- Node: kubelet, kube-proxy, container runtime.
- Only the API server reads and writes etcd.
- Scheduler picks the node. Kubelet starts the container.
- Desired state in YAML, controllers reconcile actual to desired.
- Labels and selectors connect Services and Deployments to Pods.
- Namespaces separate names, quotas and RBAC, not network traffic.
- AKS manages the control plane. You manage node pools and workloads.
