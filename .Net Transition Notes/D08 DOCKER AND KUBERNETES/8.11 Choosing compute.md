1 What is it
- Choosing compute means picking where your application code runs in Azure: App Service, Container Apps, AKS, Functions or VMs.
- App Service is a managed web host: you give it code or a container, Azure runs the servers.
- Container Apps runs containers without making you manage Kubernetes. It scales on events and can scale to zero.
- AKS (Azure Kubernetes Service) is managed Kubernetes. Azure runs the control plane, you run nodes, upgrades and workloads.
- Functions runs small pieces of code when something triggers them (HTTP call, timer, queue message).
- VMs are full servers you own and patch yourself.
- Legacy equivalent: choosing between IIS on a physical or virtual server, a Windows Service, and a scheduled task.

2 Why needed
- Each option trades control against operations work. Picking wrongly costs money, time or both.
- Too much control (AKS for a simple API) means a small team spends its time on cluster upgrades and YAML.
- Too little control (Functions for a long-running stateful job) means hitting limits and rewriting later.
- Interviewers and AZ-305 questions test exactly this reasoning.

3 Before you read
- Container: a package holding your app and its dependencies, so it runs the same everywhere.
- Image: the read-only template a container starts from. A registry stores images.
- Scaling: adding more instances (scale out) or a bigger instance (scale up).
- Stateless: the app keeps no important data in its own memory or disk between requests.

4 Features and core concepts
- App Service vs Container Apps vs AKS vs Functions vs VMs
  - Plain meaning: five hosting models, ordered roughly from least to most control: Functions, App Service, Container Apps, AKS, VMs.
  - Why it matters: you pick by how much you want to operate, not by what is fashionable.
- Decision criteria: control, operations load, scaling, cost, team skill
  - Control: can you change the OS, network layout or runtime? Operations load: who patches, upgrades, monitors? Scaling: how fast and how far, and does it scale to zero? Cost: pay per instance, per execution or per node. Team skill: do you have anyone who knows Kubernetes?
  - Why it matters: team skill is the criterion most often ignored and most often fatal.
- Container Apps: revisions, KEDA scaling, ingress, jobs, Dapr awareness
  - Revision: an immutable snapshot of a version of your app. You can split traffic between revisions for canary or blue-green.
  - KEDA (Kubernetes Event-driven Autoscaling): scales instances from event sources like Service Bus queue length or HTTP load, including down to zero.
  - Ingress: the built-in way to expose your app over HTTP or TCP, internal or external.
  - Jobs: containers that run to completion (batch, scheduled, on demand) instead of staying up.
  - Dapr (awareness only): optional sidecar giving ready-made building blocks like pub/sub and state. Know it exists.
  - Why it matters: it gives most of the microservice benefits of AKS with far less operations work.
- App Service containers
  - Plain meaning: App Service can run your Docker image instead of raw code, on a Linux or Windows plan.
  - Why it matters: a cheap first step for teams that have containers but no Kubernetes skill.
- Migration paths from IIS-hosted monoliths
  - Plain meaning: options for moving an existing IIS app to Azure, from least to most change: rehost on a VM, App Service (code or Windows container), then Container Apps or AKS after modernizing.
  - Why it matters: this is your real job in the Kolkata market. Most legacy estates land on App Service or VMs first.
- Windows containers for legacy .NET Framework
  - Plain meaning: containers built on a Windows base image, the only container route for .NET Framework apps (modern .NET runs in Linux containers).
  - Why it matters: AKS supports Windows node pools and App Service supports Windows containers, but Windows images are large and some services are limited (verify which hosts support them).
- Memorize this decision line: stateless web or API with no special needs, App Service; event-driven or microservices without a platform team, Container Apps; need Kubernetes features or ecosystem, AKS; short event-triggered code, Functions; need OS control or lift and shift, VMs.

5 Core focus (exam and interview)
- Most asked: given a scenario, pick the compute service and justify it by operations load and scaling shape.
- Functions hosting plans differ in scale to zero, cold start, max execution time and VNet support (verify current limits and plan names).
- Container Apps scales to zero; App Service plans do not (the plan is billed while running).
- AKS is the answer when the scenario says custom networking, Kubernetes APIs, operators, service mesh, or an existing Kubernetes team.
- VMs are the answer for unsupported software, full OS access, or lift and shift with minimal change.
- .NET Framework apps: App Service Windows, VMs or Windows containers. Not Linux containers.
- Pricing and SKU limits change often (verify on Microsoft Learn).

6 Real-world use case
- Situation: a Kolkata client has a .NET Framework 4.8 MVC portal on IIS plus a Windows Service that processes queue messages, and a team of six with no Kubernetes experience.
- Choice made: portal to App Service (Windows) as a first move, the Windows Service rewritten as a modern .NET worker in a Container Apps app scaling on Service Bus queue length (KEDA). New APIs go to Container Apps.
- Trade-off: you get low operations work and event scaling, but give up Kubernetes-level control and some networking flexibility.
- When NOT to use: do not use Container Apps or App Service if you need custom kernel modules, privileged containers, or a specific Kubernetes operator. Do not choose AKS just because it looks impressive on a resume.

7 Interview lens
- Q: When AKS over Container Apps?
  - A: When you need the Kubernetes API, custom controllers, service mesh, fine network or node control, or the team already runs Kubernetes. Otherwise Container Apps is cheaper to operate.
- Q: How do you move an IIS monolith to Azure?
  - A: Assess first. Rehost on VMs or App Service for quick wins, then modernize pieces using the strangler approach into Container Apps. Pick by effort, risk and business deadline.
- Q: Why not put everything in Functions?
  - A: Execution time limits, cold starts, hard-to-trace sprawl and cost at constant high load. It suits event-driven glue, not full application backends by default.
- Q: Can .NET Framework run in containers?
  - A: Only as Windows containers. Modern .NET can use Linux containers, which are smaller and cheaper.

8 Common mistakes
- Choosing AKS for a three-service app. Shows up as the team spending weeks on upgrades and ingress instead of features. Fix: start with Container Apps or App Service, move when a real limit appears.
- Ignoring team skill. Shows up as an unmaintained cluster and slow incident response. Fix: score skill as a criterion and plan training before choosing.
- Assuming Functions scales and runs without limits. Shows up as timeouts and cold-start latency. Fix: check hosting plan limits and use a plan or service that suits the workload (verify).
- Forcing legacy .NET Framework into Linux containers. It cannot work. Fix: Windows containers or App Service Windows, or port to modern .NET first.
- Comparing only list price. Shows up as surprise bills from idle always-on plans or egress. Fix: model real load and include operations time.

9 Mental model
- A ladder of responsibility:

  Functions: you write code only
  App Service: you own the app
  Container Apps: you own the container
  AKS: you own the cluster workloads
  VMs: you own the machine

- Move down the ladder only when a concrete need forces you to.

10 Mini lab
- Goal: deploy the same container to App Service and Container Apps and compare. Time: 30 to 40 minutes. Tools: Azure free tier, Azure CLI, a public sample image (mcr.microsoft.com/azuredocs/containerapps-helloworld:latest).
- Steps:
  - az group create -n rg-compute-lab -l centralindia
  - Container Apps: az containerapp up -n hello-ca -g rg-compute-lab --image mcr.microsoft.com/azuredocs/containerapps-helloworld:latest --ingress external --target-port 80
  - App Service: create a Linux plan (az appservice plan create -g rg-compute-lab -n plan-lab --is-linux --sku B1), then az webapp create -g rg-compute-lab -p plan-lab -n <unique-name> --deployment-container-image-name mcr.microsoft.com/azuredocs/containerapps-helloworld:latest
  - Open both URLs. Note setup effort and the pricing page for each (verify SKU availability in your region).
- Expected result: both show the sample page. Container Apps shows revisions and scale rules in the portal; App Service shows plan size and scale settings.
- Clean-up: az group delete -n rg-compute-lab --yes --no-wait

11 Revision summary
- Order of control: Functions, App Service, Container Apps, AKS, VMs.
- Criteria: control, operations load, scaling, cost, team skill.
- Container Apps = revisions plus KEDA scaling (to zero) plus ingress plus jobs; Dapr is optional.
- AKS only when you need Kubernetes features or already have the skill.
- App Service can run containers, a good first step for container beginners.
- IIS monolith path: VM or App Service first, then modernize with strangler into Container Apps or AKS.
- .NET Framework in containers means Windows containers only.
- Limits, SKUs and prices change: always verify on Microsoft Learn.
