1 What is it

Docker runtime commands and local development setup. This is how you run, inspect, network and compose containers on your own machine while building a service.
- A container is a running instance of an image. The image is the packaged app plus its dependencies. Docker is the tool that runs them.
- Docker Compose is a tool that starts several containers together from one YAML file.

Legacy equivalent: IIS Express plus a local SQL Server install and a hand-maintained setup doc, replaced by one docker compose up that gives every developer the same environment.

----

2 Why needed

- The "works on my machine" problem. Legacy teams share a Word document of install steps for SQL Server, Redis and tools. Versions drift between laptops.
- Without runtime skills you cannot see why a container exited, why a port is unreachable or why data vanished after a restart.
- Without Compose, a new joiner needs hours to start the app and its dependencies. With it, one command.

----

3 Before you read

- Image vs container: the image is read-only, the container is a running copy with a thin writable layer.
- Dockerfile basics from note 8.01 (FROM, COPY, ENTRYPOINT).
- Port: a numbered door on a machine that a program listens on.
- YAML: indented key-value text format.

4 Features and core concepts

- run: creates and starts a container from an image. Why: this is the entry point for every container.
  docker run -d --name api -p 8080:8080 myapp:1.0
- exec: runs a command inside an already running container. Why: lets you look inside, like remote desktop into a server.
  docker exec -it api sh
- logs: shows what the container wrote to stdout and stderr. Why: first stop for any failure. Containers should log to the console, not files.
  docker logs -f --tail 100 api
- inspect: prints full JSON details (IP address, mounts, env vars, health state). Why: confirms what Docker actually configured, not what you assumed.
- volumes: storage managed by Docker that outlives the container. Why: the container's own writable layer is deleted with it, so a database without a volume loses data on removal.
- bind mounts: a folder from your host mapped into the container. Why: edit code on your laptop and see it live in the container. Slower on some hosts and tied to host paths.
- bridge network: the default private network on the host. Containers on a user-defined bridge reach each other by name. Why: your API can call "sql" or "redis" by name, with no IP addresses.
- host network: the container shares the host's network stack, so no port mapping. Why: rarely needed; it removes isolation. Not available the same way on Docker Desktop (verify).
- port mapping: -p host:container publishes a container port on the host. Why: without it, nothing outside the container can reach the app. The container port is the right side.
- environment and secrets: -e sets a variable, --env-file loads a file. Why: matches ASP.NET Core config precedence, where environment variables override appsettings. Double underscore maps to nesting: ConnectionStrings__Default. Secrets in env vars are visible in docker inspect, so use them for local dev only.
- Docker Compose: one file describing services, networks and volumes.
  - services: each container to run.
  - healthchecks: a command that tells Docker whether the service is ready, not merely started.
  - networks: named networks; Compose creates a default one so services find each other by service name.
  - volumes: named storage declared once, reused by services.
  - profiles: tags that let optional services (for example a debug tool) start only when asked: docker compose --profile tools up.
  Why: depends_on with condition service_healthy stops your API from starting before SQL Server accepts connections.
- debugging in Visual Studio and VS Code: Visual Studio's container tools run the app in a container with the debugger attached, using a fast-mode build. VS Code uses the Docker extension and a launch configuration that attaches to the process. Why: you debug the real runtime, not just your laptop's.
- local dependencies:
  - SQL Server: image from mcr.microsoft.com, needs ACCEPT_EULA=Y and a strong SA_PASSWORD (verify variable names for the current image).
  - Redis: official redis image, port 6379.
  - Azurite: local emulator for Azure Blob, Queue and Table storage.
  - emulators: Cosmos DB emulator and Service Bus emulator exist (verify current availability and limits).

Command worth memorizing:
  docker compose up -d --build
  docker compose logs -f api
  docker compose down -v

5 Core focus (exam and interview)

- Most asked: difference between volume and bind mount; why containers cannot see each other on the default bridge by name; difference between EXPOSE and -p.
- EXPOSE is documentation only. -p actually publishes.
- Default network: containers on the default bridge reach each other only by IP. User-defined networks and Compose give name-based DNS.
- docker stop sends SIGTERM, then SIGKILL after 10 seconds by default. Your .NET host must shut down gracefully inside that window.
- Container exits when its main process (PID 1) exits.
- docker compose down keeps named volumes. down -v deletes them.
- Restart policies: no (default), on-failure, always, unless-stopped.
- Inside a container, localhost means the container itself, not your laptop. Use the service name, or host.docker.internal for the host (verify per OS).

6 Real-world use case

Situation: A Kolkata team moves a legacy MVC solution to ASP.NET Core. Each developer installs SQL Server, Redis and a storage emulator by hand, and setup takes a day.

Choice: Add a compose.yaml with api, sql, redis and azurite. SQL has a named volume and a healthcheck. The api waits for sql to be healthy. A .env file holds the local password and is kept out of Git, with a .env.example committed.

Trade-off: Onboarding drops to one command and everyone has the same versions. Cost: RAM use (SQL Server wants about 2 GB minimum, verify), slower file access with bind mounts on Windows and macOS, and Docker Desktop licensing for larger companies (verify current terms).

When NOT to use it: Compose is for local development and simple single-host setups. Do not run production on it when you need scaling, rolling updates or self-healing. Use App Service, Container Apps or AKS. Also skip a containerised database if the team already has a shared dev database and the setup works.

7 Interview lens

- Q: Volume or bind mount?
  A: Volumes are Docker-managed and portable, best for databases and persistent data. Bind mounts map a host folder and suit live code editing in development.
- Q: Why does depends_on not guarantee the database is ready?
  A: By default it only waits for the container to start. Add a healthcheck and condition: service_healthy, and keep retry logic in the app.
- Q: My API in a container cannot reach SQL Server on my laptop at localhost. Why?
  A: localhost is the container itself. Use the compose service name, or host.docker.internal for a host-installed service.
- Q: A container keeps exiting. How do you debug it?
  A: docker ps -a to see the exit code, docker logs for output, docker inspect for config and state. Exit code 137 suggests it was killed, often out of memory (verify).

8 Common mistakes

- No volume on the database: data disappears after docker compose down or container removal. Fix: named volume on the data path.
- Using latest tags: a teammate pulls a newer image and things break. Fix: pin versions.
- Committing passwords in compose.yaml: leaks into Git. Fix: .env file, ignored by Git.
- Mapping the wrong side of -p: writing -p 8080:80 when the app listens on 8080. Fix: container port is on the right.
- App binds to localhost inside the container: unreachable from outside. Fix: bind to 0.0.0.0, for example ASPNETCORE_URLS=http://+:8080 (port details vary by .NET version, verify).
- Running everything as root and with the shell form of ENTRYPOINT: signals are not received, shutdown is slow. Fix: exec form and a non-root user.

9 Mental model

Your laptop = a building.
- Image = a blueprint of a room.
- Container = a built room.
- Volume = a storage locker outside the room, kept when the room is demolished.
- Port mapping = a door cut from the building's street to a room.
- Bridge network = an internal corridor where rooms call each other by room name.
- Compose = one order form that builds all rooms and corridors together.

10 Mini lab (30 minutes)

Tools: Docker Desktop or Docker Engine, any text editor. No Azure needed.

Steps:
- Create a folder lab802 and a file compose.yaml with two services: redis (image redis:7, healthcheck using redis-cli ping, named volume redisdata on /data) and a second service named tools using image redis:7, command sleep infinity, profile "tools".
- Run docker compose up -d. Run docker compose ps and wait for redis to show healthy.
- Run docker compose --profile tools up -d. Then docker compose exec tools redis-cli -h redis set course docker.
- Run docker compose exec tools redis-cli -h redis get course. Expected result: "docker". This proves name-based networking.
- Run docker compose down, then docker compose up -d redis, then read the key again from a tools container. Expected result: "docker" still present, because the volume survived.
- Run docker inspect on the redis container and find the Mounts and Networks sections.
- Run docker compose down -v, then bring redis up and read the key. Expected result: key is gone.

Clean-up: docker compose --profile tools down -v, then docker image prune if you want disk space back.

11 Revision summary

- docker run creates and starts; exec enters a running container; logs reads stdout and stderr; inspect shows real config.
- Volumes persist data and Docker manages them; bind mounts map host folders and suit live code.
- User-defined bridge networks and Compose give name-based DNS; the default bridge does not.
- -p host:container publishes a port; EXPOSE only documents.
- Inside a container, localhost is the container itself.
- depends_on needs a healthcheck and service_healthy to mean ready.
- Profiles start optional services only on request.
- docker compose down keeps volumes; down -v deletes them.
