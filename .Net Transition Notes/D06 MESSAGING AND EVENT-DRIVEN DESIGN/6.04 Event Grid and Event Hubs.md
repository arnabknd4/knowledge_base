6.04 Event Grid and Event Hubs [P2 R E L]. Tags: no K, so treat as new; R means a FULL note.

---

1 What is it

- Event Grid is an Azure service that pushes small "something happened" notices from a source to any handler that subscribed. It is a router for events.
- Event Hubs is an Azure service that takes in a huge, continuous stream of records (telemetry, clickstream, logs) and keeps them in order inside partitions so many readers can process them at their own pace. It is a high-volume ingestion pipe.
- Event: a fact that already happened (BlobCreated, OrderPlaced). Partition: one ordered lane inside a stream.
- Legacy equivalent: Event Grid resembles .NET events or webhooks wired between systems. Event Hubs resembles writing every record to a log table or file and having batch jobs read it, but built for millions of records per second.

2 Why needed

- Polling storage or APIs to see "did anything change" wastes calls and adds delay. Event Grid pushes the notice instead.
- Normal queues cannot handle device or log firehoses with replay. Event Hubs can.
- Without a clear choice among four messaging services, teams use Service Bus for everything and pay for the wrong features, or lose messages by using the wrong one.

3 Before you read

- Message vs event vs command (topic 6.01).
- Queue vs topic vs stream (topic 6.01).
- Webhook: an HTTP POST sent to your URL when something happens.
- At-least-once delivery means duplicates are possible.

4 Features and core concepts

Event Grid

- Topic: the endpoint where a publisher sends events. Why: one entry point for many subscribers. Custom topics are yours; system topics are created for Azure sources.
- System events: events Azure services emit themselves (blob created, resource group changed, Key Vault secret near expiry). Why: react to Azure changes with no publisher code.
- Event subscription: a rule that says "send events of this kind to this handler" (Function, Service Bus, Storage Queue, webhook, Event Hubs). Why: this is the push wiring.
- Filtering: subscription rules on event type, subject prefix or suffix, or data fields. Why: handlers receive only what they need.
- Retry: Event Grid retries failed deliveries with backoff for a limited time (verify exact schedule and limits), then drops or sends to a dead-letter location if configured. Why: handlers can be briefly down. Configure dead-lettering to Blob storage so nothing is lost silently.
- Schema: Event Grid schema or CloudEvents (verify supported options per topic type).
- Memorize: subject-prefix filter such as /blobServices/default/containers/invoices/ narrows blob events to one container.

Event Hubs

- Namespace and event hub: the container and the stream inside it. Why: namespace holds throughput and network settings.
- Partitions: parallel ordered lanes. Order is guaranteed only within one partition. Why: this is how throughput scales. Partition count is chosen at creation; changing it is limited by tier (verify).
- Partition key: a value hashed to choose the partition. Why: same key (for example deviceId) lands in the same partition, so that device's events stay ordered.
- Consumer groups: independent views of the same stream. Why: analytics and alerting can each read everything without affecting each other.
- Checkpointing: a reader saves its position (offset) in Blob storage. Why: after a restart it continues where it stopped instead of starting over.
- Capture: automatic copy of the stream to Blob or Data Lake files. Why: cheap long-term storage without writing code.
- Retention: events stay for a set period and are not deleted when read (limit depends on tier, verify). Why: replay is possible.
- Memorize: EventProcessorClient with a BlobContainerClient for checkpoints is the standard .NET reader.

Choosing among the four

- Event Grid: reactive notifications, one event, push, many subscribers.
- Event Hubs: big streams, telemetry, partitioned, replayable, pull by readers.
- Service Bus: business messages and commands needing queues, sessions, transactions, dead-letter, ordered workflow.
- Storage Queues: simple, cheap, huge queue, no frills.

5 Core focus (exam and interview)

- Most asked: pick the right service from a scenario. "React when a blob is uploaded": Event Grid. "Ingest IoT telemetry": Event Hubs. "Reliable order processing with dead-letter": Service Bus. "Cheap simple work queue": Storage Queue.
- Event Grid pushes; Event Hubs and Service Bus are pulled by the consumer.
- Event Hubs ordering is per partition only. Parallel readers per consumer group are limited to the partition count.
- Event Hubs offers a Kafka-compatible endpoint (verify tier support).
- Event Grid is at-least-once; handlers must be idempotent.
- Tiers, throughput units, maximum retention and event size limits change often: check Microsoft Learn (verify).

6 Real-world use case

- Situation: a billing system uploads PDF invoices to Blob storage. Downstream steps must run: virus scan, text extraction, notification.
- Choice: Event Grid system topic on the storage account, filtered to the invoices container, with subscriptions to an Azure Function (extract) and a Service Bus queue (workflow). Also, application telemetry from 200 services goes to Event Hubs, then to Stream Analytics and Capture to Data Lake.
- Trade-off: Event Grid gives no ordering and no replay; failures need dead-lettering and idempotent handlers. Event Hubs needs partition planning and checkpoint storage.
- When NOT to use: do not use Event Grid for ordered business commands (use Service Bus sessions). Do not use Event Hubs as a work queue where each message is processed once by one worker and then removed; it is a log, not a queue.

7 Interview lens

- Q: Event Grid vs Service Bus? A: Event Grid pushes lightweight event notifications to many handlers with no ordering. Service Bus holds business messages with queues, sessions, transactions and dead-letter for reliable processing.
- Q: How does Event Hubs scale and keep order? A: Partitions give parallelism. Order holds only within a partition, so choose a partition key such as deviceId.
- Q: What happens when an Event Grid handler is down? A: Event Grid retries with backoff, then drops or dead-letters to Blob storage if configured. Handlers must be idempotent.
- Q: What is a consumer group? A: An independent read position over the same stream, so several applications can read all events without interfering.

8 Common mistakes

- No dead-letter configured on Event Grid: failed events vanish after retries. Fix: set a Blob dead-letter destination and monitor it.
- Assuming global order in Event Hubs: events arrive out of order across partitions. Fix: use a partition key, or accept per-key order.
- Too few partitions: readers cannot scale past the partition count. Fix: plan partitions for peak parallelism at creation.
- Not checkpointing, or checkpointing every event: duplicate processing after restart, or slow readers. Fix: checkpoint in batches.
- Using Event Hubs as a task queue: no per-message complete or dead-letter. Fix: use Service Bus.
- Webhook handlers that skip endpoint validation or take too long: subscription fails. Fix: complete validation handshake, return quickly.

9 Mental model

Event Grid = doorbell: it rings the listed handlers when something happens.
Event Hubs = conveyor belt with lanes: items flow in, stay for a while, and each reader walks along at its own pace.

  source --> [Event Grid] --push--> Function / Queue / webhook
  devices --> [Event Hubs: lane0 lane1 lane2] --> reader group A, reader group B

10 Mini lab (30 to 40 minutes, Azure free tier)

- Step 1: create a resource group and a general-purpose v2 storage account with a container named invoices.
- Step 2: create a Storage Queue named events-in in the same account.
- Step 3: in the storage account open Events, add an event subscription: type Blob Created, endpoint type Storage Queue, queue events-in, subject begins with /blobServices/default/containers/invoices/.
- Step 4: upload a small file to invoices. Open the queue and refresh. Expected: one message containing a BlobCreated event with the blob URL.
- Step 5: upload a file to a different container. Expected: no new message (filter works).
- Step 6: create an Event Hubs namespace (Basic or Standard, verify free-tier eligibility) with a hub of 2 partitions. In Data Explorer, send a test event and view it.
- Clean-up: delete the resource group.

11 Revision summary

- Event Grid pushes events to handlers; Event Hubs ingests streams that readers pull.
- Event Grid: topics, event subscriptions, filters, retry, dead-letter to Blob.
- Event Grid is at-least-once with no ordering, so make handlers idempotent.
- Event Hubs: partitions, partition key, consumer groups, checkpoints, Capture.
- Event Hubs order is guaranteed per partition only.
- Service Bus for business messages; Storage Queues for simple cheap queues.
- Event Hubs is a replayable log, not a work queue.
- Limits, tiers and retention change: verify on Microsoft Learn.
