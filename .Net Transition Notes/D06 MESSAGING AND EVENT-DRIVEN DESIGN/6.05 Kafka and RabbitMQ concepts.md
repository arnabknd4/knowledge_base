1 What is it

- A broker is a server that sits between programs that send messages and programs that receive them. Kafka and RabbitMQ are two different kinds of broker.
- RabbitMQ is a smart broker. Producers send messages to an exchange, the exchange routes them to queues using rules, and the broker removes a message once a consumer acknowledges it.
- Kafka is a log. Producers append records to the end of a topic, and the records stay on disk for a set time. Consumers keep their own position (offset) and read at their own pace.
- Legacy equivalent: MSMQ or a SQL table used as a job queue in .NET Framework apps. Kafka is closer to an append-only audit table that many readers can replay.

2 Why needed

- Direct service-to-service calls break when one side is slow or down. A broker lets the sender move on and the receiver catch up later.
- Without the right broker choice, you either lose messages (no acknowledgement), overload consumers (no backpressure), or cannot replay history after a bug fix.
- Azure already gives you Service Bus. You need to know when Kafka or RabbitMQ is the better fit, because many employers outside Azure-only shops run them.

4 Features and core concepts

- Broker vs log. A broker (RabbitMQ) pushes messages to consumers and deletes them after acknowledgement. A log (Kafka) stores records in order and consumers pull them. Why it matters: a log allows replay and many independent readers; a broker is simpler for task distribution.
- Topics. A topic is a named stream of records in Kafka. Why it matters: it is the unit you publish to and subscribe to, like a table name.
- Partitions. A topic is split into partitions, each an ordered file. Why it matters: partitions give parallelism and set the maximum number of consumers working in parallel in one group.
- Offsets. An offset is the number of a record within a partition. Why it matters: a consumer stores its offset, so it can resume or rewind. Committing the offset after processing gives at-least-once delivery.
- Consumer groups. Consumers sharing a group id split the partitions between them. Different groups each get every record. Why it matters: this is how you scale one service and also feed many services.
- Retention and compaction. Retention deletes records after a time or size limit. Compaction keeps only the latest record per key. Why it matters: compaction suits "current state" topics; retention suits event streams.
- Exchanges and bindings (RabbitMQ). The exchange receives messages and a binding links it to a queue with a rule. Types: direct (exact key), topic (pattern), fanout (all queues), headers. Why it matters: routing logic lives in the broker.
- Acknowledgements. RabbitMQ consumers send ack, nack or reject. Unacknowledged messages are redelivered. Why it matters: ack after the work succeeds, not before, or you lose messages on crash.
- Ordering guarantees. Kafka guarantees order only within a partition; use the same key to land related records in one partition. RabbitMQ keeps order per queue, but redelivery and multiple consumers can break it. Why it matters: global order is not available at scale.
- Throughput trade-offs. Kafka batches and writes sequentially, so it handles very high volume. RabbitMQ is tuned for low latency and flexible routing at moderate volume. Why it matters: pick by workload, not by popularity.
- Kafka Connect awareness. A framework to move data between Kafka and databases or other systems with ready-made connectors, no custom code.
- Event Hubs Kafka endpoint. Azure Event Hubs accepts Kafka client connections, so Kafka apps can run on a managed Azure service (verify supported features).
- Abstractions: MassTransit, NServiceBus, Wolverine. .NET libraries that hide the broker behind a common API and add retries, sagas and outbox. Why it matters: you can switch brokers with less code change. Check current licensing (verify).
- Worth memorizing (Confluent.Kafka consumer setting): EnableAutoCommit = false, then call consumer.Commit(result) after processing.

5 Core focus (exam and interview)

- Most asked: Kafka vs RabbitMQ, ordering in Kafka, what a consumer group does, how to get at-least-once, and how to handle duplicates.
- Remember: consumers in one group cannot exceed the partition count usefully.
- Remember: Kafka does not delete on read; RabbitMQ does on ack.
- Remember: exactly-once is limited in scope and costly; design idempotent consumers instead.
- Azure exams usually test choosing Service Bus, Event Hubs or Event Grid (see 6.04), not Kafka internals.

6 Real-world use case

- Situation: an order system in .NET must publish order events to billing, inventory, analytics and a fraud service, and analytics must be able to reprocess last week's events.
- Choice: Kafka (or Event Hubs with the Kafka endpoint on Azure). Key by order id so events for one order stay in order. Each service uses its own consumer group.
- Trade-off: more operational work (partitions, retention, offsets) and no per-message routing or priority queues.
- When not to use it: simple background jobs, request-reply, or complex routing by headers. RabbitMQ or Service Bus fits better there, and low volume does not justify running Kafka.

7 Interview lens

- Q: How do Kafka and RabbitMQ differ at the core?
  A: Kafka is a replayable log read by pull with consumer-owned offsets. RabbitMQ is a routing broker that pushes and deletes after acknowledgement.
- Q: How do you keep order in Kafka?
  A: Order holds only within one partition. Use the same key so related records go to the same partition.
- Q: What happens if a consumer crashes before committing its offset?
  A: It re-reads from the last committed offset, so records can be processed twice. Make handlers idempotent.
- Q: How do you scale consumers?
  A: Add consumers to the same group up to the partition count. Beyond that, add partitions, which can change key-to-partition mapping.

8 Common mistakes

- Auto-commit offsets before processing finishes. Shows up as lost records after a crash. Fix: commit manually after success.
- Too few partitions at the start. Shows up as a consumer ceiling. Fix: plan partitions for future peak consumers.
- Assuming exactly-once. Shows up as duplicate charges or emails. Fix: idempotency keys and a de-duplication table.
- Acking in RabbitMQ before work completes. Shows up as silent message loss. Fix: ack after commit.
- Unbounded queue growth in RabbitMQ with slow consumers. Shows up as memory alarms and blocked publishers. Fix: prefetch limits, TTL, dead-letter queue, scale consumers.
- Large messages. Shows up as broker slowdown. Fix: claim-check pattern, store the payload in Blob storage.

9 Mental model

- Kafka: a notebook with numbered lines. Writers add lines at the end. Each reader keeps a bookmark and can move it back.
- RabbitMQ: a post office. The exchange is the sorting desk, queues are pigeonholes, and a letter is removed once the recipient signs for it.

10 Mini lab

- Time: about 30 minutes. Tools: Docker Desktop and a terminal.
- Part A, Kafka:
  - Step 1: run a single-node Kafka container (use the current official apache/kafka image, verify tag) and expose port 9092.
  - Step 2: create a topic named orders with 3 partitions using the kafka-topics script inside the container.
  - Step 3: start a console producer with a key (parse.key=true) and send records like 1:created and 1:paid.
  - Step 4: start a console consumer with group.id=billing and read from the beginning. Start a second consumer with group.id=audit.
  - Expected: both groups see every record. Records with key 1 come out in the order sent.
  - Step 5: run kafka-consumer-groups --describe to see offsets and lag per partition.
- Part B, RabbitMQ:
  - Step 1: run docker run -p 5672:5672 -p 15672:15672 rabbitmq:management (verify tag), open http://localhost:15672, login guest/guest.
  - Step 2: create a queue named jobs, publish a message from the UI, then use Get Message with Ack mode "Reject and requeue".
  - Expected: the message returns to the queue until you choose "Automatic ack", then it disappears.
- Clean-up: docker rm -f for both containers.

11 Revision summary

- Kafka is a log with retention; RabbitMQ is a broker that deletes on ack.
- Kafka order is per partition only; key by business id.
- Consumers in one group share partitions; useful parallelism is capped by partition count.
- Commit the offset or ack after processing for at-least-once, and make handlers idempotent.
- Compaction keeps the latest record per key; retention deletes by age or size.
- RabbitMQ routes with exchanges (direct, topic, fanout, headers) and bindings.
- Event Hubs offers a Kafka endpoint (verify feature support).
- MassTransit, NServiceBus and Wolverine abstract the broker (verify licensing).
