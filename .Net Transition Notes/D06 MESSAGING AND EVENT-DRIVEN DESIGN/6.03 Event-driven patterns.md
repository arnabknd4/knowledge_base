6.03 Event-driven patterns [P2 R L] is new to you (no K tag), so this is a FULL note with a mini lab.

1 What is it

- Event-driven patterns are ways to make services talk by announcing facts ("OrderPlaced") instead of calling each other directly. Other services react on their own time.
- Outbox and inbox make sure a database change and its message are never out of step. A saga coordinates a business process that spans several services.
- Eventual consistency means all parts agree after a short delay, not instantly.
- Legacy equivalent: a single SQL transaction with TransactionScope or MSDTC across tables, plus nightly jobs and triggers that copied data between systems.

2 Why needed

- Microservices cannot share one database transaction. Saving an order and then publishing a message are two separate actions, and either can fail.
- Without these patterns you get lost messages, duplicate processing, half-finished orders, and no way to undo a step that already happened elsewhere.

3 Before you read

- Message, queue, topic and delivery semantics (6.01): at-least-once delivery means duplicates can happen.
- Azure Service Bus basics (6.02): topics, subscriptions, dead-letter queue.
- ACID transaction: all steps succeed together or none do.
- Idempotent: doing the same operation twice has the same effect as doing it once.

4 Features and core concepts

- Outbox: write the business row and the outgoing message into the same database transaction, in an Outbox table. A separate processor reads that table and publishes to the broker. Why: removes the "saved but not published" gap.
- Inbox: the consumer records each message ID it has handled and skips repeats. Why: duplicates become harmless.
- Transactional messaging: the general idea behind outbox and inbox, that database state and messages move together. Why: this replaces distributed transactions, which do not scale.
- Saga: a chain of local transactions, each followed by an event or command that triggers the next. If one fails, earlier steps are undone. Why: gives you a multi-service business transaction without a global lock.
- Orchestration: one central coordinator tells each service what to do next. Easy to follow and debug, but the coordinator is a dependency.
- Choreography: no coordinator. Each service listens for events and reacts. Loosely coupled, but the overall flow is hard to see as it grows.
- Process manager: the stateful component that tracks one saga instance and decides the next step. It is the orchestrator's brain.
- Event notification: a small event saying "something happened, ID 42". Receivers call back for details. Why: small messages, but extra calls and coupling to the source.
- Event-carried state transfer: the event carries the data receivers need, so they keep their own copy. Why: no callbacks and better autonomy, but data is duplicated and can go stale.
- CQRS read-model projections: handlers consume events and build a read-optimized table or document for queries. Why: fast reads without joining across services.
- Eventual consistency in the UI: the screen may briefly show old data. Show "processing" status, return 202 Accepted, or update the UI after the event arrives. Why: users must not think the action failed.
- Compensating actions: a new action that semantically reverses an earlier one (refund payment, release stock). It is not a rollback because the original already committed. Why: this is how a saga undoes work.
- Replay: reprocess old events to rebuild a read model or fix a bug. It needs idempotent consumers and a retained log. Why: recovery and new projections.
- Schema registry: a central store of event schemas and versions. Why: producers and consumers can evolve safely. Azure options (verify).
- Event versioning: add fields without removing or renaming old ones, and keep old versions readable. Why: consumers deploy on different schedules.
- Testing async flows: test handlers directly, run the outbox against a real broker or Testcontainers, and assert eventually with a timeout, not a fixed sleep.

Worth memorizing (inbox check):
- if (await db.Inbox.AnyAsync(x => x.MessageId == id)) return;
- handle the message and insert the Inbox row in the same transaction

5 Core focus (exam and interview)

- Asked most: why not a distributed transaction, how outbox prevents lost messages, orchestration vs choreography, how to undo a failed step.
- Exactly-once delivery is a myth. Aim for at-least-once delivery plus idempotent handling.
- The outbox processor can itself publish a message twice. The inbox or idempotent handler absorbs that.
- Saga steps need compensations, and compensations must also be idempotent and retryable.
- Service Bus duplicate detection and sessions help but do not replace an inbox (check limits and window defaults on Microsoft Learn) (verify).

6 Real-world use case

- Situation: an e-commerce platform on Azure. The Order service (ASP.NET Core and Azure SQL) must trigger Payment and Inventory services.
- Choice: Order writes the order and an OrderPlaced outbox row in one transaction. A BackgroundService publishes to a Service Bus topic. Payment and Inventory subscribe, each with an inbox table. An orchestrated saga (a process manager in the Order service) handles failure: if payment fails, it sends ReleaseStock.
- Trade-off: more moving parts, delay between steps, and the saga state must be stored and monitored.
- When NOT to use it: a single database and one team. A plain local transaction is simpler and safer. Also avoid saga when the business needs strict instant consistency.

7 Interview lens

- Q: Why not use a distributed transaction (MSDTC)? A: It locks resources across services, hurts availability and is not supported by most cloud brokers. Outbox plus idempotent consumers give reliability without it.
- Q: How does outbox prevent lost events? A: The event is saved in the same local transaction as the data. If the app crashes, the row is still there and the processor sends it later.
- Q: Orchestration or choreography? A: Orchestration for longer flows with clear steps and error handling. Choreography for simple flows with few services.
- Q: How do you handle a failure in step 3 of a saga? A: Run compensating actions for steps 2 and 1 in reverse. Each compensation is idempotent and retried until it succeeds.

8 Common mistakes

- Publishing to the broker and then saving to the database in code. A crash between them loses or invents events. Fix: outbox.
- No inbox, so duplicates double-charge a customer. Fix: store processed message IDs or make operations idempotent.
- Treating compensation as rollback and forgetting side effects like emails already sent. Fix: design business-level reversals.
- Breaking changes to event schemas. Old consumers crash and messages pile in the dead-letter queue. Fix: additive changes and versioned events.
- Choreography grown to ten services with nobody understanding the flow. Fix: switch to orchestration or document the flow with tracing.
- Outbox table never cleaned. It slows the database. Fix: delete or archive sent rows.

9 Mental model

- Think of a post office with a sorting tray on your desk.

  Order saved + letter placed in the tray (one action)
  courier collects from the tray and delivers (may deliver twice)
  receiver keeps a "received" register and ignores repeats
  if a later step fails, send a new letter that cancels the earlier one

10 Mini lab (about 35 minutes)

- Tools: .NET SDK, Docker, SQL Server container or SQLite, Azurite is not needed. Use a local RabbitMQ container or in-memory queue if you do not want Service Bus.
- Steps:
  - Create a console or minimal API project with a SQLite database. Add tables Orders, Outbox (Id, Type, Payload, SentAt null), Inbox (MessageId).
  - In one SaveChanges call, insert an Order and an Outbox row.
  - Add a BackgroundService that every 2 seconds reads Outbox rows where SentAt is null, publishes them (log to console or send to the queue), then sets SentAt.
  - Add a consumer that checks Inbox first, handles the message, and inserts the Inbox row in the same transaction.
  - Break it on purpose: throw an exception after publishing but before setting SentAt. Restart the app.
- Expected result: the message is published twice, but the consumer processes it only once because of the inbox.
- Clean-up: delete the project folder, the SQLite file and any Docker containers (docker rm -f).

11 Revision summary

- Outbox: data and message saved in one local transaction, published later.
- Inbox: remember handled message IDs so duplicates are skipped.
- Exactly-once is a myth. Use at-least-once plus idempotency.
- Saga is a sequence of local transactions with compensating actions.
- Orchestration has a central coordinator. Choreography has none.
- Event notification is a small signal. Event-carried state transfer includes the data.
- Read models are built by projections and can be rebuilt by replay.
- Evolve event schemas by adding fields, never by breaking old ones.
