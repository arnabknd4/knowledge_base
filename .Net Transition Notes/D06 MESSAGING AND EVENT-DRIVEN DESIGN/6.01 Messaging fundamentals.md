1 What is it
- Messaging is how one part of a system sends data to another without waiting for an immediate reply. The sender drops a message on a broker (a middleman that stores and routes messages). The receiver picks it up later.
- A queue holds messages for one consumer group. A topic copies each message to many subscribers. A stream is an ordered log that consumers can re-read.
- Message vs event vs command: a command says "do this" (PlaceOrder). An event says "this happened" (OrderPlaced). A message is the general envelope for either.
- Legacy equivalent: MSMQ, database tables used as job queues, or a SQL Agent job polling a status column.

2 Why needed
- Synchronous calls tie the caller to the callee's speed and uptime. If the callee is down, the caller fails.
- Messaging absorbs traffic spikes, lets services fail independently, and lets you add new consumers without changing the sender.
- Without it you get timeouts, lost work during deployments, and tightly coupled services.

3 Before you read
- HTTP request and response: the caller waits for the answer.
- Idempotent: doing the same operation twice gives the same result as doing it once.
- Transaction: a group of changes that succeed or fail together.

4 Features and core concepts
- Sync vs async: sync waits for a reply; async hands off and moves on. Matters because async removes runtime coupling but adds complexity (eventual results).
- Queue vs topic vs stream: queue = one consumer gets each message; topic = every subscriber gets a copy; stream = retained log, consumers track their own position. Pick by who needs the data and whether replay matters.
- Point-to-point vs publish-subscribe: one receiver vs many receivers. Pub-sub lets you add consumers without touching the publisher.
- Message vs event vs command: command targets one handler and expects action; event is a fact for anyone interested. Mixing them up causes hidden coupling.
- Delivery semantics: at-most-once (may lose, never duplicates), at-least-once (never loses, may duplicate), exactly-once (a myth end to end; you get it by at-least-once plus idempotent processing). At-least-once is the practical default.
- Ordering: messages may arrive out of order across consumers. Strict order usually needs one partition or session per key, which limits throughput.
- Partitions: a stream is split into lanes. Order holds only inside one lane. The partition key decides which lane.
- Competing consumers: many workers read one queue and share the load. Scales processing, but order is no longer guaranteed.
- Backpressure: a slow consumer signals or causes the producer to slow down. Without it queues grow without limit and memory or cost explodes.
- Poison messages and dead-letter queues (DLQ): a poison message fails every time. After a set number of attempts, move it to a DLQ so it does not block the queue. Monitor the DLQ.
- Retry and backoff: retry failed processing with growing delays. Immediate retries hammer a struggling dependency.
- TTL (time to live): a message expires if not consumed in time. Prevents stale work (an old OTP, for example).
- Message size: brokers have size limits (verify per service). Large payloads slow everything.
- Schema versioning: message shape changes over time. Add fields only, never remove or rename, so old consumers keep working.
- Idempotent consumers: the handler can safely process the same message twice. Needed because of at-least-once delivery. Typical method: store processed message IDs, or use upserts.
- Claim-check pattern: store the big payload in Blob Storage and send only a reference in the message. Keeps messages small.
- Worth memorizing: message ID check before processing: if (await store.Exists(msg.Id)) return; then process and save the ID in the same transaction.

5 Core focus (exam and interview)
- Most asked: at-least-once vs exactly-once, DLQ purpose, queue vs topic, why idempotency is mandatory.
- Ordering only holds within a partition, session or single consumer.
- Defaults to remember: at-least-once delivery is the norm; retries must have a limit before dead-lettering.
- Command vs event wording: commands are imperative, events are past tense.
- Do not claim exactly-once delivery in an interview. Say "effectively once through idempotency."

6 Real-world use case
- Situation: an order API in ASP.NET Core must trigger payment, inventory, email and invoice. Calling all four over HTTP makes checkout slow and fragile.
- Choice: the API saves the order and publishes OrderPlaced to an Azure Service Bus topic. Each downstream service has its own subscription. Consumers are idempotent and use a DLQ.
- Trade-off: checkout becomes fast and resilient, but the user sees "order received" rather than a final result. You must handle eventual consistency, duplicates and monitoring.
- When NOT to use it: when the caller needs the answer right now (price lookup, login), when the volume is tiny and one process owns everything, or when the team cannot yet operate a broker.

7 Interview lens
- Q: Is exactly-once delivery possible? A: Not end to end across systems. Use at-least-once delivery plus idempotent consumers to get an effectively-once result.
- Q: Queue or topic? A: Queue when one logical consumer handles each message. Topic when several independent consumers each need a copy.
- Q: What is a DLQ and why use it? A: It holds messages that failed after the retry limit or expired. It stops poison messages blocking the queue and lets you inspect and replay them.
- Q: How do you keep order? A: Route related messages to the same partition or session using a key. Order is guaranteed only inside that lane, and parallelism drops.

8 Common mistakes
- Non-idempotent handler: a redelivery charges a customer twice. Fix: dedupe by message ID or use natural idempotency keys.
- No DLQ monitoring: failures pile up silently. Fix: alert on DLQ depth.
- Infinite retries: one bad message loops forever. Fix: cap attempts, then dead-letter.
- Fat messages: slow brokers and size-limit errors. Fix: claim-check.
- Breaking schema changes: old consumers crash after a deploy. Fix: additive changes and versioned contracts.
- Assuming global order: bugs appear under load with several consumers. Fix: partition by key, or design order-independent handlers.
- Publishing after the database commit in separate steps: a crash between them loses the event. Fix: the outbox pattern (covered in 6.03).

9 Mental model
Post office:
Producer -> [Broker: queue/topic/stream] -> Consumer(s)
- Queue = one mailbox, one reader takes each letter.
- Topic = newsletter, every subscriber gets a copy.
- Stream = a logbook everyone can re-read from their own bookmark.
- DLQ = the "undeliverable" shelf.

10 Mini lab (30 minutes, local, no cost)
- Step 1: run RabbitMQ locally: docker run -d --name rmq -p 5672:5672 -p 15672:15672 rabbitmq:3-management
- Step 2: open http://localhost:15672 (guest / guest). Create a queue named orders.
- Step 3: create two console apps (dotnet new console) and add the RabbitMQ.Client NuGet package. One publishes 10 messages with an ID. The other consumes with manual acknowledgement.
- Step 4: make the consumer throw on message 5 and not acknowledge it. Observe it redelivered (the "Redelivered" flag).
- Step 5: add an in-memory HashSet of processed IDs and skip duplicates. Run again.
- Expected result: message 5 is redelivered, and your ID check makes the second processing a no-op.
- Optional: start two consumers and watch the messages split between them (competing consumers).
- Clean-up: docker rm -f rmq

11 Revision summary
- Queue: one consumer per message. Topic: a copy per subscriber. Stream: replayable log.
- Command = do this. Event = this happened.
- Real delivery is at-least-once; exactly-once is achieved by idempotent consumers.
- Order holds only within a partition, session or single consumer.
- DLQ catches poison and expired messages; monitor it.
- Retry with backoff and a cap.
- Claim-check: store the payload in Blob, send the reference.
- Schema changes must be additive.
