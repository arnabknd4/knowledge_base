1 What is it
- Azure Service Bus is a managed message broker in Azure. One part of your system puts a message in. Another part picks it up later, even if it was offline when the message was sent.
- A queue holds messages for one consumer group. A topic holds messages for many subscribers, each with its own copy.
- The broker stores messages durably and tracks who has processed what. You do not run servers.
- Legacy equivalent: MSMQ or a SQL table used as a job queue with a polling Windows service, but managed, durable and much more reliable.

2 Why needed
- Direct calls between services fail when the receiver is down or slow. Messages wait in the broker instead.
- It smooths traffic spikes. Consumers process at their own pace.
- Without it, you build your own retry, lock and dead-letter logic on SQL tables, and it breaks under load.
- It separates the sender from the receiver, so each can be deployed and scaled alone.

3 Before you read
- Sync vs async calls: sync waits for a reply, async does not.
- At-least-once delivery means a message can arrive more than once.
- Managed identity and Azure RBAC: how an app logs in without a password.
- Namespace: the top-level Azure resource that holds your queues and topics.

4 Features and core concepts
- Queues: one message goes to one consumer, from a pool of competing consumers. Use for work distribution.
- Topics and subscriptions: a topic is a publish point. Each subscription gets its own copy. Use for one event, many reactions.
- Filters and rules: a subscription can accept only messages matching conditions on properties (SQL filter, correlation filter). This avoids consumers discarding unwanted messages.
- Sessions: messages with the same SessionId are delivered in order to one consumer at a time. Use when order matters per key, such as per order or per customer.
- Peek-lock: the consumer gets the message, it is locked, then the consumer completes or abandons it. If the lock expires, the message returns to the queue. Safe default.
- Receive-and-delete: the message is removed on receive. Faster, but a crash loses the message. Use only when loss is acceptable.
- Lock duration and renewal: the lock is time-limited (default 1 minute, verify). Long jobs need lock renewal or they get redelivered and duplicated.
- Dead-letter queue (DLQ): a sub-queue for messages that cannot be processed. Messages go there after max delivery count (default 10, verify), TTL expiry, or explicit dead-lettering. Why it matters: poison messages stop blocking the queue.
- Scheduled messages: send now, deliver at a future time. Useful for reminders and delayed retries.
- Duplicate detection: the broker drops messages with the same MessageId within a time window. Why it matters: producer retries do not create duplicates. It does not replace idempotent consumers.
- Transactions: send and complete several operations atomically within one namespace entity scope. It cannot span Service Bus and your SQL database.
- Standard vs Premium: Standard is shared and priced per operation. Premium has dedicated capacity, larger messages, VNet and private endpoint support, and predictable latency (verify limits and prices).
- Managed identity access: grant roles such as Azure Service Bus Data Sender and Data Receiver. Avoid connection strings.
- .NET SDK processor: ServiceBusProcessor runs a message handler loop with concurrency and automatic lock renewal.
- Monitoring: watch active message count, DLQ count, oldest message age, and throttling.
- Geo-disaster recovery: pairs two namespaces so metadata fails over to the secondary. It does not replicate message data (verify). Premium offers geo-replication (verify).

Code worth memorizing:
- var client = new ServiceBusClient(fqdn, new DefaultAzureCredential());
- var processor = client.CreateProcessor(queue, new ServiceBusProcessorOptions { MaxConcurrentCalls = 4 });
- processor.ProcessMessageAsync += async a => { await Handle(a.Message); await a.CompleteMessageAsync(a.Message); };
- processor.ProcessErrorAsync += a => Task.CompletedTask;
- await processor.StartProcessingAsync();

5 Core focus (exam and interview)
- Queue vs topic: one consumer vs many subscribers.
- Peek-lock plus Complete is the safe default. Know what happens when the lock expires.
- DLQ triggers: max delivery count exceeded, TTL expired, explicit dead-letter, filter evaluation errors (verify).
- Delivery is at-least-once, so consumers must be idempotent.
- Sessions give FIFO per session key, not global order.
- Duplicate detection needs a MessageId that you set, and it works within a window (default 10 minutes, verify).
- Premium for isolation, private networking, large messages and predictable performance (verify limits).
- Use managed identity and RBAC roles instead of shared access keys.
- Service Bus vs Event Grid vs Event Hubs is covered in 6.04.

6 Real-world use case
- Situation: a legacy order system does inventory, billing and email inside one web request. Checkout is slow and one failure fails the whole order.
- Choice: publish an OrderPlaced message to a topic. Inventory, billing and notification each have a subscription and a worker (BackgroundService or Azure Function). Use a session per OrderId when updates to one order must stay in order. Use managed identity.
- Trade-off: the user sees a result before all steps finish, so the UI needs eventual-consistency handling. You also run and monitor more moving parts, and you need idempotent handlers and DLQ handling.
- When not to use it: a simple in-process call within one app, very high-volume telemetry streaming (Event Hubs fits better), or when you need immediate synchronous results.

7 Interview lens
- Q: Queue or topic? A: Queue when one logical consumer handles each message. Topic when several independent consumers each need the message.
- Q: How do you avoid duplicate processing? A: Delivery is at-least-once, so make handlers idempotent using a business key or an inbox table. Duplicate detection helps only on the send side.
- Q: What do you do with messages in the DLQ? A: Alert on DLQ count, inspect the reason property, fix the cause, then resubmit or discard. Never ignore it.
- Q: How do you keep order? A: Use sessions with a key such as OrderId. Order is guaranteed only within a session, and one consumer holds a session at a time.

8 Common mistakes
- Handler runs longer than the lock. Messages are redelivered and processed twice. Fix: renew the lock, shorten the work, or tune lock duration.
- Non-idempotent handlers. Duplicates double-charge or double-email. Fix: idempotency key or inbox table.
- Nobody watches the DLQ. Failures pile up silently. Fix: alert on DLQ depth.
- Using connection strings with manage rights everywhere. Fix: managed identity with sender or receiver roles only.
- Sending DB update and message separately. A crash between them loses consistency. Fix: outbox pattern (see 6.03).
- Huge payloads in messages. Fix: store the data in Blob Storage and send a reference (claim check).
- Creating a new client per message. Fix: reuse one ServiceBusClient for the app lifetime.

9 Mental model
- Post office with sorting.
- Producer -> [Queue] -> competing workers.
- Producer -> [Topic] -> (Sub A) -> worker A, (Sub B) -> worker B.
- Each message: received and locked -> Complete (gone) or Abandon (back) or lock expires (back) -> too many tries -> DLQ.

10 Mini lab
Time: about 30 minutes. Tools: Azure free account, Azure CLI, .NET SDK.
- Create a resource group and a Standard namespace: az servicebus namespace create -g rg-sb-lab -n sb-lab-<unique> --sku Standard -l <region>
- Create a queue with max delivery count 3: az servicebus queue create -g rg-sb-lab --namespace-name sb-lab-<unique> -n orders --max-delivery-count 3
- Assign your user the Azure Service Bus Data Owner role on the namespace (portal, Access control).
- Create a console app, add the Azure.Messaging.ServiceBus and Azure.Identity packages. Send 3 messages with a ServiceBusSender.
- Add a ServiceBusProcessor. In the handler, call Complete for two messages and throw an exception for one.
- Expected result: two messages complete. The failing one is retried 3 times, then appears in the orders dead-letter queue (portal, Service Bus Explorer, orders, Dead-letter tab). Check its DeadLetterReason.
- Clean-up: az group delete -n rg-sb-lab --yes --no-wait

11 Revision summary
- Queue: one consumer per message. Topic: one copy per subscription.
- Peek-lock is the default safe mode. Receive-and-delete can lose messages.
- Delivery is at-least-once, so handlers must be idempotent.
- DLQ receives messages after max delivery count, TTL expiry or explicit dead-letter.
- Sessions give ordering per session key only.
- Duplicate detection uses MessageId in a time window and protects the send side only.
- Use managed identity with Data Sender or Data Receiver roles.
- Premium gives isolation and private networking. Geo-DR replicates metadata, not messages (verify).
