1 What is it

Caching means keeping a copy of data that is expensive to fetch in a faster place, so the next request is served from the copy. The fast place is usually memory. The slow place is a database, an API or a disk.

- Hit ratio: the share of requests served from the cache. Latency: time per request. A high hit ratio lowers latency and database load.
- Cache-aside: the app checks the cache, on a miss reads the database, then writes the result to the cache.
- Read-through: the cache itself loads data from the database on a miss. The app only talks to the cache.
- Write-through: every write goes to the cache and the database together.
- Write-behind: the write goes to the cache first and the database is updated later in the background.
- Refresh-ahead: the cache reloads a hot entry before it expires.

Legacy equivalent: ASP.NET Cache, HttpRuntime.Cache and Session state in .NET Framework MVC apps, plus SQL Server query results kept in static dictionaries.

2 Why needed

- Databases and remote APIs are slow and have limited capacity. Repeated identical reads waste both.
- Without a cache, traffic spikes hit the database directly and response time grows.
- Without a cache, every request pays the full cost of expensive calculations and joins.
- Cost: cloud databases are billed by size and throughput. A cache is often the cheapest way to cut that bill.

3 Before you read

- Latency means time to answer one request. Throughput means requests handled per second.
- A TTL (time to live) is a timer after which data is treated as expired.
- Stale data is a cached copy that no longer matches the source.
- Stateless services keep no user data in their own memory between requests.

4 Features and core concepts

- Hit ratio and latency: hit ratio = hits divided by total requests. Matters because a 90 percent hit ratio means only 1 request in 10 reaches the database. Measure it before and after adding a cache.
- Cache-aside: app controls loading. Matters because it is the simplest and most common pattern, and a cache failure does not break reads.
- Read-through: the cache layer owns loading. Matters because the loading code lives in one place, not in every caller.
- Write-through: writes go to cache and database together. Matters because the cache is never behind the database, at the cost of slower writes.
- Write-behind: database write is delayed. Matters because writes are fast, but data can be lost if the cache dies before it flushes.
- Refresh-ahead: reload before expiry. Matters because users never wait on a miss for hot keys.
- TTL and sliding expiry: absolute TTL expires at a fixed time after being written. Sliding expiry resets the timer on every read. Matters because sliding alone can keep an entry alive forever, so combine it with an absolute limit.
- Invalidation strategies: remove or update cached data when the source changes. Options: time-based, event-based (on write, delete the key), or version-based. Matters because stale data is the main risk of caching.
- Versioned keys: put a version in the key, such as product:42:v7. Matters because bumping the version makes all old entries unreachable without deleting them.
- Stampede: many requests miss the same hot key at once and all hit the database. Fix: lock so only one request reloads, or add jitter to TTLs.
- Penetration: requests for keys that never exist always miss and always hit the database. Fix: negative caching or a bloom filter.
- Avalanche: many keys expire at the same moment. Fix: add random jitter to TTLs.
- Negative caching: cache the answer "not found" for a short TTL. Matters because it blocks repeated lookups of missing data.
- Consistency trade-offs: a cache is a second copy, so it can disagree with the source. Matters because you must decide how much staleness each data type can tolerate.
- What not to cache: highly personal data, data that must be exact (balances, stock at checkout), rarely repeated queries, and data cheaper to compute than to fetch.
- Key design: keys should be unique, predictable and include tenant, entity and version. Example: tenant7:order:1001:v2. Matters because a key clash serves one user another user's data.
- Serialization cost: storing objects in a remote cache means converting them to bytes and back. Matters because large objects can make the cache slower than the database.
- Eviction (LRU, LFU): when memory is full, the cache removes entries. LRU removes the least recently used. LFU removes the least frequently used. Matters because it decides which data survives under pressure.

Cache-aside pattern worth memorizing:

- value = cache.Get(key)
- if value is null: value = db.Read(key); cache.Set(key, value, ttl + jitter)
- on update: db.Write(key, value); cache.Remove(key)

5 Core focus (exam and interview)

- Most asked: name the five patterns and say which one you would choose. Default answer: cache-aside.
- Most asked: explain stampede, penetration and avalanche and give one fix for each.
- Most asked: why invalidation is hard, and how TTL plus event-based removal works together.
- Remember: on update, delete the cache key rather than update it. Deleting avoids races where two writers store an older value.
- Remember: write-behind risks data loss. Write-through is slower but safer.
- Remember: LRU is the common default. LFU suits stable hot sets.
- Remember: always set a TTL. A cache entry with no TTL is a permanent stale copy.
- Remember: measure hit ratio. A cache with a low hit ratio adds cost without benefit.

6 Real-world use case

Situation: an ASP.NET Core API in Azure serves a product catalog. Reads are 95 percent of traffic. Azure SQL CPU is high at peak.

Choice: cache-aside with a 10 minute TTL plus 0 to 60 seconds jitter. When an admin edits a product, the write path deletes the key. A lock on reload prevents stampede on popular products.

Trade-off: users may see old prices for a short time if an invalidation is missed. The TTL caps that window.

When NOT to use it: order totals and payment amounts at checkout, inventory counts that must be exact, and data unique per request. Also skip it if the database is not the bottleneck. Measure first.

7 Interview lens

- Q: Which caching pattern would you pick by default and why?
  A: Cache-aside. The app controls loading, and a cache outage only slows reads instead of breaking them.
- Q: How do you stop a cache stampede?
  A: Allow one request to reload the key while others wait, and add random jitter to TTLs. Refresh-ahead also helps for hot keys.
- Q: Why delete the key on update instead of writing the new value?
  A: Two concurrent writers can store values in the wrong order. Deleting forces the next read to load the current database value.
- Q: When is caching the wrong answer?
  A: When data must be exact, is unique per request, or the real bottleneck is elsewhere. Caching then adds complexity and stale-data bugs.

8 Common mistakes

- No TTL: entries never expire and users see old data for weeks. Fix: always set a TTL.
- Same TTL on all keys: a mass expiry spikes the database. Fix: add jitter.
- Weak keys: missing tenant or user id leaks data across users. Fix: put tenant and entity id in every key and review key builders.
- Caching large objects: memory fills and serialization slows requests. Fix: cache small projections, not full entities.
- Never measuring hit ratio: the cache runs at 20 percent and nobody notices. Fix: track hits, misses and evictions.
- Caching errors: a failed database call gets cached as a result. Fix: only cache successful results, and use short negative caching deliberately.

9 Mental model

A desk and a filing room. The desk (cache) is small and fast. The filing room (database) is big and slow. You keep the papers you use often on the desk, and when the desk is full you put away the least used one. When a paper in the filing room changes, you throw away the copy on your desk.

10 Mini lab (about 30 minutes, local tools)

Steps:
- Create a console or minimal API project: dotnet new web -n CacheLab
- Add a method GetProduct(int id) that sleeps 500 ms to simulate a slow database call and returns a string.
- Run it 5 times with no cache and note the time per call. Expect about 500 ms each.
- Add IMemoryCache with cache-aside. Use TTL 30 seconds plus a random 0 to 10 seconds. Keep a counter for hits and misses.
- Run 5 calls again. Expected result: the first call takes about 500 ms (miss), the other four take under 5 ms (hits). Counter shows 1 miss, 4 hits.
- Add an update method that removes the key. Call it, then read again. Expected: one miss, then hits again.
- Clean-up: delete the CacheLab folder.

11 Revision summary

- Hit ratio = hits divided by total requests. Track it.
- Default pattern: cache-aside. App checks cache, loads on miss, stores with TTL.
- Write-behind is fast but can lose data. Write-through is safer.
- On update, delete the key instead of updating it.
- Stampede: many misses on one key. Penetration: keys that never exist. Avalanche: many keys expire together.
- Fix: locking, negative caching or bloom filter, TTL jitter.
- Always set a TTL. Include tenant and entity id in keys.
- Do not cache exact-value or per-request data.
