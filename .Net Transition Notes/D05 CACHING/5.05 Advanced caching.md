5.05 Advanced caching [P3 O]. This is a SHORT note, so sections 1, 4, 6 and 11 only.

---

1 What is it

- Advanced caching is a set of techniques that go beyond basic cache-aside with a TTL. They cover cases where plain caching is too slow, too heavy on memory, or too weak on consistency.
- You use them when a single Redis cache and simple expiry stop being enough: very hot keys, huge key spaces, cold starts, and multiple regions.
- Legacy equivalent: ASP.NET Framework Application cache and Output Cache with manual warm-up in Application_Start, plus sticky sessions to keep each user on one server.

4 Features and core concepts

- Redis streams: an append-only log inside Redis, with consumer groups. Plain meaning: a lightweight message log. Why it matters: gives you ordered events and replay without a separate broker, but it is not a replacement for Service Bus or Kafka at scale.
- Lua scripts: small scripts that Redis runs atomically on the server. Plain meaning: several Redis commands executed as one indivisible step. Why it matters: fixes race conditions in rate limiters, safe lock release and check-then-set logic without round trips.
- Bloom filters: a compact structure that answers "definitely not present" or "probably present". Plain meaning: a cheap pre-check before hitting the cache or database. Why it matters: blocks cache penetration (requests for keys that never exist). Trade-off: false positives are possible, false negatives are not, and you cannot delete entries from a basic filter.
- Client-side caching: the application keeps a local copy and the server tells it when the key changes (Redis tracking and invalidation messages). Plain meaning: serve hot keys from process memory. Why it matters: removes network latency for the hottest reads. Risk: stale data if invalidation is missed, and more memory per instance.
- Cache warming: filling the cache before traffic arrives. Plain meaning: pre-load known hot data on deploy, restart or failover. Why it matters: avoids a cold-start stampede that overloads the database. Do it with a startup job or a hosted service, throttled.
- Multi-region caches: a cache per region, kept in sync or loosely consistent. Plain meaning: put data near users in each region. Why it matters: lower latency and resilience to a regional outage. Trade-off: replication lag and conflict handling. Check current Azure Redis geo-replication options (verify).
- One thing worth memorizing: in StackExchange.Redis, run a Lua script with db.ScriptEvaluateAsync(script, keys, values). Use it for atomic operations instead of separate GET and SET calls.

6 Real-world use case

- Situation: a booking API on Azure App Service (.NET) with Azure Redis and Azure SQL. Every morning after a deploy, the first minutes of traffic overload SQL because the cache is empty. Searches for non-existent booking IDs also hit SQL every time.
- Choice made: add a warm-up hosted service that loads the top few thousand hot keys at startup, with a concurrency limit. Add a Bloom filter of valid booking IDs in front of the lookup. Use a small Lua script for the per-user rate limit so the check and increment are atomic.
- Trade-off: more moving parts to build, monitor and keep correct. The Bloom filter must be rebuilt as data changes, and the warm-up list can go stale.
- When NOT to use it: if your hit ratio is already good and SQL is not under pressure, skip all of this. Fix basic TTLs and key design first. Do not use client-side caching for data that must always be fresh, such as balances or inventory counts.

11 Revision summary

- Streams give ordered, replayable logs inside Redis, but they are not a full broker.
- Lua scripts make multi-step Redis operations atomic.
- Bloom filter: no false negatives, some false positives, no deletes.
- Bloom filters protect against cache penetration.
- Client-side caching trades freshness risk for the lowest read latency.
- Warm the cache on deploy and failover, and throttle the warm-up.
- Multi-region caches trade consistency for latency and resilience.
- Add these only after basic caching is measured and proven insufficient.
