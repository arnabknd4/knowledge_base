1 What is it
- Redis is an in-memory data store. It keeps data in RAM and answers in well under a millisecond.
- Used as a cache, a session store, a message broker and a counter service.
- Data is stored as typed structures (string, hash, list, set, sorted set, stream), not just plain key and value.
- Single-threaded command execution, so each command is atomic.
- Azure offers it as a managed service: Azure Cache for Redis and Azure Managed Redis (verify which is current and which is being retired).
- Legacy equivalent: in-process HttpRuntime.Cache or Session state in InProc mode, moved out to a shared server. Also resembles the old SQL Server or StateServer session store, but much faster.

2 Why needed
- A database round trip costs milliseconds. Redis cuts that to microseconds for hot data.
- In-process memory cache is per server. With two or more instances, each has a different copy and users see inconsistent data.
- Session data in a web farm needs a shared place. Without it, users get logged out when the load balancer switches servers.
- Without a shared fast store, the database takes all read load and becomes the bottleneck.
- Rate limiting and locks across many instances need one shared counter. Local memory cannot do this.

3 Before you read
- Cache-aside pattern (note 5.01): read cache, on miss read database, then fill cache.
- TTL (time to live): the seconds after which a key expires on its own.
- Difference between in-process cache and distributed cache (note 5.02).
- Basic TCP client-server idea: clients connect to one server over a socket.

4 Features and core concepts
- Data structures. Plain meaning: Redis values have types. Why it matters: the right type removes application code and gives atomic operations.
- String: text, number or bytes up to 512 MB. Use for cached JSON, counters (INCR).
- Hash: a field-value map under one key. Use for an object where you update single fields.
- List: ordered items, push and pop at both ends. Use for simple queues.
- Set: unique unordered items. Use for tags, unique visitors.
- Sorted set: unique items each with a score, kept ordered. Use for leaderboards and delayed jobs.
- Stream: append-only log with consumer groups. Use for event processing.
- TTL. Plain meaning: a key deletes itself after a set time. Why it matters: stops stale data and unbounded memory. Memorize: SET key value EX 300, and TTL key.
- Eviction policies. Plain meaning: what Redis removes when memory is full. Why it matters: wrong policy means errors on write or lost hot keys. Common ones: noeviction, allkeys-lru, volatile-lru, allkeys-lfu, volatile-ttl. Cache use usually picks allkeys-lru or allkeys-lfu (verify Azure default).
- Persistence. Plain meaning: saving memory to disk so data survives restart. RDB is a point-in-time snapshot, compact, can lose recent writes. AOF logs every write, safer, larger and slower. Why it matters: decides how much data you lose in a crash.
- Replication. Plain meaning: a replica copies a primary asynchronously. Why it matters: read scaling and failover. Async means a failover can lose the last few writes.
- Clustering and sharding. Plain meaning: data is split across nodes by hash slot (16384 slots). Why it matters: scale beyond one node's memory. Multi-key commands must hit the same slot, so use hash tags like {user1}.
- Sentinel awareness. Plain meaning: a monitor process that detects a failed primary and promotes a replica. Why it matters: automatic failover for non-cluster setups. Azure manages this for you.
- Azure Cache for Redis and Azure Managed Redis (verify). Plain meaning: Microsoft-hosted Redis with tiers, patching and failover handled for you. Why it matters: you pick a tier and size, not servers. Check Microsoft Learn for current SKUs, retirement dates and limits.
- StackExchange.Redis multiplexer. Plain meaning: one shared ConnectionMultiplexer carries all commands over few connections. Why it matters: creating one per request exhausts sockets and is slow. Memorize: register ConnectionMultiplexer as a singleton in DI.
- Pipelining. Plain meaning: send many commands without waiting for each reply. Why it matters: cuts network round trips. StackExchange.Redis does this automatically for async calls.
- Pub/sub. Plain meaning: publishers send to a channel, live subscribers receive. Why it matters: simple fan-out, but messages are not stored. A subscriber that is offline misses them. Use Streams or Service Bus when delivery matters.
- Distributed locks and their risks. Plain meaning: SET key value NX PX 30000 acquires a lock that expires. Why it matters: stops two instances doing the same job. Risks: lock expires while work continues, failover loses the lock, clock and pause issues. Always release only if you still own it (compare a unique value, use a Lua script). Do not use for correctness-critical work without fencing tokens.
- Rate limiting. Plain meaning: count requests per key per window. Memorize: INCR key, then EXPIRE key 60 on first hit. Why it matters: one shared counter across all API instances.
- Session storage. Plain meaning: user session kept in Redis, with the session id in a cookie. Why it matters: any instance can serve any user. Set a sliding TTL.
- Big key problems. Plain meaning: one huge value or collection. Why it matters: a slow command blocks everyone because Redis runs commands on one thread. Avoid KEYS *, use SCAN. Split large keys.
- Monitoring. Watch: latency, memory used, evictions, cache hit ratio, connected clients, CPU, server load. Why it matters: rising evictions or load mean the cache is undersized.

5 Core focus (exam and interview)
- Most asked: why Redis is fast (memory, single-threaded commands, efficient structures), cache-aside, TTL and eviction, RDB vs AOF, persistence vs durability, cluster vs replication.
- Pick the structure for the job: counter (string INCR), object (hash), leaderboard (sorted set), queue (list or stream), unique count (set).
- Redis is not a durable primary database by default. Treat it as rebuildable.
- Defaults and limits to remember: string max 512 MB, 16384 hash slots, default 16 logical databases on standalone Redis but cluster uses only db 0. Check Azure tier limits (verify).
- Pub/sub has no persistence and no acknowledgement. Streams have consumer groups and acknowledgement.
- Client must reuse ConnectionMultiplexer. Handle transient failures with retry and timeouts.
- Distributed lock safety is a known interview trap. Explain expiry, ownership token and why it is still not perfect.

6 Real-world use case
- Situation: an ASP.NET Core order-lookup API runs on 4 App Service instances. Product catalog reads hit Azure SQL at 2000 requests per second and the database CPU stays high. Users also lose sessions on scale-out.
- Choice: add Azure Redis. Cache catalog JSON with cache-aside and a 10 minute TTL plus a little random jitter. Store sessions in Redis. Use IDistributedCache with StackExchange.Redis as a singleton connection.
- Trade-off: an extra network hop and another service to monitor and pay for. Data can be stale up to the TTL. Cache outage must not take the app down, so the code falls back to the database with a timeout and circuit breaker.
- When NOT to use it: data that must be strongly consistent every read, tiny workloads that one in-memory cache handles, large blobs better served by Blob storage and CDN, or as the only copy of important data.

7 Interview lens
- Q: Why is Redis fast even though it is single-threaded?
  A: Data is in RAM, structures are efficient, and no lock contention or context switching on commands. Network IO is the usual limit, and newer versions use IO threads.
- Q: RDB or AOF?
  A: RDB gives compact snapshots and fast restart but can lose minutes of data. AOF logs writes for less loss but costs more disk and IO. Many setups use both, or none for a pure cache.
- Q: How do you build a safe distributed lock?
  A: SET with NX and a TTL, store a unique token, release with a check-and-delete Lua script. Still unsafe across failover or long pauses, so add fencing tokens for critical work.
- Q: Cache-aside with Redis, what goes wrong?
  A: Stampede on popular key expiry, stale data after a write, and cache penetration for missing keys. Fix with jittered TTL, locking or request coalescing, delete on write, and negative caching.

8 Common mistakes
- New ConnectionMultiplexer per request. Shows as timeouts and socket exhaustion. Fix: one singleton.
- No TTL on keys. Memory grows until evictions or write errors. Fix: always set expiry on cache keys.
- Using KEYS * or huge collections in production. Shows as latency spikes for all clients. Fix: SCAN, split keys.
- Treating Redis as the system of record. Data lost on failover or restart. Fix: keep the source of truth in the database.
- Same TTL for all keys. Mass expiry causes a database spike (avalanche). Fix: add random jitter.
- Ignoring cache failure. App returns 500 when Redis is down. Fix: timeouts, fallback and circuit breaker.
- Unsafe lock release. One instance deletes another's lock. Fix: ownership token and Lua script.

9 Mental model
- Redis is a shared whiteboard next to the busy database clerk.
- Text diagram:
  App instances (many) --> Redis (fast, temporary, shared) --miss--> Azure SQL (slow, permanent)
- Fast and shared, but small and forgetful. Anything you cannot rebuild does not belong only there.

10 Mini lab
- Time: 30 minutes. Local tools only, no Azure cost.
- Steps:
- 1. Run Redis in Docker: docker run -d --name redis-lab -p 6379:6379 redis
- 2. Open the CLI: docker exec -it redis-lab redis-cli
- 3. Try: SET greeting hello EX 20, then GET greeting, then TTL greeting. Wait 20 seconds and GET again.
- 4. Counter: INCR hits three times. Hash: HSET user:1 name Arnab city Kolkata, then HGETALL user:1. Sorted set: ZADD board 50 a 80 b, then ZRANGE board 0 -1 WITHSCORES.
- 5. Lock: SET lock:job1 abc NX EX 30, run it twice, and see the second return nil.
- 6. Create a console app: dotnet new console, dotnet add package StackExchange.Redis. Connect with ConnectionMultiplexer.Connect("localhost:6379"), write a key and read it back.
- Expected result: key disappears after 20 seconds, TTL counts down, INCR returns 1, 2, 3, second NX lock returns nil, the .NET app reads the value it wrote.
- Clean-up: docker rm -f redis-lab

11 Revision summary
- Redis: in-memory, typed structures, sub-millisecond, shared across instances.
- Structures: string, hash, list, set, sorted set, stream. Pick by access pattern.
- Always set TTL. Cache use: allkeys-lru or allkeys-lfu eviction.
- RDB snapshots can lose recent data. AOF logs writes. Replication is asynchronous.
- Cluster has 16384 hash slots. Multi-key operations need the same slot.
- One singleton ConnectionMultiplexer per app.
- Pub/sub is fire and forget. Streams give consumer groups and acknowledgement.
- Locks: SET NX with TTL, unique token, Lua release. Not fully safe.
- Avoid KEYS and big keys. Watch latency, memory, evictions, hit ratio.
- Azure service names and tiers change often (verify on Microsoft Learn).
