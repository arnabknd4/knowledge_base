1 What is it
- A cache is a fast, temporary copy of data kept close to the code, so you skip a slow trip to the database or an API.
- In .NET, the built-in caching APIs are IMemoryCache (inside one process), IDistributedCache (shared across servers, often Redis), HybridCache (combines both, verify it is stable in your target version), plus output caching and response caching (cache whole HTTP responses).
- Legacy equivalent: HttpRuntime.Cache, System.Web.Caching, OutputCache attribute in MVC, and Session state kept in a state server.

----

2 Why needed
- Databases and remote APIs are slow and expensive to call on every request.
- Without caching, repeated reads of the same data hammer SQL Server, raise latency, and cost more.
- Without a distributed cache, each server in a scaled-out app holds its own copy and users see different data.

4 Features and core concepts

IMemoryCache
- Plain meaning: a dictionary inside your app process, with expiry rules. Registered with AddMemoryCache.
- Why it matters: it is the fastest option, with no network and no serialization. Objects are stored by reference.
- Size limits: you set SizeLimit on the cache and a Size on every entry. If a limit is set and an entry has no size, it throws.
- Expiration: absolute (dies at a fixed time) and sliding (timer resets on each read). Use both together, or sliding alone can keep an entry alive forever.
- Eviction callbacks: a method that runs when an entry is removed (expired, removed, capacity, replaced). Why it matters: you can log evictions or refresh data.
- Memorize: GetOrCreateAsync(key, e => { e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5); e.Size = 1; return LoadAsync(); })

IDistributedCache
- Plain meaning: a common interface for a cache that lives outside your app (Redis, SQL Server, NCache). Values are byte arrays or strings.
- Why it matters: all instances share one copy, and data survives an app restart or deploy.
- Cost: every call is a network call plus serialization. It is slower than memory.
- Interface is minimal: Get, Set, Refresh, Remove (plus async versions). No tags, no bulk operations, no atomic updates.

HybridCache (verify)
- Plain meaning: one API that checks local memory first (L1), then the distributed cache (L2), then your factory method.
- Why it matters: it adds stampede protection, so many concurrent requests for the same missing key trigger only one database call. IMemoryCache alone does not do this.
- It supports tags for group invalidation and handles serialization for you. Check the current package name and version on Microsoft Learn.

Output caching
- Plain meaning: the server stores the full HTTP response and replays it for matching requests, without running your endpoint.
- Why it matters: it skips controller, database and serialization work. The server controls it, and you can invalidate by tag.
- Configure with AddOutputCache and UseOutputCache, then [OutputCache] or CacheOutput on endpoints. Policies can vary by query, header or route.

Response caching
- Plain meaning: it sets Cache-Control headers so browsers and proxies cache the response. The server does not hold the data itself.
- Why it matters: it saves bandwidth and server hits, but the client decides, and you cannot purge it. It does not cache requests carrying an Authorization header by default.
- Output caching replaced most uses of the old ResponseCaching middleware for server-side needs.

Two-level cache (local plus distributed)
- Plain meaning: check L1 memory, fall back to L2 Redis, then to the source.
- Why it matters: it cuts network calls for hot keys while keeping a shared copy.

Multi-instance consistency issues
- Plain meaning: with IMemoryCache each server has its own copy, so an update on server A leaves stale data on server B until it expires.
- Why it matters: this causes bugs like "I changed it but still see the old value, sometimes".
- Fixes: short L1 TTLs, Redis pub/sub or tag invalidation to clear L1 on every instance, or use only distributed cache for data that must be consistent.

5 Core focus (exam and interview)
- Most asked: IMemoryCache vs IDistributedCache, and why memory cache breaks when you scale out.
- Sliding expiration without an absolute limit can keep stale data forever.
- IMemoryCache is per process, lost on restart, and stores object references (mutating a cached object changes it for everyone).
- IDistributedCache needs serialization, and the Redis implementation is AddStackExchangeRedisCache.
- Output caching is server-side and tag-invalidated. Response caching is header-based and client-controlled.
- The cache stampede problem: IMemoryCache.GetOrCreateAsync does not lock, so the factory can run several times. HybridCache fixes this.
- Memory cache grows without a size limit and can cause out-of-memory errors.

6 Real-world use case
- Situation: an ASP.NET Core API on Azure App Service, three instances, serving a product catalog that changes a few times a day. SQL Server CPU is high from repeated catalog reads.
- Choice: HybridCache with Azure Cache for Redis (verify current service name) as L2, 5-minute L1 TTL, 30-minute L2 TTL, and tag-based invalidation when an admin edits a product. Output caching on the public catalog list endpoint.
- Trade-off: data can be stale for a few minutes, and you now run and pay for Redis and must handle its outages (fall back to the database, do not fail the request).
- When NOT to use: user-specific or highly volatile data (stock counts, balances), data needing strict consistency, or tiny datasets that are cheap to query. Never cache authenticated responses in a shared cache keyed only by URL.

7 Interview lens
- Q: Why not just use IMemoryCache on a scaled-out app?
- A: Each instance has its own copy, so data diverges and a restart loses it. Use IDistributedCache or HybridCache for shared state.
- Q: What is a cache stampede and how do you stop it?
- A: Many requests miss the same key at once and all hit the database. Use HybridCache, a per-key lock such as SemaphoreSlim, or staggered TTLs.
- Q: Output caching vs response caching?
- A: Output caching stores the response on the server and supports tag invalidation. Response caching only sets headers and relies on clients and proxies.
- Q: How do you keep L1 caches consistent across instances?
- A: Keep L1 TTL short, or broadcast invalidation through Redis pub/sub or HybridCache tags. Accept brief staleness where allowed.

8 Common mistakes
- No SizeLimit on IMemoryCache: memory grows until the app is recycled. Fix: set SizeLimit and entry sizes.
- Caching mutable objects by reference: one request changes shared data for all. Fix: cache immutable DTOs or copies.
- Sliding expiry only: hot keys never refresh. Fix: add an absolute expiration.
- Poor key design (missing tenant or user id): users see each other's data. Fix: build keys with every varying input.
- Treating Redis as always available: an outage takes the API down. Fix: timeouts and fallback to the source.
- Caching null or errors without a plan: failures stay cached. Fix: short TTL for negative results, never cache exceptions.

----

9 Mental model
- Request -> L1 memory (nanoseconds) -> L2 Redis (milliseconds) -> database (tens of ms or more).
- Each step down is slower and more shared. Each step up is faster but may be staler and private to one server.

10 Mini lab (30 minutes)
- Tools: .NET SDK, Docker Desktop (free), a new minimal API project.
- Step 1: dotnet new web -n CacheLab, then add a /slow endpoint that does await Task.Delay(2000) and returns DateTime.UtcNow.
- Step 2: Add AddMemoryCache. Wrap the endpoint with GetOrCreateAsync, 30 second absolute expiry. Call it twice and confirm the second call is instant with the same timestamp.
- Step 3: Run Redis: docker run -d --name lab-redis -p 6379:6379 redis. Add Microsoft.Extensions.Caching.StackExchangeRedis and AddStackExchangeRedisCache with localhost:6379.
- Step 4: Add a /dist endpoint using IDistributedCache with SetStringAsync and GetStringAsync. Run two copies of the app on ports 5001 and 5002. Expected: both return the same cached value.
- Step 5: Repeat with IMemoryCache on both ports. Expected: different values, which shows the consistency problem.
- Step 6: Add AddOutputCache with a 10 second policy on /slow, and confirm repeat calls skip the 2 second delay.
- Clean-up: docker rm -f lab-redis and delete the CacheLab folder.

11 Revision summary
- IMemoryCache is per process, fastest, stores references, and needs SizeLimit.
- IDistributedCache is shared, serialized, byte-based, with a minimal API.
- HybridCache = L1 plus L2 plus stampede protection plus tags (verify version).
- Output caching is server-side with tag purge. Response caching is header-based.
- Use absolute plus sliding expiry together.
- Scaled-out apps with only IMemoryCache serve inconsistent data.
- Include every varying input in the cache key.
- Cache failures must degrade to the source, not break the request.
