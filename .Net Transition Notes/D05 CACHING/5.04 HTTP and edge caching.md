Topic 5.04 is HTTP and edge caching [P2 R L], so this is a FULL note for a topic that is new to you.

---

1 What is it

- HTTP caching is the set of rules (headers) that tell browsers, proxies and CDNs whether they may reuse a stored copy of a response instead of asking the origin server again.
- Edge caching means a CDN (Content Delivery Network, a set of servers spread across many cities) keeps copies of your responses close to users.
- Legacy equivalent: IIS output caching and client-side caching settings in web.config (clientCache, staticContent expiration), plus ASP.NET MVC OutputCache attributes.

2 Why needed

- Every request that reaches your server costs CPU, database calls and money. Cached responses cost almost nothing.
- Users far from your region (example: Kolkata users hitting a Central US app) see high latency. An edge copy served from a nearby location removes that distance.
- Without it, static files are re-downloaded on every visit, traffic spikes hit the origin directly, and a CDN can do little for you.

3 Before you read

- HTTP request and response basics: headers, status codes, GET vs POST.
- What a browser cache is (the local copy your browser keeps).
- What a reverse proxy is: a server standing in front of your app and forwarding requests.
- Idea of a hash or version in a filename (for example app.3f9a1c.js).

4 Features and core concepts

- Cache-Control: the main header that sets caching rules. Why it matters: it controls everything else.
  Example: Cache-Control: public, max-age=3600
  Common values: public (any cache may store), private (browser only, not shared caches), no-store (never store), no-cache (store, but revalidate before reuse), immutable (will never change).
- max-age: seconds a response stays fresh in any cache. Why it matters: during this time the browser makes no request at all.
- s-maxage: seconds a response stays fresh in shared caches (CDN, proxy) only, overriding max-age there. Why it matters: lets the CDN keep a copy for an hour while browsers keep it for a minute.
- ETag and If-None-Match: the server sends a fingerprint (ETag) of the response. The client later sends it back in If-None-Match. If unchanged, the server replies 304 Not Modified with no body. Why it matters: saves bandwidth, not the round trip.
- Last-Modified (and If-Modified-Since): the same idea using a timestamp instead of a fingerprint. Why it matters: simpler but less precise than ETag.
- Vary: names request headers that change the response (example: Vary: Accept-Encoding). Why it matters: without it, a cache may serve a gzip copy to a client that cannot read it. Vary: * or Vary: Cookie effectively kills sharing.
- Fingerprinted assets: files named with a content hash, so a changed file gets a new URL. Why it matters: you can cache them for a year with immutable and never serve stale files. Angular builds do this by default.
- CDN (Azure Front Door, Azure CDN): servers at many points of presence that cache and serve your content. Why it matters: lower latency and less load on origin. (verify) current Azure CDN product lineup, as Microsoft has been retiring some CDN SKUs in favour of Front Door.
- Purge: removing cached content from the CDN before it expires. Why it matters: it is your emergency fix for a bad or stale cached response.
- Caching authenticated content risks: a shared cache may store a response meant for one user and serve it to another. Why it matters: this is a real data leak. Use private or no-store for per-user data.
- Reverse-proxy caching awareness: Nginx, YARP or IIS ARR can cache in front of your app. Why it matters: it is another cache layer you must account for when debugging stale data.

ASP.NET Core setting worth memorizing:
- builder.Services.AddResponseCaching(); app.UseResponseCaching();
- [ResponseCache(Duration = 60, Location = ResponseCacheLocation.Any)] on an action sets the Cache-Control header.

5 Core focus (exam and interview)

- Freshness vs validation: fresh means reuse with no request; stale means revalidate with ETag or Last-Modified.
- no-cache does not mean "do not cache". no-store means do not cache. This is the most common trap.
- public vs private decides whether CDNs may store the response.
- s-maxage applies only to shared caches and wins over max-age there.
- Cache key: normally the URL plus any Vary headers. Query strings may or may not be part of the key (depends on the CDN setting) (verify per product).
- Browsers do not cache POST responses in practice. Cache GET only.
- Azure Front Door can cache at the edge and respects origin headers by default, with rules to override (verify).
- Authorization-header requests are not stored by shared caches unless the response explicitly allows it.

6 Real-world use case

- Situation: an Angular front end plus ASP.NET Core API on Azure App Service, users across India, slow first load, high origin traffic.
- Choice: put Azure Front Door in front. Hashed JS/CSS get Cache-Control: public, max-age=31536000, immutable. index.html gets no-cache so users always revalidate and pick up new hashes. Public catalog API responses get s-maxage=60 with an ETag. User-specific endpoints get private, no-store.
- Trade-off: stale data for up to 60 seconds on catalog responses, and extra work for purge during releases.
- When NOT to use it: personalised or per-user responses, rapidly changing data like stock levels, or anything where showing stale data has a cost. Do not cache authenticated content in a shared cache unless the key varies per user.

7 Interview lens

- Q: Difference between no-cache and no-store?
  A: no-cache allows storing but forces revalidation before reuse. no-store forbids storing the response at all.
- Q: How do you cache static assets for a year and still ship updates?
  A: Fingerprint filenames with a content hash and set max-age=31536000, immutable. A new build produces new URLs, while index.html stays no-cache.
- Q: What does ETag give you if the browser still makes a request?
  A: A 304 response with no body, so bandwidth and server work drop. The round trip remains.
- Q: How can caching leak user data?
  A: A shared cache stores a per-user response and serves it to others. Prevent it with Cache-Control: private or no-store and a correct Vary.

8 Common mistakes

- Using no-cache thinking it disables caching. Shows up as unexpected extra requests or, the reverse, sensitive data stored. Fix: use no-store for secrets.
- Caching index.html for a long time. Shows up as users running old JS after a release. Fix: no-cache on index.html, long cache on hashed assets.
- Missing Vary: Accept-Encoding or Vary: Origin. Shows up as garbled content or CORS failures from the CDN. Fix: set Vary correctly.
- Cookies on responses. Many CDNs refuse to cache responses that set cookies. Shows up as a zero hit ratio. Fix: remove Set-Cookie from cacheable routes.
- Forgetting to purge after a hotfix. Fix: add a purge step to the release pipeline.
- Cache key includes random query strings (tracking parameters). Shows up as low hit ratio. Fix: ignore or normalize them at the CDN.

9 Mental model

User browser cache -> CDN edge cache -> origin (App Service / API)

- Each layer asks: "Is my copy fresh? If stale, can I revalidate cheaply?" Only if both answers are no does the request travel to the next layer.
- Think of two dials: how long a copy is fresh (max-age, s-maxage) and who may keep it (public, private).

10 Mini lab (about 30 minutes)

Goal: see freshness and validation headers working, locally.
- Step 1: dotnet new web -o CacheLab, then cd CacheLab.
- Step 2: in Program.cs add a GET /time endpoint that sets Response.Headers.CacheControl = "public, max-age=30" and returns DateTime.UtcNow.ToString("O").
- Step 3: add a GET /data endpoint that returns a fixed string and sets an ETag header ("v1"). If the request header If-None-Match equals "v1", return Results.StatusCode(304).
- Step 4: run with dotnet run. Open Chrome DevTools, Network tab, leave Disable cache unticked.
- Step 5: load /time twice within 30 seconds. Expected: second load shows "(memory cache)" or "(disk cache)" and the same timestamp. Wait 30 seconds, reload: new timestamp.
- Step 6: run curl -i https://localhost:PORT/data, note the ETag, then curl -i -H "If-None-Match: \"v1\"" https://localhost:PORT/data. Expected: 304 with no body.
- Step 7: change /time to Cache-Control: no-store and confirm each reload gets a new timestamp.
- Clean-up: stop the app and delete the CacheLab folder.

11 Revision summary

- Cache-Control is the master header: max-age for browsers, s-maxage for shared caches.
- no-cache means revalidate before reuse; no-store means never store.
- ETag plus If-None-Match gives a 304 with no body; it saves bandwidth, not the round trip.
- Hash the filename, cache for a year with immutable; keep index.html at no-cache.
- Vary lists the request headers that change the response; Vary: Cookie breaks sharing.
- Per-user data: private or no-store, never public.
- Purge is the emergency lever on a CDN; add it to the release pipeline.
- Cookies and random query strings are the usual causes of a poor CDN hit ratio.
