1 What is it
- A portfolio write-up is a short, public-facing document set that explains one project you built: what it does, how it is designed, what decisions you made, and what you learned.
- For you, the project is the capstone. The set is: README, architecture diagram, ADRs (Architecture Decision Records), postmortem, cost estimate, "what I would change", and an honest label for lab vs production work.
- Define terms: ADR = a one-page record of one design decision. Postmortem = a blameless write-up of one failure and its fix. Capstone = the project you build during this study plan.
- Legacy equivalent: the project handover document or Word design document in a .NET Framework project, but shorter, kept in the repo, and written for an outside reader.

2 Why needed
- Interviewers and recruiters cannot see your 12 years of private client code. A repo with clear write-ups is the only proof they can open.
- Without it, a good capstone looks like a folder of code. Reviewers skim for 2 minutes and leave.
- It forces you to explain trade-offs, which is the core skill tested in architect interviews.
- It keeps your claims honest, which protects your credibility in background checks and technical rounds.

3 Before you read
- You should have at least a rough capstone running (Batch 2 onwards).
- Know what a C4 diagram is (topic 15.01 covers it fully).
- Know basic Markdown and Git hosting (GitHub or Azure DevOps repo).

4 Features and core concepts
- Capstone README
  - Plain meaning: the front page of the repo. Answers what, why, how to run, and what to read next.
  - Why it matters: most reviewers read only this file.
  - Order to use: one-line purpose, problem statement, architecture diagram, tech stack, how to run in 5 commands, links to ADRs, status, honest limits.
- Architecture diagram
  - Plain meaning: one picture of the system parts and how they talk.
  - Why it matters: shows you can think at system level, not just code level.
  - Keep it to C4 level 1 (context) and level 2 (containers). Store as Mermaid text in the repo so it can be edited.
- ADRs
  - Plain meaning: one short file per decision. Fields: context, options, decision, consequences, status.
  - Why it matters: shows reasoning, not just results. Architect interviews test this directly.
  - Write 4 to 6 for the capstone. Example titles: why Service Bus over Event Grid, why modular monolith first, why Terraform over Bicep.
  - Memorize the file name pattern: docs/adr/0001-title.md
- Postmortem
  - Plain meaning: a blameless account of one real failure in your project, such as a bad deploy, a lost message, or a cost spike.
  - Why it matters: proves you can operate systems, not only build them.
  - Sections: summary, timeline, impact, root cause, what went well, what went badly, action items.
  - If nothing failed, cause a safe failure on purpose in the lab and write it up. Label it as a drill.
- Cost estimate
  - Plain meaning: a monthly cost table for the capstone if it ran for real, at small and medium scale.
  - Why it matters: architects are asked about cost in every design round.
  - Use the Azure Pricing Calculator. Show assumptions (region, SKU, traffic) and one saving you would make. Prices change (verify) before you publish.
- What I would change
  - Plain meaning: a short honest list of weaknesses and next steps.
  - Why it matters: shows judgment and self-awareness. Interviewers trust people who name their own flaws.
  - Three to five items, each with the reason and the rough effort.
- Describing lab vs production work honestly
  - Plain meaning: clearly label what ran on real users and what was a practice build.
  - Why it matters: a false claim found in an interview ends the process. Honest framing still scores well.
  - Use plain labels: "Built in lab", "Ran in production at client X (details withheld)", "Based on a real project, rebuilt from scratch".
  - Never paste client code, names, or data. Rebuild the idea from scratch.

5 Core focus (exam and interview)
- Most asked: "Walk me through a design decision you made and what you gave up."
- Most asked: "What would you do differently?"
- Know the ADR fields by heart: context, options, decision, consequences, status.
- Know the postmortem rule: blameless, focus on system and process, not people.
- Know the C4 levels: context, container, component, code.
- Limit to remember: one README page. If it needs scrolling through many screens, split detail into docs/.
- Limit to remember: ADRs are short, about half a page each.
- Not an exam topic for Azure certifications. It is an interview and hiring topic.

6 Real-world use case
- Situation: you built an order-processing capstone with ASP.NET Core API, Service Bus, Azure SQL and Container Apps, deployed by Azure DevOps and Terraform.
- Choice made: you wrote a README with a C4 container diagram, five ADRs, one postmortem from a dead-letter queue incident you triggered, and a cost sheet.
- Result: a recruiter or hiring manager can judge your design thinking in 10 minutes without running anything.
- Trade-off: writing takes about 8 to 12 hours across the project and delays new features.
- When NOT to do it: do not write all documents up front. Write ADRs when you decide, the postmortem when something breaks, and the README last. Do not write portfolio documents for a throwaway lab you will not show anyone.

7 Interview lens
- Q: Tell me about an architecture decision you documented.
  - A: Name the ADR, the two options, the deciding factor, and the cost you accepted. Close with how you would revisit it.
- Q: How do you separate lab work from production work on your resume?
  - A: I label each project as lab, personal or client work. I describe only what I personally did and never claim scale I did not run.
- Q: What does a good postmortem contain?
  - A: Timeline, impact, root cause, what worked, and owned action items. It is blameless and ends in changes to the system.
- Q: What would you change in your capstone?
  - A: Name two or three real weaknesses, such as no multi-region failover or weak load testing, with the reason and the fix.

8 Common mistakes
- README that only lists tools. Shows up as recruiters seeing a stack but no thinking. Fix: lead with the problem and the decisions.
- ADRs written after the fact for decisions never made. Shows up as vague or fake-sounding reasons. Fix: write each ADR on the day you decide, even if short.
- Diagram that is a screenshot with no source. Shows up as outdated pictures. Fix: keep Mermaid or Structurizr text in the repo.
- Cost estimate with no assumptions. Shows up as numbers nobody can check. Fix: list region, SKU, traffic and date.
- Overstating scale or experience. Shows up as a failed follow-up question in the interview. Fix: use the honest labels above.
- Copying client code or data into a public repo. Shows up as a legal or contract problem. Fix: rebuild from scratch with fake data.

9 Mental model
- Think of it as a museum plaque next to your exhibit.
- The capstone is the exhibit. The write-up is the plaque: what it is, why it was built this way, what broke, what it costs, what you would fix.

  README (front door)
    -> diagram (map)
    -> ADRs (why)
    -> postmortem (what broke)
    -> cost sheet (what it costs)
    -> what I would change (honesty)

10 Mini lab (30 to 40 minutes)
- Use a local Git repo with any small project, or your capstone folder.
- Step 1: create the folders docs/adr and docs/postmortems.
- Step 2: write docs/adr/0001-first-decision.md with five headings: Context, Options, Decision, Consequences, Status. Use a real decision you already made, such as the choice of database.
- Step 3: create a Mermaid diagram in README.md inside a mermaid code block with three boxes: Client, API, Database. Push to GitHub and check that it renders.
- Step 4: add a README section "Honest status" with three lines: what works, what is lab only, what is missing.
- Step 5: open the Azure Pricing Calculator (free) and estimate the monthly cost of your three boxes. Save the numbers and assumptions in docs/cost.md.
- Expected result: a repo where a stranger can learn the purpose, the picture, one decision and the cost in under 5 minutes.
- Clean-up: nothing to delete in Azure, since the calculator creates no resources. Delete the test repo if it was only practice.

11 Revision summary
- Write-up set: README, diagram, ADRs, postmortem, cost estimate, what I would change.
- ADR fields: context, options, decision, consequences, status.
- Postmortem is blameless: timeline, impact, root cause, actions.
- Keep diagrams as text (Mermaid) in the repo, at C4 context and container level.
- Cost estimate always lists assumptions, and prices need (verify).
- Label work as lab, personal or client. Never overstate scale.
- Never publish client code or data.
- Write each document when the event happens, README last.
