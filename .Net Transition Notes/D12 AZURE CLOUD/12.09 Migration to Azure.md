1 What is it

Migration to Azure is the planned process of moving existing applications, databases and servers from on-premises or another host into Azure. It covers choosing a strategy for each workload, discovering what you have, assessing readiness and cost, moving it, and cutting over safely.
- Azure Migrate: the central hub in Azure that discovers servers, assesses them and helps move them.
- The six Rs: six labels for what you do with each application (rehost, refactor, rearchitect, rebuild, replace, retire or retain).
- Cutover: the moment production traffic switches from the old system to the new one.

Legacy equivalent: moving an IIS-hosted .NET Framework app from one data centre server to another by hand, with a weekend downtime window, copied web.config files and a restored SQL backup.

2 Why needed

- Most enterprise estates have hundreds of apps. Without a method, teams move things randomly and miss hidden dependencies.
- Without assessment, you size Azure resources wrongly. You overpay or the app runs slowly.
- Without a cutover plan and a rollback plan, a failed move means a long outage.
- Without a business case, leadership cannot see why the move is worth the cost.
- Not every app should move. Some should be retired. Some should be replaced by a SaaS product.

4 Features and core concepts

- The six Rs (strategy per workload).
  - Rehost: move as is, VM to VM. Also called lift and shift. Fastest, lowest risk, least cloud benefit.
  - Refactor: small changes to use a managed service, for example IIS app to App Service, SQL Server to Azure SQL. Also called replatform. Good balance of effort and gain.
  - Rearchitect: change the design, for example monolith to microservices or queue-based design. High effort, high gain.
  - Rebuild: rewrite from scratch on cloud-native services. Highest effort. Used when the code is beyond saving.
  - Replace: drop the custom app and buy SaaS. Needs data migration and user change.
  - Retire or retain: switch off what nobody uses, or keep on-premises what cannot move yet (compliance, latency, licensing).
  - Why it matters: one strategy for all apps is the classic mistake. Each app gets its own R.
- Azure Migrate (discovery, assessment, migration).
  - Discovery: an appliance scans your servers and collects configuration, performance and installed software. It shows what really exists.
  - Assessment: it recommends VM size, estimates monthly cost and flags readiness problems (unsupported OS, for example).
  - Migration: server migration replicates VMs to Azure and lets you test and cut over.
  - Why it matters: decisions come from measured data, not guesses. Use performance-based sizing, not just current hardware size.
- App Service Migration Assistant.
  - A tool that checks an IIS site for compatibility with Azure App Service and moves it if suitable.
  - Why it matters: this is the quick path for legacy .NET Framework web apps that need little change.
- Database Migration Service (DMS).
  - Moves databases to Azure SQL targets, offline or with minimal downtime (online).
  - Why it matters: data is the hardest part of any cutover. Online mode keeps the downtime window short.
  - Related: Data Migration Assistant (DMA) checks compatibility before the move (see 4.07).
- Site Recovery.
  - Replicates VMs continuously to Azure. Originally built for disaster recovery. Also used for migration.
  - Why it matters: it gives a test failover without touching production.
- Cutover planning.
  - A written sequence of steps: freeze changes, final sync, switch DNS, smoke test, go or no-go, rollback trigger.
  - Why it matters: rehearse it at least once in a test run.
- Dependency mapping.
  - A view of which servers talk to which on which ports.
  - Why it matters: moving a web server without its database or file share breaks the app. Group dependent servers in the same wave.
- Business case and TCO.
  - TCO is total cost of ownership: hardware, licences, power, staff, support compared with Azure cost.
  - Why it matters: leadership approves money based on this. Include migration effort cost, not only run cost.
- Migration waves.
  - Batches of apps moved together. Start with low-risk apps to learn, then move critical ones.
  - Why it matters: it limits risk and lets the team improve the process each wave.
- Hybrid connectivity.
  - Site-to-site VPN or ExpressRoute links on-premises to Azure so both sides talk during the move.
  - Why it matters: apps are rarely moved all at once. Moved apps still call on-premises systems.
- Legacy .NET Framework on App Service, VMs and Windows containers.
  - App Service (Windows) runs many .NET Framework apps with small changes.
  - VMs run anything, including apps with Windows services or custom installers.
  - Windows containers package the app without full VM overhead, but need Windows-based hosts.
  - Why it matters: this is your real-world situation. Pick by how much the app depends on the OS.
- Command worth memorizing: az migrate is not a core command. Remember the Azure portal flow: Azure Migrate project, Discover, Assess, Migrate (verify current portal names).

5 Core focus (exam and interview)

- Know the six Rs and match a described situation to one.
- Rehost equals least change. Rearchitect and rebuild equal most change.
- Azure Migrate has discovery and assessment tools plus migration tools (verify current tool names).
- Assessment uses performance-based sizing for better right-sizing.
- Site Recovery can be used for migration as well as disaster recovery.
- DMS supports offline and online migration (online needs a premium-type tier in some targets, verify).
- Azure Hybrid Benefit reduces cost when you bring existing Windows Server or SQL Server licences with Software Assurance (verify eligibility).
- Interviewers ask: how do you choose a strategy, how do you reduce downtime, how do you handle dependencies, how do you prove the business value.

6 Real-world use case

- Situation: a client has 40 legacy .NET Framework apps, SQL Server 2014 and file shares in a Kolkata data centre. The lease ends in 12 months.
- Choice made: run Azure Migrate discovery for 4 weeks. Classify apps. Retire 6 unused apps. Rehost 15 VM-bound apps. Refactor 15 web apps to App Service with Azure SQL. Replace 2 with SaaS. Retain 2 on-premises for a vendor licence. Move in four waves, each with a rehearsed cutover and VPN link between sites.
- Trade-off: rehost is fast but keeps VM patching work and cost. Refactor takes more testing per app but lowers run effort.
- When NOT to use it: do not rehost everything just for speed if the goal is cost saving, because rehosted VMs often cost more than the old hardware. Do not refactor an app that is retiring in a year.

7 Interview lens

- Q: How do you decide between rehost and refactor?
  A: I look at deadline, app age, OS and code dependencies, and business value. Tight deadline or unsupported code means rehost first, then improve later. Healthy code with a long life means refactor to managed services.
- Q: How do you keep downtime low for a database move?
  A: I use online migration with continuous sync, then a short final cutover. I rehearse in a test run and keep the old database read-only as the rollback path.
- Q: Why is dependency mapping important?
  A: Servers that talk to each other must move together or be linked by a stable network path. Missing one dependency causes failures after cutover.
- Q: How do you build the business case?
  A: I compare current TCO with Azure run cost plus one-time migration cost. I add risk, agility and licence effects, and show payback time.

8 Common mistakes

- Sizing Azure VMs from old hardware specs. Shows up as high bills. Fix: use performance-based assessment.
- Skipping discovery. Shows up as surprise servers and broken dependencies. Fix: run discovery for a full business cycle (month end included).
- Moving apps without moving their database or file shares. Shows up as high latency across the VPN. Fix: move dependent groups in one wave.
- No rollback plan. Shows up as long outages after a failed cutover. Fix: keep the source intact and define a rollback trigger before cutover.
- Treating migration as a one-time technical task. Shows up as unhappy users and missed training. Fix: plan communication, training and support.
- Ignoring licences and compliance. Shows up as audit findings. Fix: check licence terms and data residency early.

9 Mental model

Think of moving house with a plan:

Inventory (discover) -> Decide what to keep, sell, or throw away (six Rs) -> Pack in groups (waves) -> Rehearse the van route (test migration) -> Move day (cutover) -> Keep the old keys for a while (rollback) -> Cancel the old lease (decommission)

10 Mini lab

Time: about 30 minutes. Goal: see an Azure Migrate project and an assessment workflow without moving real servers.
- Step 1: Sign in to the Azure portal with a free-tier subscription.
- Step 2: Search for Azure Migrate and create a project in a new resource group named rg-migrate-lab, choosing a nearby region.
- Step 3: Open the Discover, Assess and Migrate section and read the tools listed for servers, databases and web apps (verify names in the portal).
- Step 4: Open Azure Migrate, then the web apps option, and download the App Service Migration Assistant details page (verify location). If you have a small local .NET Framework site in IIS, note what checks it reports.
- Step 5: Open the Azure pricing calculator and price one D2s-type VM against an App Service plan for a small web app. Write the difference down.
- Expected result: an empty Azure Migrate project, a list of tools, and a cost comparison showing what a refactor to App Service can save over a VM.
- Clean-up: delete the resource group rg-migrate-lab so nothing is billed.

11 Revision summary

- Six Rs: rehost, refactor, rearchitect, rebuild, replace, retire or retain.
- Rehost is fastest. Rebuild is the most work.
- Azure Migrate does discovery, assessment and migration.
- Use performance-based sizing to avoid overpaying.
- Map dependencies and move dependent servers in the same wave.
- DMS moves databases, online mode keeps downtime short.
- Hybrid connectivity (VPN or ExpressRoute) is needed while apps are split across sites.
- Always rehearse cutover and keep a rollback path.
