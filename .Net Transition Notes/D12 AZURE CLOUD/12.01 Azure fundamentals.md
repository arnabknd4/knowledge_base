1 What is it
- Azure fundamentals are the basic building blocks and rules of Azure. They cover how your account, subscriptions and resources are organized, where things physically run, and how you manage them.
- A tenant is your organization's identity boundary in Microsoft Entra ID (the Azure identity service). A subscription is a billing and access boundary that holds resources. A resource group is a folder-like container for related resources.
- Azure Resource Manager (ARM) is the single control layer through which every create, update and delete request passes, whether it comes from the portal, CLI or code.
- Legacy equivalent: like Active Directory domain plus data center rack and cost-center structure in an on-premises .NET Framework setup, with IIS servers grouped by project and managed by one admin console.

----------------------------------------

2 Why needed
- Without structure, resources scatter, nobody knows who owns what, costs cannot be split, and one wrong click can delete production.
- This layer gives you access control at the right level, cost tracking per team, protection from accidental deletion, and a consistent way to automate.
- Every later topic (networking, compute, security, cost) sits on top of these ideas. Wrong subscription or region design is expensive to undo.

----------------------------------------

3 Before you read
- Identity means proving who a user or app is (login) versus what they may do (permission).
- A data center is a building with servers, power and cooling. A region is a group of them in one area.
- REST API means calling a URL with a verb like GET or PUT to manage something.
- SLA (service level agreement) is a promised uptime percentage with credits if missed.

----------------------------------------

4 Features and core concepts
- Tenant: one dedicated Entra ID directory for an organization. It holds users, groups and apps. Why it matters: it is the identity root; one tenant can trust many subscriptions.
- Management group: a container above subscriptions. Why it matters: apply policy and access once to many subscriptions. Up to six levels deep, excluding the root (verify).
- Subscription: a billing and access boundary with its own quotas. Why it matters: separate prod and dev, or team budgets, by using separate subscriptions.
- Resource group: a logical container for resources that share a lifecycle. Why it matters: delete the group and everything in it is removed. Each resource lives in exactly one group, and the group's own location only stores metadata.
- Resource provider: a service namespace that must be registered in a subscription before use, for example Microsoft.Compute. Why it matters: "not registered" errors on first use of a service.
- Region: a set of data centers in one geography. Why it matters: affects latency, price, data residency and which services are available.
- Availability zone: physically separate data centers inside one region with independent power and network. Why it matters: spreading VMs across zones survives a data center failure.
- Paired region: Microsoft's designated partner region for disaster recovery and staged updates (verify current pairings). Why it matters: some geo-redundant storage replicates to the pair.
- ARM: the deployment and management layer behind all tools. Why it matters: same permissions, tags and locks apply no matter which tool you use. ARM templates and Bicep are its declarative formats.
- Locks: CanNotDelete or ReadOnly, set on a subscription, group or resource. Why it matters: protects from accidental delete even for owners. A lock overrides RBAC.
- Tags: name and value pairs on resources. Why it matters: cost reporting and ownership (for example env=prod, owner=team-a). Tags are not inherited by default.
- Quotas: per-subscription limits on resources such as vCPU cores per region. Why it matters: deployments fail until you request an increase.
- Pricing models: pay-as-you-go, reservations, savings plans, spot, free tier (verify details). Why it matters: the same workload can differ greatly in cost.
- SLA: composite uptime depends on chaining services. Two services in series multiply their percentages. Why it matters: the combined figure is lower than either.
- Portal, CLI, PowerShell, Cloud Shell: the portal is a web UI, CLI (az) and PowerShell are scripting tools, Cloud Shell is a browser-hosted terminal with them preinstalled. Why it matters: scripts are repeatable, clicking is not.
- Resource Graph: a fast query service across subscriptions using KQL (Kusto Query Language). Why it matters: inventory questions like "all VMs without tags" in seconds.
- Naming conventions: a consistent pattern such as type-workload-env-region-instance. Why it matters: some names are globally unique (storage accounts) and cannot be renamed later.
- Commands to memorize:
  - az login
  - az account set --subscription "<name>"
  - az group create -n rg-demo-dev-cin-001 -l centralindia
  - az graph query -q "Resources | summarize count() by type"

5 Core focus (exam and interview)
- Hierarchy order: management group, subscription, resource group, resource. Access and policy inherit downward.
- A resource moves between groups or subscriptions only if the resource type supports it (verify per service).
- RBAC (role-based access control) assigned at a higher scope flows down. Locks also inherit downward.
- Region choice affects latency, price, compliance and service availability. Not every region has zones (verify).
- Deleting a resource group deletes all resources in it.
- Tags are not inherited unless you enforce it with Azure Policy.
- Subscription limits and quotas are per region; request increases through support.
- Know the difference: tenant (identity) versus subscription (billing and resources). A subscription trusts exactly one tenant, and a tenant can have many subscriptions.

6 Real-world use case
- Situation: a company moves an IIS-hosted .NET Framework monolith to Azure with separate dev, test and prod, and finance wants cost per team.
- Choice: one tenant, a management group each for non-prod and prod, a subscription per environment, resource groups per application and environment, mandatory tags (owner, cost-center, env), a CanNotDelete lock on prod groups, and naming rules agreed up front.
- Trade-off: more subscriptions mean more setup and cross-subscription networking, but give clean quotas, billing and blast-radius limits.
- When NOT to use it: a small team with one app does not need many management groups or subscriptions. One subscription with a few resource groups is enough until real boundaries appear.

7 Interview lens
- Q: Difference between tenant and subscription?
  - A: A tenant is the identity directory. A subscription is a billing and resource container that trusts one tenant.
- Q: When would you add a new subscription instead of a resource group?
  - A: When you need separate billing, quota limits, access boundaries or policy scope, such as prod versus dev.
- Q: What is the difference between a region and an availability zone?
  - A: A region is a geographic area. Zones are separate data centers inside it, so zone-redundant design survives a data center failure but not a regional one.
- Q: How do you stop someone deleting a production database by mistake?
  - A: Apply a CanNotDelete lock at resource group or resource scope, together with least-privilege RBAC. Locks override owner permissions until removed.

8 Common mistakes
- Everything in one subscription and one resource group. Shows up as tangled costs and hard-to-scope permissions. Fix: plan hierarchy early and split by environment.
- Assuming tags inherit. Shows up as empty cost reports. Fix: use Azure Policy to require or inherit tags.
- Ignoring quotas. Shows up as failed deployments late in a release. Fix: check and request vCPU quota before go-live.
- Poor resource names. Shows up as unreadable portals and name clashes on global names. Fix: adopt one convention and a naming policy.
- Picking a region only by price. Shows up as latency or compliance problems. Fix: weigh latency, residency, services and zones.
- Forgetting locks block legitimate changes. Shows up as pipelines failing on delete or update. Fix: document locks and scope them narrowly.

9 Mental model
Think of a company building:

Tenant = the company (who you are)
  Management group = a floor
    Subscription = a department with its own budget
      Resource group = a project room
        Resource = a desk, server or tool in that room

Region = the city. Zone = a separate building in that city. ARM = the front desk every request must pass through.

10 Mini lab
Goal: build a small structure, tag, lock, query and clean up. Use the Azure free account (verify current free offer) and Cloud Shell.
- Step 1: open Cloud Shell (Bash) in the portal.
- Step 2: run az group create -n rg-lab-dev-cin-001 -l centralindia --tags env=dev owner=arnab
- Step 3: create a free-cost resource, a storage account with a unique name: az storage account create -n <uniquename> -g rg-lab-dev-cin-001 -l centralindia --sku Standard_LRS
- Step 4: add a lock: az lock create --name nodelete --lock-type CanNotDelete -g rg-lab-dev-cin-001
- Step 5: try az group delete -n rg-lab-dev-cin-001. Expected result: it fails with a lock error.
- Step 6: run az graph query -q "Resources | where tags.env == 'dev' | project name, type, location". Expected result: your storage account is listed. If the command is missing, run az extension add --name resource-graph first.
- Step 7: in the portal, open Subscriptions and note your quota under Usage + quotas for the region.
- Clean-up: az lock delete --name nodelete -g rg-lab-dev-cin-001, then az group delete -n rg-lab-dev-cin-001 --yes.
