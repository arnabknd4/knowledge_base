1 What is it
- Azure Monitor is the single platform in Azure that collects, stores, analyzes and acts on telemetry (numbers and text records) from your apps and resources.
- Metrics are small numeric samples over time (CPU percent, request count). Logs are text or structured records (errors, requests, audit events). You query logs with KQL (Kusto Query Language).
- Alerts watch metrics or logs and notify people or trigger actions. Action groups are the list of "who or what to notify".
- Application Insights is the part of Azure Monitor focused on your application code (requests, dependencies, exceptions, traces).
- Backup and Site Recovery protect data and whole workloads, Update Manager patches VMs, and Automation runbooks run scripts for operations.
Legacy equivalent: Windows Performance Monitor, Event Viewer, IIS logs, log4net files and SCOM or Nagios alerts, now in one managed service.

2 Why needed
- Without it you find out about outages from users, not from alerts.
- Without central logs you remote into servers and read files one by one.
- Without autoscale rules you pay for peak capacity all day or fall over at peak.
- Without backup and recovery planning, one deletion or region failure can mean permanent loss.
- Without patching, VMs drift into known vulnerabilities.

3 Before you read
- A resource (VM, App Service, SQL Database) is the thing being watched.
- Telemetry means data a system emits about itself: numbers, logs, traces.
- A Log Analytics workspace is a database where logs are stored and queried.
- RPO (how much data you can lose) and RTO (how long you can be down) are recovery targets.

4 Features and core concepts
- Azure Monitor metrics: numeric time series, collected automatically for most resources, kept 93 days (verify). Cheap and near real time, so use them for fast alerts and autoscale.
- Azure Monitor logs: records stored in a Log Analytics workspace. Good for deep search and joins across resources. Billed by data ingested and retained.
- Alerts: a rule (metric, log query or activity log condition) that fires when a threshold is met. Alerts have a severity from 0 (critical) to 4 (verbose).
- Action groups: reusable set of notifications (email, SMS, push, voice) and actions (webhook, Function, Logic App, runbook, ITSM). One group can serve many alerts, so you define it once.
- Autoscale: rules that add or remove instances based on a metric or schedule (VM scale sets, App Service plan). Set a minimum, maximum and default, plus a cool-down, to avoid flapping.
- Log Analytics and KQL basics: you write queries as a pipeline of operators. Worth memorizing:
  AppRequests
  | where TimeGenerated > ago(1h) and Success == false
  | summarize count() by Name
  | order by count_ desc
- Application Insights: tracks requests, dependencies (SQL, HTTP calls), exceptions, custom events and traces. Workspace-based Application Insights stores its data in a Log Analytics workspace (classic mode is retired, verify).
- Distributed tracing: follows one request across services using a shared operation or trace ID, so you see where time was spent.
- Availability tests: synthetic checks that call your URL from several locations and alert when it fails. They catch outages when there is no user traffic.
- Sampling: keep only a percentage of telemetry to control cost, while counts stay statistically correct. Adaptive sampling is on by default in the .NET SDK (verify).
- Diagnostic settings: per-resource setting that sends platform logs and metrics to a workspace, storage account or Event Hub. Resource logs are not collected until you create one.
- Workbooks: interactive reports that combine metrics, KQL and text. Good for shared team dashboards.
- Service Health and Resource Health: Service Health shows Azure-wide incidents and planned maintenance affecting your subscription. Resource Health shows whether one specific resource is healthy.
- Azure Backup: policy-based backup of VMs, SQL in VMs, Azure Files and more into a Recovery Services vault. Soft delete and immutability protect backups from deletion.
- Site Recovery: replicates VMs to another region and fails over during a disaster. It handles DR, not data backup.
- Update Manager: assesses and schedules OS patching for Azure and Arc-enabled VMs.
- Automation runbooks (awareness): PowerShell or Python scripts run on a schedule or by an alert, for tasks like start/stop VMs.

5 Core focus (exam and interview)
- Metrics vs logs: metrics are fast and lightweight, logs are rich and queryable.
- Activity log is subscription-level control-plane events (who created or deleted what). It is separate from resource logs.
- Resource logs need a diagnostic setting. This is a top exam trap.
- Alert types: metric, log search, activity log. Alert processing rules can suppress notifications during maintenance.
- Backup vs Site Recovery: backup restores data to a point in time, Site Recovery fails the whole VM over to another region. Many scenarios need both.
- Vault redundancy for Backup: LRS, ZRS, GRS (GRS is default) (verify).
- Autoscale needs at least one scale-out and a matching scale-in rule.
- Log Analytics default retention is 30 days on workspace (verify), and Application Insights data follows the workspace.

6 Real-world use case
- Situation: a .NET API on App Service with Azure SQL, previously monitored by log files and IIS logs.
- Choice: workspace-based Application Insights, diagnostic settings from App Service and SQL to one workspace, an availability test on the health endpoint, alerts on failed requests and response time sent to an action group (email plus Teams webhook), autoscale on CPU, and Azure Backup for any VMs.
- Trade-off: more telemetry means faster diagnosis but higher cost, so use sampling and retention limits.
- When not to use: do not send verbose debug logs from every environment into one expensive workspace. Use short retention or a separate workspace for dev. Do not rely on autoscale alone for sudden spikes that need minutes to start instances.

7 Interview lens
- Q: When do you use metrics and when logs? A: Metrics for fast alerts and autoscale because they are near real time and cheap. Logs for investigation, joins and audit because they are queryable.
- Q: A resource shows no logs in Log Analytics. Why? A: Resource logs need a diagnostic setting to a workspace. Also check the workspace, region and permissions.
- Q: Backup or Site Recovery? A: Backup protects against deletion and corruption with point-in-time restore. Site Recovery protects against a region outage with failover. Use both when the RPO and RTO require it.
- Q: How do you cut Application Insights cost? A: Enable sampling, limit custom telemetry, set workspace retention, filter noisy dependencies, and set a daily cap carefully.

8 Common mistakes
- No diagnostic settings, so logs are missing when needed. Fix: enforce with Azure Policy.
- Alert on every metric, causing alert fatigue. Fix: alert on symptoms (failures, latency), set severity, use action groups with the right people.
- Autoscale with no scale-in rule, so cost stays high. Fix: define paired rules and a cool-down.
- Never testing restore. Fix: run scheduled restore drills.
- One workspace for everything with no access control. Fix: plan workspaces and use RBAC (verify the best-practice guidance on workspace design).

9 Mental model
Resources emit data, which flows to Azure Monitor.
  Resources -> metrics store (fast) and Log Analytics workspace (deep)
  Both feed -> alerts -> action groups -> people and automation
  Metrics also feed -> autoscale
  Application Insights = same pipeline, from inside your code
  Backup, Site Recovery, Update Manager = protect and maintain what you watch

10 Mini lab
Time: about 35 minutes. Azure free tier or a small pay-as-you-go cost (verify).
- Step 1: create a resource group, a Log Analytics workspace and a small App Service (Free or Basic plan).
- Step 2: create a workspace-based Application Insights resource and connect it to the App Service.
- Step 3: add a diagnostic setting on the App Service sending logs and metrics to the workspace.
- Step 4: create an action group with your email, then a metric alert on Http 5xx greater than 0 over 5 minutes.
- Step 5: add an availability test on your app URL.
- Step 6: open the workspace Logs blade and run the KQL query from section 4 against requests.
- Expected result: telemetry appears in the workspace within minutes, hitting a bad URL shows failed requests, and an alert email arrives after repeated failures.
- Clean-up: delete the resource group, which removes everything and stops billing.

11 Revision summary
- Metrics are numeric and fast, logs are rich and queried with KQL.
- Resource logs need a diagnostic setting, the activity log does not.
- Action groups are reusable notification targets for alerts.
- Autoscale needs min, max, default and paired scale-out and scale-in rules.
- Application Insights gives requests, dependencies, exceptions and distributed tracing, and sampling controls cost.
- Availability tests catch outages even when no users are active.
- Backup restores data, Site Recovery fails over VMs to another region.
- Update Manager schedules patching, runbooks automate operations tasks.
