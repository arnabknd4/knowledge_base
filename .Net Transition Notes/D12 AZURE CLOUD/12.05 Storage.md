1 What is it
- Azure Storage is a set of cloud services for keeping data: blobs (files and objects), Azure Files (shared network drives), queues (small messages), tables (simple key-value rows) and managed disks (disks for VMs).
- Everything lives inside a storage account, which is the top-level container and billing unit for these services. Data is kept as several copies, and the redundancy setting says how many copies and where.
- Legacy equivalent: file shares and SAN or NAS disks behind IIS servers, plus MSMQ for queues and the App_Data or network-share folders that .NET Framework apps used for uploads.

2 Why needed
- Cloud apps cannot rely on a local disk. A web app instance can be replaced or scaled out at any time, so files must live outside it.
- Without it: uploads vanish when an instance restarts, every server needs its own copy of the files, and backups and disaster recovery are manual.
- It gives cheap, durable, scalable storage with tiers for hot and cold data, and security that does not need a shared password.

3 Before you read
- A subscription holds resource groups, and a storage account lives in a resource group in one region.
- Redundancy means keeping extra copies of data so one failure does not lose it.
- Authentication means proving who you are. Authorization means what you are allowed to do.
- A private endpoint is a private IP address inside your virtual network that points to an Azure service.

4 Features and core concepts

Account types and redundancy (LRS, ZRS, GRS, GZRS)
- A storage account is the container for all storage services. The common type is general-purpose v2 (verify).
- LRS: three copies in one datacenter. Cheapest. Fails if the whole datacenter is lost.
- ZRS: three copies across availability zones in one region. Survives a datacenter or zone failure.
- GRS: LRS in the primary region, plus a copy in the paired region. Survives a regional disaster, but the secondary is not readable unless you choose the RA option (verify).
- GZRS: ZRS in the primary region, plus a copy in the paired region. Best protection, highest cost.
- Why it matters: redundancy is the main durability and cost choice. It ties directly to RPO and RTO (how much data you can lose and how long you can be down).

Blob tiers and lifecycle
- Blobs are objects such as images, PDFs and backups. Tiers set the price of storing versus reading: hot (frequent access), cool, cold, archive (verify the list).
- Archive is the cheapest to store but data is offline and must be rehydrated first, which takes hours.
- Lifecycle management rules move or delete blobs automatically based on age or last access.
- Why it matters: it cuts cost without manual work. Early deletion fees apply if you move data out of cool or archive too soon (verify the minimum days).

Azure Files
- A managed file share you can mount over SMB (and NFS in some setups, verify). It behaves like a network drive.
- Why it matters: it is the lift-and-shift answer for apps that expect a shared folder, such as old .NET Framework apps with UNC paths.

Queues and tables
- Queue storage holds simple messages for a worker to process later. It is basic and cheap compared with Service Bus (no topics, no sessions).
- Table storage holds key-value rows with no fixed schema. Cosmos DB has a Table API for larger needs.
- Why it matters: they are useful for simple background work and simple lookups, and they appear in exam questions on choosing a service.

Managed disks
- Disks for VMs, handled by Azure so you do not manage the storage account. Types include Standard HDD, Standard SSD, Premium SSD and Ultra (verify the current list).
- Why it matters: disk type affects VM performance and cost. Disks can be replicated with ZRS or LRS depending on type.

SAS, stored access policies, Entra authentication
- Storage account keys give full access to everything. Avoid them.
- A shared access signature (SAS) is a URL token with limited permission and a time limit. Types: account SAS, service SAS, user delegation SAS (signed with Entra credentials, safest).
- A stored access policy is a named rule on a container that a service SAS can point to. You can revoke or change it without re-issuing tokens.
- Entra authentication uses Azure RBAC roles such as Storage Blob Data Contributor, with a managed identity for apps.
- Why it matters: this is the most tested part of storage. Prefer Entra and managed identity, then user delegation SAS, then service SAS with a stored policy.
- Setting worth memorizing: az storage account update --allow-shared-key-access false

Immutability, soft delete, failover
- Immutability (WORM) makes blobs unchangeable for a set period, for compliance. Time-based retention and legal hold are the two kinds.
- Soft delete keeps deleted blobs, containers or shares for a set number of days so you can recover them. Versioning keeps old copies after overwrite.
- Account failover lets you switch a GRS or GZRS account to the secondary region. It can lose recent data not yet replicated, and the account becomes LRS or ZRS afterwards (verify).
- Why it matters: protects against mistakes, ransomware and regional failure.

Private endpoints
- Gives the storage account a private IP in your VNet. Pair it with a private DNS zone (privatelink.blob.core.windows.net) so names resolve to the private IP.
- Service endpoints are the older, simpler option. They keep the public address but limit traffic to your subnet.
- Why it matters: lets you turn off public access and keep traffic on the Microsoft network.

Data Lake Gen2, AzCopy, Azurite
- Data Lake Gen2 is a storage account with the hierarchical namespace turned on. It adds real folders and POSIX-style permissions for analytics.
- AzCopy is a command-line tool for fast bulk copy to, from and between storage accounts.
- Azurite is a local emulator for blob, queue and table, used for development and tests.
- Command worth memorizing: azcopy copy "./data" "https://<acct>.blob.core.windows.net/<container>?<SAS>" --recursive

5 Core focus (exam and interview)
- Pick redundancy from the failure you must survive: datacenter (ZRS), region (GRS or GZRS).
- Account name must be globally unique, 3 to 24 characters, lowercase letters and numbers only (verify).
- Redundancy can be changed later, but some conversions need a support request or a migration (verify).
- Entra auth with RBAC is the recommended access method. Disable shared key access when possible.
- Know the three SAS types and that a stored access policy lets you revoke a service SAS.
- Know which services support what: blob tiers apply to blobs only. Archive needs rehydration.
- Soft delete and versioning are not backups of the whole account. Use Azure Backup or replication for real protection.
- Choose by workload: Blob for objects, Files for shares, Queue for simple messages, Disks for VMs.
- Defaults and limits change often. Check Microsoft Learn for current numbers (verify).

6 Real-world use case
- Situation: a legacy MVC app saves invoice PDFs to a network share. You move it to App Service with several instances.
- Choice: store PDFs in Blob Storage in a ZRS account. Use a managed identity with the Storage Blob Data Contributor role. Return a short-lived user delegation SAS so users download directly. Add a lifecycle rule: cool after 30 days, archive after one year (adjust to policy). Turn on soft delete and versioning. Use a private endpoint and disable public access.
- Trade-off: ZRS costs more than LRS and does not survive a regional disaster. Private endpoints add DNS and network setup work. Archive saves money but retrieval is slow.
- When NOT to use it: do not use Blob for data that needs fast random file-system access by old software (use Azure Files). Do not use Queue storage when you need topics, ordering or dead-letter handling (use Service Bus). Do not use GZRS if the data is easy to rebuild.

7 Interview lens
- Q: LRS vs ZRS vs GRS?
  A: LRS keeps three copies in one datacenter. ZRS spreads them across zones in a region.
  GRS adds a copy in the paired region for disaster recovery.
- Q: How do you give a client temporary access to one blob?
  A: Issue a user delegation SAS with minimal permission and a short expiry.
  Better still, let the app use a managed identity and never hand out keys.
- Q: How do you keep storage off the public internet?
  A: Create a private endpoint with a private DNS zone, then disable public network access.
  Use firewall rules or service endpoints only if private endpoints are not possible.
- Q: A user deleted a blob by mistake. What helps?
  A: Blob soft delete and versioning let you restore it within the retention period.
  Immutability policies stop deletion entirely when compliance needs it.

8 Common mistakes
- Using account keys in config files. A leaked key gives full access. Fix: managed identity, Key Vault, and disable shared key access.
- Long-lived SAS with write permission. It leaks in logs or URLs. Fix: short expiry, minimum permission, user delegation SAS, stored policy for revocation.
- Choosing LRS for important data. A datacenter loss means data loss. Fix: ZRS or GZRS based on RPO.
- Private endpoint without private DNS. The app still resolves the public IP and gets blocked. Fix: link the private DNS zone to the VNet.
- Leaving everything in hot tier. Storage bill grows. Fix: lifecycle rules.
- Assuming GRS secondary is always readable. Fix: check RA-GRS or RA-GZRS (verify) or plan failover.
- Moving data to archive and expecting instant reads. Fix: plan rehydration time.

9 Mental model
- Storage account = a building with one address and one security desk.
- Inside: a warehouse (blobs), a shared office drive (files), an inbox tray (queue), a card index (table).
- Redundancy = how many copies of the building contents exist and how far apart.

```
[Storage account]
   |-- Blob containers --> tiers: hot / cool / cold / archive
   |-- File shares
   |-- Queues
   |-- Tables
Access: Entra + RBAC (best) > user delegation SAS > service SAS + policy > account key (avoid)
Network: public off + private endpoint + private DNS
```

10 Mini lab
- Time: about 30 minutes. Tools: Azure free account, Azure CLI (or Cloud Shell), Azure Storage Explorer optional.
- Steps:
  - 1. az group create -n rg-stor-lab -l centralindia
  - 2. az storage account create -n <uniquename> -g rg-stor-lab -l centralindia --sku Standard_ZRS --kind StorageV2 --allow-blob-public-access false
  - 3. Assign yourself the role Storage Blob Data Contributor on the account (portal: Access control, Add role assignment).
  - 4. az storage container create --account-name <uniquename> -n docs --auth-mode login
  - 5. echo hello > a.txt, then az storage blob upload --account-name <uniquename> -c docs -f a.txt -n a.txt --auth-mode login
  - 6. In the portal, open the account, Data protection, enable blob soft delete (7 days). Delete a.txt, then undelete it.
  - 7. Create a lifecycle rule: move blobs to cool after 30 days (portal, Lifecycle management).
  - 8. Generate a user delegation SAS: az storage blob generate-sas --account-name <uniquename> -c docs -n a.txt --permissions r --expiry <UTC time 1 hour ahead> --auth-mode login --as-user --full-uri
  - 9. Open the SAS URL in a browser.
- Expected result: upload works with login auth only, deleted blob returns after undelete, SAS URL downloads the file until it expires, anonymous access without SAS fails.
- Clean-up: az group delete -n rg-stor-lab --yes --no-wait

11 Revision summary
- Redundancy: LRS (one datacenter), ZRS (zones), GRS (paired region), GZRS (zones plus paired region).
- Blob tiers: hot, cool, cold, archive. Archive is offline and needs rehydration. Use lifecycle rules.
- Prefer Entra RBAC and managed identity over keys. Disable shared key access when possible.
- SAS types: account, service, user delegation. Stored access policy allows revocation of service SAS.
- Soft delete and versioning recover mistakes. Immutability (WORM) blocks changes for compliance.
- Private endpoint plus private DNS zone keeps traffic private. Then disable public access.
- Data Lake Gen2 = hierarchical namespace on. AzCopy for bulk copy. Azurite for local dev.
- Queue storage is basic. Use Service Bus for topics, sessions and dead-lettering.
