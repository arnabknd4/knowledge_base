1 What is it
- High availability (HA) means the system keeps running when a part fails. Disaster recovery (DR) means getting the system back after a big failure, such as a whole region going down. Business continuity is the wider plan that keeps the business working during and after an outage.
- This topic covers how to design HA and DR on Azure: where to place workloads (zones or regions), how to measure availability, how to back up and fail over, and how to prove the plan works with drills.
- Legacy equivalent: two IIS servers behind a load balancer for HA, plus a standby data centre with log-shipped SQL Server and a paper DR plan.

2 Why needed
- Hardware, software, network and whole data centres fail. Without a design, one failure means a long outage.
- Without defined recovery targets, nobody knows how much data loss or downtime the business can accept, so the design is a guess.
- Without drills, a DR plan only exists on paper and fails when needed.
- More redundancy costs more money. The design must balance cost against business impact.

4 Features and core concepts
- Zones vs regions
  - A zone is a separate data centre inside one region, with its own power, cooling and network. A region is a geographic area with many zones.
  - Zones protect against a data centre failure with very low latency between them. Regions protect against a whole-region failure but add latency and cost.
- SLA math
  - An SLA is the uptime Microsoft promises for a service, as a percentage. Serial dependencies multiply: 99.95% x 99.99% = about 99.94%.
  - Parallel redundant copies raise availability: 1 - (1 - A)^n for independent copies. Always compute the composite SLA of the full path, not one service.
  - Memorize: 99.9% is about 8.76 hours of downtime a year, 99.99% is about 52 minutes.
- Backup strategies
  - A backup is a separate copy you can restore from after deletion or corruption. Replication copies bad data too, so replication is not a backup.
  - Use Azure Backup for VMs and files, point-in-time restore for Azure SQL, and soft delete and versioning for blobs.
  - Test restores. An untested backup is not proven.
- Site Recovery
  - Azure Site Recovery (ASR) replicates VMs to another region (or on-premises to Azure) and orchestrates failover with recovery plans.
  - It matters for lift-and-shift VM workloads, including legacy .NET Framework apps on Windows VMs.
- Geo-replication per service
  - Each service has its own option. Azure SQL: active geo-replication and failover groups. Storage: GRS, GZRS, RA-GRS. Cosmos DB: multi-region replication. Redis and Service Bus: geo options on higher tiers (verify).
  - Check the option per service, since the names and limits differ.
- Traffic Manager and Front Door failover
  - Traffic Manager is DNS-based routing with health probes. Failover time depends on DNS TTL.
  - Front Door is a global layer 7 entry point that routes by health and latency. It usually fails over faster than DNS-based routing, and adds WAF and caching.
- RPO and RTO design
  - RPO (recovery point objective) is the maximum acceptable data loss, measured in time. RTO (recovery time objective) is the maximum acceptable downtime.
  - The business sets them. Tighter targets mean higher cost. Pick the cheapest design that meets them.
- DR drills
  - A drill is a planned failover test. It finds broken steps, missing permissions and stale runbooks.
  - Run them on a schedule and record the measured RTO and RPO.
- Multi-region data
  - Cosmos DB multi-write lets several regions accept writes and needs a conflict resolution policy. SQL failover groups give one writable primary and a read-only secondary with a listener endpoint that does not change on failover.
  - Multi-region writes trade complexity for lower RTO.
- Runbooks
  - A runbook is the step-by-step failover and failback procedure, ideally automated and stored with the code.
  - It matters because outages happen under stress, and people follow written steps better than memory.
- Useful memory item: SQL failover group creation uses az sql failover-group create (verify the exact parameters on Microsoft Learn).

5 Core focus (exam and interview)
- Most asked: given RPO, RTO and budget, choose zones only, warm standby or active-active across regions.
- Know the four DR tiers: backup-restore (cheapest, slowest), pilot light, warm standby, active-active (most expensive, fastest).
- Know that zone redundancy does not protect against a region failure.
- Calculate composite SLA for a path with several services.
- Know that GRS storage replicates asynchronously, so some data loss is possible. Failover for storage accounts is a customer-initiated action in most cases (verify current behaviour).
- Know the difference between DNS failover (Traffic Manager, TTL delay) and Front Door failover.
- Defaults and limits change often. Check the Microsoft Learn page for each service before the exam (verify).

6 Real-world use case
- Situation: a Kolkata client runs an order system on App Service, Azure SQL and Blob storage in Central India. The business accepts 15 minutes of data loss (RPO) and 1 hour of downtime (RTO) for a region failure.
- Choice: zone-redundant App Service and Azure SQL in the primary region. A SQL failover group to a second region (verify the paired region choice for India). A warm standby App Service plan in the second region, deployed by Terraform. Front Door in front with health probes. GZRS or GRS for blobs. A written runbook and one drill every six months.
- Trade-off: the warm standby adds a standing monthly cost for the second region, and the team must keep both regions in sync.
- When NOT to use it: for an internal tool where a day of downtime is acceptable, a backup-restore plan costs far less and is enough. Do not build active-active for a system that does not need it.

7 Interview lens
- Q: What is the difference between HA and DR?
  A: HA keeps the system running through local failures, usually with zones and redundancy. DR restores service after a large failure, usually in another region.
- Q: Your RPO is 5 minutes and your RTO is 30 minutes. What do you choose?
  A: Asynchronous geo-replication or a failover group with a warm standby in a second region. A backup-restore plan cannot meet the RTO.
- Q: Why is replication not a backup?
  A: Replication copies deletes and corruption to the replica. A backup keeps older versions you can restore.
- Q: How do you know your DR plan works?
  A: By running scheduled drills and recording the actual RTO and RPO. Then fix the runbook gaps found.

8 Common mistakes
- Assuming zones protect against a region outage. In production the whole region fails and the system is down. Fix: add a second region where the targets need it.
- Using one service SLA instead of the composite SLA. The real availability is lower than promised. Fix: multiply along the dependency chain.
- Never testing restores or failover. The plan fails during the real event. Fix: schedule drills and restore tests.
- Failing over the app but not the database or secrets. The app starts and cannot connect. Fix: include data, Key Vault, DNS and config in the runbook.
- Long DNS TTL with Traffic Manager. Users keep hitting the dead region. Fix: lower the TTL or use Front Door.
- Ignoring failback. The system stays on the expensive secondary. Fix: document and test failback.

9 Mental model
- Think of building fire safety.

  Zone = another fire-proof room in the same building.
  Region = a second building in another city.
  Backup = the archived paper copies in a vault.
  RPO = how many hours of paperwork you can afford to lose.
  RTO = how long before the office must reopen.
  Drill = the fire drill that proves everyone knows the exit.

10 Mini lab
- Goal: see a failover work with Azure SQL failover groups on the free tier or a small budget. Time: 30 to 40 minutes. (verify that your subscription allows two SQL servers in two regions, and check the cost first; Basic tier databases are cheap.)
- Steps:
  - Create a resource group. Create two Azure SQL logical servers in two different regions.
  - On the primary server, create a Basic tier database.
  - On the primary server, create a failover group that includes the database and the secondary server.
  - Note the read-write listener name of the failover group.
  - Connect with SSMS or Azure Data Studio using the listener name and create a table with one row.
  - In the portal, trigger a planned failover of the failover group.
  - Reconnect using the same listener name and check that the row is still there.
- Expected result: after failover the same listener name connects, now served by the second region, with your data intact.
- Clean-up: delete the resource group, which removes both servers and the failover group.

11 Revision summary
- Zones protect against a data centre failure. Regions protect against a region failure.
- Serial SLAs multiply. Parallel copies raise availability.
- Replication is not backup. Test restores.
- RPO is the data loss limit. RTO is the downtime limit. The business sets both.
- DR tiers: backup-restore, pilot light, warm standby, active-active.
- Front Door fails over faster than DNS-based Traffic Manager.
- SQL failover groups keep one listener name across failover.
- A DR plan not drilled is not a DR plan.
