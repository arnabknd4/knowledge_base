1 What is it
- Azure networking is the set of services that connect your Azure resources to each other, to on-premises networks and to the internet.
- A VNet (virtual network) is your private network in Azure. A subnet is a slice of that address range. Traffic rules, routes and gateways control what flows where.
- Legacy equivalent: the corporate LAN, VLANs, firewalls, routers, load balancers and DNS servers that sat between your IIS servers and SQL Server in a data centre.

2 Why needed
- Without a network design, every resource gets exposed to the internet or cannot talk to its dependencies.
- Without careful address planning, VNets overlap and cannot be peered or connected to on-premises later. This is expensive to fix.
- Without private connectivity, databases and storage stay on public endpoints, which fails most security reviews.

3 Before you read
- IP addressing and CIDR notation (for example 10.0.0.0/16 means 65,536 addresses).
- DNS basics: name to IP resolution.
- TCP and HTTP layers: L4 (TCP/UDP) vs L7 (HTTP).
- Azure subscriptions and resource groups (topic 12.01).

4 Features and core concepts
- VNets and subnets: a VNet is a private address space in one region. Subnets split it so you can apply different rules per tier. Azure reserves 5 addresses per subnet (verify).
- Address planning: choose non-overlapping CIDR ranges across all VNets and on-premises. Overlap blocks peering and VPN. Leave room to grow.
- NSGs (network security groups): allow or deny rules by source, destination, port and protocol, attached to a subnet or NIC. Rules are processed by priority number, lowest first. Needed because subnets are open internally by default.
- ASGs (application security groups): name a group of VMs and use the name in NSG rules instead of IPs. Keeps rules readable.
- User-defined routes (UDR): your own route table that overrides Azure's default routing, for example forcing traffic through a firewall. Needed for inspection.
- Peering: connects two VNets over the Microsoft backbone with private IPs. It is not transitive: A to B and B to C does not give A to C.
- VPN Gateway: encrypted tunnel over the internet to on-premises (site-to-site) or a single client (point-to-site). Cheaper, but speed and latency vary.
- ExpressRoute: private dedicated circuit via a provider, not over the public internet. Predictable latency and higher cost.
- Virtual WAN (awareness): managed hub service for connecting many branches and VNets at scale.
- Hub-spoke: a central hub VNet holds shared services (firewall, VPN, DNS). Spoke VNets peer to the hub. Gives one place for control.
- Azure Firewall: managed, stateful firewall with FQDN and threat-intelligence filtering. Sits in the hub, used with UDRs.
- Azure DNS and private DNS zones: public DNS hosting, and private name resolution inside VNets. Private endpoints depend on private DNS zones.
- Private Endpoint vs Service Endpoint: a private endpoint puts a private IP of the PaaS service inside your subnet. A service endpoint keeps the public IP but restricts access to your subnet. Private endpoint is the stronger option and works from on-premises.
- Load Balancer: L4, distributes TCP/UDP traffic inside a region.
- Application Gateway and WAF: L7, regional, URL routing, TLS termination, with a web application firewall against OWASP attacks.
- Front Door: L7, global entry point with CDN, WAF and failover across regions.
- Traffic Manager: DNS-based global routing. It does not proxy traffic.
- Bastion: browser-based RDP/SSH to VMs without public IPs.
- NAT Gateway: fixed outbound public IP for a subnet and avoids SNAT port exhaustion.
- Network Watcher: diagnostics such as IP flow verify, next hop, connection troubleshoot, NSG flow logs.
- Worth memorizing: az network vnet create -g rg1 -n vnet1 --address-prefixes 10.0.0.0/16 --subnet-name web --subnet-prefixes 10.0.1.0/24

5 Core focus (exam and interview)
- NSG evaluation: lowest priority number first, stop at first match. Default rules allow VNet-to-VNet and outbound internet, deny inbound internet.
- NSG at both subnet and NIC: inbound hits subnet NSG then NIC NSG. Outbound is the reverse. Both must allow.
- Peering is non-transitive. Gateway transit needs "use remote gateway" and "allow gateway transit" settings.
- Private endpoint needs a private DNS zone link (for example privatelink.database.windows.net) or names resolve to public IPs.
- Load Balancer L4 vs Application Gateway L7 vs Front Door global L7 vs Traffic Manager DNS. Know the choice by scope (regional or global) and layer.
- VPN Gateway vs ExpressRoute: internet encrypted vs private circuit.
- Gateway subnet must be named GatewaySubnet. Azure Firewall subnet must be named AzureFirewallSubnet. (verify sizes)
- Basic vs Standard SKU differences for public IPs and Load Balancer (verify current retirements).

6 Real-world use case
- Situation: a legacy IIS and SQL Server app is rehosted to Azure. Web tier in App Service, database in Azure SQL, staff connect from the Kolkata office.
- Choice: hub-spoke. Hub has Azure Firewall and VPN Gateway. A spoke VNet holds the app. Azure SQL gets a private endpoint with a private DNS zone. App Service uses VNet integration. Application Gateway with WAF is the public entry. NSGs restrict each subnet.
- Trade-off: more cost (Firewall, gateways, WAF) and more design effort in return for central control and no public database.
- When NOT to use it: a small internal tool or prototype. A single VNet with NSGs and a service endpoint is enough. Hub-spoke and Firewall are overkill there.

7 Interview lens
- Q: Private endpoint or service endpoint?
  A: Private endpoint gives a private IP and works from on-premises and peered networks. Service endpoint keeps a public IP and only limits it to your subnet.
- Q: Why can VNet A not reach VNet C if both peer with B?
  A: Peering is non-transitive. Use hub routing through a firewall or NVA with UDRs, or peer A and C directly.
- Q: Application Gateway vs Front Door?
  A: Application Gateway is regional L7 inside your VNet. Front Door is global L7 at Microsoft's edge with failover across regions.
- Q: How do you secure a PaaS database from the internet?
  A: Private endpoint, private DNS zone, disable public network access, and restrict with NSG and identity-based auth.

8 Common mistakes
- Overlapping address ranges: peering or VPN fails later. Fix: plan ranges in one central sheet before building.
- Private endpoint without DNS link: app still resolves the public IP and gets blocked. Fix: link the private DNS zone to the VNet.
- Assuming peering is transitive: traffic drops with no error. Fix: route through hub firewall with UDRs.
- Opening RDP or SSH to the internet: gets scanned within minutes. Fix: use Bastion or just-in-time access.
- UDR forcing traffic to a firewall with no return path: asymmetric routing, broken sessions. Fix: check next hop with Network Watcher.
- Subnet too small: cannot add scale instances or gateways. Fix: size with growth in mind.

9 Mental model
- Think of a company campus.
- VNet is the campus boundary. Subnets are buildings. NSGs are door guards on each building.
- Peering is a private road between campuses. VPN is a courier over public roads. ExpressRoute is a private rail line.
- Hub-spoke is a main gate with security (firewall) that all campuses use.
- Front Door is the city-wide reception, Application Gateway is the campus reception, Load Balancer is the corridor traffic splitter.

  Internet -> Front Door -> App Gateway (WAF) -> web subnet -> app subnet -> private endpoint -> SQL
  On-prem -> VPN or ExpressRoute -> hub (Firewall) -> spoke VNets

10 Mini lab (30 to 40 minutes, Azure free tier, uses a Linux VM with a small SKU, costs minimal)
- Step 1: create resource group rg-net-lab in your nearest region.
- Step 2: create vnet-a (10.1.0.0/16, subnet web 10.1.1.0/24) and vnet-b (10.2.0.0/16, subnet app 10.2.1.0/24).
- Step 3: create a small Linux VM in each VNet with no public IP for vm-b, and a public IP for vm-a. Choose key-based SSH.
- Step 4: try ssh from vm-a to the private IP of vm-b. Expected: fails (no connectivity).
- Step 5: create a peering vnet-a to vnet-b and the reverse. Retry. Expected: connection works.
- Step 6: add an NSG on the app subnet that denies inbound SSH from 10.1.1.0/24 at priority 100. Retry. Expected: blocked.
- Step 7: in Network Watcher, run IP flow verify for vm-a to vm-b port 22. Expected: shows the denying rule name.
- Step 8: remove the deny rule and run connection troubleshoot. Expected: reachable.
- Clean-up: az group delete -n rg-net-lab --yes --no-wait

11 Revision summary
- Azure reserves 5 IPs per subnet (verify).
- NSG rules: lowest priority number first, first match wins.
- Peering is non-transitive and needs non-overlapping ranges.
- Private endpoint needs a private DNS zone link.
- Layer 4 regional: Load Balancer. Layer 7 regional: Application Gateway. Layer 7 global: Front Door. DNS global: Traffic Manager.
- VPN Gateway uses the internet, ExpressRoute is private.
- GatewaySubnet and AzureFirewallSubnet are fixed names.
- Hub-spoke centralizes firewall, VPN and DNS.
