1 What is it

- Identity and access answers two questions: who is calling (identity) and what may they do (access).
- Microsoft Entra ID (formerly Azure Active Directory) holds the identities. Azure RBAC decides what each identity can do to Azure resources.
- Legacy equivalent: on-premises Active Directory, Windows auth, domain groups and ACLs on IIS folders and SQL logins.

2 Why needed

- Every Azure call must be authenticated and authorized.
- Without a central identity layer you get shared passwords, connection strings in config files and admin rights for everyone.
- One leaked secret then opens the whole subscription.

3 Before you read

- Authentication proves who you are. Authorization decides what you can do.
- Tokens: a signed proof of identity that the caller presents to an API.
- Azure hierarchy: tenant, management group, subscription, resource group, resource (topic 12.01).
- OAuth 2.0 and OIDC basics (topic 3.03).

4 Features and core concepts

- Entra ID tenant: your organization's dedicated directory. Every subscription trusts exactly one tenant.
- Users and groups: people and sets of people. Assign access to groups, not individuals, so joiners and leavers are one change.
- App registration: the definition of your application in the tenant (client ID, redirect URIs, permissions). It exists once, in the home tenant.
- Enterprise application: the local instance of an app in a tenant, where assignments, SSO and consent are controlled.
- Service principal: the identity an app uses to sign in. Think of it as a service account.
- Managed identity: a service principal whose credentials Azure rotates for you. No secret in code.
  - System-assigned: tied to one resource and deleted with it.
  - User-assigned: standalone, reusable across resources.
- Azure RBAC: an assignment is who (principal), what (role definition) and where (scope). Scopes inherit downward: management group, subscription, resource group, resource.
- Custom roles: your own list of allowed actions, used when built-in roles are too broad.
- Entra roles vs Azure roles: Entra roles manage the directory (users, apps). Azure roles manage resources. Different systems, though Global Administrator can elevate itself to access all subscriptions.
- Conditional Access: if-then policies on sign-in, such as requiring MFA from outside the office.
- MFA: a second proof beyond the password.
- PIM (Privileged Identity Management): time-limited, approval-based activation of privileged roles instead of permanent admin.
- Access reviews: periodic checks that people still need their access.
- B2B guests: external people invited into your tenant using their own identity.
- SSO (SAML, OIDC): one sign-in for many apps. SAML is older and XML-based. OIDC is modern and token-based.
- Hybrid identity: on-premises AD synced to Entra ID (Entra Connect, verify current name). Awareness level only.
- Remember: az role assignment create --assignee <id> --role Reader --scope <scope>

5 Core focus (exam and interview)

- Built-in roles: Owner, Contributor, Reader, User Access Administrator.
- Contributor cannot grant access. Owner and User Access Administrator can.
- Inheritance flows down and cannot be blocked by a lower scope.
- Prefer managed identity over client secrets.
- Conditional Access, PIM and access reviews need paid Entra licenses (verify tier names).
- Role assignments per subscription have a limit (verify).
- A secret on an app registration expires. Managed identities have no secret to expire.

6 Real-world use case

- Situation: an App Service API must read blobs and secrets, and your ops team needs occasional admin access.
- Choice: enable a system-assigned managed identity on the App Service. Grant it Storage Blob Data Reader on the one storage account and Key Vault Secrets User on the vault. Put ops engineers in a group that is eligible for Contributor through PIM.
- Trade-off: more setup than a connection string, and RBAC changes can take minutes to apply.
- Avoid user-assigned identities when each resource needs its own tight permissions. Avoid client secrets when a managed identity works.
- A managed identity only works for code running on Azure. Code running elsewhere needs workload identity federation.

7 Interview lens

- App registration vs enterprise application? The registration is the global definition. The enterprise app is the tenant-local service principal where access is controlled.
- System-assigned vs user-assigned? System-assigned shares the resource lifecycle. User-assigned is reusable and survives resource deletion.
- Entra role vs Azure role? Entra roles govern the directory. Azure roles govern resources, assigned at a scope.
- How do you reduce standing admin access? Use PIM for just-in-time roles, require MFA on activation and run access reviews.

8 Common mistakes

- Owner at subscription scope for everyone. Result: accidental deletions. Fix: least privilege at resource group scope.
- Assigning to individuals. Result: orphaned access after people leave. Fix: use groups.
- Client secrets in appsettings. Result: leaks and expiry outages. Fix: managed identity.
- Mixing up Entra roles and Azure roles. Result: "I'm Global Admin but can't see the VM". Fix: assign an Azure role.
- No break-glass admin account when Conditional Access locks everyone out. Fix: keep two excluded emergency accounts.

9 Mental model

- Entra ID is the passport office and RBAC is the building access system.
- Who: user, group, service principal, managed identity.
- What: role definition.
- Where: scope.
- Access = who + what + where.

10 Mini lab (30 minutes, Azure free tier)

- Create a resource group and a storage account: az group create -n rg-iam-lab -l centralindia (location, verify).
- Create a test user in Entra ID, or use a second account of yours.
- Assign it Reader at the resource group: az role assignment create --assignee <user> --role Reader --resource-group rg-iam-lab
- Sign in as that user. Confirm you can view the storage account but cannot delete it.
- Change the assignment to Contributor and retry. Expected: delete is now allowed.
- Clean up: az group delete -n rg-iam-lab --yes, then delete the test user.

11 Revision summary

- Access = principal + role + scope, and it inherits downward.
- Assign roles to groups, not people.
- Managed identity beats secrets. System-assigned is tied to its resource, user-assigned is reusable.
- App registration is the definition. Enterprise application is the tenant-local instance.
- Entra roles manage the directory. Azure roles manage resources.
- Contributor cannot assign roles. Owner can.
- Conditional Access enforces conditions, PIM gives time-limited admin and access reviews remove stale access.
- B2B guests bring their own identity. SSO uses SAML or OIDC.
