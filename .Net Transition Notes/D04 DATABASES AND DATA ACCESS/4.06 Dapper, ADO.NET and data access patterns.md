1 What is it

Dapper is a small library that runs your SQL and maps result rows to C# objects. ADO.NET is the lower layer underneath it: SqlConnection, SqlCommand and SqlDataReader. Dapper adds extension methods on IDbConnection. It does not generate SQL, track changes or manage a model.

Data access patterns are the ways you organize this code: repository, unit of work, CQRS read side, specification and query objects.

Legacy equivalent: raw SqlDataAdapter or DataReader code in old ASP.NET, or hand-rolled helper classes around stored procedures.

----------------

2 Why needed

- EF Core is productive for writes and simple reads, but it adds overhead and can generate SQL you do not control.
- Reports, dashboards and bulk loads often need exact SQL and low allocation.
- Without a fast, direct path, teams either fight the ORM or write verbose ADO.NET.
- Without clear patterns, data access leaks into controllers and becomes untestable, or gets wrapped in layers that add no value.

4 Features and core concepts

Dapper basics
- Plain meaning: Query<T>, QueryFirstOrDefault<T>, Execute, QueryMultiple and multi-mapping extension methods.
- Why it matters: near ADO.NET speed with far less code. You write SQL, Dapper maps columns to properties by name.
- Worth memorizing:
  - var rows = await conn.QueryAsync<OrderDto>("select Id, Total from Orders where CustomerId = @id", new { id });
  - await conn.ExecuteAsync("update Orders set Status = @s where Id = @id", new { s, id });

When to prefer it over EF
- Plain meaning: choose by the job, not by habit.
- Prefer Dapper for: read-heavy queries, reports, joins across many tables, hot paths, stored procedures, bulk reads.
- Prefer EF for: complex write models, change tracking, migrations, rapid CRUD.
- Why it matters: using both in one app is normal and often best.

Connection pooling
- Plain meaning: ADO.NET keeps closed connections in a pool keyed by connection string, so opening a connection is cheap.
- Why it matters: open late, dispose early (using or await using). Holding connections long exhausts the pool (default max 100 per pool, verify).

Parameterization
- Plain meaning: values go as parameters (@id), never concatenated into the SQL text.
- Why it matters: stops SQL injection and lets SQL Server reuse query plans. Dapper does this for you when you pass an object. Table and column names cannot be parameters, so whitelist them.

Repository and unit of work critique
- Plain meaning: a repository hides data access behind an interface. Unit of work groups changes into one transaction.
- Why it matters: EF Core's DbContext already is a repository and unit of work. Wrapping it in generic repositories often adds a layer with no benefit and hides useful query features. Repositories still help around Dapper, or to give an aggregate a clear boundary.

CQRS read side
- Plain meaning: Command Query Responsibility Segregation. Writes go through the domain model (EF), reads use thin, purpose-built queries returning DTOs (Dapper).
- Why it matters: reads skip the domain model and tracking, so they are faster and simpler. You do not need separate databases to start.

Specification and query objects
- Plain meaning: specification is a reusable, named filter rule. A query object is a class that holds one query and its parameters.
- Why it matters: keeps SQL out of controllers, makes each query testable, and avoids a repository with fifty methods.

SqlBulkCopy
- Plain meaning: the fast way to load many rows into SQL Server using the bulk insert protocol.
- Why it matters: inserting 100,000 rows one by one is very slow. SqlBulkCopy streams them in batches. Load into a staging table, then merge with set-based SQL.

5 Core focus (exam and interview)

- Dapper is a micro-ORM: no change tracking, no migrations, no LINQ provider.
- Always parameterize. Any concatenation of user input into SQL is a failing answer.
- Dapper extends IDbConnection. The connection comes from you, so you control lifetime and transactions.
- A pooled connection is returned to the pool on Dispose or Close.
- Buffered by default: Query returns a materialized list. Use buffered: false (or the streaming overloads) for huge results.
- Dapper does not map joins to nested objects on its own. Use multi-mapping with splitOn, or QueryMultiple.
- Transactions: pass the transaction explicitly to each call.
- Pool size and timeout defaults come from SqlClient (verify).

6 Real-world use case

Situation: an order management API on Azure SQL. Writes (place order, change status) use EF Core with a rich Order aggregate. The order search screen needs a filtered, sorted, paged list joining five tables.

Choice: keep EF Core for commands. Add a read-side query object, OrderSearchQuery, that uses Dapper with a parameterized SQL statement and returns a flat OrderListItemDto. A nightly import of partner files uses SqlBulkCopy into a staging table, then a stored procedure merges.

Trade-off: two data access styles to maintain, and SQL strings are not compile-time checked. Mapping bugs show up at runtime.

When NOT to use it: simple CRUD where EF is fast enough; teams without SQL skill; cases that need change tracking or migrations. Do not add generic repositories over Dapper just for ceremony.

7 Interview lens

Q1: When would you choose Dapper over EF Core?
A: For read-heavy, performance-critical or complex SQL paths, reports and stored procedures. I keep EF for writes and normal CRUD, and often use both in one service.

Q2: Is a generic repository over EF Core a good idea?
A: Usually not. DbContext already implements repository and unit of work, so the wrapper adds indirection and hides features like Include and projections. I use focused query objects or aggregate repositories instead.

Q3: How does Dapper protect against SQL injection?
A: Only if you pass values as parameters, which Dapper sends as SqlParameters. It does not protect string concatenation, and identifiers like table names must be whitelisted.

Q4: How do you insert 500,000 rows efficiently?
A: SqlBulkCopy into a staging table, then one set-based insert or merge. Row-by-row inserts, or EF SaveChanges on that volume, would be far slower.

8 Common mistakes

- Concatenating strings into SQL: shows up as injection or plan cache bloat. Fix: parameters.
- Long-lived shared SqlConnection: shows up as thread errors or "timeout expired obtaining a connection from the pool". Fix: open per operation, dispose quickly.
- Forgetting the transaction argument: shows up as partial writes. Fix: pass the transaction to every call.
- Loading huge results into memory: shows up as memory spikes. Fix: paging or unbuffered streaming.
- Wrong splitOn in multi-mapping: shows up as null or half-filled child objects. Fix: set splitOn to the first column of the next object.
- Generic repository over everything: shows up as layers with no logic. Fix: query objects per use case.
- Column and property name mismatch: shows up as default values. Fix: alias columns in SQL or configure mapping.

----------------

9 Mental model

  Write path:  Controller -> Command handler -> EF Core (aggregate) -> SQL Server
  Read path:   Controller -> Query object -> Dapper (hand-written SQL) -> DTO
  Bulk path:   File -> SqlBulkCopy -> staging table -> set-based merge

Both paths sit on ADO.NET and the same connection pool. EF is the productive tool, Dapper is the sharp tool.

10 Mini lab (about 30 minutes)

Goal: compare Dapper and EF for a read, and run a bulk load.

Steps:
- Run SQL Server locally in Docker (docker run -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD=... -p 1433:1433 mcr.microsoft.com/mssql/server).
- Create a console project and add Dapper and Microsoft.Data.SqlClient packages.
- Create table Orders (Id int identity, CustomerId int, Total decimal(10,2)) and insert 200,000 rows using SqlBulkCopy from a DataTable.
- Write a Dapper query: select top 50 with a where CustomerId = @id and order by Total desc, mapped to a record OrderDto.
- Time it with Stopwatch. Then try the same query with string concatenation and note the difference in how you would have to guard it.
- Optional: add an EF Core context and time the same read with AsNoTracking.

Expected result: the bulk load of 200,000 rows finishes in seconds. The Dapper and EF no-tracking reads are close for this simple query, and the Dapper code is shorter.

Clean-up: docker stop and docker rm the container, delete the project folder.

11 Revision summary

- Dapper is a micro-ORM over IDbConnection: you write SQL, it maps rows.
- Always use parameters. Identifiers cannot be parameters, so whitelist them.
- Use EF for writes and CRUD, Dapper for hot reads, reports and stored procedures.
- Open connections late, dispose early. The pool does the reuse.
- DbContext is already a repository and unit of work. Avoid generic repository wrappers over it.
- CQRS read side means thin query objects returning DTOs, not necessarily a separate database.
- SqlBulkCopy plus a staging table is the fast path for large loads.
- Multi-mapping needs the correct splitOn.
