1 What is it

- Schema design is deciding how data is organised in tables: what each table holds, how rows are identified, how tables link, and which rules the database enforces. Data modeling is the thinking step before it: turning business facts into entities and relationships.
- A keys, constraints and data types decision made here is hard to change later, because every query, index and report depends on it.
- Legacy equivalent: the ER diagram and the EDMX or Code First model you built for an EF6 and SQL Server MVC application.

----------------------------------------

2 Why needed

- Problem solved: wrong structure causes slow queries, duplicate data, bad reports and painful migrations.
- Without it: tables with repeated data drift out of sync, large keys bloat every index, and bad data enters because nothing blocks it.
- Multi-tenant products live or die on this choice, because retrofitting tenant isolation later means rewriting data access everywhere.

----------------------------------------

4 Features and core concepts

- Normalization: store each fact once, in one place. Why: avoids update anomalies and duplicate data.
- Denormalization: deliberately copy or pre-join data to read faster. Why: reads in reporting and hot paths avoid expensive joins, but writes must keep copies in sync.
- Natural key: a real-world value used as the identifier (email, PAN, ISBN). Why: meaningful, but real-world values change and can be reused.
- Surrogate key: a meaningless generated identifier (identity, GUID). Why: stable and small; the safe default for primary keys.
- Identity: database-generated incrementing integer. Why: compact, sequential, index-friendly; hard to generate in advance or across systems.
- GUID (random): globally unique id generated by the app. Why: no round trip needed and merge-friendly, but random values fragment a clustered index and are 16 bytes.
- Sequential GUID: GUID that increases over time (NEWSEQUENTIALID in SQL Server, or Guid.CreateVersion7 in .NET 9 and later (verify)). Why: keeps global uniqueness while avoiding page splits.
- Constraints: primary key, foreign key, unique, check, default, not null. Why: the database is the last line of defence; app validation alone gets bypassed.
- Data types: pick the smallest correct type (int vs bigint, decimal vs float for money, datetime2 vs datetime, varchar vs nvarchar). Why: size affects memory, index depth and IO.
- Temporal tables: system-versioned tables that keep full row history automatically. Why: free audit trail and point-in-time queries.
- Soft delete: mark a row deleted (IsDeleted, DeletedAt) instead of removing it. Why: recovery and audit; cost is every query must filter it, and unique constraints need filtered indexes.
- Audit columns: CreatedAt, CreatedBy, UpdatedAt, UpdatedBy, RowVersion. Why: traceability and optimistic concurrency.
- Multi-tenancy models: shared schema with a TenantId column; schema per tenant; database per tenant. Why: trades cost against isolation (see use case).
- Partitioning: splitting a large table into ranges (usually by date) while it stays one logical table. Why: faster maintenance, archiving by switching a partition out, some query pruning.
- Archiving: moving old rows to cheaper storage or a separate table. Why: keeps hot tables and indexes small.
- Worth memorizing:
  - ALTER TABLE dbo.Orders ADD CONSTRAINT CK_Orders_Total CHECK (Total >= 0);
  - CREATE UNIQUE INDEX UX_Users_Email ON dbo.Users(Email) WHERE IsDeleted = 0;

5 Core focus (exam and interview)

- Most asked: GUID vs identity as clustered key, normalization levels (1NF to 3NF, why stop at 3NF), soft delete pitfalls, choosing a tenancy model.
- Clustered key rule of thumb: narrow, unique, static, ever-increasing. Random GUID breaks the last one.
- The clustered key is copied into every nonclustered index, so a wide key makes all indexes larger.
- Denormalize only after measuring a real read problem.
- Exam angle (Azure SQL and Cosmos): database per tenant maps to elastic pools in Azure SQL (verify details on Microsoft Learn).
- Temporal table history is stored in a separate history table; retention can be configured (verify limits).

6 Real-world use case

- Situation: a SaaS invoicing product for 300 small firms in India, to be moved from a single legacy database to Azure SQL.
- Choice: shared database and shared schema, with TenantId on every table, a composite index starting with TenantId, and an EF Core global query filter on TenantId. Large enterprise customers get their own database later.
- Keys: bigint identity internally, plus a public GUID column for APIs so ids are not guessable.
- Trade-off: lowest cost and one migration to run, but a missed tenant filter leaks data and a noisy tenant can slow others.
- When NOT to use shared schema: strict regulatory isolation, per-tenant backup and restore needs, or very large tenants. Use database per tenant, with elastic pools to control cost.
- When NOT to use soft delete: data covered by erasure requests (privacy law); delete it or anonymise it instead.

7 Interview lens

- Q: Why is a random GUID a poor clustered key?
  A: Inserts land at random places, causing page splits and fragmentation. The 16-byte key is also copied into every nonclustered index.
- Q: When would you denormalize?
  A: When a measured read path is slow because of joins and writes are rare. I accept the sync cost and document it.
- Q: How do you choose a multi-tenancy model?
  A: By isolation need, tenant count and size, and cost. Shared schema is cheapest, database per tenant gives the strongest isolation and easy per-tenant restore.
- Q: What goes wrong with soft delete?
  A: Queries forget the filter, unique values collide with deleted rows, and tables grow without limit. Fix with global filters, filtered unique indexes and an archive job.

8 Common mistakes

- Natural key as primary key (email, phone): the value changes and foreign keys everywhere must change. Fix: surrogate key plus a unique constraint on the natural value.
- float for money: totals drift by fractions. Fix: decimal with explicit precision.
- nvarchar(max) everywhere: wasted memory grants and unindexable columns. Fix: sized columns.
- No foreign keys "for speed": orphan rows appear in production. Fix: add them; the cost is small.
- Missing TenantId in an index: every tenant query scans other tenants' rows. Fix: lead composite indexes with TenantId.
- Partitioning a small table: added complexity, no gain. Fix: partition only multi-hundred-million-row, date-driven tables.

9 Mental model

- The schema is the foundation of a building:

  business facts -> entities -> tables -> keys and constraints -> indexes -> queries

- Mistakes at the left are cheap to fix on paper and very expensive once data and code sit on top.

11 Revision summary

- Normalize to 3NF by default, denormalize only for a measured read problem.
- Use a surrogate key as the primary key; keep natural values under a unique constraint.
- Clustered key should be narrow, unique, static and increasing.
- Random GUID fragments the clustered index; use a sequential GUID if you need GUIDs.
- Constraints belong in the database, not only in app code.
- Temporal tables give automatic history; soft delete needs filters and filtered unique indexes.
- Tenancy models: shared schema, schema per tenant, database per tenant, chosen by isolation vs cost.
- Partition and archive only very large, time-based tables.
