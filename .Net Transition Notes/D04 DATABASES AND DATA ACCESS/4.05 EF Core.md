1 What is it

EF Core is the modern object-relational mapper (ORM) from Microsoft. An ORM maps C# classes to database tables so you write LINQ queries instead of SQL, and it generates the SQL for you. It runs on modern .NET and is a full rewrite of EF6.
- Legacy equivalent: Entity Framework 6 (EF6) in .NET Framework MVC apps, plus hand-written ADO.NET and stored procedure calls.

2 Why needed

- Hand-written SQL and DataReader code is repetitive and easy to get wrong.
- EF6 does not run on modern .NET in a supported, fast way and has no new features.
- Without EF Core you either stay on .NET Framework or write the data layer yourself.
- Misuse of EF Core (tracking everything, N+1 queries) is a top cause of slow APIs, so a lead must know how it behaves.

3 Before you read

- LINQ: IEnumerable runs in memory, IQueryable is translated to SQL.
- Dependency injection lifetimes: scoped, singleton, transient (note 1.03).
- Basic SQL: joins, indexes, transactions.
- Async/await basics (note 1.07).

4 Features and core concepts

- DbContext lifetime
  - Plain meaning: DbContext is one unit of work holding a connection, a change tracker and a model.
  - Why it matters: it is not thread-safe and is cheap to create. Register it as scoped (one per request). Never make it a singleton. Use AddDbContextPool only when you profile a gain. For background jobs, create a scope or use IDbContextFactory.
- Tracking vs no-tracking
  - Plain meaning: tracking means EF remembers loaded entities to detect changes on SaveChanges. No-tracking skips that.
  - Why it matters: read-only queries are faster and use less memory with AsNoTracking().
- Loading strategies
  - Plain meaning: eager (Include), explicit (Entry().Load), lazy (proxies, off by default).
  - Why it matters: lazy loading hides queries and creates N+1. Prefer eager or projection.
- N+1
  - Plain meaning: one query for a list, then one extra query per row to fetch related data.
  - Why it matters: 100 rows become 101 round trips. Fix with Include or a projection.
- Projections
  - Plain meaning: Select into a DTO or anonymous type so only needed columns are fetched.
  - Why it matters: smaller SQL, no tracking overhead, no accidental exposure of entity fields.
- Compiled queries
  - Plain meaning: EF.CompileAsyncQuery caches the translation of a LINQ query.
  - Why it matters: helps only on very hot paths. EF already caches query plans, so measure first.
- Raw SQL
  - Plain meaning: FromSql, FromSqlInterpolated and Database.ExecuteSql run your own SQL.
  - Why it matters: for complex reports or tuned queries. Use interpolated forms so values become parameters (prevents SQL injection). Never concatenate strings.
- Global query filters
  - Plain meaning: a WHERE condition added to every query of an entity type.
  - Why it matters: used for soft delete and multi-tenancy. Bypass with IgnoreQueryFilters(). Easy to forget it is there.
- Concurrency tokens
  - Plain meaning: a column (often rowversion) checked on update to detect that someone else changed the row.
  - Why it matters: optimistic concurrency. A conflict throws DbUpdateConcurrencyException, which you handle by reload or retry.
- Migrations (scripts, bundles)
  - Plain meaning: versioned C# files that evolve the schema from the model.
  - Why it matters: in production, generate an idempotent SQL script or a migration bundle and run it in the pipeline. Do not call Database.Migrate() at app startup on multi-instance apps.
- Owned types
  - Plain meaning: value-object-like types stored in the owner's table (for example an Address).
  - Why it matters: models value objects without a separate table or identity.
- Value converters
  - Plain meaning: convert a property between C# type and database type (enum to string, strongly typed IDs).
  - Why it matters: keeps domain types clean while the column stays simple.
- ExecuteUpdate and ExecuteDelete
  - Plain meaning: set-based update and delete sent as one SQL statement, without loading entities.
  - Why it matters: fast bulk changes. They bypass the change tracker and do not run SaveChanges interceptors or tracked state. Entities already loaded become stale.
- Split queries
  - Plain meaning: AsSplitQuery() runs one SQL query per included collection instead of one big join.
  - Why it matters: avoids cartesian explosion (huge duplicated rows) with multiple collection Includes. Trade-off: several round trips and possible inconsistency between them.
- Interceptors
  - Plain meaning: hooks into EF events (SaveChanges, commands, connections).
  - Why it matters: audit columns, soft delete conversion, query logging, adding auth tokens to connections.
- EF6 vs EF Core differences
  - Plain meaning: EF Core is a rewrite with a different API surface.
  - Why it matters: lazy loading off by default; no EDMX or designer; many-to-many without join entity is supported in newer versions; GroupBy and Include behave differently; migrations differ; some EF6 features were missing for years (verify per version).

- builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(cs));
- var list = await db.Orders.AsNoTracking().Where(o => o.CustomerId == id).Select(o => new OrderDto(o.Id, o.Total)).ToListAsync();

5 Core focus (exam and interview)

- Most asked: N+1, tracking vs no-tracking, DbContext lifetime, how to run migrations in production, concurrency handling.
- Defaults to remember:
  - Tracking is on by default.
  - Lazy loading is off by default.
  - DbContext is scoped by default with AddDbContext.
  - SaveChanges wraps all changes in one transaction.
  - Queries translate to SQL only for IQueryable. Anything untranslatable either throws or, in older versions, ran in memory (verify version behavior).
- Know the difference between SaveChanges (tracked) and ExecuteUpdate (direct SQL).
- Connection resiliency: EnableRetryOnFailure for Azure SQL transient faults. With retries on, manual transactions need an execution strategy.

6 Real-world use case

- Situation: a legacy MVC app on EF6 is being moved to ASP.NET Core API on Azure SQL. The order list endpoint is slow.
- Choice: EF Core with AsNoTracking and a Select projection to a DTO for read endpoints. Tracked entities only for write endpoints. A rowversion concurrency token on Order. Migrations applied as an idempotent script in the Azure DevOps pipeline. EnableRetryOnFailure for Azure SQL.
- Trade-off: you gain speed and safety, but you write more explicit queries and DTOs than EF6 lazy loading allowed.
- When NOT to use it: very heavy reporting, bulk loads of millions of rows, or highly tuned SQL. Use Dapper, stored procedures or SqlBulkCopy there (note 4.06). Many teams mix EF Core for writes and Dapper for hot reads.

7 Interview lens

- Q: How do you find and fix N+1 in EF Core?
  - A: Turn on SQL logging and look for repeated similar queries per row. Fix with Include, a projection, or a batched query.
- Q: Why not make DbContext a singleton?
  - A: It is not thread-safe, and the change tracker would grow forever and hold stale data. Use scoped, or IDbContextFactory in background services.
- Q: How do you apply migrations safely in production?
  - A: Generate an idempotent script or a bundle and run it in the release pipeline with review. Avoid Migrate() at startup when several instances start together.
- Q: What is optimistic concurrency in EF Core?
  - A: A concurrency token (such as rowversion) is added to the WHERE clause on update. If zero rows are affected, EF throws DbUpdateConcurrencyException and you reload, merge or tell the user.

8 Common mistakes

- Returning entities directly from APIs: over-posting, circular references, leaking columns. Fix: map to DTOs.
- Loading whole entities for read-only lists: slow and memory-heavy. Fix: AsNoTracking and Select.
- Using Include on many collections: giant cartesian result. Fix: split queries or separate queries.
- Calling ToList() too early then filtering in memory: the whole table comes to the app. Fix: keep IQueryable until the end.
- String-concatenated raw SQL: SQL injection. Fix: FromSqlInterpolated or parameters.
- Global filter forgotten in admin or reporting queries: missing rows. Fix: IgnoreQueryFilters where intended and test it.
- Stale entities after ExecuteUpdate: old values in the tracker. Fix: reload or use a fresh context.
- Migrate() on startup across many pods: race conditions and locked schema. Fix: run migrations in the pipeline.

9 Mental model

DbContext = a shopping basket for one request.
  Load (query) -> basket tracks items -> you change items -> SaveChanges = checkout (one transaction).
  AsNoTracking = just looking at the shelf, not filling the basket.
  ExecuteUpdate = telling the shop to change prices directly, without opening your basket.

10 Mini lab (30 to 40 minutes, local only)

Tools: .NET SDK, SQL Server in Docker (or LocalDB), dotnet-ef tool.
- Step 1: dotnet new webapi -n EfLab, then cd EfLab. dotnet add package Microsoft.EntityFrameworkCore.SqlServer and Microsoft.EntityFrameworkCore.Design. dotnet tool install --global dotnet-ef (skip if installed).
- Step 2: Create Customer (Id, Name) and Order (Id, CustomerId, Total, RowVersion with [Timestamp]). Create AppDbContext with DbSets. Register with AddDbContext and a connection string.
- Step 3: dotnet ef migrations add Init, then dotnet ef database update.
- Step 4: Seed 20 customers with 5 orders each. Turn on SQL logging with LogTo(Console.WriteLine).
- Step 5: Write a loop that reads each customer's orders without Include (use lazy-style access in a loop). Count SQL statements in the console. Expect 1 + 20 queries.
- Step 6: Fix with Include, then with a Select projection and AsNoTracking. Expect 1 query each.
- Step 7: Open two contexts, load the same Order in both, change and save in the first, then the second. Expect DbUpdateConcurrencyException.
- Step 8: Run dotnet ef migrations script --idempotent and read the SQL.
- Result to see: query counts drop from 21 to 1, and the concurrency exception fires.
- Clean-up: stop and remove the Docker SQL container, delete the EfLab folder.

11 Revision summary

- DbContext is scoped, not thread-safe, one per request.
- Tracking is on by default; use AsNoTracking for reads.
- Lazy loading is off by default; prefer Include or projections.
- N+1 means one query per row; fix with Include or Select.
- Use FromSqlInterpolated, never string concatenation.
- Concurrency token (rowversion) gives optimistic concurrency.
- Run migrations via idempotent script or bundle in the pipeline, not at startup.
- ExecuteUpdate and ExecuteDelete skip the tracker and do set-based SQL.
