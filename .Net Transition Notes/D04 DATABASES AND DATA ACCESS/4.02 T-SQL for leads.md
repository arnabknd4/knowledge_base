1 What is it
- T-SQL is Microsoft's SQL dialect for SQL Server and Azure SQL. It adds variables, control flow, procedures and extra functions on top of standard SQL.
- This topic is about writing set-based, index-friendly T-SQL that stays fast and safe at scale.
- Legacy equivalent: the stored procedures, inline SQL and temp-table-heavy scripts in your .NET Framework and EF6 projects.

2 Why needed
- A lead reviews data access code, so you must spot slow or unsafe queries before production does.
- Without it: row-by-row loops, non-SARGable filters, injectable dynamic SQL and wrong MERGE usage cause timeouts, blocking and data bugs.

4 Features and core concepts
- Joins: combine tables on keys. Gap to check: a LEFT JOIN with a WHERE filter on the right table silently becomes an inner join. Put that filter in the ON clause.
- Window functions: calculate across a set of rows without collapsing them (ROW_NUMBER, RANK, LAG, LEAD, SUM OVER). They replace self-joins and cursors for top-N-per-group and running totals.
- CTEs: named temporary result sets for readability and recursion. They are not materialized in SQL Server; each reference re-runs the query.
- Set-based vs row-by-row: one statement over many rows beats a cursor or WHILE loop. The engine optimizes sets, not loops.
- Stored procedures vs inline SQL: procedures give plan reuse, permission control and a deploy unit. Parameterized inline SQL also reuses plans. The real choice is about testability, versioning and team skill.
- Temp tables vs table variables: temp tables (#t) have statistics and support indexes, so they suit larger sets. Table variables had fixed row-count guesses; deferred compilation in newer versions improves this (verify version).
- MERGE pitfalls: it combines insert, update and delete in one statement, but has a history of bugs, race conditions without HOLDLOCK and trigger oddities. Many teams prefer separate UPDATE and INSERT.
- Pagination: OFFSET FETCH needs a deterministic ORDER BY. Deep offsets get slower; keyset (seek) pagination scales better.
- JSON support: OPENJSON, JSON_VALUE and FOR JSON handle JSON in queries. JSON stays in text columns, so index it through computed columns. Newer native json type exists (verify).
- SARGability: a predicate is SARGable if the engine can seek an index with it. Wrapping the column in a function (WHERE YEAR(d)=2025) forces a scan. Rewrite as a range on the bare column.
- Dynamic SQL and injection: building SQL strings from input is injectable. Use sp_executesql with parameters and QUOTENAME for object names.
- Bulk operations: batch large writes (for example 5,000 to 10,000 rows) to limit log growth and lock escalation. SqlBulkCopy and BULK INSERT are for loads.

Worth memorizing:
- EXEC sp_executesql N'SELECT * FROM dbo.Orders WHERE Id = @Id', N'@Id int', @Id = @OrderId;
- WHERE OrderDate >= '20250101' AND OrderDate < '20260101'

5 Core focus (exam and interview)
- Most asked: SARGability, temp table vs table variable, CTE vs temp table, parameter sniffing link, injection-safe dynamic SQL, why cursors are slow.
- Defaults to remember: CTEs are not cached; MERGE needs HOLDLOCK for upsert safety; OFFSET FETCH requires ORDER BY; lock escalation commonly triggers around 5,000 locks (verify).
- Window function frame default with ORDER BY is RANGE, which can be slower and surprising. State ROWS explicitly for running totals.

6 Real-world use case
- Situation: an Azure SQL-backed order API times out on a paged order list and a nightly row-by-row recalculation job.
- Choice: rewrite the filter to be SARGable, switch to keyset pagination, replace the cursor with one set-based UPDATE using a window function, and batch it in chunks.
- Trade-off: keyset pagination cannot jump to an arbitrary page and needs a unique sort key. Set-based code is harder to debug than a loop.
- When NOT to use it: do not move business rules into giant stored procedures if your team tests and deploys through .NET code. Do not use temp tables for tiny sets, where table variables or CTEs are fine.

7 Interview lens
- Q: Why can a function on a column slow a query?
  A: It makes the predicate non-SARGable, so the engine scans instead of seeking. Rewrite as a range on the raw column or add a computed, indexed column.
- Q: Temp table or table variable?
  A: Temp tables have statistics and indexes, so they suit large or reused sets. Table variables suit small sets and have lighter recompile cost.
- Q: Why avoid MERGE?
  A: Known bugs and concurrency edge cases, and it needs HOLDLOCK for upserts. Separate statements in a transaction are clearer and safer.
- Q: How do you page 10 million rows?
  A: Keyset pagination on an indexed unique key. Offset paging reads and discards all earlier rows.

8 Common mistakes
- SELECT * in APIs: breaks covering indexes and sends extra data. Select only needed columns.
- Implicit conversion (nvarchar parameter vs varchar column): causes scans. Match data types in EF and Dapper parameters.
- Cursor or WHILE loops for bulk updates: slow and lock-heavy. Use set-based statements in batches.
- String-concatenated dynamic SQL: injection risk. Use sp_executesql with parameters.
- NOLOCK as a performance fix: allows dirty and missing rows. Use read committed snapshot instead.
- Pagination without a unique tiebreaker in ORDER BY: duplicate or skipped rows across pages. Add the key.

9 Mental model
- Think of the engine as a librarian with an index card catalog.
- Ask for a range of cards (SARGable) and it jumps straight there. Ask it to transform every card first (function on column) and it walks every shelf.
- One request for many books (set-based) beats a thousand trips for one book each (row-by-row).

11 Revision summary
- SARGable means a bare column compared to a range or value.
- Window functions replace cursors and self-joins for ranking and running totals.
- CTEs are not materialized; temp tables have statistics.
- MERGE needs HOLDLOCK and is risky; prefer explicit UPDATE and INSERT.
- OFFSET FETCH needs ORDER BY; use keyset pagination for deep paging.
- Dynamic SQL: sp_executesql with parameters, QUOTENAME for identifiers.
- Batch large writes to avoid log growth and lock escalation.
- Use ROWS, not the default RANGE, for running totals.
