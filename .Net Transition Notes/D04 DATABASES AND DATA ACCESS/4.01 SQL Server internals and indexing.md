1 What is it
- Topic 4.01 is SQL Server internals and indexing. It covers how SQL Server stores rows on disk and how indexes and the optimizer find them fast.
- Page: the 8 KB block SQL Server reads and writes. Extent: 8 pages (64 KB), the allocation unit.
- Execution plan: the optimizer's chosen steps to run a query.
- Legacy equivalent: the SQL Server tuning you did on EF6 and stored-procedure apps, now viewed with Query Store and Azure SQL features.

2 Why needed
- Most slow .NET APIs are slow because of the database, not the C# code.
- Without index knowledge, you add random indexes, slow down writes, and cannot explain a timeout in an interview.
- An architect must predict query cost at design time, not after go-live.

4 Features and core concepts
- Pages and extents: data lives in 8 KB pages grouped in 8-page extents. Why it matters: I/O cost is counted in pages, so fewer pages read means faster queries. Tip: check page reads with SET STATISTICS IO ON.
- Clustered vs heap: a clustered index stores the table rows in key order. A heap has no order. Why it matters: a table has one clustered index, and its key is copied into every nonclustered index, so keep it narrow, unique and ever-increasing.
- B-tree and nonclustered indexes: a balanced tree with root, intermediate and leaf levels. Nonclustered leaves hold key columns plus a pointer to the row. Why it matters: seeks cost a few page reads even on huge tables.
- Covering and included columns: a covering index holds every column the query needs. INCLUDE adds non-key columns at the leaf only. Why it matters: it removes key lookups without bloating the key.
- Filtered indexes: an index with a WHERE clause on a subset of rows. Why it matters: smaller and cheaper for skewed data, such as active rows only.
- Statistics: histograms of value distribution per column or index. Why it matters: the optimizer estimates row counts from them. Stale statistics cause bad plans.
- Execution plans: scan reads everything, seek jumps to matching keys, key lookup fetches missing columns from the clustered index. Join types: nested loops (few rows), hash (large unsorted), merge (both sorted). Why it matters: compare estimated vs actual rows to find the problem.
- Parameter sniffing: the plan is built for the first parameter values and reused. Why it matters: fast for one customer, slow for another. Fixes: OPTION (RECOMPILE), OPTIMIZE FOR, Query Store plan forcing, or better indexes.
- Plan cache: memory where compiled plans are reused. Why it matters: unparameterized ad hoc SQL bloats it and forces compiles.
- Missing index DMVs: sys.dm_db_missing_index_* suggestions. Why it matters: good hints, but never apply blindly. They ignore write cost and overlap.
- Query Store: built-in history of queries, plans and runtime stats per database. Why it matters: shows regressions over time and lets you force a plan. On by default in Azure SQL Database and new SQL Server 2022 databases (verify).
- tempdb: shared scratch database for temp tables, sorts, spills and row versions. Why it matters: heavy spills and version store growth make everything slow.

5 Core focus (exam and interview)
- Most asked: scan vs seek, key lookup, covering index, parameter sniffing, stale statistics.
- Clustered index: one per table. Nonclustered indexes: many, but each costs writes and storage.
- Key column order matters: equality columns first, then range columns.
- Estimated vs actual row counts show statistics problems.
- Missing index DMV suggestions are hints only.
- Query Store: find regressed queries, compare plans, force the good plan.
- In Azure SQL, automatic tuning can create or drop indexes and force plans (verify current settings).

6 Real-world use case
- Situation: an orders API on Azure SQL times out on GET orders by customer. EF Core generates a query filtered on CustomerId and ordered by OrderDate.
- Choice: the plan shows a clustered index scan. Create a nonclustered index on (CustomerId, OrderDate) INCLUDE (Status, Total). Use Query Store to confirm the new plan and lower reads.
- Trade-off: faster reads, but slower inserts and more storage. A wide included list grows the index.
- When NOT to use it: small tables, write-heavy tables with rare reads, or when the query itself is non-SARGable (a function on the column). Fix the query first.

7 Interview lens
- Q: Why would a query scan despite an index? A: The predicate is non-SARGable, the index is not selective, or the optimizer expects most rows. Check the plan and statistics.
- Q: What is parameter sniffing and how do you handle it? A: The plan is compiled for the first parameter values and reused for others. Use recompile, OPTIMIZE FOR, plan forcing, or fix the skew with indexes.
- Q: Clustered vs nonclustered index? A: Clustered defines physical row order, one per table. Nonclustered is a separate structure pointing to rows, many allowed.
- Q: How do you find a regression after a deployment? A: Open Query Store, sort by duration or reads, compare plans before and after, and force the old plan if needed.

8 Common mistakes
- Indexing every column: inserts and updates slow down and storage grows. Fix: base indexes on real queries and drop unused ones using usage stats.
- GUID random clustered key: page splits and fragmentation. Fix: identity or sequential GUID.
- Blindly applying missing index suggestions: duplicate, overlapping indexes. Fix: merge with existing ones first.
- Functions on columns in WHERE (for example YEAR(col)): forces scans. Fix: rewrite as a range.
- SELECT * from EF projections: key lookups and wide reads. Fix: project only needed columns.
- Ignoring statistics on big tables: wrong estimates and spills. Fix: scheduled updates and check auto-update settings.

9 Mental model
- A phone book (clustered index) holds full entries sorted by name. A nonclustered index is the index at the back of a textbook pointing to page numbers. A covering index is a card that already has the answer, so you never open the book. The optimizer is a planner that guesses road length from old traffic stats (statistics).

11 Revision summary
- Page 8 KB, extent 8 pages.
- One clustered index per table; narrow, unique, increasing key.
- Seek beats scan for selective queries; key lookup means missing columns in the index.
- INCLUDE columns sit at the leaf and do not affect key order.
- Bad estimates usually come from stale statistics or parameter sniffing.
- Query Store keeps plans and stats, and can force a plan.
- Missing index DMVs are hints, not orders.
- tempdb spills and version store growth hurt the whole instance.
