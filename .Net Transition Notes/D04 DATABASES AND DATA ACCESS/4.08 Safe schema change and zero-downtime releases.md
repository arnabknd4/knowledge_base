1 What is it
- Safe schema change means altering a database structure while the application keeps running, with no downtime and no broken old code.
- Core idea: never change the schema and the code in one step. Change the schema in small steps that both the old and new code can live with.
- Expand and contract is the main technique. First add the new thing (expand), move the code and data over, then remove the old thing (contract).
- Legacy equivalent: a Friday-night release with a maintenance window, one big SQL script run by hand, and a "site is down" banner.

2 Why needed
- Modern apps run on several instances. During a rolling deployment, old and new code run at the same time against one database.
- A rename or drop that suits the new code breaks the old code still serving users.
- Without this discipline: failed deployments, locked tables during business hours, data loss on rollback, and long maintenance windows.
- A rollback of code is easy. A rollback of a destructive schema change is often impossible.

3 Before you read
- Rolling deployment: instances are replaced one by one, so two versions of the app coexist for a while.
- Table lock: while a statement changes a table, other queries may wait. Long locks cause timeouts.
- Migration: a versioned script or class that moves the schema from one state to the next.
- Feature flag: a runtime switch that turns a code path on or off without a deployment.

4 Features and core concepts
- Expand and contract: add first, switch, remove last. Why it matters: every step is reversible until the final removal.
  - Phase 1 expand: add new column or table, nullable or with a default.
  - Phase 2 migrate: backfill data, deploy code that writes to both.
  - Phase 3 contract: after all code uses the new shape, drop the old.
- Backward-compatible migrations: the new schema must work with the previous app version. Why it matters: during rollout the old version is still live. Safe: add nullable column, add table, add index. Unsafe: rename, drop, change a type, add a NOT NULL column without a default.
- Online index operations: build or rebuild an index without blocking reads and writes. Why it matters: a normal index build on a big table can lock it for minutes. SQL Server needs Enterprise or Azure SQL for ONLINE = ON (verify edition support).
  - CREATE INDEX IX_Orders_Date ON Orders(OrderDate) WITH (ONLINE = ON);
- Data backfill: filling the new column for existing rows. Why it matters: one huge UPDATE bloats the transaction log and holds locks. Do it in small batches (for example 5,000 rows) with a short pause between batches.
- Dual write: during transition the app writes to both the old and new column or table. Why it matters: keeps both shapes consistent until cutover. Risk: the two writes can drift if one fails. Use one transaction, or reconcile afterwards.
- Feature-flagged cutover: a flag decides whether code reads from the old or new structure. Why it matters: switch over and back in seconds, with no redeploy.
- Database version control: the schema lives in source control like code.
  - EF migrations: C# migration classes, good for EF Core teams. Generate SQL scripts or a migration bundle for pipelines.
  - DACPAC: a compiled snapshot of the desired state, deployed by SqlPackage, which works out the diff. Good for state-based control.
  - DbUp: runs numbered SQL scripts once each, in order. Simple and predictable.
  - Flyway: similar to DbUp, versioned SQL files, runs on the JVM.
- Database CI: pipeline builds a fresh database from migrations, runs tests, and checks the script on a copy of production-like data. Why it matters: catches bad scripts before production.
- Rollback strategy: prefer roll forward with a fix. Keep the old column until the new path is proven. Take a backup or snapshot before the contract step. Why it matters: dropped data cannot be restored from a code rollback.

5 Core focus (exam and interview)
- Most asked: how do you rename a column with zero downtime? Answer: add new column, dual write, backfill, switch reads, stop old writes, drop old column in a later release.
- Know which changes are safe and which are not (see list above).
- Know the difference between state-based (DACPAC) and migration-based (EF, DbUp, Flyway) version control.
- Remember: never drop in the same release that stops using the object.
- Remember: batch backfills, and run them outside peak hours.
- Adding a NOT NULL column with a default on a large table may be a metadata-only change on recent SQL Server and Azure SQL (verify for your version).
- Azure DevOps and GitHub Actions can run migrations as a pipeline stage with approval before production.

6 Real-world use case
- Situation: an order system on Azure SQL must rename Customer.Phone to Customer.MobileNumber. The app runs on three App Service instances with rolling deployment.
- Choice made:
  - Release 1: add MobileNumber (nullable). Code writes both columns, reads Phone.
  - Backfill job copies Phone to MobileNumber in batches of 5,000.
  - Release 2: a flag switches reads to MobileNumber. Watch errors for a few days.
  - Release 3: code stops writing Phone.
  - Release 4: drop Phone after a backup.
- Trade-off: four releases instead of one, extra code to maintain, and temporary data duplication. In return: no downtime and an easy rollback at every step.
- When NOT to use it: a small internal tool with a planned maintenance window, an empty or tiny table, or a new feature with no existing data. A simple one-step migration is fine there.

7 Interview lens
- Q: What is expand and contract?
  A: Add the new structure first, move code and data across, and remove the old structure last. Each step works with both old and new app versions.
- Q: Why is renaming a column dangerous?
  A: Old app instances still use the old name during rollout and will fail. A rename is really add, copy, switch, drop.
- Q: EF migrations or DACPAC?
  A: EF migrations are code-first and versioned, good when EF owns the schema. DACPAC is state-based and good for teams with SQL-first or mixed ownership, though destructive diffs need review.
- Q: How do you roll back a bad schema change?
  A: Prefer a forward fix. Keep the old column until the new path is proven, and take a backup before any drop. Code rollback alone does not restore dropped data.

8 Common mistakes
- Dropping a column in the same release that stops using it. Shows up as errors from old instances. Fix: drop one release later.
- One giant UPDATE for backfill. Shows up as lock waits, timeouts and log growth. Fix: small batches with pauses.
- Adding an index without ONLINE on a busy table. Shows up as blocked queries. Fix: online build or off-peak window.
- Dual write without a consistency check. Shows up as mismatched data at cutover. Fix: reconciliation query before switching reads.
- Letting the app auto-migrate on startup in production. Shows up as several instances racing, or a failed migration blocking startup. Fix: run migrations as a separate pipeline step.
- No rehearsal. Shows up as surprises in production. Fix: run the script on a restored copy first.

9 Mental model
- Building a new bridge beside the old one, moving traffic lane by lane, then demolishing the old bridge only when nobody uses it.

old shape + new shape (both live) -> traffic moves -> old shape removed
 expand ----------> migrate ----------> contract

10 Mini lab (30 minutes, local SQL Server in Docker or Azure SQL free tier)
- Step 1: create a table Customers(Id int primary key, Phone nvarchar(20)) and insert 20,000 rows.
- Step 2 (expand): ALTER TABLE Customers ADD MobileNumber nvarchar(20) NULL;
- Step 3 (backfill): run a loop that updates 5,000 rows at a time where MobileNumber IS NULL, using UPDATE TOP (5000), until zero rows are affected.
- Step 4 (verify): SELECT COUNT(*) FROM Customers WHERE ISNULL(Phone,'') <> ISNULL(MobileNumber,''); expect 0.
- Step 5 (index): create an index on MobileNumber with ONLINE = ON (skip on editions without support).
- Step 6 (contract): back up the table with SELECT INTO, then ALTER TABLE Customers DROP COLUMN Phone.
- Expected result: all rows copied, mismatch count 0, old column gone, no long locks seen.
- Clean-up: drop the table and the backup copy, stop and remove the Docker container or delete the Azure SQL resource.

11 Revision summary
- Expand, migrate, contract: add first, remove last.
- New schema must work with the old app version.
- Safe: add nullable column, add table, add index. Unsafe: rename, drop, type change.
- Backfill in small batches, not one big update.
- Dual write needs a reconciliation check before cutover.
- Feature flag makes cutover and rollback instant.
- EF migrations and DbUp and Flyway are migration-based. DACPAC is state-based.
- Never drop in the same release. Back up before contract.
