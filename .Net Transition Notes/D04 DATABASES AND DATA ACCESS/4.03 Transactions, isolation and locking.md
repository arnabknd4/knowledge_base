1 What is it

- A transaction groups several database operations so they succeed or fail together.
- Isolation levels decide how much one transaction can see of another transaction's uncommitted or in-flight work.
- Locking is how SQL Server enforces that. Row versioning (snapshot) is the alternative that avoids most reader-writer blocking.
- Legacy equivalent: TransactionScope around ADO.NET or EF6 calls, default READ COMMITTED with locking, and deadlock errors handled by hand or ignored.

2 Why needed

- Without correct isolation you get dirty reads, non-repeatable reads, phantoms and lost updates. Money and inventory numbers go wrong.
- Without understanding locking you get blocking chains and deadlocks that appear only under production load.
- Cloud scale makes this worse: more concurrent users, more retries, more distributed calls.

4 Features and core concepts

- ACID: Atomic (all or nothing), Consistent (constraints hold), Isolated (transactions do not corrupt each other), Durable (committed data survives a crash, via the transaction log). Why it matters: it is the contract that SQL Server and Azure SQL give you inside one database.
- Isolation levels: READ UNCOMMITTED (dirty reads allowed), READ COMMITTED (default), REPEATABLE READ, SERIALIZABLE, SNAPSHOT. Why it matters: each level trades correctness against concurrency.
- Read committed snapshot (RCSI): READ COMMITTED, but readers use row versions from tempdb or the version store instead of shared locks. Why it matters: readers stop blocking writers. It is the default in Azure SQL Database (verify for your tier), but not in on-premises SQL Server.
- Snapshot isolation: the transaction sees a consistent view as of its start. Needs ALLOW_SNAPSHOT_ISOLATION. Why it matters: gives repeatable reads without locks, but writers can hit update conflicts (error 3960) and must retry.
- Lock types: shared (S), exclusive (X), update (U), intent (IS, IX, IU), schema. Why it matters: lock compatibility explains who blocks whom.
- Lock escalation: SQL Server converts many row or page locks into one table lock, typically around 5,000 locks (verify). Why it matters: a bulk update can suddenly block the whole table.
- Deadlocks: two sessions each hold a lock the other needs. SQL Server picks a victim and rolls it back with error 1205. Why it matters: it is not a bug in SQL Server. Your code must be ready to retry.
- Blocking diagnosis: sys.dm_exec_requests (blocking_session_id), sys.dm_tran_locks, sys.dm_os_waiting_tasks, the deadlock graph from Extended Events (system_health session), Query Store wait stats. Why it matters: you find the head blocker, not the victim.
- Optimistic vs pessimistic concurrency: optimistic checks for conflict at save time (rowversion, EF concurrency token, ETag). Pessimistic locks first (UPDLOCK, application locks). Why it matters: web apps with long user think time need optimistic.
- Distributed transactions and why to avoid them: MSDTC and two-phase commit span multiple resources. Why it matters: they are slow, fragile across services and not supported by most cloud services. Use outbox and saga instead (see 6.03, 9.05).
- Retry on deadlock: catch error 1205 (and transient Azure SQL errors), then retry the whole transaction with backoff. Why it matters: a deadlock victim is expected behavior.
- Worth memorizing:
-   ALTER DATABASE MyDb SET READ_COMMITTED_SNAPSHOT ON;
-   ALTER DATABASE MyDb SET ALLOW_SNAPSHOT_ISOLATION ON;
-   SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

5 Core focus (exam and interview)

- Most asked: difference between READ COMMITTED and RCSI, what causes deadlocks, how to find a blocker, optimistic vs pessimistic, why not MSDTC.
- Default isolation in SQL Server is READ COMMITTED with locking. Azure SQL Database has RCSI on by default (verify).
- Dirty read needs READ UNCOMMITTED. Phantoms are prevented only by SERIALIZABLE (or SNAPSHOT, which avoids them via versioning).
- NOLOCK hint equals READ UNCOMMITTED for that table: it can return dirty, duplicate or missing rows. Not a performance fix.
- Deadlock victim is chosen by lowest DEADLOCK_PRIORITY, then cheapest rollback.
- Exam angle (E): Azure SQL, Cosmos DB consistency and transactions scope. Cosmos DB transactions work only within one partition key (verify).

6 Real-world use case

- Situation: an order API on Azure SQL. Under load, inventory updates deadlock with a nightly report query, and users see 500 errors.
- Choice: turn on RCSI so the report stops taking shared locks. Make all code update tables in the same order (Orders, then OrderLines, then Stock). Add a retry policy for error 1205 using Polly. Add a rowversion column and EF concurrency token for edits made through the UI.
- Trade-off: RCSI adds version store load on tempdb or the database. Retry logic needs idempotent operations.
- When NOT to use it: SNAPSHOT or RCSI will not stop two writers updating the same row. For a hot counter or stock row, use an atomic UPDATE with a WHERE condition, not read-then-write. Do not use SERIALIZABLE broadly. Do not wrap calls to other services in a database transaction.

7 Interview lens

- Q: What is the difference between READ COMMITTED and RCSI?
  A: Both prevent dirty reads. READ COMMITTED blocks readers behind writers using shared locks, RCSI reads the last committed version and does not block.
- Q: How do you debug a deadlock in production?
  A: Capture the deadlock graph from the system_health Extended Events session. Find the two statements and the lock order, then fix index or access order, and add retry.
- Q: Why avoid distributed transactions in microservices?
  A: Two-phase commit couples availability of all participants and many cloud services do not support it. Use outbox plus saga with compensating actions.
- Q: When would you choose pessimistic concurrency?
  A: Short, high-conflict operations such as reserving the last stock item, using UPDLOCK or an atomic conditional UPDATE. Optimistic suits long user edits with low conflict.

8 Common mistakes

- NOLOCK everywhere: shows up as wrong report totals and phantom duplicates. Fix: enable RCSI.
- Long transactions that include HTTP calls or user waits: shows up as blocking chains. Fix: keep transactions short, no remote calls inside.
- No retry on 1205 or transient Azure SQL errors: shows up as random 500s. Fix: retry whole unit of work with backoff, or use EF execution strategy.
- Inconsistent table access order: shows up as recurring deadlocks. Fix: agree a standard order.
- Missing indexes causing scans: shows up as huge lock footprint and escalation. Fix: index the predicate columns.
- Using TransactionScope with two connections silently escalating to MSDTC: shows up as slow calls or failures in the cloud. Fix: one connection, or redesign.
- Assuming SNAPSHOT removes all conflicts: shows up as error 3960. Fix: catch and retry.

9 Mental model

- Think of a ledger book in a shop.
- Locking: only one clerk can hold the page at a time, the others wait (blocking). Two clerks each holding a page the other wants is a deadlock.
- Row versioning: readers get a photocopy of the last signed page, so they never wait. Two clerks writing to the same page still collide.

  reader --(RCSI)--> old version ---- no wait
  writer --X lock--> current row ---- other writers wait

11 Revision summary

- ACID: Atomic, Consistent, Isolated, Durable.
