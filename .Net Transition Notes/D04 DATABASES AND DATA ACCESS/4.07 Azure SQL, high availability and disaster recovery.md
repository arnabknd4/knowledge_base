1 What is it

Azure SQL is Microsoft's managed SQL Server in the cloud. Microsoft runs the servers, patching, backups and failover. You run databases and queries. There are three deployment options: SQL Database, Managed Instance and SQL Server on a VM.
Legacy equivalent: an on-premises SQL Server with Always On, SQL Agent backup jobs and a DBA team, now rented as a service.

----

2 Why needed

- Your on-premises SQL Server needs patching, backup jobs, failover clusters and hardware. Azure SQL moves this work to Microsoft.
- Without a high availability and disaster recovery design, one zone or region failure means downtime and data loss.
- Security settings (encryption, private access, identity) are easy to leave open if you do not know them.

----

3 Before you read

- RPO (Recovery Point Objective): how much data loss you can accept, measured in time.
- RTO (Recovery Time Objective): how long you can be down before service returns.
- Availability zone: a separate datacenter inside one Azure region. Region: a geographic area with several zones.
- Transaction log: the SQL Server file that records every change, which is how backups and replication work.

4 Features and core concepts

Deployment options
- SQL Database: a single managed database. Most modern apps use it. Newest features arrive here first.
- Managed Instance: a near-complete SQL Server instance, with SQL Agent, cross-database queries and linked servers. Best for lift and shift of legacy apps with minimal code change.
- SQL on VM: full SQL Server on an Azure virtual machine. Full control, but you patch and back up. Use for features the managed options lack.
- Why it matters: the choice decides how much migration effort and how much operations work you keep.

DTU vs vCore
- DTU: a bundled score of CPU, memory and IO, sold as simple tiers (Basic, Standard, Premium).
- vCore: you pick CPU count, memory and storage separately. Allows reserved pricing and Azure Hybrid Benefit (reuse existing SQL licenses).
- Why it matters: vCore is the usual choice for new work and gives more control. DTU is simpler for small workloads.

Serverless
- Compute scales automatically and can pause when idle. You pay per second of compute used, plus storage.
- Why it matters: good for dev, test and spiky workloads. A paused database takes time to resume, so the first query is slow.

Elastic pools
- Many databases share one pool of compute.
- Why it matters: saves cost when databases peak at different times, such as a SaaS with one database per tenant.

Hyperscale awareness
- A tier that separates compute from storage, supports very large databases and fast scale and restore.
- Why it matters: know it exists for very large databases (verify current size limits).

Backups
- Point-in-time restore (PITR): automatic backups let you restore to any moment within a retention window (verify default and maximum days).
- Long-term retention (LTR): keeps full backups for months or years for compliance.
- Why it matters: this is your protection against human error such as a bad DELETE.

Geo-replication
- A readable secondary copy of one database in another region, kept in sync asynchronously.
- Why it matters: gives regional disaster recovery and a read replica. Failover is manual and per database.

Failover groups
- A group of databases that fail over together, with a listener endpoint that does not change after failover.
- Why it matters: your connection string stays the same. This is the preferred option for application-level disaster recovery.

RPO and RTO
- Plain meaning in section 3. Async replication means RPO is small but not zero.
- Why it matters: every design question starts with the RPO and RTO the business needs.

Always On awareness
- The SQL Server feature behind high availability on VMs: availability groups and failover cluster instances.
- Why it matters: Azure SQL gives you similar behavior built in. SQL on VM needs you to set it up.

Security
- TDE (Transparent Data Encryption): encrypts files at rest. On by default.
- Always Encrypted: the client encrypts columns, so the server never sees plaintext.
- Private endpoint: gives the database a private IP in your VNet, so it is not reachable from the internet.
- Entra authentication: use Entra ID identities, including managed identity, instead of SQL passwords.
- Why it matters: this removes passwords from connection strings and shrinks the attack surface.

Monitoring
- Metrics and alerts in Azure Monitor, Query Store, Query Performance Insight, and Intelligent Insights (verify current names).
- Why it matters: you find slow queries and resource limits before users do.

Migration tools
- DMA (Data Migration Assistant): checks compatibility.
- DMS (Database Migration Service): moves data, online or offline.
- BACPAC: a portable export of schema and data, good for smaller databases.
- Why it matters: assessment first, then choose the tool by size and allowed downtime.

Worth memorizing:
- az sql failover-group create (verify exact parameters)

5 Core focus (exam and interview)

- Most asked: which deployment option for which scenario (legacy app with SQL Agent means Managed Instance).
- Failover group vs geo-replication: groups give a stable endpoint and failover many databases together.
- Zone redundancy handles a zone failure. Geo-replication and failover groups handle a region failure.
- PITR is automatic. LTR must be configured.
- Auto-failover groups use async replication, so RPO is not zero (verify current published RPO and RTO targets).
- Use Entra authentication and private endpoint as the secure default.
- Limits and prices change often (verify on Microsoft Learn).

6 Real-world use case

Situation: a legacy .NET Framework app uses SQL Server with SQL Agent jobs and linked servers, and moves to Azure.
Choice: Managed Instance, because it keeps those features and needs almost no code change. The app runs on App Service, reaching the database through a private endpoint, with a failover group to a paired region.
Trade-off: Managed Instance costs more than SQL Database and takes longer to create.
When not to use it: new apps without legacy dependencies should use SQL Database. Use SQL on VM only when you need OS access or an unsupported feature.

7 Interview lens

Q: When would you pick Managed Instance over SQL Database?
A: When the app needs instance-level features like SQL Agent, linked servers or cross-database queries. It suits lift and shift with minimal change.

Q: How do you design disaster recovery for Azure SQL?
A: Start from RPO and RTO. Use a failover group to a paired region, with the listener endpoint in the connection string. Test failover regularly.

Q: What is the difference between geo-replication and a failover group?
A: Geo-replication works per database with manual failover. A failover group manages many databases together and gives a stable endpoint.

Q: How do you secure the connection from an app to Azure SQL?
A: Private endpoint, Entra authentication with managed identity, TDE on, and no SQL passwords in config.

8 Common mistakes

- Choosing the largest tier "to be safe". It shows up as a high bill. Fix: measure, then right-size, or use serverless or an elastic pool.
- Assuming geo-replication fails over by itself. It shows up as an outage in a region failure. Fix: use failover groups, and rehearse.
- Never testing restore. It shows up when a backup cannot be restored under pressure. Fix: run restore drills.
- Skipping a compatibility check before migration. It shows up as failures at cutover. Fix: run DMA first.
- Using SQL logins with passwords in app settings. It shows up as leaked credentials. Fix: managed identity and Entra auth.
- Serverless for steady production load. It shows up as slow first requests after auto-pause. Fix: use provisioned compute.

9 Mental model

Think of renting an apartment instead of owning a house.
- SQL Database: a studio flat. Small, cheap, fully managed.
- Managed Instance: a full apartment with your own furniture (SQL Agent, linked servers).
- SQL on VM: a house. You maintain everything.

For recovery: zones are a spare generator in the same building. Failover groups are a second building in another city with the same phone number.

10 Mini lab

Time: about 30 minutes. Use the Azure free tier or free offer (verify current offer).
- Create a resource group and an Azure SQL logical server with Entra admin set to your account.
- Create a SQL Database using the serverless tier or free offer. Add your client IP in the server firewall.
- Connect from SSMS or Azure Data Studio with Entra authentication and create a table with a few rows.
- Open the database's restore options and note the earliest restore point. Do a point-in-time restore to a new database name.
- Open Backups and note the long-term retention settings.
- Optional: view the failover groups page and read what it asks for.
Expected result: a restored copy of the database with the same rows, and a clear view of the retention settings.
Clean-up: delete the resource group to remove the server and all databases.

11 Revision summary

- Three options: SQL Database, Managed Instance, SQL on VM.
- Managed Instance is the lift and shift choice for legacy features.
- vCore gives control and reserved pricing. DTU is a simple bundle.
- Serverless pauses when idle. Elastic pools share compute across databases.
- PITR is automatic. LTR is configured for long retention.
- Failover group gives a stable listener and group failover. Geo-replication is per database.
- RPO is data loss, RTO is downtime. Replication is async, so RPO is not zero.
- Secure by default: TDE, private endpoint, Entra authentication.
