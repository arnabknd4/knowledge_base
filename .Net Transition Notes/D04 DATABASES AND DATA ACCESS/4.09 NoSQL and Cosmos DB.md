1 What is it
- A NoSQL database stores data in shapes other than relational tables. Instead of rows and joins, you model data around how the application reads it.
- Four common types: document (JSON-like records), key-value (a key points to a value), column-family (wide rows grouped by column families), graph (nodes and edges).
- Cosmos DB is Azure's globally distributed NoSQL service. It is a managed service: Microsoft runs servers, replication and patching. You choose an API, such as the NoSQL (document) API or the MongoDB API.
- MongoDB is a popular document database. Table storage and Blob storage are cheap Azure storage options for simple key-based data and files.
Legacy equivalent: SQL Server tables with XML or JSON columns, or file shares and ASP.NET Session State stores, used where a relational schema was too rigid.

2 Why needed
- Some workloads do not fit tables well: huge write volume, flexible schemas, data read as a whole object, and users spread across the world.
- Relational databases scale up on one big server. NoSQL databases scale out by splitting data across many machines (partitions).
- Without it, you force every shape of data into joins and fixed columns. Reads get slow, schema changes hurt, and global latency stays high.

3 Before you read
- Relational basics: tables, primary keys, joins, indexes.
- JSON format: objects, arrays, nested fields.
- Scale-up vs scale-out: bigger machine vs more machines.
- ACID in SQL Server (see 4.03). CAP below builds on it.

4 Features and core concepts
- Document type: one record is a JSON document with nested data. Why it matters: one read returns an order with its lines, no joins.
- Key-value type: you get or put by key only. Why it matters: very fast and simple, good for sessions and caches.
- Column-family type: rows hold groups of columns, tuned for large writes. Why it matters: time-series and logging style data.
- Graph type: data is nodes and relationships. Why it matters: friend-of-friend or recommendation queries that need many joins in SQL.
- CAP implications: when the network splits, a system must choose between consistency (all see the same data) and availability (always answers). Why it matters: it explains why NoSQL offers tunable consistency instead of always-strong.
- Cosmos DB partition key: the property that decides which physical partition stores an item. Why it matters: a good key spreads load evenly. A bad key creates a hot partition. You cannot change it later without migrating data. (verify)
- Cosmos DB request units (RU): the cost currency of every operation (read, write, query), covering CPU, memory and IO. Why it matters: you pay and get throttled (HTTP 429) based on RUs. Provisioned throughput, autoscale and serverless modes exist. (verify)
- Consistency levels: strong, bounded staleness, session, consistent prefix, eventual. Why it matters: stronger means higher latency and RU cost. Session is the default and the usual choice. (verify)
- Change feed: an ordered log of inserts and updates in a container. Why it matters: it feeds projections, events and sync to other systems without polling.
- Indexing policy: Cosmos DB indexes all properties by default. Why it matters: excluding unused paths lowers RU cost on writes.
- TTL (time to live): items auto-delete after a set number of seconds. Why it matters: free cleanup of sessions and temporary data.
- MongoDB basics: documents live in collections; indexes speed queries; the aggregation pipeline transforms data in stages; a replica set is one primary plus secondaries for failover. Why it matters: Cosmos DB offers a MongoDB API and jobs often ask for MongoDB.
- Table and Blob storage: Table stores key and property rows cheaply; Blob stores files and large objects. Why it matters: cheaper than Cosmos DB for simple cases and used for claim-check style payloads.
- Modeling for access patterns: list your queries first, then design documents and keys to answer them. Why it matters: it is the reverse of SQL, where you normalize first.
- When NoSQL is wrong: heavy joins, multi-row transactions, ad-hoc reporting, or strong relational integrity. Why it matters: choosing it by fashion is a common architect failure.
- Code worth memorizing (C#): var c = new CosmosClient(endpoint, new DefaultAzureCredential()); var item = await container.ReadItemAsync<Order>(id, new PartitionKey(customerId)); (point read by id plus partition key is the cheapest read).

5 Core focus (exam and interview)
- Most asked: how to choose a partition key; why RUs matter; which consistency level to pick; SQL vs NoSQL decision.
- Good partition key: high cardinality, even spread of data and requests, and appears in most queries.
- Cross-partition queries cost more RUs. Point reads are the cheapest.
- Cosmos DB logical partition size limit and throughput limits exist. (verify exact numbers)
- Default consistency is session. Multi-region writes are possible. (verify)
- Exam angle: match the Cosmos DB API and consistency level to a scenario, and know when Table or Blob storage is enough.

6 Real-world use case
- Situation: an order tracking service for an e-commerce platform written in ASP.NET Core. Read volume is high and each screen needs an order with its items and status history.
- Choice: store each order as one Cosmos DB document, partition key customerId, session consistency. The write side stays in Azure SQL; the change feed updates the read model. This is the read side of CQRS.
- Trade-off: reads are fast and cheap. You duplicate data, accept eventual consistency to the read model, and manage RU cost.
- When NOT to use it: financial ledgers, reporting with many joins, small apps where SQL Server already works, and teams with no NoSQL modeling skill.

7 Interview lens
- Q: How do you choose a Cosmos DB partition key? A: Pick a property with many distinct values that spreads storage and traffic evenly and appears in your common queries. Avoid values like status or date that create hot partitions.
- Q: What is an RU? A: A normalized cost unit for each operation. Cheap point reads cost little; large cross-partition queries cost many, and exceeding provisioned RU/s gives 429 errors.
- Q: Strong vs session consistency? A: Strong guarantees latest data but costs latency and limits multi-region use. Session guarantees a user sees their own writes and is enough for most apps.
- Q: When would you avoid NoSQL? A: When you need multi-entity transactions, many joins or ad-hoc reporting. Relational databases do that better.

8 Common mistakes
- Using the wrong partition key: one hot partition gets throttled while others sit idle. Fix: test key choice against real traffic before launch.
- Modeling like SQL: queries need many cross-partition calls. Fix: design from the queries and embed related data.
- Over-provisioning RUs or leaving default indexing on write-heavy data: bills rise. Fix: use autoscale and trim the indexing policy.
- Ignoring 429 responses: failures under load. Fix: use SDK retry and set sensible limits.
- Treating NoSQL as schema-free: old and new document shapes break code. Fix: version documents.

9 Mental model
- SQL: you design the tables, then ask any question later.
- NoSQL: you design the questions, then shape the data to answer them.
- Cosmos DB picture: account -> database -> container -> logical partitions (by key) -> items. RUs are the fuel; the partition key decides which tank is used.

10 Mini lab (30 minutes, local, no cost)
- Step 1: install the Azure Cosmos DB emulator locally, or create a Cosmos DB free tier account in the portal. (verify current free tier terms)
- Step 2: create a database shop and a container orders with partition key /customerId.
- Step 3: in a small .NET console app, add the Microsoft.Azure.Cosmos NuGet package and insert 20 order documents across 3 customer ids.
- Step 4: do a point read with id plus partition key, then a query without the partition key. Print the RequestCharge of each.
- Expected result: the point read costs about 1 RU; the cross-partition query costs more.
- Step 5: set a container TTL of 60 seconds, add an item, and confirm it disappears.
- Clean-up: delete the database, stop the emulator, or delete the resource group of the Azure account.

11 Revision summary
- Four NoSQL types: document, key-value, column-family, graph.
- CAP: under a network split, choose consistency or availability.
- Partition key: high cardinality, even spread, used in queries, hard to change.
- RU is the cost unit; point read by id plus key is cheapest; 429 means throttled.
- Five consistency levels from strong to eventual; session is the default. (verify)
- Change feed feeds projections and events; TTL auto-deletes items.
- Model for access patterns, not for normalization.
- NoSQL is wrong for joins, multi-row transactions and ad-hoc reporting.
