1 What is it
- Architecture documentation is the habit of writing down why a system looks the way it does, using small, repeatable formats instead of long documents nobody reads.
- It covers decisions (ADRs), pictures at different zoom levels (C4), behavior and deployment diagrams, operating guides (runbooks), and a short proposal process (RFC).
- Term: ADR means Architecture Decision Record, a one-page note of one decision.
- Term: RFC means Request for Comments, a short proposal circulated before a big change.
- Term: runbook means a step-by-step guide for operating or fixing a system.
- Legacy equivalent: the big Word "High Level Design" and "Low Level Design" documents and Visio diagrams on .NET Framework projects, which went stale within a month.

2 Why needed
- Teams forget why a choice was made. New joiners reverse it without knowing the trade-off.
- Without diagrams in a shared notation, every person draws boxes differently and meetings go in circles.
- Without runbooks, 2 a.m. incidents depend on one person's memory.
- Without a light RFC process, big changes arrive as surprises in code review.
- Architect interviews test whether you can communicate decisions, not only make them.

3 Before you read
- Know the difference between a component, a service and a container (in C4 a container is a deployable unit, not Docker).
- Know basic UML-style boxes and arrows.
- Know what Git, pull requests and Markdown are.
- Know the term trade-off: every option gains something and loses something.

4 Features and core concepts
- ADR (Architecture Decision Record): one short file per decision. Fields: context, options, decision, consequences, status. Why: it keeps the reasoning, not only the result.
  - Context: the forces and constraints at that time.
  - Options: two or three real alternatives, including "do nothing".
  - Decision: one sentence starting "We will...".
  - Consequences: good and bad results you accept.
  - Status: proposed, accepted, deprecated, superseded by ADR-NNN.
  - Rule: never edit an accepted ADR. Write a new one that supersedes it.
- C4 model: four zoom levels for diagrams. Why: one notation, many audiences.
  - Level 1 System Context: your system as one box, with users and external systems. For business people.
  - Level 2 Container: deployable or runnable units (web app, API, database, queue). For developers and ops.
  - Level 3 Component: parts inside one container (controllers, services). For the team that owns it.
  - Level 4 Code: classes. Usually generated, rarely drawn.
  - Every box has a name, a type and a short description. Every arrow has a label and a protocol.
- Sequence diagram: shows messages between participants over time. Why: it exposes ordering, retries and who waits for whom. Use it for one scenario, such as "place order".
- Deployment diagram: shows where containers run (Azure regions, App Service, AKS, VNets). Why: it answers network, failover and security questions.
- arc42 (awareness): a ready-made template with 12 sections (context, building blocks, runtime view, deployment view, decisions, risks and others). Why: you borrow the headings instead of inventing them. Use only the sections you need.
- Runbook: steps to deploy, roll back, restart, scale, or handle a named alert. Why: it turns tribal knowledge into a checklist. Include trigger, check, action, verify, escalate.
- Diagrams as code: diagrams written as text and rendered by a tool. Why: they live in Git, get reviewed in pull requests, and show diffs.
  - Mermaid: renders in GitHub, GitLab and Azure DevOps wikis. Best for sequence and simple flow.
  - Structurizr: C4-first, one model, many views.
  - PlantUML: older, powerful, needs a renderer.
  - Worth memorizing, a Mermaid sequence: sequenceDiagram / Client->>API: POST /orders / API->>DB: insert
- Lightweight RFC process: a short template (problem, proposal, alternatives, risks, open questions), a review window (for example 3 to 5 working days), a named decider, and an ADR written at the end. Why: it gathers input early without long meetings.

5 Core focus (exam and interview)
- Most asked: what goes into an ADR, and why you supersede instead of edit.
- Most asked: name the four C4 levels and who each is for.
- Expected: docs live next to the code, in the repo, reviewed like code.
- Expected: a diagram has a title, a legend and labeled arrows, or it is not finished.
- Remember: ADR statuses are proposed, accepted, deprecated, superseded.
- Remember: C4 "container" is not a Docker container.
- Remember: keep an ADR to about one page. Number them in order (0001, 0002).
- Exam link: AZ-305 and the Azure Well-Architected Framework expect documented decisions and trade-offs (verify current wording on Microsoft Learn).

6 Real-world use case
- Situation: a team extracts the Orders module from a legacy MVC monolith into a service on Azure Container Apps. Three weeks later a new developer asks why it uses Azure Service Bus and not direct HTTP calls.
- Choice: the lead had written ADR-0007 in the repo (docs/adr/0007-use-service-bus-for-order-events.md). Options listed: direct REST, Service Bus, Event Grid. Decision: Service Bus. Consequences: gains retry and dead-letter handling, loses simple debugging and adds cost.
- Also produced: C4 level 1 and 2 diagrams in Mermaid in the README, a sequence diagram for "place order", and a runbook for dead-letter queue handling.
- Trade-off: documentation costs time and can go stale. Keeping it in Git with a pull request checklist item ("docs updated?") keeps the cost low.
- When NOT to use it: a two-week throwaway prototype, or a tiny script. Write a README of ten lines and stop. Also avoid a full RFC for a small, easily reversed change. A short ADR or pull request description is enough.

7 Interview lens
- Q: What is in an ADR and why?
  - A: Context, options, decision, consequences, status. It records the reasoning so future teams can judge whether it still holds.
- Q: How do you keep diagrams from going stale?
  - A: Write them as code in the repo and review them in pull requests. Draw only the levels people use, usually C4 levels 1 and 2.
- Q: When do you write an RFC and when an ADR?
  - A: An RFC is for changes that need input from several teams before deciding. An ADR records the final decision, and can stand alone for small ones.
- Q: Explain C4 to a non-technical manager.
  - A: It is like maps: world view, city view, street view, building view. The system context diagram is the world view and needs no technical words.

8 Common mistakes
- Writing ADRs after the fact with no real options. In production it shows as "we always did it this way". Fix: write at decision time, list at least two options.
- Editing old ADRs. History is lost and trust drops. Fix: supersede with a new numbered ADR.
- Mixing levels in one diagram (users, classes and servers together). Readers cannot tell what they see. Fix: one C4 level per diagram.
- Diagrams in Visio or PowerPoint outside the repo. They go out of date silently. Fix: Mermaid or Structurizr in Git.
- Runbooks that say "check the logs". Responders freeze at night. Fix: exact commands, queries, expected output, escalation contact.
- Heavy RFC process for everything. Teams route around it. Fix: size the process to the risk and reversibility.

9 Mental model
- Docs are a map with three jobs:
  - Why (ADRs and RFCs): the history of choices.
  - What (C4, sequence, deployment): the picture at the right zoom.
  - How (runbooks): the instructions for operating it.
- Text diagram:
  - RFC (discuss) -> ADR (decide) -> C4 and sequence (show) -> runbook (operate)
  - All of it lives in the Git repo next to the code.

10 Mini lab (30 to 40 minutes, local tools, free)
- Steps:
  - Create a Git repo with folders docs/adr and docs/diagrams. Add a README.md.
  - Create docs/adr/0001-record-architecture-decisions.md with the five ADR fields. Decision: "We will record decisions as ADRs in this repo". Status: accepted.
  - Create docs/adr/0002-use-service-bus-for-order-events.md. Give three options, one decision, two good and two bad consequences. Status: proposed.
  - In README.md add a Mermaid block for a C4 level 2 style diagram using flowchart: Browser --> API --> SQL, API --> Service Bus --> Worker. Label each arrow with its protocol.
  - Add a second Mermaid block with a sequence diagram for "place order" (Client, API, DB, Service Bus).
  - Write docs/runbook-dead-letter.md with: trigger, how to check, how to reprocess, how to verify, who to escalate to.
  - Push to GitHub or GitLab and open the README in the browser.
- Expected result: both diagrams render on the page, and the repo shows three small docs plus the README.
- Clean-up: delete the repo, or keep it as a template for the capstone project.

11 Revision summary
- ADR fields: context, options, decision, consequences, status.
- Accepted ADRs are never edited. Supersede them.
- C4 levels: context, container, component, code. Container means deployable unit.
- Sequence diagram shows order of messages. Deployment diagram shows where things run.
- arc42 is a 12-section template. Borrow only what you need.
- Runbook: trigger, check, action, verify, escalate.
- Diagrams as code (Mermaid, Structurizr, PlantUML) live in Git and are reviewed in pull requests.
- RFC proposes, ADR records. Size the process to risk.
