1 What is it
- A cloud design pattern is a named, reusable solution to a problem that keeps showing up in distributed systems on Azure.
- The Azure Architecture Center catalogs about 40 of them. This topic covers the main ones: resilience, messaging, data, gateway, deployment and design patterns.
- Each pattern has a trade-off. A pattern is a tool to pick, not a rule to follow.
- Legacy equivalent: the Gang of Four patterns you used in .NET Framework (Factory, Decorator), but applied to whole systems and services instead of classes.

2 Why needed
- Distributed systems fail in partial, unpredictable ways: slow calls, lost messages, overloaded services.
- Without patterns, each team reinvents fixes badly. Retries create retry storms. One slow dependency drags down the whole app.
- Patterns give a shared vocabulary for design reviews and interviews.

4 Features and core concepts

Resilience group
- Retry: repeat a failed call after a wait. Plain meaning: transient errors often clear on their own. Use backoff plus jitter (random delay) so clients do not retry together. Only retry idempotent operations (safe to repeat).
- Circuit breaker: stop calling a failing service for a while. Plain meaning: like an electrical breaker, it trips open after repeated failures and fails fast. Protects the caller's threads and gives the dependency time to recover. States: closed, open, half-open.
- Bulkhead: isolate resources per dependency. Plain meaning: ship compartments. A separate thread or connection pool per downstream means one slow service cannot eat all capacity.
- Throttling: limit how many requests a client or tenant may make. Protects the service under load. Returns 429 Too Many Requests.
- Health endpoint monitoring: expose a health URL that probes dependencies. Load balancers and Front Door use it to remove unhealthy instances.

Messaging and load group
- Queue-based load leveling: put a queue between producer and consumer. Absorbs traffic spikes so the consumer works at a steady rate.
- Competing consumers: several workers read from one queue. Gives scale-out and resilience. Messages must be processed idempotently.
- Priority queue: separate queues or priorities so urgent work is processed first. Needed when SLAs differ per customer.
- Claim check: store the large payload in Blob Storage and send only a reference in the message. Avoids message size limits and cuts cost.
- Saga: a long business process split into local transactions, each with a compensating action if a later step fails. Replaces distributed transactions. Two styles: orchestration (central coordinator) and choreography (services react to events).
- Compensating transaction: an action that undoes a prior step (refund after a failed shipment). Must itself be retryable.

Structure and gateway group
- Sidecar: helper process deployed beside the main app (logging, proxy, Dapr). Keeps cross-cutting code out of the app and works across languages.
- Ambassador: a sidecar that handles outbound calls for the app (retry, TLS, monitoring).
- Gateway offloading: move shared concerns (TLS, auth, rate limits) to the gateway. Example: API Management or Application Gateway.
- Gateway routing: one public endpoint routes to many backend services.
- Gateway aggregation: the gateway combines several backend calls into one response. Cuts chatty client calls.

Data and access group
- Valet key: give the client a limited, time-bound token to access a resource directly. Example: SAS token for a Blob upload. Takes load off your API.
- Cache-aside: app checks the cache first, loads from the database on a miss, then fills the cache. Needs an invalidation plan.
- CQRS: separate models for writing and reading. Lets reads scale and be shaped differently from writes. Adds eventual consistency.
- Event sourcing: store every change as an event, derive current state by replaying. Gives audit and replay, but is complex to query and version.
- Sharding: split data across databases by a key. Needed beyond one database's limits. Choose the key carefully to avoid hot partitions.
- Leader election: among several instances, one is chosen to coordinate. Prevents duplicated work. On Azure use a blob lease or a distributed lock.

Deployment-scale group
- Deployment stamps: deploy independent copies of the full stack, each serving a set of tenants or a region. Limits blast radius and scales out.
- Geode: deploy identical nodes in many regions, all serving active traffic with replicated data. Low latency and high availability, with hard data consistency problems.

5 Core focus (exam and interview)
- Most asked: retry vs circuit breaker, queue-based load leveling, saga, CQRS, cache-aside, claim check, valet key.
- Match problem to pattern. Spike of traffic: queue-based load leveling. Cascading failure: circuit breaker and bulkhead. No distributed transaction: saga. Big payload: claim check. Direct blob upload: valet key.
- Service Bus message size limits differ by tier (verify). Standard is much smaller than Premium.
- Circuit breaker states: closed, open, half-open.
- Retry only transient faults (timeouts, 503, 429). Never retry 400 or 404.
- Exam map: Front Door and Application Gateway do gateway routing and offloading. API Management does offloading and aggregation. Azure Functions and Service Bus fit competing consumers.

6 Real-world use case
- Situation: an order system for a retailer in India has a sale-day spike. Checkout calls inventory, payment and shipping services.
- Choice: API gateway (API Management) for offloading. Orders are written, then an event goes to Service Bus (queue-based load leveling). Workers compete on the queue. The order flow is an orchestrated saga with compensations (refund, restock). HttpClient calls use retry with jitter and a circuit breaker. Redis cache-aside serves product reads.
- Trade-off: more moving parts, eventual consistency (the customer sees "processing"), harder debugging, and extra cost for messaging and cache.
- When NOT to use: a small internal app with a few hundred users on one database. A modular monolith with plain transactions is simpler and safer. Do not add sagas or CQRS "just in case".

7 Interview lens
- Q: Retry vs circuit breaker? A: Retry handles short transient faults by trying again. Circuit breaker stops calls to a failing service so you fail fast and protect resources. Use them together, with the retry inside the breaker.
- Q: How do you handle a transaction across services? A: Use a saga with local transactions and compensating actions instead of two-phase commit. Choose orchestration for complex flows and choreography for simple ones.
- Q: Why use claim check? A: Messages have size limits and large messages are slow and costly. Store the payload in Blob Storage and pass a reference.
- Q: Bulkhead in practice? A: Give each dependency its own limited pool (threads, connections, or separate deployment). A slow dependency then exhausts only its own pool.

8 Common mistakes
- Retry without backoff or jitter: causes a retry storm that takes down a recovering service. Fix: exponential backoff, jitter, retry budget.
- Retrying non-idempotent calls: duplicate payments. Fix: idempotency keys and deduplication.
- Circuit breaker with no fallback: users still get errors. Fix: cached or degraded response.
- Competing consumers that are not idempotent: duplicate processing on redelivery. Fix: idempotent handlers.
- Cache-aside with no invalidation: stale data. Fix: TTL and versioned keys.
- Choosing a shard key with skew: one hot partition. Fix: high-cardinality key, test with real data.
- Pattern overuse: microservice complexity for a simple app. Fix: justify each pattern by a real problem.

9 Mental model
- Think of a busy restaurant.
- Queue = order tickets on a rail (load leveling). Several cooks take tickets (competing consumers).
- Circuit breaker = stop ordering from a supplier who keeps failing.
- Bulkhead = separate kitchen stations.
- Saga = if the dessert step fails, cancel the dessert and credit the bill (compensation).
- Valet key = a temporary key card for one door only.
- Stamps = open identical restaurants instead of one giant one.

10 Mini lab (about 30 minutes, local only, no Azure cost)
- Create a console app: dotnet new web -n PatternLab, then cd PatternLab.
- Add the package: dotnet add package Microsoft.Extensions.Http.Resilience (verify name and version).
- In Program.cs register a named HttpClient pointing to https://localhost:5099/flaky and call AddStandardResilienceHandler().
- Add a second minimal endpoint /flaky that returns 503 for the first two calls, then 200 (use a static counter). Add an endpoint /call that uses the HttpClient to call /flaky.
- Run with dotnet run and open /call. Expected: you get 200 even though the first two attempts returned 503. Check the console logs to see retries.
- Change /flaky to always return 503 and call /call repeatedly. Expected: after several failures the circuit opens and calls fail fast with a broken circuit error.
- Clean-up: stop the app and delete the PatternLab folder.

11 Revision summary
- Resilience: retry (with backoff and jitter), circuit breaker, bulkhead, throttling, health endpoint monitoring.
- Messaging: queue-based load leveling, competing consumers, priority queue, claim check.
- Consistency: saga and compensating transaction replace distributed transactions.
- Data: cache-aside, CQRS, event sourcing, sharding, leader election, valet key.
- Gateway: offloading, routing, aggregation. Sidecar and ambassador add helper processes.
- Scale and isolation: deployment stamps (isolated copies), geode (active in many regions).
- Circuit breaker states: closed, open, half-open.
- Every pattern adds cost and complexity, so use it only for a real problem.
