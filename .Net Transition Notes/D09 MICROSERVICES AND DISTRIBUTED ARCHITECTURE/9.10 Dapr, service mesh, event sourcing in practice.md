1 What is it
- Dapr (Distributed Application Runtime) is a sidecar process that sits next to your service and gives it ready-made distributed-system features through a simple HTTP or gRPC API.
- A service mesh is a layer of sidecar proxies that handles service-to-service traffic (encryption, retries, routing) without changing application code.
- Event sourcing means storing every change as an event in order, instead of storing only the current state. Current state is rebuilt by replaying events.
- .NET Aspire is a .NET tool set for describing and running a multi-service app locally, with built-in telemetry and service wiring (verify current name, version and scope).
- Legacy equivalent: Dapr resembles shared WCF or enterprise library plumbing for messaging and state. A mesh resembles load balancer and firewall rules moved into the platform. Event sourcing resembles an audit table that is the source of truth.

4 Features and core concepts
- Dapr building blocks: ready-made APIs for service invocation, state store, pub/sub, bindings, secrets, configuration, actors, workflows (verify list). Why it matters: you swap Redis for Service Bus by changing a component file, not code.
- Dapr sidecar model: each service gets a local Dapr process. Why it matters: language-neutral, but adds a hop and one more process to operate.
- Mesh trade-offs: gives mutual TLS, traffic splitting, retries and observability for free (Istio, Linkerd). Why it matters: you pay in CPU and memory per pod, extra latency, upgrade effort and hard debugging. Small teams often do not need one.
- Dapr vs mesh: Dapr gives application-level features (state, pub/sub). A mesh gives network-level features. They overlap on retries and mTLS, so choose one owner for each.
- Event sourcing costs: event schema versioning, replay time (solved with snapshots), eventual consistency in read models, harder queries, steep learning curve. Why it matters: it is a heavy choice, not a default.
- Event sourcing tooling: event store databases, Marten on PostgreSQL, EventStoreDB (verify current names), Cosmos DB change feed for projections.
- .NET Aspire: an app host project lists services and dependencies, and a dashboard shows logs, traces and metrics locally (verify).

6 Real-world use case
- Situation: an order system needs a full history of every order change for audit and dispute handling.
- Choice: event-source only the Order aggregate. Project read models into Azure SQL for screens. Keep the rest of the system as ordinary CRUD.
- Trade-off: you gain a perfect audit trail and replay. You pay with version handling for old events and delayed read models.
- When NOT to use: simple CRUD, reporting-heavy screens, small teams. Skip a mesh below roughly a dozen services, and skip Dapr if you already use one messaging SDK happily.

11 Revision summary
- Dapr is a sidecar offering building-block APIs; components are swappable by config.
- A mesh handles network concerns; Dapr handles application concerns.
- Mesh cost: per-pod resources, latency, operational complexity.
- Event sourcing stores events, not current state; state is rebuilt by replay.
- Snapshots shorten replay; projections build query-friendly read models.
- Event sourcing is for audit-heavy aggregates, not whole systems.
- Aspire is local orchestration plus telemetry for .NET apps (verify).
