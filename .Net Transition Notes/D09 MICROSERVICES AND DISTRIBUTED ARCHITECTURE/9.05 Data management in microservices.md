1 What is it

- Each microservice owns its data. Other services cannot reach into its tables. They ask through an API or react to events it publishes.
- This means no shared schema, and no single big SQL transaction across services. Consistency between services is built with messages and compensations.
- Terms: a read model is a copy of another service's data, stored in your own shape for fast queries. Eventual consistency means copies catch up after a short delay.
- Legacy equivalent: one big SQL Server database used by every module of the MVC app, with joins across any tables and one TransactionScope around everything.

2 Why needed

- A shared database couples every team. One column rename or index change can break five services.
- Services cannot be deployed or scaled independently if they share a schema.
- Locks and long queries from one service slow down all others.
- Without clear data ownership, nobody knows who is the source of truth for a customer or an order.

4 Features and core concepts

- Database per service: each service has its own private store, and only it reads or writes it. Why: independent deployment, schema freedom, fault isolation. Private can mean separate database, or separate schema with separate credentials (weaker, but a common first step).
- Shared database anti-pattern: many services use one schema. Why it matters: it is a distributed monolith with extra network hops. Schema changes need cross-team coordination.
- Data duplication and read models: a service keeps a local copy of the fields it needs from other services, updated from events. Why: avoids a call to the owner on every request. Cost: copies can be stale. Store only what you need, and keep the owner's id.
- API composition: a caller (gateway or BFF) calls several services and joins the results in memory. Why: simplest way to answer a query across services. Weakness: slow for big lists, and lower availability, because every service in the call must be up.
- CQRS: separate the write model from the read model. Why: reads get their own shape and store, for example Azure SQL for writes and a denormalized projection for queries. It adds moving parts, so use it only where reads and writes really differ.
- Outbox: write the business change and an outgoing message row in the same local transaction. A separate process publishes the row to the broker. Why: avoids the dual-write problem, where the database commit succeeds but the publish fails (or the reverse).
- Change data capture (Debezium awareness): a tool reads the database transaction log and emits row changes as events. Why: publishes changes without touching application code. Good for legacy databases you cannot change. It exposes your table shape, so prefer outbox-table CDC over raw table CDC.
- Saga: a long business process split into local transactions, each with a compensating action if a later step fails. Orchestration has one coordinator, choreography uses events only. Why: replaces the distributed transaction.
- Alternatives to distributed transactions: avoid 2PC (two-phase commit, a protocol where a coordinator locks all participants). Use saga, outbox, idempotent consumers, or merge services that must be atomic. Why: 2PC blocks, couples availability, and most cloud brokers and NoSQL stores do not support it.
- Reporting across services: do not run joins across live service databases. Stream events or CDC into a reporting store (data lake, Azure Synapse or Fabric, or a reporting SQL database). Why: analytics load stays off OLTP stores.
- Reference data sharing: slow-changing data such as country codes, currencies and tax rates. Options: a reference service with caching, a shared versioned package for truly static lists, or events that refresh local copies. Why: avoids a call on every request and avoids shared tables.
- Memorize (outbox shape):
  - BEGIN TRAN; INSERT Orders; INSERT Outbox(Id, Type, Payload); COMMIT;
  - Publisher: read unsent rows, publish, mark sent. Consumers must be idempotent.

5 Core focus (exam and interview)

- Most asked: why not a shared database, how to do a query across services, how to keep two services consistent without 2PC.
- Know the dual-write problem and how outbox fixes it.
- Delivery is at-least-once, so consumers need idempotency (a dedupe key, or an operation that is safe to repeat).
- Know saga orchestration vs choreography and when to prefer each: orchestration for many steps with clear flow, choreography for few steps and loose coupling.
- Azure Service Bus gives duplicate detection and transactions inside one namespace, but not a transaction spanning your SQL database (verify current limits).
- Cosmos DB change feed can drive projections (verify details in note 4.09).
- Rule of thumb: if two things must always be strongly consistent, they likely belong in the same service and aggregate.

6 Real-world use case

- Situation: an order system migrated from a legacy .NET Framework monolith. Orders, Inventory and Payments were tables in one SQL Server database, joined freely.
- Choice: each service gets its own Azure SQL database. Order service writes an order and an outbox row in one transaction. A worker publishes OrderPlaced to Azure Service Bus. Inventory and Payment react and publish their own events. An orchestrated saga in the Order service cancels the order and releases stock if payment fails. A Customer summary is kept as a local read model, updated from CustomerChanged events.
- Trade-off: more infrastructure, duplicated data, and the UI must handle "order pending" states. Debugging needs distributed tracing.
- When NOT to use it: a small team, one deployable, strong consistency needs, or reporting-heavy screens. Stay with a modular monolith and one database with schema-per-module boundaries.

7 Interview lens

- Q: Why is a shared database an anti-pattern for microservices?
  A: It couples schemas, deployments and performance of all services. It creates a distributed monolith where one change forces coordinated releases.
- Q: How do you query data owned by several services?
  A: Use API composition for small, simple joins. Use a CQRS read model fed by events for heavy or frequent queries. Use a reporting store for analytics.
- Q: What is the dual-write problem?
  A: Writing to a database and a broker separately can leave them out of sync if one fails. Fix it with the outbox pattern or CDC, plus idempotent consumers.
- Q: Why avoid distributed transactions?
  A: 2PC locks resources across services, hurts availability, and many cloud services do not support it. Use sagas with compensations instead.

8 Common mistakes

- Shared tables "just for now". Shows up as a release freeze when one team changes a column. Fix: give each service its own schema and credentials first, then split the database.
- Publishing after commit in application code. Shows up as lost events after a crash. Fix: outbox.
- Non-idempotent consumers. Shows up as double charges or double stock deduction on redelivery. Fix: store processed message ids, or make operations naturally repeatable.
- Copying too much data into read models. Shows up as hidden coupling and stale data bugs. Fix: copy only needed fields and treat the owner as the source of truth.
- Cross-service joins in reports against live databases. Shows up as slow OLTP. Fix: reporting store.
- Sagas without compensation design or timeouts. Shows up as orders stuck in pending. Fix: define compensations and a timeout path for every step.

10 Mini lab

- Time: about 30 minutes. Tools: .NET SDK, Docker, SQL Server container (local only, no Azure cost).
- Steps:
  - Run docker run -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD=Your_pass123 -p 1433:1433 -d mcr.microsoft.com/mssql/server:2022-latest
  - Create two databases, OrderDb and InventoryDb.
  - In OrderDb create Orders(Id, Total) and Outbox(Id, Type, Payload, SentAt NULL).
  - Write a console app that inserts one order and one outbox row in one transaction.
  - Write a second loop that reads unsent outbox rows, prints them as "published", and sets SentAt.
  - In InventoryDb create ProcessedMessages(MessageId PK). A consumer method inserts the message id first and skips the work if it already exists.
  - Run the publisher twice on the same row, and replay the message to the consumer.
- Expected result: the order and outbox row appear together. The consumer processes a message once even when delivered twice.
- Clean-up: docker rm -f the container and delete the console project.

11 Revision summary

- Each service owns its data. Others use API or events only.
- Shared database equals distributed monolith.
- Read models are copies. Accept eventual consistency.
- API composition is simple but weak on availability and big joins.
- Outbox solves the dual-write problem. Consumers must be idempotent.
- Saga replaces distributed transactions. Every step needs a compensation.
- Reports go to a separate store fed by events or CDC.
- If two things need strong consistency, keep them in one service.
