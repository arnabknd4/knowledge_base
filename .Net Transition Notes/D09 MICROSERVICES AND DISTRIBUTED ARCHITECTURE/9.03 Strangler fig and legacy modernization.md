1 What is it
- Strangler fig is a way to replace an old system piece by piece instead of rewriting it all at once.
- A new layer (a facade, which is a front door that hides what is behind it) sits in front of the legacy app. You move one slice of functionality at a time into new code. The legacy app shrinks until you can switch it off.
- The name comes from the strangler fig tree, which grows around a host tree and slowly replaces it.
- Legacy equivalent: a big-bang rewrite or a long-lived "v2" branch of the .NET Framework MVC app, but done in small, releasable steps.

----

2 Why needed
- Big-bang rewrites run late, freeze feature work and often fail. The old system keeps changing while you rebuild it.
- Without this approach, you cannot ship value or roll back until the whole rewrite is done.
- Strangler fig gives early releases, small risk per step and a rollback path at every step.

----

3 Before you read
- A reverse proxy is a server that receives requests and forwards them to another server.
- A bounded slice is one business capability, for example "invoicing" or "customer search".
- Idempotent means running the same operation twice gives the same result as running it once.
- A database transaction keeps several writes consistent as one unit.

4 Features and core concepts

Seams
- Plain meaning: a place in the code where you can cut and redirect behaviour without editing the code around it.
- Why it matters: you can only extract what has a clean boundary. Look for URLs, interfaces, queue messages or stored procedures as seams.

Incremental extraction
- Plain meaning: move one slice at a time to new code, never everything.
- Why it matters: every step is small, testable and releasable. Pick slices with low coupling first to build confidence.

Facade and proxy (YARP, API Management)
- Plain meaning: a routing layer in front of the legacy app. It sends each URL to either old or new code.
- Why it matters: clients never change. You flip a route to move traffic. YARP is Microsoft's reverse proxy library for .NET. Azure API Management (APIM) is the managed gateway option.
- Memorize: a YARP route maps a path like /invoices/{**catch-all} to a cluster pointing at the new service. Everything else goes to legacy.

Anti-corruption layer (ACL)
- Plain meaning: a translation layer so the new code does not adopt the legacy model, names or quirks.
- Why it matters: without it the new service inherits the old design mess.

Branch by abstraction
- Plain meaning: put an interface in front of old logic inside the same codebase, build the new implementation behind the same interface, then switch with a flag.
- Why it matters: lets you replace internals without a long-lived branch. Use it when the slice has no URL seam.

Parallel run
- Plain meaning: send the same request to old and new code, return the old answer, and compare the results.
- Why it matters: proves the new code is correct with real data before users depend on it.

Data synchronization (change data capture, risks of dual writes)
- Plain meaning: keeping old and new databases in step. Change data capture (CDC) reads the database log and publishes changes. A dual write means the app writes to two places itself.
- Why it matters: dual writes can fail halfway and leave the two stores different. CDC or an outbox is safer.

Migration sequencing
- Plain meaning: the order of slices.
- Why it matters: start with low risk and low coupling, then the high value ones. Leave the tangled core for last.

Measuring progress
- Plain meaning: track the share of traffic, routes or features served by new code, and legacy lines or endpoints remaining.
- Why it matters: shows the client it is working, and tells you when to retire legacy.

Rollback
- Plain meaning: flip the route or flag back to legacy.
- Why it matters: this is the main safety benefit. It only works if legacy still receives data updates.

Handling organizational change
- Plain meaning: people, ownership and communication, not only code.
- Why it matters: teams need clear ownership of each slice, a shared roadmap and agreement on when legacy is switched off.

5 Core focus (exam and interview)
- Most asked: why not a big-bang rewrite, how routing works, how data is handled, how rollback works.
- Key idea: the proxy gives you the switch. Without a facade there is no strangler.
- Data is the hardest part. Expect questions on shared database vs separate database and on dual writes.
- Know the three data options: shared database at first, CDC sync, or a new owned database with an outbox.
- Azure terms to recall: API Management, Front Door, Application Gateway as routing options (verify the current feature set).

----

6 Real-world use case
- Situation: a 12-year-old .NET Framework MVC app for order management on IIS. The client wants cloud and modern .NET but cannot stop feature work.
- Choice: put YARP in a new ASP.NET Core app in front of the old site. Extract "order tracking" first because it is read-only and has few dependencies. Run it as a new service reading through an ACL. Compare outputs in parallel run, then route 10 percent of traffic, then 100 percent.
- Trade-off: you run two systems for a long time and pay for both. Routing, auth and sessions must work across both.
- When NOT to use it: small apps that can be rewritten in a few weeks, systems with no seams where everything shares one transaction, or apps due to be retired soon.

7 Interview lens
- Q: Why strangler fig over a rewrite?
  A: Each step ships and can be rolled back. A rewrite delivers nothing until the end and the old system keeps changing meanwhile.
- Q: How do you pick the first slice?
  A: Low coupling, clear seam, visible value, low risk. Read-only features are a good start.
- Q: How do you handle data during extraction?
  A: Start with the shared database behind an ACL, then move to an owned database. Sync with CDC or an outbox, and avoid dual writes.
- Q: How do you know when to switch off legacy?
  A: When traffic and data for all slices are on the new side for an agreed period, with metrics and sign-off.

----

8 Common mistakes
- Dual writes without a recovery plan: the two databases drift apart. Fix: use an outbox or CDC and reconcile regularly.
- Skipping the ACL: the new service copies legacy models. Fix: translate at the boundary.
- Extracting the hardest, most tangled module first: months pass with no result. Fix: start small.
- Forgetting auth and session state: users are logged out when the route changes. Fix: share the cookie or token scheme, or move to token auth first.
- No end date for legacy: two systems live forever. Fix: set a retire plan and track progress.
- Rollback that is impossible because new writes never reached legacy. Fix: keep data in sync both ways until sign-off.

----

9 Mental model
- Picture a road diversion:

  Client -> Facade (YARP/APIM) -> route A -> Legacy app
                                 -> route B -> New service
- Over time more routes point right, until legacy has none.

10 Mini lab
- Time: about 30 minutes. Tools: .NET SDK installed locally.
- Steps:
  - Create two small apps: dotnet new web -n Legacy and dotnet new web -n NewSvc. In Legacy, map "/" and "/orders" to return the text "legacy". In NewSvc, map "/orders" to return "new".
  - Create a third app: dotnet new web -n Gateway, then dotnet add package Yarp.ReverseProxy.
  - In Gateway add AddReverseProxy().LoadFromConfig(...) and app.MapReverseProxy(). In appsettings.json define route "orders" with path /orders/{**catch-all} to cluster "new", and route "rest" with path /{**catch-all} (Order 100) to cluster "legacy".
  - Run all three on different ports and set the cluster addresses to match.
  - Call the Gateway: /orders should return "new", and / should return "legacy".
  - Change the "orders" route to point at "legacy" and restart. Confirm the rollback works.
- Expected result: one URL, two backends, switched by config only.
- Clean-up: stop the three apps and delete the three folders.

----

11 Revision summary
- Strangler fig replaces legacy slice by slice behind a facade.
- The facade (YARP or API Management) is the traffic switch and the rollback.
- Seams decide what can be extracted. Use branch by abstraction when no URL seam exists.
- The ACL keeps legacy models out of the new code.
- Parallel run compares old and new results before cutover.
- Avoid dual writes. Use CDC or an outbox.
- Start with low-risk read-only slices. Track progress by traffic share.
- Set a retire date for legacy or you run two systems forever.
