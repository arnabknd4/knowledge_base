1 What is it
- Operating microservices means running many small, independently deployed services in production without losing control of them.
- It covers the daily work after the design is done: pipelines per service, versions, configuration, tracing, ownership, on-call and cost.
- The main idea is that each service must be deployable, observable and owned on its own. Without that, you have many small apps that fail together.
- Legacy equivalent: one big IIS-hosted solution with one release train, one Web.config and one support team, now split into many releases, many configs and many owners.

2 Why needed
- Splitting a monolith moves complexity from code into operations.
- Without independent CI/CD, every service waits for a shared release and you get a distributed monolith.
- Without tracing and SLOs, nobody can say which service caused a slow request.
- Without clear ownership, incidents bounce between teams and nobody fixes the root cause.
- Without cost allocation, the cloud bill grows and nobody is accountable.

4 Features and core concepts
- Independent CI/CD: each service has its own pipeline, repo or folder, and release schedule. Why: a change in one service must not force a release of others.
- Versioning: each service has its own version (semantic versioning), and APIs have a version policy. Why: consumers need to know what breaks and when.
- Config and secrets per service: each service owns its settings and its own Key Vault access through managed identity. Why: one leaked or wrong shared secret affects everything.
- Service templates and golden paths: a starter template with pipeline, logging, health checks and Dockerfile already set up, plus the recommended way to build and deploy. Why: new services start correct and teams do not reinvent the basics.
- Distributed tracing: one trace ID follows a request across all services (W3C trace context, Application Insights or OpenTelemetry). Why: you can see which hop was slow or failed.
- SLOs per service: a measurable target such as 99.9 percent of requests succeed within 500 ms. Why: it tells the team when to stop shipping features and fix reliability.
- Dependency management: track which services call which, and which NuGet packages and base images they share. Why: one vulnerable package or breaking change spreads across many services.
- On-call ownership: the team that builds a service also runs it ("you build it, you run it"). Why: owners feel the pain and fix causes, not symptoms.
- Platform team: a small team that provides the shared tooling (clusters, pipelines, templates, observability). Why: product teams stay focused on features.
- Cost allocation: tags on every resource so cost maps to a service and team. Why: you can see which service is expensive and who decides about it.
- Feature flags: turn behaviour on or off without a deployment. Why: you can release code dark, roll out slowly and switch off a bad feature fast.
- Worth memorizing: a trace ID is propagated in the traceparent HTTP header (W3C trace context).

5 Core focus (exam and interview)
- Most asked: what makes microservices hard to run, and how you keep them manageable.
- Expect: independent deployability, tracing across services, SLOs and error budgets, ownership model.
- Tagging for cost: use consistent tags such as service, team, environment (Azure Policy can enforce them).
- Managed identity is preferred over stored secrets for service-to-Azure access.
- Rule to remember: if two services must always deploy together, they are not independent.
- Platform team gives paved roads, not mandatory control. Teams may leave the golden path with a reason.

6 Real-world use case
- Situation: a Kolkata-based team splits a legacy order system into 8 services on AKS. After three months, releases are slow because all services share one pipeline and one config file.
- Choice made: one pipeline per service from a shared YAML template, a service starter template, Application Insights with OpenTelemetry for tracing, a Key Vault per environment with managed identity per service, tags for cost, and a named on-call team per service.
- Trade-off: more setup and more moving parts. You pay with platform effort and standards that teams must follow.
- When NOT to use it: with a small team (under about 10 developers) or one product with a single release cadence. A modular monolith is cheaper to run and easier to debug.

7 Interview lens
- Q: How do you know a service is truly independent?
  A: It builds, tests and deploys on its own, with its own data and config. A release of it never requires releasing another service.
- Q: How do you trace a slow request across 6 services?
  A: Propagate one trace ID through HTTP and messaging headers and send spans to a central store like Application Insights. Then read the trace to find the slow hop.
- Q: Who should be on call for a service?
  A: The team that owns and builds it. A separate ops team lacks context and removes the feedback that drives fixes.
- Q: How do you stop microservice cost from growing unseen?
  A: Enforce tags with Azure Policy and report cost per service and team. Review the top services regularly with their owners.

8 Common mistakes
- Shared pipeline or shared release train. Shows up as one failed service blocking all deployments. Fix: one pipeline per service from a common template.
- Shared secrets and shared config. Shows up as one rotation breaking many services. Fix: per-service config and managed identity.
- No correlation ID. Shows up as logs that cannot be linked across services. Fix: propagate trace context everywhere, including queue messages.
- SLOs set on infrastructure only (CPU) instead of user outcomes. Shows up as green dashboards while users see errors. Fix: set SLOs on success rate and latency.
- Unowned services. Shows up as alerts nobody answers. Fix: an owner and escalation path recorded for every service.
- Platform team becomes a gatekeeper. Shows up as teams waiting on tickets. Fix: self-service templates and clear paved roads.

9 Mental model
- Each service is a small company with its own pipeline, config, health targets, owners and bill. The platform team is the city that provides roads, power and rules.

```
request -> [svc A] -> [svc B] -> [svc C]
             |           |          |
        same trace ID, own pipeline, own SLO, own owner, own cost tag
        shared: platform tooling, templates, observability
```

10 Mini lab
- Goal (30 minutes, local only, no Azure cost): see one trace ID flow through two services.
- Steps:
  - Create two minimal ASP.NET Core APIs, ServiceA and ServiceB (dotnet new web).
  - Add the OpenTelemetry packages (OpenTelemetry.Extensions.Hosting, instrumentation for AspNetCore and HttpClient, console exporter) to both.
  - Make ServiceA call ServiceB with HttpClient on one endpoint.
  - Run both and call ServiceA once.
  - Watch the console output of both services.
- Expected result: spans in both consoles show the same TraceId, and the ServiceB span has the ServiceA span as its parent.
- Clean-up: stop both processes and delete the two project folders.

11 Revision summary
- Independent CI/CD per service is the base of microservice operations.
- Each service owns its version, config, secrets and data access.
- Golden paths and templates make new services correct from day one.
- One trace ID across all services makes failures findable.
- SLOs per service decide when to fix reliability before shipping features.
- The team that builds the service is on call for it.
- A platform team provides self-service tooling and does not gate teams.
- Tag every resource so cost maps to a service and team.
