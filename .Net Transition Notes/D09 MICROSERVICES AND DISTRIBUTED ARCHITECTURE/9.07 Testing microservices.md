Topic 9.07 is Testing microservices, tagged P3 R L with no K tag, so this is a full note with a mini lab.

1 What is it

- Testing microservices means checking a system made of many small, separately deployed services. Each service has its own code, its own data and its own release cycle.
- The old test pyramid (many unit tests, fewer integration tests, few UI tests) still applies. It needs extra layers because the risk moves to the connections between services.
- Contract = an agreed description of the requests and replies between two services. A consumer is the service that calls. A provider is the service that is called.
- Legacy equivalent: a monolith with one solution, one test project and one shared test database. Here you cannot start everything together, so tests must isolate each service.

2 Why needed

- Services change independently. A provider can rename a field, deploy on Tuesday, and break a consumer nobody told.
- Full end-to-end tests across all services are slow, flaky and hard to debug. Without other layers, teams either stop testing integration or wait hours for a broken pipeline.
- A good strategy catches most bugs cheaply inside one service and only a few at the system level.

4 Features and core concepts

- Adapted test pyramid. Plain meaning: unit tests at the base, then component, contract and integration tests, with a thin layer of end-to-end tests on top. Why it matters: it keeps most checking cheap and fast and limits the slow flaky tests.
- Unit tests. Plain meaning: test one class or function with no network or database. Why it matters: they are the fastest feedback for business rules.
- Component tests. Plain meaning: run one whole service in memory or in a container, with its dependencies faked or replaced. Why it matters: you test the real HTTP, serialization and database code of one service without needing the others. In .NET use WebApplicationFactory and Testcontainers.
- Contract tests. Plain meaning: a check that consumer and provider agree on request and reply shape, without running both at once. Why it matters: it catches breaking changes before deployment.
- Consumer-driven contracts (Pact). Plain meaning: the consumer writes down what it needs. That file is the contract. The provider pipeline replays it against the real provider. Why it matters: providers learn exactly which fields consumers depend on, so they can change the rest safely. A pact broker (shared store of contracts) tracks versions and answers "can I deploy this?".
- Integration tests. Plain meaning: test a service with its real neighbours, such as a real database or message broker. Why it matters: they find wiring, configuration and query errors that fakes hide. Keep them few.
- End-to-end tests. Plain meaning: drive a whole business flow through the deployed system. Why it matters: it proves the pieces work together, but it is slow and fragile, so cover only critical journeys (checkout, login).
- Test doubles for external services (WireMock). Plain meaning: a fake HTTP server that returns canned replies. Why it matters: you can simulate slow replies, errors and third-party APIs you do not control.
- Testing in production. Plain meaning: safe checks on the live system. Why it matters: some failures only appear under real traffic and data.
  - Canary: send a small share of traffic to the new version and watch metrics.
  - Synthetic checks: scheduled fake users that run a key flow and alert on failure.
- Chaos testing awareness. Plain meaning: deliberately break things (kill an instance, add latency) to see if the system copes. Why it matters: it proves resilience claims. Awareness level only for now.
- Test environment strategy. Plain meaning: where tests run. Options are local containers, shared dev, per-pull-request ephemeral environments, and staging. Why it matters: a shared staging environment becomes a bottleneck and a source of "who broke it?".
- Test data. Plain meaning: how you create and clean the data tests need. Why it matters: shared mutable data causes flaky tests. Prefer each test creating its own data, with builders (topic 1.11) and unique IDs.

5 Core focus (exam and interview)

- Most asked: why not rely on end-to-end tests, and what is contract testing.
- Know the difference: a contract test checks shape, not business logic. A component test checks one service, an integration test checks real neighbours.
- Consumer-driven means the consumer defines expectations. Provider-driven means the provider publishes a spec (OpenAPI) and consumers conform.
- Know the canary versus blue-green difference (topic 7.06): canary shifts traffic gradually.
- Async flows are hard to test. Test the producer publishes the right message and the consumer handles it, including duplicates (idempotency, topic 6.01).
- Pact tool versions and the managed broker offering change often (verify).

6 Real-world use case

- Situation: an order service calls a pricing service, and a notification service listens to order events on Azure Service Bus. Eight teams, weekly releases.
- Choice made:
  - Unit tests for pricing rules.
  - Component tests per service with Testcontainers for SQL Server and WireMock for the payment gateway.
  - Pact contracts between order and pricing, and for the OrderPlaced event schema.
  - Pipeline step "can-i-deploy" against the broker before release.
  - Three end-to-end tests for place-order and cancel-order.
  - Canary release plus a synthetic check on checkout.
- Trade-off: contracts need discipline and broker setup, and they only protect the interactions you wrote down.
- When NOT to use it: a small system with two or three services owned by one team. A shared integration test suite is simpler and enough. Do not add Pact for third-party APIs you cannot make run provider verification on; use WireMock and a scheduled check against the real API instead.

7 Interview lens

- Q: Why are end-to-end tests a poor main strategy for microservices? A: They are slow, flaky and hard to diagnose, because any of many services or environments can fail. Keep a few for critical journeys and push the rest down the pyramid.
- Q: What problem does consumer-driven contract testing solve? A: It detects a provider change that breaks a consumer before deployment, without running both together. The provider verifies the consumer's recorded expectations in its own pipeline.
- Q: How do you test a service that depends on a flaky external API? A: Stub it with WireMock for normal tests, including error and delay cases. Add a separate scheduled contract or smoke check against the real API.
- Q: How do you test asynchronous messaging? A: Check the producer emits the correct message, check the consumer handles it and handles duplicates, and pin the event schema with a contract. Use a real broker or emulator in a few integration tests only.

8 Common mistakes

- Inverted pyramid: many end-to-end tests. Shows up as a 60-minute pipeline that fails randomly. Fix: move checks down into component and contract tests.
- Shared test database or environment. Shows up as tests failing when two runs overlap. Fix: per-run containers and self-created data.
- Over-mocking. Shows up as green tests but broken production because the mock was wrong. Fix: add contract tests and a few real integration tests.
- Contracts that are never verified by the provider pipeline. Shows up as a stale contract giving false confidence. Fix: make verification and can-i-deploy a required pipeline gate.
- No production checks. Shows up as outages found by customers. Fix: synthetic checks, canary and alerts.

9 Mental model

- Think of a bridge between two river banks (services). Strength tests on each bank (unit, component) are cheap. A contract is the drawing both builders agreed on for where the bridge meets each bank. Walking the whole bridge in traffic (end-to-end) is rare and expensive. Cameras on the bridge in service (canary, synthetic checks) catch the rest.

Text picture:

- many unit tests
-   component tests per service
-     contract tests per pair
-       few end-to-end tests
-         production checks over everything

10 Mini lab (about 40 minutes, local tools)

Goal: see a consumer break when a provider changes, using a WireMock stub and a simple contract check.

Steps:

- Install the .NET SDK and Docker (verify current versions). Create a folder and run: dotnet new webapi -n Pricing, then dotnet new xunit -n Pricing.Tests.
- In Pricing, expose GET /price/{id} returning { "id": 1, "amount": 100 }.
- In Pricing.Tests, add package Microsoft.AspNetCore.Mvc.Testing and write a WebApplicationFactory test that calls /price/1 and asserts the status is 200 and the JSON has fields id and amount. This is your component test.
- Add package WireMock.Net. Write a second test for a small client class that calls a fake pricing server stubbed to return 503 with a delay. Assert the client times out or returns a fallback.
- Optional contract step: add package PactNet (verify current version and API). Write a consumer test that records the expectation for /price/1, then verify it against the Pricing provider.
- Break it: rename amount to cost in Pricing and rerun.

Expected result: the component test and the contract verification fail with a clear message naming the missing amount field. The 503 test passes only if your client handles the failure.

Clean-up: delete the folder and remove Docker containers with docker system prune only if you created them for this lab.

11 Revision summary

- Pyramid for microservices: unit, component, contract, integration, then few end-to-end tests.
- Component test = one real service, fake neighbours (WebApplicationFactory, Testcontainers).
- Contract test checks shape agreement between consumer and provider without running both.
- Consumer-driven contract (Pact): consumer records expectations, provider verifies them, broker answers can-i-deploy.
- WireMock fakes external HTTP services, including errors and delays.
- Test in production with canary releases and synthetic checks. Chaos testing is awareness only for now.
- Avoid shared test environments and shared data. Each test creates its own.
- Few end-to-end tests, only for critical journeys.
