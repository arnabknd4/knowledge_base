7.09 Delivery metrics and engineering practice [P3 R L]. Full note, no K tag, so it is treated as new.

1 What is it

- Delivery metrics are numbers that show how fast and how safely a team ships software to production. Engineering practice is the set of team habits (review rules, definition of done, shared code, docs in the repo) that keep those numbers healthy.
- The best-known set is the four DORA metrics. DORA is the DevOps Research and Assessment programme, now part of Google Cloud. Its research links these four numbers to team and business performance.
- Legacy equivalent: the release-count and bug-count reports in a .NET Framework project, plus the "release readiness" checklist before a monthly deployment.

2 Why needed

- Without numbers, "we are slow" or "we are stable" is opinion. Leads cannot show a client or manager whether a change helped.
- Without shared practices, quality depends on who reviews the pull request that day.
- Metrics used badly become targets that people game. This note covers how to avoid that.

4 Features and core concepts

- DORA metrics: four numbers. Deployment frequency (how often you deploy to production). Lead time for changes (commit to running in production). Change failure rate (share of deployments that cause a failure needing a fix, rollback or hotfix). Time to restore service (how long to recover after a failure). Why it matters: the first two measure speed, the last two measure stability. Good teams improve both together.
- Lead time: the clock from first commit (or merge) to production. Plain meaning: how long a finished idea waits. Why it matters: long lead time means big batches, slow feedback and risky releases. Define your start and end points once and keep them fixed.
- Change failure rate: failed deployments divided by total deployments. Why it matters: it shows whether speed is bought with quality. It needs a clear rule for what counts as a failure.
- MTTR: mean time to restore (some sources say recovery or repair; DORA now calls it failed deployment recovery time, verify). Plain meaning: how fast you get users working again, not how fast you find the root cause. Why it matters: it rewards good rollback, alerts and runbooks.
- Flow metrics: cycle time (work started to done), work in progress (items open at once), throughput (items finished per week), work item age. Plain meaning: they track work moving through the board. Why it matters: they find waiting and overload before releases suffer. Small limits on work in progress usually shorten cycle time.
- Pull request size and review standards: keep pull requests small (a common guideline is a few hundred changed lines, team-defined). Agree a review time target (example: first response within one working day). Why it matters: big pull requests get shallow reviews and slow merges. Use CODEOWNERS and required checks to enforce it.
- Definition of done: a written checklist that every item must meet. Example: code reviewed, tests passing, pipeline green, security scan clear, docs updated, deployed to test, monitoring added. Why it matters: it ends "done but not really" arguments with clients.
- Inner source: running internal shared code like open source. Teams can read, fork and send pull requests to each other's repositories, with a README, contribution guide and named maintainers. Why it matters: it replaces the shared-DLL-owned-by-nobody problem and cuts duplicate work across offshore teams.
- Documentation as code: docs live in the repository as Markdown, reviewed in pull requests and published by the pipeline. ADRs and diagrams as code fit here (15.01). Why it matters: docs change with the code and stay current.
- Worth memorizing: the four DORA metrics as two speed plus two stability. Azure DevOps and GitHub can supply the raw data (pipeline runs, pull request dates, work item dates). A dashboard or Analytics view turns it into charts.

5 Core focus (exam and interview)

- Asked most: name the four DORA metrics, say which are speed and which are stability, and say how you would improve each.
- AZ-400 asks about metrics, dashboards and feedback loops in the "processes and communications" area (verify the current skills outline on Microsoft Learn).
- DORA publishes performance bands (elite, high, medium, low) with thresholds. The names and numbers change between yearly reports (verify before quoting).
- Remember: metrics measure the system, not people. Never rank developers by them.
- Remember: Goodhart's law. When a measure becomes a target, it stops being a good measure.

6 Real-world use case

- Situation: a client in Kolkata complains that releases take six weeks and often break. You lead a team of eight on an Azure DevOps project.
- Choice made: measure first. Pull deployment dates from pipeline runs, pull request open-to-merge time from Azure Repos, and failures from incident tickets. Baseline: lead time 25 days, release monthly, change failure rate high. Then act on the biggest wait: cap pull requests, add a required-checks policy, add a definition of done, and move to smaller weekly releases behind feature flags.
- Result to aim for: shorter lead time and lower change failure rate over two or three months, shown as a simple trend chart in the sprint review.
- Trade-off: collecting data costs setup time, and noisy or inconsistent definitions make the numbers misleading.
- When NOT to use it: a very small team or a one-off project (too little data to trend). Also never use the numbers for individual appraisals or to compare unlike teams (a regulated banking system versus an internal tool).

7 Interview lens

- Q: What are the DORA metrics? A: Deployment frequency, lead time for changes, change failure rate and time to restore. The first two show speed and the last two show stability.
- Q: How do you improve lead time without raising failures? A: Shrink batch size with small pull requests, automate tests and deployment, and use feature flags. Smaller changes are easier to review and to roll back.
- Q: How do you stop teams gaming metrics? A: Use them as team-level trends, never as individual targets. Track speed and stability together, and review them in a retrospective.
- Q: What makes a good definition of done? A: It is short, testable and agreed by the whole team. It covers quality, security, deployment and documentation, and it is reviewed regularly.

8 Common mistakes

- Measuring only deployment frequency. Shows up as many risky releases. Fix: always pair it with change failure rate.
- Counting lines of code, commits or velocity as productivity. Shows up as padded changes. Fix: use flow and DORA measures.
- No agreed failure definition. Shows up as arguments over the numbers. Fix: write one rule (rollback, hotfix or incident counts).
- Using metrics to compare or rank people. Shows up as hidden problems and gaming. Fix: report at team level only.
- Definition of done that nobody enforces. Shows up as the same rework every sprint. Fix: add it to the pull request template and pipeline checks.
- Inner source with no owner. Shows up as stale shared repositories. Fix: name maintainers and a response time.

9 Mental model

A pipe carrying water from commit to production.

Commit -> review -> build and test -> deploy -> production -> (failure?) -> restore

- Lead time is how long water takes to flow through.
- Deployment frequency is how often a bucket is poured.
- Change failure rate is how many buckets leak.
- Time to restore is how fast you patch the leak.
- Practices (small pull requests, definition of done, docs in the repo) keep the pipe clear and narrow.

10 Mini lab

Time: about 30 minutes. Tools: a free Azure DevOps organisation or a GitHub repository, plus a spreadsheet.

- Step 1: pick a repository with at least 10 merged pull requests (use a personal or practice repo if work data is not allowed).
- Step 2: write down for each pull request the date opened, the date merged and the lines changed. Both Azure Repos and GitHub show these on the pull request list.
- Step 3: calculate the average open-to-merge time and the average size. Mark pull requests larger than 400 lines.
- Step 4: add a pull request template file to the repository with a definition of done checklist (five to seven items) and a CODEOWNERS file. In Azure DevOps, add a branch policy that needs one reviewer and a passing build.
- Step 5: open a new pull request and confirm the template appears and the policy blocks merge until checks pass.
- Expected result: a baseline table of review time and size, a visible checklist on new pull requests and a policy that enforces review.
- Clean-up: delete the test branch and pull request. Remove the branch policy only if the repository is shared.

11 Revision summary

- DORA has four metrics: deployment frequency, lead time for changes, change failure rate, time to restore.
- Two are speed, two are stability. Improve them together.
- Lead time runs from commit to production. Fix the start and end points once.
- Flow metrics: cycle time, work in progress, throughput, work item age.
- Keep pull requests small and set a review response target.
- A definition of done is a short, agreed, enforced checklist.
- Inner source means shared code with an owner, README and open pull requests.
- Documentation as code means Markdown in the repo, reviewed and published by the pipeline.
- Metrics measure the system, never individuals (Goodhart's law).
