7.06 Deployment strategies. P2, R, L. No K tag, so this is a full note for a topic that is new to you.

1 What is it
- A deployment strategy is the plan for how a new version of an app replaces the old one in production.
- The main strategies are recreate, rolling, blue-green and canary. Feature flags and App Service slot swaps are tools that make them safer.
- Legacy equivalent: copying a build to the IIS server on a Friday night, with the site down, and restoring the old folder if it breaks.

2 Why needed
- Users should not see downtime or broken releases.
- Without a strategy, every release is a risky big bang. A bad release hits 100 percent of users, and rollback is slow and manual.
- Faster, smaller and safer releases let teams ship more often.

3 Before you read
- Know what an environment is (dev, test, staging, production).
- Know what a load balancer does: it splits traffic across instances.
- Know what a health check is: a URL that tells whether an instance is working.
- Know what a pipeline stage is in Azure DevOps or GitLab CI.

4 Features and core concepts
- Recreate: stop the old version, then start the new one.
  - Simplest option, but it causes downtime. Fine for dev and test, or for apps that tolerate an outage window.
- Rolling: replace instances a few at a time. Old and new versions run side by side during the rollout.
  - No downtime and no extra capacity. The catch is that two versions run together, so APIs and database changes must be compatible with both.
- Blue-green: keep two identical environments. Blue is live and green holds the new version. Switch traffic to green after testing.
  - Rollback is instant: switch back. The cost is double capacity during the release.
- Canary: send a small share of traffic (for example 5 percent) to the new version, watch the metrics, then increase.
  - Limits the damage of a bad release to a few users. It needs good monitoring to be useful.
- Feature-flag releases: deploy code switched off, then turn the feature on for chosen users.
  - Separates deploying from releasing. A flag turned off is the fastest rollback.
- App Service slot swaps: a staging slot runs the new build, warms up, then swaps with production.
  - Gives blue-green on App Service with no new infrastructure. The swap is a routing change, and swap back is the rollback.
  - Slot settings marked "sticky" stay with the slot and do not move in a swap. Use them for environment-specific config.
- Traffic shifting: move traffic in steps between versions.
  - Done by slot traffic percentage, Front Door, Application Gateway, Container Apps revisions or Kubernetes ingress (verify the exact feature per service).
- Smoke tests: a few quick automated checks right after deploy (home page loads, health endpoint returns 200, one key API call).
  - They catch obviously broken releases before users do.
- Automated rollback: the pipeline reverts on its own when health checks or metrics fail.
  - Removes the delay of waiting for a human at 2 AM.
- Database changes in pipelines: schema changes must work with both the old and new code.
  - Use expand and contract: add first, deploy code, remove later (see 4.08). Never ship a breaking schema change in the same step as code.
- Per-environment config: the same build artifact goes everywhere, and only config changes.
  - Build once, deploy many. Config comes from variables, App Configuration or Key Vault.
- Approvals: a person must approve before a stage runs, usually before production.
  - In Azure DevOps this is done with environments, approvals and checks.
- Zero-downtime deployment: the result of combining the above, with health checks, graceful shutdown and backward-compatible changes.
  - Needs readiness probes so traffic reaches only instances that are ready.
- Command worth memorizing:
  - az webapp deployment slot swap -g rg -n app --slot staging --target-slot production

5 Core focus (exam and interview)
- Know the trade-off table in words: downtime, cost, rollback speed and risk for each strategy.
  - Recreate: downtime, cheap, slow rollback.
  - Rolling: no downtime, cheap, slower rollback.
  - Blue-green: no downtime, double cost, instant rollback.
  - Canary: no downtime, needs monitoring, small blast radius.
- Slot swap warms up the staging slot first, then swaps routing. Slots need Standard tier or higher (verify).
- Slot-specific settings do not swap.
- Rolling and canary need backward-compatible APIs and schemas.
- AZ-400 asks which strategy fits a given scenario and how to configure environments, approvals and checks.

6 Real-world use case
- Situation: a customer portal built on ASP.NET Core runs on Azure App Service with Azure SQL. Releases used to need a 30-minute downtime window.
- Choice: a staging slot for each deploy, smoke tests against the slot, then a swap. A feature flag guards risky new features. Schema changes use expand and contract.
- Result: no downtime, and rollback is a second swap.
- Trade-off: slots cost more because of the higher plan tier, and both versions hit the same database, so the schema discipline is mandatory.
- When NOT to use blue-green or slots: when the app holds long in-memory state, or when a release includes a breaking database change that cannot be made compatible. Use a planned maintenance window instead.

7 Interview lens
- Q: Blue-green vs canary?
  - A: Blue-green switches all traffic at once and rolls back instantly, but costs double capacity. Canary exposes a few users first and needs metrics to judge the release.
- Q: How do you do zero-downtime deploys with a database change?
  - A: Use expand and contract. Add the new column, deploy code that works with both shapes, then remove the old one in a later release.
- Q: What does a slot swap actually do?
  - A: It warms up the staging slot, then swaps the routing between slots. Sticky slot settings stay behind.
- Q: How does rollback work in your pipeline?
  - A: Swap back or shift traffic back, or turn off the feature flag. Automated checks trigger it when health or error metrics fail.

8 Common mistakes
- Breaking schema change shipped with the code. Production errors appear mid-rollout. Fix: expand and contract.
- Config baked into the build. A separate build per environment gives untested artifacts. Fix: build once, inject config.
- No warm-up before the swap. Users hit a cold app and see slow first requests. Fix: warm-up and health check before swapping.
- Canary without monitoring. A bad version goes unnoticed. Fix: define success metrics and alerts before the rollout.
- Forgetting sticky settings. Production connects to the staging database after a swap. Fix: mark connection strings as slot settings.
- Manual rollback only. Recovery takes too long. Fix: script and rehearse rollback.

9 Mental model
- Old IIS way: close shop, change stock, reopen.
- Modern way: build a second shop next door (green), test it, then move the customers across. Move a few first if unsure (canary).

  users -> [router] -> blue (v1)
                   -> green (v2)   switch or shift gradually

10 Mini lab (30 to 40 minutes, Azure free tier)
- Steps:
  - Create a resource group and an App Service plan at Standard S1 or higher, since slots are not on free tiers (verify). Delete it right after the lab to limit cost.
  - Create a web app and deploy a simple app that shows "v1".
  - Add a slot named staging and deploy "v2" to it.
  - Open the staging URL and confirm it shows v2 while production shows v1.
  - Run the swap command from section 4.
  - Refresh production and confirm v2. Swap again to confirm rollback to v1.
- Expected result: production changes version with no downtime, and swapping back restores v1.
- Clean-up: delete the resource group (az group delete -n rg).

11 Revision summary
- Four strategies: recreate (downtime), rolling, blue-green, canary.
- Blue-green gives instant rollback at double capacity.
- Canary limits blast radius but needs monitoring.
- Slot swap is routing-based blue-green on App Service, and sticky settings do not move.
- Build once, deploy many, with config per environment.
- Rolling and canary need backward-compatible code and schema (expand and contract).
- Smoke tests and automated rollback protect the release.
- Feature flags separate deploy from release.
