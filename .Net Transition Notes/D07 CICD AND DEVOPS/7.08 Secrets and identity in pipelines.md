1 What is it

- A pipeline is an automated job that builds and deploys your code. It needs credentials to talk to Azure, Key Vault, registries and databases.
- This topic is how the pipeline gets those credentials safely: no passwords stored, no long-lived secrets, and only the access it needs.
- Key Vault references: a setting that points to a secret in Key Vault instead of holding the value.
- Managed identity: an identity Azure gives to a resource, with no password for you to manage.
- Workload identity federation (OIDC): the pipeline proves who it is with a short-lived token, so Azure trusts it without a stored secret.
- Legacy equivalent: a service account password saved in a Jenkins, TFS or GitLab variable, or in Web.config transforms checked into source control.

2 Why needed

- Pipelines are a top target for attackers. They hold keys to production.
- A leaked client secret works from anywhere until it expires or someone rotates it.
- Without this: secrets in repos, expired secrets breaking releases at night, and one over-powered account that can delete production.

3 Before you read

- Service principal: an identity for an app in Entra ID (verify current naming).
- Azure RBAC: roles assigned to an identity at a scope (subscription, resource group, resource).
- Service connection: the Azure DevOps object that holds the link to Azure.
- Token: a signed proof of identity that expires.

4 Features and core concepts

- Key Vault references: the app or pipeline reads the secret at run time from Key Vault. Why it matters: the value lives in one place, so rotation does not need code changes.
- Managed identity: Azure resources (App Service, AKS, VM) get an identity automatically. Why it matters: nothing to store or rotate. Limit: it covers resources running in Azure, not hosted pipeline agents. A self-hosted agent on an Azure VM can use one.
- Workload identity federation (OIDC): Azure trusts tokens issued by Azure DevOps or GitHub for a specific pipeline. Why it matters: no secret exists to leak.
- Least-privilege service principals: grant only the role needed, at the smallest scope. Why it matters: a stolen identity can do little.
- Secret rotation: replacing secrets on a schedule. Why it matters: limits damage from an unnoticed leak. Prefer removing secrets entirely over rotating them.
- No secrets in repositories: use secret scanning and pre-commit checks. Why it matters: git history keeps secrets forever, so a leaked one must be revoked, not just deleted.
- Variable masking: the pipeline hides secret values in logs. Why it matters: but masking is not security. A script can still print a transformed value.
- Protected branches and environments: only approved branches can deploy to production, with approvals and checks. Why it matters: stops a random branch from using production access.
- Pipeline permission hardening: restrict who can edit pipelines, use service connections, and use variable groups. Limit pull request pipelines from forks. Why it matters: editing the YAML is a way to steal access.
- Worth memorizing, an Azure DevOps task using a federated service connection: `AzureCLI@2` with `azureSubscription: '<connection-name>'`. No secret appears in the YAML.

5 Core focus (exam and interview)

- Most asked: OIDC federation vs client secret vs certificate, and why federation is preferred.
- Federated credentials are matched on issuer, subject and audience (verify exact subject format per platform).
- Managed identity types: system-assigned (tied to one resource, deleted with it) and user-assigned (separate resource, shareable).
- Key Vault access: Azure RBAC is the recommended model over access policies (verify current default).
- Service principal secrets have an expiry, and maximum lifetimes are set by Entra settings (verify).
- Rotation answer: reduce the number of secrets first, then automate rotation of the rest.

6 Real-world use case

- Situation: an Azure DevOps pipeline deploys a .NET API to App Service and runs EF migrations. Today it uses a client secret stored in a variable group. It expired at 2 am during a release.
- Choice: switch the service connection to workload identity federation. Give the identity Contributor only on the app resource group. Move the database password to Key Vault and have the app read it using its managed identity. Restrict the production environment to the main branch with a manual approval.
- Trade-off: setup takes more steps and needs Entra permissions. Debugging a failed federated login is harder than rotating a secret.
- When NOT to use it: a tool that cannot do OIDC, such as an old third-party system, needs a secret. Store that one in Key Vault, rotate it and scope it narrowly. A throwaway sandbox pipeline does not need full approval gates.

7 Interview lens

- Q: Why is OIDC federation better than a client secret? A: There is no secret to steal or expire. The token is short-lived and tied to a specific pipeline.
- Q: A secret was committed to the repo. What do you do? A: Revoke and rotate it immediately. Then remove it from code and add secret scanning. Deleting the commit is not enough.
- Q: Does variable masking protect secrets? A: No, it only hides exact values in logs. Real protection is access control and not exposing secrets to untrusted code.
- Q: How do you stop a pull request from using production credentials? A: Use environments with branch restrictions and approvals. Do not run fork pull requests with secrets.

8 Common mistakes

- Subscription-wide Owner for the pipeline. Shows up as a pipeline bug able to delete production. Fix: the narrowest role and scope.
- Secrets kept in variable groups unlocked. Anyone with edit rights can read them. Fix: Key Vault-backed groups or federation.
- One service connection for all environments. A dev pipeline can reach prod. Fix: one identity per environment.
- Expiring secrets with no owner. Shows up as a failed release at night. Fix: remove the secret or add expiry alerts.
- Allowing any pipeline to use a service connection. Fix: require approval to authorize each pipeline.

9 Mental model

- A hotel keycard, not a master key.
- Old way: a copied key kept in a drawer (stored secret).
- New way: the front desk checks your booking and gives a card that opens only your room and expires tonight (OIDC token plus least privilege).

```
Pipeline run -> signed token -> Entra checks issuer + subject
            -> short-lived Azure token -> only the allowed role/scope
```

10 Mini lab (30 to 40 minutes, Azure free tier)

- Needs: an Azure subscription, an Azure DevOps organization and project (free tier), and a small repo.
- Step 1: create a resource group `rg-lab-708` and a storage account in it.
- Step 2: in Azure DevOps, Project settings, Service connections, New, Azure Resource Manager, choose the workload identity federation option (automatic), scope it to `rg-lab-708` only.
- Step 3: create a YAML pipeline with one `AzureCLI@2` step using that connection, running `az storage account list -g rg-lab-708 -o table`.
- Step 4: run it. Expected result: the storage account is listed and no secret was ever entered.
- Step 5: change the command to `az group list -o table`. Expected result: only `rg-lab-708` shows, or access is denied for other scopes. This proves least privilege.
- Step 6: in the service connection, set security so only approved pipelines can use it.
- Clean-up: delete `rg-lab-708` (`az group delete -n rg-lab-708`), then delete the service connection and the pipeline.

11 Revision summary

- Best secret is no secret: prefer OIDC federation and managed identity.
- Federation trusts a token by issuer, subject and audience.
- Managed identity: system-assigned dies with the resource, user-assigned is reusable.
- Least privilege means smallest role at smallest scope, one identity per environment.
- A committed secret must be revoked, not just deleted.
- Masking hides values in logs only and is not a security control.
- Protect production with environment approvals, branch restrictions and locked-down pipeline edit rights.
- Key Vault holds the secrets you cannot remove, with rotation and RBAC access (verify default model).
