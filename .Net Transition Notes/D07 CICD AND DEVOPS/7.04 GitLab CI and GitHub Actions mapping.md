7.04 GitLab CI and GitHub Actions mapping
[P1 R L, no K tag: new-topic depth, FULL note with mini lab]

1 What is it

- GitLab CI is the pipeline system built into GitLab. You describe your build and deploy steps in a file named .gitlab-ci.yml.
- Azure Pipelines (inside Azure DevOps) and GitHub Actions do the same job in different words. Each reads a YAML file in your repo and runs steps on a machine when code changes.
- This topic is a translation table in your head: every GitLab term you already use has a twin in the other two tools.
- Legacy equivalent: your existing GitLab CI pipeline for the .NET Framework app, now rebuilt in another tool.

2 Why needed

- Many Kolkata and remote India job postings say Azure DevOps or GitHub Actions, not GitLab. Your 12 years of GitLab CI are valuable only if you can say "I know the same thing there."
- Without a mapping, you restart from zero in every tool and sound junior in interviews.
- Migration projects are common: a client moves from GitLab to Azure DevOps or GitHub. The lead is expected to plan it.

3 Before you read

- YAML basics: indentation, lists, key-value pairs.
- What a CI pipeline is: build, test, publish on every commit.
- Git branches and pull requests (merge requests in GitLab).
- Secret versus plain variable.

4 Features and core concepts

GitLab concepts first. Each line: GitLab term, then the twin in Azure Pipelines and GitHub Actions.

- Stages: ordered groups of jobs (build, test, deploy). Azure Pipelines has stages too. GitHub Actions has no stage keyword; you order jobs with needs. Why it matters: ordering and gates work differently per tool.
- Jobs: a unit of work with a script. Azure Pipelines: job inside a stage. GitHub Actions: job inside a workflow.
- Script lines: the commands a job runs. Azure Pipelines: steps (script, task). GitHub Actions: steps (run, uses).
- Rules (and only/except): decide when a job runs. Azure Pipelines: condition and trigger filters. GitHub Actions: on (events, branches, paths) and if conditions.
- Runners: the machines that run jobs. Azure Pipelines: agents in pools (Microsoft-hosted or self-hosted). GitHub Actions: runners (GitHub-hosted or self-hosted). Why it matters: self-hosted is needed for private network access and legacy .NET Framework builds on Windows.
- Artifacts: files kept from a job for later jobs or download. Azure Pipelines: pipeline artifacts (publish and download steps). GitHub Actions: upload-artifact and download-artifact actions.
- Cache: reuse downloaded packages to speed builds. Azure Pipelines: Cache task. GitHub Actions: cache action or built-in cache in setup actions. Why it matters: NuGet restore dominates .NET build time.
- Environments: named deploy targets with protection. Azure Pipelines: environments with approvals and checks. GitHub Actions: environments with required reviewers and secrets.
- Variables: GitLab CI/CD variables (masked, protected). Azure Pipelines: variables and variable groups (link to Key Vault). GitHub Actions: variables and secrets at repo, environment or organization level.
- Includes and templates: GitLab include and extends. Azure Pipelines: templates (extends, steps, jobs). GitHub Actions: reusable workflows (workflow_call) and composite actions.
- Parallel variations: GitLab parallel:matrix. Azure Pipelines: strategy matrix. GitHub Actions: strategy matrix.
- Actions (GitHub term): ready-made steps from a marketplace, used with uses. Azure Pipelines twin: tasks and extensions. GitLab twin: includes and CI/CD components.
- Secrets to Azure with OIDC: the keyless login. Azure Pipelines: service connection with workload identity federation. GitHub Actions: azure/login with OIDC and a federated credential on an Entra app. Why it matters: no stored client secret to leak or rotate.
- Migration approach: inventory pipelines, map each concept, move one low-risk pipeline first, run old and new in parallel, compare results, cut over, then retire. Azure DevOps offers an official GitLab-to-Azure Pipelines path and GitHub offers GitHub Actions Importer (verify current tooling).
- GH-200 blueprint: the GitHub Actions certification exam. Check status and skills outline on Microsoft Learn (verify status).

Memorize this skeleton for GitHub Actions:

- on: push: branches: [main]
- jobs: build: runs-on: ubuntu-latest
- steps: - uses: actions/checkout@v4 (verify version)
- steps: - run: dotnet build --configuration Release

5 Core focus (exam and interview)

- Most asked: "Map X in GitLab to Azure Pipelines." Know runners/agents, stages/jobs, rules/conditions, artifacts, templates, environments.
- Hierarchy in Azure Pipelines: pipeline, stages, jobs, steps. In GitHub Actions: workflow, jobs, steps (no stages).
- Agent and runner terms are not interchangeable: agent pool (Azure DevOps), runner group (GitHub).
- Secrets: never in YAML. Use variable groups linked to Key Vault, or OIDC federation.
- Hosted agents are clean per run. Self-hosted keep state, so clean up after each job.
- Hosted-agent limits and free minutes change often (verify).

6 Real-world use case

- Situation: a client has a .NET Framework 4.8 app built by GitLab CI on a Windows shell runner. They are moving to Azure and want Azure DevOps because Boards and Boards-to-pipeline traceability are already in use.
- Choice: rebuild the pipeline as multi-stage YAML in Azure Pipelines. Stages: build, test, publish, deploy-dev, deploy-prod. Dev and prod are environments, prod with an approval check. Secrets from a variable group linked to Key Vault. Deploy through a service connection using workload identity federation.
- Trade-off: you gain native integration with Azure and approvals, but you lose GitLab's single-product feel (repo, registry, CI in one place), and some job logic (rules) needs rewriting as conditions.
- When NOT to do this: if the whole team lives in GitLab with a working pipeline, and the target is not Azure-centric, migration cost may exceed benefit. Mapping knowledge still helps, but do not migrate for fashion.

7 Interview lens

- Q: How does a GitLab runner differ from an Azure DevOps agent?
- A: Both execute jobs. Agents belong to pools and are hosted by Microsoft or self-hosted. Same self-hosted trade-off: more control, you own patching and cleanup.
- Q: How would you reuse pipeline logic across 20 repos?
- A: GitLab include, Azure Pipelines templates from a shared repo, GitHub reusable workflows. Version the shared repo and pin refs.
- Q: How do you deploy from a pipeline to Azure without a stored secret?
- A: OIDC workload identity federation. The pipeline gets a short-lived token via a federated credential on an Entra app.
- Q: How do you migrate 50 GitLab pipelines?
- A: Inventory and group by pattern, build shared templates first, migrate low-risk first, run in parallel, compare outputs, then cut over and archive.

8 Common mistakes

- Copying GitLab YAML line by line. Shows up as awkward pipelines and missed native features. Fix: translate concepts, not syntax.
- Expecting stages in GitHub Actions. Shows up as jobs running in parallel when you wanted order. Fix: use needs.
- Secrets in YAML or plain variables. Shows up as leaks in logs. Fix: secret variables, Key Vault, OIDC.
- Unpinned action or template versions. Shows up as sudden breakage or supply chain risk. Fix: pin to a version or commit SHA.
- Self-hosted runners with leftover files. Shows up as builds that pass only on one machine. Fix: clean workspace each run.

9 Mental model

Same machine, three dashboards:

  trigger (rules / trigger / on)
    -> runner or agent picks up the job
      -> steps run (script / task / run, uses)
        -> artifact saved, environment gate, deploy

GitLab, Azure Pipelines and GitHub Actions use different labels on the same flow.

10 Mini lab (about 35 minutes)

Goal: build the same .NET pipeline in GitLab terms and GitHub Actions, side by side.

- Step 1: on your machine run dotnet new console -n maplab and git init inside it. Commit.
- Step 2: create a GitHub repo (free) and push.
- Step 3: add .github/workflows/ci.yml with on: push, a job build on ubuntu-latest, steps: checkout, setup-dotnet, dotnet restore, dotnet build, dotnet test (verify action names on the marketplace).
- Step 4: add an upload-artifact step for the build output folder.
- Step 5: write the equivalent .gitlab-ci.yml on paper only (stages, job, script, artifacts). Mark each line with its GitHub twin.
- Step 6: push, open the Actions tab, confirm the run is green and the artifact downloads.
- Expected result: a green workflow run with one downloadable artifact, and a one-page mapping sheet in your handwriting.
- Clean-up: delete the test repo, or at least disable the workflow, so no scheduled or stray runs continue.

11 Revision summary

- GitLab runner = Azure DevOps agent = GitHub runner.
- GitLab stages map to Azure stages; GitHub Actions orders jobs with needs.
- GitLab rules map to conditions (Azure) and on plus if (GitHub).
- Include and extends map to templates (Azure) and reusable workflows (GitHub).
- Pipeline artifacts, cache and environments exist in all three with different keywords.
- Use OIDC workload identity federation instead of stored Azure secrets.
- Migrate by inventory, shared templates, pilot, parallel run, cutover.
- GH-200 blueprint and tool versions: verify on Microsoft Learn.
