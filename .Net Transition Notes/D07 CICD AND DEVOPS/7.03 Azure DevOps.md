1 What is it
- Azure DevOps is Microsoft's hosted suite for planning work, storing code, building, testing and releasing software. Its parts: Boards (work tracking), Repos (Git), Pipelines (CI/CD), Test Plans, Artifacts (package feeds).
- A YAML pipeline is a file in your repo (azure-pipelines.yml) that describes how to build and deploy. The pipeline runs on an agent, which is a machine that executes your steps.
- Legacy equivalent: TFS (Team Foundation Server) and its XAML build definitions, or your GitLab CI setup. YAML pipelines are the Azure DevOps counterpart of .gitlab-ci.yml.

2 Why needed
- Without automated pipelines, builds and releases are manual, inconsistent and hard to audit.
- Without approvals and checks, anyone can push to production.
- Without a shared feed, teams copy DLLs and packages by hand.
- Without work items linked to code, nobody can trace why a change was made.
- Most Azure-focused employers in India run Azure DevOps, and AZ-400 is built on it.

4 Features and core concepts
- Organization and project structure: an organization is the top container, holding projects. A project holds repos, pipelines, boards and feeds. It matters because permissions, billing and policies are set at these levels. Few large projects are usually better than many small ones.
- Triggers: rules that start a pipeline (push, pull request, schedule, another pipeline). They matter because the wrong trigger wastes build minutes or misses builds.
- Stages, jobs, steps: a stage is a major phase (Build, Deploy). A stage has jobs, and a job has steps. Each job runs on one agent. Stages run in sequence by default, jobs in parallel by default. This matters for speed and for placing approvals between stages.
- Templates: reusable YAML fragments for steps, jobs or stages, referenced with template:. They matter because 20 services should not carry 20 copies of the same pipeline.
- Parameters: values fixed at queue time (compile time), with types and defaults. Variables: values read at runtime. Use parameters for choices like environment name, variables for settings. Syntax differs: ${{ parameters.x }} compile time, $(var) runtime.
- Variable groups: named sets of variables shared across pipelines, can link to Key Vault. They matter for central config and secrets.
- Conditions: expressions that control whether a step, job or stage runs (succeeded(), failed(), eq(variables['Build.SourceBranch'], 'refs/heads/main')). They matter for deploying only from main.
- Agents and pools: an agent is the machine running a job. Microsoft-hosted agents are fresh VMs per job, with no maintenance. Self-hosted agents are your own machines, needed for private networks or special software. A pool is a group of agents. Trade-off: hosted is easy, self-hosted gives control and private access.
- Service connections: stored credentials that let a pipeline reach Azure, a registry or GitHub. Prefer workload identity federation (OIDC) over secrets. They matter because they are a main security surface.
- Environments, approvals and checks: an environment is a named deployment target (dev, test, prod). Approvals and checks (manual approval, branch control, business hours, required template) gate deployment to it. They matter for controlled releases.
- Azure Artifacts feeds: private package feeds for NuGet, npm, Maven, Python. They matter for sharing internal libraries and for upstream caching of public packages.
- Pipeline artifacts: files produced by a build and passed to later stages (publish and download steps). They matter because you build once and deploy the same package everywhere.
- Test reporting: tasks publish test results and coverage into the pipeline UI (PublishTestResults, PublishCodeCoverageResults). They matter for visibility and quality gates.
- Boards: work items (epic, feature, user story, task, bug), backlogs, sprints, boards. They matter for traceability, since commits and PRs link to work items.
- Permissions: security groups, roles and per-resource rights (repos, pipelines, feeds, environments). They matter because defaults are often too open.
- Worth memorizing, a minimal pipeline:
trigger: [main]
pool: { vmImage: ubuntu-latest }
steps:
- script: dotnet test
- task: PublishBuildArtifacts@1

5 Core focus (exam and interview)
- Asked most: stages vs jobs vs steps, agent types, service connection types, templates, environment approvals, variable group with Key Vault, build once and deploy many.
- Pipelines defined in YAML are called multi-stage pipelines. Classic pipelines use the visual editor (Build and Release). Classic is legacy. (verify current status)
- Microsoft-hosted agents have job time limits and are discarded after each job. Limits depend on plan and public vs private project. (verify)
- Parallel jobs control how many jobs run at once, and free tier grants are limited. (verify)
- Approvals and checks are set on the environment, not in the YAML.
- Pipeline permissions on service connections and environments must be granted to a pipeline before it can use them.
- Variable precedence: runtime and queue-time values can override YAML values only where allowed. Secret variables are not passed to scripts automatically, you must map them in env.

6 Real-world use case
- Situation: a .NET API for a client, code in Azure Repos, deployed to App Service in dev, test and prod.
- Choice: one multi-stage YAML pipeline. Stage Build runs restore, build, test, publish and uploads one artifact. Stages Dev, Test, Prod each deploy that same artifact to an environment. Prod environment has a manual approval and a branch check allowing main only. Shared steps live in a templates repo. Service connection uses OIDC. Connection strings come from a Key Vault linked variable group.
- Trade-off: templates and shared repos add indirection, so debugging takes longer. Hosted agents cannot reach a private database.
- When NOT to use it: if the whole company already runs on GitHub with Actions and Advanced Security, adding Azure DevOps splits tooling. Also avoid hosted agents when builds need private network access, use self-hosted agents there.

7 Interview lens
- Q: Difference between a stage, job and step?
  A: Stage is a phase, containing jobs. A job runs on one agent and contains steps. Steps are single tasks or scripts.
- Q: How do you stop a pipeline deploying to prod without approval?
  A: Add an approval check on the prod environment. Add a branch control check so only main can deploy.
- Q: How do you handle secrets in pipelines?
  A: Key Vault linked variable group or Key Vault task, secret variables, and OIDC service connections instead of stored client secrets. Never commit secrets.
- Q: How do you avoid copy-pasting pipelines across 30 services?
  A: Extend from shared templates in a central repo, with parameters for the differences. Optionally enforce a required template through checks.

8 Common mistakes
- Rebuilding per environment: artifacts differ between stages and bugs appear only in prod. Fix: build once, promote the artifact.
- Using client secrets in service connections: secrets expire and break deploys or leak. Fix: workload identity federation.
- Confusing ${{ }} with $( ): value is empty at runtime. Fix: remember compile time vs runtime.
- Secret variable used in a script without mapping: script sees an empty value. Fix: map it under env.
- Giving all pipelines access to all connections: one compromised pipeline reaches prod. Fix: restrict per-pipeline permissions and add checks.
- Self-hosted agents never patched: security and build drift. Fix: use scale set agents or rebuild images regularly.

9 Mental model
- Organization > Project > (Repo -> Pipeline -> Environment) with Boards on the side.
- Code push -> trigger -> Stage Build (job: steps) -> artifact -> Stage Dev -> Stage Test -> [approval] -> Stage Prod.
- Each job gets an agent from a pool. Each deploy stage targets an environment, and environments hold the gates.

10 Mini lab (30 to 40 minutes)
- Steps:
  - Create a free Azure DevOps organization at dev.azure.com and a project named lab-pipeline. (Free parallel job grants may need a request form. verify)
  - In Repos, push a small .NET project (dotnet new webapi, with one unit test project).
  - Create azure-pipelines.yml with two stages. Build: restore, build, test, publish, then upload pipeline artifact. Deploy: a job that downloads the artifact and echoes a message.
  - Under Pipelines, Environments, create environment dev-lab. Add an Approval check with yourself as approver. Reference it in the Deploy stage using a deployment job with environment: dev-lab.
  - Run the pipeline. Approve the deployment when it pauses.
- Expected result: Build stage passes with test results shown in the Tests tab. Deploy stage waits for approval, then runs and prints your message. The artifact is listed on the run summary.
- Clean-up: delete the project from Project settings, Overview, Delete. No Azure resources were created, so no cost.

11 Revision summary
- Organization contains projects. Project contains repos, pipelines, boards, feeds.
- Stage contains jobs, job contains steps, and a job runs on one agent.
- Hosted agents are fresh per job. Self-hosted agents are for private network access.
- Parameters are compile time. Variables are runtime.
- Approvals and checks live on the environment.
- Build once, deploy the same artifact to every stage.
- Prefer OIDC service connections over stored secrets.
- Templates remove duplication across pipelines.
