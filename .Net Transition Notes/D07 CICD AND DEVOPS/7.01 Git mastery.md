1 What is it
- Git is a distributed version control system. Every clone holds the full history, and every commit is a snapshot of the whole project.
- This note covers the gaps beyond daily use: how Git stores data, how history is rewritten safely, and how teams run Git at scale.
- Legacy equivalent: TFVC and SVN were central-server systems with one history on the server. Git replaces them with a full local history.

2 Why needed
- A lead decides how the team merges, reviews and recovers. Weak Git habits cause lost work and unreadable history.
- Without the reflog, bisect and rebase knowledge, a bad merge or a broken commit takes hours to fix.
- Without conventions and signed commits, you cannot trace who changed what or trust a release.

4 Features and core concepts
- Object model: Git stores four object types (blob, tree, commit, tag), each named by a hash of its content. A branch is only a movable pointer to a commit. This explains why branching is cheap and why history is a chain of snapshots.
- Merge vs rebase: merge joins two histories with a merge commit. Rebase replays your commits on a new base for a linear history. Merge keeps the true history. Rebase gives a cleaner one but rewrites commits.
- Cherry-pick: copies one commit onto the current branch as a new commit with a new hash. Useful for hotfixes. Overuse causes duplicate commits and confusing merges.
- Bisect: a binary search through history to find the commit that introduced a bug. It turns a hunt through hundreds of commits into about 8 steps. Command: git bisect start; git bisect bad; git bisect good <hash>.
- Reflog: a local log of where HEAD and branches pointed. It is your undo for bad resets and rebases. Command: git reflog, then git reset --hard HEAD@{n}.
- Stash: parks uncommitted changes. Command: git stash push -u -m "msg". The -u flag includes untracked files.
- Tags: fixed names for commits. Annotated tags (git tag -a) carry author and message, and are the right choice for releases. Lightweight tags are only a pointer.
- Hooks: scripts that run on Git events, such as pre-commit and commit-msg. They are local and not shared by default, so enforce the same checks in CI as well. Tools like Husky share them.
- Conflict resolution: happens when two changes touch the same lines. Resolve, stage, then continue the merge or rebase. Settings that help: rerere remembers resolutions, and merge.conflictStyle zdiff3 shows the base version.
- History rewriting rules: amend, rebase -i and reset change commit hashes. Rewrite only commits that are not yet shared. If you must push after rewriting, use git push --force-with-lease, never plain --force.
- Monorepo vs polyrepo: a monorepo keeps many projects in one repository, which gives atomic cross-project changes and one set of tooling. A polyrepo gives clear ownership and independent pipelines. Monorepos need path filters in CI and sparse checkout or partial clone at scale.
- Commit conventions: Conventional Commits (feat:, fix:, feat!:) allow automatic changelogs and version bumps. They also make history searchable.
- Signed commits: commits signed with GPG, SSH or Sigstore prove the author. Enforce them with branch protection (verify per platform).

5 Core focus (exam and interview)
- Most asked: merge vs rebase, reset vs revert, recovering lost commits, and monorepo vs polyrepo.
- reset moves the branch pointer. revert adds a new commit that undoes an old one. Use revert on shared branches.
- reset has three modes: --soft keeps the staging area and files, --mixed (default) keeps files only, --hard discards both.
- A detached HEAD means HEAD points at a commit and not at a branch. Commits made there are lost unless you create a branch.
- git pull equals fetch plus merge (or rebase with pull.rebase).
- Unreachable commits are removed by garbage collection after a grace period, often 30 days or more (verify).

6 Real-world use case
- Situation: a release branch has a regression and nobody knows which of 200 commits caused it.
- Choice: run git bisect with an automated test script (git bisect run). The faulty commit is found in about 8 runs. A cherry-pick then moves the fix to the release branch.
- Trade-off: bisect works best when commits are small and each one builds. Large mixed commits make the result useless.
- When not to use rebase: on a shared branch that others have pulled. Use merge there.
- Team rule used by many leads: squash merge feature branches into main, rebase locally before opening a PR, never rewrite shared history.

7 Interview lens
- Q: Merge or rebase?
  A: Rebase local, unshared work for a linear history. Merge shared branches to keep the true history and avoid rewriting.
- Q: You force-pushed and a teammate's commits vanished. Recover?
  A: Find the old tip in the reflog of a clone that had it, or in the server's reflog if the platform exposes it. Then create a branch at that hash and restore it. Prevent it with --force-with-lease and protected branches.
- Q: Monorepo or polyrepo for 15 services?
  A: Decide on team autonomy, shared code and tooling cost. Monorepo needs path-based CI and ownership via CODEOWNERS. Polyrepo needs a plan for shared libraries and versioning.
- Q: How does Git store a file change?
  A: Each commit points to a tree of blobs, so it is a snapshot. Unchanged files reuse the same blob. Packfiles use deltas for storage only.

8 Common mistakes
- Rebasing a shared branch: teammates get duplicate commits and conflicts. Fix: agree that only local work is rebased.
- Plain --force push: overwrites others' work. Fix: --force-with-lease plus branch protection.
- Committing secrets: removing the file in a later commit leaves it in history. Fix: rotate the secret first, then clean history (git filter-repo) and add secret scanning.
- Large binaries in the repo: slow clones. Fix: Git LFS or an artifact feed.
- Giant commits with mixed changes: bisect and revert become hard. Fix: small, single-purpose commits.
- Relying on local hooks only: they can be skipped with --no-verify. Fix: repeat the checks in CI.

9 Mental model
- Commits are nodes in a graph. Each one points to its parent.
- Branches and tags are sticky notes on nodes.
- HEAD is "you are here".
- Rewriting history means creating new nodes and moving the notes. The old nodes stay until cleaned up, so the reflog can still find them.

11 Revision summary
- Git objects: blob, tree, commit, tag, named by content hash.
- A branch is a pointer to a commit.
- Revert on shared branches, reset on local ones.
- Never rewrite pushed history on shared branches. Use --force-with-lease if you must.
- Reflog is the local undo and recovers most "lost" commits.
- Bisect finds a bad commit in about log2(n) steps.
- Conventional Commits and signed commits give traceable, automatable history.
- Enforce hook checks again in CI.
