Topic 7.05: Build, test and scan stages [P2 R L]. No K tag, so this is a FULL note for a new topic.

1 What is it
- A build, test and scan stage is the automated part of a pipeline that turns source code into a tested, checked, versioned package without a person doing it by hand.
- Build means restore dependencies, compile and publish. Test means run automated tests and measure coverage. Scan means look for security and quality problems in code, libraries, secrets and container images.
- Quality gate: a rule that fails the pipeline if a measure is bad (example: new critical vulnerabilities, coverage below a set limit).
- Legacy equivalent: MSBuild on a build server plus manual code review and a separate security check before release.

2 Why needed
- Problem solved: every change is built and checked the same way, early, before it reaches users.
- Without it: broken builds reach test environments, vulnerable libraries ship unnoticed, secrets leak into repositories, and "it works on my machine" becomes a release risk.
- Finding a problem at pull request time costs minutes. Finding it in production costs days.

4 Features and core concepts
- Restore, build, test, publish for .NET: download NuGet packages, compile, run tests, produce deployable output. Why: this is the base sequence every other check hangs on.
  dotnet restore
  dotnet build --no-restore -c Release
  dotnet test --no-build -c Release --collect:"XPlat Code Coverage" --logger trx
  dotnet publish -c Release -o ./out
- Test reports and coverage: results files (trx) and a coverage file (Cobertura) that the pipeline publishes to its UI. Why: failures are visible without reading logs.
- Static analysis (SonarQube): a tool that reads source code without running it and reports bugs, smells and duplication. Why: catches defects tests miss.
- SAST: static application security testing. Static analysis aimed at security flaws such as injection. Why: finds vulnerable code patterns before deployment.
- Dependency scanning (Dependabot, NuGet audit): checks your libraries against known vulnerability lists. Why: most of your running code is other people's packages. NuGet audit is built into restore (dotnet list package --vulnerable also works).
- Secret scanning: searches commits for keys, passwords and tokens. Why: a leaked secret is a breach even if the code is perfect.
- Container scanning (Trivy, Defender for Cloud): scans image layers for vulnerable OS packages and libraries. Why: the base image carries its own risks.
- SBOM: software bill of materials, a list of every component in the build. Why: when a new vulnerability is announced you can see at once whether you are affected.
- Quality gates: pass or fail thresholds on results. Why: turns reports into enforcement.
- Build caching: reuse restored packages or Docker layers between runs. Why: faster feedback, lower agent cost.
- Artifact versioning: every build gets a unique version (semver plus build number or git SHA). Why: you can trace a running version to its exact code.
- Signing: a cryptographic signature on packages or images. Why: proves the artifact came from your pipeline and was not changed.

5 Core focus (exam and interview)
- Most asked: where each check sits and why. Cheap, fast checks first (build, unit tests, secret scan); slow ones later (container scan, integration tests).
- Build once, deploy the same artifact to every environment. Never rebuild per environment.
- Gate on new code, not on old debt, so teams are not blocked by history.
- Pull request builds run checks; main branch builds produce releasable artifacts.
- Coverage is a signal, not a goal. A percentage target alone can be gamed.
- Defaults and limits: tool thresholds and hosted agent limits change often (verify). Azure DevOps task names and Defender for Cloud scanning options (verify).

6 Real-world use case
- Situation: a team migrating a legacy MVC app to .NET on Azure DevOps. Releases used to be built on a developer machine.
- Choice: a pipeline with stages: build and unit test, then analysis (Sonar, dependency and secret scan), then docker build with Trivy scan, then publish artifact with version 1.4.0+gitSHA to Azure Artifacts or ACR.
- Gate: fail on new critical or high vulnerabilities and on failed tests. Pull request cannot merge on a red build.
- Trade-off: more checks mean slower pull requests and more false positives to triage. Mitigate with caching, running slow scans only on main or nightly, and a suppression process with owners.
- When NOT to use heavy gating: a tiny prototype or spike. Start with build and tests only, add scans as the project becomes real.

7 Interview lens
- Q: Why build once and promote the artifact? A: What you tested is exactly what you deploy. Rebuilding can change the output through different dependencies or tooling.
- Q: SAST vs dependency scanning? A: SAST checks your own code for flaws. Dependency scanning checks third-party packages against known vulnerabilities.
- Q: Why is coverage a weak gate on its own? A: Tests can run code without asserting anything. Pair it with test quality review and gate on new code.
- Q: How do you handle a scanner false positive blocking release? A: Document it, suppress with an expiry and an owner, and review it later. Do not disable the scan.

8 Common mistakes
- Rebuilding per environment: the tested build differs from production. Fix: one artifact, promote it.
- Scans that only warn: nobody reads them. Fix: gate on severity, with a triage process.
- Gating on total legacy debt: team is blocked on day one. Fix: gate on new code.
- Secrets in pipeline logs or repo: leak. Fix: secret scanning, masked variables, Key Vault (topic 7.08).
- Floating image tags like latest: scan results do not match what runs. Fix: pin versions and use digests.
- No caching: 20 minute builds that people bypass. Fix: cache NuGet and Docker layers.

9 Mental model
- A factory line with inspection points:
  commit -> build -> unit test -> code and secret scan -> package -> image scan -> sign and version -> artifact store
  Any red light stops the line. What exits the line is the only thing allowed to be deployed.

10 Mini lab (about 35 minutes, local plus free Azure DevOps or GitHub)
- Step 1: create a sample app and tests: dotnet new webapi -o lab75, dotnet new xunit -o lab75.tests, add a project reference.
- Step 2: run the four commands from section 4. Expected: build passes, tests pass, a coverage XML and trx file are created, publish output in ./out.
- Step 3: run dotnet list package --vulnerable --include-transitive. Expected: a report (likely none).
- Step 4: add an old vulnerable package version on purpose and rerun. Expected: the vulnerability appears.
- Step 5: install Trivy locally and run trivy fs . and, if Docker is installed, build an image and run trivy image on it. Expected: a list of findings with severities.
- Step 6: put the commands into a basic azure-pipelines.yml with a test results publish step and push it to a free Azure DevOps project (or equivalent GitHub workflow). Expected: green run with test results tab.
- Clean-up: remove the vulnerable package, delete the test project and image (docker image rm), delete the lab repo or pipeline.

11 Revision summary
- Order: restore, build, test, publish, then scan, version, sign.
- Build once, promote the same artifact everywhere.
- SAST scans your code; dependency scan checks packages; secret scan checks commits; container scan checks images.
- SBOM lists components so you can answer "are we affected?" fast.
- Quality gates fail the pipeline; gate on new code.
- Coverage is a signal, not a target.
- Version every artifact with semver plus git SHA.
- Cache packages and layers to keep feedback fast.
