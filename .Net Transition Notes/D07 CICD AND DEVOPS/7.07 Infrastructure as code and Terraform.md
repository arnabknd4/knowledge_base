1 What is it
- Infrastructure as code (IaC) means you describe cloud resources in text files and a tool creates them for you, instead of clicking in the Azure portal.
- Terraform is one such tool. You write what you want (a resource group, a database, an App Service). Terraform compares it with what exists and makes the changes needed.
- Bicep and ARM templates are Azure's own IaC languages. Terraform works across many clouds.
- Legacy equivalent: PowerShell deployment scripts, manually configured IIS servers, and release runbooks kept in Word documents.

2 Why needed
- Portal-built environments cannot be repeated exactly. Dev, test and production drift apart.
- Without IaC, nobody knows who changed what, and a lost environment cannot be rebuilt quickly.
- With IaC, infrastructure goes through pull requests, review, and pipelines like application code.

4 Features and core concepts

IaC principles
- Declarative: you state the end result, not the steps. Why: the tool works out the steps.
- Idempotent: running it twice gives the same result. Why: safe to re-run after a failure.
- Version controlled: infra lives in Git. Why: history, review, rollback.

Provider
- A plugin that talks to one platform (azurerm for Azure, azuread for Entra ID). Why: Terraform core knows nothing about Azure without it.
- Pin the version: required_providers with version = "~> 4.0" (verify current major).

Resource
- One thing to create, such as azurerm_resource_group. Why: this is the unit of change.

Variables, outputs, locals
- Variables are inputs. Outputs are values you print or pass on (an endpoint, an ID). Locals are named expressions inside a module. Why: one codebase serves many environments.

State
- A file recording what Terraform created and the real IDs. Why: Terraform needs it to calculate changes. Never edit it by hand and never commit it to Git.

azurerm backend and locking
- Remote state stored in an Azure Storage blob container. The blob lease gives state locking, so two people cannot apply at once. Why: team safety.

Modules
- A folder of Terraform reused with different inputs. Why: standard building blocks (a "web app" module) instead of copy-paste.

Workspaces
- Several state files from the same code. Why: simple environment split. Many teams prefer separate folders or state per environment instead (verify team convention).

Plan and apply
- terraform plan shows the changes. terraform apply performs them. Why: plan is your review gate in the pipeline.

Drift
- Real infrastructure differs from the code because someone changed it manually. Detect it with plan. Why: portal edits silently break repeatability.

Import
- Bring an existing resource under Terraform control (import block or terraform import). Why: migrating portal-built estates.

Lifecycle
- Rules inside a resource: prevent_destroy, ignore_changes, create_before_destroy. Why: protects databases from accidental deletion.

Testing and linting
- terraform test runs built-in tests. tflint catches bad arguments and naming. checkov scans for security misconfigurations. Why: failures found before apply.

Bicep and ARM
- ARM is the JSON deployment engine in Azure. Bicep is a cleaner language that compiles to ARM. Bicep is Azure-only, has no state file (Azure itself tracks it), and gets new Azure features fast. Terraform is multi-cloud with state. Why: you must be able to justify the choice in an interview.

Secrets in IaC
- Never put secrets in .tf files or state. Use Key Vault references and generate passwords outside Terraform or mark values sensitive. Remember that state can still hold secret values, so restrict access to the state storage.

CI for IaC
- Pipeline runs fmt, validate, tflint, checkov, plan on pull request. Apply only after approval on main.

Naming and tagging
- Follow a convention, for example rg-app-env-region. Apply tags (owner, environment, cost-centre) through variables. Why: cost allocation and governance.

Azure Verified Modules
- Microsoft-maintained, tested modules for common Azure resources (verify current status and coverage). Why: reuse instead of writing your own.

Commands worth memorizing
- terraform init
- terraform fmt -check
- terraform validate
- terraform plan -out=tfplan
- terraform apply tfplan

5 Core focus (exam and interview)
- Order of work: init, validate, plan, apply.
- State is the source of truth for Terraform. Losing it is a serious incident.
- Remote state in Azure Storage supports locking through blob leases.
- Plan is read-only. Apply changes things.
- Drift handling: plan detects it, apply or code change fixes it.
- Terraform vs Bicep: multi-cloud with state vs Azure-only without state.
- For AZ-400, know IaC concepts, ARM and Bicep, and pipeline integration. The Terraform Associate exam is separate (verify current version).

6 Real-world use case
- Situation: a team moving a legacy .NET Framework app to Azure needs identical dev, test and prod: resource group, App Service plan, App Service, Azure SQL, Key Vault.
- Choice: a Terraform repo with one module per component, a tfvars file per environment, remote state in a storage account, and a pipeline that runs plan on pull request and apply after approval.
- Trade-off: you gain repeatability and audit history, but you must manage state, learn HCL, and train the team.
- When NOT to use it: a one-off proof of concept, or an Azure-only team that already knows Bicep and has no multi-cloud need. A single throwaway resource is faster in the portal.

7 Interview lens
- Q: What is Terraform state and why does it matter?
  A: It maps your code to real resources and their IDs. Without it Terraform cannot compute what to change.
- Q: How do you stop two engineers applying at the same time?
  A: Use a remote backend with locking. The azurerm backend uses blob leases.
- Q: Terraform or Bicep for an Azure-only company?
  A: Bicep is simpler with no state. Choose Terraform if there is any multi-cloud need or existing skill.
- Q: Someone changed a resource in the portal. What now?
  A: Run plan to see the drift. Update the code to match, or apply to revert. Restrict portal write access.

8 Common mistakes
- State committed to Git: secrets leak. Fix: remote backend, .gitignore.
- Local state on a laptop: lost state, duplicate resources. Fix: remote backend from day one.
- Unpinned provider versions: a new version breaks the pipeline. Fix: pin versions and commit the lock file.
- Applying without reading the plan: a database gets destroyed and recreated. Fix: review plan output and use prevent_destroy.
- One giant state for everything: slow plans and big blast radius. Fix: split state by layer or environment.
- Secrets in variables files: exposure. Fix: Key Vault and sensitive values.

9 Mental model
- Code (desired state) -> plan -> compare with State (what Terraform knows) and Azure (what is real) -> apply -> Azure updated, State updated.
- Think of it as a shopping list checked against the fridge before shopping.

10 Mini lab (about 30 minutes)
- Tools: Terraform CLI, Azure CLI, Azure free account.
- Steps:
  - az login, then az account set --subscription "<your subscription>".
  - Make a folder and a main.tf with the azurerm provider (features {} block), and one azurerm_resource_group in a nearby region (for example Central India), with a tag environment = "lab".
  - Run terraform init, terraform fmt, terraform validate.
  - Run terraform plan. Expected: 1 to add.
  - Run terraform apply and confirm. Expected: the resource group appears in the portal.
  - Change the tag in the portal, then run terraform plan. Expected: it shows the drift and plans to revert it.
- Clean-up: terraform destroy, then confirm the resource group is gone.

11 Revision summary
- IaC is declarative, idempotent and version controlled.
- Providers talk to platforms. Resources are the unit of change.
- State maps code to real resources. Keep it remote and never in Git.
- azurerm backend uses an Azure Storage blob, with locking by lease.
- Flow: init, validate, plan, apply. Plan is the review gate.
- Drift is found by plan. Import brings existing resources under control.
- lifecycle prevent_destroy protects critical resources.
- Bicep: Azure-only, no state file. Terraform: multi-cloud, with state.
- Checks in CI: fmt, validate, tflint, checkov, terraform test.
