7.10 GitOps, Ansible, Jenkins awareness [P4 O]. Short note, per the tags.

---

1 What is it

- GitOps: Git is the single source of truth for what should run. A tool inside the cluster watches the repo and makes the cluster match it. Argo CD and Flux are the two main tools.
- Ansible: an agentless tool that configures servers by running playbooks over SSH or WinRM. You describe the desired state in YAML.
- Jenkins: a self-hosted CI/CD server. Pipelines are written as code (a Jenkinsfile) and run on worker machines called agents.
- Policy as code and drift detection: rules and checks written as files, and a way to notice when real systems differ from what Git says.
- Legacy equivalent: Jenkins resembles TeamCity or old TFS build servers. Ansible resembles PowerShell scripts or manual setup of IIS servers. GitOps resembles a release folder that deploys itself.

4 Features and core concepts

- Argo CD and Flux: controllers inside Kubernetes that read Git and apply changes. They also repair manual changes. This gives an audit trail and easy rollback with git revert.
- Pull vs push deployment: pull means the cluster fetches from Git itself. Push means a pipeline runs kubectl or helm from outside. Pull keeps cluster credentials inside the cluster, so it is safer and self-healing.
- Ansible inventory: the list of hosts and groups to manage. It tells Ansible where to act.
- Ansible playbooks: YAML files listing tasks to run on hosts. They make server setup repeatable.
- Ansible idempotency: running a playbook twice leaves the same result and changes nothing the second time. This makes reruns safe.
- Jenkins pipeline as code: the build and deploy steps live in a Jenkinsfile in the repo, so they are versioned and reviewed.
- Jenkins agents: machines or containers that run the jobs. The controller only schedules work.
- Policy as code (OPA, Azure Policy): rules such as "no public storage" written as code and enforced automatically. This stops bad config before or after deployment.
- Drift detection: finding that live resources differ from the declared state. It catches manual portal changes.
- Command worth knowing: ansible-playbook -i inventory.ini site.yml --check (dry run, shows what would change)

6 Real-world use case

- Situation: a team runs AKS with six microservices deployed by an Azure DevOps pipeline that runs kubectl apply. People also hot-fix the cluster by hand, so staging and production slowly differ.
- Choice: move to Argo CD (or Flux) watching a config repo. The pipeline only builds the image and updates the image tag in Git. Argo CD applies it and reverts manual edits. Azure Policy blocks non-compliant resources.
- Trade-off: you get audit, rollback and consistency. You pay with an extra tool to run, a second repo to manage, and secrets that need a separate solution.
- When NOT to use it: a small app on App Service or a few VMs. A simple pipeline is enough. Use Ansible mainly for VM or on-premises configuration, and use Terraform for creating cloud resources. Do not start a new Jenkins setup unless the employer already runs it. Azure DevOps or GitHub Actions cost less to maintain.

11 Revision summary

- GitOps means Git holds the desired state and an in-cluster agent applies it.
- Argo CD and Flux use the pull model, so the cluster fetches changes and no external pipeline needs cluster credentials.
- Rollback in GitOps is a git revert.
- Ansible is agentless, uses inventory plus playbooks, and tasks must be idempotent.
- Jenkins uses a Jenkinsfile and agents. It is common in older enterprises, so know it for job interviews.
- Policy as code (OPA, Azure Policy) enforces rules automatically.
- Drift is the gap between declared and live state. GitOps tools detect and fix it.
- Terraform creates infrastructure, Ansible configures servers, and Argo CD or Flux deploys to Kubernetes.
