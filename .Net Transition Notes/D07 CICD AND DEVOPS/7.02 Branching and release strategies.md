1.  What is it
- A way to decide how code moves between branches, and from branches into releases. A branching strategy is the rule set for who creates which branch, how it merges, and how it reaches production.
- A release strategy is how a version gets numbered, tagged, packaged and promoted through environments (dev, test, staging, production).
- Branching and release strategies cover trunk-based development, GitFlow and GitHub Flow, release and hotfix branches, pull request policies, semantic versioning, changelogs, feature flags and environment promotion.
- Legacy equivalent: long-lived branches per environment or per client in GitLab, with manual merges before each release and a release build cut by hand.

2  Why needed
- Without a rule, every developer branches differently and merges land late and large.
- Late merges cause conflicts, broken builds and release-day surprises.
- Without versioning, nobody can say which build is in production or what changed in it.
- Without pull request policies, unreviewed code reaches the main branch.
- Hotfixes are risky when there is no defined path from production back to the main line.

3  Before you read
- Git basics: branch, merge, rebase, tag (topic 7.01).
- CI pipeline: a build and test that runs on every push.
- Environment: a separate deployed copy of the app (dev, test, staging, production).
- Pull request: a request to merge one branch into another, with review.

4  Features and core concepts
- Trunk-based development: everyone commits to one main branch (the trunk) in small changes, or uses very short-lived branches (a day or two). Why it matters: merges stay small, and it is the style that supports continuous delivery best.
- GitFlow: long-lived main and develop branches, plus feature, release and hotfix branches. Why it matters: it fits scheduled, versioned releases (boxed products, client-installed software), but adds merge overhead.
- GitHub Flow: main is always deployable. Work happens on a short feature branch, goes through a pull request, merges to main, then deploys. Why it matters: simple, good for web apps and APIs with frequent deploys.
- Release branch: a branch cut from main to stabilize a version while main moves on. Why it matters: lets you fix release bugs without blocking new work. Costs extra merging back.
- Hotfix branch: a branch from the production tag to ship an urgent fix, then merged back to main. Why it matters: gives a safe, fast path for production bugs. Forgetting the merge back reintroduces the bug.
- Pull request policies: rules enforced on the target branch. Reviews: minimum reviewer count. Required checks: build, tests and scans must pass. CODEOWNERS: a file that maps paths to people who must approve changes. Why it matters: quality is enforced by the platform, not by habit. In Azure DevOps these are branch policies.
- Semantic versioning (SemVer): version as MAJOR.MINOR.PATCH. MAJOR for breaking changes, MINOR for compatible features, PATCH for compatible fixes. Why it matters: consumers can judge upgrade risk from the number.
- Changelog: a human-readable list of changes per version. Why it matters: support, testers and clients can see what changed. Can be generated from commit conventions.
- Feature flags: a runtime switch that turns code on or off without a deploy. Why it matters: lets you merge unfinished work to main safely and separate deploy from release. Old flags must be removed.
- Environment promotion: build once, then promote the same artifact through dev, test, staging and production. Why it matters: what you tested is exactly what you ship. Rebuilding per environment breaks this.
- Worth memorizing: git tag -a v1.4.2 -m "Release 1.4.2" and git push origin v1.4.2

6  Real-world use case
- Situation: a Kolkata team of 12 on an ASP.NET Core API serving a client. The legacy approach was a develop branch and per-client release branches, with a merge day every two weeks that often broke things.
- Choice: move to trunk-based development with short-lived branches, pull requests with build validation, and feature flags for unfinished work. Each merge to main builds one versioned artifact, which is promoted from test to staging to production through Azure DevOps environments with approval at production.
- Hotfix path: tag in production, branch from the tag, fix, pull request to main, release from that, then confirm main has the fix.
- Trade-off: needs good automated tests and discipline about flags. Weak tests make a trunk that is always one bad commit from broken.
- When NOT to use trunk-based: software installed by customers with many supported versions at once. There GitFlow-style release branches, or long-lived support branches, are justified.

7  Interview lens
- Q: Trunk-based or GitFlow for a SaaS API?
- A: Trunk-based or GitHub Flow, with feature flags. Deploys are frequent and only one version runs in production, so GitFlow overhead is wasted.
- Q: How do you ship an urgent production fix?
- A: Branch from the production tag, fix, pull request with checks, release, then merge to main. If main moved on, cherry-pick or merge so the fix is not lost.
- Q: What branch policies do you set on main?
- A: Minimum reviewers, required build and test checks, CODEOWNERS approval, no direct push, and linked work items. Also block force push.
- Q: How do you handle unfinished features on trunk?
- A: Merge behind a feature flag that is off. Release by turning the flag on, and delete the flag after rollout.

8  Common mistakes
- Long-lived feature branches: shows up as painful merges and surprise conflicts. Fix: branch for days not weeks, merge main in often, use flags.
- Rebuilding per environment: shows up as "worked in staging, failed in production". Fix: build once, promote the same artifact.
- Hotfix not merged back: the bug returns in the next release. Fix: make the merge back a required step in the hotfix checklist.
- Direct pushes to main: shows up as broken builds and unreviewed code. Fix: enforce branch policies, including for admins where possible.
- Version numbers set by hand: shows up as duplicates and confusion. Fix: generate versions in the pipeline from tags or a tool (verify tool choice).
- Stale feature flags: shows up as dead code paths and risk. Fix: record an owner and removal date for each flag.

9  Mental model
- Think of a river and tributaries.
- Main is the river, always flowing and always clean. Feature branches are short streams that join quickly.
- Releases are tagged points on the river. Hotfix is a small side channel from a tagged point that must rejoin the river.
- main --o--o--o--o--o--> (tags: v1.4.0, v1.4.1)
- feature branches: short, merge in days

10  Mini lab
- Time: 30 minutes. Tools: Git and any local folder, no Azure needed.
- Step 1: git init demo, create a file, commit on main, then git tag v1.0.0.
- Step 2: git switch -c feature/greeting, change the file, commit, then git switch main and git merge --no-ff feature/greeting. Tag v1.1.0.
- Step 3: simulate a hotfix: git switch -c hotfix/1.0.1 v1.0.0, fix the file, commit, tag v1.0.1.
- Step 4: merge the hotfix into main: git switch main, git merge hotfix/1.0.1. Resolve any conflict.
- Expected result: git log --oneline --graph --all --decorate shows main, the feature merge, and the hotfix merge, with tags v1.0.0, v1.0.1 and v1.1.0.
- Optional extension: in a free GitHub repo, add branch protection on main requiring a pull request and one review.
- Clean-up: delete the demo folder, or delete the test repo on GitHub.

11  Revision summary
- Trunk-based: small, frequent merges to main, short-lived branches.
- GitFlow: develop, release and hotfix branches, for scheduled versioned releases.
- GitHub Flow: main is always deployable, short feature branch plus pull request.
- Hotfix: branch from the production tag, then always merge back to main.
- Pull request policies: reviewers, required checks, CODEOWNERS, no direct push.
- SemVer: MAJOR breaking, MINOR compatible feature, PATCH compatible fix.
- Feature flags separate deploy from release, and must be removed later.
- Build once, promote the same artifact through environments.
