# Infrastructure as Code (IaC) with Terraform

## 1. What is it?
Infrastructure as Code (IaC): Managing and provisioning infrastructure through code instead of manual processes.

Terraform: A declarative tool by HashiCorp that enables multi-cloud and hybrid workflows.

Key concepts: Declarative vs Imperative, Idempotency, State management.

---

## 2. Why do we need it?
Eliminates manual configuration errors.

Enables repeatability and consistency across environments.

Facilitates automation, version control, and collaboration.

Supports multi-cloud deployments with a single workflow.

---

## 3. Real World Example
A company deploying workloads across AWS and Azure uses Terraform to define infrastructure in .tf files.

Running terraform apply provisions identical environments in both clouds.

Ensures disaster recovery and hybrid cloud flexibility.

---

## 4. Exam Perspective
Expect questions on declarative vs imperative approaches.

Understand idempotency: applying the same configuration multiple times yields the same result.

Know Terraform’s role in multi-cloud workflows and state management.

---

## 5. Interview Questions
- What is Infrastructure as Code (IaC)?
- Difference between declarative and imperative IaC?
- How does Terraform ensure idempotency?
- Why is Terraform popular for multi-cloud deployments?
- What challenges does IaC solve compared to manual provisioning?

---

## 6. Common Mistakes
- Confusing imperative scripts (step-by-step commands) with declarative IaC (desired state).
- Ignoring state file management, leading to drift.
- Not using version control for .tf files.
- Overlooking idempotency when writing configurations.

---

## 7. Mental Model
Think of Terraform as a blueprint architect:

You describe the desired state (like a house plan).

Terraform ensures the infrastructure matches that plan, no matter how many times you apply it.

The state file acts as the “memory” of what’s already built.

---

## 8. Revision Summary
- IaC = infrastructure managed via code.
- Declarative (Terraform) vs Imperative (scripts).
- Idempotency ensures consistent results.
- Terraform enables multi-cloud, hybrid workflows.
- State management is critical for accuracy.

---

# Terraform Fundamentals

## 1. What is it?
- Core building blocks of Terraform that enable infrastructure provisioning.  
- Includes **providers**, **provider versions**, **dependency lock file**, and **installation basics**.  
- Foundation for all Terraform workflows.

---

## 2. Why do we need it?
- Providers act as **plugins** to interact with cloud platforms (AWS, Azure, GCP, etc.).  
- Versioning ensures **stability** and avoids breaking changes.  
- Dependency lock file (`.terraform.lock.hcl`) guarantees consistent provider versions across teams.  
- Proper installation and initialization (`terraform init`) set up the working directory.

---

## 3. Real World Example
- A DevOps team uses Terraform with **AWS provider v5.0.0**.  
- The lock file ensures every team member uses the same provider version, preventing mismatched behavior.  
- Running `terraform init` downloads the provider plugin and prepares the environment.

---

## 4. Exam Perspective
- Know the role of **providers** and how they connect Terraform to external APIs.  
- Understand **provider version constraints** (`>=`, `~>`, `=`).  
- Be familiar with the **dependency lock file** and its purpose.  
- Expect questions on `terraform init` and what it does.

---

## 5. Interview Questions
- What is a Terraform provider?  
- Why do we need provider versioning?  
- What is the purpose of the `.terraform.lock.hcl` file?  
- What happens when you run `terraform init`?  
- How does Terraform ensure consistency across environments?

---

## 6. Common Mistakes
- Not specifying provider versions → risk of breaking changes.  
- Ignoring the lock file → inconsistent environments.  
- Forgetting to run `terraform init` after adding new providers.  
- Misunderstanding version constraints (`~>` vs `=`).

---

## 7. Mental Model
Think of **providers** as **drivers**:
- Terraform is the car 🚗.  
- Providers are the drivers that know how to talk to AWS, Azure, GCP.  
- The lock file ensures all drivers use the same “manual” version.  
- `terraform init` is like starting the engine before driving.

---

## 8. Revision Summary
- Providers = plugins for cloud APIs.  
- Provider versions must be pinned for stability.  
- `.terraform.lock.hcl` ensures consistent versions.  
- `terraform init` sets up the environment.  
- Fundamentals = foundation for all Terraform workflows.

---
# Core Terraform Workflow

## 1. What is it?
- The **core lifecycle commands** in Terraform that manage infrastructure.  
- Includes initialization, planning, applying, destroying, validation, and formatting.  
- Provides visibility into execution plans (create, update, replace, destroy).

---

## 2. Why do we need it?
- Ensures infrastructure changes are **predictable and controlled**.  
- Allows teams to **validate** configurations before deployment.  
- Provides a **repeatable workflow** for provisioning and managing resources.  
- Helps maintain **consistency** across environments.

---

## 3. Real World Example
- A DevOps engineer runs:  
  - `terraform init` → downloads providers and sets up the working directory.  
  - `terraform plan` → previews changes before applying.  
  - `terraform apply` → provisions resources.  
  - `terraform destroy` → removes resources when no longer needed.  
- `terraform validate` ensures syntax correctness, while `terraform fmt` enforces style consistency.

---

## 4. Exam Perspective
- Know the purpose of each command (`init`, `plan`, `apply`, `destroy`, `validate`, `fmt`).  
- Understand **execution plan interpretation**: create, update, replace, destroy.  
- Expect questions on workflow order and best practices.  
- Be able to identify when to use `validate` vs `fmt`.

---

## 5. Interview Questions
- What is the purpose of `terraform init`?  
- How does `terraform plan` help avoid mistakes?  
- What is the difference between `terraform validate` and `terraform fmt`?  
- How do you interpret an execution plan?  
- Why is `terraform destroy` important in lifecycle management?

---

## 6. Common Mistakes
- Forgetting to run `terraform init` after adding new providers.  
- Skipping `terraform plan` → unexpected changes in production.  
- Confusing `validate` (syntax check) with `fmt` (style formatting).  
- Misinterpreting execution plan actions (e.g., replace vs update).  

---

## 7. Mental Model
Think of Terraform workflow as a **construction project**:
- `init` → gather tools and materials.  
- `plan` → blueprint of changes.  
- `apply` → build according to the blueprint.  
- `destroy` → dismantle when project ends.  
- `validate` → check blueprint correctness.  
- `fmt` → ensure blueprint is neatly drawn.

---

## 8. Revision Summary
- Core commands: `init`, `plan`, `apply`, `destroy`.  
- Supporting commands: `validate`, `fmt`.  
- Execution plan shows create, update, replace, destroy.  
- Workflow ensures predictable, consistent infrastructure changes.

---

# Terraform Configuration

## 1. What is it?
- Defines infrastructure using **resources** and **data sources**.
- Uses **variables, outputs, locals** with precedence rules.
- Supports **expressions, functions, dynamic blocks**.
- Handles **dependencies** (implicit/explicit) and references.
- Integrates with Vault for **sensitive data handling**.

---

## 2. Why do we need it?
- Provides flexibility and reusability in configurations.
- Ensures secure handling of secrets.
- Enables modular, maintainable infrastructure definitions.

---

## 3. Real World Example
- Using `aws_instance` resource with a `data.aws_ami` data source to fetch the latest AMI.
- Variables store environment-specific values, outputs expose resource attributes.

---

## 4. Exam Perspective
- Differentiate **resources vs data sources**.
- Understand variable precedence (default, environment, CLI).
- Know how to use **dynamic blocks** and **functions**.
- Sensitive data best practices with Vault.

---

## 5. Interview Questions
- Difference between resources and data sources?
- How does Terraform handle variable precedence?
- What is a dynamic block?
- How do you manage sensitive data in Terraform?

---

## 6. Common Mistakes
- Confusing resources with data sources.
- Hardcoding values instead of using variables.
- Ignoring sensitive data handling → secrets exposed in state.

---

## 7. Mental Model
Think of configuration as a **recipe**:
- Resources = ingredients.
- Data sources = lookup tables.
- Variables = parameters.
- Outputs = results.
- Dependencies = cooking order.

---

## 8. Revision Summary
- Resources vs data sources.
- Variables, outputs, locals, precedence.
- Expressions, functions, dynamic blocks.
- Dependencies and references.
- Sensitive data handling with Vault.

---

- Inputs/outputs, variable scope.
- Versioning and reuse.

# Terraform State Management

## 1. What is it?
- State = Terraform’s record of infrastructure.
- Stored in **local or remote backends**.
- Supports **state locking** and **drift detection**.

---

## 2. Why do we need it?
- Maps real-world resources to configuration.
- Prevents conflicts with state locking.
- Detects drift between actual and desired state.

---

## 3. Real World Example
- Team stores state in **S3 backend** with DynamoDB for locking.
- Commands like `terraform state list`, `mv`, `import` manage state.

---

## 4. Exam Perspective
- Local vs remote backends.
- State locking and drift detection.
- Key commands: `state list`, `state mv`, `state import`.

---

## 5. Interview Questions
- Why is state important in Terraform?
- Difference between local and remote backends?
- How does Terraform detect drift?
- What are common state commands?

---

## 6. Common Mistakes
- Storing state locally → risk of loss.
- Not enabling locking → race conditions.
- Ignoring drift detection.

---

## 7. Mental Model
State is Terraform’s **memory**:
- Local = personal notebook.
- Remote = shared notebook with locks.
- Commands = tools to edit memory.

---

## 8. Revision Summary
- Local vs remote backends.
- State locking, drift detection.
- Commands: `state list`, `mv`, `import`.

# Key CLI Commands

- `terraform init` → Initialize working directory.  
- `terraform plan` → Preview changes.  
- `terraform apply` → Apply changes.  
- `terraform destroy` → Remove infrastructure.  
- `terraform fmt` → Format configuration.  
- `terraform validate` → Validate syntax.  
- `terraform state list` → Show resources in state.  
- `terraform state mv` → Move resources in state.  
- `terraform import` → Import existing resources.  
- `terraform output` → Show output values.  
- `terraform providers` → List providers used.
