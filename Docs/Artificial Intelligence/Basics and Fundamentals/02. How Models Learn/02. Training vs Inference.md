## 1. Learn It (Core Understanding)
- **One-line definition:** Training is the phase where a model learns patterns from data by adjusting its internal parameters; inference is the phase where the trained model is used to produce outputs (predictions, text, images) on new inputs.
- **Plain-English explanation (3-4 lines):**
  Training is the "studying" phase: the model sees many examples, measures its errors, and adjusts its weights until it performs well. It is compute-heavy and happens occasionally. Inference is the "taking the exam or doing the job" phase: the weights are frozen, and the model simply applies what it learned to new inputs. It happens every time someone uses the model, potentially millions of times a day.
- **Why it exists / problem it solves:**
  - Separates the expensive, one-time work of learning from the cheap, repeated work of using
  - Lets one trained model serve many users and requests
  - Creates clear control points: what goes into training (data governance) and what goes into and out of a live model (usage governance)
- **Key terms to know:**
  - **Training:** Learning by adjusting parameters to reduce error on training data
  - **Inference (serving / prediction / deployment):** Using a trained model on new inputs
  - **Parameters / weights:** Internal numbers adjusted during training; fixed during inference
  - **Loss function:** Measures how wrong the model is during training
  - **Epoch:** One full pass through the training data
  - **Backpropagation / gradient descent:** The core method used to update weights during training
  - **Hyperparameters:** Settings chosen before training (learning rate, model size), not learned from data
  - **Pre-training:** Initial large-scale training on broad data
  - **Fine-tuning:** Further training of a pre-trained model on narrower data
  - **Checkpoint:** Saved snapshot of a model's weights during or after training
  - **Latency:** Time to return an answer at inference
  - **Throughput:** Number of requests handled per unit of time
  - **Batch inference:** Processing many inputs together, offline
  - **Real-time (online) inference:** Answering individual requests immediately
  - **Edge inference:** Running the model on a local device (phone, sensor) rather than the cloud
  - **Retraining:** Training again on fresh data, often triggered by drift
  - **In-context learning:** Model adapts its behaviour using examples in the prompt, **without** changing weights
- **How it works (simple steps):**
  1. **Training:** Feed data → model predicts → compare with the correct answer (loss) → adjust weights → repeat many times.
  2. **Evaluate:** Test on unseen data; if acceptable, save the model.
  3. **Deploy:** Release the model to an application or API.
  4. **Inference:** A user sends an input → the model applies its fixed weights → returns an output.
  5. **Monitor and retrain:** Track performance and drift; retrain or update when needed.
- **Where it sits in the AI stack:** Model lifecycle layer. Training sits in the build phase; inference sits in the run phase. Governance applies to both.

## 2. Mental Model
- **Analogy:** A medical student vs a practising doctor. **Training** is medical school: years of study, expensive, done once (with periodic updates). **Inference** is seeing patients: fast, repeated daily, using what was already learned. The doctor does not rewrite their medical education with each patient, just as a deployed model does not update its weights with each prompt.
- **Diagram / flow:**
```
  TRAINING (build phase)                    INFERENCE (run phase)
  ─────────────────────                     ─────────────────────
  Training data                             New input (prompt / record)
       │                                         │
       ▼                                         ▼
  [Model] ─► prediction ─► loss ─► update    [Trained model, frozen weights]
       ▲                        │                │
       └──── adjust weights ◄───┘                ▼
                                              Output (prediction / text)
  Heavy compute, occasional, weights change    Lighter per request, constant, weights fixed
                      │
                      ▼
            Saved trained model ────────────► deployed for inference
                      ▲                                   │
                      └──── retrain when drift detected ◄─┘
```
- **The one thing to remember:** Training **changes** the model; inference **uses** the model. A deployed model's weights do not change when you chat with it.
- **Compare and contrast:**

  | | Training | Inference |
  |---|---|---|
  | Purpose | Learn patterns from data | Apply learned patterns to new inputs |
  | Weights | Updated | Frozen |
  | Data used | Large training datasets (often labelled) | Live or new inputs |
  | Frequency | Occasional (once, then periodic retraining) | Continuous, every request |
  | Compute | Very high (GPU/TPU clusters) per run | Lower per request, but large in total at scale |
  | Cost pattern | Large upfront cost | Ongoing running cost |
  | Key concern | Data quality, bias, cost, reproducibility | Latency, reliability, cost per request, security |
  | Typical risks | Data poisoning, bias, privacy leakage, IP issues | Prompt injection, data leakage, hallucination, misuse |
  | Who is involved | Data scientists, ML engineers | Applications, end users, operations teams |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / Compare / Scenario / Best-fit / Pick-the-risk
- **Must-memorize facts:**
  - [ ] Training = learning (weights updated); inference = using (weights fixed)
  - [ ] Training is compute-intensive and infrequent; inference is frequent, latency-sensitive, and cost accumulates with usage
  - [ ] Models do **not** learn from individual user prompts during normal inference
  - [ ] In-context learning (few-shot examples in a prompt) changes behaviour temporarily, not the weights
  - [ ] Pre-training → fine-tuning → deployment (inference) → monitoring → retraining
  - [ ] Data drift or performance decay triggers retraining
  - [ ] Hyperparameters are set before training; parameters are learned during training
  - [ ] Inference modes: real-time (online), batch, edge
  - [ ] Training-stage risks: poisoned or biased data, privacy leakage (memorisation), copyright issues, reproducibility
  - [ ] Inference-stage risks: prompt injection, sensitive data in prompts, hallucination, model misuse, availability and cost
  - [ ] User prompts may be logged or used for future training **depending on vendor terms**, so check the settings
- **Keywords that signal this topic in a question:** "learns," "weights updated," "epoch," "loss," "prediction," "serving," "latency," "deployed model," "real-time," "batch"
- **Commonly confused with:**
  - Training vs fine-tuning (fine-tuning is additional training on a narrower dataset)
  - Inference vs deployment (deployment makes the model available; inference is the act of using it)
  - In-context learning vs training (no weight change)
  - Parameters vs hyperparameters
  - Training data vs inference input (prompt)
  - Retraining vs continuous learning (retraining is a deliberate, controlled process)
- **Elimination tips (how to rule out wrong options):**
  - Reject "the model learns from every conversation and updates itself instantly" unless the scenario explicitly describes an online-learning setup.
  - Reject "inference is the expensive part of a single run." Per request it is cheap, but total cost grows with usage.
  - Reject "more inference fixes a poor model." Only better data, training, or design does.
  - For scenarios about latency, speed, and cost at scale, think inference. For bias in historical data or data quality, think training.
  - For "model performance degrades after deployment," think drift → monitoring → retraining.
- **Frameworks / standards link:**
  - **EU AI Act:** Data-governance duties for high-risk systems focus on **training, validation, and testing data**. Record-keeping, human oversight, accuracy, and robustness obligations apply during **operation (inference)**. For **general-purpose AI models**, providers must document training and publish a summary of training content and maintain a copyright policy.
  - **NIST AI RMF:** Risks span the lifecycle: data and model building (Map and Measure) and deployment and operation (Manage, monitoring).
  - **ISO/IEC 42001:** AI lifecycle controls cover development (training, verification, validation), deployment, operation, and monitoring.
  - **Privacy link:** Training on personal data needs a lawful basis; prompts at inference may contain personal data and need protection, retention limits, and vendor controls.
  - **Governance angle:** Training-time controls = data quality, provenance, bias testing. Inference-time controls = access control, input and output filtering, logging, human oversight, monitoring.

## 4. 🛠️ Real-World Use Cases
| # | Scenario | Industry | Training vs Inference in practice | Outcome / risk |
|---|---|---|---|---|
| 1 | Fraud detection on card payments | Banking | Trained periodically on past transactions; real-time inference scores each payment in milliseconds | Latency is critical; retraining needed as fraud patterns drift |
| 2 | Enterprise chatbot using a vendor LLM | Cross-industry | Vendor did the training; the company only does inference (plus optional fine-tuning or RAG) | Ongoing per-use cost; prompts may contain confidential data |
| 3 | Overnight customer-scoring run | Telecom / Insurance | Batch inference on the full customer base | Cheaper and simpler than real-time; results can be stale |
| 4 | On-device face unlock or speech recognition | Consumer tech | Trained in the cloud; edge inference on the phone | Better privacy and speed; limited by device power |
| 5 | Model fine-tuned on company documents | Legal / Consulting | Additional training on internal data, then inference | Better domain fit; risk of leaking training data, needs data governance |

- **Consulting / assurance lens:**
  - Ask the client: "Did you train the model, fine-tune it, or just call someone else's? Who is responsible for each stage?"
  - Training responsibility shifts the focus to data governance; inference-only use shifts it to vendor management, input and output controls, and monitoring.
- **Evidence or controls you would look for:**
  - Training documentation: data sources, versions, hyperparameters, evaluation results, reproducibility records
  - Model versioning and approval before deployment
  - Monitoring of live performance, drift, and errors
  - Defined triggers and process for retraining or rollback
  - Logging of inputs and outputs (with privacy safeguards) and incident handling
  - Vendor terms on whether prompts are retained or used for training
  - Cost and capacity monitoring for inference at scale

## 5. Q&A Bank

### Quick recall
- **Q:** What happens during training?
  **A:** The model learns from data by repeatedly measuring its errors and adjusting its weights.

- **Q:** What happens during inference?
  **A:** The trained model, with fixed weights, produces outputs for new inputs.

- **Q:** Do model weights change during inference?
  **A:** No, not in standard deployments.

### Conceptual
- **Q:** Why is training usually more expensive than a single inference, yet inference can cost more overall?
  **A:** Training needs huge compute for a concentrated period. Inference is cheap per request but repeats across millions of requests, so the total cost over a model's life can exceed training cost.

- **Q:** What is the difference between fine-tuning and in-context learning?
  **A:** Fine-tuning further trains the model and changes its weights permanently. In-context learning supplies examples in the prompt, which shapes the output temporarily without changing any weights.

- **Q:** What triggers retraining?
  **A:** Performance degradation, data or concept drift, new data, changed business rules or regulation, or discovered bias or errors.

- **Q:** What are the main inference deployment modes?
  **A:** Real-time (online) for instant responses, batch for large offline runs, and edge for on-device processing.

### Scenario-based
- **Q:** A user tells a chatbot their name, and the next day a different user cannot get the model to repeat it. The first user is surprised. Why?
  **A:** The model's weights are not updated by individual conversations. Within one conversation, information stays in the context window, but it is not stored in the model itself. (Separate memory features or data logging, if any, are application-level and vendor-dependent.)

- **Q:** A fraud model performed well at launch but misses new scam types six months later. What should be done?
  **A:** Investigate data and concept drift via monitoring, refresh the training data with recent cases, retrain and validate, then redeploy with version control and rollback.

- **Q:** Staff paste client data into a public AI tool. Which stage is the risk, and why does it matter?
  **A:** Inference-time input risk. The data leaves the organisation and, depending on vendor terms, might be retained or used to train future models. Controls: acceptable-use policy, approved enterprise tools with no-training terms, data classification rules, and monitoring.

### Interview-style
- **Q:** "Explain training vs inference to a non-technical executive."
  **A:** "Training is when the AI learns, like sending a new hire through a long, expensive course. Inference is when it does the job, answering questions or making predictions day to day. The learning is done upfront and updated occasionally, while the daily work happens constantly. That split matters for governance: we control the quality of what it learns during training, and we control how it's used, what goes in, and what comes out during everyday operation."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Document training data, settings, and results for reproducibility | Deploy a model with no record of how it was trained |
| Validate the model on unseen data before release | Assume training performance equals real-world performance |
| Monitor live performance and drift after deployment | Treat deployment as the finish line |
| Define triggers and a process for retraining or rollback | Retrain ad hoc without testing and approval |
| Check vendor terms on prompt retention and training use | Assume your prompts are never stored or used for training |
| Plan for inference cost, latency, and scale | Budget only for training and ignore running costs |
| Keep sensitive data out of unapproved tools | Paste confidential or personal data into public models |
| Version models and keep approved checkpoints | Overwrite models without traceability |

- **Common mistakes / misconceptions:**
  1. "The model learns from every conversation." (Not in standard deployments; weights are fixed.)
  2. "Inference is cheap, so cost doesn't matter." (Cost scales with usage.)
  3. "Training once is enough." (Drift makes periodic retraining necessary.)
  4. "Prompt examples retrain the model." (In-context learning does not change weights.)
  5. "Using a vendor's LLM means we have no training-related risk." (Training data risks such as bias and IP are inherited.)
- **Red flags in practice:**
  - No model versioning or training documentation
  - No monitoring after go-live
  - Unknown vendor policy on prompt data use
  - No retraining or rollback process
  - Inference costs or latency never estimated

## 7. Revision Snapshot
- **30-second summary:**
  Training is where a model learns by adjusting weights on large datasets; it is compute-heavy and occasional. Inference is where the trained, frozen model produces outputs for new inputs; it is continuous, latency-sensitive, and its cost scales with usage. Pre-training and fine-tuning are training stages; in-context learning is not training. Drift triggers retraining. Training risks centre on data (bias, poisoning, privacy, IP); inference risks centre on usage (prompt injection, data leakage, hallucination, misuse). Governance covers both the build and run phases.
- **3 bullets to recall on exam day:**
  1. Training changes weights; inference uses frozen weights
  2. Training = heavy and occasional; inference = light per request but constant, and cost scales
  3. Drift → monitor → retrain; check vendor terms on prompt data
