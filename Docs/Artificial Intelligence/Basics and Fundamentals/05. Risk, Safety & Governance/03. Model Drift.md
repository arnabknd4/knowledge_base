## 1. Learn It (Core Understanding)
- **One-line definition:** Model drift (also called model decay or degradation) is the loss of a model's performance over time after deployment, because the real-world data or the relationships it learned from have changed since training.
- **Plain-English explanation (3-4 lines):**
  A model is trained on a snapshot of the past. Once deployed, the world keeps moving: customers change behaviour, fraudsters adapt, prices shift, new products appear, a sensor is replaced, or a data pipeline quietly changes a field. The model's weights stay frozen, so its picture of the world slowly goes out of date and its accuracy falls, often silently and without any error message. Drift is not a bug in the code; it is a natural consequence of deploying a static model into a changing environment, which is why it must be monitored.
- **Why it exists / problem it solves:**
  - Explains why a model that passed validation can still fail months later
  - Justifies continuous monitoring, retraining, and lifecycle governance rather than "deploy and forget"
  - Provides early-warning signals so problems are caught before they harm customers or the business
- **Key terms to know:**
  - **Model drift / model decay:** General term for performance degradation over time
  - **Data drift (covariate shift):** The distribution of the **input features** changes (e.g., customers become younger on average), while the input-output relationship may be unchanged
  - **Concept drift:** The **relationship between inputs and the target** changes (e.g., what counts as a fraudulent transaction changes)
  - **Label drift / prior probability shift:** The distribution of the **target** itself changes (e.g., fraud rate doubles)
  - **Upstream data change / data quality drift:** Schema, units, encoding, or pipeline changes that corrupt inputs (e.g., a field switches from dollars to cents)
  - **Sudden vs gradual vs seasonal vs recurring drift:** Patterns in how drift appears over time
  - **Training-serving skew:** Mismatch between how data looked in training and how it is produced in production (not the same as drift over time)
  - **Ground truth / feedback delay:** True outcomes (e.g., loan default) may arrive months later, delaying direct performance measurement
  - **Proxy metrics:** Indirect signals (input distributions, prediction distributions, confidence, business KPIs) used when ground truth is delayed
  - **Population Stability Index (PSI):** Common measure of how much a feature's distribution has shifted (rule of thumb: below 0.1 stable, 0.1-0.25 moderate shift, above 0.25 significant shift)
  - **Statistical drift tests:** Kolmogorov-Smirnov test, chi-square test, Kullback-Leibler and Jensen-Shannon divergence, Wasserstein distance
  - **Performance monitoring:** Tracking accuracy, precision/recall, error rates, and calibration in production, including by subgroup
  - **Retraining:** Refreshing the model on newer data; can be scheduled, triggered by thresholds, or continuous (with controls)
  - **Champion-challenger / shadow / canary deployment:** Safe ways to test a new model against the live one before replacing it
  - **Feedback loop:** Model outputs influence future data (e.g., only approved applicants generate repayment data), which can reinforce bias or hide drift
  - **Rollback:** Reverting to a previous approved model version
  - **LLM-specific drift:** Changes in behaviour after a vendor updates or retires a model version, shifts in user prompts, stale knowledge, changes in retrieval content (RAG corpus), and prompt regressions
  - **Knowledge cutoff / staleness:** An LLM's training data ends at a date; facts after it are unknown unless supplied
- **How it works (simple steps):**
  1. **Baseline:** Record training data statistics and validated performance as the reference point.
  2. **Monitor inputs and outputs:** Track feature distributions, prediction distributions, data quality, and confidence in production.
  3. **Measure performance:** Compare predictions with ground truth as it becomes available (with subgroup views); use proxy metrics while waiting.
  4. **Detect and alert:** Statistical tests and thresholds (e.g., PSI, error rates) trigger alerts to model owners.
  5. **Diagnose:** Is it data drift, concept drift, a pipeline fault, or a real-world shift? Check upstream changes first.
  6. **Respond:** Fix the pipeline, recalibrate, retrain on recent data, rebuild the model, add human review, or roll back.
  7. **Validate and release safely:** Test the updated model (champion-challenger, shadow, canary), get approval, version it, and document the change.
- **Where it sits in the AI stack:** Operations and governance layer (post-deployment monitoring and lifecycle management). Drift is the main reason validation is not a one-time event.

## 2. Mental Model
- **Analogy:** **A paper map in a growing city.** The map was accurate on the day it was printed. New roads open, old ones close, and one-way systems change, but the map in your glovebox never updates. At first it is mostly right, then it occasionally sends you the wrong way, and eventually you are lost, all without the map ever "breaking". Monitoring is checking the map against the road signs; retraining is buying the new edition.
- **Diagram / flow:**
```
  Performance
   │ ████████████                     Validated at launch
   │            ████
   │                ████              ← gradual drift (slow decay)
   │                    ████
   │                        ██        ← sudden drift (pipeline change / market shock)
   │                          ██
   └───────────────────────────────► Time since deployment
        ▲ alert threshold crossed ─► investigate ─► retrain / fix / roll back

  WHAT CHANGED?
  Inputs changed, relationship same        → DATA DRIFT (covariate shift)
  Inputs same, relationship changed        → CONCEPT DRIFT
  Target mix changed (e.g., fraud rate)    → LABEL / PRIOR SHIFT
  Pipeline or schema broke                 → DATA QUALITY / UPSTREAM CHANGE
  Vendor swapped or updated the LLM        → LLM VERSION DRIFT
```
- **The one thing to remember:** A deployed model's weights are frozen but the world is not, so performance decays unless you monitor and maintain it.
- **Compare and contrast:**

  | | Data drift | Concept drift | Label drift |
  |---|---|---|---|
  | What changes | Input distribution P(X) | Input-output relationship P(Y given X) | Target distribution P(Y) |
  | Example | Applicants become younger on average | Fraud tactics evolve, so old patterns no longer signal fraud | Default rate rises during a recession |
  | Detectable without ground truth? | Yes (compare input distributions) | Hard (usually needs outcomes) | Partly (from predictions, fully with outcomes) |
  | Typical fix | Retrain on recent data; check pipeline | Retrain, re-engineer features, rethink the model | Recalibrate thresholds; retrain |

  | | Model drift | Overfitting | Training-serving skew |
  |---|---|---|---|
  | When it appears | After deployment, over time | Already at training/validation time | From day one in production |
  | Cause | World or data changes | Model memorised noise | Different processing in training vs serving |
  | Signal | Performance slowly or suddenly falls | Big train-test gap | Bad performance immediately after launch |

  | | Scheduled retraining | Trigger-based retraining | Continuous / online learning |
  |---|---|---|---|
  | Approach | Fixed cadence (e.g., monthly) | When monitoring thresholds are crossed | Model updates constantly from new data |
  | Pros | Simple, predictable | Efficient, responsive | Adapts quickly |
  | Risks | May retrain too late or needlessly | Needs good monitoring | Harder to govern; risks of poisoning, feedback loops, unvalidated changes |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / Identify-the-drift-type / Scenario (performance drops after deployment) / Best-control / Compare (drift vs overfitting) / Pick-the-first-step
- **Must-memorize facts:**
  - [ ] **Model drift** = performance degradation after deployment caused by change in data or relationships
  - [ ] **Data drift (covariate shift)** = inputs change; **concept drift** = input-output relationship changes; **label drift** = target distribution changes
  - [ ] Drift can be **sudden, gradual, seasonal, or recurring**
  - [ ] Drift usually happens **silently**: no error, just worse decisions
  - [ ] Drift is **not** overfitting (overfitting exists at training time; drift emerges later)
  - [ ] **Ground truth is often delayed**, so monitor **input distributions, prediction distributions, data quality, and proxy/business metrics** as early warnings
  - [ ] Common detection measures: **PSI, KS test, KL/JS divergence, chi-square**, plus direct **performance monitoring** (accuracy, precision/recall, calibration, by subgroup)
  - [ ] **First check the pipeline:** many "drift" incidents are upstream data or schema changes
  - [ ] Responses: fix data pipeline, **retrain**, recalibrate, rebuild, add human review, or **roll back**; validate before redeploying
  - [ ] Safe release patterns: **shadow mode, canary release, champion-challenger**, with versioning and rollback
  - [ ] **Feedback loops** (model decisions shape future training data) can hide drift and amplify bias
  - [ ] **LLM/GenAI drift:** vendor model updates or retirements change behaviour; prompts may regress; RAG content and knowledge go stale; re-run evaluation suites after any change
  - [ ] Drift monitoring should cover **fairness and subgroup performance**, not only overall accuracy
  - [ ] Monitoring is a **governance requirement**, not just a technical nice-to-have (NIST Manage, EU AI Act post-market monitoring, ISO 42001 performance evaluation, SR 11-7 ongoing monitoring)
  - [ ] Retraining is not automatically safe: **newly trained models must be re-validated and re-approved**
- **Keywords that signal this topic in a question:** "performance degraded over time," "worked at launch," "data distribution changed," "ongoing monitoring," "retraining trigger," "post-deployment," "stale model," "seasonality," "pandemic changed behaviour," "vendor updated the model"
- **Commonly confused with:**
  - Drift vs overfitting (time after deployment vs fit at training)
  - Data drift vs concept drift (inputs changed vs meaning of inputs changed)
  - Drift vs training-serving skew (gradual change vs mismatch from the start)
  - Drift vs a software bug or outage (model runs "fine" but is increasingly wrong)
  - Monitoring vs testing (continuous in production vs pre-release)
  - Retraining vs fine-tuning (retraining refreshes on new data; fine-tuning adapts a pre-trained model to a task; both need validation)
  - Data drift vs data quality problems (real-world change vs broken data)
- **Elimination tips (how to rule out wrong options):**
  - Reject "a model validated at launch stays accurate indefinitely."
  - Reject "retrain immediately and deploy without testing" as the answer to a drift alert.
  - Reject "drift only matters for accuracy"; check fairness, calibration, and business impact too.
  - Reject "no errors in the logs means the model is fine."
  - Reject "drift detection requires ground truth labels" (input and prediction monitoring work without them, though labels give the clearest view).
  - For **performance fell after a pipeline/schema change** → fix data quality and upstream change control; retraining on bad data makes it worse.
  - For **fraud or adversarial behaviour evolving** → think concept drift; frequent monitoring and retraining.
  - For **seasonal patterns** → include seasonality in monitoring baselines; do not mistake normal cycles for drift.
  - For **vendor LLM behaviour changed** → pin model versions where possible, run regression evaluations, have a rollback or fallback.
- **Frameworks / standards link:**
  - **EU AI Act:** High-risk providers must run a **post-market monitoring system** (Art. 72) and meet **accuracy and robustness** requirements across the lifecycle (Art. 15), including addressing **feedback loops** for systems that keep learning; **logging/record-keeping** supports detection and investigation (Art. 12); **deployers** must monitor operation according to instructions and act on risks (Art. 26); **serious incidents** must be reported (Art. 73). Obligations apply in phases, so verify the current dates.
  - **NIST AI RMF:** Post-deployment monitoring and response sit mainly in **Manage** (e.g., monitoring, incident response, decommissioning); **Measure** covers tracking system functionality and behaviour in production; "valid and reliable" is a trustworthy characteristic that drift undermines.
  - **ISO/IEC 42001:** **Performance evaluation** (monitoring, measurement, internal audit, management review) and **improvement** clauses require ongoing oversight; lifecycle controls cover change and version management.
  - **Model risk management (e.g., SR 11-7):** Expects **ongoing monitoring**, outcome analysis, and periodic revalidation of models.
  - **Governance angle:** Define monitoring metrics, thresholds, owners, response playbooks, and retraining/approval procedures before go-live, and keep evidence.

## 4. 🛠️ Real-World Use Cases
| # | Scenario | Industry | Drift type and how it appears | Outcome / risk |
|---|---|---|---|---|
| 1 | Fraud detection model misses new scam patterns | Banking / Payments | **Concept drift:** fraudsters adapt | Rising losses; needs frequent monitoring, retraining, analyst feedback |
| 2 | Demand forecast breaks after a market shock or pandemic | Retail / Supply chain | **Data and concept drift:** behaviour changes abruptly | Overstock or stockouts; needs re-baselining and human override |
| 3 | Credit model trained before a recession | Banking | **Label/concept drift:** default patterns change | Mispriced risk, regulatory scrutiny; needs revalidation |
| 4 | A data feed changes units or a field becomes null | Any | **Upstream/data quality drift** | Sudden, silent failure; needs data validation checks and change control |
| 5 | Clinical model deployed in a new hospital with different scanners | Healthcare | **Data drift** (population/equipment shift) | Lower accuracy for some patients; needs local validation and monitoring |
| 6 | Vendor updates the LLM behind a support bot | Cross-industry | **LLM version drift:** tone, refusals, formats change | Prompts regress; needs regression evals, version pinning, rollback |
| 7 | Policy documents change but the RAG index is not refreshed | Enterprise | **Knowledge staleness** | Bot gives outdated answers; needs content refresh process |

- **Consulting / assurance lens:**
  - Ask the client: "How do you know each model is still performing as validated today, who is alerted when it is not, and what happens next?"
  - Typical gaps: monitoring only infrastructure (uptime), not model quality; no thresholds; no owner; delayed ground truth ignored; retraining done ad hoc with no re-approval.
- **Evidence or controls you would look for:**
  - Monitoring plan per model: metrics, baselines, thresholds, frequency, and owners
  - Dashboards and alert logs showing drift and performance over time, including subgroup metrics
  - Data quality checks and schema/change control on upstream feeds
  - Retraining policy: triggers, data selection, validation, approval, and documentation
  - Version control, release records, and rollback procedures
  - Shadow/canary/champion-challenger testing results
  - Incident records and post-incident reviews
  - Periodic revalidation reports (independent for high-risk models)
  - For LLMs: regression evaluation suites, pinned versions or vendor-change notifications, content refresh schedule for RAG sources
  - Human-review fallback when confidence falls or alerts fire

## 5. Q&A Bank

### Quick recall
- **Q:** What is model drift?
  **A:** The decline in a deployed model's performance over time because the data or real-world relationships have changed since training.

- **Q:** What is the difference between data drift and concept drift?
  **A:** Data drift: the input distribution changes. Concept drift: the relationship between inputs and the target changes.

- **Q:** Is drift the same as overfitting?
  **A:** No. Overfitting is a training-time fit problem; drift appears after deployment as the world changes.

### Conceptual
- **Q:** Why is drift dangerous?
  **A:** It is usually silent: the system keeps running with no errors while decisions get steadily worse, potentially harming customers, finances, and compliance before anyone notices.

- **Q:** How can you detect drift when ground truth arrives late?
  **A:** Monitor input feature distributions (PSI, KS tests), prediction distributions, confidence, data quality, and proxy or business metrics, then confirm with direct performance measurement as outcomes arrive.

- **Q:** What are the typical responses to confirmed drift?
  **A:** Check and fix the data pipeline first; then recalibrate, retrain on recent data, rebuild the model, add human review, or roll back. Any new model must be validated and approved before release.

- **Q:** What are champion-challenger, shadow, and canary deployments?
  **A:** Safe release methods. Champion-challenger compares a new model against the current one on live data; shadow runs the new model silently alongside without affecting decisions; canary exposes the new model to a small share of traffic first.

- **Q:** What is a feedback loop and why does it matter for drift?
  **A:** When model outputs shape future data (e.g., only approved applicants produce repayment records), the data becomes skewed, which can hide drift and reinforce bias. It needs deliberate controls such as exploration samples, holdouts, and bias monitoring.

- **Q:** How does drift apply to LLM-based systems?
  **A:** Behaviour can change when the vendor updates or retires a model version, user prompts and topics shift, knowledge becomes stale after the cutoff, and retrieved content changes. Controls include version pinning, regression evaluations, content refresh, and monitoring of output quality.

### Scenario-based
- **Q:** A credit model's approval quality drops six months after launch; logs show no errors. What should be the first steps?
  **A:** Check for upstream data or schema changes first, compare current input and prediction distributions with the training baseline, measure performance on recent outcomes (including by subgroup), then decide whether to recalibrate, retrain, or roll back, with validation and approval before redeploying.

- **Q:** A retailer's forecasting model fails after an unexpected market event. Is retraining on last week's data enough?
  **A:** Not automatically. The shift may be abrupt and temporary or permanent. Assess the nature of the change, validate on recent and historical data, consider human overrides and wider uncertainty bands, and avoid overfitting to an unusual short period.

- **Q:** A vendor quietly updates the model behind your support chatbot and the formatting of answers breaks a downstream process. What should have been in place?
  **A:** Model version pinning or change notifications, a regression evaluation suite run on each version, output validation before downstream use, a rollback or fallback option, and vendor contract terms covering change notice.

- **Q:** Leadership asks, "We validated the model thoroughly before launch, so why do we need monitoring?" How do you respond?
  **A:** Validation only proves performance on past data. Real-world data changes, so performance can decay silently. Monitoring provides early warning, supports regulatory expectations for post-deployment oversight, and triggers maintenance before harm occurs.

### Interview-style
- **Q:** "Explain model drift to a non-technical executive."
  **A:** "An AI model learns from yesterday's data, but the world keeps changing, including customer behaviour, fraud tactics, and even our own data systems. Over time the model's answers quietly get less reliable, like a map that's slowly going out of date, and nothing flashes red when it happens. So we treat models like any critical asset: we measure their accuracy continuously, set alarm thresholds, assign owners, and refresh or roll back when needed. That protects customers and keeps us compliant."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Define baselines, metrics, thresholds, and owners before go-live | Deploy without a monitoring plan |
| Monitor inputs, predictions, data quality, and outcomes | Monitor only infrastructure uptime |
| Track subgroup performance and fairness metrics over time | Watch only overall accuracy |
| Use proxy metrics when ground truth is delayed | Wait for outcomes before looking at anything |
| Check upstream data and schema changes first when performance drops | Retrain on possibly corrupted data |
| Re-validate and re-approve models before redeploying | Push retrained models straight to production |
| Use shadow, canary, or champion-challenger release patterns | Swap models with no safe testing |
| Keep version control and a rollback path | Overwrite models without traceability |
| Account for seasonality in baselines | Treat normal seasonal swings as incidents (or ignore real drift) |
| For LLMs, pin versions, run regression evals, and refresh RAG content | Assume vendor models and knowledge stay constant |
| Document monitoring, incidents, and retraining decisions | Rely on informal knowledge held by one person |

- **Common mistakes / misconceptions:**
  1. "If it passed validation, it's safe." (Validation is a snapshot.)
  2. "No errors means no problem." (Drift is silent.)
  3. "Drift always means the model is bad." (The world changed; the model was fine for the old world.)
  4. "More frequent retraining always fixes it." (Bad data, feedback loops, or unvalidated updates can make things worse.)
  5. "Drift monitoring needs labels." (Input and output monitoring work earlier, labels confirm.)
  6. "Drift only affects predictive ML." (LLM systems drift through vendor updates, prompts, and stale content.)
- **Red flags in practice:**
  - No owner or thresholds for model performance
  - Monitoring shows only system health, not model quality
  - Validation documents dated years ago with no revalidation
  - Retraining done ad hoc with no approval or testing
  - Delayed outcomes ignored, so no one knows current accuracy
  - Vendor model changes discovered by customer complaints
  - Feedback loops unexamined (e.g., only approved cases used as training data)

## 7. Revision Snapshot
- **30-second summary:**
  Model drift is the post-deployment decline in a model's performance because the data or the real-world relationships it learned have changed. Types: data drift (inputs change), concept drift (input-output relationship changes), and label drift (target mix changes), plus upstream data-quality breaks and, for LLMs, vendor version changes and stale knowledge. It is silent, so organisations monitor inputs, predictions, data quality, and outcomes (PSI, KS tests, performance and subgroup metrics), with proxy metrics while ground truth is delayed. Responses: check the pipeline, then retrain, recalibrate, rebuild, add human review, or roll back, always with re-validation, safe release, and version control. Monitoring is a governance requirement under NIST AI RMF (Manage), EU AI Act post-market monitoring, ISO 42001 performance evaluation, and model risk management.
- **3 bullets to recall on exam day:**
  1. Data drift = inputs change; concept drift = relationship changes; label drift = target mix changes; drift ≠ overfitting
  2. Silent decay → monitor inputs, outputs, quality, and outcomes (with subgroups); use proxy metrics when labels are late
  3. Response = check pipeline → retrain/fix/roll back → re-validate and approve; LLMs drift via vendor updates and stale content
