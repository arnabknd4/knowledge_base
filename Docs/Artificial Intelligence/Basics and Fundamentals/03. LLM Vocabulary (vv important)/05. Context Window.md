## 1. Learn It (Core Understanding)
- **One-line definition:** The context window is the maximum amount of text, measured in tokens, that an LLM can consider at one time, covering the prompt, conversation history, any supplied documents, and the model's own output.
- **Plain-English explanation (3-4 lines):**
  Think of the context window as the model's working desk. Everything it needs for the current answer (your instructions, the chat so far, pasted documents, retrieved snippets, and the reply it is writing) must fit on that desk. Anything that does not fit is invisible to the model. It does not "remember" earlier conversations on its own; if something is not in the window, the model does not have it. Window sizes vary widely by model and keep growing, so always check the vendor's current documentation.
- **Why it exists / problem it solves:**
  - Attention compares tokens with each other, so compute and memory grow quickly as input length grows; a fixed limit keeps the model practical to train and run
  - Gives a clear boundary for what the model can "see" in a single request
  - Makes it possible to give a general model task-specific information at query time (documents, examples, instructions) without retraining
- **Key terms to know:**
  - **Context window (context length):** Maximum tokens the model can process in one request (input + output)
  - **Token:** The unit the window is measured in
  - **Input / prompt tokens:** System prompt, user messages, history, documents, tool results
  - **Output (completion) tokens:** The tokens the model generates; counted against the window, and often also capped separately by a **max output tokens** setting
  - **Context budget:** How you split the window between instructions, history, documents, and room for the answer
  - **Truncation:** Cutting off content that does not fit (oldest or excess text is dropped, or the request is rejected)
  - **Conversation history / state:** Previous turns that the application re-sends each time; the model itself is stateless between requests
  - **Summarisation / compaction:** Condensing older content so it takes fewer tokens
  - **Chunking:** Splitting long documents into pieces that fit
  - **RAG:** Retrieving only relevant chunks to place in the window instead of everything
  - **Prompt caching:** Reusing a repeated prompt prefix to cut cost and latency
  - **Lost in the middle:** Models often use information at the start and end of a long context better than information buried in the middle
  - **Context rot / degradation:** Quality can decline as the window fills with long or noisy content
  - **Needle-in-a-haystack test:** Benchmark that checks whether a model can find a specific fact in a long context
  - **Reasoning (thinking) tokens:** In reasoning-style models, intermediate thinking tokens may count toward usage and limits, depending on the model
  - **Memory (application feature):** Stored notes or history that an app injects into the window; not the model's weights
- **How it works (simple steps):**
  1. **Assemble:** The application builds the request: system prompt + conversation history + documents/retrieved text + the new user message.
  2. **Count:** Everything is tokenised; the total input plus the room reserved for output must fit within the window.
  3. **Process:** The transformer attends over all tokens in the window to generate the next token.
  4. **Generate:** Each output token is added to the window as the answer is produced.
  5. **Overflow handling:** If the limit would be exceeded, the application (or API) truncates, summarises, or rejects the request.
  6. **Next turn:** The application re-sends the needed history; the model starts fresh each time with whatever is in the window.
- **Where it sits in the AI stack:** Model/application boundary. It is a model property (architecture and training) that shapes application design (memory, RAG, document handling, cost).

## 2. Mental Model
- **Analogy:** A **desk of fixed size**. Your instructions, the ongoing conversation, reference documents, and the answer being written all have to fit on it. When the desk is full, something must come off (older pages get dropped, or you summarise them into a short note). The model can only work with what is physically on the desk right now, and it tends to notice papers at the top and bottom of the pile more than those buried in the middle. A bigger desk helps, but a cluttered desk is still hard to work at.
- **Diagram / flow:**
```
  ┌──────────────────── CONTEXT WINDOW (token budget) ────────────────────┐
  │ System prompt │ History │ Documents / RAG chunks │ User msg │ OUTPUT  │
  │ (instructions)│ (turns) │ (grounding data)       │ (new ask)│ (reply) │
  └───────────────────────────────────────────────────────────────────────┘
      input tokens  ───────────────────────────────────►  + output tokens
                                ≤ context window

  If it doesn't fit:   truncate  |  summarise/compact  |  retrieve less (RAG)  |  reject
  Model memory between requests: none, the app must re-send what matters
```
```
  Attention strength across a very long context (typical tendency):
  start ▇▇▇▇  middle ▂▂▂ (weaker)  end ▇▇▇▇
```
- **The one thing to remember:** If it is not in the context window, the model cannot see it, and the window is a shared budget for input plus output.
- **Compare and contrast:**

  | | Context window | Training data | Parameters / weights |
  |---|---|---|---|
  | What it is | What the model sees right now | What the model learned from earlier | Where learned patterns are stored |
  | Changes per request? | Yes | No | No |
  | Limit | Max tokens per request | Fixed at training time | Fixed after training |
  | Used for | Instructions, documents, conversation, answer | General knowledge and language ability | The model itself |

  | | Bigger context window | RAG (retrieval) |
  |---|---|---|
  | Approach | Put everything in the window | Retrieve only the relevant pieces |
  | Cost and latency | Higher with more tokens | Lower per request, but adds a retrieval step |
  | Risk | Noise, lost-in-the-middle, higher cost, more data exposed to the model | Retrieval may miss relevant content |
  | Best for | Tasks needing the whole document at once | Large knowledge bases, frequently updated data |

  | | Context window | Application "memory" feature |
  |---|---|---|
  | Who stores it | The request itself (temporary) | The application (persistent store) |
  | How it reaches the model | It is the input | The app selects notes and injects them into the window |
  | Scope | One request/conversation | Across sessions, under app and vendor rules |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / Scenario (overflow, cost, lost instructions) / Compare (window vs RAG vs training) / Best-fix / Pick-the-risk
- **Must-memorize facts:**
  - [ ] Context window = max **tokens** the model can handle at once, **input + output combined**
  - [ ] Content outside the window is **invisible** to the model
  - [ ] The model is **stateless** between requests; apps re-send history to simulate memory
  - [ ] Overflow leads to **truncation or rejection**, which can silently drop instructions or evidence
  - [ ] Longer context = higher **cost and latency**
  - [ ] Bigger window ≠ perfect recall: **lost in the middle** and context degradation are real
  - [ ] The window is **not** the model's knowledge (training data) and **not** its parameters
  - [ ] Ways to manage long content: **chunking, summarisation, RAG, prompt caching, trimming history**
  - [ ] Output tokens also consume the window; there is usually a separate **max output** cap
  - [ ] Everything placed in the window (including pasted documents and retrieved data) is **sent to the model provider**, so data-protection rules apply
  - [ ] Untrusted content in the window (web pages, emails, documents) can carry **prompt injection**
  - [ ] Window sizes differ by model and change over time, so check current vendor documentation
- **Keywords that signal this topic in a question:** "token limit," "maximum input length," "truncated," "forgot earlier instructions," "long document," "conversation history," "lost in the middle," "memory," "cost per request"
- **Commonly confused with:**
  - Context window vs training data (seen now vs learned before)
  - Context window vs memory (temporary input vs stored information the app injects)
  - Context window vs parameters
  - Context window vs max output tokens
  - Bigger window vs better accuracy
  - Fine-tuning (changes weights) vs putting information in the window (temporary)
- **Elimination tips (how to rule out wrong options):**
  - Reject "the model remembers everything from earlier conversations by default."
  - Reject "the window only limits the prompt"; output counts too.
  - Reject "a larger window guarantees the model uses all information accurately."
  - Reject "adding information to the prompt permanently teaches the model"; it is temporary and leaves the weights unchanged.
  - For "answer questions from a large, changing knowledge base" → **RAG**, not stuffing everything in the window or retraining each time.
  - For "chatbot ignores early rules in a long chat" → window overflow or dilution; restate key instructions, summarise history, pin the system prompt.
  - For "reduce cost of repeated long prompts" → prompt caching, shorter context, retrieval.
- **Frameworks / standards link:**
  - **NIST AI 600-1 (Generative AI Profile) and AI RMF:** Context handling relates to confabulation and information integrity (missing or truncated context leads to wrong answers), data privacy (what enters the window), and information security (prompt injection through untrusted content).
  - **EU AI Act:** No rule about context length itself. Relevant obligations are use-case-based: accuracy and robustness, human oversight, data governance, and transparency for systems built on LLMs, plus GPAI provider documentation duties.
  - **ISO/IEC 42001:** Operational controls, monitoring, and data management cover how context is assembled, what data enters prompts, and how performance is monitored.
  - **Privacy link:** Personal or confidential data in prompts, history, or retrieved documents is processed by the model provider; apply data minimisation, retention limits, and vendor terms.
  - **Governance angle:** Control what goes into the window (classification, access rights, filtering), because it determines both answer quality and data exposure.

## 4. 🛠️ Real-World Use Cases
| # | Scenario | Industry | How this topic applies | Outcome / risk |
|---|---|---|---|---|
| 1 | Summarising a long contract or audit file | Legal / Audit | Document must fit the window or be chunked | Truncation can drop critical clauses |
| 2 | Customer-support chatbot with long conversations | Retail / Banking | History is re-sent each turn and grows | Early rules forgotten; cost rises over the session |
| 3 | Enterprise Q&A over thousands of policies | Enterprise | RAG selects a few relevant chunks for the window | Accurate and cheaper if retrieval works; misses if it does not |
| 4 | Coding assistant reading a large codebase | Software | Relevant files placed in context | Better suggestions; irrelevant files add noise and cost |
| 5 | AI agent reading emails and web pages | Operations / IT | Untrusted content enters the window | Indirect prompt injection; needs isolation and least privilege |
| 6 | Repeated long system prompt across millions of calls | Cross-industry | Prompt caching reuses the stable prefix | Lower cost and latency; requires careful prompt design |

- **Consulting / assurance lens:**
  - Ask the client: "What goes into the model's context for each request, who controls it, and what happens when it gets too long?"
  - Weak context design shows up as wrong answers, cost overruns, and data exposure, not just technical inefficiency.
- **Evidence or controls you would look for:**
  - Documented design of how prompts are assembled (system prompt, history, retrieved data)
  - Handling for overflow (chunking, summarisation, user notification) and tests of it
  - Tests that critical instructions still hold in long conversations
  - Access controls so retrieval respects user permissions (no pulling documents the user should not see)
  - Data classification and filtering rules for what may enter prompts
  - Controls against prompt injection from untrusted content (separation, filtering, human approval for sensitive actions)
  - Usage and cost monitoring, retention terms for logged prompts

## 5. Q&A Bank

### Quick recall
- **Q:** What is a context window?
  **A:** The maximum number of tokens an LLM can consider at once, including both input and output.

- **Q:** What happens to text that does not fit in the context window?
  **A:** It is truncated or the request is rejected, and the model cannot see it.

- **Q:** Does an LLM remember previous conversations by default?
  **A:** No. It is stateless between requests; applications re-send history or inject stored memory.

### Conceptual
- **Q:** Does a larger context window always give better results?
  **A:** No. It lets you include more, but cost and latency rise, and models can still miss information in the middle of long inputs or be distracted by irrelevant content.

- **Q:** How is the context window different from the model's training data?
  **A:** Training data shaped the model's weights earlier and is not directly visible at run time. The context window holds the specific information supplied for the current request, and it disappears after the request.

- **Q:** How do RAG and a large context window differ as ways to give the model information?
  **A:** A large window lets you supply a lot of text directly. RAG retrieves only the most relevant pieces for each query, which scales to big, changing knowledge bases at lower cost, but depends on retrieval quality.

- **Q:** What is "lost in the middle"?
  **A:** A tendency for models to use information at the beginning and end of a long context better than information in the middle, so important facts should be placed and structured carefully.

- **Q:** Why does context matter for security?
  **A:** Everything in the window influences the model. Untrusted content (web pages, emails, documents) can contain hidden instructions (prompt injection), and sensitive data in the window is processed by the provider.

### Scenario-based
- **Q:** A chatbot follows its rules at first but ignores them 40 messages later. What is likely happening and how would you fix it?
  **A:** The conversation is filling or overflowing the window, so early instructions are dropped or diluted. Fix by pinning the system prompt, summarising older turns, restating critical rules, and testing long sessions.

- **Q:** A firm wants an assistant to answer questions over 50,000 internal documents. Should it just paste everything into the prompt?
  **A:** No. That will not fit and would be costly and noisy. Use RAG to retrieve the relevant passages, enforce access permissions in retrieval, and verify answers against sources.

- **Q:** A summarisation tool sometimes omits sections of long reports without any error. What should an assurance professional check?
  **A:** Whether inputs are being silently truncated. Check token counts against the limit, add overflow handling (chunking or map-reduce summarisation), alert users when content is cut, and test with documents near and above the limit.

- **Q:** An email-reading AI agent forwards confidential files after reading a message containing hidden instructions. What happened?
  **A:** Indirect prompt injection: untrusted content in the context window was treated as instructions. Reduce the risk with least-privilege tool access, human approval for sensitive actions, separating trusted instructions from untrusted content, and monitoring.

### Interview-style
- **Q:** "Explain the context window to a non-technical executive."
  **A:** "It's the AI's working desk. Everything it needs for a given answer, your instructions, the conversation so far, any documents, and the reply it writes, has to fit on that desk. If something doesn't fit, the AI simply can't see it, and it doesn't keep anything between requests unless the software re-supplies it. A bigger desk helps, but it's still possible for it to overlook things in a huge pile, and everything we put on it is data we're sharing with the provider. So we decide carefully what goes in and check the answers."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Plan the token budget: instructions + history + documents + room for output | Fill the window with input and leave no space for the answer |
| Use RAG, chunking, or summarisation for large content | Paste entire large documents and assume they were fully used |
| Alert users when input is truncated | Let content be dropped silently |
| Keep critical instructions in the system prompt and restate them in long chats | Assume early instructions persist indefinitely |
| Put the most important information where models attend well (start or end) | Bury key facts in the middle of a huge prompt |
| Enforce access controls on retrieved content | Let retrieval pull documents a user is not entitled to see |
| Treat untrusted content in the window as potentially hostile | Mix untrusted text with trusted instructions without safeguards |
| Monitor token usage and cost per request | Assume longer context is free |
| Check each model's current window size in vendor documentation | Rely on outdated or remembered limits |

- **Common mistakes / misconceptions:**
  1. "The model remembers our past conversations." (Not unless the app supplies them.)
  2. "A bigger window means perfect recall." (Quality can still degrade.)
  3. "The window limits only the prompt." (It includes output.)
  4. "Putting a document in the prompt trains the model on it." (Temporary; weights are unchanged.)
  5. "Context window and memory are the same." (Memory is an app feature that feeds into the window.)
- **Red flags in practice:**
  - No overflow handling or user notification
  - Long-session behaviour never tested
  - Retrieval that ignores user permissions
  - Untrusted documents or web pages passed straight into an agent's context
  - No cost monitoring for long-context workloads
  - Vendor context limits assumed, not verified
