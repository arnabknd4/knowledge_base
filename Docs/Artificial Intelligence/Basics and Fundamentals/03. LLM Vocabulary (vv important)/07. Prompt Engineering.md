## 1. Learn It (Core Understanding)
- **One-line definition:** Prompt engineering is the practice of designing, testing, and refining the instructions, context, and examples given to an LLM so that it produces accurate, consistent, and useful outputs for a specific task.
- **Plain-English explanation (3-4 lines):**
  An LLM responds to exactly what it is given, so wording, structure, and context change the result. Prompt engineering is about giving the model what a smart new colleague would need: a clear task, the relevant background, the constraints, the format you want, and examples of good output. It is iterative: write, test on realistic cases, see where it fails, adjust. It works on the input only, so it does not change the model's weights, and it cannot add knowledge the model lacks (that needs RAG or other data sources).
- **Why it exists / problem it solves:**
  - LLM output is sensitive to phrasing, so unmanaged prompting gives inconsistent and unreliable results
  - It is the fastest and cheapest way to adapt a general model to a task (no training, no extra infrastructure)
  - Turns one-off chatting into repeatable, testable, governable workflows
- **Key terms to know:**
  - **Prompt engineering:** Designing and iterating prompts to improve output quality and reliability
  - **Zero-shot prompting:** Give the task with no examples
  - **One-shot / few-shot prompting:** Include one or several worked examples in the prompt (in-context learning)
  - **Chain-of-thought (CoT):** Ask the model to reason step by step before answering; helps on multi-step problems
  - **Self-consistency:** Sample several reasoning paths and pick the most common answer
  - **Role prompting:** Assign a persona or expertise ("You are a risk auditor...")
  - **Prompt chaining:** Break a big task into a sequence of smaller prompts, with each output feeding the next
  - **Task decomposition:** Splitting a complex task into simpler sub-tasks
  - **ReAct (reason + act):** Pattern where the model alternates reasoning with tool calls (basis of many agents)
  - **Delimiters / structure tags:** Markers (quotes, headings, XML-style tags) that separate instructions from data
  - **Structured output:** Requiring a fixed format (JSON, table, schema) so software can consume the result
  - **Constraints:** Explicit limits on scope, length, tone, sources, or what to avoid
  - **Grounding instruction:** "Answer only from the provided text; say 'not found' if missing"
  - **Prompt template:** Reusable prompt with placeholders filled at run time
  - **Meta-prompting:** Using an LLM to draft or improve prompts
  - **Prompt versioning and evals:** Tracking prompt changes and testing them against a fixed set of cases
  - **Prompt brittleness:** Small wording changes causing large output changes
  - **Temperature (related setting):** Controls randomness; low for consistency, higher for variety
- **How it works (simple steps):**
  1. **Define success:** What does a good output look like? (accuracy, format, tone, length)
  2. **Draft the prompt:** Role (optional), context, task, constraints, output format, examples.
  3. **Test on realistic cases:** Include normal, edge, and adversarial inputs, not just one happy path.
  4. **Diagnose failures:** Missing context? Ambiguous instruction? No example? Wrong format? Task too big?
  5. **Refine:** Clarify, add examples, add structure, split into steps, adjust settings (e.g., temperature).
  6. **Lock and govern:** Version the prompt, record test results, monitor in production, and re-test after any model or prompt change.
- **Where it sits in the AI stack:** Application layer, the first and lowest-cost customisation lever, before RAG and fine-tuning.

## 2. Mental Model
- **Analogy:** **Briefing a capable but literal new hire.** If you say "write something about our audit findings," you get a generic result. If you say who the audience is, what the findings are, what tone to use, what format you need, and show one good example, you get something useful. The hire is fast and knowledgeable but has no access to your unstated context and will confidently fill gaps with guesses. Good prompt engineering removes the gaps.
- **Diagram / flow:**
```
  A STRONG PROMPT (building blocks)
  ┌──────────────────────────────────────────────┐
  │ 1. Role / context     who, for whom, why     │
  │ 2. Task               the specific ask       │
  │ 3. Input data         delimited clearly      │
  │ 4. Constraints        scope, tone, length,   │
  │                       "use only provided text"│
  │ 5. Output format      JSON / table / steps   │
  │ 6. Examples           few-shot good outputs  │
  └──────────────────────────────────────────────┘

  THE LOOP
  Define success → Draft → Test (normal + edge + adversarial) → Diagnose → Refine
        ▲                                                                   │
        └──────── version, monitor, re-test after model/prompt changes ◄────┘
```
- **The one thing to remember:** Be clear, specific, and structured, then test and iterate. Prompts guide the model but cannot add missing knowledge or guarantee correctness.
- **Compare and contrast:**

  | | Zero-shot | Few-shot | Chain-of-thought |
  |---|---|---|---|
  | What you give | Instruction only | Instruction + examples | Instruction + ask for step-by-step reasoning |
  | Best for | Simple, common tasks | Format or style consistency, unusual tasks | Multi-step reasoning, math, logic |
  | Cost | Lowest | More tokens | More output tokens |
  | Caution | May misread intent | Examples can bias or be copied too literally | Reasoning shown is not proof of correctness |

  | | Prompt engineering | RAG | Fine-tuning |
  |---|---|---|
  | Changes | How you ask | What facts the model sees | The model's weights |
  | Adds new knowledge? | No | Yes (at query time) | Partly (style, patterns, some knowledge) |
  | Effort and cost | Lowest | Medium | Highest |
  | Try it | First | When facts are missing or change | When prompting and RAG are not enough |

  | | Vague prompt | Engineered prompt |
  |---|---|---|
  | Example | "Summarise this report." | "Summarise for a CFO in 5 bullets, focus on financial risks, cite section numbers, say 'not stated' if unclear." |
  | Result | Generic, inconsistent | Targeted, repeatable, checkable |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / Match-technique-to-scenario / Compare (prompting vs RAG vs fine-tuning) / Best-fix for bad output / Pick-the-risk
- **Must-memorize facts:**
  - [ ] Prompt engineering improves outputs by changing the **input**, not the model's weights
  - [ ] Core elements: **clear task, context, constraints, output format, examples**
  - [ ] Techniques: **zero-shot, one-shot, few-shot, chain-of-thought, role prompting, prompt chaining/decomposition, structured output, ReAct**
  - [ ] Few-shot = **in-context learning** (temporary, no weight change)
  - [ ] Chain-of-thought helps on **multi-step reasoning**, but shown reasoning does not guarantee a correct answer
  - [ ] Prompt engineering **cannot fix missing or outdated knowledge**; use **RAG** for facts, and verify outputs
  - [ ] Lower **temperature** improves consistency; it does not guarantee accuracy
  - [ ] Outputs are **probabilistic and brittle**: small prompt changes can change results, so **test, version, and re-test** (including after model upgrades)
  - [ ] Put untrusted data in **delimited sections** and instruct the model to treat it as data, but this **does not fully stop prompt injection**
  - [ ] Customisation order: **prompting → RAG → fine-tuning**
  - [ ] Include **edge and adversarial cases** in prompt testing, and use a **fixed evaluation set** to compare versions
  - [ ] Prompts and context consume **tokens**, so longer prompts raise cost and latency
  - [ ] Staff skills matter: **AI literacy** of people writing and using prompts is a governance item
- **Keywords that signal this topic in a question:** "examples in the prompt," "step by step," "persona," "output format," "template," "inconsistent responses," "rewrite the instructions," "reduce hallucination without retraining," "prompt library"
- **Commonly confused with:**
  - Prompt engineering vs fine-tuning (input change vs weight change)
  - Prompt engineering vs RAG (how you ask vs what facts you supply)
  - System prompt vs prompt engineering (one component vs the overall practice)
  - Few-shot prompting vs training (in-context only)
  - Prompt engineering vs guardrails (wording vs enforced controls)
  - Temperature tuning vs prompt design
- **Elimination tips (how to rule out wrong options):**
  - Reject "prompt engineering adds new knowledge to the model permanently."
  - Reject "a perfect prompt guarantees no hallucinations."
  - Reject "few-shot examples retrain the model."
  - Reject "one successful test proves the prompt is reliable."
  - Reject "just make the prompt longer" as a universal fix; clarity and structure matter more than length.
  - For **missing or current company facts** → RAG/grounding, not prompt tweaks alone.
  - For **inconsistent format** → explicit format, examples, structured output, lower temperature.
  - For **complex multi-step tasks failing** → decompose or chain prompts, and ask for step-by-step reasoning.
  - For **security** (injection, data exposure) → enforced controls plus testing, not wording alone.
- **Frameworks / standards link:**
  - **NIST AI 600-1 (Generative AI Profile):** Pre-deployment testing, red teaming, and monitoring cover prompt-related risks (confabulation, prompt injection, harmful content); prompts and configuration are part of the system to be mapped and measured.
  - **NIST AI RMF:** Change control and documentation for prompts fall under Govern and Manage; testing prompts against representative and adversarial cases falls under Measure.
  - **EU AI Act:** Prompts are not regulated directly. Relevant duties are use-case based (human oversight, accuracy, robustness, transparency). The **AI literacy obligation (Article 4)** expects providers and deployers to ensure staff have sufficient AI literacy, which includes competent, responsible prompting. Check current application dates and guidance.
  - **ISO/IEC 42001:** Competence, documented information, change management, and operational controls support trained users and versioned, approved prompts.
  - **Governance angle:** Treat production prompts as controlled configuration: owned, reviewed, tested, versioned, and monitored, with training for the people who write them.

## 4. 🛠️ Real-World Use Cases
| # | Scenario | Industry | How this topic applies | Outcome / risk |
|---|---|---|---|---|
| 1 | Extracting key fields from contracts into JSON | Legal / Finance | Clear schema, few-shot examples, "say null if absent" | Reliable automation; errors need validation before use |
| 2 | Drafting audit or client reports in a house style | Consulting / Audit | Role, audience, tone, template, and examples | Faster drafting with consistent quality; facts still need human verification |
| 3 | Support chatbot answering only from approved documents | Banking / Retail | Grounding instruction + RAG + "cite source or say unknown" | Fewer made-up answers; still needs testing |
| 4 | Multi-step analysis (extract → classify → summarise) | Operations | Prompt chaining with validation between steps | More accurate than one giant prompt; more steps to monitor |
| 5 | Team prompt library for common tasks | Cross-industry | Reviewed, versioned templates | Consistency and efficiency; risk if templates are unreviewed or embed sensitive data |
| 6 | Model upgrade changes behaviour of existing prompts | Any | Prompts tuned to one model version | Regressions; needs re-testing against a fixed evaluation set |

- **Consulting / assurance lens:**
  - Ask the client: "Who writes and approves the prompts behind your AI use cases, and how do you know they still work after a model update?"
  - Mature practice shows test sets, version control, and training; immature practice shows ad hoc prompts pasted from colleagues.
- **Evidence or controls you would look for:**
  - Prompt inventory with owners, versions, and change history
  - Evaluation set and results per prompt version, including edge and adversarial cases
  - Regression testing after model or prompt changes
  - Approved templates for high-impact use cases
  - Guidance and training for staff on effective and safe prompting (what data must not be entered)
  - Output validation (schema checks, human review) for high-impact uses
  - Monitoring of output quality and drift in production

## 5. Q&A Bank

### Quick recall
- **Q:** What is prompt engineering?
  **A:** Designing and refining the instructions, context, and examples given to an LLM to get better, more consistent outputs.

- **Q:** What is few-shot prompting?
  **A:** Including a few worked examples in the prompt so the model follows the demonstrated pattern or format.

- **Q:** Does prompt engineering change the model?
  **A:** No. It only changes the input for that request.

### Conceptual
- **Q:** What are the main elements of an effective prompt?
  **A:** A clear task, relevant context, constraints (scope, tone, length), a specified output format, and examples where helpful, with input data clearly separated.

- **Q:** When does chain-of-thought prompting help, and what is its limit?
  **A:** It helps on multi-step reasoning by making the model work through intermediate steps. The limit: fluent reasoning can still lead to a wrong answer, and it adds output tokens and cost.

- **Q:** Why break a complex task into a chain of prompts?
  **A:** Smaller, focused steps are easier to get right, easier to test and debug, and allow validation between steps.

- **Q:** When is prompt engineering not enough?
  **A:** When the model lacks the needed facts (use RAG), needs a consistently specialised behaviour at scale (consider fine-tuning), or when security and compliance require enforced controls rather than instructions.

- **Q:** Why must prompts be tested and versioned?
  **A:** Outputs are probabilistic and sensitive to wording, and model updates can change behaviour. Testing against a fixed evaluation set and tracking versions catches regressions and supports accountability.

### Scenario-based
- **Q:** A model returns summaries in a different format each time, breaking a downstream system. What is the best fix?
  **A:** Specify the exact output format or schema, add examples, use structured-output features, lower the temperature, and validate outputs automatically before passing them on.

- **Q:** A chatbot invents policy details that are not in the company documents. Will rewording the prompt fix this?
  **A:** Partly at best. Ground it with RAG over the approved documents, instruct it to answer only from the provided text and say "not found" otherwise, require citations, test against known questions, and keep human review for high-impact cases.

- **Q:** A prompt works well in testing but produces poor results after the vendor updates the model. What should the team have had in place?
  **A:** A fixed evaluation set and regression tests run on each model or prompt change, version control of prompts, and a rollback plan.

- **Q:** Employees share their own favourite prompts informally, some containing client names. What should the organisation do?
  **A:** Create reviewed, approved prompt templates, set data-handling rules for prompts (no client-identifying or confidential data in unapproved tools), provide training, and monitor use.

### Interview-style
- **Q:** "Explain prompt engineering to a non-technical executive."
  **A:** "It's the skill of briefing an AI clearly, much like briefing a smart new hire. The more precisely we say who the audience is, what we need, what to avoid, and what a good answer looks like, the better and more consistent the result. It's the cheapest way to improve AI output, but it isn't magic: it can't supply facts the AI doesn't have, and it doesn't make the answers automatically correct. So we test our prompts, keep them under version control, train our people, and still have humans check the important outputs."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Define what a good output looks like before writing the prompt | Start prompting without success criteria |
| Be specific about task, audience, constraints, and format | Use vague one-line requests for important work |
| Provide examples for format or style consistency | Assume the model will infer your preferred format |
| Separate instructions from input data with clear delimiters | Mix untrusted text and instructions together |
| Split complex work into steps or chained prompts | Cram a long multi-part task into one prompt |
| Tell the model what to do when information is missing ("say unknown") | Leave gaps the model will fill with guesses |
| Test on normal, edge, and adversarial cases; keep a fixed evaluation set | Judge a prompt from a single good output |
| Version, review, and re-test prompts after model changes | Change production prompts ad hoc |
| Train staff and set rules on what data may go into prompts | Let staff paste confidential data into unapproved tools |
| Verify outputs and keep humans in the loop for high-impact uses | Treat a well-crafted prompt as proof of correctness |

- **Common mistakes / misconceptions:**
  1. "A better prompt removes hallucinations." (It reduces them; grounding and verification are still needed.)
  2. "Prompt engineering teaches the model new facts." (Only RAG or supplied context does, temporarily.)
  3. "Longer prompts are always better." (Clarity and relevance beat length; length costs tokens.)
  4. "If it worked once, it's reliable." (Outputs vary; test repeatedly.)
  5. "Prompts are a security control." (They are a soft control; enforce security outside the model.)
  6. "A prompt tuned for one model works the same on every model." (Behaviour differs by model and version.)
- **Red flags in practice:**
  - No inventory, owner, or version history for production prompts
  - No evaluation set or regression testing
  - Prompts copied between staff with no review
  - Confidential or client data embedded in shared prompts
  - Reliance on wording alone to prevent harmful or off-scope behaviour
  - No re-testing after model upgrades

## 7. Revision Snapshot
- **30-second summary:**
  Prompt engineering is the iterative practice of writing clear, structured inputs (task, context, constraints, format, examples) so an LLM gives accurate and consistent outputs. Key techniques: zero/few-shot, chain-of-thought, role prompting, prompt chaining, delimiters, and structured output. It changes the input only, cannot add missing knowledge (use RAG) and cannot guarantee correctness. Because outputs are probabilistic and brittle, prompts must be tested on realistic and adversarial cases, versioned, re-tested after model changes, and backed by real controls, human review, and trained users.
- **3 bullets to recall on exam day:**
  1. Clear task + context + constraints + format + examples; iterate and test
  2. Prompting changes input only: no new knowledge (RAG), no retraining (fine-tuning); order is prompting → RAG → fine-tuning
  3. Govern it: evaluation sets, versioning, regression tests after model changes, staff training, human review
