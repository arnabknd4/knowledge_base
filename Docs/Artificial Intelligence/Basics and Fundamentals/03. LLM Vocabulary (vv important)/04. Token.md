## 1. Learn It (Core Understanding)
- **One-line definition:** A token is the basic unit of text (a whole word, part of a word, a punctuation mark, or a space) that an LLM reads and writes; models process text as sequences of tokens, and usage limits and costs are measured in tokens.
- **Plain-English explanation (3-4 lines):**
  An LLM cannot read letters or words directly. A tokenizer first chops the text into pieces from a fixed vocabulary, and each piece is mapped to a number (a token ID). Common words are often one token ("the"), while rare or long words are split into several ("unbelievably" → "un" + "believ" + "ably"). The model takes in tokens, predicts the next token, and repeats. As a rough English rule of thumb, 1 token ≈ 4 characters ≈ ¾ of a word.
- **Why it exists / problem it solves:**
  - Models need numeric input of a manageable, fixed vocabulary size
  - Whole-word vocabularies would be huge and could not handle new or misspelled words; letter-by-letter would make sequences too long
  - Sub-word pieces balance both: a compact vocabulary that can still represent any text
- **Key terms to know:**
  - **Token:** One unit of text in the model's vocabulary
  - **Tokenizer:** The component that splits text into tokens and converts them to IDs (and back)
  - **Vocabulary:** The fixed set of tokens a model knows (often tens or hundreds of thousands)
  - **Token ID:** The number that represents a token
  - **Sub-word tokenization:** Splitting text into pieces smaller than words (common methods: BPE, WordPiece, SentencePiece)
  - **BPE (Byte Pair Encoding):** Builds the vocabulary by repeatedly merging the most frequent character pairs
  - **Special tokens:** Reserved tokens with structural meaning (start/end of text, role markers in chat)
  - **Input (prompt) tokens vs output (completion) tokens:** What you send vs what the model generates; often priced differently, with output usually costing more
  - **Context window:** Maximum tokens the model can handle at once (input + output combined)
  - **Max output tokens:** Cap on how long a single response can be
  - **Token count / usage:** Number of tokens processed; drives cost, latency, and limits
  - **Embedding:** Numeric vector that represents each token's meaning (the next step after tokenization)
  - **Rate limit (tokens per minute):** Vendor cap on how many tokens you can send or receive over time
  - **Token inflation:** Some languages, code, numbers, or unusual text break into more tokens, so the same content costs more and uses more context
- **How it works (simple steps):**
  1. **Tokenize:** The tokenizer splits the text into tokens and maps each to an ID.
  2. **Embed:** Each token ID becomes a vector the model can process.
  3. **Process:** The transformer uses attention across the tokens in the context window.
  4. **Predict:** The model outputs probabilities for the next token and picks one (temperature affects the choice).
  5. **Repeat:** The new token is appended and the loop continues until the response ends or hits the output limit.
  6. **Detokenize:** The output token IDs are converted back into readable text.
- **Where it sits in the AI stack:** Input/output layer of the model. It is the unit that connects raw text to the transformer, and the unit that cost, limits, and context are measured in.

## 2. Mental Model
- **Analogy:** **LEGO bricks for language.** Instead of carving each word from scratch, the model builds every text from a fixed set of standard bricks. Common words are one big brick, rare words are assembled from several small bricks. The model reads and builds text brick by brick, and the vendor charges (and limits you) by the number of bricks, not by the number of words.
- **Diagram / flow:**
```
  "Tokenization matters"
          │  tokenizer
          ▼
  ["Token", "ization", " matters"]      ← sub-word pieces
          │  vocabulary lookup
          ▼
  [ 4421,   2860,      8326 ]            ← token IDs
          │  embeddings
          ▼
  [ vectors ] ──► Transformer ──► next-token probabilities
                                        │
                      sample → new token ID → append → repeat
                                        ▼
                  token IDs → detokenize → readable text

  Context window = input tokens + output tokens (shared budget)
```
- **The one thing to remember:** Models think and get billed in **tokens, not words**; the context window is a shared token budget for input plus output.
- **Compare and contrast:**

  | | Token | Word | Character |
  |---|---|---|---|
  | What it is | Model's unit of text (often a word piece) | Human-readable unit | Single letter or symbol |
  | Used by | LLMs, for processing, limits, and billing | Humans | Sometimes for rough estimates |
  | English ratio | ~1 token ≈ ¾ word ≈ 4 characters | 1 word ≈ 1.3 tokens | 1 character ≈ 0.25 token |
  | Varies by model? | Yes (different tokenizers split text differently) | No | No |

  | | LLM token | Security/authentication token |
  |---|---|---|
  | Meaning | Unit of text the model processes | Credential proving identity or access (API key, access token) |
  | Context | Language models | IT security and APIs |
  | Risk | Cost, limits, truncation | Theft, leakage, misuse |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / Calculate-or-estimate / Compare (token vs word) / Scenario (limits, cost, truncation) / Best-fit
- **Must-memorize facts:**
  - [ ] A token ≠ a word; it can be a word, sub-word, punctuation, or space
  - [ ] Rule of thumb (English): **1 token ≈ 4 characters ≈ ¾ word** (100 tokens ≈ 75 words)
  - [ ] The **context window** is measured in tokens and covers **input + output** together
  - [ ] Cost, latency, and rate limits are driven by token counts; **output tokens typically cost more than input tokens**
  - [ ] Different models use **different tokenizers**, so the same text gives different token counts
  - [ ] Non-English text, code, numbers, and rare words often use **more tokens** for the same meaning (higher cost, less usable context)
  - [ ] If input exceeds the context window, content is **truncated or rejected**, and the model cannot see what was cut
  - [ ] Longer prompts and outputs increase cost and latency
  - [ ] Tokenization is the step **before** embeddings and the transformer
  - [ ] Common tokenizer methods: **BPE, WordPiece, SentencePiece**
  - [ ] Model behaviour with letters, spelling, and arithmetic can be affected by tokenization (the model sees tokens, not individual letters)
- **Keywords that signal this topic in a question:** "context window," "token limit," "cost per million tokens," "input/output tokens," "truncated," "tokenizer," "sub-word," "rate limit," "prompt length"
- **Commonly confused with:**
  - Token vs word (not one-to-one)
  - Token vs character
  - Token vs embedding (token is the text unit; embedding is its numeric vector)
  - Context window vs parameters vs training data size
  - LLM token vs security/access token
  - Training tokens (size of the training dataset) vs tokens in a prompt
- **Elimination tips (how to rule out wrong options):**
  - Reject "1 token = 1 word" and "token count equals word count."
  - Reject "the context window only limits the prompt." It includes the output too.
  - Reject "all models count tokens the same way."
  - Reject "a larger context window guarantees the model uses all the information well."
  - For cost-control questions, prefer shorter prompts, concise outputs, caching or summarising context, and right-sizing the model over "ignore usage."
  - For "conversation loses early instructions" questions, think context window overflow and truncation.
- **Frameworks / standards link:**
  - **EU AI Act:** Systemic-risk presumption for GPAI models is based on **training compute** (10^25 FLOPs), not token counts. Providers must publish a summary of training content; dataset size is often described in tokens.
  - **NIST AI RMF and AI 600-1:** Token-based cost and capacity limits touch on resilience and availability; context handling connects to information-integrity and confabulation risks.
  - **ISO/IEC 42001:** Resource management, monitoring, and operational controls can include usage and cost tracking.
  - **Privacy and security link:** Everything in a prompt is sent as tokens to the model, and prompts and outputs may be logged or retained by the vendor, so sensitive data in tokens is a data-protection concern.
  - **Governance angle:** Token usage is the basis for cost governance, quota management, and monitoring for abuse (e.g., unusually high usage).

| # | Scenario | Industry | How this topic applies | Outcome / risk |
|---|---|---|---|---|
| 1 | Estimating and capping monthly LLM spend | Cross-industry | Budget = tokens × price; set quotas and alerts | Predictable costs; runaway usage if uncontrolled |
| 2 | Summarising a 200-page contract | Legal / Audit | Document must fit the context window or be chunked | Truncated input means missed clauses |

| 4 | Long chat session losing early instructions | Customer service | Older tokens fall out of the window | Inconsistent behaviour; need summarising or restating rules |

- **Consulting / assurance lens:**
  - Ask the client: "How do you monitor and cap token usage, and what happens when a document exceeds the context window?"
  - Token awareness shows up in cost governance, design quality, and resilience.
- **Evidence or controls you would look for:**
  - Usage dashboards, budgets, and alerts by team or application
  - Input length limits and rate limiting on public-facing apps
  - Design handling for long documents (chunking, summarising, retrieval)
  - Testing that critical instructions survive long conversations
  - Vendor pricing and quota terms documented
  - Policy on what data may enter prompts (since prompts are tokens sent to a third party)

## 5. Q&A Bank

### Quick recall
- **Q:** What is a token?
  **A:** The basic unit of text an LLM processes: a word, part of a word, punctuation, or space.

- **Q:** Roughly how many words is 1,000 tokens in English?
  **A:** About 750 words (1 token ≈ ¾ word).

- **Q:** What does the context window measure?
  **A:** The maximum number of tokens the model can handle at once, including both input and output.

### Conceptual
- **Q:** Why do LLMs use sub-word tokens instead of whole words or single letters?
  **A:** Whole-word vocabularies would be enormous and fail on new or misspelled words; single letters would make sequences too long. Sub-word tokens give a compact vocabulary that can still represent any text.

- **Q:** Why might the same sentence cost more in one language than another?
  **A:** Tokenizers are usually optimised for the languages most common in their training data. Other languages (and code or numbers) often split into more tokens, raising cost and using more context.

- **Q:** Why do output tokens often cost more than input tokens?
  **A:** Generating each output token requires a separate model step (autoregressive), which is more computationally expensive than processing the input in parallel.

- **Q:** Does a larger context window mean the model handles long inputs perfectly?
  **A:** No. It can accept more tokens, but quality can still drop for information buried in very long contexts, and cost and latency rise.

- **Q:** Is the token count the same across different models?
  **A:** No. Each model family has its own tokenizer, so counts for the same text can differ.

### Scenario-based
- **Q:** An application sends a 150,000-token document to a model with a 100,000-token window. What happens and how do you fix it?
  **A:** The input is truncated or rejected, so parts are never seen. Fix by chunking, summarising in stages, retrieving only relevant sections (RAG), or using a model with a larger window.

- **Q:** A team's LLM bill is three times the forecast. What should be checked?
  **A:** Average prompt and output lengths, repeated or unnecessarily long context, chat histories resent each turn, model choice, retries, and possible abuse. Then apply limits, caching, summarisation, and usage monitoring.

- **Q:** A compliance team says, "We only send short questions, so no sensitive data is involved." Is that reasoning sound?
  **A:** Not necessarily. Prompts can include personal or confidential data however short they are, and attached context, history, and retrieved documents all count as tokens sent to the model. Data classification and vendor terms still apply.

### Interview-style
- **Q:** "Explain tokens to a non-technical executive."
  **A:** "AI language tools don't read whole words the way we do. They break text into small building blocks called tokens, roughly three-quarters of a word each. Those blocks matter for two business reasons: vendors charge by the number of tokens, and each model can only handle a fixed number at once, like a desk with limited space. So longer documents, longer conversations, and some languages cost more and can run out of room, which is why we plan for usage and watch it."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Estimate token usage and cost before scaling a use case | Assume tokens equal words or ignore usage costs |
| Remember the window covers input **and** output | Fill the whole window with input and leave no room for the answer |
| Set input limits, quotas, and rate limits on public apps | Leave token usage unmonitored or uncapped |
| Chunk, summarise, or retrieve for long documents | Paste huge documents and assume the model saw everything |
| Test multilingual and code-heavy inputs for cost and quality | Assume token costs are equal across languages |
| Restate critical instructions in long conversations | Assume early instructions persist forever |
| Treat prompt content as data sent to a vendor | Assume short prompts are free of sensitive data |
| Check each model's own tokenizer and pricing | Reuse one model's token estimates for another |

- **Common mistakes / misconceptions:**
  1. "A token is a word." (It is often a word piece.)
  2. "Context window = prompt limit." (It is input plus output.)
  3. "Token counts are universal." (Tokenizers differ by model.)
  4. "Bigger context window solves every long-document problem." (Cost, latency, and recall quality still matter.)
  5. "An LLM token is the same as an API access token." (Completely different meanings.)
- **Red flags in practice:**
  - No cost or usage monitoring for LLM applications
  - Public chatbot with no input-length or rate limits
  - Documents silently truncated without the user knowing
  - Budget planned per word or per query instead of per token
  - Sensitive data included in prompts without controls
