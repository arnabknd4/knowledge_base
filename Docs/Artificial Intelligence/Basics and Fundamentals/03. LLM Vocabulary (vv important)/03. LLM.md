## 1. Learn It (Core Understanding)
- **One-line definition:** A Large Language Model (LLM) is a very large transformer-based neural network, trained on vast amounts of text (and often code), that learns to predict the next token and can therefore understand and generate human-like language.
- **Plain-English explanation (3-4 lines):**
  An LLM reads text as tokens and, during training, plays one game billions of times: given the tokens so far, predict the next one. To get good at this, it absorbs grammar, facts, writing styles, and some reasoning patterns. At use time it generates answers one token at a time, each based on the prompt plus everything it has already written. It produces *plausible* language from learned patterns; it does not look up verified facts or "know" things the way a person does.
- **Why it exists / problem it solves:**
  - One general-purpose model can handle many language tasks (drafting, summarising, translating, coding, Q&A) without a separate model for each
  - Lets people instruct software in plain language
  - Automates knowledge-work tasks that were previously hard to automate
- **Key terms to know:**
  - **LLM:** Large transformer model trained on massive text data to predict the next token
  - **Token:** Chunk of text (word or word piece) the model reads and writes; usage limits and cost are measured in tokens
  - **Next-token prediction:** The core training objective (self-supervised)
  - **Pre-training:** Initial large-scale training on broad text
  - **Fine-tuning / instruction tuning:** Further training so the model follows instructions or specialises in a domain
  - **RLHF (and similar alignment methods):** Training with human (or AI) feedback so outputs are more helpful, honest, and safe
  - **Foundation model:** Large base model adaptable to many tasks
  - **Base model vs chat/instruct model:** Raw next-token predictor vs one tuned to follow instructions and converse
  - **Prompt / system prompt:** The user's input, and the hidden standing instructions set by the developer
  - **Context window:** Maximum tokens the model can consider at once (prompt + output)
  - **Temperature / sampling:** Settings that control how random or predictable the output is
  - **Hallucination (confabulation):** Fluent but false or invented output
  - **Knowledge cutoff:** Date after which the model has no training data (unless given tools or retrieved context)
  - **Emergent abilities:** Capabilities that appear at larger scale (e.g., few-shot learning, reasoning-like behaviour)
  - **In-context / few-shot learning:** Adapting behaviour from examples in the prompt, without changing weights
  - **RAG:** Supplying retrieved documents to ground answers in trusted data
  - **Agents / tool use:** LLMs that call tools or APIs and take multi-step actions
  - **SLM (small language model):** Smaller, cheaper language model for narrower or on-device use
  - **Open-weight vs closed (API-only) models:** Downloadable weights vs vendor-hosted access
- **How it works (simple steps):**
  1. **Pre-train:** Train a transformer on huge text corpora to predict the next token (weights are learned).
  2. **Adapt and align:** Instruction-tune and apply RLHF-style methods so it follows instructions and behaves safely.
  3. **Deploy:** Serve the model via an API or application, with a system prompt and guardrails.
  4. **Prompt:** The user's input (plus any retrieved context) is tokenised and fed in.
  5. **Generate (inference):** The model produces one token at a time, sampling from probabilities (temperature affects variety), until complete.
  6. **Govern:** Filters, human review, logging, and monitoring wrap around the model.
- **Where it sits in the AI stack:** Model layer (a transformer-based generative model). Applications like chatbots, RAG systems, and agents are built on top of it.

## 2. Mental Model
- **Analogy:** An extremely well-read **autocomplete**: it has read a huge library and learned how text tends to continue. Ask it a question and it writes the most fitting continuation, word by word. It is like a brilliant writer with a great memory for *patterns* but no built-in fact-checker and no eyes on the real world, so it can sound certain while being wrong.
- **Diagram / flow:**
```
  PREPARE (once)                               USE (every request)
  ──────────────                               ───────────────────
  Huge text corpus                             System prompt + user prompt (+ retrieved docs)
        │                                                    │
        ▼                                                    ▼
  [Pre-training: predict next token]                   Tokenise
        │                                                    │
        ▼                                                    ▼
  [Instruction tuning + RLHF]                  [LLM: frozen weights, attention over context]
        │                                                    │
        ▼                                                    ▼
  Deployed LLM ───────────────────────────►    Next-token probabilities → sample (temperature)
                                                             │
                                                   append token, repeat ──► final answer
                                                             │
                                                  Guardrails / human review / logging
```
- **The one thing to remember:** An LLM predicts the next token from patterns. It produces plausible text, not guaranteed truth, so it needs grounding, verification, and governance.
- **Compare and contrast:**

  | | LLM | Traditional ML model | Search engine |
  |---|---|---|---|
  | Purpose | Generate and understand language | Predict or classify for one task | Retrieve existing documents |
  | Output | New, open-ended text | Label or number | Links to existing content |
  | Knowledge | Compressed in weights (may be outdated or wrong) | Task-specific patterns | Live index of real pages |
  | Main failure | Hallucination, bias, prompt injection | Misclassification, drift | Irrelevant or low-quality results |
  | Flexibility | Very high (prompt-driven) | Low (retrain for new task) | Low (retrieval only) |

  | | Base model | Instruction/chat model |
  |---|---|---|
  | Trained to | Continue text | Follow instructions helpfully and safely |
  | Behaviour | Raw, may ramble or ignore requests | Conversational, aligned to guidelines |
  | Typical use | Starting point for tuning | Direct end-user use |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / How-it-works / Compare / Limitation-and-risk / Scenario / Best-mitigation
- **Must-memorize facts:**
  - [ ] LLM = transformer-based model trained on massive text to **predict the next token**
  - [ ] Training stages: **pre-training → fine-tuning/instruction tuning → alignment (RLHF)**
  - [ ] Generation is **autoregressive** and **probabilistic** (same prompt can give different outputs)
  - [ ] Size measured in **parameters**; input/output limit measured in **tokens** (context window)
  - [ ] Weights are **frozen at inference**; models do not learn from individual chats by default
  - [ ] LLMs have a **knowledge cutoff** and cannot access live or private data unless given tools or retrieved context
  - [ ] Key limitations: **hallucination, bias, outdated knowledge, inconsistent outputs, sensitivity to prompt wording, limited context, no true understanding**
  - [ ] Key risks: **prompt injection, data leakage/privacy, IP/copyright, harmful content, over-reliance, misuse**
  - [ ] Main mitigations: **RAG (grounding), human-in-the-loop, guardrails and filters, evaluation and red teaming, access controls, logging and monitoring, clear usage policy**
  - [ ] **Temperature** higher = more varied/creative; lower = more deterministic/consistent
  - [ ] LLMs are one type of generative AI (text/code); other GenAI covers images, audio, video
  - [ ] Customisation options in order of effort: **prompting → RAG → fine-tuning → training from scratch**
- **Keywords that signal this topic in a question:** "next token," "context window," "hallucination," "prompt," "pre-training," "fine-tuning," "RLHF," "parameters," "token limit," "foundation model"
- **Commonly confused with:**
  - LLM vs transformer (model vs architecture)
  - LLM vs generative AI (text-focused subset vs broad category)
  - LLM vs chatbot (chatbot is an application built on an LLM)
  - LLM vs search engine / database (generates vs retrieves)
  - Fine-tuning vs RAG (changes weights vs supplies context at query time)
  - Context window vs training data vs memory
  - Open-weight vs open-source
- **Elimination tips (how to rule out wrong options):**
  - Reject "LLMs retrieve stored facts from a database" and "LLMs always give factual answers."
  - Reject "LLMs understand language the way humans do."
  - Reject "the model learns from every user conversation and updates immediately."
  - Reject "a bigger model eliminates hallucination."
  - For **factual accuracy on company-specific data** → choose **RAG/grounding** plus verification, not "raise temperature" or "use a bigger model."
  - For **consistent, repeatable output** → lower temperature, clearer prompts, structured output.
  - For **confidential data concerns** → data controls, approved enterprise tools, vendor terms; not "ban all use" or "trust the vendor blindly."
  - For **low-effort customisation** → prompting first, then RAG, before fine-tuning.
- **Frameworks / standards link:**
  - **EU AI Act:** LLMs are typically **general-purpose AI (GPAI) models**. Providers must keep technical documentation, share information with downstream providers, maintain a copyright policy, and publish a training-content summary. Models with **systemic risk** (presumed above 10^25 FLOPs of training compute) face extra duties (evaluations, adversarial testing, incident reporting, cybersecurity). Applications built on LLMs are classified by **use case** (e.g., high-risk if used for hiring or credit scoring), and **transparency duties** cover AI interaction and AI-generated content. Verify the latest application dates, as obligations are phased in.
  - **NIST AI 600-1 (Generative AI Profile):** Lists GenAI risks (confabulation, information integrity, data privacy, intellectual property, harmful or biased content, information security, human-AI configuration) mapped to Govern / Map / Measure / Manage.
  - **ISO/IEC 42001:** AI management system covering risk and impact assessment, data governance, lifecycle controls, and monitoring for LLM-based services.
  - **Privacy link:** Prompts may contain personal data; check lawful basis, retention, and whether prompts are used for training.
  - **Governance angle:** Approved-use policy, model and vendor inventory, use-case risk rating, evaluation evidence, human oversight, and incident handling.

## 4. 🛠️ Real-World Use Cases
| # | Scenario | Industry | How this topic applies | Outcome / risk |
|---|---|---|---|---|
| 1 | Drafting emails, reports, and meeting summaries | Cross-industry | LLM generates and condenses text | Time saved; hallucinated details, confidential data in prompts |
| 2 | Customer-support assistant grounded in company documents | Banking / Retail / Telecom | LLM + RAG answers from approved knowledge base | Faster service; wrong or unsafe answers, prompt injection, brand risk |
| 3 | Code generation and review | Software / IT | LLM suggests, explains, and tests code | Faster delivery; insecure or incorrect code, licence issues |
| 4 | Contract and policy analysis | Legal / Audit / Consulting | LLM extracts clauses, flags risks, compares documents | Efficiency; missed or invented content, needs human verification |
| 5 | Internal knowledge search and Q&A | Enterprise | LLM answers over intranet and document stores | Better access to knowledge; access-control bypass if permissions are not respected |
| 6 | Agentic workflows (LLM calls tools to complete tasks) | Operations / IT | LLM plans and executes multi-step actions | Automation gains; unintended actions, excessive permissions |

- **Consulting / assurance lens:**
  - A client asks, "Where are we using LLMs and is it governed?" An auditor asks, "What data goes in, who reviews the output, how was it tested, and what does the vendor do with our prompts?"
  - Common findings: shadow AI, no use-case inventory, no output review for customer-facing use, weak vendor terms.
- **Evidence or controls you would look for:**
  - Acceptable-use policy and list of approved LLM tools
  - Inventory of LLM use cases with risk ratings and owners
  - Data classification rules for prompts (what must never be entered)
  - Vendor due diligence: data retention, training on customer data, security certifications, location of processing
  - Evaluation results: accuracy, bias, safety, and red-team reports for each high-impact use case
  - Human-in-the-loop checkpoints and escalation paths
  - Guardrails (input/output filtering), access controls, least-privilege tool permissions for agents
  - Logging, monitoring, and incident response for harmful or incorrect outputs
  - Disclosure/labelling of AI interaction or AI-generated content where required

## 5. Q&A Bank

### Quick recall
- **Q:** What is an LLM?
  **A:** A large transformer-based model trained on vast text data to predict the next token, enabling it to understand and generate language.

- **Q:** What is the core training objective of an LLM?
  **A:** Next-token prediction (self-supervised learning on large text corpora).

- **Q:** What are the main stages of building a chat LLM?
  **A:** Pre-training, then fine-tuning/instruction tuning, then alignment (e.g., RLHF).

### Conceptual
- **Q:** Why do LLMs hallucinate?
  **A:** They generate the most statistically plausible continuation, not verified facts. They have no built-in fact-checking, may lack the relevant knowledge, and are trained to always produce fluent text, so they can be confidently wrong.

- **Q:** What is a context window and why does it matter?
  **A:** The maximum number of tokens (prompt plus output) the model can consider at once. Content outside it is invisible to the model, and longer contexts increase cost and latency.

- **Q:** What does temperature do?
  **A:** It controls randomness in token selection. Low temperature gives more predictable, consistent outputs; high temperature gives more varied, creative ones.

- **Q:** How do RAG and fine-tuning differ as ways to customise an LLM?
  **A:** RAG retrieves relevant documents at query time and adds them to the prompt (no weight change; good for current or private facts). Fine-tuning further trains the model, changing its weights (good for style, format, or specialised behaviour).

- **Q:** Does an LLM learn from my conversation?
  **A:** Not in its weights during normal use. Within a conversation it uses the context window. Whether prompts are stored or used for future training depends on the vendor's terms and settings.

- **Q:** Is an LLM the same as a search engine or database?
  **A:** No. It generates text from learned patterns; it does not retrieve verified records. Combining it with retrieval (RAG) gives grounded answers.

### Scenario-based
- **Q:** A customer-facing chatbot gives incorrect refund-policy answers. What is the best fix?
  **A:** Ground it in the approved policy documents (RAG), add guardrails and a fallback to a human agent, test against known policy questions, and monitor live answers. Do not just switch to a bigger model or raise temperature.

- **Q:** Staff are pasting confidential client documents into a public chatbot. What should the organisation do?
  **A:** Issue an acceptable-use policy with data-classification rules, provide an approved enterprise LLM with suitable data protections and no-training terms, train staff, and monitor for shadow AI. Blocking alone without an alternative tends to push use underground.

- **Q:** A team wants to use an LLM to screen job applicants automatically. What should concern an assurance professional?
  **A:** Hiring is a high-risk use case under the EU AI Act. Concerns include bias and fairness testing, transparency to candidates, human oversight, data protection, and documentation. Fully automated rejection without human review is a red flag.

- **Q:** An LLM agent with access to email and file systems is tricked by a malicious instruction hidden in a web page it read. What happened and how do you reduce the risk?
  **A:** Indirect prompt injection. Apply least-privilege permissions, require human approval for sensitive actions, separate trusted instructions from untrusted content, filter inputs and outputs, and log and monitor agent actions.

### Interview-style
- **Q:** "Explain an LLM to a non-technical executive."
  **A:** "An LLM is an AI system trained on an enormous amount of text so it gets very good at predicting what words should come next. That lets it draft, summarise, translate, and answer questions in natural language. It's like an extremely well-read assistant that's great at patterns, but it isn't looking facts up, so it can sound confident and still be wrong. That's why we pair it with trusted company data, keep people reviewing important outputs, and set clear rules on what information can be shared with it."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Verify important outputs before acting on them | Treat fluent answers as verified facts |
| Ground factual use cases in trusted data (RAG) | Expect the base model to know your company's latest or private information |
| Keep a human in the loop for high-impact decisions | Fully automate decisions affecting people, money, safety, or legal rights |
| Define an approved-use policy and approved tools | Allow unmanaged shadow AI |
| Classify data and restrict sensitive inputs | Paste confidential, personal, or regulated data into unapproved tools |
| Start with prompting and RAG before fine-tuning | Jump to fine-tuning or training from scratch without need |
| Test, red-team, and monitor continuously | Rely on a one-time demo as proof of reliability |
| Apply least privilege to agents and tools | Give LLM agents broad access without approval steps |
| Review vendor terms (retention, training use, IP, location) | Assume vendor defaults protect your data |

- **Common mistakes / misconceptions:**
  1. "LLMs understand and reason like humans." (They predict patterns; reasoning-like behaviour can be unreliable.)
  2. "LLMs look up answers in a database." (They generate from learned patterns.)
  3. "A bigger model means no hallucinations." (It reduces but does not eliminate them.)
  4. "The model learns from our chats automatically." (Not in weights by default; depends on vendor terms for data use.)
  5. "LLM = chatbot = generative AI." (LLM is a model; chatbot is an application; GenAI is the broader category.)
  6. "Low temperature guarantees correct answers." (It increases consistency, not accuracy.)
- **Red flags in practice:**
  - No inventory of LLM use cases or vendors
  - Sensitive data going into public tools
  - No human review on customer-facing or decision-support outputs
  - No testing evidence, red-teaming, or monitoring
  - Agents with broad permissions and no approval steps
  - Unclear vendor terms on prompt retention and training use

## 7. Revision Snapshot
- **30-second summary:**
  An LLM is a huge transformer trained on massive text to predict the next token, then instruction-tuned and aligned (RLHF) to follow instructions safely. It generates text one token at a time, probabilistically, within a limited context window, with frozen weights at inference. It is versatile but produces plausible, not guaranteed-true, output. Key risks: hallucination, bias, prompt injection, data leakage, IP issues, and over-reliance. Key controls: use policy, RAG grounding, human-in-the-loop, guardrails, evaluation and red teaming, least-privilege for agents, vendor due diligence, and monitoring, aligned to NIST AI RMF (and GenAI Profile), EU AI Act (GPAI and use-case rules), and ISO 42001.
- **3 bullets to recall on exam day:**
  1. LLM = transformer + massive text + next-token prediction; pre-train → fine-tune → align (RLHF)
  2. Plausible ≠ true: hallucination is the signature risk; fix factual gaps with RAG and verification
  3. Customisation order: prompting → RAG → fine-tuning; controls = policy + human review + testing + monitoring
