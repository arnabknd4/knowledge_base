## 1. Learn It (Core Understanding)
- **One-line definition:** A prompt is the input given to an LLM to steer its output; a system prompt is the standing set of instructions, set by the developer or operator, that defines the model's role, rules, tone, and limits for every interaction in an application.
- **Plain-English explanation (3-4 lines):**
  The prompt is everything you send the model: your question, instructions, examples, pasted documents, and the conversation so far. The system prompt is the part written by whoever built the application, usually hidden from end users, that says things like "You are a support assistant for Bank X. Only answer banking questions. Never give legal advice." The user prompt then arrives inside those rules. Both sit in the same context window, and the model reads them all as text. It follows instructions by pattern, not by enforced logic, so a system prompt guides behaviour but is not a guarantee.
- **Why it exists / problem it solves:**
  - One general model can be turned into many specific assistants without retraining, just by changing the instructions
  - Lets developers set role, tone, format, scope, and safety rules once, instead of repeating them in every user message
  - Separates the developer's standing instructions from the user's changing requests
- **Key terms to know:**
  - **Prompt:** The full input to the model for a request (instructions, context, examples, question)
  - **System prompt (system message):** Developer-set standing instructions that shape behaviour across a session or application
  - **User prompt:** The message typed by the end user
  - **Assistant message:** The model's previous replies, kept in the conversation history
  - **Instruction hierarchy:** The intended order of priority: system/developer instructions over user instructions over instructions found in retrieved or tool content
  - **Prompt engineering:** The craft of writing prompts to get reliable, useful outputs
  - **Zero-shot / one-shot / few-shot prompting:** No examples / one example / several examples included in the prompt
  - **Chain-of-thought prompting:** Asking the model to work through steps before answering
  - **Role prompting:** Assigning a persona or expertise ("You are an auditor...")
  - **Structured output:** Asking for a fixed format (JSON, table) so software can use the result
  - **Prompt template:** A reusable prompt with placeholders filled in at run time
  - **Guardrails:** Checks and filters around the model (input and output filtering, policy rules); a system prompt is one soft guardrail, not a hard one
  - **Prompt injection:** Malicious or untrusted text that tries to override the model's instructions
  - **Jailbreak:** A prompt crafted to make the model bypass its safety rules
  - **System prompt leakage:** The model revealing its hidden instructions
  - **Prompt versioning:** Tracking changes to prompts like code, with testing and approval
- **How it works (simple steps):**
  1. **Developer writes the system prompt:** role, scope, tone, rules, output format, refusal behaviour.
  2. **Application assembles the request:** system prompt + conversation history + any retrieved documents + the new user prompt.
  3. **Everything is tokenised** and placed in the context window as one sequence.
  4. **The model generates** a reply by predicting tokens conditioned on all of that text.
  5. **Guardrails and review:** Output filters, validation, and human checks run before the result is used.
  6. **Iterate and govern:** Prompts are tested, versioned, and monitored, since small wording changes can change behaviour.
- **Where it sits in the AI stack:** Application layer, on top of the model. It is the cheapest and fastest way to customise an LLM, and the first control point developers reach for.

## 2. Mental Model
- **Analogy:** A **new contractor and a briefing pack**. The **system prompt** is the employer's standing brief handed over before the contractor meets any customer: "Here's your role, the company tone, what you may and may not do." The **user prompt** is each customer's request. A good contractor follows the brief, but it is a brief, not a locked door: a persuasive customer, or a forged note slipped into the paperwork, may still talk them into bending the rules. That is why sensitive controls belong in the building's security system, not only in the brief.
- **Diagram / flow:**
```
  ┌──────────────── CONTEXT WINDOW ────────────────┐
  │ SYSTEM PROMPT  (developer: role, rules, format) │  ← highest intended priority
  │ CONVERSATION HISTORY (user + assistant turns)   │
  │ RETRIEVED / TOOL CONTENT (docs, web, emails)    │  ← untrusted: treat as data
  │ USER PROMPT  (current request)                  │
  └─────────────────────────┬───────────────────────┘
                            ▼
                         [ LLM ]
                            ▼
             Output ──► guardrails / validation ──► human review (if high impact)
```
- **The one thing to remember:** A system prompt steers the model but does not enforce anything. Treat it as a soft control and back it with real safeguards.
- **Compare and contrast:**

  | | System prompt | User prompt |
  |---|---|---|
  | Written by | Developer / operator | End user |
  | Visible to user? | Usually hidden | Yes |
  | Purpose | Set role, rules, tone, scope, format | Make a specific request |
  | Persistence | Standing across the session or app | Changes each turn |
  | Trust level | Highest intended priority | Lower; may be adversarial |
  | Main risk | Leakage, over-reliance as a security control | Injection, jailbreaks |

  | | Prompting | RAG | Fine-tuning |
  |---|---|---|
  | What changes | Instructions in the input | Retrieved facts added to the input | Model weights |
  | Effort and cost | Lowest | Medium | Highest |
  | Good for | Behaviour, tone, format, task framing | Current or private facts | Consistent style, specialised behaviour |
  | Permanent? | No (per request) | No (per request) | Yes (baked into weights) |

## 3. 🎯 Exam Focus
- **Likely question types:** Definition / Compare (system vs user) / Scenario (injection, leakage, inconsistent output) / Best-mitigation / Pick-the-technique
- **Must-memorize facts:**
  - [ ] A prompt = all input text to the model; system prompt = developer's standing instructions; user prompt = the end user's request
  - [ ] All prompt parts share the **context window** and consume **tokens**
  - [ ] Models follow instructions **probabilistically**; system prompts reduce but do not eliminate unwanted behaviour
  - [ ] **Instruction hierarchy:** system/developer > user > untrusted content (retrieved documents, web pages, tool outputs)
  - [ ] Prompting techniques: **zero-shot, one-shot, few-shot, chain-of-thought, role prompting, structured output**
  - [ ] Prompts **do not change weights**; few-shot examples are **in-context learning**, temporary
  - [ ] **Prompt injection** = untrusted text overriding instructions; **direct** (user types it) vs **indirect** (hidden in content the model reads)
  - [ ] **Jailbreak** = user trying to bypass safety rules; **system prompt leakage** = hidden instructions revealed
  - [ ] Never put **secrets** (API keys, credentials, confidential rules) in a system prompt; assume it can leak
  - [ ] Security must be enforced **outside** the model: access control, least privilege, input/output filtering, human approval
  - [ ] Small prompt changes can change outputs, so **version, test, and approve** prompts like code
  - [ ] Customisation order: **prompting → RAG → fine-tuning**
  - [ ] Clear, specific prompts (context, task, format, constraints, examples) give better and more consistent results
- **Keywords that signal this topic in a question:** "instructions," "system message," "persona," "few-shot," "chain-of-thought," "override instructions," "hidden instructions," "guardrail," "prompt template," "injection"
- **Commonly confused with:**
  - System prompt vs user prompt
  - Prompting vs fine-tuning (temporary input vs changed weights)
  - Prompt injection vs jailbreak (injection comes through untrusted content or overrides app instructions; jailbreak targets the model's safety training, usually by the user directly; the two overlap)
  - System prompt vs guardrails (instructions vs enforced filters and controls)
  - Prompt engineering vs fine-tuning vs RAG
  - Prompt vs context window (prompt is what you send; window is the limit it must fit in)
- **Elimination tips (how to rule out wrong options):**
  - Reject "the system prompt guarantees the model will never do X."
  - Reject "put the API key in the system prompt so the model can use it."
  - Reject "user instructions can never override the system prompt" as a certainty; it is the intent, not a guarantee.
  - Reject "few-shot examples retrain the model."
  - For **data-exposure or unauthorised-action** scenarios, choose **enforced controls** (least privilege, access checks, human approval, filtering) over "write a stricter prompt" alone.
  - For **inconsistent formatting** → clearer instructions, examples, structured output, lower temperature.
  - For **domain facts** the model lacks → RAG, not a longer system prompt.
- **Frameworks / standards link:**
  - **NIST AI 600-1 (Generative AI Profile):** Covers information security risks such as prompt injection and data leakage, plus confabulation and harmful content; controls include testing, red teaming, and monitoring.
  - **NIST AI RMF:** Prompts and configurations are part of the system to be mapped, measured, and managed; change control matters.
  - **EU AI Act:** Does not regulate prompts directly. Relevant duties are use-case based: human oversight, accuracy, robustness, cybersecurity, record-keeping for high-risk systems, and transparency (telling people they are interacting with AI; labelling AI-generated content). System prompts are one way operators implement these, but they do not replace them.
  - **ISO/IEC 42001:** Change management, documentation, and operational controls support versioned, approved prompts.
  - **Governance angle:** Treat production prompts as controlled configuration: owned, reviewed, versioned, tested against misuse cases, and monitored.

## 4. 🛠️ Real-World Use Cases
| # | Scenario | Industry | How this topic applies | Outcome / risk |
|---|---|---|---|---|
| 1 | Customer-support bot limited to company topics | Banking / Telecom | System prompt sets role, scope, tone, and escalation rules | Consistent service; users may try to push it off-scope |
| 2 | Extracting fields from invoices into JSON | Finance / Ops | Prompt with examples and a required output format | Reliable automation; errors need validation before use |
| 3 | Internal policy assistant with RAG | Enterprise | System prompt says "answer only from provided documents and cite them" | Better grounding; still needs testing for made-up answers |
| 4 | AI agent reading emails and web pages | IT / Operations | Untrusted content enters the prompt context | Indirect prompt injection; needs least privilege and approvals |
| 5 | Team-wide prompt library for drafting and analysis | Consulting / Audit | Shared, reviewed prompt templates | Consistent quality and efficiency; risk if templates are unreviewed or contain sensitive data |
| 6 | Attacker extracts hidden instructions from a chatbot | Any | System prompt leakage | Exposes business logic or embedded secrets |

- **Consulting / assurance lens:**
  - Ask the client: "What do your system prompts say, who owns and approves changes, and what happens if a user or a document tries to override them?"
  - Also ask: "Which controls work even if the prompt fails?" A mature answer includes access control, output checks, and human review, not just wording.
- **Evidence or controls you would look for:**
  - Inventory of production prompts with owners, versions, and change history
  - Testing records against misuse cases (injection, jailbreak, leakage, off-scope requests)
  - Evidence that no secrets or sensitive data sit in system prompts
  - Least-privilege permissions and approval steps for agent actions
  - Input and output filtering, logging, and monitoring of unusual behaviour
  - Human review for high-impact outputs
  - Red-team reports and periodic re-testing after model or prompt changes
  - Policy on what employees may put into prompts (data classification)

## 5. Q&A Bank

### Quick recall
- **Q:** What is a system prompt?
  **A:** Standing instructions from the developer or operator that set the model's role, rules, tone, and limits across an application.

- **Q:** What is few-shot prompting?
  **A:** Including a few examples in the prompt to show the model the desired pattern or format.

- **Q:** Does a prompt change the model's weights?
  **A:** No. It only shapes the output for that request.

### Conceptual
- **Q:** Why is a system prompt not a security control?
  **A:** The model follows instructions probabilistically, so determined or cleverly worded inputs can override or expose them. Real protection needs enforced controls outside the model, such as access restrictions, filtering, and human approval.

- **Q:** What is the difference between direct and indirect prompt injection?
  **A:** Direct: the user types malicious instructions into the prompt. Indirect: the malicious instructions are hidden in content the model reads (a web page, email, or document), so the model may follow them without the user knowing.

- **Q:** How do prompting, RAG, and fine-tuning differ?
  **A:** Prompting changes the instructions in the input. RAG adds retrieved facts to the input. Fine-tuning changes the model's weights. Prompting is the quickest and cheapest; fine-tuning is the heaviest.

- **Q:** What is chain-of-thought prompting?
  **A:** Asking the model to reason through intermediate steps before giving the final answer, which can improve results on multi-step problems. The visible reasoning is not a guarantee that the answer is correct or that it reflects the model's true internal process.

- **Q:** What makes a good prompt?
  **A:** Clear task, relevant context, constraints (scope, length, tone), a specified output format, and examples where helpful, plus iteration and testing.

### Scenario-based
- **Q:** A company puts its database password in the chatbot's system prompt so the bot can "look things up." What is wrong?
  **A:** System prompts can leak through extraction attempts or injection. Secrets must never be placed in prompts. Use proper credential management and let a separate, permission-controlled tool make the lookup with least privilege.

- **Q:** A support chatbot occasionally discusses topics outside its scope after users push it. What should be done?
  **A:** Tighten and clarify the system prompt, add input and output filters for off-scope content, test with adversarial conversations, monitor live interactions, and escalate risky cases to humans. Recognise that the prompt alone will not fully prevent it.

- **Q:** An AI assistant that can send emails follows a hidden instruction in a received message and leaks data. What controls address this?
  **A:** Least-privilege tool access, human approval before sending or sharing sensitive data, separating trusted instructions from untrusted content, output and action filtering, and logging with alerts.

- **Q:** Two team members get very different summaries from the same model using their own prompts. How should the organisation respond?
  **A:** Standardise with reviewed prompt templates, specify format and criteria, test them on sample cases, version them, and keep humans reviewing outputs for important uses.

### Interview-style
- **Q:** "Explain prompts and system prompts to a non-technical executive."
  **A:** "A prompt is simply the instructions and information we give the AI for a task. The system prompt is the standing briefing written by whoever built the tool: its role, what it should and shouldn't do, and how to sound. The user's question then comes in on top of that briefing. It's a powerful and inexpensive way to shape behaviour, but it's guidance, not a lock. A determined user or a booby-trapped document can sometimes talk the AI out of its instructions, so the real safety comes from permissions, checks, and human review around it."

## 6. ✅ Dos and ❌ Don'ts

| ✅ Do | ❌ Don't |
|---|---|
| Write clear, specific prompts: task, context, constraints, format | Use vague prompts and expect consistent results |
| Use examples (few-shot) and structured output where consistency matters | Assume the model will guess your format |
| Treat system prompts as controlled configuration: owned, versioned, tested | Edit production prompts ad hoc with no review |
| Enforce security outside the model (least privilege, filters, approvals) | Rely on a system prompt as the only safeguard |
| Assume the system prompt can leak | Put secrets, credentials, or sensitive rules in it |
| Treat retrieved and tool content as untrusted data | Let untrusted text mix freely with trusted instructions |
| Test against injection, jailbreak, and off-scope cases, and re-test after changes | Test only the happy path once |
| Keep a human in the loop for high-impact outputs | Automate consequential decisions from prompt-driven output alone |
| Set rules on what staff may paste into prompts | Allow sensitive data in prompts without classification rules |

- **Common mistakes / misconceptions:**
  1. "The system prompt guarantees the rules are followed." (It guides; it does not enforce.)
  2. "Hidden means secret." (System prompts can often be extracted.)
  3. "Few-shot examples train the model." (Temporary in-context learning; weights unchanged.)
  4. "A longer prompt is always better." (Clarity and relevance matter; length costs tokens and can dilute focus.)
  5. "Prompt engineering is a substitute for data grounding." (Facts the model lacks need RAG or other sources.)
  6. "Prompt injection is only a user problem." (It can arrive through documents, web pages, and tool outputs.)
- **Red flags in practice:**
  - Secrets or confidential logic stored in system prompts
  - No owner, version history, or testing for production prompts
  - Agents with broad permissions and no approval steps
  - Untrusted content passed directly into an agent's context
  - Security posture described as "we told the model not to"
  - No re-testing after a model upgrade or prompt change
