#### 1. Learn It (Core Understanding)
*   **One-line definition:** The structured, layered prompt-configuration architecture in Claude Code that organizes coding instructions, rules, and commands across root files, directory inheritance, modular `@import` statements, and path-scoped `.claude/rules/` files.
*   **Plain-English explanation (3-4 lines):** Rather than stuffing every single coding rule, style guide, and architecture detail into one giant prompt file, Claude Code uses a modular hierarchy. Root `CLAUDE.md` defines repository-wide build/test commands and high-level style rules. Subdirectories can contain local `CLAUDE.md` files that extend or override root settings. Dedicated rule modules sit inside `.claude/rules/`, and external or shared instruction files can be pulled in using `@import`. This keeps prompts clean, token-efficient, and easy to maintain across large engineering teams.
*   **Why it exists / problem it solves:** Solves "monolithic prompt bloat" where dumping thousands of lines of instructions into a single file wastes prompt context tokens, increases latency, and degrades the LLM's adherence to critical instructions.
*   **Key terms to know:**
    *  `CLAUDE.md`: The primary project configuration file containing bash build/test commands, code style guidelines, and architecture notes for Claude Code.
    *  Instruction Inheritance: The mechanism where subdirectories automatically inherit rules from parent directory `CLAUDE.md` files, allowing local subpackage files to override or refine global settings.
    *  `@import` Syntax: A directive used inside `CLAUDE.md` files to pull in external or reusable markdown rule modules (e.g., `@import ./docs/style-guide.md`).
    *  `.claude/rules/`: A specialized directory for modular, domain-specific, or path-scoped rule files (e.g., `.claude/rules/testing.md`, `.claude/rules/api.md`).
*   **How it works (simple steps):**  
    1. **Global & Root Loading:** Claude Code reads user-global configurations and the repository root `CLAUDE.md`.
    2. **Import Resolution:** `@import` statements inside active instruction files are evaluated and expanded recursively into prompt context.
    3. **Hierarchy & Rules Discovery:** As the agent interacts with specific files, local subdirectory `CLAUDE.md` files and matching `.claude/rules/` files are discovered and merged.
    4. **Context Assembly:** Claude Code compiles the layered instructions into a consolidated system prompt context for execution.
*   **Where it sits in the AI stack:** Application Layer → Agentic Coding Configuration & Context Control

#### 2. Mental Model
*   **Analogy:** "`CLAUDE.md` hierarchy works like CSS cascades: Root `CLAUDE.md` acts like global styles (`body`), subpackage `CLAUDE.md` files act like component overrides, `@import` works like `@import` in stylesheets, and `.claude/rules/` act like specific utility classes targeted to matching elements."
*   **Diagram / flow (ASCII or mermaid):**
Root `CLAUDE.md` → `@import` Statements → Subdirectory `CLAUDE.md` → `.claude/rules/*.md` → Merged System Prompt Context
*   **The one thing to remember:** Keep root `CLAUDE.md` lean with high-frequency build/test commands, and offload detailed domain rules to `.claude/rules/` or `@import` targets.
*   **Compare and contrast:**
|  | Root `CLAUDE.md` | `@import` Directive | `.claude/rules/` Directory |
| ------ | ------ | ------ | ------ |
| Purpose | Primary repository entry point & build/test command hub | Explicit inclusion of external markdown instruction modules | Modular, domain-specific, or path-scoped rule storage |
| Scope | Repository-wide defaults | Loaded wherever imported | Loaded automatically or matched via file path rules |
| Best for | Common bash commands, tech stack overview, primary rules | Sharing standardized team guidelines across projects | Granular rules (e.g., DB migration rules, testing standards) |

#### 5. Q&A Bank
##### Quick recall
*   **Q:** What syntax is used inside a `CLAUDE.md` file to include instructions from another markdown file?  
    **A:** The `@import` directive (e.g., `@import ./path/to/file.md`).
##### Conceptual
*   **Q:** Why is a hierarchical instruction structure (`CLAUDE.md` + `.claude/rules/`) superior to placing all project guidelines in a single root `CLAUDE.md` file?  
    **A:** A single massive file consumes excessive prompt context tokens on every turn and degrades rule adherence. A hierarchical structure dynamically loads relevant rules based on active paths and task scope, preserving token budget and improving instruction following.
##### Scenario-based
*   **Q:** A team notices that Claude Code frequently ignores their database migration formatting rules when editing frontend components. How should they restructure their configuration hierarchy?  
    **A:** Remove database migration rules from root `CLAUDE.md` and move them into a targeted rule file inside `.claude/rules/db-migrations.md` (or a `/backend` subdirectory `CLAUDE.md`), so they only load when database files are actively being touched.
##### Interview-style
*   **Q:** "How do you manage prompt context limits while maintaining detailed coding standards in enterprise AI development?"  
    **A:** "We leverage the `CLAUDE.md` instruction hierarchy. We keep the root `CLAUDE.md` minimal—focusing strictly on primary build, test, and lint commands—and modularize specialized guidelines into `.claude/rules/` and `@import` modules. This ensures developers get precise, context-aware rule enforcement without overloading the model's context window."

#### 6. ✅ Dos and ❌ Don'ts
| ✅ Do | ❌ Don't |
| ------ | ------ |
| Keep root `CLAUDE.md` lean, focusing on common bash commands and high-level architecture | Dump exhaustive, multi-page API documentation or style manuals into root `CLAUDE.md` |
| Use `.claude/rules/` for domain-specific guidelines (e.g., testing, database migrations) | Duplicate identical coding rules across multiple project files instead of using `@import` |
| Commit `CLAUDE.md` and `.claude/rules/` to Git so the entire team shares identical AI setup | Mix technical MCP tool declarations (`.mcp.json`) into prompt instruction files (`CLAUDE.md`) |

*   **Common mistakes / misconceptions:** 1. Believing all rules in `.claude/rules/` consume tokens on every single turn (they can be loaded conditionally based on context/path scope). 2. Confusing `CLAUDE.md` (prompt rules) with `.claude.json` (environment/MCP configuration).
*   **Red flags in practice:** Monolithic root `CLAUDE.md` files exceeding 500 lines, leading to instruction dropping and context window bloat.
