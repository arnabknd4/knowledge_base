## 1. Learn It (Core Understanding)
- **One-line definition:**  
  Failure mode patterns are structured responses to system breakdowns that ensure graceful recovery, continuity, or safe degradation.

- **Plain-English explanation (3–4 lines):**  
  Instead of letting systems crash, failure mode patterns define how AI agents behave under stress. Graceful degradation reduces functionality but keeps service alive. Fallback switches to alternate methods. Redundancy ensures backup systems take over. These patterns minimize disruption and protect users.

- **Why it exists / problem it solves:**  
  - Prevents catastrophic failure  
  - Maintains user trust and continuity  
  - Provides resilience in unpredictable environments  

- **Key terms to know:**  
  - **Graceful degradation:** Reduce features but keep core service running  
  - **Fallback:** Switch to alternate method/tool  
  - **Redundancy:** Duplicate systems for backup  
  - **Fail‑safe:** Default to safest state  

- **How it works (simple steps):**  
  1. Detect failure or risk  
  2. Trigger appropriate failure mode pattern  
  3. Maintain continuity or safe state  
  4. Log and escalate if needed  

- **Where it sits in the AI stack:** Reliability + governance layer  
- **Related topics:** [[Retries]], [[Checkpointing]], [[Human interrupts]]

## 2. Mental Model
- **Analogy:**  
  Failure modes are like emergency exits in a building—graceful degradation = dim lights but safe exit, fallback = alternate staircase, redundancy = multiple exits, fail‑safe = fire doors closing.  

- **Diagram / flow:**
    - Failure → Graceful degradation → Reduced service
↘ Fallback → Alternate method
↘ Redundancy → Backup system
↘ Fail‑safe → Safe default state

- **The one thing to remember:** Failure modes = planned responses to breakdowns.  

- **Compare and contrast:**

| | Graceful Degradation | Fallback | Redundancy | Fail‑Safe |
|---|---|---|---|---|
| Purpose | Keep partial service | Switch method | Backup takeover | Default safe state |
| Trigger | Resource limits | Tool/service failure | System failure | Critical risk |
| Human role | None | Optional | None | Oversight optional |

## 6. ✅ Dos and ❌ Don’ts

| ✅ Do | ❌ Don’t |
|---|---|
| Define clear failure modes | Assume systems won’t fail |
| Document fallback paths | Ignore redundancy costs |
| Test fail‑safe states | Let unsafe defaults persist |

- **Common mistakes / misconceptions:**  
  1. Confusing reliability patterns (proactive) with failure modes (reactive).  
  2. Assuming redundancy alone solves all failures.  

- **Red flags in practice:** No defined fail‑safe state.
