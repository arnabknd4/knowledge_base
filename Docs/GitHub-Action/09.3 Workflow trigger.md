# Workflow Trigger in GitHub Actions

## 1. What is it?
- A **workflow trigger** defines the event that starts a GitHub Actions workflow.
- It specifies when and why a workflow should run (e.g., on code push, pull request, issue creation, or scheduled time).

## 2. Why do we need it?
- Ensures automation runs at the right time.
- Helps control CI/CD pipelines by linking workflows to repository activity.
- Provides flexibility to run workflows manually or on schedules.

## 3. Real World Example
```yaml
name: CI Pipeline
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
  schedule:
    - cron: '0 0 * * 0'
```
Runs on:

- Every push to main.
- Every pull request targeting main.
- Weekly (Sunday midnight) via cron schedule.

## 4. Exam Perspective
Key focus areas: on: keyword, supported events (push, pull_request, workflow_dispatch, schedule, issue, release).

Expect questions on how to configure multiple triggers and cron syntax.

## 5. Interview Questions and Answers
Q: What is a workflow trigger in GitHub Actions?
A: It defines the event that starts a workflow, such as a push, PR, or scheduled job.

Q: How do you manually trigger a workflow?
A: Using workflow_dispatch in the workflow file.

Q: What is the difference between push and pull_request triggers?
A: push runs when code is pushed to a branch, while pull_request runs when a PR is opened, updated, or merged.

## 6. Common Mistakes
Forgetting to specify branches → workflows run on all branches unexpectedly.

Misconfigured cron syntax → schedules don’t run as intended.

Using push instead of pull_request for PR validation.

Overlapping triggers causing duplicate workflow runs.

## 7. Mental Model
Think of workflow triggers as “switches”:

Each switch (event) turns on the pipeline.

You decide which switches (push, PR, schedule) should activate the workflow.

Without a switch, the pipeline never starts.
