# GITHUB_TOKEN

## 1. What is it?
- A **special, automatically generated secret** provided by GitHub for each workflow run.
- Used to authenticate with GitHub’s API without needing to create a personal access token.
- Scoped to the repository where the workflow runs.

## 2. Why do we need it?
- Provides secure, short‑lived authentication for workflows.
- Eliminates the need to manually manage credentials.
- Ensures CI/CD jobs can interact with GitHub (clone repos, push commits, create issues, etc.) safely.

## 3. Real World Example
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Use GITHUB_TOKEN
        run: gh api repos/${{ github.repository }}/issues \
             -F title='Automated issue' \
             -F body='Created by workflow'
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```
The workflow uses `secrets.GITHUB_TOKEN` to authenticate API calls.

## 4. Exam Perspective
- Understand default permissions (read/write depending on scope).
- Know how to configure permissions in workflow YAML:

```yaml
permissions:
  contents: read
  issues: write
```
Be aware of least privilege principle: restrict permissions to only what’s needed.

## 5. Interview Questions and Answers
Q: What is `GITHUB_TOKEN`?
A: A built‑in secret automatically created by GitHub for each workflow run, used for authentication.

Q: How is `GITHUB_TOKEN` different from a Personal Access Token (PAT)?
A: `GITHUB_TOKEN` is short‑lived and scoped to the repo; PATs are long‑lived and user‑managed.

Q: How do you restrict `GITHUB_TOKEN` permissions?
A: By defining permissions: in the workflow YAML.

## 6. Common Mistakes
- Forgetting to configure permissions → workflows may have more access than needed.
- Using `GITHUB_TOKEN` for cross‑repo actions without proper permissions.
- Assuming it works like a PAT (it doesn’t persist beyond the workflow run).
- Logging the token accidentally → security risk.

## 7. Mental Model
- Think of GITHUB_TOKEN as a “temporary visitor pass”:
- Issued automatically for each workflow run.
- Grants limited access to the repo.
- Expires when the workflow finishes.
