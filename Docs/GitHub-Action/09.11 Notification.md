# Notifications for Workflow Runs in GitHub Actions

## 1. What is it?
- Notifications inform users about the status of workflow runs (success, failure, or cancellation).
- They are typically delivered via **GitHub UI**, **email alerts**, or **integrations** (Slack, Teams, etc.).

## 2. Why do we need it?
- Keeps developers updated on pipeline results without constantly checking GitHub.
- Enables quick response to failures or deployment issues.
- Improves collaboration by alerting teams in real-time.

## 3. Real World Example
### Email Notifications (default)
- GitHub automatically sends emails when:
  - A workflow fails.
  - You are mentioned in a workflow run.
  - You are subscribed to repository notifications.

### Custom Notifications (Slack/Teams)
```yaml
jobs:
  notify:
    runs-on: ubuntu-latest
    steps:
      - name: Send Slack notification
        uses: slackapi/slack-github-action@v1.23.0
        with:
          payload: |
            {
              "text": "Workflow run ${{ github.workflow }} completed with status: ${{ job.status }}"
            }
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK }}
```
- Sends a Slack message with workflow status using a webhook.

## 4. Exam Perspective
- Key focus areas: default GitHub notifications, configuring custom alerts, using secrets for integrations.
- Expect questions on how to notify teams via Slack/Teams and how GitHub’s default notification system works.

## 5. Interview Questions and Answers
Q: How does GitHub notify users about workflow runs by default?
A: Through email alerts and GitHub UI notifications.

Q: How can you set up custom notifications?
A: By integrating with third-party services (Slack, Teams, Discord) using Actions and webhooks.

Q: Why are notifications important in CI/CD pipelines?
A: They ensure developers are immediately aware of failures or successes, enabling faster response.

## 6. Common Mistakes
- Forgetting to configure secrets for webhooks → notifications fail.
- Sending too many notifications → alert fatigue.
- Not filtering events → unnecessary alerts for minor runs.
- Relying only on email → slower team response compared to chat integrations.

## 7. Mental Model
- Think of notifications as “alarm bells”:
- Default GitHub notifications = personal alerts.
- Slack/Teams integrations = team-wide alarms.
- Without alarms, failures may go unnoticed until too late.

## 8. Revision Summary
- Notifications = alerts about workflow run status.
- Default: GitHub UI + email.
- Custom: Slack, Teams, Discord via webhooks.
- Essential for fast response and collaboration in CI/CD.
