# GitHub Actions vs GitHub Apps

## 1. What is it?
- **GitHub Actions**: A CI/CD automation feature inside GitHub that lets you build, test, and deploy code directly from your repository using workflows triggered by events.  
- **GitHub Apps**: Integrations that provide identity, permissions, and event delivery for external services or bots, enabling persistent interaction with GitHub’s API.

## 2. Why do we need it?
- **Actions**: Automate repository-centric tasks like testing, building, and deployment without external infrastructure.  
- **Apps**: Enable long-lived integrations across multiple repositories or organizations with fine-grained permissions.

## 3. Real World Example
- **Actions**: A team uses GitHub Actions to run unit tests and deploy a web app to Azure whenever code is pushed to `main`.  
- **Apps**: A monitoring bot built as a GitHub App listens to repository events and posts alerts to Slack when issues are created.

## 4. Exam Perspective
- Expect questions on differences between Actions and Apps, their use cases, and how they complement each other.  
- Actions are often tested in CI/CD contexts, while Apps are tested in integration/security contexts.

## 5. Interview Questions and Answers
- **Q:** What is the difference between GitHub Actions and GitHub Apps?  
  **A:** Actions automate workflows inside repositories, while Apps provide persistent integrations with identity and permissions for external services.  

- **Q:** When would you use GitHub Apps instead of Actions?  
  **A:** When you need a long-lived service or bot that interacts with multiple repositories or external systems.  

- **Q:** Can GitHub Actions and Apps work together?  
  **A:** Yes, Apps can trigger workflows or provide tokens/secrets that Actions use for secure automation.

## 6. Common Mistakes
- Confusing Apps with Actions — Apps are integrations, not workflow runners.  
- Using Actions for persistent tasks (better suited for Apps).  
- Misconfiguring permissions in Apps, leading to security risks.  
- Overloading Actions with external service logic instead of delegating to Apps.

## 7. Mental Model
Think of **Actions as “short-lived workers”** that run tasks when triggered, and **Apps as “long-lived bots”** that continuously interact with GitHub and external systems.

## 8. Revision Summary
- **Actions = CI/CD automation inside GitHub.**  
- **Apps = Persistent integrations with identity + permissions.**  
- Use Actions for repository workflows; use Apps for cross-repo or external integrations.  
- Enterprises often use both together for complete DevOps automation.
