# Actions Runner Controller (ARC)

## 1. What is it?
- An open‑source **Kubernetes controller** that manages GitHub Actions self‑hosted runners.
- Provides **dynamic provisioning, auto‑scaling, and lifecycle management** of runners inside Kubernetes clusters.

## 2. Why do we need it?
- Manual runner management is inefficient for enterprise workloads.
- ARC ensures:
  - **Elastic scaling** based on queued jobs.
  - **Cost efficiency** by shutting down idle runners.
  - **Centralized management** using Kubernetes CRDs.
  - **Multi‑repo/org support** for large organizations.

## 3. Real World Example
```yaml
apiVersion: actions.summerwind.dev/v1alpha1
kind: RunnerDeployment
metadata:
  name: my-runners
spec:
  template:
    spec:
      repository: my-org/my-repo
---
apiVersion: actions.summerwind.dev/v1alpha1
kind: HorizontalRunnerAutoscaler
metadata:
  name: my-runners-autoscaler
spec:
  scaleTargetRef:
    name: my-runners
  minReplicas: 1
  maxReplicas: 10
  metrics:
    - type: TotalQueuedAndInProgressWorkflowRuns
      repositoryNames:
        - my-org/my-repo
```
- Ensures 1–10 runners scale automatically based on workload demand.

## 4. Exam Perspective
- Know RunnerDeployment vs RunnerSet vs HRA.
- Understand YAML structure and runs-on usage.
- Be able to explain advantages over static runners.
- Scenario questions on scaling, cost optimization, and Kubernetes integration.

## 5. Interview Questions and Answers
Q: What problem does ARC solve?
A: It eliminates manual runner provisioning by auto‑scaling runners in Kubernetes.

Q: How does ARC integrate with GitHub Actions?
A: It listens to GitHub events and provisions runners dynamically via CRDs.

Q: Difference between RunnerDeployment and RunnerSet?
A: RunnerDeployment manages runners for a repo/org; RunnerSet is used for scale sets with broader scope.

## 6. Common Mistakes
- Misconfigured autoscaler metrics → runners don’t scale properly.
- Forgetting GitHub App authentication → ARC cannot register runners.
- Over‑provisioning → wasted Kubernetes resources.
- Assuming ARC supports all GitHub Enterprise Server versions (compatibility varies).

## 7. Mental Model
- Think of ARC as a “Kubernetes operator for GitHub runners”:
- GitHub jobs = workload demand.
- ARC = orchestrator ensuring enough Pods (runners) exist.
- Kubernetes = infrastructure layer providing elasticity.

## 8. Revision Summary
- ARC = Kubernetes controller for GitHub Actions runners.
- Provides auto‑scaling, lifecycle management, and cost optimization.
- Uses CRDs: Runner, RunnerDeployment, RunnerSet, HRA.
- Best for enterprise CI/CD pipelines with variable workloads.
