# Types of GitHub Actions

## 1. Container Actions
### What is it?
- Container Actions run inside a Docker container.
- They allow developers to package dependencies and environments together.

### Why do we need it?
- Useful when the Action requires specific tools or libraries not available in GitHub-hosted runners.
- Ensures consistent execution across environments.

### Real World Example
- A security scanning Action packaged in a Docker container with custom tools.
- Runs inside the container to analyze code for vulnerabilities.

### Exam Perspective
- Focus on Dockerfile usage, container packaging, and portability.
- Know how to define `runs.using: docker` in `action.yml`.

### Interview Q&A
- **Q:** When should you use Container Actions?  
  **A:** When your Action requires custom dependencies or isolated environments.  

### Common Mistakes
- Forgetting to include required dependencies in the Docker image.
- Large container images slowing down execution.

### Mental Model
Think of Container Actions as **“sealed toolboxes”** — everything needed is inside the container.

### Revision Summary
- Runs inside Docker.
- Best for custom environments and dependencies.
- Defined with `runs.using: docker`.

---

## 2. JavaScript Actions
### What is it?
- JavaScript Actions run directly on GitHub-hosted runners using Node.js.
- They are lightweight and fast compared to container-based Actions.

### Why do we need it?
- Ideal for Actions that require quick execution without heavy dependencies.
- Easy to share and maintain in GitHub Marketplace.

### Real World Example
- A JavaScript Action that posts a comment on a pull request when tests fail.

### Exam Perspective
- Focus on `runs.using: node12` or `node16`.
- Understand how to bundle dependencies with `npm` or `yarn`.

### Interview Q&A
- **Q:** Why use JavaScript Actions over Container Actions?  
  **A:** They are faster, simpler, and don’t require Docker setup.  

### Common Mistakes
- Forgetting to bundle `node_modules` before publishing.
- Using unsupported Node.js versions.

### Mental Model
Think of JavaScript Actions as **“lightweight scripts”** — quick, efficient, and easy to run.

### Revision Summary
- Runs with Node.js.
- Best for lightweight automation.
- Defined with `runs.using: node12` or `node16`.

---

## 3. Composite Actions
### What is it?
- Composite Actions combine multiple workflow steps into a single reusable Action.
- They don’t require Docker or Node.js — just YAML definitions.

### Why do we need it?
- Useful for reusing common workflow logic across repositories.
- Simplifies pipelines by grouping steps.

### Real World Example
- A Composite Action that sets up environment variables, installs dependencies, and runs tests.

### Exam Perspective
- Focus on `runs.using: composite`.
- Know how to define multiple steps inside `action.yml`.

### Interview Q&A
- **Q:** What is the advantage of Composite Actions?  
  **A:** They allow reuse of workflow logic without requiring code or containers.  

### Common Mistakes
- Forgetting that Composite Actions cannot run scripts directly — they only orchestrate steps.
- Overcomplicating workflows instead of keeping them modular.

### Mental Model
Think of Composite Actions as **“workflow templates”** — reusable sets of steps.

### Revision Summary
- Runs multiple steps defined in YAML.
- Best for reusing workflow logic.
- Defined with `runs.using: composite`.

# Comparison: Container vs JavaScript vs Composite Actions

| Feature              | **Container Actions**                          | **JavaScript Actions**                       | **Composite Actions**                        |
|----------------------|-----------------------------------------------|----------------------------------------------|----------------------------------------------|
| **Execution**        | Runs inside a Docker container                 | Runs directly on GitHub-hosted runners using Node.js | Runs multiple workflow steps defined in YAML |
| **Dependencies**     | Custom dependencies packaged in Docker image   | Uses Node.js ecosystem (`npm`, `yarn`)       | No external dependencies, just YAML steps    |
| **Performance**      | Slower (container build/startup overhead)      | Faster (lightweight scripts)                 | Fast (no runtime overhead)                   |
| **Use Cases**        | Security scans, custom environments, isolated tools | Lightweight automation, PR comments, quick scripts | Reusable workflow logic across repos         |
| **Definition**       | `runs.using: docker`                          | `runs.using: node12` or `node16`             | `runs.using: composite`                      |
| **Portability**      | Highly portable (same container everywhere)    | Limited to Node.js runtime                   | Portable YAML logic, but no runtime execution|
| **Best For**         | Complex tasks needing custom environments      | Quick, lightweight tasks                     | Sharing workflow templates                   |
| **Common Mistakes**  | Large images, missing dependencies             | Forgetting to bundle `node_modules`          | Overcomplicating steps, forgetting YAML limits|

## Revision Summary
- **Container Actions** → Docker-based, best for custom environments.  
- **JavaScript Actions** → Node.js-based, best for lightweight automation.  
- **Composite Actions** → YAML-based, best for reusable workflow logic.
