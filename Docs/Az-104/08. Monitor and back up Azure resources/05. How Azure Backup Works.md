# 🔧 How Azure Backup Works

## 1. Backup Policy Creation
- Admin defines **backup schedule** (daily/weekly) and **retention period**.  
- Policies are applied at scale across workloads.  

## 2. Snapshot & Data Capture
- Azure Backup takes **snapshots** of VMs, files, folders, or databases.  
- Consistency levels:  
  - **App‑consistent** (using VSS or scripts).  
  - **File‑consistent** (no app writes during snapshot).  
  - **Crash‑consistent** (default if app consistency fails).  

## 3. Storage in Recovery Services Vault
- Backups are stored in a **Recovery Services vault**.  
- Vault provides centralized management and monitoring.  
- Storage redundancy options:  
  - **LRS** (Locally Redundant Storage).  
  - **GRS** (Geo‑Redundant Storage).  

## 4. Security & Protection
- Data encrypted in transit and at rest (AES‑256).  
- **Soft delete** prevents accidental/malicious deletion.  
- RBAC ensures only authorized users manage backups.  

## 5. Restore Operations
- Recovery points allow **granular restore** (files, disks, databases, or full workloads).  
- Restore can be initiated via **Portal, CLI, or PowerShell**.  
- Minimal impact on production workloads.  

---

# 🏢 Real‑World Example
A retail company protects its SQL databases and VMs with Azure Backup. Policies enforce daily backups, retention for 90 days, and GRS ensures resilience against regional outages.  

---

# 🧠 Mental Model
Think of Azure Backup as a **“time machine vault”**: every snapshot is a checkpoint stored securely, ready to rewind workloads when needed.

# 📌 Revision Summary
- Policy‑driven backup schedules + retention  
- Snapshots ensure app/file/crash consistency  
- Recovery Services vault = secure storage  
- Redundancy options: LRS vs GRS  
- Security: encryption + soft delete + RBAC  
- Restore granularity: files → workloads
