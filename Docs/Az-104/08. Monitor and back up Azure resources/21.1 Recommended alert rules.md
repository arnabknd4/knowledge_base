# Recommended Alert Rules for VM Monitoring

## 1. Host VM
- **CPU > 80% sustained for 15 min**
- **Memory > 75% sustained for 15 min**
- **Disk latency > 20 ms**
- **Network throughput drops below baseline**

## 2. Guest Operating System (OS)
- **High % of failed logins (security baseline)**
- **Critical Windows Event IDs (e.g., 6008 unexpected shutdown)**
- **Linux syslog errors (kernel panic, OOM events)**
- **Patch compliance drift alerts**

## 3. Client Workloads
- **Service availability check (SQL/IIS/Apache)**
- **Transaction latency > SLA threshold**
- **Queue length > defined threshold**
- **Workload‑specific extension alerts (SQL deadlocks, IIS 503 errors)**

## 4. Applications
- **Application Insights availability test failures**
- **Request duration > SLA (e.g., >2s for API calls)**
- **Error rate > 5% sustained**
- **Dependency call failures (DB, external APIs)**

## 5. Best Practices
- Use **Action Groups** for routing alerts (Email, SMS, ITSM).
- Apply **dynamic thresholds** where workloads vary.
- Configure **severity levels** (Critical vs Informational).
- Avoid **alert fatigue** by tuning frequency and scope.
- Archive logs to **cheaper storage tiers** for compliance.

## 6. Revision Summary
- Host: CPU, memory, disk, network
- Guest OS: login failures, event logs, patch drift
- Workloads: service availability, latency, queue length
- Applications: SLA breaches, error rates, dependency failures
- Action Groups + dynamic thresholds = effective alerting
