# Azure Cloud Shell – How It Works

## 1. What is it?
A browser-based shell environment (Bash or PowerShell) hosted in Azure with preinstalled tools like `az CLI`, Terraform, Git, and `kubectl`.

## 2. How It Works (Mechanics)
- **Launch** → Access via Azure Portal, CLI, or shell.azure.com.  
- **Identity** → Authenticates using your Azure AD account; permissions flow from RBAC.  
- **Environment** → Runs in a temporary container managed by Microsoft.  
- **Persistent Storage** → First launch auto-creates a 5 GB Azure Files share, mounted as `clouddrive`.  
- **Tools** → Preloaded with Azure CLI, PowerShell modules, Git, Terraform, Kubernetes tools, etc.  
- **Session Lifecycle** → Container is ephemeral; when closed, only files in `clouddrive` persist.  

## 3. Core Exam Focus
- Launch Cloud Shell and switch between Bash/PowerShell.  
- Persistent storage setup (Azure Files).  
- Preinstalled tools usage (az CLI, Terraform, Git).  
- Authentication tied to Azure AD identity.  

## 4. Real‑World Use Case
Architects use Cloud Shell to run Terraform scripts and az CLI commands across multiple subscriptions without configuring local environments.

## 5. Interview Lens
- How does Cloud Shell differ from local CLI installation?  
- What’s the trade‑off between Cloud Shell and DevOps pipelines for automation?  
- How would you secure Cloud Shell usage in a multi‑tenant environment?  

## 6. Common Mistakes
- Assuming Cloud Shell has unlimited storage (only 5 GB persistent).  
- Forgetting to mount storage → session data lost.  
- Treating Cloud Shell as a replacement for CI/CD (it’s not).  

## 7. Mental Model
Think of Cloud Shell as a **“portable toolbox in the cloud”** — always available, preloaded, tied to your identity.

## 8. Revision Summary
- Browser-based shell (Bash/PowerShell).  
- Ephemeral container + persistent 5 GB Azure Files.  
- Preinstalled tools (az CLI, Terraform, Git, kubectl).  
- Auth via Azure AD identity.  
- Exam trap: Cloud Shell ≠ full automation platform.
