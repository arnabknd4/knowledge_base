# Adding Resources to an ARM Template

## 1. What is it?
The **resources** section in an ARM template defines the actual Azure services (VMs, storage, VNets, etc.) you want to deploy or update.

## 2. Why do we need it?
- Core of the template — without resources, nothing is deployed.  
- Ensures declarative, repeatable infrastructure provisioning.  
- Supports dependencies (`dependsOn`) for correct deployment order.  

## 3. Structure of Resources Section
Each resource definition includes:
- **type** → Azure resource type (e.g., `Microsoft.Storage/storageAccounts`).  
- **apiVersion** → API version for the resource.  
- **name** → Resource name (can use parameters/variables).  
- **location** → Region where resource is deployed.  
- **properties** → Configuration details.  
- **dependsOn** → Dependencies on other resources.  

## 4. Supporting Code Snippet (Add Storage Account Resource)
```json
"resources": [
  {
    "type": "Microsoft.Storage/storageAccounts",
    "apiVersion": "2022-09-01",
    "name": "[parameters('storageName')]",
    "location": "[resourceGroup().location]",
    "sku": {
      "name": "Standard_LRS"
    },
    "kind": "StorageV2",
    "properties": {}
  }
]
```
## 5. Adding Multiple Resources Example
``` json
"resources": [
  {
    "type": "Microsoft.Network/virtualNetworks",
    "apiVersion": "2022-09-01",
    "name": "[parameters('vnetName')]",
    "location": "[resourceGroup().location]",
    "properties": {
      "addressSpace": {
        "addressPrefixes": [ "10.0.0.0/16" ]
      }
    }
  },
  {
    "type": "Microsoft.Compute/virtualMachines",
    "apiVersion": "2022-09-01",
    "name": "[parameters('vmName')]",
    "location": "[resourceGroup().location]",
    "dependsOn": [
      "[resourceId('Microsoft.Network/virtualNetworks', parameters('vnetName'))]"
    ],
    "properties": {
      "hardwareProfile": {
        "vmSize": "Standard_DS1_v2"
      }
    }
  }
]
```
## 6. Real‑World Use Case
Architects define VNets, subnets, NSGs, and VMs in one template to ensure consistent environment setup across dev, test, and prod.

## 7. Interview Lens
- How do you enforce dependencies between resources?
- What’s the difference between dependsOn and implicit dependencies?
- How would you modularize large templates with linked templates?

## 8. Common Mistakes
- Forgetting dependsOn → deployment failures.
- Hardcoding names instead of using parameters.
- Using outdated API versions.

## 9. Mental Model
Think of resources as the actual buildings in your blueprint — parameters are inputs, variables are shortcuts, but resources are the structures that get built.

## 10. Revision Summary
- Resources = actual Azure services.
- Required fields: type, apiVersion, name, location, properties.
- Use dependsOn for order.
- Parameterize names/locations for flexibility.
- Exam trap: missing dependencies → failed deployments.
