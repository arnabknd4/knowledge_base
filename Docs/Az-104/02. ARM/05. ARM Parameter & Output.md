# ARM Template – Parameters and Outputs

## 1. Parameters
### What are they?
- **Optional section** in ARM templates.  
- Allow you to pass values at deployment time (via parameter file, CLI, or portal).  
- Increase flexibility and reusability of templates.

### Structure
```json
"parameters": {
  "storageName": {
    "type": "string",
    "defaultValue": "mystorageacct",
    "metadata": {
      "description": "Name of the storage account"
    }
  },
  "location": {
    "type": "string",
    "defaultValue": "eastus"
  }
}
```
Usage Example
```json
"name": "[parameters('storageName')]",
"location": "[parameters('location')]"
```
### The allowed types of parameters are:
- string
- secureString
- integers
- boolean
- object
- secureObject
- array

## 2. Outputs
- What are they?
  - Optional section in ARM templates.
  - Return values after deployment (e.g., resource IDs, connection strings).
  - Useful for chaining deployments or passing values to scripts/pipelines.

Structure
```json
"outputs": {
  "storageEndpoint": {
    "type": "string",
    "value": "[reference(parameters('storageName')).primaryEndpoints.blob]"
  },
  "resourceId": {
    "type": "string",
    "value": "[resourceId('Microsoft.Storage/storageAccounts', parameters('storageName'))]"
  }
}
```
# ARM Template – Output Elements

| Element       | Description                                                                 |
|---------------|-----------------------------------------------------------------------------|
| output-name   | Must be a valid JavaScript identifier.                                      |
| condition     | *(Optional)* A Boolean value that indicates whether this output value is returned. When true, the value is included in the output for the deployment. When false, the output value is skipped. Default = true. |
| type          | The type of the output value (e.g., string, int, bool, object, array).      |
| value         | *(Optional)* A template language expression to be evaluated and returned as an output value. |
| copy          | *(Optional)* Used to return more than one value for an output.              |


## 3. Real‑World Use Case
- Parameters let architects deploy the same template across dev/test/prod with different names, sizes, or regions.
- Outputs provide connection strings or resource IDs to downstream automation (e.g., pipelines, linked templates).

## 4. Interview Lens
- Why use parameters instead of hardcoding values?
- How do outputs help in multi‑stage deployments?
- What’s the difference between variables and parameters?

## 5. Common Mistakes
- Hardcoding values → reduces reusability.
- Forgetting to define metadata → poor documentation.
- Not using outputs → harder to chain deployments.

## 6. Mental Model
- Think of parameters as inputs to your blueprint (like knobs you can adjust), and outputs as the report you get after construction (IDs, endpoints, results).

## 7. Revision Summary
- Parameters = deployment-time inputs.
- Outputs = values returned post-deployment.
- Both are optional but critical for flexibility and automation.
- Parameters improve reusability; outputs enable chaining.
- Exam trap: confusing variables (internal) with parameters (external).
